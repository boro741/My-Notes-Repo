1DynamoDB Overview

Relational databases like RDS trade off horizontal scaling for the power to join data, aggregate it, and ask complex questions. DynamoDB trades the other way: it sacrifices joins and aggregations to achieve near-unlimited scale — millions of requests per second, trillions of items, hundreds of terabytes, all managed for you.

💡 New word DynamoDB is a fully managed, serverless NoSQL database from AWS. It stores data as key-value pairs and documents, automatically replicates across availability zones, and scales horizontally without you having to manage hardware or databases.
💡 New word NoSQL means "not only SQL" — a database that doesn't use relational tables and SQL queries. Instead of rows and columns, NoSQL databases store flexible documents, key-value pairs, or graphs. No joins.

The core trade-off

Relational databases give you rich querying (joins, aggregations) but scale mostly vertically; NoSQL databases like DynamoDB trade that querying power for near-unlimited horizontal scale.

Relational databases are built for asking "give me all orders from this month grouped by customer." DynamoDB is built for asking "give me this customer's profile right now" — and answering billions of times per second. You can still ask complex questions, but you have to design your data model upfront to support the specific questions you'll ask. That's the fundamental shift.

🏭 In real companies Amazon (the retail giant and also AWS's parent) built DynamoDB to power their own shopping cart, user profiles, and product catalogs. When Thanksgiving rolls around and traffic spikes 10x, the system keeps running without anyone provisioning extra capacity. Companies like Airbnb, Netflix, and Lyft rely on DynamoDB for the same reason — it scales to match their actual traffic, not a guessed capacity.

Core basics

A DynamoDB table stores items (like rows), each identified by a primary key. The primary key comes in two flavors: a simple partition key (hash key), or a partition key plus sort key (hash + range). Items can have any number of attributes (columns), which you can add or remove anytime — there's no schema lock-in. Each item is capped at 400 KB.

💡 New word Partition key determines which internal server ("partition") holds an item, and must be unique across all items with that key. Design it so that load spreads evenly — a key like "region" with only 4 values would concentrate all data in 4 partitions, causing one to get hot.
💡 New word Sort key (optional) is a second part of the primary key. The combination (partition key + sort key) must be unique. This lets you store multiple items under one partition key — like many posts from one user, sorted by date.
A simple partition key must be unique per item; a partition+sort key combo lets multiple items share a partition key (e.g. many games per user) as long as the pair is unique.

DynamoDB supports scalar data types (string, number, binary, boolean, null), document types (lists, maps), and sets (string, number, or binary sets). It replicates synchronously across three availability zones in a region, so you never lose data. There's no "create a database" step — you just create tables.

Partition key design is critical: pick a key with high cardinality (many unique values) that distributes evenly. A voting app with partition key = "Candidate" (only 2 values) will create two "hot" partitions handling all the traffic. Later on we'll see how to fix this.

2Basics & Hands-On

Creating a DynamoDB table is straightforward: you pick a name, choose your partition key (and optionally a sort key), decide whether the table is Standard or Standard-IA (for infrequently accessed data), and pick a capacity mode.

Capacity modes

ModeHow it worksBest for
ProvisionedYou specify RCU/WCU upfront (can auto-scale)Predictable, steady workloads
On-demandScales automatically with trafficUnpredictable or spiky workloads

You can switch between modes once every 24 hours. Provisioned is cheaper if you know your traffic pattern. On-demand is roughly 2.5× more expensive but requires zero capacity planning. Most new projects start On-demand, then switch to Provisioned once the pattern is clear.

The flexibility trap

One huge difference from traditional databases: you can add a new attribute to one item without touching the rest. Other items simply won't have that attribute (it reads as missing/null). This flexibility is powerful, but it's also a trap — without discipline, your data model can become chaotic. Team consensus on attribute names and structure matters more than in SQL.

A practical rule: use a schema validation library or layer in your application to enforce consistent shapes, even though DynamoDB itself doesn't require it.

3WCU & RCU — Throughput

💡 New word WCU (Write Capacity Unit) measures write throughput. 1 WCU = 1 write per second for an item up to 1 KB. Larger items cost more.
💡 New word RCU (Read Capacity Unit) measures read throughput. 1 RCU = 1 strongly consistent read per second (or 2 eventually consistent reads) for an item up to 4 KB.

The math

Always round up item size to the next KB (for writes) or 4 KB (for reads). If you're writing 10 items per second, each 2 KB, that's 10 items × (2 KB rounded up = 2) = 20 WCU. If you're reading 16 items per second eventually consistent, each 12 KB (rounds to 16 KB = 4 × 4 KB), that's (16 ÷ 2) × 4 = 32 RCU.

The confusing part for many: RCU and WCU are split evenly across partitions. If you provision 1000 WCU, that's split across your internal partitions. If one partition key gets all the traffic, that one partition hits its share of the budget and starts throttling — even though the table's total capacity looks fine. This is called a "hot partition," and we'll see how to detect and fix it later.

Consistency trade-off

Writes replicate across internal servers; reading right after a write can hit an un-replicated copy (eventually consistent) unless you explicitly request a strongly consistent read (set ConsistentRead: true).

When you read an item right after writing it, you might hit a server that hasn't fully replicated the write yet. Asking for eventually consistent reads (the default, cheaper) accepts this risk. Asking for strongly consistent reads (setting ConsistentRead: true) adds latency and costs 2× the RCU, but guarantees you see the latest version.

🏭 In real companies Most applications use eventually consistent reads for the vast majority of requests — the latency and cost savings are worth the rare race conditions. Only critical reads (like "am I out of stock?") use strong consistency.

Auto scaling

In provisioned mode, you can enable auto scaling: set a minimum and maximum capacity, plus a target utilization percentage. DynamoDB adjusts RCU/WCU automatically to hit that target. It's similar to EC2 Auto Scaling — if you hit 80% capacity, it scales up.

4Basic Operations & APIs

Every DynamoDB interaction goes through a small set of core operations. Some read, some write, some batch multiple items together.

OperationAPIUse case
Write (full replace)PutItemOverwrite or create an item by key
Write (partial)UpdateItemModify specific attributes; also for atomic counters
Read oneGetItemFetch by primary key
Read by key rangeQueryFind items matching partition key (and optionally sort key range)
Read everythingScanExpensive — reads the entire table, filters client-side
Delete oneDeleteItemRemove by primary key
Delete whole tableDeleteTableFar faster than scanning + deleting each item

The Query operation is optimized: it uses the partition key to jump straight to the right partition, then searches within it using the sort key. Scan is not optimized — it reads everything and filters after, so it's expensive. Avoid it in production unless you're rebuilding an index or doing a one-time migration.

Batch operations

BatchGetItem fetches up to 100 items (across one or more tables) in one request. BatchWriteItem creates or deletes up to 25 items (no updates in a batch, though). Both are capped at 16 MB. If any items fail, they come back in UnprocessedItems — retry them with exponential backoff.

PartiQL — SQL syntax for DynamoDB

If your team knows SQL, PartiQL lets you write SELECT/INSERT/UPDATE/DELETE queries against DynamoDB without learning the native API syntax. Under the hood it's the same operations — you're just using SQL-like syntax. No joins, though. You can use it from the console, the CLI, the SDK, or NoSQL Workbench.

5Conditional, Concurrent & Atomic Writes

What happens when two clients try to update the same item at the same time? DynamoDB has three answers, depending on what you ask for.

Without conditions

Two clients update the same item. Both "succeed," but whichever write lands second silently overwrites the first. Data loss, silently. Avoid this.

With conditions (optimistic locking)

You attach a condition to your write: "only update if the version attribute equals 3." Whichever update lands first, the other fails because the condition no longer holds. The client that failed knows to fetch the latest version and retry. It's called optimistic locking — you assume conflicts are rare, and only handle them when they actually happen.

💡 New word Condition expressions are rules you attach to writes (Put, Update, Delete) to decide whether they happen. Common building blocks: attribute_exists, attribute_not_exists, contains, begins_with, BETWEEN, IN, size().

Atomic writes

Two clients each increment a counter by some amount. Without special handling, one might overwrite the other. But if you use the SET counter = counter + :amount syntax (which DynamoDB evaluates server-side), both increments apply correctly. The final value reflects both.

Filter vs. condition expressions: a filter expression applies to reads (Query/Scan results) after they're fetched, reducing the size of what's returned. A condition expression applies to writes (Put/Update/Delete) and decides whether the write happens at all. Filter expressions consume RCU whether they match or not; condition expressions are free.

6Indexes: GSI & LSI

Your main table is indexed by the partition key you picked at creation time. But what if you need to query by a different key? That's where indexes come in. There are two types, and they behave very differently.

💡 New word LSI (Local Secondary Index) lets you query the same partition key with a different sort key. It must be created at table creation time, shares the base table's capacity, and is limited to 10 GB per partition key value.
💡 New word GSI (Global Secondary Index) lets you query by an entirely different partition (and optionally sort) key. It can be created or deleted anytime, has its own provisioned RCU/WCU, and has no size limit.
LSIGSI
Partition keySame as base tableCan be different
Sort keyDifferent (alternative)Can be different
CreatedOnly at table creationAnytime
CapacityShares base table RCU/WCUOwn RCU/WCU
Throttling behaviorNo special handlingIf GSI throttles, the base table throttles too
An LSI just gives you an alternative sort key on the same partition key; a GSI gives you a whole different partition (and optionally sort) key, with its own dedicated capacity.

An LSI is convenient but inflexible — you have to know at table creation time that you'll want to query by (old_partition_key, new_sort_key). A GSI is more flexible — you can add it months later — but costs more and has trickier throttling behavior. If a query hits the GSI and the GSI is overloaded, the whole table gets throttled, not just the GSI.

🏭 In real companies Most teams start with one main table and one or two GSIs. When you realize you need to query differently, you add a GSI instead of redesigning the main table. The cost is worth it for the flexibility.

7PartiQL

PartiQL is a SQL-like syntax for DynamoDB. If your team is more familiar with SQL than the DynamoDB API, this is a friendlier way to interact with the database.

You can use it from the console (there's a PartiQL editor), the CLI, NoSQL Workbench, or any SDK. Common examples:

SELECT * FROM users WHERE user_id = '123'
INSERT INTO users VALUE {'user_id': '123', 'name': 'Alice'}
UPDATE users SET #name = 'Bob' WHERE user_id = '123'
DELETE FROM users WHERE user_id = '123'

Under the hood, PartiQL is translated to the same API calls we discussed earlier (Query, PutItem, UpdateItem, DeleteItem). It's just syntax. No joins, no aggregations — same limitations as the core DynamoDB model.

8DAX — The Cache Layer

Imagine a table storing user profiles. Every single app request reads the same few profiles — celebrities, popular accounts — over and over. Those reads are hitting DynamoDB billions of times per day, burning through RCU. What if you cached the answers?

💡 New word DAX (DynamoDB Accelerator) is a fully managed, in-memory cache for DynamoDB. It caches queries, scans, and individual items with microsecond latency. Your app talks to DAX instead of DynamoDB directly — if the item is cached, DAX answers instantly; if not, DAX fetches it from DynamoDB, caches it, and returns it.
The app talks to the DAX cluster instead of DynamoDB directly; DAX serves cached results (default 5-minute TTL) or fetches and caches on a miss.

When to use it

DAX is perfect for "hot" items — popular profiles, trending posts, frequently read settings. It's overkill for data accessed once or twice. A typical DAX cluster has 3 nodes across availability zones (for production HA) and a default 5-minute TTL. Items expire from the cache automatically, ensuring freshness.

The magic part: DAX is API-compatible with DynamoDB. You change your endpoint from DynamoDB to DAX, and the rest of your code stays the same. No rewrite needed.

DAX is not the same as ElastiCache. DAX caches DynamoDB objects and queries. ElastiCache is a general-purpose in-memory store; you'd use it for caching the results of your own application-side aggregation or computation.

9DynamoDB Streams

Every time an item in a table is created, updated, or deleted, you might want to react to that change — send a welcome email, update analytics, replicate to another database, feed a search engine. DynamoDB Streams capture these changes for 24 hours, making them available to downstream consumers.

💡 New word DynamoDB Streams is an ordered list of item-level modifications on a table. Each modification (create, update, delete) becomes a record in the stream, visible for 24 hours.

How streams work

Every create/update/delete lands in the stream; Lambda (via an Event Source Mapping) or a Kinesis Client Library app can consume it in near real-time.

Enable streams on a table and choose a view type: KEYS_ONLY (just the key), NEW_IMAGE (the new version of the item), OLD_IMAGE (the old version), or NEW_AND_OLD_IMAGES (both). Lambda functions can automatically trigger on stream records via event source mappings. Or a Kinesis app can consume them for real-time processing. The stream is made of shards, like Kinesis — AWS manages shard provisioning automatically.

Streams enable powerful patterns: welcome emails on new signups, derivative tables (denormalized copies for specific query patterns), real-time analytics, or Global Tables (multi-region replication).

Important: streams are not retroactive. You only get events for changes that happen after you enable the stream. You can't replay history from before you turned it on.

10TTL — Auto-Expiring Data

Session data, temporary tokens, or any item with an expiration date can be tedious to manage manually. You'd have to run a job to scan and delete old items — expensive in terms of RCU/WCU.

💡 New word TTL (Time To Live) in DynamoDB automatically deletes items when a specified Unix epoch timestamp passes. It's free — no WCU consumed — because DynamoDB does the cleanup internally.

How it works

You pick one numeric attribute (e.g., expires_at) and tell DynamoDB "this is my TTL attribute." DynamoDB periodically scans for expired items and deletes them — usually within a day, sometimes longer. Expired-but-not-yet-deleted items still show up in reads, queries, and scans, so filter client-side if that matters. When TTL deletes an item, it also deletes it from any LSI/GSI, and the delete appears in the DynamoDB Stream (if enabled).

🏭 In real companies Every session storage system uses TTL. Every API key expiration. Every rate-limit bucket. DynamoDB's TTL is often the first operational burden it removes — you stop having to write cleanup jobs.

11CLI & Pagination

When you use the CLI or SDK, you often need to control how much data comes back at once. Query and Scan can return thousands of items; you probably want to process them in pages.

OptionPurpose
--page-sizeBreak one logical request into smaller API calls behind the scenes (avoids timeouts) while still returning everything
--max-itemsLimit how many items are shown per command output
--starting-token + NextTokenContinue retrieving the next page after a previous command
--projection-expressionOnly fetch specific attributes (saves RCU)
--filter-expressionFilter results client-side (consumes RCU whether matches or not)

--page-size and --max-items solve different problems. Page-size keeps individual API calls small (preventing timeouts) while returning all results. Max-items caps how much you see, requiring you to use NextToken to fetch more. If you're scanning a million items, page-size prevents your single command from timing out; max-items lets you display 50 at a time on a web page.

12Transactions

Imagine a banking system. You need to debit one account and credit another — atomically. If the first write succeeds and the second fails, money disappears. Or imagine a game where a player buys an item for gold. You need to deduct their gold AND add the item to their inventory, all at once or not at all.

💡 New word Transactions in DynamoDB give you all-or-nothing semantics across multiple items or tables. Either all writes succeed, or none do. Full ACID guarantees.

Cost and limitations

Transactions cost 2× the RCU/WCU of an equivalent non-transactional operation. DynamoDB has to prepare the transaction, then commit it, and that double work is billed. Example: 3 transactional writes/sec × 5 KB = 3 × 5 × 2 = 30 WCU (versus 15 WCU if they weren't transactional).

Two transaction APIs: TransactGetItems (read multiple items consistently) and TransactWriteItems (write multiple items atomically). You can include up to 25 items per transaction.

Use sparingly: transactions are more expensive and slower than normal operations. Only use them when atomicity is actually required (payments, inventory, gaming). Most reads and writes don't need them.

13Session State Storage

When a user logs into a web app, the server stores their session (authentication token, preferences, cart, etc.) somewhere — not in memory on a single server, because the next request might hit a different server. Where should it go?

Most new teams pick DynamoDB or ElastiCache. DynamoDB if you want zero operational overhead and automatic scaling. ElastiCache if you have a dedicated team to manage it and you need microsecond latency for in-memory operations.

14Write Sharding

A voting app needs to count votes for candidates. You use partition key = "candidate_name" (either "Alice" or "Bob"). The problem: all data lands in just two partitions. Millions of votes all hitting the same two partition keys means two hot partitions throttling.

Write sharding solves this by artificially spreading writes across many more partition keys. Instead of "CandidateA", use "CandidateA#1", "CandidateA#2", ..., "CandidateA#10". When you write a vote, randomly pick one shard. When you count votes for Alice, you query all 10 shards and sum the results.

Appending a random or hashed suffix to a low-cardinality partition key artificially spreads writes across many more partitions, avoiding hot-partition throttling.
💡 New word Write sharding adds a random or hashed suffix to a low-cardinality partition key, spreading writes across many more partitions so no single partition gets hot. Cost: more queries needed to read (you must query all shards).
You can also use a distributed hash function to generate the shard ID deterministically, rather than randomly picking one. The goal is just better distribution.

15Patterns with S3

Pattern 1: Large objects in S3, metadata in DynamoDB

DynamoDB items max out at 400 KB. If you're storing large files (images, videos, PDFs), put them in S3 and keep only a pointer (the S3 key or URL) plus metadata in DynamoDB. When a user requests a file, your app reads metadata from DynamoDB (fast), then fetches the actual object from S3.

Pattern 2: Index S3 objects in DynamoDB

S3 doesn't have a way to ask "show me all images uploaded by this user in the last month" — it's just a flat store of objects. But you can: when an object is uploaded to S3, an event notification triggers a Lambda function that writes the object's metadata (size, timestamp, uploader, etc.) to a DynamoDB table. Now you can query DynamoDB to find objects by timestamp, owner, or type, then fetch the actual objects from S3 by their key.

This pattern works because DynamoDB is optimized for queryability and metadata storage, while S3 is optimized for durability and large objects. Use each for what it's good at.

16Table Operations: Cleanup & Copy

Clearing a table

Never scan a table and delete each item individually — that's slow and expensive. Instead, use DeleteTable and recreate it. Far faster, and if you've designed your data model to be ephemeral (which you should for testing), no data loss.

Backup and restore

AWS Backup can back up a source table and restore it to the same account or a different one. The restore creates a new table with the same schema and data. Perfect for disaster recovery or cloning.

Migration and ETL

AWS Glue can export data from DynamoDB to other services, or import data in. It generates a script to read the source and write the destination. For custom logic, write your own code using Scan + BatchWriteItem.

17Security & Fine-Grained Access

DynamoDB integrates with IAM, KMS, VPC endpoints, and other AWS security services. But there's one pattern that stands out: giving end-user applications direct access to DynamoDB without a backend server.

Federated access for clients

Clients authenticate via an identity provider, exchange that identity for temporary AWS credentials tied to a restricted IAM role — never long-lived IAM users handed out to end users.

A mobile app needs to read and write a user's own data without a backend service. You use Cognito or another identity provider to authenticate the user. After authentication, they get temporary AWS credentials tied to an IAM role. That role's policy uses a condition on dynamodb:LeadingKeys to restrict the user to reading/writing only rows where the partition key equals their own identity.

💡 New word Point-in-Time Recovery (PITR) automatically backs up your table and lets you restore to any point in the last 35 days. No manual snapshots needed, and zero performance impact.

Other security features

  • Encryption at rest (KMS) and in transit (TLS/HTTPS).
  • VPC Endpoints keep DynamoDB traffic off the public internet.
  • Global Tables: multi-region, multi-active replication (requires Streams enabled).
  • DynamoDB Local: run a local simulation for testing without hitting the real service.
  • AWS DMS: migrate data to/from DynamoDB (e.g., Oracle → DynamoDB, or DynamoDB → S3).
🏭 In real companies Many apps use Cognito + DynamoDB for the full identity + storage stack. Mobile apps especially: authenticate with Cognito, get a role with fine-grained DynamoDB access, and never need a backend server — pure serverless.

📋 Cheat Sheet

Core Concepts

  • Partition key: determine item distribution. High cardinality, even spread. Must be unique (for partition-key-only tables) or part of unique combo (with sort key).
  • Sort key: optional, enables range queries and multiple items per partition key.
  • WCU/RCU math: 1 WCU = 1 write/sec up to 1KB; 1 RCU = 1 strong read/sec (or 2 eventual) up to 4KB. Always round up.
  • Hot partitions: uneven load across partitions causes throttling even if table capacity is fine. Fix with write sharding or better key distribution.
  • LSI: alternate sort key, same partition key, created at table creation, shares capacity.
  • GSI: different partition/sort key, created anytime, own capacity. Throttling on GSI throttles the whole table.
  • Transactions: 2× cost, full ACID across items. Use only for atomicity-critical operations.
  • DAX: microsecond cache for hot items. ElastiCache for app-side computed results.
  • Streams: 24-hour event log. Not retroactive. Triggers Lambda, feeds Global Tables.
  • TTL: free auto-expiration. Deletes are not instant, still visible until garbage-collected.

Decision Tree

  • Need to query by an alternate sort key on the same partition? → LSI
  • Need to query by a completely different key? → GSI
  • Hot partition from low-cardinality keys? → Write sharding
  • Slow reads on popular items? → DAX
  • React to table changes in real-time? → Streams + Lambda
  • Auto-expire old data? → TTL
  • All-or-nothing writes across items? → Transactions
  • Files bigger than 400 KB? → S3 + DynamoDB metadata

The Big Picture

DynamoDB gives you unlimited scale by constraining how you query: no joins, no aggregations, all needed data in one row. Design your partition key to distribute load evenly. Understand RCU/WCU math so you provision correctly. Use the right extension (LSI, GSI, DAX, Streams, TTL, Transactions) for each pattern. Master these basics, and DynamoDB stops being mystifying and becomes a straightforward choice for any serverless application that needs a data store.
