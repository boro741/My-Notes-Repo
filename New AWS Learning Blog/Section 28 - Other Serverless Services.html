1Step Functions Overview

You've got a Lambda here, a database write there, maybe an ECS task over there. When you need those steps to happen in order — or conditionally, or in parallel — someone has to glue them together. AWS Step Functions is that glue. It is a service that lets you build workflows — sequences of actions that can branch, retry, wait, and handle errors — all without writing any code to wire them together.

💡 New word State machine — a formal model where you have distinct states and rules for transitioning from one state to the next. In Step Functions, each state does one bit of work (invoke a Lambda, write to DynamoDB, wait 5 seconds), and the JSON definition tells Step Functions how to move from state to state.

You define a workflow in JSON using the Amazon States Language (ASL). That JSON becomes a visual diagram you can see in the console. When you run the workflow, Step Functions executes it step by step, with a full history of every transition, every input and output, and every retry or error catch. If something fails, you know exactly where and why.

💡 New word Orchestration — coordinating multiple pieces of work so they happen in the right order, under the right conditions, and with the right error handling. Step Functions orchestrates AWS services and your own tasks.

The main state types

A workflow is built from states. Here are the most important ones:

State TypeWhat it does
TaskPerforms one unit of work — invoke Lambda, run an ECS task, write to DynamoDB, publish to SNS.
ChoiceTests a condition and branches to different next states based on the result.
WaitPauses execution for a fixed duration or until a specific date/time.
PassDoes no real work, just passes input through (or injects fixed data) to the next state.
ParallelStarts two or more branches running at the same time, then waits for all to finish.
MapLoops over a list, running the same steps for each item.
Fail / SucceedEnds the workflow with a failure or success status.

A typical workflow starts with a Task (invoke a Lambda), then branches on a Choice (was it successful?). If yes, do more work. If no, fall back to error handling. Then wait, do something in parallel, map over results, and finally succeed or fail.

A simple state machine: Start → Task → Choice branches to either Wait+Task (yes) or End (no).

How workflows start and what happens inside

A workflow can be triggered by:

  • An SDK or API call (your app requests it).
  • An event in EventBridge (time-based schedule, or another AWS service).
  • Manually, from the Step Functions console (for testing).

Once a workflow runs, Step Functions assigns it an execution ID, and every state transition is logged. If a task fails, you see the error. If a retry happens, you see how many times and what the backoff was. This history stays in the console for 90 days, or forever in CloudWatch Logs.

🏭 In real companies Step Functions orchestrates order fulfillment (receive order → check inventory → charge payment → ship → confirm). It orchestrates ETL pipelines (extract from S3 → transform in Lambda → load to data warehouse). It orchestrates approval workflows (submit request → wait for human approval → update database). The common thread: multiple steps that may fail independently, and you need visibility and control flow without writing custom orchestration code.

2Step Functions — Hello World Hands On

The easiest way to build a state machine is with Workflow Studio, a visual drag-and-drop editor built into the AWS console. You drag Lambda functions, choices, waits, and other blocks onto a canvas. Studio generates the equivalent ASL JSON automatically — the visual diagram and the JSON are two views of the exact same thing.

The console ships with a Hello World template that demonstrates the key patterns. It starts by setting variables in a Pass state (just injecting data, no real work), then branches on a Choice (is this a Hello World example?), waits if true, runs a Parallel block to do multiple things at once, and finally either succeeds or fails depending on the branch.

Hands-on walkthrough

  1. Open Step Functions → Create state machine → choose Design in Studio.
  2. Studio offers templates. Select Hello World to start with a pre-built example.
  3. You see the visual flow: Pass (set variables) → Choice (branch) → Wait or Fail → end.
  4. On the right side, the Definition panel shows the generated ASL JSON. Edit variables in the Pass state to change what the workflow does.
  5. Click Create to save the state machine, then Execute to run it.
  6. In the execution view, step through each state. You see input, output, duration, variables, and any errors.
Try this: Change IsHelloWorldExample from true to false, save the definition, and run it again. The Choice state now sends execution down the Fail branch instead — you'll see the execution status marked as Failed with your custom error message.

3Step Functions — Invoke Lambda Hands On

The most common Task state is one that invokes a Lambda function. You define a simple Lambda (say, one that appends "Hello" and a name together), then wire it into a state machine that invokes it and branches based on the output.

Building the pieces

  1. Create a Lambda function that reads a who key from its input and returns Hello, <who>!. Test it in the Lambda console first with a sample input like {"who":"Stephane"}.
  2. Back in Step Functions, create a new state machine. Use the visual editor or paste ASL JSON that includes a Task state.
  3. In the Task state, set the Resource field to the Lambda's ARN (Amazon Resource Name) — you can paste it from the Lambda console.
  4. Add a Choice state after the Lambda that branches based on the output. For example, if the output contains "Stephane", take the success branch; otherwise, fail.
  5. Step Functions automatically creates an execution role with permission to invoke that Lambda.

Now when you run the workflow with input {"who":"Stephane"}, the Lambda is invoked, its output is "Hello, Stephane!", the Choice sees "Stephane" in the result, and execution takes the success path. If you run it with {"who":"John"}, the output doesn't contain "Stephane", and execution fails with your custom error message.

🏭 In real companies This exact pattern — Lambda → Choice → downstream actions — is the skeleton of real workflows. A data-processing pipeline might do: read a file name (Lambda) → check if it's valid (Choice) → transform it (Lambda) → store the result (DynamoDB Task). Each Lambda is kept small and focused; the state machine coordinates.

4Step Functions — Error Handling

In a real workflow, one of your tasks will fail. A Lambda throws an exception. A database write times out. A third-party API is temporarily down. Step Functions has Retry and Catch blocks that live right in the state machine JSON — you define error handling once, declaratively, and it applies without touching the task code.

💡 New word Retry — automatically run the task again if it fails, with configurable delays and backoff. Catch — if retries are exhausted, route to a fallback state (e.g., send an alert email).

Retry rules

Each task can have a list of Retry rules, evaluated top-to-bottom. A rule specifies:

  • ErrorEquals — which error type(s) this rule matches (e.g., States.Timeout, States.TaskFailed, or a custom error name).
  • IntervalSeconds — how long to wait before the first retry (e.g., 1 second).
  • BackoffRate — multiplier for the wait time each retry (e.g., 2 means 1s, 2s, 4s, 8s...).
  • MaxAttempts — how many times to retry (default 3; 0 means never retry). After all attempts fail, control falls through to Catch.

Catch rules

If all retries for a task are exhausted, Catch rules decide what happens next. Each rule specifies:

  • ErrorEquals — which errors this rule catches.
  • Next — the state to transition to.
  • ResultPath — where to merge the error details (e.g., $.error). The input {"foo":"bar"} becomes {"foo":"bar", "error": {...}}, so the fallback state can inspect what went wrong.
Task fails → Retry with exponential backoff → once retries are exhausted, Catch routes to a fallback state → continue execution.

Predefined error types

Error TypeMeaning
States.ALLMatches any error.
States.TimeoutTask ran longer than its timeout, or an activity heartbeat was not received.
States.TaskFailedThe task threw an uncaught exception.
States.PermissionsThe execution role lacks permission to run the task.
Key insight: Error handling is outside your Lambda or application code. A Lambda stays simple — it just does its job and throws on error. The state machine handles retries, backoff, and fallbacks. If you need to change retry logic, you edit the JSON, not your code, and no redeployment happens.

5Wait For Task Token

Sometimes a task can't complete right away. You need approval from a human. You need a third-party system to finish something. You need another AWS service to do work that takes hours. You can't just invoke a Lambda and wait for a response — because there's no response coming immediately.

💡 New word Task token — a unique ID that Step Functions generates for a task. You send the token to an external system or queue, and later, when the work is done, that external system calls back with the token to tell Step Functions the task is complete.

To enable this, append .waitForTaskToken to the task's Resource field. Step Functions will pause the execution and generate a unique token. You send that token (along with the work description) to a queue like SQS, or to a topic like SNS, or directly to a webhook. Later, when the work is done, the external actor calls SendTaskSuccess or SendTaskFailure with that token, and Step Functions resumes.

Step Functions pauses and sends a task with a unique token to SQS. A worker processes it, then calls SendTaskSuccess with that token to resume the workflow.
🏭 In real companies Approval workflows use this pattern: a workflow sends a task token + request details to a notification queue, a manager's app polls that queue and displays the request, the manager clicks Approve or Reject, and the app calls SendTaskSuccess with the manager's choice, resuming the workflow. Because the workflow is paused waiting for the token, there's no need for the manager to complete the task in any particular time — it can wait hours.

6Activity Tasks

Task tokens are push-based — Step Functions pushes a task to a queue, and something picks it up. Activity Tasks are pull-based — a worker directly polls Step Functions asking "do you have any work for me?"

💡 New word Activity worker — a piece of software (running on EC2, in a container, on a mobile device, anywhere) that repeatedly calls the GetActivityTask API to ask Step Functions for work. If work is available, it gets it, does it, then calls SendTaskSuccess or SendTaskFailure with the result.

How Activity Tasks work

  1. Create an Activity resource in Step Functions (just a name, like MyWorkerActivity).
  2. In the state machine, use an Activity state pointing to that activity's ARN.
  3. Your worker runs on EC2 (or anywhere) and calls GetActivityTask in a loop.
  4. When the state machine enters that Activity state, Step Functions puts the work on an internal queue. The worker's next GetActivityTask call returns the work (input data + a task token).
  5. The worker processes the data and calls SendTaskSuccess (with output) or SendTaskFailure (with an error), using the task token.
  6. Step Functions resumes the workflow with the output.

Timeouts and heartbeats

An Activity state can have a TimeoutSeconds setting — how long the task can run before Step Functions considers it failed. But if the work takes longer than a few minutes, you can send heartbeats. Your worker calls SendHeartbeat periodically, which tells Step Functions "I'm still alive, still working." With regular heartbeats, an Activity Task can run for up to one year.

Activity worker polls GetActivityTask. Step Functions returns work + token. Worker processes, then sends back result + token.
🏭 In real companies Activity Tasks are used for work that can't be done in a Lambda (it's too long-running, or requires special libraries/tools). A video transcoding pipeline might have Activity Tasks — a fleet of EC2 instances polls for "transcode this video" tasks, does the work locally (which can take hours), periodically sends heartbeats, then reports success when done. The state machine waits, and once all videos are done, the workflow continues to the next step.

7Standard vs Express Workflows

Step Functions comes in three flavors, and picking the right one matters for cost, latency, and how errors are handled.

Standard (default)Express AsyncExpress Sync
Max durationUp to 1 yearUp to 5 minutesUp to 5 minutes
Execution guaranteeExactly-onceAt-least-onceAt-most-once
Throughput~2,000 exec/sec100,000+ exec/sec100,000+ exec/sec
Best forNon-idempotent work (payments, order processing)High-volume fire-and-forget (IoT, streaming)Synchronous API response (Lambda invoked via API Gateway)

Standard — exactly-once, durable

Every task in a Standard workflow is executed exactly once. If a step fails, Step Functions retries it per your rules. If a step succeeds, it never runs again. Executions can run for up to a year, making it suitable for long-running business processes. Cost is per state transition, so a 100-step workflow costs more than a 5-step one — but you're paying for durability and correctness.

Express Async — at-least-once, fast and cheap

Express Async workflows fire and forget. You trigger a workflow and immediately get a response — you don't wait for the workflow to finish. Internally, the workflow runs asynchronously, and if a step fails, it may be retried automatically, which means the same task could run twice. Because "at least once" means your workflow steps must be idempotent — doing them twice shouldn't cause problems. Cost is per execution, per-minute duration, and memory used, not per state transition.

💡 New word Idempotent — a property where doing something twice has the same effect as doing it once. Writing a record with a unique ID is idempotent (the second write overwrites the first with the same data). Incrementing a counter is not idempotent (it increments twice).

Express Sync — at-most-once, synchronous

Express Sync workflows are synchronous. You trigger a workflow and wait for the result (just like a function call). If any step fails, the entire workflow fails with no automatic retries — it's up to your application to retry. Cost is per execution, duration, and memory, like Express Async.

Express Sync gotcha: "at-most-once" means a failed step is not retried by Step Functions. Your application code must decide whether to retry. This is different from Standard, where retries are built into the state machine itself.
🏭 In real companies Standard workflows orchestrate business processes (payment, order fulfillment, approval). Express Async handles IoT sensor ingestion (millions of events, each kicking off a quick workflow, no need to wait). Express Sync is wrapped inside API Gateway + Lambda for on-demand synchronous APIs — you want the workflow to run fast and return the result to the client.

8AppSync Overview

Building a REST API means writing many endpoints. GET /users returns all fields of all users, even if the client only needs names. GET /users/{id} returns another set of fields. GET /users/{id}/posts requires a separate endpoint. Every time a frontend wants a different shape of data, you write a new endpoint or add a new query parameter. GraphQL solves this: the client specifies exactly which fields it wants, and the server returns exactly that.

💡 New word GraphQL — a query language where the client specifies a shape of data, and the server returns exactly that shape. Instead of fixed endpoints, there's one GraphQL endpoint, and the client sends a query document that says "I want the User with id 5, and their name and email, and the titles of their posts."

AWS AppSync is a managed GraphQL service. You define a GraphQL schema (the shape of your data: User has a name and email, Post has a title and content). Then you define resolvers — instructions for how to fetch each field. A resolver can query DynamoDB, call Lambda, fetch from a REST API, or read from Aurora. When a client sends a GraphQL query, AppSync routes each field to its resolver and combines the results.

Client sends one GraphQL query to AppSync. Resolvers fetch from multiple backends (DynamoDB, Aurora, Lambda) and assemble the result.
💡 New word Resolver — a mapping from a GraphQL field to a backend operation. For example, "to resolve User.name, query DynamoDB for the user and return the name field."
💡 New word Data source — a connection to a backend system (DynamoDB table, Aurora database, Lambda function, HTTP endpoint) that AppSync uses to fetch data.

Authorization and security

AppSync supports four authorization modes. You can mix and match them on a single API:

ModeUse for
API_KEYPublic access or testing. Keys are short-lived (default 7 days) and easy to rotate.
AWS_IAMAWS users and roles, including cross-account access.
AMAZON_COGNITO_USER_POOLApp users authenticated via Cognito. Can federate to social logins (Google, Facebook).
OPENID_CONNECTExternal OIDC providers like Auth0.
🏭 In real companies A mobile app uses Cognito for user sign-in and AppSync for the API. A third-party integration uses an API key or IAM role to read data. A backend service uses an IAM role. All on the same AppSync API, with different authorization rules for each.

Real-time data and offline support

AppSync integrates WebSocket connections for real-time subscriptions — clients can subscribe to changes, and AppSync pushes updates when data changes. For mobile apps, AppSync's DataStore feature (part of the Amplify ecosystem) lets offline-first apps work locally and automatically sync to the cloud when connectivity returns.

9AppSync Hands On

Creating your first GraphQL API

  1. Go to AppSync → Create API. Choose Design from scratch (as opposed to building from a DynamoDB table).
  2. Name the API and choose an authorization type (API key is fine for testing).
  3. Once created, you're in the AppSync console. The left sidebar shows Schema (the GraphQL schema), Data sources (backends), and Resolvers.

Auto-generating a schema and table

  1. In the Schema panel, you can write GraphQL schema by hand, or use the quick-create feature. Click Create resources and define a type (e.g., Student with fields id, name, age, certified).
  2. AppSync auto-generates CRUD (Create, Read, Update, Delete) mutations and queries, and automatically creates a DynamoDB table to back the type.
  3. Under Data sources, you now see the DynamoDB table. Under Resolvers, you see the auto-generated mappings (e.g., "to resolve Query.getStudent, query DynamoDB for the student").

Testing queries

  1. In the left sidebar, find Queries (also called the GraphQL Explorer). It's a playground where you write GraphQL queries and see results.
  2. Try a mutation: mutation { createStudent(input: {name: "Alice", age: 20, certified: true}) { id name age } }. This creates a student in DynamoDB and returns the id, name, and age.
  3. Try a query: query { listStudents { items { id name } } }. This lists all students, returning only id and name (you didn't ask for age).

Every mutation and query you run is logged, and the results show in real time. If there's an error in your GraphQL (wrong field name, wrong type), AppSync rejects it immediately.

Caching: AppSync can cache full requests, cache individual resolver outputs, or cache nothing. You configure this per resolver or for the entire API. This helps reduce database load for repeated queries.

Cleanup

To delete an AppSync API, go to Settings → Delete API, type the API name to confirm. The DynamoDB table it created is separate and needs to be deleted manually from the DynamoDB console.

10AWS Amplify

You now know how to build workflows (Step Functions) and GraphQL APIs (AppSync). But what if you want to build a full app — frontend UI, backend, database, authentication, hosting — all at once, fast? AWS Amplify is a toolkit that bundles the common building blocks into one CLI and visual studio.

💡 New word Amplify is actually several tools packaged together: a CLI (command line tool), a Studio (visual builder in the console), JavaScript/TypeScript libraries for your app code, and hosting. Think of it as a scaffolding tool that quickly wires Cognito, AppSync, DynamoDB, S3, and Lambda together.

Instead of manually creating a Cognito User Pool, then an AppSync API, then a DynamoDB table, then setting up hosting — you run amplify add auth (which provisions Cognito), amplify add api (which provisions AppSync + DynamoDB), and amplify add hosting (which sets up CI/CD). The Amplify Libraries then give your React/Vue/Angular/iOS/Android app pre-built functions to sign in, fetch data, upload files, etc.

The Amplify stack

  • Amplify CLI — commands like amplify add auth, amplify add api, amplify add storage (S3). Each command provisions AWS resources and updates your app's configuration.
  • Amplify Studio — a visual console inside the AWS console where you can design your data model (AppSync schema), build UI components, and configure auth/hosting without CLI commands.
  • Amplify Libraries — JavaScript/Python/Swift/Kotlin packages you import into your app. They wrap AWS service calls into simpler functions (e.g., await signIn(email, password) instead of manual Cognito calls).
  • Amplify Hosting — connects to GitHub, auto-builds and deploys your app on every push. Includes pull request previews, custom domains, and monitoring.

What Amplify sets up

amplify add auth creates a Cognito User Pool, with sign-up, sign-in, email verification, MFA options, and social login (Google, Facebook, Apple) all pre-wired.

amplify add api creates an AppSync GraphQL API backed by DynamoDB. It also enables DataStore, which gives you offline data access — your app can write to the local database, and when connectivity returns, DataStore syncs with AppSync automatically.

amplify add storage creates an S3 bucket for file uploads.

amplify add hosting connects your GitHub repo. Amplify watches for pushes, runs your build steps, and deploys the output to CloudFront.

🏭 In real companies Amplify is used by teams building mobile and web apps fast. Instead of spending two weeks hand-wiring Cognito, AppSync, and Lambda — they run Amplify CLI commands, get a working auth/API/storage system in minutes, and focus on app logic. For teams using AWS, it beats third-party platforms like Firebase for customization and integration with other AWS services.

11AWS Amplify Hands On

Deploy an Amplify-hosted app

  1. Go to Amplify → Create app → Host web app.
  2. Choose GitHub as your repository provider. Authorize Amplify to access your GitHub account.
  3. Select your repository and branch (or let Amplify create a sample app repo for you).
  4. Accept the default build settings (Amplify detects your framework: React, Vue, etc.).
  5. Create a service role if you don't have one, and click Save and deploy.
  6. Amplify begins the deployment. Under CloudFormation, you can watch nested stacks being created — one for the hosting infrastructure, one for build settings, etc.
  7. Once complete, the app is live at a URL like https://main.abc123.amplifyapp.com.

What you get in the console

After deployment, you see several sections:

  • Deployments — a log of every deployment (one per GitHub push) with build logs and status.
  • Data Manager — if you've enabled DataStore via amplify add api, you can view and edit records directly (useful for seeding data or inspection).
  • User management — shows users from your Cognito User Pool, their sign-in status, and auth settings.
  • Storage — view files uploaded to S3 via your app.
  • Functions — backend Lambda functions you've added.
  • UI Library — pre-built components (authentication flows, data forms) that you drag into your app, with Figma-to-React code generation.
Automatic deployments: Every time you push to the connected GitHub branch, Amplify automatically builds and deploys your app. No manual steps needed.

Cleanup

To delete everything, go to App settings → General → Delete app. Type "delete" to confirm. This removes the app from Amplify but not the GitHub repository — you can delete that separately if you want.

To clean up all AWS resources created by Amplify CLI (locally), run amplify delete in your project folder.

📋 Cheat Sheet

Step Functions at a glance

  • State machine — a JSON document that orchestrates a workflow. States do work (Task), branch (Choice), wait, run in parallel, or loop (Map).
  • Task — invokes Lambda, DynamoDB, ECS, or another AWS service. Most common state type.
  • Choice — branches based on a condition (is the result > 100?).
  • Retry / Catch — automatically retry on error with backoff; route to a fallback state once retries are exhausted.
  • Standard — exactly-once execution, up to 1 year, for non-idempotent work (payments). Priced per state transition.
  • Express Async — at-least-once, fire-and-forget, high throughput. For IoT and streaming. Priced per execution + duration.
  • Express Sync — at-most-once, waits for result. Good for synchronous API responses. Priced per execution + duration.
  • Task token — pause a workflow and wait for an external system to call back (useful for approvals, long-running work).
  • Activity — a worker polls Step Functions for work, does it, then reports back (pull-based, unlike task tokens which are push-based).

AppSync and Amplify at a glance

  • GraphQL — a query language where the client specifies exactly which fields it wants. One endpoint, many query shapes.
  • AppSync — a managed GraphQL API service. Define a schema, wire up resolvers (mappings to DynamoDB, Lambda, Aurora, HTTP), and handle auth (API key, IAM, Cognito, OIDC).
  • Resolver — a mapping from a GraphQL field to a backend data source.
  • DataStore — AppSync + offline sync + local database. Clients write locally, AppSync syncs to the cloud when online.
  • Amplify — a toolkit bundling CLI, Studio, Libraries, and Hosting. Commands like amplify add auth, amplify add api, amplify add hosting provision full-stack resources.
  • Amplify Hosting — auto-deploys to CloudFront on every GitHub push. Includes pull request previews, custom domains, and end-to-end testing with Cypress.
