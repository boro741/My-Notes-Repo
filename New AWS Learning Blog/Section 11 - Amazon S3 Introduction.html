1What S3 Does (And Why It Matters)

Most applications need somewhere safe to store files that doesn't disappear when a server restarts. S3 solves this problem at planetary scale — from tiny startup projects to companies storing exabytes of data.

💡 New word S3 stands for Simple Storage Service. It is AWS's infinitely scalable, durable file storage system that you can reach from anywhere in the world, and it secures your data with nearly unbreakable durability.

Why companies use S3

Database backups that need to survive a data center failure. Videos and images that serve millions of users. Archives of old records that must legally exist forever. Log files from thousands of servers. Website static files (HTML, CSS, images) served directly without a web server running. All of these live in S3.

🏭 In real companies Netflix streams movies by pulling video files from S3. Shopify stores product images there. Millions of databases back up to S3 every night. If S3 went down, a significant portion of the internet would notice within hours. This is why AWS invests enormous engineering effort into making it bulletproof.

The core guarantee: 11 Nines durability

S3 promises that over a year, you have a 99.999999999% chance your data stays intact. That sounds like marketing math, but it means AWS expects to lose one object per million billion objects stored per year. Real companies bet their compliance, their customer data, and their legal requirements on this number.

💡 New word Durability is the probability that a piece of data will not be lost due to disk failures, bit rot, or other hardware disasters. S3's 11 Nines durability means AWS stores your data across multiple physical disks and facilities automatically, so one failing hard drive never touches your files.

Three things every S3 setup needs

First, you need a place to store files — that is a bucket. Second, you need to decide who can read or change those files — that is access control. Third, you need to know whether you are choosing between regular fast access, or cheaper cold storage for files you rarely touch. The rest is just details.

2Buckets and Objects

💡 New word Bucket is a top-level container in S3, kind of like a folder at the root level of a hard drive. Every file you store lives inside exactly one bucket. Bucket names must be globally unique across all AWS accounts worldwide.

When you create a bucket, you pick an AWS Region — a physical geography where AWS has data centers, like Mumbai (ap-south-1) or Northern Virginia (us-east-1). Your bucket physically lives there, but the AWS console shows all your buckets together no matter which region each one sits in.

💡 New word Region is a geographic area where AWS runs data centers. S3 buckets are created in one region, and replication can send copies to a different region for disaster recovery.

Bucket naming

Names must use only lowercase letters, numbers, and hyphens. No uppercase, no underscores, and the name cannot look like an IP address. Pick something clear and descriptive like my-company-backups-prod or project-alpha-assets-2024. Names are globally unique, so if someone else already took it, you need a different one.

Objects — the actual files

An object is simply a file stored inside a bucket. Unlike folders on your computer, S3 does not actually have nested directories — it is a flat key-value store. But the console shows slashes as if they were folders, so you can organize visually.

💡 New word Object is a file stored in S3. Every object has a unique Key, which is its full path name (e.g., images/2024/vacation.jpg). The Key consists of a Prefix (the path part, like images/2024) and an Object Name (the filename, like vacation.jpg).

Object size limits and metadata

A single S3 object can be up to 50 terabytes. Files larger than 5 GB must use Multi-part Upload, which splits them into chunks and uploads them in parallel — much faster than uploading one giant file at once.

Each object can also carry metadata (key-value pairs describing what the file is), up to 10 tags (labels you can use for security rules or cost tracking), and a Version ID if you enable versioning on the bucket.

Best practice: Use descriptive object keys and tags from day one. They make it far easier to find, organize, and apply security rules to files months later when your bucket has thousands of objects.

3Creating and Uploading — Hands-On

Step 1: Create a bucket

  1. Open the AWS Management Console and go to S3.
  2. Click Create bucket and give it a globally unique name.
  3. Choose your Region (e.g., eu-west-1 for Ireland).
  4. Leave Block Public Access enabled — this is the default safe choice.
  5. AWS automatically encrypts objects at rest using keys it manages, so encryption is already on.
  6. Click Create.

Step 2: Upload a file

  1. Inside your bucket, click Upload.
  2. Select a file from your computer (like photo.jpg).
  3. Click Upload and the file appears in your bucket as an object.

Viewing and downloading

Click any object in the console to see its details, including its Object URL (the address where it lives on S3). Copying that URL into a browser and opening it gives an error — AccessDenied — because S3 buckets are private by default. Only users or services with permission can access files.

The console's Open button works because AWS generates a temporary signed URL just for you. This is a time-limited pass that lets you view the file without changing bucket permissions.

💡 New word Pre-signed URL is a temporary, time-limited link that AWS generates to let someone view or download a private S3 file without needing permanent access. They expire after a set time (default is 15 minutes) and are perfect for sharing files securely.
Common mistake: Copying the raw Object URL and sharing it does not work because the bucket is private. Use pre-signed URLs for temporary sharing, or change the bucket policy if the file needs to be permanently public.

4Making Files Public with Bucket Policies

By default, your S3 bucket is locked down tight — nobody can see or download anything without explicit permission. Sometimes you need to flip that. A website's logo, a public dataset, a photo gallery. That is where bucket policies come in.

💡 New word Bucket Policy is a JSON permission document attached directly to a bucket. It controls who can do what to any object inside — read, write, delete, etc. It is the same JSON format you saw in the IAM section, but it lives on the bucket itself, not on a user.

How bucket policies work

A bucket policy has the same basic structure as an IAM policy: an Effect (Allow or Deny), a Principal (who this applies to — often * for the entire public internet), an Action (which S3 operations), and a Resource (which objects or buckets).

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::my-bucket/*"
    }
  ]
}

This policy says: anyone, anywhere, can read (GetObject) any file inside my-bucket. That is how you make a bucket public.

💡 New word ARN (Amazon Resource Name) is AWS's way of naming every single resource uniquely. For S3, arn:aws:s3:::my-bucket/* means "all objects in my-bucket". ARNs let policies target exactly what they need to, nothing more.

Steps to make files public

  1. Go to your bucket and click the Permissions tab.
  2. Scroll down to Block Public Access and click Edit.
  3. Uncheck Block all public access and confirm the warning. (This is scary on purpose — AWS wants you to be intentional.)
  4. Go to Bucket Policy and paste a policy that allows public read access, or use the AWS Policy Generator tool to build one with checkboxes.
  5. Save, and now the raw Object URL works in any browser.
🏭 In real companies Publicly readable S3 buckets are a leading cause of data breaches — not because S3 is broken, but because someone forgets to set up the policy correctly and accidentally exposes millions of documents. Every major cloud provider has horror stories. The solution: use bucket policies carefully, audit them regularly, and keep Block Public Access on until you truly need to turn it off.
Gotcha: An IAM user can access an S3 object if either their IAM policy allows it OR the bucket policy allows it — unless there is an explicit Deny somewhere. Combining IAM policies, bucket policies, and the Block Public Access setting can get confusing fast. When in doubt, test the access from a browser in incognito mode as if you were a stranger.

5Static Website Hosting

You do not need a web server to run a website. If your site is just HTML, CSS, JavaScript, and images — no backend code that changes on each request — S3 can host it directly.

How it works

You upload your website files (index.html, styles, images) to S3. Then you tell S3 which file to serve when someone visits the bucket's website endpoint. S3 generates a special website URL, and anyone who visits gets your pages. No servers to patch, no uptime to worry about, no EC2 instances to pay for.

Steps to enable static hosting

  1. Upload your website files to a bucket (at least an index.html).
  2. Go to the bucket, click Properties, and scroll to Static website hosting.
  3. Click Edit, select Enable, and type index.html as the index document.
  4. Optionally, set an error page (usually error.html) for 404s.
  5. Save. AWS gives you a unique website endpoint URL like my-bucket.s3-website-eu-west-1.amazonaws.com.

Public read permissions

The bucket must have a public read policy (or at least allow the public to GetObject on all files). Otherwise, visitors get a 403 Forbidden error.

💡 New word Public bucket means the bucket policy (or an ACL) allows anyone on the internet to read objects without signing in. Opposite of private, which is the default.
Production pattern: Many companies use S3 static hosting for their main marketing site, then use CloudFront (a content delivery network) in front of it to cache files globally and add HTTPS. This keeps bandwidth costs low and makes the site lightning-fast worldwide.

6Versioning — Never Lose a File Again

You upload a file called report.pdf. A week later, you upload a new version by accident. The old one is gone. Or someone deletes a critical file and nobody notices for three weeks. Versioning prevents both nightmares.

💡 New word Versioning in S3 keeps every old copy of a file whenever it is re-uploaded or changed. You can see the history, restore old versions, or permanently delete specific versions. It is turned off by default and must be enabled on the bucket.

How versioning works

Once enabled, every file upload creates a new Version ID. S3 stores all of them. When you delete a file, S3 does not actually remove it — instead, it adds a Delete Marker on top, like stacking a sticky note saying "Hidden" on a document. The old file is still there; it just looks deleted in the console.

If you remove the Delete Marker, the file appears again. But if you delete a specific Version ID, that version is gone for good — permanent removal, no recovery.

Important: Versioning increases storage costs because every version takes up space. If you have a large file that you update weekly, enabling versioning means you are paying for every copy. Plan accordingly.
🏭 Best practice in production Most production systems enable versioning on any bucket that holds critical data — databases, backups, compliance records. It costs a bit extra in storage, but it turns accidental deletions from disasters into recoverable mistakes. When a developer accidentally runs rm -rf / on a production backup in S3, versioning is what saves the day.

Enabling versioning

  1. Go to the bucket, click Properties, scroll to Versioning.
  2. Click Edit and select Enable.
  3. Save. Versioning is now on for all future uploads.
Good news: Versioning can only be enabled or suspended, never turned off (because AWS wants to preserve history). If you suspend it, new uploads stop getting version IDs, but old versions stay.

7Replication — Backup Across Regions

Your bucket is in Mumbai, and Mumbai's entire data center goes offline. If you have not replicated your data anywhere else, you are in trouble. S3 Replication automatically copies new files to another bucket, letting you survive disasters.

💡 New word Replication in S3 is automatic copying of objects from a source bucket to a destination bucket. It happens asynchronously (in the background) and requires versioning to be enabled on both buckets.

Two types

Cross-Region Replication (CRR) copies files to a bucket in a different Region — say, Mumbai to Northern Virginia. This survives regional disasters and lets users in different parts of the world access files from a bucket closer to them.

Same-Region Replication (SRR) copies files to a bucket in the same Region, usually in a different account. This is useful for log aggregation or testing — replicating live production data to a staging account so you can safely practice disaster recovery.

💡 New word CRR (Cross-Region Replication) copies files across AWS Regions automatically. SRR (Same-Region Replication) copies them within the same Region. Both require versioning enabled.

Critical replication rules

Only newly uploaded objects replicate automatically. If you have 1 million existing files in the source bucket, they do not instantly appear in the destination — you must run S3 Batch Replication separately.

When you delete a specific version ID (permanent deletion), it does not replicate. This is on purpose — AWS does not want a mistake in one region to cascade and delete the backup too.

Replication does not chain. If Bucket A replicates to Bucket B, and Bucket B replicates to Bucket C, files from Bucket A do not automatically reach Bucket C. You need to set up replication from A to C separately.

🏭 Real-world pattern Netflix uses Cross-Region Replication to ensure video files are available in multiple regions globally. If one region fails, playback continues from the replica. Companies backing up databases to S3 often replicate to a different region daily — so even if AWS loses an entire region (extremely rare, but it has happened), backups survive.

Enabling replication

  1. Ensure versioning is on in both source and destination buckets.
  2. In the source bucket, go to Management → Replication rules.
  3. Click Create replication rule, give it a name, and choose which objects to replicate (usually all).
  4. Pick the destination bucket and region.
  5. Create an IAM role that allows S3 to replicate (AWS creates a default one).
  6. Save. Replication is now active for new uploads.

8Storage Classes — Balancing Cost and Speed

You do not pay the same price for every file in S3. Files you access daily are stored on fast, expensive drives. Files you touch once a year can move to cheap cold storage. S3 Storage Classes let you choose the trade-off that fits your workload.

💡 New word Storage Class is S3's tier system for balancing cost, retrieval speed, and availability. Standard is fast but pricier. Glacier is cheap but slow to retrieve.

All classes share the same 11-Nines durability

The critical point: whether you choose Standard or Glacier, your data will not be lost. Durability is identical. The differences are in how fast you can access it and how much it costs.

Choosing the right class

If you access a file daily, S3 Standard. If it is a weekly backup, Standard-IA. If it is a compliance record you might need in a few years but hope you never do, Glacier Deep Archive. When you are not sure how often you will access something, use Intelligent-Tiering — it watches your access patterns and moves files between tiers automatically.

💡 New word Glacier is S3's ultra-cheap archive tier. Files take hours to retrieve. Use it for backups, compliance records, and data you legally must keep but hope never to access again.
🏭 Real cost example A 1 TB database backup in S3 Standard costs about $23 per month. In Standard-IA, around $12. In Glacier Deep Archive, around $4. If you keep one year of daily backups (365 TB), the difference between Standard and Glacier is the cost of a small car. Many companies run lifecycle policies that automatically move backups older than 90 days to Glacier, saving thousands per year.

Lifecycle policies

You can tell S3 to automatically move files to cheaper tiers as they age. For example: new uploads stay in Standard for 30 days, then move to Standard-IA for the next 90 days, then move to Glacier after that. You set it once and stop thinking about it.

Key Facts Worth Remembering

  • All S3 storage classes share the same 11-Nines durability. You will not lose your data.
  • S3 buckets are private by default. You must add a bucket policy or IAM permissions to make files public.
  • Objects can be up to 50 TB; files larger than 5 GB should use Multi-part Upload.
  • Normal delete adds a Delete Marker (restorable if versioning is on). Deleting a specific Version ID is permanent.
  • Replication requires versioning on both source and destination buckets. Only new objects replicate automatically.
  • Choose Standard for frequent access, Standard-IA for monthly backups, Glacier for archives. Use Intelligent-Tiering when unsure.
  • Lifecycle policies can auto-move files to cheaper tiers as they age, cutting costs significantly.

The One-Paragraph Version

S3 is infinitely scalable file storage that powers backup, archival, and web hosting globally. You create a bucket (a container for files), upload objects (files with Keys like folder paths), and control access with bucket policies or IAM permissions. Private by default. Versioning keeps file history so deletes become recoveries. Replication copies new files to other buckets for disaster recovery. Durability is guaranteed at 11 Nines across all storage classes. Choose Standard for active data, Standard-IA for backups you might need, and Glacier for compliance records you hope never to touch. Lifecycle policies automatically move aging files to cheaper tiers, slashing storage costs on data you rarely access.
