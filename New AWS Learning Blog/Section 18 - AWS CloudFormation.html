1Overview: Why Infrastructure as Code

Imagine you're setting up a web application in AWS. You need a security group to allow traffic, an EC2 instance behind it, an Elastic IP so the instance keeps the same address if you stop and restart it, an S3 bucket for data storage, and a load balancer to spread traffic. Normally, you click through the console, create each piece manually, and hope you remember what you did so you can do it again next week for staging or production.

💡 New word CloudFormation is AWS's service for describing your entire infrastructure in a text file called a template — then telling CloudFormation to read that file and create, update, or delete everything inside it automatically.
💡 New word Infrastructure as Code (IaC) means treating your cloud setup the same way you treat your application code — it lives in version control (Git), gets code reviewed before deploying, can be tested, and is repeatable.

Why this matters

With CloudFormation, you write once and deploy many times. Destroy a stack and recreate it in seconds. Replicate your entire production setup in a test account to safely try out changes. Most critically: your infrastructure is versioned in Git, every deployment can be audited, and rolling back is automatic if something fails.

🏭 In real companies Large organizations use CloudFormation (or similar tools like Terraform) as the single source of truth. A change to production infrastructure doesn't happen because someone clicked buttons — it happens because a pull request was approved, merged to main, and a CI/CD pipeline deployed it. That creates an audit trail, enables code review, and makes disasters recoverable: if something breaks, you roll back the code commit, not the infrastructure.
💡 New word A stack is the set of AWS resources CloudFormation created from one template. Stacks are named, live in one region, and are the unit you update or delete together. Delete the stack, everything inside it is destroyed.

Template building blocks

A CloudFormation template is a text file written in YAML or JSON. It has several sections:

SectionRequired?Purpose
AWSTemplateFormatVersionNoInternal AWS version info — usually "2010-09-09"
DescriptionNoComments about what this template does
ResourcesYesThe AWS resources to create — the only mandatory section
ParametersNoDynamic inputs from whoever launches the stack
MappingsNoFixed lookup tables (e.g., AMI IDs per region)
OutputsNoValues to display after stack creation, optionally shared with other stacks
ConditionsNoLogic to control whether resources get created

2Stacks: Create, Update, Delete

A stack is the central unit CloudFormation works with. Creating a stack means uploading your template and telling CloudFormation to build everything inside it. Updating a stack means providing a new template version and letting CloudFormation figure out what changed. Deleting a stack tears down every resource it owns.

Creating a stack

You start by writing a template (in YAML or JSON) describing what resources you want. Upload it to the CloudFormation console or use the CLI. CloudFormation reads the template, validates it, and creates the resources in the right order — if a resource depends on another, CloudFormation waits for the dependency first. Once all resources are provisioned, the stack status becomes CREATE_COMPLETE.

💡 Good to know You can also store templates directly in S3 (AWS's file storage) and reference them from the console or CLI, which is handy for large templates or templates managed by a deployment pipeline.

Updating a stack

You can't edit a template in place. Instead, you upload a new version and tell CloudFormation to update the stack with it. CloudFormation compares the old and new templates, figures out which resources changed, and applies the minimal set of modifications needed. Some changes can happen in place (like updating a tag). Others require the resource to be replaced — destroyed and recreated.

💡 New word A change set is a preview of what will change before you actually apply an update. It lists which resources will be added, which will be modified in place, and which will be replaced. You review it before committing.

Before the update is applied, CloudFormation shows you a change set — a detailed list of what will be added, removed, or modified. Only after you approve it does CloudFormation proceed.

Important: If a resource must be replaced (destroyed and recreated), CloudFormation handles the ordering automatically — it creates the new resource first, then removes the old one, so your service stays running. But if you're replacing a database, the old data goes away — that's why deletion policies exist.

Deleting a stack

Clicking delete on a stack tells CloudFormation to remove every resource it created. The order is automatic — dependent resources are deleted first, and CloudFormation respects any protection settings (like deletion policies that preserve certain resources). This is cleaner and safer than manually deleting individual resources in the console.

Critical: Deleting a stack destroys all its resources. If you have important data, deletion policies must preserve it first, or you'll lose it.

3Templates: The Blueprint

💡 New word A template is a text file (YAML or JSON) that describes what AWS resources you want, how they're configured, and how they relate to each other.

Templates are usually written in YAML because it's more readable than JSON — no heavy string escaping, and indentation creates structure naturally. The core structure is simple: top-level keys like Resources, Parameters, Outputs, and inside those, nested objects and lists.

YAML basics

  • Key-value pairs: key: value.
  • Indentation creates nesting: spaces (not tabs) show hierarchy.
  • Lists start with a dash: - item1, - item2.
  • Multi-line strings use a pipe: | long text here preserves line breaks.
  • Comments start with # and are ignored.

In a CloudFormation template, Resources is a nested object. Each resource (like an EC2 instance) has a logical name, a Type (e.g., AWS::EC2::Instance), and a Properties block listing its settings.

Resources:
  MyInstance:
    Type: AWS::EC2::Instance
    Properties:
      ImageId: ami-0c55b159cbfafe1f0
      InstanceType: t2.micro
      SecurityGroups:
        - MySecurityGroup

The template is uploaded to S3, and CloudFormation references it to create the stack. Updates happen by uploading a new template version.

4Resources

💡 New word A resource in a CloudFormation template is any AWS component you want to create — an EC2 instance, a security group, an S3 bucket, a database, a network interface, etc.

Resources are the core of any template and the only mandatory section. Every resource has a type (like AWS::EC2::Instance or AWS::S3::Bucket) and a set of properties specific to that type. CloudFormation supports over 700 resource types, covering almost every AWS service.

How CloudFormation figures out order

You write resources in a template without worrying about creation order. CloudFormation automatically detects dependencies — if resource A references resource B, CloudFormation creates B first. This dependency graph is built by CloudFormation reading your template, so you only write what you want, not how to build it.

Resource types

Each resource type has a documented format showing required and optional properties, what happens when you change each property (can it be modified in place or does the resource need replacement), and what values it returns (via functions like Ref or GetAtt).

Common resource typeExample
AWS::EC2::InstanceAn EC2 compute instance
AWS::S3::BucketAn S3 storage bucket
AWS::EC2::SecurityGroupA firewall rule set
AWS::RDS::DBInstanceA relational database
AWS::Lambda::FunctionA serverless function
💡 Good to know CloudFormation supports almost all AWS services, but not every feature of every service. For a few gaps, you can use a Custom Resource (covered later) to work around it.

5Parameters: Making Templates Reusable

💡 New word A parameter is a value that changes when the template is launched — the person deploying the stack provides it. Use parameters for things that differ between deployments, environments, or teams.

Imagine you have a template that creates a web server. The instance type (t2.micro, t2.small, etc.) might differ in dev versus production. Instead of maintaining two separate templates, define an InstanceType parameter. When the stack is created, CloudFormation prompts for the instance type, and users pick what they need.

Parameter types and constraints

Parameters have types: String, Number, CommaDelimitedList, specific AWS types (like an AMI ID), or even values loaded from Systems Manager Parameter Store. You can set constraints like a list of allowed values (so users only see valid options in a dropdown), minimum/maximum values, or a pattern (regex) that the input must match.

Parameters:
  InstanceType:
    Type: String
    Default: t2.micro
    AllowedValues:
      - t2.micro
      - t2.small
      - t2.medium
    Description: "Choose an EC2 instance type"

When a parameter has AllowedValues, the console shows a dropdown. When it has a pattern, CloudFormation validates the input before allowing stack creation.

Referencing parameters

In your template, use !Ref ParameterName to insert the parameter value. CloudFormation substitutes it wherever it appears.

Resources:
  MyInstance:
    Type: AWS::EC2::Instance
    Properties:
      InstanceType: !Ref InstanceType
      ImageId: ami-0c55b159cbfafe1f0
Exam tip: Parameters are for values that differ at deployment time. If a value is fixed (like the AMI ID for a specific region), use a Mapping instead.

6Mappings: Lookup Tables

💡 New word A mapping is a fixed, hardcoded lookup table inside a template — useful for values that differ by region, environment, or some other known variable, but are the same every time the template runs.

A classic example is AMI IDs. They're different in every AWS region. You could ask users to provide the right AMI ID as a parameter, but that's error-prone. Instead, define a mapping that lists the AMI ID for each region, then use a function to look up the right one based on where the stack is being launched.

Mappings:
  RegionMap:
    us-east-1:
      HVM64: ami-0c55b159cbfafe1f0
    eu-west-1:
      HVM64: ami-0dad359ff462124ca
    ap-southeast-1:
      HVM64: ami-0c5e2d9fcf3a1a3ba

Then, inside a resource property, use !FindInMap [RegionMap, !Ref "AWS::Region", HVM64] to get the right AMI ID for the current region automatically.

Mappings vs. Parameters

Use Mappings whenUse Parameters when
All possible values are known in advance (e.g., AMI IDs for each region)The value genuinely depends on who's launching the stack (e.g., instance type)
You want consistency and control — no room for typosYou want flexibility — different teams, different choices

7Outputs: Sharing Data Across Stacks

💡 New word An output is a value calculated by your stack that you want visible after creation — typically an ID, ARN, or URL. Outputs can be exported so other stacks can import them.

After a stack is created, you might want to know the IP address of the EC2 instance, the ARN (Amazon Resource Name — unique ID) of a database, or the URL of a load balancer. Outputs make those values visible in the console or CLI. More powerfully, you can export an output so other stacks can reference it.

Exporting and importing

Imagine you have a network stack that creates a VPC and exports its ID. Your application stack then imports that VPC ID and launches resources inside it. This lets teams build modular, reusable stacks without tight coupling.

Outputs:
  VpcId:
    Value: !Ref MyVpc
    Export:
      Name: !Sub "${AWS::StackName}-VpcId"
    Description: "The VPC ID for this stack"

Another stack imports it with Fn::ImportValue: MyStackName-VpcId. CloudFormation ensures the export is unique per region, and won't let you delete a stack if other stacks are still importing its values.

Important: You cannot delete a stack while another stack is importing one of its exports. You must update the importing stack first to stop using the export, then delete the exporting stack.

8Conditions: Conditional Creation

💡 New word A condition in CloudFormation is a logical statement that controls whether a resource (or output) gets created.

Sometimes you want different resources depending on context. For example, in production, create a read replica database for high availability. In development, don't — it's expensive. Define a condition based on an environment parameter, then attach it to resources that should only exist in certain environments.

Parameters:
  Environment:
    Type: String
    AllowedValues: [dev, prod]

Conditions:
  IsProd: !Equals [!Ref Environment, prod]

Resources:
  PrimaryDB:
    Type: AWS::RDS::DBInstance
    Properties:
      # ... database config

  ReplicaDB:
    Type: AWS::RDS::DBInstance
    Condition: IsProd
    Properties:
      # ... replica config

If the condition is false, CloudFormation doesn't create that resource at all. This is more efficient than creating it and then deleting it manually.

💡 Good to know For the AWS Certified Cloud Practitioner exam, you just need to know conditions exist and roughly how they're used — you don't need to write complex conditional logic from scratch.

9Functions: Getting the Most Out of Templates

CloudFormation provides built-in functions to make templates dynamic and powerful. Here are the most important ones.

FunctionWhat it does
!RefReturns a parameter's value, or a resource's physical ID (e.g., the instance ID of an EC2 instance)
Fn::GetAttReturns a specific attribute of a resource (e.g., the public DNS name of an EC2 instance, or the endpoint of a database)
Fn::FindInMapLooks up a value from a mapping based on keys
Fn::ImportValueImports a value exported by another stack
Fn::Base64Converts a string to Base64 encoding — commonly used for EC2 user data scripts
Fn::JoinJoins a list of strings with a delimiter
Fn::SubSubstitutes variables inside a string template

Functions are used to make templates dynamic. For example, !Ref MyInstance inserts the instance ID of a resource named MyInstance into an output, so you can see the ID after the stack is created.

💡 Good to know The shorthand !Ref is equivalent to the longer Fn::Ref — YAML supports both, but !Ref is more concise and commonly used.

10Rollbacks: When Updates Go Wrong

Stack creation failures

If CloudFormation hits an error while creating a stack (e.g., an AMI ID doesn't exist in the region, or you don't have permission to create a resource), the default behavior is to roll back — delete everything that was successfully created and leave nothing behind. This prevents you from having a half-built, unusable stack.

Alternatively, you can choose to preserve successfully created resources for troubleshooting. This leaves a partial stack running, but remember: you can't fix-and-update a failed stack. You'd need to delete it and retry.

Exam tip: By default, failure rolls back completely. You can change this behavior during stack creation if you need partial results for debugging.

Update failures and rollback

If an update fails (e.g., the new template is invalid, or a resource can't be updated), CloudFormation automatically rolls back to the last known working state. Any resources created during the failed update are deleted, and the stack returns to its previous configuration.

In rare cases, the rollback itself can fail — for instance, if someone manually modified a resource outside of CloudFormation, CloudFormation might not be able to undo the update. In that case, you'd need to fix the resource manually and then trigger ContinueUpdateRollback to tell CloudFormation to retry.

🏭 In real companies Automatic rollback is a massive safety feature. Teams depend on it so they can update stacks without fear — if something goes wrong, the rollback is immediate and automatic, limiting damage. Manual updates to resources (clicking through the console instead of updating the template) are exactly what CloudFormation is designed to prevent.

11Service Roles: Delegation

💡 New word A service role for CloudFormation is an IAM role that CloudFormation assumes (temporarily uses) to create, update, and delete stack resources on your behalf.

Normally, CloudFormation uses your own IAM permissions to create resources. But in large organizations, you might want to separate concerns: a user creates a stack, but CloudFormation uses a separate role with its own, more powerful permissions to actually build the resources. This lets you grant users the ability to manage stacks without giving them direct permissions on all the underlying resources.

To use a service role, you pass it when creating the stack, and CloudFormation assumes it. The user only needs permission to invoke CloudFormation and pass the role — the role itself holds the actual resource creation permissions.

Exam point: The user must have iam:PassRole permission to pass a role to CloudFormation. This is a safety gate — you can't pass a role unless you have explicit permission to do so.

12Capabilities: Acknowledging Permissions

💡 New word A capability is an explicit acknowledgment that a template does something that requires special handling — most commonly, creating IAM resources.

CloudFormation requires you to explicitly acknowledge when a template creates or updates IAM resources (users, roles, policies, etc.). This is a safety measure — it prevents someone from accidentally deploying a template that grants permissions they didn't intend to grant.

CapabilityWhen to use
CAPABILITY_IAMTemplate creates IAM resources with auto-generated names
CAPABILITY_NAMED_IAMTemplate creates IAM resources with custom, specific names
CAPABILITY_AUTO_EXPANDTemplate uses macros or nested stacks that may transform the template before deployment

In the console, you check a box acknowledging the capability. Via CLI, you pass --capabilities with the right value. If you forget and your template creates IAM resources, you'll get an InsufficientCapabilitiesException.

💡 Good to know This is a safety measure to prevent accidents — it makes sure whoever is deploying the template explicitly understands what it's doing.

13Deletion Policies: Protecting Data

💡 New word A deletion policy on a resource controls what happens to it when the stack is deleted or the resource is removed from the template.

By default, when you delete a stack, CloudFormation deletes every resource it created. But for important resources like databases or S3 buckets holding data, you want different behavior. A deletion policy lets you protect data.

PolicyBehavior
DeleteResource is deleted (default). For S3 buckets, the bucket must be empty first or the delete fails.
RetainResource stays alive even after the stack is deleted — perfect for important data or resources you want to keep.
SnapshotA final snapshot is taken (EBS volumes, RDS databases, ElastiCache clusters, etc.), then the resource is deleted. You keep the snapshot for recovery.
Resources:
  ImportantDatabase:
    Type: AWS::RDS::DBInstance
    DeletionPolicy: Snapshot
    Properties:
      # ... database config

When you delete the stack, CloudFormation creates a final snapshot of the database and stores it. The database itself is deleted, but your data is safe in the snapshot.

Important: DeletionPolicy: Delete on an S3 bucket only works if the bucket is empty. If the bucket has objects, the deletion fails. You'd need to either empty it first manually or use a Custom Resource (covered next) to empty it as part of stack deletion.

14Stack Policies: Protecting Resources from Changes

💡 New word A stack policy is a JSON document that restricts which resources can be modified during stack updates.

Deletion policy protects resources when a stack is deleted. Stack policy protects resources when a stack is updated. By default, any resource can be updated. You can set a stack policy to deny updates on critical resources — like your production database — so they can't accidentally be modified by a template update.

Stack policies work on a deny-by-default principle: once you set a policy, all resources are protected unless you explicitly allow updates on them. This is the opposite of regular IAM policies.

Statement:
  - Effect: Allow
    Principal: "*"
    Action: Update:*
    Resource: "*"
  - Effect: Deny
    Principal: "*"
    Action: Update:*
    Resource: "LogicalResourceId/ProductionDatabase"

This policy allows updates on everything except the ProductionDatabase resource.

Termination protection

A simpler alternative: enable termination protection on the stack. This prevents anyone from accidentally deleting the entire stack until protection is explicitly disabled. It's a quick safety catch.

💡 Good to know Termination protection prevents deletion of the whole stack. Stack policies are more fine-grained — they protect specific resources from changes during updates.

15Custom Resources: Extending CloudFormation

💡 New word A custom resource lets you define CloudFormation resources for anything CloudFormation doesn't natively support — either by running custom code (via Lambda) or sending a message to an SNS topic.

CloudFormation supports 700+ resource types, but not every scenario. For example, CloudFormation can create an S3 bucket but can't empty it. When you delete a bucket, if it has objects, the deletion fails. A custom resource can solve this: use a Lambda function to empty the bucket first, then let CloudFormation delete the (now-empty) bucket.

Resources:
  EmptyBucketFunction:
    Type: AWS::Lambda::Function
    Properties:
      # ... Lambda code to empty S3 buckets

  MyBucket:
    Type: AWS::S3::Bucket
    Properties:
      BucketName: my-bucket

  EmptyBucket:
    Type: Custom::EmptyS3Bucket
    Properties:
      ServiceToken: !GetAtt EmptyBucketFunction.Arn
      BucketName: !Ref MyBucket

When the stack is deleted, CloudFormation invokes the Lambda function (via the custom resource), which empties the bucket, and then CloudFormation deletes the (now-empty) bucket successfully.

🏭 In real companies Custom resources are commonly used for one-off operations: cleaning up resources before deletion, fetching data from external systems, calling third-party APIs during stack creation, or integrating with on-premises systems. They're a powerful escape hatch when CloudFormation's native resources don't do exactly what you need.

16StackSets: Multi-Region, Multi-Account

💡 New word StackSets let you create, update, or delete CloudFormation stacks across multiple AWS accounts and regions from a single operation.

Imagine you have 10 AWS accounts and you need to deploy a security baseline (firewall rules, logging configuration, etc.) to each one, in each region. Creating stacks manually in each account/region would take forever and be error-prone. StackSets let you define the template once and deploy it everywhere at once.

An administrator account creates a StackSet with the template. Then, you specify which accounts and regions to target. CloudFormation deploys the stack to each target, automatically. Updates to the StackSet fan out to all stacks in all targets.

Important: Only an administrator account (or a delegated administrator) in an AWS Organization can create StackSets. This is a security measure — preventing individual accounts from pushing changes into other accounts without permission.

StackSets are especially useful in large enterprises where a central team owns compliance and wants to ensure all accounts follow the same policies.

📋 Cheat Sheet

Core Building Blocks

ConceptWhat it is
TemplateText file (YAML/JSON) describing AWS resources, parameters, outputs, conditions, and mappings
StackThe running instance of a template — all resources CloudFormation created from that template, managed as one unit
ResourceAn AWS component (EC2 instance, S3 bucket, database, etc.) defined in a template
ParameterUser input — values that change at deployment time (instance type, environment name, etc.)
MappingFixed lookup table in the template (e.g., AMI IDs per region) — known in advance
OutputValue calculated by the stack, visible after creation, optionally exported for other stacks to import
ConditionLogic that controls whether a resource is created (e.g., only in prod, not in dev)

Key Workflows

  • Create: Upload template → CloudFormation provisions resources → stack status becomes CREATE_COMPLETE.
  • Update: Upload new template → CloudFormation shows change set (preview) → approve → apply changes. Some changes are in-place, others require replacement.
  • Delete: CloudFormation removes all resources, respecting deletion policies (retain or snapshot important data first).

Important Protections and Policies

  • Change Sets: Preview updates before applying them — see what will be added, modified, or replaced.
  • Rollbacks: Failed creation rolls back by default. Failed updates auto-rollback to the last good state.
  • Deletion Policies: Delete (default), Retain (keep resource after stack deletion), Snapshot (take final backup, then delete).
  • Stack Policies: Restrict which resources can be modified during updates — protect critical resources from accidental changes.
  • Termination Protection: Prevent accidental stack deletion until explicitly disabled.
  • Capabilities: Acknowledge when templates create IAM resources — safety measure to prevent accidents.

Advanced Features

  • Service Roles: CloudFormation assumes a role to create resources on your behalf — separate concerns between who manages stacks and who has resource permissions.
  • Custom Resources: Use Lambda or SNS to extend CloudFormation — handle things it doesn't natively support (e.g., emptying S3 before bucket deletion).
  • StackSets: Deploy the same stack to many accounts and regions at once — powerful for multi-account organizations.
  • Exports and Imports: One stack exports values, another imports them — modular, reusable stacks without tight coupling.

The Big Picture

CloudFormation is Infrastructure as Code: instead of clicking the console, you write a template describing what you want (resources, parameters, conditions, outputs). Upload it, and CloudFormation builds everything, manages updates, handles rollbacks, and lets you version your infrastructure in Git just like application code. Large organizations treat CloudFormation as the source of truth — infrastructure changes only happen via code review and automated deployment, not manual clicking.
