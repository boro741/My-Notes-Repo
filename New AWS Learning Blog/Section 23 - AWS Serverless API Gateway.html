1API Gateway Overview: The Front Door for Serverless

Exposing a Lambda function directly to the internet requires either giving clients AWS credentials (a security nightmare) or fronting it with a load balancer (extra infrastructure to manage). API Gateway solves this by sitting between clients and backends, handling authentication, throttling, versioning, and data transformation without you managing a single server.

💡 New word API Gateway is AWS's serverless API front door. It accepts HTTP requests from clients, applies features like authentication and rate limiting, then forwards traffic to Lambda functions, HTTP endpoints, or AWS services directly.

What API Gateway actually does

Instead of forcing you to pick one integration target, API Gateway lets you route different paths to different backends. One path might hit a Lambda function, another might hit an HTTP service on premises or in another cloud, and a third might write directly into an AWS service like SQS (Simple Queue Service) or Step Functions (a workflow orchestrator). All of it happens through a single public URL.

API Gateway sits at the center, routing different paths to different backends — Lambda, HTTP services, or AWS services directly.

Three API types you can build

API Gateway offers three different kinds of APIs, each with different feature sets and price points. REST APIs are the full-featured option. HTTP APIs are newer and cheaper, optimized for simple proxy patterns. And WebSocket APIs handle persistent two-way connections for real-time applications. For most of this section we'll focus on REST APIs, which is where the depth is.

Your security toolkit

API Gateway works with four main security layers. First, IAM roles authenticate internal AWS services and applications already in your account. Second, Amazon Cognito handles external users for mobile and web apps without you writing authentication code. Third, a custom Lambda authorizer (also called a Lambda authorizer) lets you integrate third-party identity systems or implement completely custom authorization logic. Fourth, HTTPS with custom domains and ACM certificates handles encryption for data in transit.

🏭 In real companies Most teams building customer-facing APIs start with Cognito for authentication if they don't already have an identity system (Google/GitHub login, etc.). Lambda authorizers are for integrating with enterprise systems like Auth0 or Okta, and they're powerful but require you to write and maintain the validation code yourself.

2Creating Your First API — Hands On

Building your first API is straightforward. You create a REST API, define a resource (a path like /users), attach an HTTP method to it (GET, POST, etc.), and wire it to a backend — usually a Lambda function using what's called Lambda proxy integration.

💡 New word Lambda proxy integration means the entire HTTP request — headers, query string, body, path, everything — gets passed to Lambda as a single JSON object, and Lambda is completely responsible for building the HTTP response. No transformation happens; Lambda gets the raw request and must return the raw response.

Step by step

Open the API Gateway console and create a new REST API, choosing Regional for simplicity. Add a new resource (a URL path) and create a GET method on it. In the integration settings, choose Lambda and select a function. API Gateway automatically creates a resource-based policy on your Lambda function, granting this specific API route permission to invoke it. You can test the method right in the console, seeing both the request and response logged.

Important constraint: the 29-second timeout

Lambda functions themselves can run for up to 15 minutes. API Gateway, however, has a hard timeout of 29 seconds on every request it receives — no exceptions, no way around it. If your Lambda takes 30 seconds to run, API Gateway kills the request and returns a 504 (Gateway Timeout) error. This is a real production gotcha worth memorizing.

Don't forget: changes you make to your API are not live until you explicitly deploy them to a stage. Creating a method, changing integrations, modifying timeout settings — none of it takes effect for clients until you hit the Deploy button.

3Stages & Deployment — Why Changes Don't Go Live Automatically

A stage is a named snapshot of your API — a complete configuration including all routes, methods, integrations, and settings. The same API can have multiple stages (dev, test, prod, or any names you like), each with its own configuration, its own URL, and its own deployment history for rollbacks.

💡 New word Stage is a named, independent deployment of your API. Each stage has its own URL, its own cache, its own throttle settings, and its own variable values. Deploying to dev doesn't affect prod.

This is why the workflow is: build your API, then deploy it to a stage to make it live. Edit the API again, then deploy those changes to a stage (the same stage or a different one) to publish them. Without an explicit deploy, changes exist only in your editor.

Using stages for versioning

A common pattern is to create separate stages for each version of your API (v1, v2, etc.). When you have a breaking change coming, you deploy it as v2 while v1 keeps running unchanged. Existing clients keep calling /v1, and they never feel the impact. New clients can adopt /v2 at their own pace. Once v1 usage drops to nothing, you retire it.

Two stages let a breaking change ship as a new version (canary or v2) while existing v1 clients keep working until they're ready to upgrade.

Stage variables — configuration without redeploying

💡 New word Stage variables are like environment variables for API Gateway. You set them per stage and they get passed into your Lambda as part of the context object, letting each stage point to different resources without touching the API definition.

A real example: you have three Lambda versions (PROD, TEST, DEV) representing production, testing, and development environments. You create a stage variable LambdaAlias and set it to prod for the production stage, test for the test stage, and dev for the development stage. In your API integration, you reference ${stageVariables.LambdaAlias} instead of a hard-coded alias name. Now each stage automatically calls the right Lambda version — no API redeploy needed.

Configuration options per stage

Each stage controls its own cache settings, throttling limits, CloudWatch logging verbosity, X-Ray tracing, stage variables, and canary settings. You can also track deployment history and roll back to earlier versions if something breaks.

4Canary Deployments — Testing New Versions Safely

Rolling out a backend change to 100% of traffic immediately is risky. What if it has a subtle bug? What if it's slower than you expected? Canary deployments let you send a small percentage of traffic to the new version while the rest keeps using the old one, letting you catch problems on real traffic before everyone is affected.

💡 New word Canary deployment is a release pattern where a small percentage (often 5-10%) of production traffic goes to the new version while the rest stays on the stable version. If metrics look good, you promote the canary to 100%.

API Gateway implements canaries at the stage level. You enable a canary on your prod stage, specify what percentage of traffic it should receive (e.g., 5%), and optionally override stage variables just for that canary (e.g., point it at a different Lambda alias). Metrics and logs for the canary stay separate from the main stage, making it easy to spot differences in latency, error rates, or throughput.

A canary splits a stage's traffic by percentage. If the new version looks good on real traffic, you promote it to 100%.

Once you're confident the canary version is working well, you click "promote canary" and it becomes the new 100% deployment. The old version is replaced.

5Integration Types & Mapping Templates

How API Gateway connects to your backend depends on the integration type you choose. Some integration types pass requests straight through. Others let you transform the data on the way in and on the way out, reshaping headers, query strings, and request/response bodies.

The integration types

TypeWhat it does
MockReturns a canned response without calling any backend — useful for testing or for documentation
Lambda ProxyPasses the entire HTTP request to Lambda untouched; Lambda returns the entire HTTP response. No transformation possible
Lambda (non-proxy)Lambda receives a transformed request; API Gateway transforms the response. Supports mapping templates
HTTP ProxyForwards the HTTP request to an HTTP endpoint unchanged. You can inject extra headers (like an API key) but can't reshape the body
HTTP (non-proxy)Like Lambda non-proxy but for HTTP backends — supports mapping templates
AWS ServiceDirect integration with SQS, Step Functions, Kinesis, or other AWS services. Supports mapping templates

Mapping templates and data transformation

💡 New word Mapping template is a transformation script written in VTL (Velocity Template Language) that reshapes data flowing between API Gateway and your backend. You can rename fields, filter data, convert formats, or completely restructure requests and responses.

Mapping templates are only available in non-proxy integrations. A classic use case is bridging a SOAP (XML) backend with a JSON-speaking REST API — API Gateway extracts fields from the incoming JSON request, builds an XML SOAP message, sends it to the backend, then transforms the XML response back into JSON for the client. Another use case is renaming query string parameters into different JSON keys before they reach your function.

Why proxy vs. non-proxy matters

Proxy integrations are simpler and faster because there's no transformation step. Your backend code is fully responsible for parsing and formatting. Non-proxy integrations add flexibility but also complexity — you configure the transformation rules in the console or code, and API Gateway applies them automatically. Choose proxy when your backend can handle the raw request format. Choose non-proxy when you need to reshape data or when your backend expects a specific format.

6OpenAPI — Infrastructure as Code for APIs

Building an API entirely through the console works for learning, but production APIs are usually defined in code. OpenAPI (formerly called Swagger) is the industry standard for describing REST APIs — you write a YAML or JSON file that specifies every endpoint, method, parameter, and response format, then import it into API Gateway to build the whole API at once.

💡 New word OpenAPI is a standard format for describing REST APIs as code. It specifies endpoints, methods, parameters, responses, and AWS-specific extensions. API Gateway can import and export OpenAPI specs.

Import and export

You can import an OpenAPI spec to build an API from scratch, or export an existing API as a spec file to share with other teams or generate client SDKs (for JavaScript, Java, Python, Swift, Android, etc.). The exported spec is a single source of truth for your API's contract.

Built-in request validation

OpenAPI specs support request validation rules — you can specify which parameters are required, which headers must be present, and you can validate the request body against a JSON Schema. API Gateway enforces these rules automatically, rejecting invalid requests with a 400 (Bad Request) error before they ever reach your backend.

Real use case: validation using OpenAPI specs catches bugs in client code before they hit your backend, reducing wasted Lambda invocations and database queries on bad requests.

7Response Caching

If the same client asks for the same data multiple times, why invoke Lambda and hit the database every time? Response caching stores copies of responses and returns them immediately on repeated requests, drastically reducing backend load and latency.

💡 New word Response caching stores HTTP responses from your backend in API Gateway's cache. Subsequent identical requests return the cached response instead of invoking the backend again, until the cache expires.

Cache configuration

SettingOptions
Default TTL300 seconds (5 minutes) by default; you can set it to 0 (no caching) up to 3,600 seconds (1 hour)
ScopeConfigured per stage, but you can override per-method
Cache sizeFrom 0.5 GB to 237 GB
EncryptionOptional; can encrypt cache data at rest
Cost gotcha: the cache itself is expensive (you pay for every hour it's provisioned). It's usually worth it only in production or pre-production environments where request volume is high. In dev/test stages with low traffic, the cost of the cache often outweighs the benefits.

Cache invalidation

You can manually flush the entire cache from the console instantly. Clients can also invalidate the cache by sending a header Cache-Control: max-age=0, but this requires IAM authorization for the InvalidateCache action — otherwise any client could wipe your cache at will and tank your backend.

8Usage Plans & API Keys — Metering External Customers

If you're selling API access to external customers, you need to track who's using what and enforce limits. Usage plans define rate limits (throttling) and quotas (hard monthly caps), while API keys identify individual customers.

💡 New word Usage plan bundles throttling rules and request quotas. API key is a token you give to a customer, sent in the x-api-key header, that identifies them for metering and enforces their plan's limits.

The setup workflow

First, create your API and mark which methods require an API key (via a checkbox in each method's settings). Deploy to the stages customers will use. Then generate API keys (one per customer, or however you want to organize them) and distribute them. Create usage plans with your desired throttling and quota settings. Finally — and this step is critical — associate the API stages and API keys with the plan. If you miss the last step, nothing gets enforced and all your customers hit the same account-wide limits.

Common mistake: creating API keys and usage plans but forgetting to associate them. The keys and plans exist in isolation; enforcement only happens when you explicitly link them together in the plan.

Rate limits and quotas

Throttling limits are rate-based — a customer's key is limited to, say, 100 requests per second. Quotas are volume-based — the same key might be capped at 10,000 requests per month. Both are enforced per API key, so each customer is metered independently.

9Monitoring, Logging & Tracing

Like every AWS service, API Gateway integrates with CloudWatch for metrics and logs. Enable detailed CloudWatch logging to capture request/response bodies, or turn on X-Ray tracing to see the full request path through API Gateway, Lambda, and downstream services.

CloudWatch metrics

MetricWhat it tells you
CountTotal number of API requests in the time period
CacheHitCount / CacheMissCountHow effective your cache is
IntegrationLatencyTime spent waiting for the backend to respond (Lambda, HTTP, etc.)
LatencyTotal time from request arrival to response departure — includes auth, caching, mapping, and backend time
4XXErrorClient-side errors (bad requests, auth failures, throttling)
5XXErrorServer-side errors (Lambda crashed, backend timeout, etc.)
Latency vs. IntegrationLatency: Latency is always greater than or equal to IntegrationLatency. Latency includes everything API Gateway does (authentication checks, cache lookups, mapping templates). IntegrationLatency is only the backend waiting time. If they're nearly equal, your backend is the bottleneck. If Latency is much higher, API Gateway itself is adding overhead (often due to complex mapping templates).

Throttling and rate limits

Every AWS account has a soft limit of 10,000 requests per second across all APIs. When you hit it, requests get a 429 (Too Many Requests) response and should be retried with exponential backoff. If one API is misbehaving and consuming all 10,000 requests/sec, it starves other APIs in the same account. To prevent this, set throttling limits per stage, per method, or per usage plan to compartmentalize traffic.

Exam key fact: API Gateway always times out after 29 seconds, regardless of how long your Lambda can run. Latency capped at 29 seconds, period. Exceeding it results in a 504 response.

10CORS — Browser Cross-Domain Calls

If your API is on api.example.com and your frontend is on app.example.com, the browser blocks the API call because they're different origins — this is CORS (Cross-Origin Resource Sharing). API Gateway can configure CORS responses to tell the browser it's okay to allow that frontend to call the API.

💡 New word CORS is a browser security feature that blocks JavaScript code in one origin (like app.example.com) from making requests to a different origin (like api.example.com) unless the API explicitly says it's allowed via response headers.

How it works

When your frontend makes a request to an API on a different domain, the browser first sends an OPTIONS request (a "preflight") asking if the actual request is allowed. API Gateway responds with headers like Access-Control-Allow-Methods (which HTTP methods are okay), Access-Control-Allow-Headers (which headers are okay), and Access-Control-Allow-Origin (which origins are allowed). If the response says yes, the browser then sends the actual request.

Enabling CORS in API Gateway is straightforward — select the resource, enable CORS, and specify which origins, methods, and headers to allow. API Gateway handles the OPTIONS response automatically.

Rule of thumb: enable CORS whenever a web page in one domain calls an API on another domain. CORS isn't a security feature; it's a courtesy to let you clearly document which cross-origin calls you support.

11Authentication & Authorization

API Gateway supports four main authentication mechanisms. Which one you choose depends on who's calling your API.

Four paths to security

IAM roles work when your callers are already inside your AWS account — EC2 instances, Lambda functions, or IAM users. They sign requests with their AWS credentials and API Gateway validates them against the IAM policy.

Cognito User Pools are for external app users. Cognito handles signup, login, password reset, and MFA. Your frontend authenticates with Cognito, gets a token, and passes it to API Gateway. API Gateway validates the token directly against the User Pool — no custom code needed.

Lambda Authorizer (also called a Lambda authorizer) is the most flexible option. A client passes a bearer token (usually a JWT), API Gateway invokes a Lambda function with that token, the function validates it and returns an IAM policy, and API Gateway caches that policy for future requests from the same client. This lets you integrate with third-party identity providers like Auth0, Okta, or implement completely custom authorization logic.

Resource policies attach directly to the API Gateway, allowing or denying access based on IAM principals, IP addresses, or VPC endpoints. You might use this for internal APIs that should only be reachable from within your corporate network.

💡 New word Lambda authorizer is a Lambda function that validates a client's token and returns an IAM policy specifying what they're allowed to do. The policy is cached for performance, so the authorizer doesn't run on every request.
🏭 In real companies Cognito User Pools are preferred when you don't need a custom identity system — they handle the messy details of authentication (password hashing, session management, MFA) for you. Lambda authorizers are for integrating with existing enterprise identity systems (your company's Okta instance, for example). Both are more secure than trying to implement authentication yourself.

12REST API vs HTTP API — Cost vs Features

AWS offers two different REST API types to choose from. REST APIs are the full-featured, more expensive option. HTTP APIs are newer, cheaper, and simpler — but with fewer features.

Side-by-side comparison

FeatureHTTP APIREST API
CostLower — designed for simple proxy patternsHigher — full-featured product
IntegrationsLambda proxy, HTTP proxy, AWS service (proxy only) — all proxy, no mapping templatesFull range: proxy and non-proxy integrations, mapping templates supported
AuthenticationOIDC (OpenID Connect) and OAuth 2.0 native supportIAM, Cognito, Lambda authorizers
CORSBuilt-in, automatically configuredManual configuration required
Usage plans & API keysNot supportedSupported — key for metering customers
Request validationLimitedFull OpenAPI support with request validation
Resource policiesNot supportedSupported — for IP/VPC/IAM control

When to use each

HTTP APIs are ideal for simple proxy APIs — you're just forwarding requests to a Lambda or HTTP backend and don't need advanced features like data transformation or usage-based metering. REST APIs are for everything else: complex APIs with multiple integration types, customer metering, request validation, or when you need mapping templates to transform data.

Cost consideration: if you're building a simple API that forwards requests straight to Lambda, HTTP APIs can cut costs by 30-40%. For complex APIs, REST is what you need.

13WebSocket API — Real-Time Two-Way Communication

REST APIs follow a request-response pattern — the client asks, the server answers. But what if you need real-time, two-way communication where the server pushes data to clients without them asking first? That's WebSocket, and API Gateway supports it.

💡 New word WebSocket is a protocol for persistent two-way communication between client and server over a single connection. The server can push data at any time without waiting for the client to request it first.

WebSocket APIs are used for chat applications, collaborative editing tools, live notifications, multiplayer games, and any system where real-time updates are critical. The client opens a WebSocket connection to API Gateway, gets a connection ID, and can send and receive messages over that persistent connection.

How it works

When a client connects, a $connect Lambda function fires (you might use this to store the connection ID in DynamoDB so you know how to reach them later). Messages from clients route to different Lambda functions based on a route selection expression — usually a field in the message body. When your backend needs to send data to a client, it makes an authenticated POST request to .../@connections/{connectionId} with the data, and API Gateway pushes it to the client. When the client disconnects, $disconnect fires.

A persistent WebSocket connection stays open. Messages route to handlers; the server pushes data back by POSTing to the connection's ID.
🏭 In real companies WebSocket APIs are commonly used for notification systems (stock prices updating in real-time), collaborative tools (multiple people editing the same document), and gaming. The key advantage is that the server can initiate communication — no polling needed.

14Microservices Architecture

API Gateway's real power emerges in microservices architectures. Instead of a monolith, you have many small, independent services — each with its own database, its own deployment schedule, and its own team. API Gateway sits at the front, routing different URL paths to different services, giving clients a single unified entry point.

One API, many backends

You might configure /users to route to a user service, /orders to route to an order service, and /docs to serve static files from S3. Each path can use different integrations — Lambda, HTTP, S3, whatever makes sense. Clients see one clean domain, but behind the scenes you're orchestrating traffic across many independent systems.

Custom domains and certificates

Using API Gateway's default domain like abc123.execute-api.us-east-1.amazonaws.com is fine for testing, but production APIs use custom domains like api.example.com. Route 53 maps your domain to the API Gateway using a CNAME or alias record. An ACM (AWS Certificate Manager) certificate handles HTTPS encryption. You can even use subdomains per customer, like customer1.api.example.com, each routing to the same or different APIs.

API Gateway routes different paths to different backends, all behind a single custom domain managed by Route 53.

📋 Cheat Sheet

Core Concepts

  • API Gateway is the front door for serverless APIs — it handles auth, throttling, caching, versioning, and data transformation.
  • Stages are independent deployments of the same API. Each stage has its own URL, config, and deployment history. Changes only go live when you deploy to a stage.
  • Lambda proxy integration passes the entire HTTP request to Lambda unchanged; Lambda is responsible for the entire response format.
  • Mapping templates (VTL) transform request/response data — only available in non-proxy integrations.
  • Canary deployment sends a small percentage of traffic to a new version while the rest uses the stable version, with separate metrics.
  • 29-second timeout is API Gateway's hard limit, no matter how long Lambda can run.
  • Usage plans + API keys meter external customers — throttle rate and enforce request quotas per key.
  • CORS enables cross-origin calls from web browsers on different domains.
  • WebSocket API maintains persistent two-way connections for real-time applications.

Authentication & Authorization Options

  • IAM: for internal AWS callers (EC2, Lambda, IAM users). Client signs request with AWS credentials.
  • Cognito User Pool: for external app users. No custom auth code needed; Cognito handles signup, login, MFA.
  • Lambda Authorizer: most flexible. Client passes a bearer token; Lambda validates it and returns an IAM policy (cached for performance).
  • Resource Policy: deny or allow based on IAM principals, IP addresses, or VPC endpoints.

REST API vs HTTP API

  • REST API: full features — usage plans, API keys, mapping templates, resource policies, rich request validation.
  • HTTP API: cheaper, simpler — proxy integrations only, native OIDC/OAuth2, built-in CORS, no usage plans or mapping templates.
  • Use HTTP API for simple proxy patterns. Use REST API for everything else.

Key Facts Worth Memorizing

  • Account-wide throttle: 10,000 requests/second soft limit across all APIs. Use per-stage/per-method/per-usage-plan limits to prevent one API from starving others.
  • Cache config: 0–3,600 seconds TTL, 0.5–237 GB size, per-stage or per-method override.
  • Latency metrics: Latency (total) ≥ IntegrationLatency (backend only). Both capped at 29 seconds.
  • Stage variables: environment-like values per stage, accessed in Lambda via context object, passed into mapping templates as ${stageVariables.varName}.
  • OpenAPI: define entire API as code, import to build it instantly, export to generate SDKs or enable request validation.
  • WebSocket routes: use a route selection expression (e.g., $request.body.action) to route incoming messages to different handlers.
  • Microservices: one API Gateway routes different paths to different backends, unified behind a custom domain.

The One-Paragraph Version

API Gateway is the serverless API front door that accepts requests and routes them to Lambda, HTTP services, or AWS services directly. You define endpoints in stages (dev/test/prod), and changes only go live when you deploy. Request and response data can be transformed using mapping templates (VTL), or passed through untouched using proxy integrations. Caching reduces backend load for repeated identical requests. Canary deployments test risky changes on a percentage of traffic before full promotion. Usage plans and API keys meter customer access with throttling and quotas. Four authentication options (IAM, Cognito, Lambda Authorizer, resource policies) cover internal and external callers. REST APIs are full-featured; HTTP APIs are simpler and cheaper. WebSocket APIs handle real-time, persistent two-way communication. The hard 29-second timeout and 10,000 requests/second account-wide throttle are critical limits to remember.
