1Introduction to Messaging: Sync vs. Async

The moment you run more than one application, they need to exchange information. The question is how they talk to each other — and that answer shapes everything else.

The first way is the obvious one: a direct call. Service A reaches out to Service B and waits for an answer. This is synchronous communication. It works fine when traffic is steady and both sides are fast. But the world isn't steady. A surge in orders — say, 1,000 instead of 10 — can overwhelm the downstream system, and the entire chain stalls.

The second way puts something in between. Service A drops a message into a queue, topic, or stream and moves on immediately without waiting. Service B pulls from that queue whenever it's ready. This is asynchronous communication. Each side scales independently, and the middleware absorbs shocks.

Sync communication can collapse under load. Async puts a buffer in the middle so each side scales independently.
💡 New word Decouple means to disconnect direct dependencies. A queue or topic between two services lets them operate at their own pace without one failing taking down the other.

AWS offers three core tools for this, each designed for a different problem:

  • SQS — when you need a reliable work queue.
  • SNS — when one event needs to reach many independent receivers.
  • Kinesis — when you need real-time streaming at scale.

2SQS Standard Queues Overview

💡 New word SQS (Simple Queue Service) is AWS's oldest and most widely used messaging service — a fully managed queue that lets applications send and receive messages without talking to each other directly.

Think of SQS like a mailbox. A producer (say, your web server) drops a message in. A consumer (maybe a backend worker) picks it up when ready. Once the consumer processes the message and deletes it, it's gone. The queue is the buffer that lets producer and consumer work at different speeds.

Producers send messages into the queue with SendMessage. Consumers poll for messages, process them, then delete to signal completion.

Core facts about SQS Standard queues

PropertyValue
ThroughputUnlimited — as many messages per second as needed, unlimited queue size
Message retention4 days by default, extendable to 14 days — unprocessed messages expire and are lost
LatencyUnder 10 milliseconds on publish and receive
Message sizeUp to 256 KB per message
Delivery guaranteeAt-least-once (messages might be delivered more than once)
OrderingBest-effort (not guaranteed) — unless you use FIFO queues

How producers and consumers work

A producer sends a message using the SendMessage API call through the SDK. A consumer polls the queue with ReceiveMessage (up to 10 messages at a time), processes each one, then deletes it with DeleteMessage. If a consumer doesn't delete a message, other consumers can still see it. Multiple consumers can pull from the same queue in parallel, letting you scale by adding more workers.

🏭 Real-world example A video-encoding app splits the work: a web tier accepts upload requests and drops a "please encode this video" message in SQS, then returns immediately to the user. A separate autoscaling group of worker instances polls the queue, grabs messages, and does the CPU-intensive encoding. When the queue backs up (many videos waiting), CloudWatch detects the queue depth growing and spins up more worker instances. When the queue empties, the ASG scales back down. The web tier never waits, and encoding workers only exist when there's actual work to do.

Security

SQS encrypts messages in transit using HTTPS, and at rest using AWS-managed or KMS-managed keys. Access is controlled by IAM policies (who can call the API) and SQS access policies (resource-based policies that control cross-account or cross-service access).

3SQS Standard Queue Hands-On

Creating and configuring a queue

In the AWS Console, go to SQS and click Create queue. Choose Standard or FIFO (we'll cover FIFO later). You can then configure the visibility timeout, delivery delay, wait time for long polling, how long to keep messages (retention), maximum message size, and encryption.

Encryption options include: disabled (no encryption), SSE-SQS (Amazon-managed encryption key, similar to S3), or SSE-KMS (you choose a specific AWS KMS key, with optional reuse intervals to reduce KMS API calls).

Sending and receiving messages

In the console, open your queue and look for the Send and receive messages panel. Sending a message makes it immediately available. When you poll for messages, SQS returns them along with metadata: message ID, receive count, size, and the body. If you poll again without deleting that message, it reappears after the visibility timeout expires and its receive count increments — only DeleteMessage signals to SQS that processing succeeded.

Other operations: Purge deletes all messages (you must type "purge" to confirm — useful for development), and you can watch monitoring metrics like queue depth and oldest message age to inform scaling decisions.

4SQS Queue Access Policies

💡 New word Access policies are resource-based permissions (like S3 bucket policies) attached to the queue itself, controlling who can send to, receive from, or manage it across accounts or from other AWS services.

Two scenarios drive most access policy use cases.

The first is cross-account access. You run an SQS queue in Account A and an EC2 instance in Account B that needs to poll messages from it. On the queue in Account A, you attach a policy allowing the principal in Account B to call sqs:ReceiveMessage.

The second is letting another AWS service write to your queue. For example, you want S3 to send event notifications to an SQS queue when objects are uploaded. S3 needs permission to call SendMessage on that queue. You attach a policy that allows S3's principal and specifies the source bucket ARN and bucket owner account as conditions.

Common mistake: You create an SNS topic and try to subscribe an SQS queue to it, but the subscription creation fails with "queue not found" or "access denied." The real issue is that your SQS queue access policy doesn't grant the SNS topic permission to send messages. The policy must explicitly allow SNS to write to that queue.

5Message Visibility Timeout

💡 New word Visibility timeout is how long a message stays hidden from other consumers after one consumer receives it. Default is 30 seconds. During this window, if the consumer deletes the message, it's gone for good. If the consumer crashes and doesn't delete it, it reappears and can be processed again.

The visibility timeout prevents duplicate processing in most cases, but it forces you to think about failure modes.

If you set the timeout too high (say, several hours), a consumer that crashes will leave messages invisible for a long time. If you set it too low (say, 5 seconds), a consumer that takes longer than 5 seconds to process a message will have that message picked up again by another consumer, resulting in duplicate processing.

The solution is the ChangeMessageVisibility API call. If your consumer realizes it needs more time, it extends the timeout rather than hoping it finishes in time.

ScenarioRisk
Timeout too highCrashed consumers hold messages hostage for hours
Timeout too lowMessages get reprocessed because consumers can't finish in time
Timeout just rightUse ChangeMessageVisibility if processing takes longer

Visibility timeout is configurable per queue from 0 seconds to 12 hours.

6Dead Letter Queues

💡 New word Dead Letter Queue (DLQ) is a separate queue that catches messages after they've failed processing a certain number of times, letting you investigate failures later without blocking the main queue.

Imagine a consumer processes messages from a queue and keeps failing on the same one — maybe due to a bug, maybe because the data is corrupt. Without intervention, that message keeps bouncing back into the queue after each visibility timeout, getting reprocessed and failing again, indefinitely.

A DLQ breaks this cycle. You configure the source queue with a maximum receive count (say, 3). If a message is received 3 times without being deleted, SQS moves it to the DLQ automatically. The main queue is no longer blocked, and you can inspect the DLQ messages at leisure to debug what went wrong.

Once you've fixed the issue, SQS provides a redrive feature that sends messages from the DLQ back to the source queue for reprocessing.

Important rules

  • A FIFO queue's DLQ must also be FIFO; a Standard queue's DLQ must also be Standard.
  • Set a long retention period on the DLQ (14 days is typical) so you have time to investigate and fix the underlying problem.

7Delay Queues

💡 New word Delay queue hides new messages from consumers for a set duration (up to 15 minutes) after they're sent. Default is 0 seconds (immediately available).

This is useful when you want to send a message but have it processed later. Set a delay at the queue level as a default, or override it per-message by passing the DelaySeconds parameter to SendMessage.

Just know this exists: It's a simple feature, not complex. The exam expects you to remember that SQS supports delayed delivery.

8SQS Developer Concepts

Long polling

By default, ReceiveMessage returns immediately if the queue is empty. If you make that call every second, you're paying for thousands of empty API calls. Long polling is better: the consumer says "wait up to 20 seconds for a message," and SQS holds the connection open. As soon as a message arrives, it's delivered. If nothing arrives, the consumer is told after the timeout.

This reduces API calls, cuts costs, and often reduces latency because the consumer doesn't miss messages while polling repeatedly. Set long polling at the queue level or on the ReceiveMessage call itself using ReceiveMessageWaitTimeSeconds (range 1–20 seconds; 20 is recommended).

Exam hint: If a scenario describes an app making too many API calls (driving up costs or CPU), the answer is often long polling.

Handling large messages

SQS limits messages to 256 KB. If you need to send a 1 GB video file, SQS alone can't carry it. The SQS Extended Client pattern solves this: the large payload goes to an S3 bucket, and SQS only carries a small metadata message pointing to it. The consumer reads the pointer and fetches the real payload from S3.

Key SQS API calls

APIPurpose
SendMessageAdd a message to the queue (supports DelaySeconds)
ReceiveMessagePoll for messages (up to 10 at a time, supports ReceiveMessageWaitTimeSeconds for long polling)
DeleteMessageRemove a processed message
ChangeMessageVisibilityExtend the visibility timeout if processing takes longer
CreateQueue / DeleteQueueManage the queue itself
PurgeQueueDelete all messages in a queue (for testing)

All three of SendMessage, DeleteMessage, and ChangeMessageVisibility have batch versions to reduce API call count and cost.

9FIFO Queues

💡 New word FIFO (First-In-First-Out) queues guarantee that messages are processed in the exact order they were sent, and each message is delivered exactly once. Queue names must end with .fifo.

Standard queues prioritize throughput and simplicity over ordering and guarantees. FIFO queues trade some throughput for strict ordering and exactly-once delivery.

FeatureStandardFIFO
OrderingBest-effort (possibly out of order)Strictly preserved
DeliveryAt-least-once (duplicates possible)Exactly-once per message group
Max throughputUnlimited~300 messages/second (3,000 with batching)

Deduplication

SQS FIFO detects duplicates within a 5-minute window using either content-based hashing (SQS computes a SHA-256 hash of the message body; identical bodies are dropped) or an explicit deduplication ID that you provide (you control what counts as a duplicate).

Message grouping

Every FIFO message requires a message group ID. Messages with the same group ID are processed strictly in order and are consumed by a single consumer. Different group IDs can be processed in parallel by different consumers. This gives you per-customer or per-entity ordering without sacrificing concurrency.

🏭 Real example An e-commerce app uses FIFO with a message group ID of the customer ID. All of Alice's orders are processed in the exact sequence she placed them, and a single worker handles Alice's queue. Meanwhile, Bob's orders are processed in sequence too, but a different worker handles them — orders from Alice and Bob can be shipped in parallel, but Alice's orders can never ship out of order.

10Amazon SNS

💡 New word SNS (Simple Notification Service) is a publish-subscribe (pub/sub) service. One producer publishes a message to an SNS topic once, and every subscriber receives a copy automatically — the producer doesn't need to know who the subscribers are or how many there are.

Think of SQS as a mailbox where one person pulls out messages. SNS is more like a megaphone: the broadcaster shouts once, and everyone listening hears it.

SNS topics can have thousands of subscribers. Subscriber types include email, SMS, mobile push notifications, HTTP/HTTPS endpoints, and AWS services like SQS, Lambda, and Kinesis Data Firehose. Many AWS services (CloudWatch, Auto Scaling, S3, RDS events, etc.) can publish directly into SNS topics.

Publishing patterns

The typical pattern is topic publish: create a topic, add subscriptions, then publish messages. Every confirmed subscriber gets a copy. SNS also supports direct publish for mobile applications, where you publish directly to a device endpoint using services like Apple APNS or Google GCM.

Security

SNS supports encryption in transit (HTTPS) and at rest (KMS). Access is controlled by IAM policies (API calls) and SNS access policies (resource-based, controlling who can publish or subscribe).

11SNS & SQS Fan-Out Pattern

💡 New word Fan-out is the pattern of publishing one message to many independent receivers. SNS pushes to multiple subscribers; SNS + SQS combines that with durability.

Suppose you have an order confirmation event that needs to reach fraud detection, shipping, and analytics — three independent systems. If you publish directly to each queue, you risk a partial failure: fraud detection gets it, shipping doesn't, and now your data is inconsistent. If you publish to SNS and subscribe three SQS queues to it, all three get a copy, and each can retry independently if it fails.

One SNS topic fans out to multiple SQS queues. Each queue has its own retention and consumer, so failures are independent.

SNS publishes the same message to each subscribed SQS queue. You must grant each SQS queue an access policy allowing the SNS topic to send messages to it. The pattern works across regions too — an SNS topic in us-east-1 can fan out to SQS queues in eu-west-1.

Other fan-out scenarios

S3 event notifications can trigger only one target per (event type + prefix) combination. To notify multiple systems, publish the S3 event to SNS, then subscribe multiple SQS queues. Similarly, SNS can fan out directly to Kinesis Data Firehose, which then loads data into S3 or other destinations — no custom code needed.

SNS FIFO

SNS also offers FIFO mode: messages stay ordered by message group ID and are deduplicated (content-based or explicit ID). But FIFO SNS can only subscribe to FIFO SQS queues, and throughput is lower. Use it when you need fan-out, ordering, and deduplication together.

Message filtering

A JSON filter policy on a subscription lets you restrict which messages that subscriber receives. For example, one SQS queue gets only fraud-flagged orders, another gets only international orders, and a third gets everything — all from the same SNS topic.

12SNS Hands-On

Creating a topic and adding subscriptions

In the SNS console, click Create topic. Choose Standard (best-effort ordering, at-least-once delivery, high throughput) or FIFO (strict ordering, exactly-once, lower throughput, SQS subscribers only).

From the topic details page, click Create subscription. Choose the protocol: Kinesis Data Firehose, SQS, Lambda, Email, Email-JSON, HTTP, HTTPS, or SMS. Provide the endpoint (e.g., your email address).

Email subscriptions require confirmation — SNS sends a confirmation link to your inbox. You must click it before you start receiving messages. SMS and HTTPS endpoints work similarly.

Publishing a test message

On the topic page, click Publish message. Enter a subject and message body, then publish. Every confirmed subscriber receives it (email will show up in their inbox, HTTPS endpoints will get an HTTP POST, etc.).

13Kinesis Data Streams

💡 New word Kinesis Data Streams is a real-time streaming service for continuous data flows like application logs, IoT sensor readings, or click-stream events. Producers send records constantly; consumers read and process them as they arrive.

SQS and SNS are good for discrete events. Kinesis is for continuous, high-volume data. An IoT device sends sensor readings every second. A web server logs thousands of requests per minute. Kinesis ingests all of it in real time, and consumers can process the stream live or replay it hours later.

💡 New word Shard is the unit of throughput in a Kinesis stream. Each shard can handle 1 MB of data per second inbound and 2 MB outbound. A stream with 3 shards can handle 3 MB/sec in and 6 MB/sec out.

Core characteristics

PropertyValue
Retention1 to 365 days — data is persistent and replayable
Record sizeUp to 1 MB per record
OrderingGuaranteed within a shard (partition key determines shard)
Throughput modesProvisioned (you choose shard count) or on-demand (auto-scales)

Producers and consumers

Producers use the Kinesis SDK (or the Kinesis Agent, a lightweight daemon for servers to send metrics/logs). Consumers can be Lambda, EC2, Kinesis Data Firehose, or the Managed Service for Apache Flink. Multiple consumers can read the same stream in parallel using different shards or the same shard (with lower throughput per consumer).

Scaling

In provisioned mode, you specify how many shards you want and pay per shard-hour. Each shard is independent. In on-demand mode, AWS watches your traffic for 30 days and auto-scales shard count based on what it observes — you pay per stream-hour plus per unit of data written and read.

🏭 In the real world Companies use Kinesis Streams with the Kinesis Agent installed on every server. The agent batches logs and metrics, sends them to Kinesis, and a Kinesis Data Firehose (or Flink) processes them, transforming and loading them into S3 for later analysis or into real-time dashboards.

14Kinesis Data Streams Hands-On

Creating a stream

In the Kinesis console, click Create stream. Choose a name, then select On-demand (auto-scaling, no free tier) or Provisioned (specify a shard count; 1 shard is cheapest for testing).

Sending data (CLI)

To send a record to a stream, use:

aws kinesis put-record \
  --stream-name my-stream \
  --partition-key my-key \
  --data "hello world" \
  --cli-binary-format raw-in-base64-out

The partition-key determines which shard the record lands on (same key always goes to the same shard, preserving order for that key). Data is base64-encoded when sent.

Reading data (CLI)

Reading is multi-step: first, describe the stream to find shard IDs, then get a shard iterator, then fetch records:

aws kinesis describe-stream --stream-name my-stream
aws kinesis get-shard-iterator \
  --stream-name my-stream \
  --shard-id shardId-000000000000 \
  --shard-iterator-type TRIM_HORIZON
aws kinesis get-records --shard-iterator <iterator>

TRIM_HORIZON starts from the beginning of the stream. Each response includes a NextShardIterator for the next call. (The Kinesis Client Library hides this complexity in real applications.)

15Amazon Data Firehose

💡 New word Amazon Data Firehose (formerly Kinesis Data Firehose) is a fully managed, auto-scaling service that ingests data from streams and AWS services, buffers it, and delivers it to destinations like S3, Redshift, OpenSearch, or third-party tools — with no code needed on your part.

Firehose is for near real-time delivery (it buffers data, which introduces a slight delay). You create a delivery stream specifying a source (Kinesis Streams, Direct PUT, CloudWatch, IoT, or another AWS service) and a destination (S3, Redshift, OpenSearch, Splunk, Datadog, or a custom HTTP endpoint). Firehose handles the buffering, compression, format conversion, and delivery for you.

How it works

You send data to Firehose. It accumulates records in a buffer (you set buffer size and/or time interval — whichever limit hits first, it delivers). Before delivery, it can optionally invoke a Lambda function to transform each record. It then compresses the batch and sends it to the destination.

FeatureKinesis Data StreamsAmazon Data Firehose
PurposeReal-time streaming — you write producer/consumer codeLoad streaming data into destinations — fully managed
TimingReal-time (immediate)Near real-time (buffered, slight delay)
Replay capabilityYes, up to 365 daysNo — data is delivered, not stored
ScalingYou manage shards (provisioned) or AWS auto-scales (on-demand)Fully automatic, no capacity planning
Important difference: Firehose buffers and batch-delivers; it doesn't store data like Kinesis does. If you need to replay records or do complex stream processing, use Kinesis Data Streams or a stream + Firehose combo.

16Amazon Data Firehose Hands-On

Creating a delivery stream

In the Firehose console, click Create delivery stream. Choose a source (Direct PUT, Kinesis Data Streams, CloudWatch Logs, IoT, or EventBridge). Choose a destination (S3, Redshift, OpenSearch, Splunk, Datadog, or HTTP).

Configuring the pipeline

Optionally add a data transformation Lambda function. Optionally convert the record format (e.g., JSON to Parquet for efficient S3 storage). Set buffer hints: a buffer size (e.g., 128 MB) and interval (e.g., 60 seconds). Whichever condition is met first triggers delivery. Smaller/faster settings mean quicker delivery but less compression efficiency.

Choose compression (gzip, Snappy, Zip, or none). Firehose automatically creates an IAM role with the permissions needed to read from your source and write to your destination.

Gotcha: Firehose only picks up data sent after the stream is created. Old records already in a Kinesis stream won't retroactively flow through. Send fresh test data, then wait out the buffer interval before checking the destination.

17Managed Service for Apache Flink

💡 New word Apache Flink is a real-time stream processing framework for transformation, aggregation, and complex logic on continuous data. AWS's Managed Service for Apache Flink runs Flink without you managing the infrastructure.

Kinesis Data Streams gives you the raw data. If you need to process it — aggregating metrics, detecting patterns, joining with reference data — Flink is for that. It reads from Kinesis Data Streams or Apache MSK (managed Kafka). You write SQL, Java, or Scala to define your processing logic. AWS runs it on a fully managed cluster with auto-scaling, checkpointing for fault tolerance, and built-in backup.

Exam trap: Flink reads from Kinesis Data Streams and MSK, but not directly from Amazon Data Firehose.

📋 Cheat Sheet

Core Building Blocks

ConceptWhat it does
SQSFully managed queue. Producers send, consumers pull. Decouple app tiers, buffer work. At-least-once delivery, best-effort ordering.
SNSPub/sub messaging. One publish, many subscribers get a copy. For fan-out and notifications. Not persistent on its own.
SNS + SQSCombine for durable fan-out — SNS publishes once, multiple SQS queues each get a persistent copy.
Kinesis StreamsReal-time streaming. Producers send continuously, consumers read as data arrives. Replayable for 1–365 days.
FirehoseManaged delivery service. Buffers streaming data, transforms with Lambda, delivers to S3/Redshift/OpenSearch/HTTP. Near real-time, not persistent.

Key Facts Worth Remembering

  • SQS Standard: unlimited throughput, 256 KB max message, 4–14 day retention, at-least-once delivery, best-effort ordering.
  • Visibility timeout (default 30s) hides a message from other consumers; extend it with ChangeMessageVisibility if processing takes longer.
  • Dead Letter Queues catch repeatedly failed messages (exceeding maxReceiveCount). Redrive them back to the source once fixed.
  • Long polling (1–20 seconds) reduces API calls and latency — always prefer it over short polling.
  • SQS FIFO: strict ordering per message group ID, exactly-once delivery (deduplication), ~300 msg/sec (3,000 with batching).
  • SNS is fully push-based; SNS + SQS fan-out makes it durable.
  • Kinesis: real-time streaming, ordered per shard (partition key), replayable up to 365 days, provisioned or auto-scaled capacity.
  • Firehose: fully managed, auto-scaling, batch delivery to S3/Redshift/OpenSearch/HTTP. No replay, near real-time (buffered).
  • Flink reads from Kinesis or MSK, never directly from Firehose.

Decision Guide

  • Two app tiers, one gets overwhelmed by the other? SQS Standard queue for decoupling and scaling.
  • Need strict ordering and no duplicates within a group? SQS FIFO with message group ID.
  • One event, many independent systems need to react? SNS (direct) or SNS + SQS fan-out (durable).
  • Real-time data stream you need to replay or analyze? Kinesis Data Streams.
  • Load streaming data into S3 or a warehouse with minimal code? Amazon Data Firehose.
  • Real-time transformation and complex stream processing? Managed Service for Apache Flink on top of Kinesis or MSK.

One-Paragraph Summary

Decoupling is the theme: instead of services calling each other directly (fragile under load), put a middleware in between. SQS is a reliable work queue that scales producer and consumer independently. SNS broadcasts one message to many subscribers (not persistent by itself, but durable when combined with SQS in a fan-out pattern). Kinesis is for real-time, continuous data streams that you can process live or replay later. Firehose is the fully managed bridge from streams into data warehouses and analytics platforms. Pick based on your problem: discrete work units (SQS), fan-out notifications (SNS + SQS), or real-time big data (Kinesis + Firehose + Flink).
