1EBS Overview

Picture this: your EC2 server hard-crashes, or you shut it down on purpose to resize it. What happens to every file you saved on it? If that data only ever lived on the server's own local disk, it would be gone for good. This is exactly the problem EBS exists to solve.

💡 New word EBS stands for Elastic Block Store. It is a virtual hard drive that lives on the network, separate from the server itself. You attach it to an EC2 instance while that instance is running.

Because an EBS volume lives outside the server, your data survives even if the server is stopped or terminated. Think of it less like a hard drive soldered into a laptop, and more like an external drive plugged in over the network. If the "computer" breaks, you unplug the drive and plug it into a new one — nothing on it is lost.

A few rules define how EBS actually behaves, and each one shows up again and again on the exam and in real production accounts.

First, by default, an EBS volume attaches to only one EC2 instance at a time. (There's one narrow exception, called Multi-Attach — we'll get to it later on this page.) Second, every EBS volume is locked to one specific location inside AWS, called an Availability Zone.

💡 New word Availability Zone (AZ) is one physical data center location inside an AWS Region. A Region, like Mumbai or N. Virginia, is actually made up of several AZs — so if one AZ has a problem, the others keep running.

So a volume created in us-east-1a can only attach to servers that are also running in us-east-1a. It cannot reach across to a server sitting in us-east-1b — not directly, anyway. (There is a workaround, and it's called a snapshot — that's next on this page.)

Third, because the connection runs over a fast internal network rather than a physical cable, you can detach a volume from one server and reattach it to another in seconds. And fourth, you choose the size and the speed you want upfront — speed here is measured in IOPS — and you pay for what you provisioned, whether you use all of it or not.

💡 New word IOPS stands for Input/Output Operations Per Second. It measures how many read or write operations a disk can handle every second — basically, how "fast" the drive feels under real load.
EBS volumes are locked to a specific Availability Zone (AZ). They cannot directly connect across AZ boundaries.

What happens to your data when a server is terminated?

Terminating an EC2 instance is permanent — you can't restart a terminated server. So what happens to the EBS volumes attached to it? That comes down to one setting: Delete on Termination.

By default, AWS treats your root volume — the one holding the operating system — differently from any extra volume you attached yourself. The root volume has Delete on Termination switched on, so it disappears the moment the instance is terminated. A secondary volume you attached later has it switched off by default, so it survives, sitting there as an unattached "orphaned" volume — still quietly costing you money until you delete it yourself.

Volume TypeDefault SettingBehavior when Instance Terminated
Root OS VolumeEnabled (Yes)Automatically deleted along with the instance.
Secondary Attached DrivesDisabled (No)Survives termination and remains saved as an orphaned volume.
🏭 A common real cost mistake Teams that spin up and terminate test servers all day, without cleaning up after themselves, often end up paying for dozens of orphaned EBS volumes nobody is using anymore — because extra volumes were never set to delete automatically, and nobody went back to remove them by hand. Checking for unattached ("available") volumes on a regular schedule is a routine part of keeping an AWS bill under control. It's even step 3 of the clean-up checklist later on this page.
Exam trap: if a question asks how to keep data on a root volume safe when terminating an instance, the answer is to turn OFF Delete on Termination for that root volume before you terminate it.

2EBS Hands-On

Here's what creating and attaching a volume actually looks like in the console, step by step.

  1. Open the EC2 Console, click on any running instance, then open its Storage tab to see every volume already attached — the root drive plus any extra block drives.
  2. To add a new one, go to Volumes, click Create Volume, pick a size and type, and — this part is easy to miss — choose the exact same Availability Zone your server is running in.
  3. Select that new volume, open Actions, click Attach Volume, and pick your server from the list.
Gotcha: if your server is in ap-south-1a and your volume is in ap-south-1b, AWS simply will not let you attach it. There's no override — matching Availability Zones is not optional.

3EBS Snapshots

We just said an EBS volume is stuck inside one Availability Zone forever. So what do you do when you genuinely need to move that data — say, to rebuild in another AZ after a failure, or copy it to a completely different Region? You take a snapshot.

💡 New word Snapshot — a point-in-time backup of an EBS volume's data. Unlike the volume itself, a snapshot isn't locked to one AZ. It's saved at the whole-Region level, so it can be used to build a brand new volume anywhere in that Region.
To move EBS data to another AZ or Region: take a snapshot, then restore that snapshot into a new EBS volume in the destination AZ.

In other words: the data effectively "teleports" across the AZ boundary that a live volume can never cross on its own.

🏭 Why this matters in practice For any real database running on EC2, EBS snapshots are the standard backup mechanism. Most companies automate them on a schedule — say, every night — using a tool like AWS Backup, rather than relying on someone remembering to click "Create Snapshot" by hand. When a disk fails or a bad deployment corrupts data, the snapshot is what actually saves the day.

Three extra snapshot features worth knowing

FeatureFunctionTrade-Off
EBS Snapshot ArchiveMoves snapshots to a low-cost archive tier (up to 75% savings).Retrieving data takes 24 to 72 hours.
Recycle Bin for SnapshotsSaves accidentally deleted snapshots for recovery (1 day to 1 year).Requires setting retention rules.

Trade-off to remember: the Archive tier is cheap to store in, but slow to get back — budget 24 to 72 hours if you ever need to restore from it. Don't archive a snapshot you might need back in a hurry.

4EBS Snapshots Hands-On

Moving data across AZs or Regions with a snapshot takes just a few clicks.

  1. Select the volume, open Actions, and click Create Snapshot.
  2. To copy the data into a different Region: right-click the snapshot, click Copy Snapshot, and pick the destination Region.
  3. To move it to a different AZ inside the same Region: select the snapshot, open Actions, click Create Volume from Snapshot, and choose a different AZ — for example us-east-1b.

5AMI Overview

Imagine you've just spent an afternoon getting one EC2 server exactly right — operating system installed, your app's dependencies configured, settings tuned. Now you need twenty identical servers for a traffic spike. Nobody wants to repeat that afternoon twenty times. That's exactly the problem an AMI solves.

💡 New word AMI stands for Amazon Machine Image. It's a saved template of a server — its operating system, its installed software, its configuration, and its permissions — used to launch new servers that start out identical to the original.

There are three sources for an AMI. AWS provides Public AMIs — clean, official images like Amazon Linux 2 or Ubuntu. You can build your own Custom AMIs — a "golden image" your own team configures and maintains. And outside vendors sell Marketplace AMIs — ready-made templates for products like SAP, WordPress, or a preconfigured firewall.

To build a custom AMI: launch a server, install software, stop the server, then create an image (the AMI).

Building a custom AMI always follows the same four steps: launch a server, install and configure whatever it needs, stop the server so its disk is in a clean state, then create the image.

6AMI Hands-On

In the console, that four-step process looks like this.

  1. Launch an EC2 server and install whatever software packages it needs.
  2. Stop the server — this matters, because stopping first keeps the saved disk data consistent.
  3. Right-click the instance, choose Image and templates, then click Create Image.
  4. From then on, launch new servers straight from that image under My AMIs — they start up already fully configured, with no setup time.
🏭 In real companies This is exactly how Auto Scaling works in a real production fleet. When traffic spikes and more servers are needed, Auto Scaling doesn't install software from scratch on each new server — it launches new instances straight from a pre-built, already-tested AMI. That's what makes it possible to go from one server to fifty in minutes instead of hours.

7EC2 Instance Store

EBS is durable and flexible, but there's a catch: it connects to your server over the network, and that adds a small amount of delay. Most applications never notice it. But for workloads that genuinely need the fastest possible disk speed, AWS offers a different option: the EC2 Instance Store.

💡 New word Instance store is high-speed storage — usually an SSD (Solid-State Drive) — physically attached to the same physical host machine your EC2 server runs on. There's no network hop, so it's about as fast as disk storage gets.
EBS offers durable network storage. Instance store offers ultra-fast physical disk speed, but its data is ephemeral (temporary).

That raw speed comes at a real cost, though.

Critical limitation: instance store is ephemeral, meaning temporary. Stop or terminate the instance, and every byte stored on it is erased permanently — there's no way to get it back. Use it only for data you can afford to lose: temporary caches, buffers, or scratch space.
🏭 Why this is actually a well-known best practice This isn't a design flaw teams work around — it's a trade-off real systems lean into on purpose. Big-data clusters running Hadoop or Spark on EC2 commonly use instance store for temporary "shuffle" and scratch data — the huge intermediate files created and thrown away while a job is processing. Since that data is disposable anyway, its raw speed is worth far more than its durability. The rule these teams never break: nothing that needs to survive a restart ever gets written only to instance store.

8EBS Volume Types

Not every EBS volume is built the same way underneath. AWS actually sells four different families of EBS volumes, each tuned for a different kind of workload — and picking the wrong one either wastes money or slows your application down.

💡 New word HDD (Hard Disk Drive) is the older, spinning-disk style of storage. It's slower than an SSD for random access, but cheaper, and it's fine for data that's read in big sequential chunks rather than small scattered pieces.
FamilyVolume TypesBootable?Best Use Case
General Purpose SSDgp2, gp3✅ YesDefault balanced storage for web servers, dev environments.
Provisioned IOPS SSDio1, io2 Block Express✅ YesHigh-performance mission-critical databases requiring low latency.
Throughput Optimized HDDst1❌ NoBig data, log processing, data warehousing (sequential I/O).
Cold HDDsc1❌ NoInfrequently accessed archival data (lowest cost).

General Purpose SSD is the default, balanced choice for most workloads — web servers, dev boxes, ordinary apps. Provisioned IOPS SSD is built for demanding, latency-sensitive databases that need guaranteed, consistent performance. Throughput Optimized HDD suits big sequential workloads like log processing or data warehousing, and Cold HDD is the cheapest option, for data you rarely touch. Notice that only the two SSD families can boot an operating system — the two HDD types can't be used as a root volume at all.

gp2 vs gp3: the two generations of General Purpose SSD

With the older gp2, disk size and speed are locked together — the bigger the volume, the more IOPS you automatically get, whether you wanted them or not. The newer gp3 breaks that link. It starts you off with a fixed baseline of 3,000 IOPS and 125 MB/s of throughput, and lets you dial in more of either, independently of how big the disk is.

gp2 links disk size with speed performance. gp3 decouples disk size and performance, often at a lower cost.
🏭 In real companies This is exactly why most teams default to gp3 today — it's usually both faster and cheaper than an equivalent gp2 volume, because you're no longer forced to buy extra disk space you don't need just to unlock more speed. It's also common to see companies pay for the pricier, higher-IOPS io2 family only on their production database tier, while dev and staging databases run on plain gp3 — same database engine, very different storage bill.

9EBS Multi-Attach

Earlier we said an EBS volume attaches to only one server at a time. That's the default rule — but there's one narrow, specific exception: EBS Multi-Attach.

💡 New word Multi-Attach lets one single EBS volume attach to up to 16 EC2 instances at the same time, as long as they're all in the same Availability Zone. Every instance it's attached to gets full read and write access to it.
Multi-Attach rules: supported only on Provisioned IOPS SSDs (io1/io2), within the same Availability Zone, up to 16 servers.
Gotcha: Multi-Attach only works on Provisioned IOPS volumes — io1 and io2 — never on gp2/gp3. And it doesn't magically make ordinary applications safe to run in parallel: your application (or its filesystem) still has to be built to handle several servers writing to the same disk at once, or you'll corrupt your own data.
🏭 In real companies Multi-Attach exists for a narrow, specific case: clustered applications that already know how to coordinate shared storage themselves, such as certain clustered database engines designed for exactly this pattern. It's not a general-purpose way to let two unrelated apps share a disk — most production systems never touch this feature at all, and reach for Amazon EFS instead when they genuinely need shared storage.

10Amazon EFS

Multi-Attach only works inside one Availability Zone, and only for applications specifically built to share a disk safely. What if you need something simpler — dozens of ordinary Linux servers, spread across several Availability Zones, all reading and writing the exact same files? That's what EFS is for.

💡 New word EFS stands for Elastic File System. It's a managed, shared file system that many EC2 instances can mount and use at the same time — even instances sitting in different Availability Zones.
💡 New word NFS (Network File System) is the standard protocol EFS uses under the hood, letting Linux servers mount and use it just like a regular folder on disk.
Amazon EFS works across multiple AZs at once, giving shared file access to a whole fleet of Linux servers.

Unlike an EBS volume, which belongs to exactly one server (or up to 16, in that one narrow Multi-Attach case), an EFS file system can be mounted by hundreds of instances at once, spread across a whole Region.

A few things worth knowing about how EFS behaves

  • It only works with Linux. EFS uses POSIX file permissions — the standard Linux/Unix permission model — and it isn't compatible with Windows servers at all.
  • You don't provision size upfront, the way you do with EBS. EFS grows and shrinks automatically, and you only pay for the bytes you actually store.
  • It offers storage tiers — Standard for frequently used files, Infrequent Access (EFS-IA), and an Archive tier for older files — which together can cut storage costs by up to 90%.
🏭 Why this matters in practice A common real use for EFS is shared configuration files or uploaded-file storage across a fleet of web servers sitting behind a load balancer — every server needs to see the same files, no matter which Availability Zone it's in, or how many extra servers Auto Scaling adds. Trying to do that with individual EBS volumes would mean copying files to every single server by hand.

11Amazon EFS Hands-On

Here's what actually proving cross-AZ file sharing looks like, step by step.

  1. Open the EFS Console, click Create File System, and select the VPC it should live in.
  2. You can mount EFS directly during the EC2 launch wizard when creating a new server.
  3. Create a file on Server A, sitting in AZ-a: 
    echo "Hello AWS" > /mnt/efs/fs1/hello.txt
  4. Log into Server B, sitting in a different zone, AZ-b, and check the same folder: 
    cat /mnt/efs/fs1/hello.txt
# Output -> Hello AWS

Server B sees the exact file Server A just created, instantly — even though they're running in different Availability Zones. That's the whole value of EFS in one small test.

12EFS vs EBS vs Instance Store

We've now covered three different ways to give an EC2 server storage. Here's the side-by-side comparison that actually matters when deciding which one to reach for.

PropertyEBSEFSInstance Store
Primary PurposeVirtual hard drive for a single server.Shared file system for a server fleet.Ultra-high-speed temporary cache drive.
Attachment Limit1 instance (except io1/io2 Multi-Attach, up to 16).Hundreds of instances concurrently.1 instance host.
Availability ZoneLocked to 1 AZ.Spans multiple AZs across the Region.Locked to the physical hardware host.
OS CompatibilityLinux & Windows.Linux only (POSIX/NFS).Linux & Windows.
Data PersistenceDurable (survives server reboot/stop).Durable (independent of any one server).Ephemeral (erased on stop/terminate).
Comparison of EBS, EFS, and Instance Store storage trade-offs.

In one line each: EBS is your durable, personal network drive, locked to one server (or up to 16, with Multi-Attach) and one AZ. EFS is a shared network drive many servers can use at once, across many AZs. Instance store is the fastest option there is, physically attached to one host — but everything on it disappears the moment that server stops.

13Clean-Up Checklist

One thing all three storage types share: they keep costing money until you explicitly delete them, even long after you've stopped actively using them. Before you walk away from a test environment, work through this order.

  1. Delete EFS file systems.
  2. Terminate all running EC2 instances.
  3. Delete any unattached EBS volumes sitting in the "available" state.
  4. Delete saved EBS snapshots you no longer need.
  5. Delete non-default security groups.
Why this order: you can't delete an EBS volume while it's still attached to a running instance, so terminating instances first, then cleaning up the storage left behind, avoids getting stuck halfway through.

Key Facts Worth Remembering

  • EBS is a network drive, locked to one AZ, and attached to one instance by default.
  • Delete on Termination is on for root volumes, off for extra volumes, by default.
  • Snapshots live at the Region level — the way you move EBS data across an AZ or Region.
  • Instance store is the fastest storage there is, but it's ephemeral — wiped on stop/terminate.
  • EBS Multi-Attach: max 16 instances, only io1/io2, same AZ only.
  • gp3 baseline: 3,000 IOPS / 125 MB/s, decoupled from disk size.
  • EFS is Linux-only, mountable by hundreds of instances, across multiple AZs.
  • Snapshot Archive tier recovery: 24 to 72 hours delay.

The One-Paragraph Version

EBS is your personal network drive, locked to one AZ, and it survives a stopped or terminated instance if you configure it to. Snapshots let you back up and move that EBS data across AZs and Regions. AMIs save a fully configured server as a template so you can launch identical copies instantly. Instance store gives you the fastest possible physical disk speed, but every byte on it disappears the moment the server stops. EFS is a shared network drive that hundreds of Linux servers can use at once, across multiple AZs — the option to reach for when many servers genuinely need the same files.
