51CloudFront Introduction

Imagine a user in Brazil trying to download a website hosted on a server in Australia. That request travels across the entire world, taking time and costing bandwidth. CloudFront fixes this.

💡 New word CloudFront is AWS's Content Delivery Network (CDN) — a network of servers spread around the world that cache and serve content to users from locations near them, not from the origin server far away.
💡 New word CDN stands for Content Delivery Network. The purpose is simple: cache content close to where users are so they get it faster, and so your origin server handles less load.

CloudFront uses hundreds of Edge Locations — small data centers positioned on every continent — to cache static content like images, video, HTML, and CSS.

💡 New word Edge Location is a small AWS facility positioned close to cities worldwide (distinct from a Region, which is much larger). It's where CloudFront caches your content.

How the Speed Works

The first user in Brazil requesting a file triggers a Cache Miss — the Edge Location doesn't have it yet, so CloudFront fetches it from the origin server in Australia and stores a copy locally. The next Brazilian user gets a Cache Hit — the Edge Location serves that file instantly from its cache, cutting latency from hundreds of milliseconds to single-digit milliseconds.

💡 New word Latency is network delay — how long it takes for data to travel from point A to point B. Lower latency means faster page loads.
The first request pulls from the origin and caches at the edge. Subsequent requests are served instantly from the edge.

Where Content Comes From

CloudFront can pull content from several types of sources, called Origins. The most common are S3 buckets (for static files), Application Load Balancers or EC2 instances (for dynamic content), and any public HTTP server.

💡 New word Origin is the backend source where CloudFront gets the actual content. It can be an S3 bucket, a load balancer, an EC2 instance, or any web server that responds to HTTP requests.

CloudFront vs S3 Cross-Region Replication

Both can distribute content globally, but they solve different problems. CloudFront caches content temporarily at edges, reducing latency for reads. S3 Cross-Region Replication copies entire buckets to different AWS Regions for real-time data durability and read-local access. Use CloudFront when you want to serve cached static files fast. Use replication when you need near-real-time copies of live data in specific Regions.

AspectCloudFrontS3 Cross-Region Replication
Coverage200+ Edge Locations globallyOnly specified Regions
Data freshnessCached (subject to TTL)Near real-time copies
Best forStatic files, fast readsDynamic data, specific Regions

Built-in Security

CloudFront integrates with AWS Shield (automatic DDoS protection) and AWS WAF (Web Application Firewall) to block common attacks. Because content is distributed across a global network, attackers would have to target hundreds of locations at once — much harder than hitting a single origin server.

🏭 In real companies CDNs are the standard way to serve websites and media globally. Companies like Netflix, Spotify, and major news outlets all use CDNs (often AWS CloudFront, but sometimes Cloudflare or Akamai) because the latency difference between "served from one data center" and "served from a nearby edge location" directly affects user behavior — research shows even 100 milliseconds of added delay causes measurable drops in engagement.

52CloudFront Hands-On Setup

Setting up a CloudFront distribution is a straightforward process. First, create a private S3 bucket and upload files to it. If you try to access those files directly via their S3 URL, you'll get an Access Denied error — exactly what you want, because CloudFront should be the only way users can reach them.

Next, navigate to CloudFront in the AWS console and create a new distribution. You'll choose your S3 bucket as the origin. At this point, you'll configure something called Origin Access Control (OAC).

💡 New word Origin Access Control (OAC) is a security mechanism that grants CloudFront exclusive permission to read from your S3 bucket. Public users cannot access the bucket directly — they can only get content through CloudFront.

When you set up OAC, AWS automatically generates an S3 bucket policy snippet. Copy it and attach it to your bucket. That policy tells S3: "Only CloudFront distribution X is allowed to read from this bucket."

Deploy the distribution. Within a few minutes, CloudFront assigns you a domain name like d111111abc.cloudfront.net. When you visit that domain with a direct file path (e.g., /image.jpg), the file loads instantly from the nearest Edge Location. If you reload, the Edge Location serves it again from cache — second load is nearly instant.

If the bare distribution domain returns Access Denied, that's expected — there's no default index file. Use a direct file path like /coffee.jpg instead.

53Understanding Caching

Every CloudFront Edge Location maintains its own cache. When a file is requested, CloudFront uses a Cache Key to look it up. By default, the Cache Key is just the domain name plus the file path — for example, mywebsite.com/images/banner.jpg.

💡 New word Cache Key is the unique identifier CloudFront uses to store and retrieve a cached file. It's what CloudFront looks at to decide if the requested file is already in cache or needs to be fetched from the origin.

The entire goal of caching is to maximize the Cache Hit Ratio — the percentage of requests served from the cache instead of going all the way to the origin. A higher ratio means faster responses and less load on your backend.

But here's the complication: websites often serve different content based on the user's language, device type, or authentication cookies. If you want CloudFront to cache different versions of the same file for different users, you need to tell it what varies. You do that with a Cache Policy.

💡 New word Cache Policy customizes what goes into the Cache Key. You can include HTTP headers (like language preferences), query string parameters, or cookies, so CloudFront caches separate copies for each variation.

For example, if you include the header Accept-Language in your Cache Policy, CloudFront will cache one version for English and another for Spanish. Each language gets its own cached file.

Including too many variations (especially if you check "All headers" or "All cookies") lowers your Cache Hit Ratio because fewer requests share the exact same Cache Key. Be selective.

You can also set TTL — Time To Live — which controls how long a file stays in the cache before CloudFront considers it stale and fetches a fresh copy from the origin.

💡 New word TTL (Time To Live) is how long a cached file is considered fresh. After the TTL expires, the next user request will fetch a new copy from the origin, even if the file hasn't changed.

Origin Request Policy: The Separate Concern

Sometimes your origin server needs headers, cookies, or query parameters to process a request properly — but you don't want those variations to split your cache. That's where Origin Request Policy comes in.

An Origin Request Policy forwards extra information to your origin without changing the Cache Key. The cache stays unified, but the origin gets the data it needs. For example, you might want all user sessions to share a cached HTML page, but you want to send a session cookie to the origin so it knows which user it's serving.

54Cache Invalidations

You deploy a new version of your website. But some users are still seeing the old cached version from CloudFront. Why? Because the file's TTL hasn't expired yet — CloudFront thinks it's still fresh.

To force CloudFront to serve new content immediately, you perform a Cache Invalidation. This tells CloudFront: "Delete these files from all Edge Location caches right now, so the next user gets the new version from the origin."

You specify file paths as patterns. Use /index.html to invalidate just that one file, /images/* to invalidate all images, or /* to clear the entire cache. The invalidation propagates to all Edge Locations within seconds.

Invalidate only the files you changed, not the whole cache with /*. Clearing everything forces your origin to process more requests, which can create a traffic spike.
🏭 In real companies Most deployment pipelines automate cache invalidations. When you push code, the CI/CD system updates S3 and then automatically calls CloudFront's API to invalidate the affected paths. This happens so fast that users almost never see an intermediate state.

55Cache Behaviors & Multiple Origins

A single CloudFront distribution can route different URL paths to different backends. You might want images to come from an S3 bucket, API calls to go to an Application Load Balancer, and everything else from your main web server.

💡 New word Cache Behavior is a rule that matches incoming request paths and determines which origin to use and what caching policy to apply. Think of it as a router.

Each Cache Behavior has a path pattern (e.g., /api/* or /images/*) and a specific origin to route traffic to. You can also attach different Cache Policies and Origin Request Policies to each behavior.

The Default Cache Behavior (path pattern /*) acts as a fallback. CloudFront evaluates specific patterns first, and if none match, uses the default behavior. This matters on exams: the default is always evaluated last.

The Default Cache Behavior is evaluated LAST, not first. Specific patterns take priority.
Cache Behaviors route request paths to different origins. Specific patterns are checked first; the default catches everything else.

56Caching & Invalidations Hands-On

Let's walk through a caching scenario. Edit a file in your S3 bucket — for example, change the text in index.html and re-upload it. If you access it directly via S3, you see the new content immediately. But if you reload the CloudFront URL, you see the old cached version, because the TTL (set to 24 hours by default) hasn't expired.

Now, create a Cache Invalidation for /* in the CloudFront console. Within seconds, the cache is cleared. Reload the CloudFront URL — now you see the new content from S3.

You can also create targeted Cache Behaviors. Add a new Cache Behavior for /images/* pointing to a different S3 bucket with a shorter TTL. Or attach an Origin Request Policy that forwards specific headers to your origin without changing the cache structure.

Test invalidations on a non-critical file first so you can see the effect without worrying about breaking anything.

57CloudFront With ALB/EC2

You can put CloudFront in front of an Application Load Balancer or EC2 instance to cache and protect dynamic content. But this requires a security choice: do you expose the backend to the public internet, or keep it private?

AWS recommends the modern approach: VPC Origins. This allows CloudFront to connect directly and securely to private load balancers or EC2 instances inside your VPC, without assigning them public IP addresses or exposing them to the internet at all.

💡 New word VPC Origin is a CloudFront origin that lives inside a private VPC — a private ALB, NLB, or EC2 instance. CloudFront reaches it through a secure connection without exposing the backend to the public internet.

When you configure a VPC Origin, CloudFront automatically establishes a secure connection. Your backend never needs a public IP, and your Security Groups can block all internet traffic. Only CloudFront can reach them.

🏭 In real companies The shift to VPC Origins removed a major security headache. The old way required opening Security Groups to CloudFront's IP address ranges, and those ranges change occasionally, requiring maintenance. Now, it's all handled internally and securely.

58Geo-Restriction

Sometimes you need to restrict who can access content based on geography. Maybe you have licensing rights only in certain countries, or you need to comply with regional regulations.

💡 New word Geo-Restriction is a CloudFront setting that allows or blocks access based on the geographic country where the user is connecting from, determined by IP address lookup.

CloudFront offers two modes. With an Allow List, only users from specified countries can access content. With a Block List, users from specified countries get access denied. CloudFront returns an HTTP 403 Forbidden response to blocked users.

🏭 In real companies Media companies use Geo-Restriction heavily. A video licensed for streaming only in North America would use an Allow List restricting access to US/Canada/Mexico. Sports broadcasters do the same — a game might be geo-locked to specific regions to enforce exclusive broadcasting deals.

59Signed URLs & Signed Cookies

You host a video library on S3, served through CloudFront. Not all videos are free — users should only be able to download a video if they've paid for it or subscribed. How do you grant temporary access without sharing the S3 URL publicly?

You use a Signed URL or Signed Cookie. Your application authenticates the user, generates a time-limited signature, and hands it to the client. The client includes that signature when requesting from CloudFront. CloudFront verifies the signature, checks the expiration, and either serves the file or denies access.

💡 New word Signed URL is a CloudFront URL with an attached cryptographic signature that proves a trusted party authorized access. It includes an expiration time and can restrict access to specific IP ranges.
💡 New word Signed Cookie works like a Signed URL but uses a browser cookie instead of a URL parameter. It's useful when you want to grant access to multiple files or an entire section of a site.
ScenarioUse Signed URLUse Signed Cookie
One premium file downloadYes — user gets a single URL that expiresNo — overkill
Access to entire video libraryNo — too many individual URLsYes — one cookie grants broad access
Share a link with someone elseYes — the URL itself contains the signatureNo — they'd need the same cookie

Both mechanisms use the same underlying cryptography. A private key (held by your application server) signs the request, and CloudFront uses the corresponding public key to verify it. If the signature is valid and hasn't expired, CloudFront serves the content. If it's expired or tampered with, access is denied.

🏭 In real companies Video platforms like Vimeo and Wistia generate signed URLs for every play request. When you click play on a private video, your browser gets a signed URL that expires in an hour. If someone else copies that URL and tries to use it tomorrow, it's invalid.

CloudFront Signed URL vs S3 Pre-signed URL

Both use cryptographic signatures, but they're different tools. CloudFront Signed URLs work with any origin (S3, ALB, external server). S3 Pre-signed URLs work only with S3. CloudFront Signed URLs can filter by IP address; Pre-signed URLs cannot. CloudFront Signed URLs benefit from edge caching; Pre-signed URLs always hit S3 directly.

FeatureCloudFront Signed URLS3 Pre-signed URL

60Key Groups & Signed URLs Hands-On

Two Ways to Manage Signing Keys

CloudFront offers two methods for managing the keys that sign URLs. The first is Trusted Key Groups — the modern, recommended approach. The second is Account CloudFront Key Pairs — a legacy method that requires Root account access and doesn't support API automation.

💡 New word Key Group is a CloudFront container for public keys used to verify signed URLs and cookies. It's the modern way to manage URL signing authority.

Setup With Key Groups (Recommended)

First, generate a 2,048-bit RSA key pair on your local machine or application server. You'll get two files: a private key and a public key.

Keep the private key secret on your application server — this is what your code uses to sign URLs. Upload the public key to CloudFront under Key Management. Create a Key Group and add your public key to it. Then attach that Key Group to the Cache Behavior that needs signed access.

Now, when a user requests a file, your application uses the private key to generate a signature with an expiration time. You hand the signed URL back to the client. The client requests that URL from CloudFront. CloudFront uses the public key in the Key Group to verify the signature. If it's valid and not expired, access is granted. If it's expired or forged, access is denied.

Store your private key securely. If it leaks, attackers can forge unlimited signed URLs with any expiration time. Rotate keys regularly.
Use Key Groups instead of Account Key Pairs. They're fully supported by AWS APIs, work with IAM, and support key rotation without breaking your distribution.

61Advanced Concepts

Price Classes

Bandwidth costs vary by geography. A CloudFront request served from Asia costs more than one from North America. To optimize costs, you can restrict which Edge Locations your distribution uses.

Price Class All uses all 200+ Edge Locations globally — maximum performance, highest cost. Price Class 200 excludes the most expensive regions, still covering 95% of the world. Price Class 100 covers only North America and Europe — cheapest, but users in Asia will get slower speeds.

Origin Groups: Automatic Failover

You want high availability. If your primary origin (an S3 bucket or ALB) fails, you want CloudFront to automatically switch to a backup origin without users noticing.

Create an Origin Group with a primary and secondary origin. If CloudFront receives HTTP error codes like 500, 502, 503, or 504 from the primary, it automatically retries the request against the secondary origin. This happens transparently to the user.

If the primary origin fails, CloudFront automatically retries against the secondary origin.

Field-Level Encryption

Users sometimes submit sensitive data (credit card numbers, social security numbers) through forms on your website. You want this data encrypted end-to-end so it stays secret even if a middle layer (like a load balancer) gets compromised.

Field-Level Encryption lets you specify which form fields to encrypt. CloudFront encrypts those fields at the Edge Location using a public key before sending the request to your origin. Only your origin server, holding the private key, can decrypt them. Intermediate servers can't read the data.

You can encrypt up to 10 fields per request. This is perfect for payment systems or healthcare applications where even temporary exposure of sensitive data is unacceptable.

62Real-Time Logs

CloudFront can stream request logs in real time to an Amazon Kinesis Data Stream. From there, you can send the logs to S3 for storage, or to OpenSearch for analytics and searching.

You configure sampling rates to control what percentage of requests get logged — 100% for critical applications, 10% to reduce volume on high-traffic sites. You can filter logs to specific Cache Behaviors or specific fields you care about.

🏭 In real companies Companies use real-time CloudFront logs for security monitoring, performance analysis, and debugging. When a user reports an issue, you can search the logs immediately to see what happened in real time, rather than waiting for batch logs to arrive hours later.

Key Facts

  • CloudFront uses a Cache Hit (serves from edge instantly) or Cache Miss (fetches from origin, then caches).
  • The Default Cache Behavior (/*) is evaluated LAST — specific patterns are checked first.
  • Use VPC Origins to connect CloudFront to private load balancers or EC2 instances without exposing them.
  • CloudFront integrates with AWS Shield and WAF for built-in DDoS and attack protection.
  • A Cache Invalidation clears files from all Edge Locations immediately — useful after deployments.
  • Signed URLs are per-file; Signed Cookies grant access to multiple files.
  • Use Trusted Key Groups (not legacy Account Key Pairs) for modern, API-driven key management.
  • Origin Groups provide automatic failover — if primary origin fails, CloudFront retries against secondary.
  • Field-Level Encryption encrypts sensitive form fields at the edge — only your origin can decrypt them.

Decision Tree

  • I need global caching for static files: CloudFront + S3 with OAC.
  • I need to serve dynamic content fast: CloudFront with VPC Origin (ALB, NLB, or EC2).
  • I need to protect paid/premium content: Signed URLs (one file) or Signed Cookies (multiple files).
  • I updated a file and users see old content: Cache Invalidation.
  • I need different content for different languages: Cache Policy including Accept-Language header.
  • I need high availability: Origin Groups with primary + secondary failover.
  • I need to restrict access by country: Geo-Restriction with Allow or Block list.
  • I'm sending credit card data through a form: Field-Level Encryption.

The One-Paragraph Version

CloudFront is a global caching network that serves content from Edge Locations near your users instead of from a distant origin server. Origin Access Control secures S3. Cache Policies determine what variations get cached separately. Invalidations force immediate refresh. Cache Behaviors route different paths to different origins. Signed URLs and Cookies restrict access to paid content using cryptographic signatures. VPC Origins keep backends private. Geo-Restriction controls access by country. Origin Groups provide failover.
