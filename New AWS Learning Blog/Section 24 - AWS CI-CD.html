1Introduction to CI/CD in AWS

Imagine you've just finished building a feature. You test it locally, it works great. You push the code to your team's repository. Then what? Do you hope someone notices? Do you manually run tests on five different machines? Do you export a zip file, send it to someone else, and pray they deploy it the right way?

That's the problem CI/CD solves. Instead of manual handoffs and crossed fingers, code flows automatically from your push, through tests, and onto live servers — safely, predictably, and fast enough to do it multiple times a day.

💡 New word CI/CD is shorthand for Continuous Integration (automatically testing code after each push) and Continuous Deployment or Delivery (automatically getting tested code onto production servers). The goal is making deployments so safe and fast that you can do them many times a day instead of once a quarter.

What happens without CI/CD

A developer finishes a feature. They test it by hand. They build it. Someone else checks the code. Then another person sets up servers and runs the deploy. Days pass. During that gap, bugs hide in branches, dependencies drift, and memory of what was tested is already fading by the time anything goes live.

What happens with CI/CD

A developer pushes code. Within seconds, a build server tests it. If tests pass, the code automatically deploys to a dev environment. Another team member reviews the live dev version, clicks "approve," and it flows to staging. Pass staging? Into production. The whole journey takes minutes, not days. The tests are the same every time. The deploy process never changes.

Breaking it down: Continuous Integration

Developers push code often into a central repository (GitHub, CodeCommit, Bitbucket, or others). A build server immediately tests the code — runs unit tests, integration tests, even checks code style. Pass? Great. Fail? The developer sees the failure instantly and fixes it. Benefits: bugs found early and cheap, faster feedback to developers, code in main branch is always tested.

Breaking it down: Continuous Delivery and Deployment

Continuous Delivery means tested code is always ready to deploy. Someone still clicks a button or approves a request before production. Continuous Deployment goes one step further: if tests pass, code goes straight to production with no approval needed. Most companies use Continuous Delivery (safer) rather than full Deployment (faster but riskier).

Code flows automatically from a developer's push, through automated tests, to production servers. The pipeline is fast, repeatable, and safe because every step is the same every time.

CodeBuild, CodePipeline, and CodeDeploy are the three services real teams actually rely on daily.

2CodeCommit Overview

CodeCommit is AWS's managed Git repository service. If you've used GitHub or Bitbucket, CodeCommit is the AWS equivalent — a place to store code, manage branches, and handle pull requests.

💡 New word CodeCommit is AWS's fully managed, private Git repository service. It lives completely inside your AWS account, encrypted at rest and in transit, with access controlled by IAM roles instead of GitHub accounts.

Key features

  • No repository size limit, fully available, encrypted using KMS for data at rest and HTTPS/SSH for transit.
  • Access controlled entirely by IAM — the same identity system you use for EC2, S3, and every other AWS service.
  • Built-in pull requests for code review. Approval rules can block merges until certain conditions are met.
  • Integrates with CodePipeline, CodeBuild, and other AWS services automatically.
  • Triggers can invoke Lambda or send SNS notifications on push events, pull request comments, or branch creation.

CodeCommit vs. GitHub

CodeCommit is simpler and stays entirely in your AWS account. GitHub is more feature-rich and is where most teams store code today. The exam mostly cares that you can distinguish them: CodeCommit is private-by-default, AWS-managed, and IAM-controlled, while GitHub is a separate service with its own user management.

CodeCommitGitHub
HostingOnly within AWSGitHub's cloud or self-hosted Enterprise
AuthenticationIAM users and rolesGitHub accounts, OAuth, SSO (Enterprise)
UI / FeaturesBasic — focused on core Git operationsRich — discussions, wikis, actions, insights
PriceIncluded in Free Tier (limited), pay per active user above thatFree for public repos, paid for private
Exam tip: CodeCommit access cross-account (when one AWS account needs to clone a repo in another account) uses IAM roles and STS, not SSH keys or GitHub credentials. That's a common trap.

3CodeCommit — Hands On

Creating and cloning a repository

  1. Go to CodeCommit console, click Create repository, give it a name (e.g. my-app), and create it.
  2. The console shows you a connection URL. Copy it — you'll need it to clone locally.
  3. On your machine, install Git (or use CloudShell, which has Git pre-installed), then run git clone <url>.
  4. Configure your Git user: git config user.email "you@example.com" and git config user.name "Your Name".

Adding files and pushing code

Once cloned, the workflow is standard Git:

echo "Hello World" > index.html
git add index.html
git commit -m "Add index page"
git push

The repository now contains your file. Branch names work the same as GitHub: the first branch is usually called master or main. Create new branches with git checkout -b feature-name.

Pull requests and approval rules

Push code to a branch other than master. Then use the console or git to open a pull request asking to merge your branch into master. Team members review the code, leave comments, and can approve or request changes. You can set approval rules that block merges until a certain number of people sign off.

Triggers and notifications

CodeCommit can watch for events: a push to master, creation of a new branch, or a pull request comment. When an event happens, it can trigger Lambda, invoke SNS to notify a Slack channel, or send a message to CodePipeline to start a build. This is how deployment pipelines know to run automatically when code changes.

Quick setup: Use CloudShell (AWS's free browser-based terminal) to clone and work with CodeCommit repos. No need to install anything on your laptop. CloudShell has Git and the AWS CLI pre-installed.

4CodePipeline Overview

CodePipeline is the conductor of your CI/CD orchestra. It watches your repository. When code changes, it automatically triggers a build, then a test, then a deploy — each stage handing the result to the next.

💡 New word CodePipeline is AWS's CI/CD orchestration service. It wires together source (CodeCommit/GitHub), build (CodeBuild), test, and deploy stages into one automated workflow. Each stage's output is stored as an artifact in S3 and handed to the next stage automatically.

What a pipeline looks like

A typical pipeline has stages that run in order:

  1. Source — CodePipeline polls CodeCommit (or GitHub, or S3) for changes. When it finds a new commit, it downloads the source code.
  2. Build — CodeBuild compiles the code and runs tests. If tests fail, the pipeline stops.
  3. Deploy — CodeDeploy rolls the built code to EC2 instances, Lambda, or Elastic Beanstalk.

You can add more stages: Test (run integration tests), Approval (pause and wait for a human to click "approve"), or Invoke (call Lambda or Step Functions).

💡 New word A stage in CodePipeline is a logical grouping of actions. A stage progresses from Source to Build to Deploy. Within each stage, an action is a specific operation: "build with CodeBuild," "approve manually," or "deploy to EC2."

How artifacts flow between stages

After the Source stage downloads code, it zips it up and stores it in an S3 bucket. The Build stage reads that zip from S3, runs its build commands, creates output (a compiled binary or Docker image), and stores that output (called an artifact) back in S3. The Deploy stage then reads the artifact from S3 and deploys it.

💡 New word An artifact in CodePipeline is the output of one stage that becomes input to the next. It's usually a zip file stored in S3 containing your application code, binaries, or container images.
CodePipeline stages don't talk to each other directly. Instead, CodeCommit → CodeBuild → CodeDeploy all speak to S3, passing artifacts through a shared bucket. This keeps the pipeline loosely coupled and easy to swap services.

Manual approval gates

Before deploying to production, you can add a Manual Approval action. The pipeline pauses, sends a notification (email or SNS), and waits for someone to review the build and click "Approve" in the console. Only then does deployment happen. This prevents accidental production deploys and gives teams a final safety net.

🏭 In real companies Most teams wire CodePipeline to GitHub (not CodeCommit) and use CodeBuild + CodeDeploy. They keep a manual approval gate before production. When someone approves, Slack gets a notification, and the code flows to production. If a deploy fails, they can trigger a rollback or manual re-deploy from the pipeline console.

5CodePipeline — Hands On

Creating a basic pipeline

You need a source (CodeCommit repo or GitHub), a destination (Elastic Beanstalk environment, EC2 instances via CodeDeploy, or Lambda), and optionally a build step (CodeBuild).

  1. Go to CodePipeline console, click Create pipeline, give it a name.
  2. Source stage: choose CodeCommit and point to your repo branch (e.g. main
  3. Skip build stage for now (we'll come back to it) or add CodeBuild if you have tests you want to run.
  4. Deploy stage: choose your target (e.g. Elastic Beanstalk environment, or CodeDeploy to EC2).
  5. Review and create. The pipeline runs immediately if your repo has commits.

Testing the pipeline

Make a small change to your code — edit a file, commit, and push. Within seconds, the pipeline should detect the change and start running. Watch the stages advance in the console. If deploy fails, click on the stage to see error logs. Usually it's a permissions issue (the pipeline's IAM role doesn't have access to the deployment target) or a misconfiguration in CodeDeploy.

Adding a manual approval step

Edit the pipeline. Add a new stage between Build and Deploy, call it "Approval." Inside it, add an action of type "Manual Approval." Give it a comment (e.g. "Deploy to production?"). Save. Now, when the build passes, the pipeline waits at this stage until someone logs into the console and clicks "Approve" or "Reject."

A realistic pipeline for small teams: source code triggers a dev deployment, then pauses at a manual approval step. Only after someone approves does it deploy to production.
Common issue: The pipeline's IAM service role might not have permissions to deploy to your target. If a stage fails with an access denied error, go to IAM, find the CodePipeline service role, and attach the right policy (e.g. Elastic Beanstalk full access, or CodeDeploy full access).

6CodeBuild Overview

CodeBuild is where the actual building and testing happens. It takes your source code and a recipe (called a buildspec.yml file), spins up a Docker container, runs the commands in the recipe, and outputs the result.

💡 New word CodeBuild is AWS's fully managed build service. It runs your source code and build commands inside a Docker container (using a language-specific image like Ubuntu/Python, Ubuntu/Node.js, etc., or your own custom image). It outputs logs to CloudWatch and artifacts to S3.

How CodeBuild works

  1. CodeBuild reads your buildspec.yml file from the root of your repository.
  2. It picks or pulls a Docker image (Java, Node.js, Python, Go, .NET, or your own).
  3. It runs the phases defined in the buildspec: install dependencies, run the build, run tests, and optionally package output.
  4. Logs go to CloudWatch. Artifacts (compiled binaries, built Docker images) go to S3.

The buildspec.yml file

This is the recipe. It lives at the root of your repo. Here's the structure:

SectionPurpose
versionUsually 0.2
envEnvironment variables (plaintext or from Secrets Manager / Parameter Store)
phases.installInstall system packages or dependencies (e.g. npm install)
phases.pre_buildCommands before the actual build (e.g. log in to Docker registry)
phases.buildCompile code, run unit tests, or run your build script
phases.post_buildClean up, zip artifacts, or push a Docker image
artifactsWhich files to extract and send to S3 for the next stage
cacheFiles to cache in S3 between builds (e.g. node_modules) to speed up future runs

Here's a real example for a Node.js app:

version: 0.2
env:
  variables:
    NODE_ENV: production
phases:
  install:
    runtime-versions:
      nodejs: 18
  pre_build:
    commands:
      - npm install
  build:
    commands:
      - npm test
      - npm run build
  post_build:
    commands:
      - echo "Build complete"
artifacts:
  files:
    - dist/**/*
    - node_modules/**/*
  name: BuildArtifact

If any command returns a non-zero exit code (fails), the entire build stops and is marked failed. The pipeline then stops — downstream stages never run.

💡 New word A buildspec.yml (or buildspec.yaml — both work) is the recipe file that tells CodeBuild exactly what to run. It must live at the root of your repository. CodeBuild reads it automatically; the file itself is never built or deployed, just executed.
🏭 In real companies Every real project has a buildspec.yml checked into the repository. It defines the exact test command, the build command, what gets packaged up for deployment, and any caching strategy. The moment a developer pushes code, the build runs the same buildspec every single time. There's no "works on my machine" — if it doesn't work in the build container, it doesn't merge.

7CodeBuild — Hands On

Setting up a CodeBuild project

  1. Go to CodeBuild console, click Create build project.
  2. Name it (e.g. my-app-build).
  3. Source: point to your GitHub repo (or CodeCommit).
  4. Environment: pick a managed image (Ubuntu, Amazon Linux 2, Windows, etc.) and a runtime (Node.js 18, Python 3.11, Java 17, etc.).
  5. Buildspec: choose "Buildspec from source" (it will read the buildspec.yml from your repo root).
  6. Logs: send build logs to CloudWatch.
  7. Artifacts: if you want to keep compiled output, point to an S3 bucket.
  8. Create and test by clicking Start build.

Creating your first buildspec.yml

At the root of your repo, create a file called buildspec.yml:

version: 0.2
phases:
  build:
    commands:
      - echo "Building..."
      - grep -Fq "Hello" index.html
artifacts:
  files:
    - index.html

This build will only succeed if the file index.html contains the word "Hello". Commit and push. When CodeBuild runs, it will grep for that text. If it's missing, the build fails.

Using CodeBuild in a pipeline

In CodePipeline, add a Build stage between Source and Deploy. Choose CodeBuild as the provider, select the project you just created, and point to the source artifacts as input. Now, when you push code, the pipeline automatically triggers CodeBuild. If the build fails (e.g. the test grep fails), the pipeline stops and never reaches the deploy stage.

Debug tip: When a build fails in the console, scroll to the bottom of the logs and look for the last error message. It usually says exactly which command failed and why.
Be careful: If you have a GitHub webhook pointing directly at CodeBuild, remove it once CodePipeline is wired up. Otherwise, CodeBuild might run twice — once from the webhook and once from the pipeline.

8CodeDeploy Overview

CodeBuild turns source code into deployable artifacts. CodeDeploy takes those artifacts and actually puts them on real servers. It handles the nitty-gritty of rolling out new versions safely: stopping old instances, starting new ones, managing traffic during the transition, and rolling back if something goes wrong.

💡 New word CodeDeploy is AWS's deployment service. It pushes application revisions (from S3 or GitHub) onto EC2 instances, on-premises servers, Lambda functions, or ECS clusters. It can roll out in-place (update existing instances) or blue-green (create a new set and cutover traffic).

Three deployment targets

EC2 and on-premises servers

CodeDeploy installs an agent on each target server. When you trigger a deployment, the agent pulls the application from S3, stops the old version, installs the new one, and starts it. It can deploy in batches (e.g. update 50% of instances, wait, then update the other 50%), or blue-green (create new instances with the new version and switch traffic over).

💡 New word An appspec.yml file (for EC2) or appspec.json (for Lambda) tells CodeDeploy how to deploy: which files go where, what commands to run before stopping the old version, what commands to run after starting the new version, and so on. It lives at the root of your repository.

Lambda

You don't need an agent. CodeDeploy manages Lambda function versions and aliases. It can shift traffic gradually from the old version to the new one (Linear, Canary, or AllAtOnce). If a CloudWatch alarm fires, it automatically rolls back.

ECS

Similar to Lambda but for ECS services. CodeDeploy manages switching traffic between the current task definition and a new one via the load balancer.

In-place vs. blue-green deployments

In-place reduces capacity briefly (some requests go unanswered during updates). Blue-green maintains full capacity the whole time but requires double the resources during the cutover window.

The appspec.yml file (EC2)

This tells CodeDeploy exactly how to deploy. It defines which files go where, and lifecycle hooks:

  • ApplicationStop — stop the running application before deploying a new version.
  • BeforeInstall — install dependencies, download packages, anything needed before the app starts.
  • ApplicationStart — start the application.
  • ValidateService — run a health check to make sure the new version is working.

A simple appspec.yml for a static website might just copy HTML files to /var/www/html. A complex one might run npm install, run a database migration, and restart a Node.js service.

🏭 In real companies The appspec.yml file is the glue between your application and deployment. It's usually customized per project. If a deployment fails partway through, CodeDeploy can automatically trigger a rollback — which is just another CodeDeploy deployment of the previous working revision. Rollbacks aren't magic; they're controlled by the same appspec.yml file.

9CodeDeploy — Hands On

Setting up CodeDeploy for EC2

This is the trickiest part because you need three things in place: the CodeDeploy agent on each EC2 instance, an IAM instance profile giving the instance permission to read from S3, and an appspec.yml file in your repo.

  1. Create an IAM role for EC2 instances. Go to IAM, create a role with the trust relationship "EC2," and attach policy AmazonEC2RoleforSSM (lets Systems Manager manage the instance) and a custom policy allowing S3 read access to your artifact bucket.
  2. Launch an EC2 instance using that role (assign it when launching). Use Amazon Linux 2 or Ubuntu.
  3. Install the CodeDeploy agent. SSH into the instance and run the installation script provided by AWS (available in the CodeDeploy console). The script installs Ruby (a dependency) and the CodeDeploy agent. 
    #!/bin/bash
sudo yum update -y
sudo yum install ruby wget -y
cd /home/ec2-user
wget https://aws-codedeploy-${AWS_REGION}.s3.${AWS_REGION}.amazonaws.com/latest/install
chmod +x ./install
sudo ./install auto
sudo systemctl start codedeploy-agent
  4. Tag the instance. Give it a tag like Environment=Production. CodeDeploy uses tags to group instances into deployment groups.
  5. Create a CodeDeploy application in the console. Give it a name and choose "EC2/on-premises" as the compute platform.
  6. Create a deployment group inside the application. Give it a name, set deployment type (in-place or blue-green), choose "Tag-based" instance selection, and enter your tag.
  7. Create an appspec.yml in the root of your repo: 
    version: 0.0
Resources:
  - TargetDirectory
os: linux
files:
  source: .
  destination: /var/www/html
hooks:
  ApplicationStop:
    - location: scripts/stop.sh
      timeout: 300
      runas: root
  ApplicationStart:
    - location: scripts/start.sh
      timeout: 300
      runas: root
  8. Upload your application code and appspec.yml as a zip to S3. (Or push to CodeCommit and let CodePipeline zip it for you.)
  9. Create a deployment pointing to your S3 zip. Choose the deployment group. Watch the deployment progress in the console.

Deployment lifecycle on the instance

The CodeDeploy agent follows these steps:

  1. ApplicationStop — run scripts/stop.sh (e.g. stop the web server).
  2. Download the new application from S3.
  3. BeforeInstall — run any setup scripts.
  4. Extract files to the destination directory.
  5. AfterInstall — run any post-installation scripts.
  6. ApplicationStart — run scripts/start.sh (e.g. start the web server).
  7. ValidateService — run a health check script.

If any step fails, the entire deployment fails. If you've configured automatic rollback, CodeDeploy triggers a fresh deployment of the last working revision.

Common mistake: Forgetting to assign the IAM instance profile to the EC2 instance. Without it, the instance can't read the application zip from S3, and the deployment fails with "Access Denied." Fix it by going to EC2 console → Actions → Security → Modify IAM role.

10CodeDeploy for EC2 & Auto Scaling Groups

In-place deployment with an ASG

When you deploy to an EC2 instance that's part of an Auto Scaling Group, the instance gets the new version. If the ASG later launches a new instance (due to a scale-up event), that new instance starts with the old application code unless you've updated the launch template or AMI. CodeDeploy solves this by updating the ASG's launch configuration/template so new instances automatically get the latest deployed version.

💡 New word An Auto Scaling Group (ASG) is a group of EC2 instances that AWS keeps at a desired count. If an instance dies, the ASG launches a replacement. If load increases, the ASG can launch more. CodeDeploy integrates with ASG so that new instances automatically get the current deployed application.

Blue-green deployment with an ASG

For higher safety, blue-green creates an entirely new ASG with the new application version, runs both ASGs side-by-side, and only after confirming the new (green) ASG is healthy does the load balancer switch traffic to it. The old (blue) ASG is then terminated.

🏭 In real companies Blue-green deployments are standard for production systems that can't tolerate any downtime. They cost more (double capacity during cutover) but are nearly bulletproof — if something goes wrong with the green instances, you switch traffic back to blue instantly.

Rollback behavior

A rollback isn't rewinding time. It's a new CodeDeploy deployment of the last working revision. You can trigger rollbacks manually, or CodeDeploy can trigger them automatically if a deployment fails or a CloudWatch alarm fires.

💡 New word A revision in CodeDeploy is a specific version of your application, identified by a commit hash (if deploying from Git) or a timestamp (if deploying from S3). Rolling back means deploying a previous revision again.
Exam trap: "Rollback" doesn't mean the instances go back in time. It means CodeDeploy runs again with the previous revision's appspec.yml and code. If you've deleted the old revision from S3, you can't roll back to it. Always keep old revisions in S3 or enable versioning.

11CodeArtifact Overview

CodeBuild needs npm packages, Python libraries, Maven jars, .NET nugets — dependencies. By default, each build downloads them from public repositories (npm.org, PyPI, Maven Central). CodeArtifact lets you proxy those repositories through AWS, caching everything so builds stay fast and dependencies never vanish.

💡 New word CodeArtifact is AWS's artifact repository service. It stores software packages (npm, pip, Maven, NuGet, etc.) and can proxy public repositories. It caches everything, ensuring your builds don't break if a public package gets deleted, and it keeps dependencies inside your AWS account for compliance.

How CodeArtifact works

You create a domain (a container for repositories) and inside it, a repository. Each repository can have an upstream connection to a public repo (npm, PyPI, Maven Central) or to another internal repository.

When your build asks for a package, CodeArtifact checks if it's cached locally. If not, it fetches from upstream, caches it, and returns it. Next time you need that package, it's already cached — faster and network-independent.

💡 New word A domain in CodeArtifact is a top-level container for repositories. An organization usually has one domain. Inside, you have multiple repositories (one for internal packages, one proxying npm, etc.). A repository can have upstream connections for proxying or dependencies.
CodeArtifact sits between your builds and public repositories, caching everything. If a public package later disappears, you still have it cached inside CodeArtifact.

Two main uses

Proxying public repos: CodeBuild connects to a CodeArtifact repository, which proxies npm/PyPI. Packages get cached. If PyPI goes down, your cached packages are still available.

Hosting internal packages: Publish your own packages (e.g. an internal logging library) into CodeArtifact. Other projects can depend on it. Versions are managed, and access is IAM-controlled.

🏭 In real companies Teams use CodeArtifact to avoid the public internet entirely during builds (network security), to cache dependencies (speed), and to host internal SDKs. When a new version of a dependency is published, CodeArtifact can trigger an EventBridge event, which can trigger CodePipeline to rebuild and redeploy — automating the "we have a new dependency, test everything" workflow.

12CodeArtifact — Hands On

Creating a domain and repository

  1. Go to CodeArtifact console, click Create domain, give it a name (e.g. my-company), and create it. (You can optionally use a KMS key for encryption.)
  2. Inside the domain, click Create repository. Name it (e.g. npm-proxy).
  3. Set an upstream repository: choose Public upstreams and select npmjs (for npm packages).
  4. Create the repository.

Configuring your build to use CodeArtifact

CodeArtifact generates an authorization token (valid 12 hours). You configure npm, pip, or Maven to use it:

aws codeartifact get-authorization-token --domain my-company --domain-owner 123456789 --region us-east-1

The token goes into your build environment (via parameter store or directly in buildspec.yml), and npm/pip is configured to use CodeArtifact as its repository source.

Installing packages through CodeArtifact

Once configured, npm install or pip install fetches from CodeArtifact, which proxies to the public repo and caches the result. The first time you install a package, it's slower (network fetch + cache). Second time, it's cached and instant.

Good to know: Cross-account access to CodeArtifact requires a resource policy on the repository (not an IAM policy). The policy is all-or-nothing per repository — you can't grant access to specific packages, only to the entire repository.

📋 Cheat Sheet

The Big Picture

CI/CD automates testing and deployment. Push code → build server tests it → if tests pass, deploy to production. AWS provides CodeCommit (repository), CodeBuild (testing/build), CodePipeline (orchestration), and CodeDeploy (actual deployment). Together, they turn "I hope this works" into "this is guaranteed to work the same way every time."

The Four Core Services

  • CodeCommit: Private Git repository inside AWS. IAM-controlled. Limited UI compared to GitHub, but integrates tightly with AWS.
  • CodePipeline: Orchestrator. Watches repositories, triggers builds, manages approval gates, and coordinates deployments. Artifacts live in S3.
  • CodeBuild: Runs buildspec.yml in a Docker container. Runs tests, compiles code, builds artifacts. Logs go to CloudWatch.
  • CodeDeploy: Deploys artifacts to EC2 (in-place or blue-green), Lambda (traffic-shift), or ECS. Controlled by appspec.yml. Auto-rollback on failure.
  • CodeArtifact: Package repository that proxies npm, pip, Maven, NuGet. Caches dependencies so they never disappear.

Key Files

  • buildspec.yml (CodeBuild) — lives at repo root. Defines install/build/test/package phases. Failure stops the pipeline.
  • appspec.yml (CodeDeploy for EC2) — defines which files go where and lifecycle hooks (ApplicationStop, ApplicationStart, ValidateService).

Deployment Strategies (CodeDeploy)

  • In-place: Update existing instances in batches. Temporarily reduces capacity. Cheaper.
  • Blue-green: Launch new instances, switch traffic, terminate old. Maintains full capacity. More expensive but safer.
  • Lambda/ECS traffic-shifting: Linear (% per time interval), Canary (small % for a period, then jump), or AllAtOnce (immediate full cutover).

Common Pitfalls

  • EC2 instances deployed via CodeDeploy need the CodeDeploy agent installed and an IAM instance profile with S3 read access.
  • appspec.yml must be at the repo root, not nested in a directory.
  • Rollback isn't rewinding — it's a new deployment of the old revision. Old revisions must exist in S3.
  • Pipeline artifacts move via S3. If S3 bucket is deleted, the pipeline breaks.
  • CodePipeline IAM role needs permissions for all downstream services (CodeBuild, CodeDeploy, etc.).

Exam Essentials

  • CI = automatic testing on every push. CD = automatic deployment of tested code.
  • Artifacts are S3 objects passed between pipeline stages.
  • buildspec.yml is for CodeBuild. appspec.yml is for CodeDeploy (EC2 and on-premises).
  • Manual Approval actions pause the pipeline and wait for human sign-off before proceeding.
  • Blue-green is zero-downtime but expensive. In-place is cheaper but has brief downtime per batch.
  • CodeDeploy agent must be running on target EC2 instances before deployment.
  • CodeArtifact proxies public repos and caches to prevent external package deletions from breaking builds.
