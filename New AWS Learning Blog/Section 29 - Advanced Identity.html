30STS — The Temporary Badge Office

Imagine hard-coding a permanent AWS access key into a mobile app or handing one to a contractor. That key never expires on its own. It's easy to leak — screenshots, GitHub commits, decompiled apps — and if it does leak, you have to hunt it down and manually revoke it. A permanent credential for a temporary need is a liability sitting in your codebase.

💡 New word STS (Security Token Service) is the AWS service that hands out short-lived, temporary credentials instead of permanent ones. You don't get to keep a master key; instead, you show your proof of identity, and STS prints you a temporary badge that expires in 15 minutes to an hour.

Once that badge expires, it's worthless. Nobody has to chase you down to take it back. That's the whole design: temporary credentials mean a leak is only dangerous for a small window, not forever.

STS works through a simple sequence. You call one of its APIs — most commonly AssumeRole — with proof of who you are. STS checks two things: does your identity have permission to assume this role, and does the role's trust policy allow your identity to assume it? If both say yes, STS returns three pieces of temporary evidence — an access key ID, a secret access key, and a session token — all bundled together and valid for 15 minutes to an hour.

Why this matters: A long-lived access key sitting on a developer's laptop is a real risk. If that laptop is lost or the key leaks, the key keeps working until someone manually notices and revokes it, which could take months. Many companies now avoid handing people permanent keys entirely, and instead issue short-lived, auto-expiring credentials through STS.

STS and MFA work together

Some actions are dangerous enough — terminating production instances, deleting a bucket — that a password alone shouldn't grant permission. So IAM lets you attach a condition to a policy: "aws:MultiFactorAuthPresent": true. But that condition needs something to check against. That's where GetSessionToken comes in. After a user proves their identity with an MFA device, this API call returns an access key, a secret key, and a session token (all three travel together), plus an expiry. Only credentials obtained this way carry the flag that says "yes, MFA was present," which is what the policy condition is checking for.

STS checks both the caller's permission to assume and the role's trust policy. Only if both allow does it return temporary credentials.

31How AWS Actually Decides Yes/No

A single IAM user can have several policies attached at once — one from their group, one attached directly, maybe an inline one too. If one policy says "allow S3 delete" and another says "deny S3 delete," which one wins? Without a strict, predictable algorithm, permissions would be a coin flip. Security systems can never be a coin flip.

AWS resolves this with one deterministic rule, evaluated the exact same way every time. The algorithm starts at a default of deny. AWS then gathers every policy attached to that user — from all groups, direct attachments, everything — and checks for an explicit deny anywhere in that pile for the action being requested. If there is an explicit deny, the request is immediately denied, and evaluation stops. Only if there's no explicit deny anywhere does AWS look for an explicit allow. If it finds one, the request is allowed. If it finds none, the request is still denied, because deny was always the starting point.

Permission evaluation always starts at deny. An explicit deny anywhere in applicable policies wins immediately. Only if no deny exists does an explicit allow matter.
Critical: One explicit deny somewhere in a user's policy set beats any number of allows. There is no "allow overrides deny" — deny is checked first and ends the conversation.

This rule has a single, powerful implication: if you want to block an action for someone, putting a deny in their policies always works. But if you want to allow an action, you have to be sure no other policy is denying it. That's why many companies use a standard set of "baseline allow" policies for everyone, and then use deny statements only to carve out exceptions.

32IAM Policy + S3 Bucket Policy — Two Votes, One Door

IAM policies are attached to people and roles inside your account. But S3 buckets often sit at the boundary between accounts, or you want the bucket itself to carry its own rules regardless of who's asking. If only IAM policies mattered, a bucket owner in a completely different account could never grant access to someone else's IAM user. So S3 needed its own policy language, attached directly to the resource itself.

💡 New word Resource-based policy is a policy attached directly to a resource (like an S3 bucket), not to a user or role. It talks about which principals — users, roles, whole accounts — are allowed to interact with this resource.

Now that two policies can both talk about the same action on the same S3 bucket, AWS needed a rule for combining them. The rule is simple: take the union — anything either policy allows is allowed — unless an explicit deny shows up in either one, which (as you just learned) always wins.

The permission math

For an S3 request to succeed, the effective permission is calculated as: (IAM policy allows OR bucket policy allows) AND NOT (explicit deny anywhere). In plain English, either the user's own IAM policy or the bucket's own policy granting access is enough, unless a deny blocks the whole thing.

🏭 In real companies This design means removing S3 permissions from an EC2 instance's IAM role doesn't necessarily block that instance from S3 — if the bucket policy separately allows that role, access still works. This trips up teams trying to revoke access; they remove the IAM policy and wonder why the instance still works. The union of both policies is what counts.

The practical implication is that you have to think about S3 permissions in two places at once. A complete access review means checking both the IAM side (what does the role allow) and the resource side (what does the bucket allow).

33Dynamic Policies — One Policy, Thousands of People

Say every employee needs a private /home/<username> folder in a shared S3 bucket, readable and writable only by themselves. The naive approach: write one IAM policy per person. That works fine for five people. For five thousand — every new hire means writing, testing, and attaching a brand-new policy. Forever. That doesn't scale.

💡 New word Policy variable is a placeholder in a policy that AWS substitutes with the actual value at the moment the request is evaluated. The most common is ${aws:username}, which resolves to the caller's actual username.

Here's the elegant solution: write one policy with a placeholder. Instead of hardcoding a username, use the variable ${aws:username}. Attach this single policy to every user in the company. When Alice makes a request, the variable resolves to "alice" and she lands in /home/alice. When Bob makes a request, it resolves to "bob" and he lands in /home/bob. Each person automatically gets their own private scope, from a single policy document.

Here's what that policy looks like:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::company-bucket/home/${aws:username}/*"
    }
  ]
}

One policy. Everyone gets it. Everyone sees only their own folder. No per-user policies to maintain, no drift, no mistakes. AWS also supports other variables: ${aws:userid}, ${aws:SourceIp}, and many others for time-based, service-specific, or context-based scoping.

Why it matters: Dynamic policies let you write one permission rule that behaves differently for each person automatically. It's the difference between maintaining a growing pile of near-identical policies and maintaining one template.

34Policy Types — Who's Allowed to Edit the Rulebook

Not every policy should be maintained the same way. Some permissions are so common — like read-only access to everything — that you'd rather AWS keep them updated as new services launch. Others are highly specific to your company and need version history, change tracking, and rollback. And sometimes you just need a quick, throwaway rule that lives on exactly one user and disappears when they leave.

AWS gives you three choices, each solving a different maintenance problem:

AWS managed policies

AWS writes and maintains these. They're good for power users, full admins, and job-function policies. The upside: AWS keeps them current as new services and APIs appear. The downside: you have zero control over the content. You either take the whole thing or you don't.

Customer managed policies

You write and maintain these. This is the best practice for granular control. You can version them, roll back to an older version, and see exactly who changed what and when. They're reusable across many principals — attach the same policy to dozens of roles. They support full audit trails, which compliance teams need.

Inline policies

A strict one-to-one relationship: one policy, one user or role. When that user leaves, the policy vanishes automatically. There's no version control. They can't be reused. And they have a hard size limit — 2 KB per principal. If your access pattern is broad enough, an inline policy might be too big to save.

Watch out: Inline policies have a 2 KB size limit per principal. A broad policy that grants "List" permissions for every EC2 operation can exceed that limit and force you to trim it or switch to a managed policy.

35Passing a Role — The Two-Lock Problem

Suppose a developer is allowed to launch EC2 instances. If they could attach any IAM role to that instance — including an admin role — they could quietly hand their own EC2 instance god-mode permissions and escalate their privilege. That's a critical security flaw, and AWS needed to stop it without stopping developers from launching EC2 instances at all.

💡 New word Assume role means to take on the identity and permissions of a role temporarily. A role doesn't belong to anyone permanently; it gets assumed (picked up) when needed.

The fix is two independent checks that both must pass before a role can be attached to a service. Call them two locks that must both open.

Lock 1: The user's own permission

The user needs the iam:PassRole permission, and this permission can be scoped down to a single role ARN. For example: "this user can launch EC2 instances, but PassRole is restricted only to the S3Access role." That's the only role this user could ever hand to an instance.

Lock 2: The role's trust policy

Even if the user is allowed to pass a role, the role itself has a separate policy called a trust policy (or trust relationship). It declares which service principals — ec2.amazonaws.com, lambda.amazonaws.com, codepipeline.amazonaws.com — are allowed to assume it in the first place. The service (EC2, Lambda, CodePipeline) checks this before accepting the role.

Both gates must open. PassRole alone means the user can hand out a role, but says nothing about which services are trustworthy recipients. The trust policy alone would mean any user with any permissions could hand any role to any service that trusts it. You need both: a gate on the giver and a gate on the receiver.

Two gates, both must open. The user needs iam:PassRole permission, and the role's trust policy must explicitly name the target service as allowed.
🏭 In real companies When a security incident happens — an employee accidentally escalated themselves to admin — the root cause is usually that one of these locks was left open. Either PassRole wasn't scoped to specific roles, or a role's trust policy was too broad and allowed services that shouldn't have been allowed. Good security hygiene means regularly checking both sides of every role assignment.

36Directory Services — Where Do People Actually Live?

Large companies have thousands of employee accounts sitting in an on-premise Microsoft Active Directory — logins, computers, printers, file shares, all centrally managed. Moving to AWS shouldn't mean recreating every one of those accounts by hand as an IAM user. AWS needed a way to either extend that existing directory into the cloud, or stand up something AD-compatible without duplicating effort.

💡 New word Microsoft Active Directory (AD) is a database of objects — user accounts, computers, printers, file shares, security groups — with centralized security management. It normally runs on Windows Server. Objects are organized into trees, a group of trees is called a forest, and a domain controller validates logins against the central database.

AWS gives you three flavors to choose from, each solving a slightly different version of the problem. Think of them as three characters in the same story: managing where your identities actually live.

Character 1 — AWS Managed Microsoft AD

A real Microsoft Active Directory, run by AWS, with users living natively in the cloud. It can optionally set up a two-way trust with your on-premise AD, so users can be validated on either side. Both sides stay in sync. MFA is supported.

Character 2 — AD Connector

Not a directory at all — a proxy. It holds no users of its own. Every login request is forwarded straight back to your on-premise AD, which stays the single source of truth. Your on-premise AD does all the actual work. MFA is supported.

Character 3 — Simple AD

A standalone, AD-compatible directory living only in AWS. Same API surface as Microsoft AD, but not real Microsoft AD under the hood. No trust relationship with an on-premise AD is possible. MFA is not supported.

💡 New word Federation in the context of identity means connecting two systems (like on-premise AD and AWS) so they recognize each other's users without having to recreate accounts.

Picking the right one

If your company already has an on-premise AD and wants to extend it into AWS while keeping both sides in sync, use AWS Managed Microsoft AD with a two-way trust. If you want to keep all users strictly on-premise and just have AWS proxy requests back to them (no AWS user accounts), use AD Connector. If you're a pure-cloud company with no on-premise directory and want something AD-compatible, use Simple AD — but remember it has no MFA and no on-premise linking.

Exam tip: The exam often tests which Directory Service flavor to pick. The key differentiator is where you want users to live and whether you need on-premise integration. Managed Microsoft AD shares users both ways; AD Connector is purely a proxy with no local users; Simple AD stands entirely alone.

📋 Cheat Sheet

Core Concepts at a Glance

  • STS: Hands out short-lived temporary credentials (15 min – 1 hour) so nobody needs to hold a permanent key for a temporary job.
  • Policy evaluation: Starts at deny. Explicit deny anywhere wins immediately. Only if no deny exists does an explicit allow matter.
  • S3 + IAM union: For S3, effective permission is the union of the IAM policy and the bucket policy — either one allowing is enough, unless a deny blocks it.
  • Dynamic policies: Use variables like ${aws:username} so one policy behaves differently per user — e.g., scoping each user to their own S3 folder.
  • Policy types: AWS managed (maintained by AWS), customer managed (best practice — versioned, reusable), inline (1:1 with a principal, no versioning, 2 KB cap).
  • PassRole: Needs two things: the user's iam:PassRole permission, and the role's own trust policy naming that service as allowed.
  • Directory Services: Managed Microsoft AD (cloud users + optional two-way on-premise trust + MFA), AD Connector (pure proxy to on-premise, no local users), Simple AD (fully standalone, AD-compatible API only, no MFA).

Key Facts Worth Remembering

  • STS APIs to know: AssumeRole (cross-account access), GetSessionToken (MFA-aware temp credentials), GetCallerIdentity ("who am I?"), DecodeAuthorizationMessage (decode denial errors).
  • Policy evaluation is not a negotiation — a single deny anywhere ends the conversation. Deny is always checked first.
  • Removing S3 permissions from a role doesn't necessarily block S3 access if the bucket policy separately grants that role access. The union still applies.
  • Dynamic policies with ${aws:username} and similar variables let you write one policy that automatically scopes itself per user.
  • Inline policies are perfect for one-off exceptions tied to a single principal; customer managed policies are the standard for anything you want to maintain long-term.
  • Passing a role to a service requires both the user's PassRole permission and the role's trust policy accepting that service — no shortcuts.
  • AD Connector is pure proxy, no local users. Managed Microsoft AD keeps users in the cloud with optional on-premise trust. Simple AD is standalone, no on-premise link possible.

The One-Paragraph Version

STS exists so you never have to give out permanent credentials for temporary jobs — temporary badges auto-expire, and a leak is only dangerous for a small window. Permission evaluation always starts at deny, and an explicit deny anywhere beats any number of allows. For S3 specifically, both the IAM policy and the bucket policy matter equally — either can grant access, but a deny in either one always wins. Dynamic policies let you write one rule that behaves differently per user by substituting variables like username at request time. Policy types exist to solve different maintenance problems — AWS managed for broad permissions AWS keeps current, customer managed for audit trails and reuse, inline for one-off exceptions. Passing a role to a service requires two independent checks, both must pass, which prevents privilege escalation. And Directory Services is simply deciding where your Windows-world identities actually live — in the cloud with optional on-premise sync, proxied from on-premise, or standalone.

Common Misconceptions

  • Wrong: "An explicit allow anywhere always wins." Right: An explicit deny anywhere always wins first; allow is only checked if no deny exists.
  • Wrong: "Removing a role's S3 permissions always blocks S3 access." Right: Not if the bucket policy separately grants that role access — the union still applies.
  • Wrong: "PassRole alone is enough to attach a role to a service." Right: The role's own trust policy must also name that service as an allowed principal — both locks must open.
  • Wrong: "Simple AD is just a smaller version of Managed Microsoft AD." Right: Simple AD isn't real Microsoft AD at all, can't trust an on-premise AD, and has no MFA — it's a different tool, not a smaller one.
  • Wrong: "Inline policies are just a lightweight version of customer managed policies." Right: They're not reusable across principals, have no version control, and vanish automatically when the principal is deleted.
