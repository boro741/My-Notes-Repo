1What is a DNS?

Type "google.com" into a browser and a page loads almost instantly. But here's the catch: computers don't actually understand words like "google.com." They only talk to each other using numbers, called IP addresses. So something has to translate the word you typed into the number a server actually uses. That something is DNS.

💡 New word DNS stands for Domain Name System. It's the system that turns a website address like www.google.com into the IP address a server actually uses, such as 142.250.190.46. People often call it "the phonebook of the internet."

Domain names are built in layers, and you read them from right to left:

  • Root — the very last, usually invisible dot at the end of every domain.
  • TLD (Top-Level Domain) — the extension, like .com, .org, or .gov.
  • Second-Level Domain — the actual brand name someone registered, like example.com.
  • Subdomain — an optional prefix in front of the domain, like www or api in api.example.com.
  • FQDN (Fully Qualified Domain Name) — the whole address written out in full, like api.www.example.com.

The words you'll keep seeing

A few pieces of vocabulary show up constantly once you start working with DNS:

  • DNS Record — a single mapping entry inside a domain's setup (an A record, a CNAME record, and so on).
  • Zone File — the text file holding every DNS record configured for a domain.
  • Name Server — a special DNS server that stores a zone file and answers questions about that domain.
💡 New word Domain Registrar is a company approved to sell and register domain names for you — Amazon Route 53 can do it, and so can outside companies like GoDaddy or Namecheap.

How your browser actually finds the right server

When you hit enter on a web address, your request doesn't go straight to the destination. It travels through a chain of servers until the exact IP address is found.

Each server points to the next level down. Your local DNS resolver keeps asking down the chain, then caches the final answer.

Your computer first asks a local DNS server if it already knows the answer. If it doesn't, that server asks a Root server, which points it toward the right TLD server — for example, the one handling all .com domains. The TLD server then points to the exact name server that owns example.com, often Route 53, which finally hands back the real IP address. Once found, that answer gets cached, so the whole chain doesn't have to repeat itself for every single visitor.

Why this matters: understanding this chain explains three things you'll run into constantly — DNS caching, TTL expiry, and the delay ("propagation") you sometimes see after changing a server's IP address.

2Route 53 Overview & Hosted Zones

If DNS is the internet's phonebook, someone still has to run AWS's own copy of it. That's Route 53's job.

Amazon Route 53 is AWS's own DNS service. It's highly available, it scales automatically, and it's authoritative — meaning you have full control over exactly what records it answers with, instead of relying on someone else's copy of the data.

  • It can act as your Domain Registrar — you can buy a brand-new domain directly inside Route 53.
  • It runs automated Health Checks against your applications, watching whether they're actually up.
  • It's the only AWS service that comes with a 100% Availability SLA — AWS's strongest possible uptime promise.
💡 New word SLA (Service Level Agreement) is a formal promise from a provider about how reliable a service will be. A 100% SLA means AWS is promising Route 53 itself will never go down — a bar it doesn't set for almost anything else it offers.

The name "Route 53" is a small in-joke: port 53 is the standard networking port reserved for DNS traffic everywhere on the internet, not just in AWS.

What's actually inside a DNS record

Every record you create in Route 53 needs the same five pieces of information:

  • Domain Name — the hostname the record applies to, like example.com or app.example.com.
  • Record Type — what kind of mapping it is (A, AAAA, CNAME, and others).
  • Value — the actual target, like an IP address or another hostname.
  • Routing Policy — the rule Route 53 uses to decide which answer to give back.
  • TTL — how long resolvers are allowed to cache that answer.

The record types you need for the exam

Record TypeTarget MappingKey Characteristic
AHostname → IPv4 addressStandard IPv4 address mapping.
AAAAHostname → IPv6 addressStandard IPv6 address mapping.
CNAMEHostname → HostnamePoints a domain alias to another domain name. Cannot be used at the domain apex (root domain).

Public vs. private hosted zones

Before Route 53 can answer any question about your domain, it needs somewhere to keep all its records. That container is called a Hosted Zone.

💡 New word Hosted Zone is a container inside Route 53 that holds all the DNS records for one domain. Every hosted zone comes in one of two flavors: public or private.
Public hosted zones answer questions from anyone on the internet. Private hosted zones only answer questions coming from inside your own VPC.
💡 New word VPC (Virtual Private Cloud) is your own private, isolated slice of network inside AWS. A private hosted zone only answers DNS questions coming from resources inside a VPC you've chosen — nobody on the public internet can even ask it a question.
Cost to remember: every hosted zone costs about $0.50 a month, and registering a new domain through Route 53 starts around $12 a year. Small per item, but it adds up if you spin up test hosted zones and forget to delete them.

3Registering a Domain (Hands-On)

Buying a domain feels like it should be complicated. It mostly isn't. Ordering one through Route 53 is a short, linear process:

  1. Go to Register Domains in the Route 53 console, and search to see if the name you want is available.
  2. Pick how many years to register it for, and decide whether to turn on auto-renew.
  3. Enter contact details for the registrant, the admin, and the technical contact.
  4. Turn on Privacy Protection so your personal contact details don't sit in a public WHOIS lookup.
  5. Review everything and submit payment.
💡 New word WHOIS is a public lookup anyone can use to see who registered a given domain. Privacy Protection hides your real name, address, and contact details from that public record.

The moment registration finishes, Route 53 doesn't leave you with nothing. It automatically creates a Public Hosted Zone for you, already pre-filled with a default NS record (the assigned name servers) and an SOA record (the technical record describing the zone itself).

Gotcha: if you turn off auto-renew and forget to renew manually, your domain will simply expire — and someone else is free to register it the moment it does.

4First Records & Demo Infrastructure

A record is just a mapping, but you can't practice DNS without something real to point it at. Creating a basic record uses the same handful of fields every time: give it a Record Name (like test.example.com), pick a Type (A is the usual starting point), enter a Value (the server's IP address), set a TTL, and choose a Routing Policy — Simple is the default choice for a single server.

To actually check what a domain resolves to, without opening a browser, you use a couple of small command-line tools:

  • nslookup <domain> — the standard lookup tool that comes with Windows.
  • dig <domain> — a more detailed lookup tool on Mac and Linux, which also shows the TTL counting down.

Neither comes pre-installed on Amazon Linux CloudShell — install it first:

sudo yum install -y bind-utils

The demo setup used throughout this section

To make every routing policy concrete, three EC2 servers were launched in three different AWS Regions, each running Amazon Linux 2 on a t2.micro instance with port 80 open, each serving a simple page announcing its own location:

  • Server 1 — eu-central-1 (Frankfurt)
  • Server 2 — us-east-1 (N. Virginia)
  • Server 3 — ap-southeast-1 (Singapore)

An Application Load Balancer was also created in eu-central-1, pointed at the Frankfurt server.

💡 New word ALB (Application Load Balancer) is an AWS service that spreads incoming web traffic across multiple servers, and checks whether each one is healthy before sending it anything. Route 53 can point straight at one.
Worth remembering: typing an EC2 instance's raw public IP into a browser skips DNS completely. A DNS record only exists to give that IP address a friendlier, memorable name.

5TTL (Time To Live)

Change a server's IP address in Route 53, and some users still hit the old one for a while afterward. The reason is caching — resolvers don't ask Route 53 the same question for every single visitor. They remember the answer for a while first.

💡 New word TTL (Time To Live) tells browsers and DNS resolvers how many seconds they're allowed to remember, or "cache," an answer before they have to ask Route 53 again.
While an answer is still cached, changes you make in Route 53 won't reach that client until the TTL window runs out.
SettingHigh TTL (e.g. 24 Hours)Low TTL (e.g. 60 Seconds)
Query Traffic / CostsLower — resolvers cache answers longer, making fewer calls to Route 53.Higher — resolvers query Route 53 frequently.
Change Propagation SpeedSlower — clients retain old cached IP addresses for up to 24 hours.Faster — clients fetch updated IP addresses rapidly.
🏭 In real companies TTL is a real lever engineering teams pull on purpose. Stable records — ones that almost never change — get a long TTL, often 24 hours or more, because that cuts down how often resolvers have to query Route 53, which lowers cost and load. Records tied to failover or an upcoming migration get a short TTL, sometimes as low as 60 seconds, specifically so that when something does change, users find out fast instead of hitting a dead server for hours.
Before a migration: lower the TTL ahead of time, wait out the old TTL window so old cached answers expire everywhere, then make the change. Clients pick up the new IP quickly, instead of some of them lagging behind by up to a full day.
Exception to remember: every record type needs a TTL you set yourself — except Alias records, which Route 53 manages automatically.

6CNAME vs Alias

You want your root domain — example.com, with no "www" — to point at a load balancer. A normal CNAME record can't do that. Both CNAME and Alias records map one domain name to another, but they behave very differently in ways AWS exams, and real production configs, care about a lot.

💡 New word CNAME record points a hostname at another hostname. The rule that trips people up: a CNAME record can never be placed at the apex — the bare root of a domain, like example.com with nothing in front of it.
💡 New word Apex domain (also called the root domain, or "zone apex") is the domain with nothing in front of it — example.com, not www.example.com. DNS rules forbid putting a CNAME record there.

That's exactly the gap Alias records exist to close.

💡 New word Alias record is a Route 53-only record type that looks like an A or AAAA record, but points directly at an AWS resource instead of a plain IP address — and unlike CNAME, it's allowed at the domain apex.
FeatureCNAME RecordAlias Record
Target DestinationAny external domain hostnameSpecific AWS resources only (ALB, CloudFront, S3 Website, etc.)
Apex / Root Domain Support? (e.g. example.com)❌ No (Forbidden at zone apex)✅ Yes (Supported at zone apex)
PricingStandard Route 53 query pricingFree of charge for AWS targets
TTL ManagementConfigured manuallyManaged automatically by Route 53
Health Check SupportNo native health checksNative built-in health check awareness
Record TypeCNAMEConfigured as A or AAAA type with Alias enabled
Alias records solve the CNAME apex limitation by letting a root domain, like example.com, map directly to an AWS-managed resource.

What Alias records are allowed to point at

Alias records only work with a specific list of AWS-managed targets:

  • Elastic Load Balancers (ALB, NLB, or the older Classic Load Balancer)
  • Amazon CloudFront Distributions
  • AWS API Gateway Endpoints
  • AWS Elastic Beanstalk environments
  • Amazon S3 Static Website Endpoints (not a raw S3 bucket name)
  • Amazon VPC Interface Endpoints
  • AWS Global Accelerator
  • Another Route 53 record in the same hosted zone
Exam trap: you cannot create an Alias record pointing straight at a raw EC2 instance's hostname. Alias records only target the AWS-managed service resources listed above.
🏭 In real companies This is exactly why almost every production setup you'll see uses an Alias record, not a CNAME, to point a company's bare root domain at its load balancer or CloudFront distribution. It's also free for AWS targets, its TTL is managed for you, and it's aware of health checks — three more reasons teams default to it whenever the target supports it.

7Routing Policies & Simple Routing

Route 53 now knows which IP address belongs to your app. But what if you have three servers, on three continents — which one does it hand back? That decision is exactly what a Routing Policy controls.

💡 New word Routing Policy is the rule Route 53 follows when a record could have more than one possible answer — it decides which IP (or which set of IPs) to hand back for a given query. Route 53 offers seven of them: Simple, Weighted, Latency-Based, Failover, Geolocation, Geoproximity, IP-Based, and Multi-Value Answer.
Worth remembering: Route 53 never actually touches your web traffic. It only answers DNS questions with an IP address. Once it hands that answer back, the client connects straight to that server itself — Route 53 is out of the conversation from that point on.

Simple Routing

Simple routing is the plain, no-frills option: one record, pointing at one resource. If you list more than one IP value under a single Simple record, Route 53 just returns all of them, and the client itself picks one at random. Health checks aren't supported here at all — there's no logic to route around a failure.

8Routing Policy: Weighted

You've built a new version of your app. You don't want to flip every user over to it at once — what if it's broken? Weighted routing splits traffic between multiple records using a percentage you set.

Route 53 works out that percentage with a simple formula: Traffic % for Record A = Weight A ÷ (sum of all weights). The weights don't need to add up to 100 — Route 53 just does the division either way.

Relative weights split DNS answers: 70% to us-east-1, 20% to eu-central-1, 10% to ap-southeast-1.

What it's actually used for

  • Spreading load across regional data centers.
  • Canary testing — sending a small slice of traffic, like 1%, to a brand-new version while 99% keeps hitting the stable one.
  • Setting a record's weight to 0 stops all traffic to it, without deleting the record.
Rule to remember: every record inside the same weighted set must share the exact same name and the exact same record type.
🏭 In real companies Weighted routing is the standard mechanism behind canary releases — the common industry practice of rolling a new version out to a tiny slice of real users first, watching for errors, then gradually raising the percentage if nothing breaks. It turns a risky "flip the switch for everyone" deploy into a slow, reversible ramp.

9Routing Policy: Latency-Based

A user in Mumbai and a user in Virginia both type the same address. Should they both land on the same server? Latency-based routing says no — send each user to whichever Region actually responds fastest for them, right now. Route 53 constantly measures real network latency between AWS Regions and the wider internet, and uses that live data to decide.

🏭 In real companies Global companies with servers running in multiple Regions commonly rely on latency-based routing for exactly this reason: a user in India gets routed to a server in Mumbai instead of one in Virginia, which can meaningfully cut page-load time. It's not about which server is closest on a map — it's about which one actually answers fastest for that specific user, which usually, but not always, turns out to be the same thing.

10Health Checks

Weighted and latency routing both quietly assume every server is actually up. What if one of them isn't? That's where a Health Check comes in — Route 53 continuously testing a server on your behalf, so it can stop sending traffic to one that's actually broken.

💡 New word Health Check is an automated, repeated test Route 53 runs against your server. If it starts failing, Route 53 can automatically stop routing traffic to it.
About 15 global health checkers test your endpoint on a schedule, watching for HTTP 2xx/3xx response codes.

The knobs you can turn

  • Check interval — every 30 seconds by default, or every 10 seconds ("Fast") for an extra cost.
  • Supported protocols — HTTP, HTTPS, or plain TCP.
  • Failure threshold — how many checks in a row have to fail before Route 53 calls it unhealthy (3, by default).
  • Healthy response codes — HTTP 2xx and 3xx status codes count as healthy; anything else doesn't.
Easy-to-miss rule: Route 53's health checkers run on the public internet. Your security groups and firewalls have to explicitly allow traffic in from Route 53's published health-checker IP ranges, or every check will just look like a failure.

Three kinds of health check

Health Check TypeMonitored Target
Endpoint Health CheckMonitors a public IP or hostname directly over HTTP, HTTPS, or TCP.
Calculated Health CheckCombines multiple child health checks using AND/OR/NOT logic (up to 256 children). Useful for maintenance windows.
CloudWatch Alarm Health CheckMonitors a CloudWatch alarm. The primary way to health-check private VPC resources that public checkers can't reach.
🏭 In real companies Public health checkers can't reach anything living inside a private VPC — there's no public IP to test. So the standard workaround is a CloudWatch Alarm health check instead: something inside the VPC reports its own status into CloudWatch, and Route 53 watches that alarm rather than trying to reach the resource directly.

11Routing Policy: Failover

Your primary Region goes down at 3am. Does someone have to wake up and manually redirect traffic — or can that happen automatically? It can happen automatically, and this is exactly what Failover routing is built for: an Active/Passive setup with one Primary resource doing all the real work, and one Secondary sitting on standby.

A mandatory health check watches the Primary. If it fails, Route 53 automatically starts answering with the Secondary instead.
Exam rule: a Failover set supports exactly one Primary and one Secondary record — no more. A health check on the Primary is mandatory, not optional.
🏭 In real companies This is the standard, well-documented mechanism behind a lot of real disaster-recovery setups: Route 53 health checks watch the primary Region, and the moment it looks unhealthy, traffic automatically starts flowing to a backup Region instead — with no human needing to react in the middle of the night. Pairing it with a low TTL on the record (see Section 5) is what makes that failover actually fast for real users, instead of technically working but taking hours to show up.

12Routing Policy: Geolocation

What if the rule isn't "fastest server" but "this content is only licensed for this country"? Geolocation routing answers DNS queries based on where the user actually is — by continent, by country, or even by US state. It's easy to confuse with Latency routing, but they solve different problems: Latency picks the fastest server; Geolocation picks strictly by the user's real-world location, even if a faster server exists elsewhere.

  • Always create a Default Record to catch any user whose location doesn't match one of your specific rules.
  • Common uses: serving a page in the right local language, respecting content licensing that only allows certain countries, or splitting load by geography.
🏭 In real companies Media and streaming platforms are the most visible example of this pattern in the wild — many restrict certain shows or movies to specific countries for licensing reasons, and geolocation-style routing is one of the tools behind enforcing that at the DNS level, alongside other checks further up the stack.

13Routing Policy: Geoproximity

What if two Regions could both serve a location, and you want to shift the boundary between them without physically moving anything? Geoproximity routing sends users to the resource that's geographically closest to them, but with a twist: you can nudge the boundary between two regions using a Bias value, without touching any actual infrastructure.

  • Positive bias (+) — makes a Region's coverage area bigger, pulling in more traffic.
  • Negative bias (-) — makes a Region's coverage area smaller, pushing traffic away.
  • Setting this up requires the Route 53 Traffic Flow policy editor — it's not available on the plain record-creation screen.
Adjusting positive bias expands a region's geographic coverage zone, shifting user traffic toward it.

This policy is reached for far less often than Weighted or Latency routing, but it's the right tool when you specifically need to reshape geographic coverage boundaries rather than just split traffic evenly.

14Routing Policy: IP-Based

IP-Based routing looks at the actual IP range — the CIDR block — that a query is coming from, and routes based on that.

💡 New word CIDR block is a compact way of writing an entire range of IP addresses at once, like 203.0.113.0/24, instead of listing every individual address.

This makes it possible to route a specific ISP's users, or an entire corporate office's network, to a particular endpoint on purpose — useful when you know in advance exactly which network ranges certain users are coming from.

15Routing Policy: Multi-Value Answer

Multi-Value Answer routing returns up to 8 healthy records for a single query, which gives the client a basic form of load balancing without needing a load balancer resource at all. Unlike Simple routing, it's fully aware of health checks — any unhealthy record gets filtered out of the list automatically before it's ever handed to a client.

163rd Party Domains & Route 53

What if you already bought your domain somewhere else, years ago — do you have to move it to switch to Route 53? No. Buying a domain (the registrar's job) and managing its DNS records (the DNS host's job) are actually two separate roles, and nothing forces them to be the same company.

Configuration steps

  1. Create a Public Hosted Zone in Route 53 for your domain.
  2. Copy the four Name Server (NS) addresses Route 53 assigns to that zone.
  3. Log into your original registrar (GoDaddy, Namecheap, wherever you bought it) and replace its default name servers with those four Route 53 addresses.
🏭 In real companies This exact pattern — a domain purchased years earlier through a general-purpose registrar, with its DNS delegated over to Route 53 — is common. Teams do it specifically to get access to Route 53's routing policies, health checks, and Alias records, without having to actually transfer ownership of the domain itself.

Key Facts Worth Remembering

  • Route 53 is authoritative DNS, a domain registrar, and a health-checking service — with the only 100% Availability SLA in AWS.
  • Hosted zones cost $0.50/month; domain registration starts around $12/year.
  • A = IPv4, AAAA = IPv6, CNAME = hostname-to-hostname (non-apex only), NS = name servers.
  • CNAME can't sit at the apex. Alias records can — and they're free, auto-TTL, and health-check aware for AWS targets. They still can't point at a raw EC2 hostname.
  • High TTL = fewer Route 53 queries, slower propagation. Low TTL = faster propagation, more queries — use it before a migration or for failover records.
  • Health checks: about 15 global checkers, >18% healthy required to pass, HTTP 2xx/3xx counts as healthy. Use a CloudWatch Alarm health check for private VPC resources.
  • Failover needs exactly one Primary and one Secondary, and the Primary's health check is mandatory.

The One-Paragraph Version

DNS turns domain names into IP addresses through a recursive chain of servers, and Route 53 is AWS's own authoritative version of that system, storing your records inside hosted zones. Every record needs a Type, a Value, a Routing Policy, and a TTL — except Alias records, which manage their own TTL and can sit at the apex where a CNAME never can. Routing policies decide which answer Route 53 gives back when more than one is possible: Simple for one target, Weighted for percentage splits and canary tests, Latency for the fastest Region, Failover for disaster recovery, Geolocation and Geoproximity for geography, IP-Based for known client ranges, and Multi-Value for a handful of healthy answers at once. Health checks are the thread tying most of these together — they're what let Route 53 notice a server is down and route around it automatically.
