1EC2 Instance Metadata — What an Instance Knows About Itself

An EC2 instance is code running on a server somewhere in AWS. That code often needs to know things about itself: its own private IP address, the IAM role attached to it, temporary credentials for that role. Asking AWS over the network for that would create a chicken-and-egg problem — how would the instance prove who it is?

The answer is the Instance Metadata Service. Every EC2 instance can query a special local address — one that only exists inside the instance itself — to fetch information about itself without needing any credentials stored on disk.

💡 New word IMDS (EC2 Instance Metadata Service) is a service running inside every EC2 instance. The instance queries it at a link-local IP address to fetch information about itself — instance ID, private IP, IAM role, and temporary credentials.

The address is always the same:

http://169.254.169.254

From this address, an instance can fetch its hostname, public IP address, private IP address, instance type, and — most importantly for security — temporary credentials for the IAM role attached to the instance.

Critical detail: You cannot fetch the policy document itself from IMDS — only the temporary credentials. If you need to see what permissions an instance actually has, read the IAM role policy directly through the console or CLI.

IMDSv1 vs. IMDSv2 — A Security Difference

IMDS has two versions, and they differ in a crucial way:

VersionHow It WorksSecurity Trade-off
IMDSv1A simple HTTP GET to the URL directly gets metadataVulnerable to attack if attacker tricks instance into making the request
IMDSv2Two-step process: PUT request to get a session token, then use that token in a GET requestStronger; harder to exploit. Default on modern AMIs
💡 New word Session token (in IMDSv2 context) is a temporary, time-bound credential that proves you are allowed to query metadata. The instance gets it via PUT request and includes it in the header of all subsequent metadata requests.
IMDSv2 requires an instance to request a session token first, then include that token in the header for subsequent requests. This stops certain types of attacks in their tracks.
🏭 In real companies Major cloud security incidents have exploited IMDSv1 vulnerabilities. When an attacker finds a Server-Side Request Forgery (SSRF) bug in an instance's application code, they can trick the code into querying metadata and stealing credentials. IMDSv2's token-based approach makes that exploit much harder. Modern security teams and AWS security standards now treat IMDSv1 the same way they treat unencrypted HTTP — acceptable only in specific circumstances, not as a default.

2Fetching Metadata in Practice

When you launch an EC2 instance, you can choose which IMDS version the instance will support: both v1 and v2, or v2 only. Newer AMI images, like Amazon Linux 2023, enforce v2 only by default.

Common error: If you try a direct IMDSv1 curl command on an instance that only supports v2, you'll get a 401 Unauthorized response. The instance is not broken — it's working correctly by refusing the less-secure protocol.

Fetching Metadata Using IMDSv2

Here's the two-step process:

  1. Request a session token with a PUT request: 
    TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
  2. Use that token to fetch metadata by adding it as a header: 
    curl -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/
  3. Specific metadata paths include /local-ipv4 (private IP), /public-ipv4 (public IP), and /iam/security-credentials/your-role-name (temporary credentials).
In production: You don't need to fetch IMDS credentials manually in your code. The AWS CLI and AWS SDK automatically call IMDS in the background. Only do this by hand when troubleshooting or testing whether an instance can reach metadata.

3AWS CLI Profiles — Managing Multiple Accounts

Most teams work across multiple AWS accounts. You might have a development account where engineers experiment freely, a staging account that mimics production, and a production account itself that real customers depend on. Switching between them manually — deleting one set of credentials and configuring another — would be tedious and error-prone.

💡 New word Named profile (in AWS CLI context) is a named set of credentials and configuration settings stored locally on your laptop, so you can switch between accounts by name instead of manually reconfiguring.

The AWS CLI stores profiles in two local files: ~/.aws/credentials (your access keys) and ~/.aws/config (region and output format). By default, there's always a [default] profile. You can create as many named profiles as you need.

Setting Up and Using Profiles

To create or update a profile called my-dev-account:

aws configure --profile my-dev-account

The CLI will prompt you for your Access Key ID, Secret Access Key, default region, and output format. Once saved, run any CLI command with that profile:

aws s3 ls --profile my-dev-account

Forget the --profile flag, and the CLI uses [default] by default. This is why it's called the default profile.

🏭 In real companies Teams with dozens of accounts often automate profile management using wrapper scripts or tools like Leapp. Manually configuring each one is fine at first, but once you have more than three or four accounts, the overhead becomes real. The bigger pattern: avoid storing permanent access keys on your laptop at all. Use temporary credentials from a central identity system instead.

4Using the AWS CLI with MFA

MFA (Multi-Factor Authentication) protects your login by requiring two different proofs of identity: something you know (your password) and something you have (an authenticator app or security key). To run AWS CLI commands when MFA is enabled, you need to generate temporary session credentials.

💡 New word STS (AWS Security Token Service) is the AWS service that hands out temporary, short-lived credentials instead of permanent ones. It's perfect for MFA workflows and assuming roles.

To get temporary CLI credentials with MFA, use the STS API call get-session-token. You pass your MFA device ARN (Amazon Resource Name) and the current 6-digit code from your authenticator:

aws sts get-session-token \
  --serial-number arn:aws:iam::123456789012:mfa/your-username \
  --token-code 123456

AWS returns three pieces: a new Access Key ID, a new Secret Access Key, and a session token. Add these to your ~/.aws/credentials file as a new temporary profile, and use that profile for CLI commands. The credentials expire automatically (usually in a few hours), so you'll repeat this step periodically.

🏭 In real companies Long-lived access keys stored on developer laptops are a known risk. A lost or stolen laptop means the attacker has permanent credentials until someone manually revokes them — and that could take hours or days. By contrast, session tokens from STS expire automatically. This is why many security teams now require MFA for CLI access and cap session-token lifetime to a few hours. It's a simple rule that significantly raises the bar for credential theft.

5AWS SDK — Calling AWS from Your Code

The AWS Console is useful for learning and making one-off changes. But real systems automate everything: deployment pipelines, data processing jobs, and background services all call AWS APIs programmatically. That's what the AWS SDK is for.

💡 New word SDK (Software Development Kit) is a language-specific library — available for Python, Java, JavaScript, Go, C++, and others — that lets your code call AWS services directly without crafting HTTP requests by hand.

For example, Python applications use Boto3 (nicknamed "boto"), Node.js uses the AWS SDK for JavaScript, and Java uses the AWS SDK for Java. Each SDK handles authentication, retries, error handling, and all the AWS-specific conventions so you only have to write the business logic.

🏭 In real companies The AWS CLI itself is written in Python and built on top of Boto3. When you run aws s3 sync, you're really calling Boto3 under the hood. This isn't a coincidence — it means the CLI and SDK share the same underlying logic, so they behave identically. A command that works in the CLI will work the same way in your Python code.

A Practical Example

Python code to list S3 buckets using Boto3 looks like this:

import boto3

s3 = boto3.client('s3')
response = s3.list_buckets()
for bucket in response['Buckets']:
    print(bucket['Name'])

The SDK handles authentication automatically — it will check for credentials in environment variables, then IMDS (if running on EC2), then local CLI config files. You don't hardcode keys into your code.

6Handling Throttling with Exponential Backoff

AWS enforces limits to protect shared infrastructure. There are two main types:

Limit TypeWhat It ControlsExample
API Rate LimitsHow many API requests per second to a specific serviceS3 allows 5,500 GET requests per second per partition key
Service QuotasTotal resources you can run simultaneously in an accountMaximum number of EC2 instances, vCPUs, or RDS databases allowed

When you exceed an API rate limit, AWS returns a throttling error (HTTP status 429, error code SlowDown or ThrottleException). A naive response is to retry immediately. A smart response is to wait a bit, then try again, and gradually increase the wait time.

💡 New word Exponential backoff is a retry strategy: when a request fails due to throttling, wait a short time before retrying. If it fails again, double the wait time (e.g., 1 second → 2 seconds → 4 seconds → 8 seconds). This gives the overloaded service time to recover without overwhelming it further.
Exponential backoff: Each failed retry triggers a progressively longer wait. This gives overloaded systems breathing room instead of hammering them with requests.
Good news: Every AWS SDK has exponential backoff built in automatically. You don't have to implement it yourself. If you're using the SDK and get throttled, it will silently retry with increasing delays. This is why the SDK is almost always the right choice for production code.
Exam tip: If a question says "my application is getting throttling errors," the correct answer is almost always "implement exponential backoff" or "use an SDK" (which does it for you). Raw HTTP requests without backoff are a red flag.

7AWS Signature v4 — How Requests Get Signed

Every single request sent to an AWS API must be cryptographically signed using your secret credentials. This proves to AWS that you actually sent the request and that the request hasn't been tampered with in transit. The signing protocol is called Signature v4 or SigV4.

💡 New word SigV4 (Signature Version 4) is AWS's request-signing protocol. It uses your Secret Access Key to compute a unique signature for each request. AWS verifies the signature to confirm authenticity.

The CLI and SDK do this signing automatically — you never see it. But under the hood, the signature can be sent in two ways:

MethodHow It WorksWhen Used
Authorization HeaderThe signature goes in a standard HTTP Authorization headerDefault for CLI and SDK requests
Query String ParametersThe signature is appended directly to the URL as a parameter like ?X-Amz-Signature=...Pre-signed URLs (e.g., temporary download links for S3 files)
SigV4 signatures can ride in the Authorization header (standard) or in the URL itself (pre-signed URLs).
🏭 In real companies Pre-signed URLs (query string signatures) are commonly used to give temporary download access to private S3 files. Instead of handing out credentials, you generate a URL that includes the signature and an expiration time. Anyone with the URL can download the file until it expires. This is how CDNs, email services, and apps share protected files without exposing access keys.

📋 Cheat Sheet

Key Concepts at a Glance

  • IMDS: Every EC2 instance can query 169.254.169.254 to fetch metadata and temporary IAM role credentials. Use IMDSv2 for better security.
  • CLI Profiles: Store multiple AWS account credentials locally as named profiles. Switch accounts using --profile flag.
  • MFA with CLI: Use aws sts get-session-token to generate temporary credentials, then configure a temporary profile in ~/.aws/credentials.
  • AWS SDK: Language-specific library for calling AWS from code. Available for Python (Boto3), JavaScript, Java, Go, C++, and others.
  • Exponential Backoff: Retry failed API requests with progressively longer delays (1s, 2s, 4s, 8s...). SDKs do this automatically.
  • SigV4: Request-signing protocol. Signature goes in either the Authorization header (default) or URL query parameters (pre-signed URLs).

Decision Tree

  • Application needs to call AWS services? → Use the SDK for your language.
  • Working with multiple AWS accounts? → Use CLI profiles.
  • Running CLI commands with MFA enabled? → Use sts get-session-token.
  • Getting 429 throttling errors? → SDKs handle exponential backoff automatically. Raw HTTP code needs to implement it manually.
  • Need to verify instance has correct role and credentials? → Query IMDS from inside the instance (IMDSv2 recommended).

One-Paragraph Mental Model

EC2 instances use IMDS to fetch metadata and temporary role credentials securely (IMDSv2 via session tokens). Developers manage multiple AWS accounts locally with CLI profiles. When MFA is required, STS generates temporary credentials that expire automatically. The AWS SDK — available in multiple languages — handles authentication and retries (exponential backoff) automatically. All requests to AWS are signed with SigV4: either in the Authorization header (standard) or in the URL (pre-signed links). The security principle throughout: temporary credentials are better than permanent ones, and automation (via SDK/CLI) is better than manual HTTP requests.
