1AWS SES

Every application that needs to send email — a password reset link, an order confirmation, a scheduled report — eventually hits the same problem: running an email server is tedious, and getting emails to land in the right inbox instead of spam requires careful setup. AWS SES solves that by giving you a managed, scalable email service.

💡 New word SES (Simple Email Service) is AWS's managed email sending and receiving service. It lets you send mail through an SMTP interface or the AWS SDK, and also receive incoming mail, routing it into S3, SNS (Simple Notification Service), or Lambda for processing.

Access to SES is controlled through ordinary IAM permissions — the same policy framework you use everywhere else in AWS.

Common use case

An e-commerce site needs to send transactional emails after a customer completes a purchase. Instead of managing SMTP credentials and a mail server, the order-processing Lambda function simply calls SES to send the email. SES handles deliverability, bounce tracking, and compliance with anti-spam rules. The entire email lifecycle is just a few lines of code.

Exam tip: If a question is about sending or receiving email, SES is almost certainly the right answer. Don't overthink it — SES = email.

2Amazon OpenSearch Service

DynamoDB is fast for queries where you know your access pattern upfront — give it a partition key and sort key, and it zips to the result. But what if you need to search for customers by email address, even if your table is keyed by customer_id? What if you want partial-text matches, or full-text search? That's where OpenSearch comes in.

💡 New word OpenSearch is a search and analytics engine (the successor to Amazon Elasticsearch, renamed for licensing reasons). Unlike DynamoDB, it lets you search any field, including partial matches and full-text queries. It's commonly used as a search layer alongside another database, not as your primary data store.

OpenSearch also surfaces data through OpenSearch Dashboards for analytics and visualization.

How OpenSearch actually works in production

A common real pattern starts with DynamoDB as your source of truth. When an item changes, a DynamoDB Stream sends that change to a Lambda function, which pushes the data into OpenSearch. Now your app can do two things: when a user types a search query, OpenSearch returns the matching item IDs in milliseconds; then the app fetches the full item details from DynamoDB. This two-step dance means DynamoDB stays authoritative, while OpenSearch handles the speed of search.

🏭 In real companies Most search implementations run exactly this pattern — a primary database (DynamoDB, PostgreSQL, or MongoDB) as the source of truth, with OpenSearch as a search index kept in sync. The separation means you can rebuild the index from scratch without losing data, and queries are fast because OpenSearch is optimized for search, not storage.

Two flavors: managed vs. serverless

OpenSearch offers a managed cluster mode, where you see and manage the actual cluster instances, deciding how many nodes you need and how to replicate them. Or choose serverless, where AWS handles all the scaling and operations — you just query it and pay for what you use.

Data flows into OpenSearch from several sources: a DynamoDB Stream plus Lambda, Kinesis Data Firehose (near real time), CloudWatch Logs, or a custom application. Security is handled through Cognito for user authentication combined with IAM, plus encryption at rest and in flight.

DynamoDB stays the source of truth, while OpenSearch (kept in sync via Streams + Lambda) provides fast partial-match search back to the item's ID.

3Amazon Athena

You have years of data sitting in S3 — server access logs, application events, clickstreams — and you want to ask questions like "how many unique users visited last week" or "what's the 99th percentile of request latency." Running a traditional database for this is expensive and overkill. Athena lets you query S3 directly using standard SQL.

💡 New word Athena is a serverless query service (built on Presto) that runs SQL directly over data in S3 — no database provisioning, no data movement. You pay a fixed amount per terabyte of data scanned, not per query or compute time.

Athena supports CSV, JSON, ORC, Avro, and Parquet formats. It's typically paired with Amazon QuickSight for dashboards — QuickSight can run queries against Athena and visualize the results in real time.

Where Athena shines

Athena is perfect for ad hoc analytics, business intelligence reports, and analyzing AWS service logs (VPC Flow Logs, load balancer access logs, CloudTrail audit trails). You write a single SQL query, Athena scans the parts of S3 it needs, and you get back a CSV of results. No infrastructure to manage.

Performance optimization (critical for the exam)

Since you pay per terabyte scanned, every optimization saves money. Use columnar formats like Parquet or ORC instead of CSV — if you only need three columns out of fifty, scanning just those three columns costs a fraction as much. Compress your data; use the AWS Glue ETL service to convert raw CSV into compressed Parquet. Partition your S3 data by date — structuring your S3 prefix as year=2024/month=06/day=15/ means a query filtering on June only scans June's folders, skipping the rest. And use larger files (128 MB+) rather than many small ones, since scanning overhead scales with file count.

Real-world optimization: A company migrated their analysis logs from raw CSV to Parquet, compressed. The same queries that scanned 500 GB of data on CSV files now scanned only 50 GB on Parquet — a 10x reduction in cost with no code changes.

Reaching beyond S3 — Federated Query

Athena's native home is S3, but it can also query databases that sit elsewhere — relational databases like RDS, NoSQL like DynamoDB, data on premises, or even custom data sources. This happens through a Data Source Connector, which is just one Lambda function per external source. Athena calls the Lambda, the Lambda talks to the external system, and results flow back to the Athena query.

Athena can query S3 natively, or reach beyond S3 through per-source Lambda connectors, combining results on the fly.

4Amazon MSK

AWS Kinesis is a good streaming solution for many teams, but some organizations are already deeply committed to Apache Kafka — a different streaming platform with its own ecosystem and operational patterns. If your team needs Kafka specifically (not Kinesis), then Amazon MSK is the managed path.

💡 New word MSK (Managed Streaming for Apache Kafka) is a fully managed Kafka cluster service. AWS provisions the Kafka brokers and Zookeeper nodes, spreads them across up to three Availability Zones for high availability, handles recovery from failures, and stores data on EBS for as long as you want. A Kafka topic is the basic unit of data — producers write to it, consumers read from it — conceptually similar to Kinesis shards, but called partitions in Kafka.

Two operating modes are available: MSK provisioned, where you decide how many brokers you need, and MSK Serverless, where AWS scales compute and storage automatically based on your workload — removing all capacity-planning burden.

Kafka vs. Kinesis — side by side

Both are streaming platforms, but the details differ. Kinesis enforces message size at 1 MB by default, while Kafka lets you configure sizes up to 10 MB or more. Kinesis shards split to scale up and merge to scale down; Kafka partitions can only be added, never removed. Kinesis always encrypts data in flight; Kafka gives you a choice — plaintext or TLS, your pick. Both support encryption at rest and retention. Kinesis has standard retention limits, but MSK lets you keep data on EBS indefinitely if you pay for the storage.

Consuming from MSK

Once data is in a Kafka topic, it can be processed by Kinesis Data Analytics for Apache Flink, a Glue streaming ETL job (powered by Spark Streaming), a Lambda function (with MSK as an event source), or your own Kafka consumer code running on EC2, ECS, or EKS.

Producers write to a Kafka topic; consumers pull from it. Partitions are replicated across brokers for durability and throughput.

5AWS Certificate Manager (ACM)

HTTPS — encrypted web traffic — requires a TLS certificate. Traditionally, you buy a certificate from a CA (Certificate Authority), upload it to your server, set up renewal reminders, and pray you don't forget and let it expire (which has caused real outages at major companies). ACM removes all that tedium.

💡 New word ACM (AWS Certificate Manager) automatically provisions, manages, and renews SSL/TLS certificates for your endpoints. Public certificates are completely free, and ACM handles automatic renewal, so your HTTPS endpoint never expires. It integrates directly with AWS-managed endpoints like load balancers, CloudFront distributions, and API Gateway.

How ACM works in the real world

You request a public certificate for your domain (e.g., example.com). ACM validates that you own the domain — typically via DNS validation, where ACM creates a special DNS record in Route 53, proves ownership, and then automatically issues the certificate. Once issued, you attach it to your load balancer, CloudFront distribution, or API Gateway. That AWS service loads the certificate and handles TLS termination — clients connect with HTTPS, your backend talks plain HTTP, and certificate renewal happens silently in the background. No code changes, no server downtime, no reminder emails.

🏭 In real companies The most common use case is attaching an ACM certificate to an Application Load Balancer (ALB). The ALB's HTTPS listener loads the certificate, terminates TLS, and forwards plain HTTP to EC2 instances behind it. This setup is so standard that AWS offers it as the default in Elastic Beanstalk and CloudFormation templates — you pick your domain, and ACM/ALB/Route 53 are configured for you.
ACM loads the TLS certificate onto the load balancer, which terminates HTTPS from clients while still talking plain HTTP to the backend.
Exam tip: Any question about provisioning or renewing certificates on an AWS-managed endpoint should immediately point you to ACM. Don't confuse it with certificate pinning, self-signed certs, or manually managing certificates on EC2 — those are different problems.

6ACM Private CA

Public certificates from ACM work for internet-facing endpoints. But inside your organization, you might need certificates for internal APIs, databases, IoT devices, or user authentication — places where you control the entire chain of trust and don't need the public internet to verify your certs. That's where a private Certificate Authority comes in.

💡 New word ACM Private CA is a managed private Certificate Authority service. You create your own root CA (and optionally subordinate CAs underneath it) to issue end-entity X.509 certificates trusted only within your organization — they're never trusted on the public internet.

These private certificates can still be loaded onto AWS services with ACM integration — load balancers, CloudFront, API Gateway, and Kubernetes services — just like public certificates. You control the entire certification process and trust chain.

Real use cases

A financial services company issues certificates to authenticate every API call between internal microservices — no passwords, just mutual TLS. A manufacturing company issues certificates to IoT devices on the factory floor, so devices can authenticate to a central system. An enterprise issues certificates for internal LDAP servers, and every employee's device trusts those certificates automatically. In each case, a private CA is the right tool.

A private CA hierarchy issues certificates trusted only internally, never exposed on the public internet.

7Amazon Macie

Your S3 buckets contain years of data — documents, images, databases, logs. But mixed in with the innocuous stuff might be personally identifiable information (names, email addresses, credit card numbers, health data, government IDs) that you didn't realize was there. If a bucket accidentally gets public read access, that sensitive data leaks. Macie uses machine learning to find what you're hiding.

💡 New word Macie is a fully managed data security and privacy service that uses machine learning and pattern matching to discover and protect sensitive data in AWS — most commonly PII (personally identifiable information) sitting in S3 buckets.

To use Macie, you simply point it at the S3 buckets you want scanned — it's essentially one click in the AWS console. Macie crawls through your data, recognizes patterns (like 16-digit numbers that look like credit card numbers, or Social Security number patterns), and surfaces its findings through EventBridge. From there, you can route discoveries to SNS for alerting, Lambda for automated remediation, or anywhere else in your event-driven pipeline.

🏭 In real companies Compliance frameworks like GDPR, CCPA, and HIPAA require organizations to know where sensitive data lives and how it's protected. Macie fills that requirement automatically — instead of running manual audits, you get continuous monitoring with alerting when new sensitive data is detected.

8AWS AppConfig

Feature flags have become essential in modern software delivery. Instead of rebuilding and redeploying an entire application to turn on a new feature, you should be able to flip a switch in production, have the running application pick up the change instantly, and if something goes wrong, flip it back. AppConfig is the AWS service that manages this lifecycle.

💡 New word AppConfig is a configuration management service that lets you configure, validate, and dynamically deploy configuration into running applications — all without restarting the app or redeploying code.

The classic use case: feature flags

You ship an application with a new feature disabled — a JSON flag in AppConfig says feature_new_checkout: false. Later, you want to enable it for just 5% of users to test. You flip the flag to true and set a canary rollout to 5%. The running application polls AppConfig, picks up the change within minutes, and routes traffic to the new code path. If your monitoring sees errors spike, a CloudWatch alarm triggers an automatic rollback, and the flag flips back to false — all without touching the deployment.

Beyond feature flags

The same mechanism works for any runtime configuration — tuning performance parameters (max connection pool size, cache TTL), managing IP allow/block lists, or any other config an application needs to read at runtime. AppConfig supports apps on EC2, Lambda, ECS, and EKS.

Validation and gradual rollout

Before a configuration change deploys, AppConfig can validate it — either using a JSON Schema (checking data types and structure) or a Lambda function (for complex custom validation logic). Once validated, you can roll out the configuration gradually across instances instead of all at once, with a CloudWatch alarm able to trigger an automatic rollback if something looks wrong.

Configuration rolls out gradually across instances, with CloudWatch alarms able to trigger automatic rollback if metrics degrade.

Quick decision guide

  • Need to send or receive email? SES.
  • Need to search data by any field, including partial matches? OpenSearch layered on top of your primary database.
  • Need to run SQL on raw S3 data without a database? Athena.
  • Need Kafka specifically, not Kinesis? MSK.
  • Need HTTPS certificates for a load balancer, CloudFront, or API Gateway? ACM.
  • Need certificates trusted only inside your organization? ACM Private CA.
  • Need to find sensitive data hiding in S3? Macie.
  • Need to toggle features or change config without redeploying? AppConfig.

The one paragraph version

This section is a grab-bag of services, each solving one narrow, well-defined problem. SES handles email. OpenSearch adds full-text search on top of another database. Athena runs SQL directly on S3 data. MSK is Kafka if you need Kafka. ACM (and its Private CA variant) manages TLS certificates automatically. Macie finds sensitive data you didn't realize was exposed. AppConfig lets you change application behavior without a redeploy — particularly useful for feature flags. None of them require deep expertise for the exam — just enough to recognize which keyword in a question points to which service.
