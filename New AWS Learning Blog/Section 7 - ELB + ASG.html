58High Availability and Scalability

Picture this: your app has 200 users today. Tomorrow, someone with a huge following shares it, and 200,000 people try to open it at the same time. Your one small server has no chance. This is exactly the problem AWS solves with scaling.

Scalability just means your app can handle more users by getting more computing power when it needs it, and less when it doesn't. There are two different ways to make that happen.

The first way is vertical scaling. You keep a single server, but you make it bigger — more CPU (Central Processing Unit, the chip that does the actual computing) and more memory. On AWS this looks like upgrading an EC2 (Elastic Compute Cloud) instance, AWS's name for a rented virtual server, from something small like t2.micro to something much bigger like t2.large. The catch: there's always a ceiling. Eventually there's no bigger server left to move to.

The second way is horizontal scaling, also called elasticity. Instead of making one server bigger, you add more servers and split the work between them. Need more capacity? Launch a few more EC2 instances — this is called scaling out. Traffic drops off? Remove some — scaling in. In the cloud, this takes seconds, which is exactly why almost every modern web app is built to scale horizontally instead of vertically.

💡 New word Availability Zone (AZ) — one physical data center location inside an AWS Region. A Region, like Mumbai, actually contains several separate AZs, so a fire or power cut in one of them doesn't take out the others.

That leads to a third, related idea: High Availability (HA). Scaling is about handling more load. HA is about staying online even when something breaks. You get HA by spreading your app across two or more Availability Zones, so one data center going dark doesn't take your whole app down with it.

🏭 In real companies Running a production workload in just one Availability Zone is treated as a real risk, not a shortcut to save a bit of setup time. AWS's own well-documented best practice is to deploy anything customer-facing across at least two AZs, precisely so a single data center outage never becomes a full outage for your users.

Here's how the three ideas line up side by side:

ConceptMeaningEveryday Example & Use Case
Vertical scalingUpgrading to a bigger EC2 instance (e.g. t2.micro → t2.large with more CPU & RAM).Single databases (like RDS or ElastiCache) that cannot split work across servers easily. Has a hardware limit.
Horizontal scalingAdding more EC2 instances (scale out) or removing extra ones (scale in).Modern web applications. Very easy in the cloud because you can launch new EC2 servers in seconds.
High Availability (HA)Running your app across 2 or more Availability Zones (separate physical data centers in a Region).Ensures your system stays online even if an entire data center experiences a power cut or disaster.
Exam tip: High Availability can be passive — like an RDS Multi-AZ standby database sitting idle until the main one fails — or active, where every server handles live traffic at once, like horizontal scaling. Don't assume HA always means every server is busy.

One more thing worth knowing: EC2 comes in a huge range of sizes. The smallest, t2.nano, has half a gigabyte of memory and a single CPU. The largest, u-12tb1.metal, has 12.3 terabytes of memory and 450 CPUs. Whatever size a workload needs, AWS almost certainly has it.

59Elastic Load Balancing (ELB) Overview

Say your app now runs on three separate EC2 servers instead of one, for extra capacity and safety. A new problem shows up immediately: which address do users actually visit? You can't hand out three different links and hope people spread out evenly.

💡 New word Load balancer — a dedicated service that sits in front of your servers, gives users one single address to visit, and spreads their requests across whichever backend servers are healthy and ready.

With a load balancer in place, users only ever talk to one front door. They never know, or need to know, which of your three servers actually answered them.

Every user connects to one central entry point (the load balancer). The load balancer spreads incoming requests across backend EC2 instances.

Why bother with a load balancer at all?

  • Single front door: your app gets one single, stable web address instead of a scattered list of server IPs.
  • Automatic fault tolerance: it constantly checks which servers are actually working, and quietly stops sending traffic to any that aren't.
  • SSL termination: it handles the heavy lifting of encrypting HTTPS traffic in one place, instead of every server doing it separately.
  • Sticky sessions: using cookies, it can keep sending one user back to the same backend server, when that matters.
  • High Availability: it spreads traffic smoothly across multiple Availability Zones, not just one.
  • Network security: your actual EC2 servers can sit inside a private network, invisible to the public internet — only the load balancer is exposed.

ELB (Elastic Load Balancer) is a fully managed service — AWS runs it for you, handling maintenance, security patches, and its own high availability. That's exactly why it's usually cheaper and more reliable than running your own load-balancing software on a server you'd have to maintain yourself. It also plugs directly into EC2, ASG, ECS (Elastic Container Service), ACM, CloudWatch, Route 53, WAF, and Global Accelerator.

💡 New word Health check — the load balancer's way of repeatedly asking each server "are you OK?" It sends a small request to a specific port and web route, for example HTTP:80/health. A reply of 200 OK means healthy. Anything else, and the load balancer marks that server unhealthy and stops sending it traffic immediately.
🏭 In real companies Health checks failing and automatically pulling a broken instance out of rotation is the standard real mechanism companies rely on to stop a bad deploy from taking down an entire service. If a new code release starts crashing on one or two servers, the load balancer notices within seconds and simply stops sending users to them — often before a human even sees an alert.

The 4 Types of AWS Load Balancers

Load balancers can also be set up as internal — reachable only inside your own private network — or internet-facing, open to the public. Which one you pick depends on whether real users need to reach it directly, or it's only routing traffic between your own internal services.

Security Group Setup — a pattern worth memorizing

Think of a Security Group as a virtual security guard standing at a door, deciding what traffic gets through. There's a specific pattern almost every real AWS setup uses:

  • The load balancer's security guard is told: let in HTTP (port 80) and HTTPS (port 443) traffic from anywhere on the internet, written as 0.0.0.0/0.
  • Each EC2 server's security guard is told something stricter: only let in traffic coming from the load balancer's own security group — never directly from the public internet.
Exam tip: this exact pattern shows up constantly on the exam. Backend EC2 instances should only ever accept traffic from the ELB's Security Group ID, blocking direct public access completely.

60A Quick Note on the Classic Load Balancer (CLB)

Heads up: the Classic Load Balancer, the oldest of the four types, is now deprecated. AWS has retired it from the Console's recommended path and from the current certification exams. Because of that, there's no hands-on walkthrough for it here — just know it exists, it's old, and it's not the right choice for a new project.

61Application Load Balancer (ALB)

Say your company runs three separate services behind one domain — a user service, a search service, and a payments service. Do you really need three separate load balancers, one per service? With an ALB, no. One is enough.

💡 New word ALB (Application Load Balancer) — a load balancer that works at Layer 7, the "application layer" that understands HTTP and HTTPS web traffic well enough to read the actual request — the URL path, the domain, even custom headers — and make smart routing decisions based on it.
💡 New word Target group — a named bucket of backend destinations that a load balancer sends traffic to. It doesn't have to be only EC2 servers — a target group can also hold ECS containers, AWS Lambda functions (serverless backend code), or even private IP addresses of on-premises machines.

An ALB can look at an incoming request and decide, in real time, which target group should handle it. That's called a routing rule, and there are a few kinds:

  • Path-based routing: send example.com/users to the user service's target group, and example.com/posts to the posts service's target group.
  • Host-based routing: send one.example.com to one target group and other.example.com to a completely different one.
  • Query string or header routing: route based on details inside the request itself, like ?platform=mobile going one way and ?platform=desktop going another.
One ALB routes /user web requests to one target group and /search requests to a completely separate target group.

This is exactly why ALB has become the default choice for microservices — small, independent services that together make up one app — and for containerized apps running on ECS, which need dynamic port mapping that ALB understands natively. It also supports newer protocols like HTTP/2 and WebSocket (a connection that stays open, used for real-time features like chat), and can automatically redirect insecure HTTP requests over to secure HTTPS.

🏭 In real companies Most companies that split a monolithic app into microservices end up standardizing on a single ALB with path-based or host-based routing rules, rather than running a separate load balancer per service. It's simpler to operate, and it's cheaper — you're paying for one load balancer instead of ten.

Target Groups Can Contain:

  • EC2 instances (usually managed automatically by an Auto Scaling Group)
  • Amazon ECS tasks (Docker containers)
  • AWS Lambda functions (serverless backend code)
  • Private IP addresses (on-premises physical servers)

Health checks run at the target group level, so a single ALB can watch the user service, search service, and payments service completely independently — and only mark the broken one as unhealthy.

A couple of details worth knowing

  • ALB gives you a fixed DNS (Domain Name System) hostname — a web link — rather than a static IP address.
  • Since the load balancer sits between the user and your server, your server never sees the user's real IP directly — it sees the load balancer's private IP instead. To find the real visitor's IP, your app code reads a header called X-Forwarded-For, which the load balancer adds to every request.
  • Two related headers, X-Forwarded-Port and X-Forwarded-Proto, tell your app which port and protocol (HTTP or HTTPS) the visitor originally used.
  • The load balancer does connection termination: client to load balancer travels over the public internet, then load balancer to EC2 travels over your private network.

62-63Application Load Balancer — Hands-On

Reading about load balancing is one thing. Here's what actually happens when you build one, step by step.

Part 1: basic setup

  1. Launch 2 EC2 instances (Amazon Linux 2, t2.micro) with a user-data startup script that serves "Hello World" over HTTP.
  2. Verify each instance returns "Hello World" individually using its public IP address.
  3. Create an ALB (DemoALB) — internet-facing, IPv4, deployed across all Availability Zones.
  4. Create a security group for the ALB (demo-sg-load-balancer) allowing incoming HTTP traffic from anywhere.
  5. Create a target group (demo-tg-alb) — HTTP protocol on port 80 — and register both EC2 instances.
  6. Link the target group to the ALB's listener on port 80.
  7. Once ALB status is active, visit its DNS name in your browser. Refreshing shows responses alternating between both instances — load balancing works cleanly.
Proof health checks actually work: stop one EC2 instance — it becomes "unhealthy" in the target group within roughly 30 seconds — and the ALB only routes traffic to the remaining healthy instance. Start it back up, and once it passes its health check again, it rejoins the traffic rotation automatically.

Part 2: security tightening & routing rules

  • Restrict direct EC2 access: edit the EC2 security group's HTTP rule — remove public internet access and allow traffic only from the ALB's security group ID. Direct access to the EC2 public IP now times out, while access via the ALB's DNS name still works perfectly.
  • Listener rules: add a custom rule on the ALB listener — condition: path is /error; action: return a fixed HTTP response, status 404, body "Not found, custom error"; priority: e.g. 5 (a lower number means AWS checks this rule first). Now visiting <alb-dns>/error immediately returns the custom 404 response, without ever reaching a backend target group.

ALB listener rules can match on host header, HTTP method, source IP, query string, or HTTP header, and can respond by forwarding to a target group, redirecting to a URL, or returning a fixed response directly.

64Network Load Balancer (NLB)

ALB is great at reading HTTP requests, but that reading takes a little time. What if your app needs raw speed — millions of requests a second, with almost no added delay — and doesn't need any of that HTTP-level smartness?

💡 New word NLB (Network Load Balancer) — a load balancer that works at Layer 4, the "transport layer." It handles TCP (Transmission Control Protocol) and UDP (User Datagram Protocol) traffic — the lower-level plumbing underneath HTTP — without inspecting the actual web request. That's what makes it so fast.
Exam trigger words: when a question mentions "UDP," "TCP," "extreme/ultra performance — millions of requests per second," "ultra-low latency (milliseconds)," or "static IP address per AZ" — choose Network Load Balancer.

Key Features

  • Ultra-high performance: handles millions of requests per second with ultra-low latency, measured in milliseconds.
  • Provides one static IP address per Availability Zone — you can also attach an Elastic IP (a fixed public address you own) per AZ for a completely stable public IP.

Target Groups Can Contain:

  • EC2 instances
  • Private IP addresses (pointing to your on-premises servers)
  • An Application Load Balancer — putting an NLB in front of an ALB gives you static IP addresses combined with ALB's smart Layer 7 HTTP routing rules underneath.

Health checks on NLB target groups support 3 protocols: TCP, HTTP, and HTTPS — a bit more flexible than you might expect from a "just plumbing" load balancer.

🏭 In real companies Workloads where every millisecond counts — high-frequency trading systems, multiplayer game servers, or IoT platforms handling huge volumes of small messages — are exactly where teams reach for NLB instead of ALB. The tradeoff is real: you give up ALB's smart HTTP-level routing in exchange for raw speed.

65Network Load Balancer — Hands-On

  1. Create an NLB (DemoNLB) — internet-facing, IPv4, across all AZs. Each AZ gets a fixed static IPv4 address.
  2. Attach a security group (demo-sg-nlb) — allow HTTP (port 80) from anywhere.
  3. Configure the listener: TCP on port 80 → forward to a target group.
  4. Create the target group (demo-tg-nlb) — TCP on port 80, health check protocol = HTTP — and register the same 2 EC2 instances.
A real troubleshooting moment: right after creating this NLB, both target instances showed "unhealthy." The cause: the EC2 security group only allowed traffic from the ALB's security group, left over from the earlier setup — not the NLB's. The fix: add an inbound rule allowing HTTP traffic from the NLB's security group ID too. After that, health checks passed and load balancing worked cleanly.

As always with hands-on AWS practice, delete the NLB and its related resources once you're done, so it doesn't keep quietly charging you.

66Gateway Load Balancer (GWLB)

Some companies want every single packet entering their network inspected by a firewall or intrusion detection system before it ever reaches their app — no exceptions. Running and scaling a fleet of those security appliances by hand is a real headache. That's the gap GWLB fills.

💡 New word GWLB (Gateway Load Balancer) — a load balancer used to deploy, scale, and manage a fleet of third-party network virtual appliances in AWS, such as firewalls, IDPS (Intrusion Detection and Prevention System) tools, and deep packet inspection tools.

GWLB operates at Layer 3 (the network / IP-packet layer) — lower than both ALB (Layer 7) and NLB (Layer 4). It actually does two jobs in one service:

  • Transparent network gateway: it acts as a single entry and exit point for all network traffic entering your VPC (Virtual Private Cloud, your own isolated network space inside AWS).
  • Load balancer: it distributes that network traffic across a target group of virtual security appliances.
GWLB routes all incoming VPC network traffic through security inspection appliances first. Approved traffic continues to your app; harmful traffic is dropped.

Target Groups Can Contain:

  • EC2 instances (registered by instance ID)
  • Private IP addresses
Exam tip: GWLB uses the GENEVE protocol on port 6081. When an exam question mentions the GENEVE protocol or port 6081, choose Gateway Load Balancer.
🏭 In real companies Companies in regulated industries — banking, healthcare, anywhere with strict compliance requirements — often have a rule that no network traffic reaches an application without passing through a firewall or intrusion detection system first. GWLB exists specifically so that rule can scale automatically with traffic, instead of a fixed number of firewall boxes becoming a bottleneck.

67Sticky Sessions (Session Affinity)

Imagine a user adds three items to a shopping cart, and each request happens to land on a different backend server. If cart data lives only in that one server's memory, the user's cart looks empty every time they refresh. That's the exact problem sticky sessions solve.

💡 New word Sticky sessions (also called session affinity) — once a user's first request lands on a specific server, the load balancer remembers that choice using a cookie, and sends every one of that user's later requests back to the exact same server.

Sticky sessions work on all three modern load balancer types — CLB, ALB, and NLB — using a browser cookie with a defined expiration time.

Gotcha: sticky sessions can cause uneven load distribution. If one very active user keeps getting stuck on the same server while everyone else spreads out evenly, that one server ends up doing more work than the rest.

Three Types of Cookies

TypeGenerated ByCookie NameNotes
Application-based cookieYour application codeCustom name (per target group)Cannot use reserved names: AWSALB, AWSALBAPP, AWSALBTG
Application cookie (LB-generated)The ALB itselfAWSALBAPPAutomated application cookie
Duration-based cookieThe load balancerAWSALB (ALB) / AWSELB (CLB)Expiration period controlled by load balancer

Turning it on, step by step

  1. Navigate to Target Group → Actions → Edit attributes → Stickiness.
  2. Enable stickiness, select cookie type (load balancer generated or application-based).
  3. Set expiration duration (range: 1 second to 7 days; default: 1 day).
  4. Save settings → refresh the ALB web link repeatedly → the exact same EC2 instance continues answering, confirmed via your browser's developer tools → Network tab → Cookies.

68Cross-Zone Load Balancing

Here's a real scenario: you have 2 EC2 instances running in one Availability Zone, and 8 running in a second Availability Zone. A user's request lands on whichever AZ their traffic happens to reach first. Does the load balancer only look at servers in that same AZ, or does it consider all 10 instances everywhere?

Uneven setup: AZ1 has 2 instances, AZ2 has 8 instances. Cross-zone balancing determines whether traffic stays within each local AZ or distributes across all 10 instances equally.

The answer comes down to one setting: cross-zone load balancing.

SettingBehavior
Cross-zone ONEach LB node distributes traffic evenly across all registered instances in all AZs (each of the 10 instances gets 10% of total traffic).
Cross-zone OFFEach LB node sends traffic only to instances in its own AZ (instances in AZ1 get 25% each, while instances in AZ2 get only 6.25% each).

Turn it on, and each server gets a fair, even share no matter which AZ it lives in. Turn it off, and servers in the smaller AZ end up doing far more work per server than servers in the bigger AZ — same total traffic, very uneven per-server load.

Default Settings per Load Balancer Type

Load BalancerDefault SettingData Transfer Fees?
ALBAlways ONNo extra charge
NLB / GWLBOFFYes, inter-AZ data transfer fees apply if enabled
CLBOFFNo extra charge if enabled
Good to know: for ALB specifically, you can turn cross-zone balancing on or off at the target group level, rather than for the whole load balancer.

69-70SSL/TLS Certificates

Every time you see a padlock icon next to a website's address, SSL/TLS is the reason your connection to that site is private. Here's how it actually works once a load balancer is sitting in front of your app.

💡 New word SSL (Secure Sockets Layer) / TLS (Transport Layer Security) — the technology that encrypts data while it travels over the internet. TLS is the modern, more secure version; people just kept saying "SSL" out of old habit. AWS actually runs on TLS today, even though the older name still gets used everywhere.

These certificates aren't something you can invent yourself and expect browsers to trust — they're issued by a recognized Certificate Authority (CA), an organization trusted to hand them out, such as DigiCert, Let's Encrypt, or AWS's own option, ACM (AWS Certificate Manager). Certificates also expire and need renewing on a schedule, not set up once and forgotten.

SSL Termination: Client-to-LB traffic is encrypted (HTTPS); LB-to-EC2 traffic can travel as plain HTTP over the secure private VPC network.

This diagram shows something called SSL termination: the connection between the user and the load balancer is encrypted HTTPS, but the connection from the load balancer to your EC2 server can just be plain HTTP — because that hop stays inside your own private, secured VPC network. The load balancer uses an X.509 certificate (the standard technical format for these certificates), managed through ACM, and every HTTPS listener needs a default certificate, plus an optional list of extra certificates for supporting multiple domains.

SNI — Server Name Indication

Problem it solves: what if you need to serve two completely different websites, each with its own SSL certificate, from one single load balancer?

💡 New word SNI (Server Name Indication) — a way for the client to tell the load balancer which domain it's trying to reach right at the start of the secure connection, before any data is exchanged. The load balancer reads that, and automatically picks the matching certificate.
Gotcha: SNI only works on modern load balancers — ALB, NLB, and CloudFront. It does not work on the old Classic Load Balancer, which is one more reason CLB is considered obsolete.
SNI enables a single ALB to serve the correct SSL certificate and route to the correct target group based on the domain requested by the client.

SSL Support Summary

Load BalancerMultiple SSL Certificates Support?
CLBOnly 1 cert (requires multiple CLBs for multiple domains)
ALBYes — supports multiple listeners, certs, and SNI

71Connection Draining

Say a user is halfway through uploading a large file when their EC2 server gets marked unhealthy and pulled out of rotation. Should that upload just get killed mid-transfer? Connection draining says no.

💡 New word Connection draining (called Deregistration Delay on ALB/NLB) — before fully removing a server from service, the load balancer gives its currently in-flight requests time to finish naturally. No new requests go to that server, but the ones already running get to complete.
A draining instance completes existing active requests; new users are routed exclusively to remaining healthy instances.
  • Active connections on draining instances are given time to finish processing.
  • New incoming connections are directed exclusively to healthy instances.
  • The delay is configurable, from 1 to 3,600 seconds (default: 300 seconds / 5 minutes).
  • Set the delay to 0 to disable connection draining completely.

How long you should set it depends entirely on what your app actually does:

Your Traffic PatternRecommended Draining Delay
Short requests (< 1 sec)Low (e.g. 30 seconds) — instances are deregistered quickly.
Long requests (file uploads, active sessions)High — gives active uploads time to complete safely.
🏭 In real companies Connection draining is what makes rolling deploys and auto scaling feel invisible to users. Without it, every deploy or scale-in event would randomly cut off whoever happened to be mid-request on the instance being removed — a steady trickle of failed requests that's hard to notice in aggregate metrics but very real for the users who hit it.

72Auto Scaling Groups (ASG) Overview

A load balancer solves how to spread traffic across servers you already have. It doesn't decide how many servers you should have running right now. That's a completely different job, and it belongs to the Auto Scaling Group.

💡 New word ASG (Auto Scaling Group) — a service that automatically adds EC2 instances when traffic rises (scaling out) and removes them when traffic falls (scaling in), so you're never stuck running too few or too many servers.

Core Capacity Settings

Every ASG is built around three simple numbers:

  • Minimum Capacity: the fewest instances the group is ever allowed to drop to.
  • Desired Capacity: the number of instances it's aiming to run right now.
  • Maximum Capacity: the most instances it's ever allowed to grow to.

Beyond just adjusting the count, an ASG quietly does two more useful things: it automatically registers every new instance it launches with a connected load balancer, and it automatically detects and terminates unhealthy instances, replacing them with fresh ones — without anyone getting paged at 2 AM to do it by hand. And the ASG service itself is completely free — you only pay for the underlying EC2 instances it provisions on your behalf.

ELB + ASG Architecture: ELB distributes web traffic and monitors health; ASG replaces unhealthy servers and adjusts server count up or down.
💡 New word Launch template — the blueprint an ASG uses every time it launches a new instance: which AMI (Amazon Machine Image, a saved snapshot of a server's disk and software) to use, the instance type, a startup script, storage volumes, security groups, an SSH (Secure Shell, the standard way to log into a remote server) key pair, an IAM role, and subnet configuration.
🏭 In real companies Large e-commerce sites are one of the most well-documented real-world uses of auto scaling: capacity gets scaled way out ahead of predictable traffic spikes like Black Friday or Cyber Monday, then scaled back in once the rush passes, so companies aren't stuck paying for peak-day capacity the other 360 days of the year. Netflix's own public engineering blog has described a similar pattern day to day — scaling infrastructure up for the evening viewing peak, then back down overnight when far fewer people are streaming, purely to control cost.

CloudWatch Alarms + ASG

What actually triggers a scaling action? A CloudWatch alarm — for example, "average CPU utilization has gone above 70%" — fires a scaling policy:

  • Scale-out policy: increases instance count when traffic surges.
  • Scale-in policy: decreases instance count when traffic subsides, to save cost.

73Auto Scaling Groups — Hands-On

  1. Clean up existing EC2 instances.
  2. Create a Launch Template (my demo template) — Amazon Linux 2, t2.micro, security group allowing HTTP, and a user-data startup script.
  3. Create the ASG (Demo ASG) using the launch template.
  4. Select a VPC and multiple Availability Zones.
  5. Attach the ASG to the existing ALB Target Group (demo-tg-alb).
  6. Enable both EC2 health checks and ELB health checks.
  7. Set initial capacity: Desired = Min = Max = 1.

Verification & Behavior

Checking the Activity tab shows exactly what happened: "Launching a new EC2 instance," as the ASG scales from 0 up to 1. The new instance shows up in the target group as "unhealthy" at first, while its startup script is still running, then flips to "healthy" once it's ready. Refreshing the ALB's DNS name returns "Hello World," confirming traffic is flowing through the load balancer cleanly.

Exam tip: if ASG instances keep failing health checks and get terminated and relaunched in an endless loop, check two things first: (1) the security group configuration, or (2) a broken user-data startup script.

Manual Scaling Test

A quick manual test makes the whole idea click. Raise Desired to 2 (with Max raised too), and a second instance launches and joins the target group within moments. Set Desired back to 1, and the ASG terminates and deregisters one instance, returning capacity to a single healthy server.

74-75Auto Scaling Groups — Scaling Policies

Knowing an ASG can scale is one thing. Deciding exactly when and how much it scales is a separate decision, and AWS gives you five different ways to make it.

Types of Scaling Policies

Policy TypeHow It Works
Dynamic — Target TrackingSimplest policy. Pick a metric (e.g. average CPU utilization) and a target value (e.g. 40%). ASG automatically scales out/in to maintain that target metric.
Dynamic — Step ScalingTriggers multi-step responses based on CloudWatch alarm thresholds (e.g. CPU > 50% → add 1 instance; CPU > 80% → add 3 instances).
Dynamic — Simple ScalingOne alarm triggers one fixed action (e.g. add 2 instances).
Scheduled ScalingFor predictable traffic patterns (e.g. "raise minimum capacity to 10 every Friday at 5 PM").
Predictive ScalingUses Machine Learning to analyze historical traffic patterns and scale capacity ahead of expected demand surges.

Whichever policy you pick, it needs a real number to react to. The most common choices are CPU utilization (the general-purpose default), RequestCountPerTarget (useful when you know roughly how many requests one server can comfortably handle, say around 1,000), average network in/out (for bandwidth-heavy apps like video uploads or downloads), or a custom CloudWatch metric your own app exports directly from its code.

💡 New word Cooldown — a pause the ASG takes after any scaling action, by default 300 seconds (5 minutes), before it will consider scaling again. It exists so a metric has time to settle down, instead of the ASG overreacting to a brief, temporary spike.
Optimization tip: if instances take a long time to boot and get ready, build a custom AMI with the needed software already installed, instead of installing it fresh via a startup script every time. Faster-booting instances let you safely use a shorter cooldown, so the ASG can react to real traffic changes faster too.

Hands-On: Target Tracking Demo

  1. Create a Target Tracking policy: metric = Average CPU Utilization, target = 40%.
  2. Set ASG max capacity higher than min (e.g. min=1, max=3) to allow room for scaling.
  3. Connect to an instance via EC2 Instance Connect (a browser-based SSH session), install the stress tool, and run stress -c 4 to push CPU utilization to 100%.
  4. AWS automatically creates two CloudWatch Alarms behind the scenes: AlarmHigh (CPU > 40% → scale out) and AlarmLow (CPU < ~28% → scale in).
  5. When AlarmHigh triggers, the ASG Activity log records new instances launching one after another (1 → 2 → 3).
  6. Reboot the stressed instance to restore normal CPU. After roughly 15 minutes, AlarmLow triggers, and the ASG scales capacity back down (3 → 2 → 1).
Cleanup reminder: delete the test scaling policy once you've confirmed it works, so it doesn't keep reacting to real traffic later by accident.

76Auto Scaling Groups — Instance Refresh

Say you've updated your launch template with a new AMI — maybe a security patch, or a new app version baked in. Every instance already running still uses the old template. How do you roll the new one out, without taking your app offline while you do it?

💡 New word Instance Refresh — a feature that updates an entire ASG to a new launch template, gradually replacing old instances with new ones, with zero application downtime.

How It Works

  1. Update your Launch Template to a new version.
  2. Click Start Instance Refresh.
  3. Set a Minimum Healthy Percentage (e.g. 60%) to ensure sufficient active capacity throughout the update.
  4. ASG gradually terminates old instances and provisions new instances running the updated template.
  5. Optionally configure a warm-up time — how long to wait before trusting a brand-new instance enough to serve real traffic.
Given enough time, every single instance running the old launch template gets replaced with one running the new template — and because the minimum healthy percentage always keeps enough capacity online, users never notice it happening.
🏭 In real companies Instance Refresh is one of the standard ways teams achieve zero-downtime rolling deployments on plain EC2 fleets, without needing a separate deployment tool. Combined with connection draining and health checks, it's the same underlying idea used across most cloud platforms: replace servers gradually, never all at once, and always keep enough healthy capacity running.

Key Facts Worth Remembering

  • Security groups: the load balancer allows HTTP(80)/HTTPS(443) from 0.0.0.0/0; EC2 allows traffic only from the load balancer's Security Group ID.
  • Sticky session cookies: AWSALB (duration-based), AWSALBAPP (LB-generated app cookie), or a custom name (your own app cookie).
  • Connection Draining Delay: default 300s (range 1–3,600s; 0 = disabled).
  • ASG Scaling Cooldown: default 300s.
  • GWLB Protocol: GENEVE on port 6081.
  • Cross-Zone Balancing Defaults: ALB = ON (free), NLB/GWLB = OFF (paid cross-AZ data if enabled), CLB = OFF (free if enabled).
  • SNI works on ALB, NLB, and CloudFront — not on the Classic Load Balancer.

The One-Paragraph Version

A load balancer gives your app one address, checks which servers are healthy, and spreads traffic only to the ones that are. ALB reads HTTP requests and routes smartly by path or host; NLB trades that intelligence for raw TCP/UDP speed and static IPs; GWLB routes all your traffic through security appliances first. An Auto Scaling Group decides how many servers should exist at all, scaling out under load and back in when things quiet down, using CloudWatch alarms and scaling policies. Put a load balancer and an Auto Scaling Group together, and you have the standard AWS pattern for a web app that stays online and doesn't waste money running idle servers.
