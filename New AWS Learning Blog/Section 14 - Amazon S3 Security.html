1S3 Encryption Overview

Every day, companies store credit card numbers, medical records, and trade secrets inside S3 buckets. If someone unauthorized gets a copy of that data, the damage is immediate and often permanent. Encryption solves this by scrambling data into unreadable code, so even if someone steals the stored bytes, they have nothing useful.

💡 New word Encryption at Rest means data is scrambled while sitting on physical disks inside AWS data centers. It protects stored files, database records, backups — anything that isn't currently traveling over the network.

Amazon S3 gives you four main ways to encrypt objects at rest. Which one you pick depends on who holds the encryption key and who manages it.

💡 New word Server-Side Encryption (SSE) means S3 itself does the encrypting after receiving your file. You send plain data, S3 encrypts it at rest using either its own keys or yours via KMS.
💡 New word KMS (Key Management Service) is AWS's encryption key vault. It stores your keys, controls who can use them, and logs every single access in CloudTrail for compliance auditing.
Four encryption paths differ by who manages the key and where encryption happens — AWS, you, or your local app.

Encryption in Transit (HTTPS)

💡 New word Encryption in Transit means data is scrambled while traveling over the internet between your client and S3. S3 uses HTTPS (TLS protocol) to protect this path.

S3 provides both unencrypted HTTP and encrypted HTTPS endpoints. For maximum safety, force HTTPS-only by attaching an S3 bucket policy that denies any request where aws:SecureTransport is false. SSE-C absolutely requires HTTPS — AWS refuses unencrypted requests with SSE-C headers.

⚠️ Common Mistake Using SSE-KMS at massive scale can hit throttling limits. Every read and write triggers a call to KMS (to generate or decrypt data keys), which counts toward regional limits of 5,000 to 30,000 requests per second. High-volume applications can exceed this. A mitigation is enabling S3 Bucket Key (available since 2021), which reduces KMS API calls and cuts costs up to 99%.
🏭 In real companies Public S3 bucket misconfigurations have caused dozens of documented data breaches, exposing millions of customer records. Organizations now use encryption (especially KMS) as a baseline control, not just a "nice to have." Compliance standards like HIPAA, PCI-DSS, and SOC 2 require audit trails of who accessed encryption keys — which is exactly what CloudTrail provides when you use KMS.

2S3 Encryption Hands-On

Setting up encryption in S3 takes just a few clicks.

  • When creating a bucket, you choose default encryption: SSE-S3 or SSE-KMS. Every uploaded object automatically inherits that setting.
  • Inspect any object's encryption under Properties → Server-side encryption settings. You'll see which method and which key was used.
  • If you change an object's encryption (say from SSE-S3 to SSE-KMS), and Versioning is enabled, a new version is created. The old version keeps its original encryption.
  • For SSE-KMS, you can either use AWS's managed aws/s3 key, or bring your own Customer Managed Key (CMK) for full control.
  • Enable the S3 Bucket Key setting for SSE-KMS to dramatically cut KMS API calls and reduce costs.
⚠️ Console Limitation SSE-C cannot be configured in the AWS Management Console — it's CLI or SDK only. The same applies to client-side encryption. These are advanced workflows handled entirely in code.

3Default Encryption vs Bucket Policies

S3 has two overlapping concepts that sometimes confuse teams: default encryption settings and bucket policies.

Every bucket automatically applies SSE-S3 to newly uploaded objects unless you configure otherwise. This is the safest default AWS could pick. But if you need to enforce a stricter rule — say, "only allow SSE-KMS uploads, never SSE-S3" — you attach an S3 Bucket Policy that denies any s3:PutObject request lacking the right encryption headers.

💡 New word S3 Bucket Policy is a JSON document (similar to IAM policies) that controls what actions are allowed or denied on a bucket. It's evaluated at the bucket level, not individual objects.
⚠️ Exam Trap Bucket Policies are evaluated BEFORE default encryption settings. If an incoming upload violates a policy's encryption condition, S3 denies it immediately. Default encryption never gets a chance to run.

4S3 CORS — Cross-Origin Resource Sharing

Imagine you host a website on S3 that loads images from a second S3 bucket. You'd expect it to work seamlessly. Instead, the browser throws an error and refuses the cross-bucket request. Why? Browsers have a built-in security rule called CORS that blocks this by default.

💡 New word CORS (Cross-Origin Resource Sharing) is a web security rule that prevents a browser from loading resources from a different domain origin unless the server explicitly permits it with special HTTP headers.

An origin is made of three parts: scheme (like https), domain (like www.example.com), and port (like 443). If any part differs, the browser sees it as a different origin. So https://www.example.com:443 and https://www.other-domain.com:443 are different origins. When your frontend code tries to fetch assets from the second origin, the browser sends an HTTP OPTIONS preflight request first. If the response headers include Access-Control-Allow-Origin matching your domain, the browser allows the real request. Otherwise, it blocks it silently.

Before loading cross-origin resources, the browser checks CORS headers. If denied, the request never happens.

For S3, if your website on Bucket A fetches images from Bucket B, you must configure Bucket B's CORS settings to allow Bucket A's origin. Without it, every fetch fails silently in the browser console as a blocked cross-origin request.

⚠️ Exam Trap Exam questions often show: "Website on Bucket A can't load images from Bucket B. Browser console shows CORS error." The answer is always "Configure CORS on Bucket B to allow Bucket A's origin." This is one of the most tested S3 security concepts.

5CORS Hands-On

Let's walk through the real scenario.

You host a static website on Bucket A. It includes JavaScript code that fetches extra-page.html from the same bucket — this works fine because both are the same origin. You then move extra-page.html to Bucket B. Now the fetch fails, and the browser developer console shows a cross-origin error.

To fix it, navigate to Bucket B's Permissions → CORS and add a CORS configuration. Here's what it looks like:

[
  {
    "AllowedHeaders": ["*"],
    "AllowedMethods": ["GET", "PUT", "POST"],
    "AllowedOrigins": [
      "http://bucket-a.s3-website.us-east-1.amazonaws.com"
    ],
    "ExposeHeaders": []
  }
]

Save it, refresh Bucket A's website, and the fetch now succeeds. Bucket B's response includes Access-Control-Allow-Origin matching Bucket A's URL, so the browser permits the request.

💡 Tip You can use * for AllowedOrigins to allow requests from any domain, but this is rarely the right choice for production. Be specific about which origins you trust.

6MFA Delete — The Nuclear Option

Imagine an attacker gains access to an S3 bucket through a leaked AWS credential. The first thing they do is delete all the files to sabotage your system. Standard S3 permissions can't stop this — they just check if you're allowed to delete, not whether you're having a good day.

💡 New word MFA Delete requires entering a 6-digit code from an authenticator device before performing destructive operations on an S3 bucket. It adds a physical barrier to prevent accidental or malicious deletion.

MFA Delete protects two specific actions: permanently deleting an object version (not just marking it deleted), and suspending versioning on the bucket. Regular object deletion still works normally — it just adds a soft delete marker, letting you restore the file later if needed.

⚠️ Major Constraint Three huge limitations: (1) S3 Versioning must be enabled first. (2) Only the Root Account owner can enable or disable MFA Delete. (3) It can ONLY be configured via AWS CLI, not the console. This is intentional — AWS makes it hard to enable to prevent accidental lockout.

To set it up, first enable MFA on your Root Account and generate temporary root access keys (delete them immediately after setup). Then run this AWS CLI command with a live MFA code from your authenticator:

aws s3api put-bucket-versioning \
  --bucket my-bucket \
  --versioning-configuration Status=Enabled,MFADelete=Enabled \
  --mfa "arn:aws:iam::123456789:mfa/root-device 123456"

Once active, standard object deletion (marking as deleted) works without MFA. But permanently removing a specific version ID requires a valid root MFA code. This turns your bucket into a write-once-read-many (WORM) archive, which is exactly what heavily-audited organizations need for compliance logs and financial records.

🏭 In real companies MFA Delete is rare in development but common in highly-regulated industries. Financial institutions use it to lock down audit logs so even a data breach can't erase the evidence. Some government agencies mandate it for any bucket holding classified data.

7S3 Access Logs

For compliance and security investigation, you need a record of everything that happened to your S3 bucket: who accessed it, what they did, whether they succeeded or got access denied. S3 Server Access Logging records exactly this.

💡 New word S3 Access Logs are detailed records of every request to your bucket — successful reads, writes, failures, across any AWS account. S3 delivers these logs as text files to a target bucket you specify.

Enable logging on your bucket, point it to a target bucket in the same AWS Region, and S3 automatically starts writing log files. There's a delay (typically 1 to 2 hours) before the first logs appear, but eventually you have a complete audit trail. You can then query these logs using Amazon Athena (a SQL service) to answer questions like "Who accessed this object in the last week?" or "Which IPs tried to access non-existent keys?"

⚠️ Critical Warning NEVER set a bucket's logging destination to itself. Writing a log file triggers a new request event, which writes another log file, which triggers another event — an infinite loop that fills your bucket with logs until it runs out of storage and racks up enormous bills. Always use a separate target bucket.

The target logging bucket must live in the same Region as the source bucket you're monitoring. S3 automatically updates the target bucket's policy to grant its logging service write access, so you don't need to manually add permissions.

8Pre-signed URLs

You have a private S3 file that a customer needs to download. You don't want to make the bucket public, and you don't want to hand out your AWS credentials. A pre-signed URL solves this perfectly.

💡 New word Pre-signed URL is a temporary, cryptographically signed link that grants time-limited access to a specific private S3 object. Whoever holds the link inherits the permissions of the user who generated it.

Generate a pre-signed URL using your credentials, set an expiration time (anywhere from seconds to hours), and share the URL with external users. When they click it, S3 verifies the signature and serves the file. After the link expires, it stops working — nobody needs to manually revoke it.

The bucket owner generates a time-limited link carrying their AWS credentials. External users access the file by clicking the link.

The console lets you generate pre-signed URLs up to 12 hours. The CLI and SDKs allow up to 7 days (168 hours). This difference exists because the console uses your current credentials, while CLI/SDK code can use temporary STS credentials.

Common real uses: premium website subscribers downloading private video files, temporary file uploads from partners, or letting mobile apps request time-bound access to user-specific S3 data without storing AWS credentials inside the app.

💡 Tip Pre-signed URLs are perfect for file sharing — they inherit the creator's permissions, so if you don't have write access, the pre-signed URL can't grant it either. This is the principle of least privilege at work.

9S3 Access Points

Large organizations often have one massive S3 bucket shared by multiple teams. Finance needs to access files in finance/, Sales needs sales/, and Analytics needs to read both. Managing this with a single bucket policy becomes a nightmare — the policy gets so complex that changes start breaking things.

💡 New word S3 Access Points create dedicated access gateways into a shared bucket, each with its own DNS name and permissions policy. Instead of one complex bucket policy, you have multiple simple access point policies.

Each access point gets its own unique DNS name (like arn:aws:s3:us-east-1:123456789:accesspoint/finance) and its own attached policy restricted to specific folder prefixes and actions. Finance team accesses data through the Finance access point, Sales through the Sales access point. If you need to change Finance's permissions, you update only that access point's policy without affecting Sales.

One bucket, three access points. Each has its own DNS name and policy, simplifying multi-team permission management.

Access Points can be internet-facing (accessible from anywhere) or restricted to a private VPC. If you want EC2 instances inside a private subnet to reach S3 without traversing the public internet, you combine an access point with an S3 Interface VPC Endpoint. This keeps your traffic inside AWS's private network.

💡 Tip Access Points are especially valuable in enterprises with multiple teams and compliance requirements. They keep your bucket policy clean and make it obvious which team accesses what data.

10S3 Object Lambda

Suppose you have a single S3 bucket holding customer data. Your e-commerce app needs the raw data as-is. Your analytics team needs the same data but with personally identifiable information (PII) like email and phone numbers redacted. Your marketing team wants it enriched with extra computed fields. Without Object Lambda, you'd need three separate copies of the data — wasteful, hard to keep in sync, and prone to errors.

💡 New word S3 Object Lambda automatically transforms S3 objects on the fly during retrieval using AWS Lambda functions. Different apps get different versions of the same underlying file without storing duplicates.

Here's how it works: You create an Object Lambda Access Point that points to your original S3 bucket. When an app requests a file through this access point, Object Lambda triggers a Lambda function you've written. The function fetches the original object, runs your custom code (redacting PII, converting formats, resizing images), and returns the transformed result to the app. The original file in S3 remains unchanged.

Single bucket, multiple transformation endpoints. Lambda handles custom logic without creating file duplicates.

Common uses include redacting PII for analytics and testing, converting file formats (XML to JSON), resizing images based on device type, and adding dynamic watermarks based on the requester's identity. It's powerful for data governance — your single source of truth stays in S3, but different consumers get purpose-built views without manual sync work.

🏭 In real companies Financial firms use Object Lambda to redact account numbers from reports visible to junior analysts. Healthcare companies redact patient names and IDs for training datasets. This keeps compliance teams happy because the audit trail shows exactly who accessed what version of the data.

📋 Cheat Sheet

The Four Encryption Methods

  • SSE-S3: AWS manages keys. Default for all buckets. No extra cost. Use unless you need audit trails.
  • SSE-KMS: You control keys via AWS KMS. CloudTrail logs every access. Watch API throttling at scale (enable S3 Bucket Key to mitigate).
  • SSE-C: You provide keys per-request over HTTPS. AWS never stores them. CLI/SDK only, not in console.
  • Client-Side: Encrypt locally before uploading. Your app handles everything. AWS sees only scrambled bytes.

Key Security Controls

  • Encryption in Transit: Force HTTPS with bucket policies. SSE-C requires HTTPS.
  • Default Encryption: Set to SSE-S3 or SSE-KMS. Applied to new uploads unless overridden.
  • Bucket Policies: Enforce encryption rules at the bucket level. Evaluated before default encryption.
  • CORS: Allow cross-bucket web requests by configuring AllowedOrigins on the target bucket.
  • MFA Delete: Requires Root Account + MFA code to permanently delete object versions. CLI only. Enables WORM archives.
  • Access Logs: Record all bucket requests to a separate target bucket. Query with Athena. Never log to itself.

Advanced Access Patterns

  • Pre-signed URLs: Time-limited links for temporary access. Console max 12 hours, CLI/SDK max 7 days. Inherit creator permissions.
  • Access Points: Separate DNS endpoints for different teams on one bucket. Each has its own policy. Simplifies multi-team management.
  • Object Lambda: Transform objects on-the-fly using Lambda functions. Redact PII, convert formats, enrich data. Single source of truth.
