1Cognito Overview: Authentication vs Authorization

IAM controls who can do what inside your AWS account. But what about the millions of end users of your web or mobile app? You need a different tool entirely — and that's what Cognito does.

💡 New word Cognito is AWS's identity service for users outside your account — it handles sign-ups, logins, and social login federation for web and mobile apps.

Cognito actually solves two separate problems, so it ships with two separate tools. The first handles "who are you" — authentication. The second handles "what can you do in AWS" — authorization. Many production apps use both together.

The two sides of Cognito

ServiceProblem it solvesOutput
User PoolsAuthentication — verify who your app users are, with sign-up, login, MFA, and social login.A JWT token after login.
Identity PoolsAuthorization — let verified users call AWS services directly (S3, DynamoDB) without creating an IAM user per person.Temporary AWS credentials via STS.
🏭 In real companies Real apps almost always use both. A mobile app lets users log in with User Pools, then exchanges that login token for temporary AWS credentials via Identity Pools — so the phone can upload photos to S3 directly without talking to a backend. A web app might use User Pools alone if the backend handles all AWS calls.
Common mix-up on exams: Cognito is for users outside your account (customers, employees, partners). IAM is for people and systems inside your account (engineers, CI/CD pipelines, servers). Don't confuse them.

2Cognito User Pools — Your App's Built-In Login Database

Setting up a user database from scratch means storing passwords safely, verifying emails, handling forgotten passwords, and implementing multi-factor authentication. User Pools gives you all of that, plus social login, without writing a line of authentication code.

💡 New word User Pool — a fully managed serverless user database for your app. It handles sign-up verification, login, password reset, MFA, and federation with social providers or corporate identity systems.

On a successful login, a User Pool returns a JWT — a token your app keeps and sends with every request to prove the user is who they say they are.

💡 New word JWT (JSON Web Token) is a signed, self-contained bundle of user information. The app stores it, and the backend can verify it without asking the User Pool again.
User Pool authenticates, returns a JWT. The app stores the JWT and includes it in future requests to prove authentication.

Two key integrations

API Gateway Authorizer: Your backend API can validate the JWT without running any code — API Gateway checks it automatically before forwarding the request to your Lambda or EC2.

Application Load Balancer: An ALB can authenticate users itself before sending requests to EC2, ECS, or Lambda backends. The backend receives the request already enriched with the user's authenticated information.

Why this matters: Your application code doesn't need to know about authentication at all. The infrastructure handles it, and the app just processes requests from already-verified users.

3User Pools Hands-On

Creating and testing a User Pool takes just a few minutes in the console. Here's the real path:

Creating the pool

  1. AWS Console → Cognito → Create user pool.
  2. Pick your app type (traditional web app, single-page app, native mobile app, or machine-to-machine).
  3. Choose sign-in options: email-based, phone-based, username-based, or a mix.
  4. Set required user attributes (email, phone, name, date of birth) — all users will need to provide these during sign-up.
  5. Configure email delivery — Cognito can send emails itself (limited to 50 per day for testing) or hand off to SES for production volume.
  6. Set a strong password policy.
  7. Optionally enable MFA — either required for all users or optional.

The console after creation

Once your pool exists, you navigate it in the Cognito console. Key sections are:

  • Users — list and manually create users, or check their status (confirmed, unconfirmed, compromised).
  • Groups — organize users; a user can belong to multiple groups.
  • Sign-in experience — customized Managed Login (formerly "Hosted UI") page. Cognito gives you a ready-made login/signup page you can style and link from your app.
  • Federated identity providers — set up Google, Facebook, Amazon, Apple, or SAML/OIDC login.
  • App clients — each client (web app, mobile app, etc.) gets its own app client configuration for the pool.
  • App integration — domain for Managed Login, allowed callback URLs after login.

Testing the flow

Sign up with the Managed Login page → Cognito sends a verification email → user enters the code → user is now confirmed in the system. On next login, they enter credentials → Cognito returns a JWT → the app keeps that JWT and uses it for all future requests.

Email note: Cognito's built-in email service is capped at 50 emails per day and is meant only for testing. Production apps must connect Amazon SES to handle verification emails at scale.

4User Pools — Advanced Features

Lambda triggers

At several points in the authentication flow, User Pools can call a Lambda function you write. This lets you customize behavior without changing Cognito itself.

Trigger pointWhat you can do
Pre sign-upAuto-confirm users, reject sign-ups, add custom attributes.
Pre authenticationCustom logic before a user is allowed to sign in (e.g., check IP, deny certain users).
Post authenticationLog sign-ins, increment counters, send alerts.
Pre token generationAdd custom claims to the JWT or suppress default claims.
Custom messageCustomize the text of verification emails or SMS messages.
Migrate userFor moving users from a legacy system, validate against the old database.

Adaptive authentication

Every login attempt gets a risk score (low, medium, or high) based on the user's device, location, and IP address. Normal logins succeed immediately. High-risk logins can be blocked or required to complete an extra challenge (like SMS code or TOTP). You see all this in CloudWatch Logs.

💡 New word Risk-based authentication — automatically requiring extra proof (MFA) for logins from unusual locations or devices, without bothering users on their normal devices.

Custom domains and Managed Login styling

The default Managed Login page lives on a Cognito-owned domain. You can set a custom domain like login.example.com to make it feel like part of your brand. Cognito handles the HTTPS certificate for you.

Exam trap: Custom domains for Managed Login require an ACM certificate, and that certificate must be in us-east-1 — even if your User Pool lives in a different region. This is a common gotcha.

JWT structure and the sub claim

A JWT has three parts: header, payload (claims), and signature. The payload contains user information like sub (the user's unique ID in the User Pool), email, phone, and custom attributes. Always verify the signature before trusting the claims.

To look up additional user details (beyond what's in the JWT), use the sub UUID to query the User Pool database directly.

💡 New word sub (subject) — a unique UUID in the JWT that identifies the user in the Cognito User Pool. Use it to look up full user records later.

5Putting Cognito on Load Balancers

One of the smartest ways to use User Pools is to let your load balancer handle authentication entirely — your backend code never needs to know about users or tokens.

ALB authentication actions

An Application Load Balancer can authenticate requests before sending them to your target group (EC2, ECS, Lambda). Two options:

ActionUse when
authenticate-cognitoYou want to use a Cognito User Pool directly, including social logins or SAML federation.
authenticate-oidcYou want to use an external OIDC-compliant identity provider without going through Cognito.

Both require the ALB listener to be HTTPS. For unauthenticated users, you can prompt for login, deny the request outright, or allow it (useful if you need the login page itself to be reachable before authentication).

How it works end-to-end

User hits the ALB → no valid session yet → ALB redirects to Cognito Managed Login → user signs in → Cognito redirects back to ALB with an authorization code → ALB exchanges code for ID and access tokens → ALB forwards the original request to your backend, enriched with the authenticated user's claims (name, email, groups) — your backend just processes the request, no auth code needed.

🏭 In real companies This pattern is how enterprises protect internal tools and legacy web apps without touching the application code at all. The ALB becomes the security layer, and the backend stays simple.

6Cognito Identity Pools — Temporary AWS Access for Users

User Pools let your app's users prove who they are. Identity Pools let those authenticated users call AWS services directly — upload to S3, read from DynamoDB, run Lambda functions — without you creating an IAM user for every single person.

💡 New word Identity Pool (also called Federated Identities) — takes a verified identity from any login source and exchanges it for temporary AWS credentials scoped to what that user is allowed to do.

The flow

App user logs in (with User Pool, Google, Facebook, or any OIDC provider) → app gets an ID token → app exchanges that token with the Identity Pool → Identity Pool calls STS to mint temporary AWS credentials → app uses those credentials to call AWS services directly (S3, DynamoDB, Lambda).

Identity Pool bridges any login source to temporary AWS credentials. The app ends up with credentials it can use to call S3, DynamoDB, or any other AWS service directly.

Login sources and IAM roles

An Identity Pool can accept login tokens from almost anywhere: a Cognito User Pool, social providers (Amazon, Facebook, Google, Apple), OIDC providers, SAML providers, or a custom backend you write. It can also allow fully unauthenticated (guest) access with its own IAM role.

For each type of user (authenticated users from the User Pool, unauthenticated guests), you attach an IAM role that defines what AWS actions they can take. These credentials are temporary and expire in hours, not months or years.

💡 New word Temporary credentials — AWS access keys that expire automatically, usually within hours. Far safer than long-lived keys because they can't be abused indefinitely if stolen.

Fine-grained access with policy variables

You can scope an Identity Pool's IAM role to lock down access per user. For example, an S3 policy with a variable like ${aws:username} means each user can only access objects under a prefix matching their own username. In DynamoDB, a policy variable on the partition key ensures each user can only query their own rows.

This is powerful: you don't grant each user a separate role — they all assume the same role, but that role's policies use their identity to limit what they can actually touch. It's row-level security without the overhead.

7Identity Pools Hands-On

Setting up an Identity Pool is different from a User Pool because you're not creating a user database — you're wiring up a login source and defining roles.

The steps

  1. Cognito → Create identity pool (the separate console from User Pools).
  2. Choose a name.
  3. Enable authenticated identities — pick your login source (e.g., a Cognito User Pool, Google, Facebook, SAML).
  4. Optionally enable unauthenticated (guest) access.
  5. Click Create role to auto-generate the authenticated and unauthenticated IAM roles.
  6. Go to IAM → Roles and edit the two roles to attach the actual permissions (S3 bucket access, DynamoDB permissions, etc.).

The critical piece: IAM roles

The Identity Pool itself is just a gatekeeper. The real security lives in the two IAM roles it creates. One role applies to authenticated users; one applies to guests. You attach policies to those roles to define what each group can actually do in AWS.

If you want different authenticated users to have different permissions (e.g., admin users can delete, regular users can only read), set up attribute-based access control: the pool can evaluate user attributes and assign different roles based on them.

Common mistake: Creating an Identity Pool without actually attaching permissions to the roles. The pool exists and returns credentials, but those credentials can't do anything — the app gets a 403 error when trying to use them.

8User Pools vs Identity Pools — Which One?

Both have "Cognito" and "Pool" in the name, so people mix them up constantly. Here's the clearest way to think about them.

User PoolsIdentity Pools
Answers"Who is this person?""What can this person do in AWS?"
OutputA JWT token (proof of identity)Temporary AWS credentials (STS issue)
Backed byInternal user database + optional social/SAML federationAny login source (User Pool, Google, Facebook, SAML, OIDC, custom backend)
Best forAuthentication — sign-ups, logins, password resets, MFAAuthorization — giving users direct access to AWS services
ExpirationJWTs typically valid for 1 hourCredentials expire in hours (configurable)

Real-world scenarios

Scenario 1: A web app with a backend. Users sign in with a User Pool (get a JWT). The backend receives requests with the JWT, validates it, and handles all AWS calls on behalf of the user. Identity Pool: not needed.

Scenario 2: A mobile photo app where phones upload directly to S3. Users sign in with a User Pool. The phone exchanges the User Pool token for Identity Pool credentials. The phone uses those credentials to upload directly to S3 — no backend call needed. Both pools: essential.

Scenario 3: An internal tool for company employees. Use User Pools with SAML federation to your corporate directory (Microsoft Active Directory, Okta, etc.). Employees log in with their work credentials through the SAML provider. If they need to trigger Lambda functions or run AWS CLI commands, add Identity Pools for temporary credentials.

💡 New word SAML (Security Assertion Markup Language) — a standard protocol for federating logins between companies. Let your corporate directory (Microsoft AD, Okta) be the source of truth for employee identity, and have Cognito trust it.
💡 New word OIDC (OpenID Connect) — a modern protocol, simpler than SAML, for using an external identity provider. Common for SaaS tools, social logins, and modern corporate directories.
🏭 The winning pattern Most real companies use this combo: User Pools for app authentication (with SAML federation to corporate identity if employees access it), plus Identity Pools for granting temporary AWS credentials to authorized users. This keeps long-lived keys out of applications entirely.

📋 Cheat Sheet

Core concepts

  • User Pools — serverless user database. Sign-ups, logins, MFA, password reset, social/SAML login, and returns a JWT.
  • Identity Pools — temporary AWS credential issuer. Takes a login token from any source (User Pool, Google, Facebook, SAML, OIDC) and exchanges it for scoped AWS credentials via STS.
  • JWT — the signed token returned by User Pools. The app stores it and includes it in requests to prove who the user is.
  • Managed Login — Cognito's pre-built, customizable login page. No need to build auth UI from scratch.
  • MFA — multi-factor authentication. User Pools supports optional or mandatory MFA for logins.
  • Adaptive authentication — risk-based: high-risk logins (unusual location, new device) can be required to complete extra challenges like SMS or TOTP.
  • Lambda triggers — hook into auth events (pre sign-up, post authentication, pre token generation, etc.) to customize behavior.
  • Temporary credentials — short-lived AWS keys issued by STS via Identity Pools. Much safer than long-lived keys.
  • Policy variables — use ${aws:username} or user attributes in IAM policies to scope access per user (e.g., each user can only see their own S3 prefix or DynamoDB rows).

Decision tree: which service?

  • Need a login database for your app? → Cognito User Pools.
  • Need users to call AWS services directly (S3, DynamoDB)? → Cognito Identity Pools.
  • Need both authentication and direct AWS access? → User Pools for login, then exchange the token with Identity Pools for AWS credentials.
  • Want to let the ALB handle authentication? → Use authenticate-cognito action on the ALB listener. No backend auth code needed.
  • Want API Gateway to validate auth? → Cognito authorizer on the API method. API Gateway validates the JWT before routing to Lambda.
  • Have an existing corporate directory (AD, Okta)? → User Pools with SAML or OIDC federation. Employees log in with their work credentials.
  • Want to allow guest/unauthenticated access? → Identity Pools with a guest IAM role.

Production patterns

  • Always use a custom domain for Managed Login (makes it feel like part of your app). Remember: ACM cert must be in us-east-1 even if the pool is elsewhere.
  • For production email, connect Amazon SES — Cognito's default 50/day limit is test-only.
  • Use Lambda triggers to customize auth flows without touching Cognito settings. Pre authentication can enforce IP allowlists or deny certain users; post authentication can log attempts.
  • Enable adaptive authentication to catch attacks. Risk scores are automatic; high-risk logins prompt for MFA or are blocked entirely.
  • Use policy variables in Identity Pool roles to ensure users can only access their own data. It's the most scalable approach to multi-tenant access control.
  • For internal tools, use SAML/OIDC federation — employees use their work identity, no separate password to manage.
  • Never store long-lived AWS keys in applications. Always use STS credentials from Identity Pools, which expire automatically.

The one-paragraph version

Cognito has two halves that work together beautifully. User Pools is a fully managed sign-up and login system for your app — handle passwords, MFA, password reset, and social login (Google, Facebook) or enterprise federation (SAML, OIDC) without writing auth code. On successful login, the user gets a JWT. If they need to call AWS services directly (upload to S3, write to DynamoDB), exchange that JWT with an Identity Pool, which calls STS to hand out temporary, scoped credentials. Those credentials are automatically revoked in hours, and can be restricted per user using policy variables — no long-lived keys ever touch your applications. Real apps typically chain them: login with User Pools, then use that token to get AWS access from Identity Pools.
