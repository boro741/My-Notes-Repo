1Docker Introduction

Picture this: you write an application that works perfectly on your laptop. You ship the code to your colleague, they try to run it, and it breaks immediately—different operating system, different library versions, missing dependencies. That's the problem Docker solves.

💡 New word Docker is a platform for packaging an entire application—code, dependencies, runtime, libraries—into a self-contained unit called a container. That container runs identically on any machine with Docker installed, regardless of the underlying OS.

Docker containers are lean and fast. Unlike a traditional virtual machine that runs an entire separate operating system (heavier, slower to boot, eats more memory), a container shares the host's OS kernel but stays isolated from everything else. You can run dozens of containers on a single server, and they all behave predictably.

🏭 In real companies Organizations run containerized applications everywhere—building microservice architectures where each small service gets its own container, migrating legacy on-premises applications to the cloud by containerizing them first, or simply deploying and updating code without worrying about environment differences between laptops and production.

Docker vs Virtual Machines

Virtual machines each run their own complete operating system (heavy, slow startup). Docker containers share the host OS but stay isolated (lightweight, faster, more containers per server).

Virtual machines offer maximum isolation but cost in overhead. Docker offers lightweight isolation and rapid deployment—and that trade-off is why containers have become the industry standard for packaging applications.

Where Docker images live

Docker Hub is the public repository where you find base images for popular technologies—Ubuntu, Node.js, MySQL, Python, and countless others. You build your application on top of one of these base images.

Amazon ECR (Elastic Container Registry) is AWS's private repository service, letting you store your own proprietary images. ECR also offers a public gallery if you want to share images with the world.

The Docker workflow in four steps

First, you write a Dockerfile—a text file describing how to build your image, starting from a base image and adding your code and dependencies. Second, you build that Dockerfile into a Docker image—a portable snapshot. Third, you push the image to a repository (Docker Hub, ECR, or wherever). Fourth, when you're ready to run it, you pull the image down and start it as a running container.

💡 New word Docker image is the immutable template—think of it as the blueprint. A Docker container is a running instance of that image—the actual thing consuming CPU and memory.

AWS gives you several choices for orchestrating and running containers at scale:

2Amazon ECS Overview

ECS stands for Elastic Container Service. It's AWS's orchestration platform—the brain that decides where your containers run, how many copies to keep healthy, and how to handle updates and scaling.

💡 New word ECS Task is the unit of work—a running Docker container inside ECS, configured by a task definition. ECS Cluster is the grouping of compute resources (either EC2 instances or Fargate) where tasks run. An ECS Service keeps a desired number of tasks running and replaces them if they fail.

ECS gives you two fundamentally different ways to run tasks: EC2 launch type and Fargate launch type. The choice shapes everything about infrastructure management.

EC2 launch type: you manage the cluster of instances. Fargate: you just say "run this task" and AWS provisions everything behind the scenes.
💡 New word Fargate is AWS's serverless container compute option. You define tasks and launch them without ever thinking about EC2 instances, auto scaling groups, or server management. AWS handles the infrastructure entirely.

EC2 Launch Type vs Fargate

IAM Roles for Container Tasks

Every container running in ECS needs the right permissions to call other AWS services. That's where IAM roles come in. There are two separate roles:

The EC2 Instance Profile is used only on EC2 launch type. It lets the ECS Agent running on the EC2 instance make API calls back to ECS, pull images from ECR, write logs to CloudWatch, and access secrets from Parameter Store.

The ECS Task Role is different. Attached at the task definition level, it lets the application code inside the container call AWS services. For example, Task A might have permission to read from S3, while Task B has permission to write to DynamoDB. This is how you apply the principle of least privilege per task.

🏭 In real companies Without a proper task role, developers would have to hardcode AWS credentials or access keys inside the container image itself—a security nightmare. Instead, the task role is assumed automatically when the container starts, providing temporary, auto-rotating credentials that expire after a few hours.

Load balancer choices

Application Load Balancer (ALB) is the default choice. It understands HTTP and HTTPS, supports dynamic host port mapping for EC2 tasks, and works seamlessly with Fargate. Network Load Balancer (NLB) is faster and handles extreme throughput—use it only if you specifically need those features or need AWS PrivateLink support. The Classic Load Balancer is older, not recommended, and doesn't support Fargate.

Sharing files across tasks: EFS

When you need multiple tasks to share data, mount an Amazon EFS (Elastic File System) volume into your task definition. EFS is a network file system compatible with both EC2 and Fargate launch types. Perfect for scenarios where tasks in different availability zones need to read and write the same files.

The ultimate serverless, stateless combo: Fargate for compute, EFS for shared persistent storage, and ALB for load balancing. You don't manage any infrastructure.

3Creating an ECS Cluster — Hands On

When you create an ECS cluster, you choose an infrastructure type. Fargate-only clusters are the simplest—you just give the cluster a name and you're done, AWS handles everything.

If you're using EC2 launch type, you can let AWS manage the instances for you (AWS-managed instances), or you can create and manage your own EC2 instances and Auto Scaling Group (self-managed instances). For most teams learning ECS, AWS-managed instances are the safer starting point because AWS handles patching and updates.

Behind the scenes, the cluster contains capacity providers. With Fargate, you get FARGATE and FARGATE_SPOT. With EC2 instances, you get an ASG capacity provider that wraps your Auto Scaling Group. When you increase the ASG's desired capacity, new EC2 instances spin up and automatically register themselves with the cluster as container instances, advertising their available CPU and memory.

💡 New word Container instance is what an EC2 instance is called once it has the ECS Agent running and has registered with a cluster. It advertises its capacity (vCPUs, memory) so ECS knows where to place tasks.

The key insight: for EC2 launch type, capacity planning happens at two levels. You need enough tasks to serve your users, and you need enough EC2 instances to fit those tasks. Fargate removes the second concern entirely.

4Creating an ECS Service — Hands On

Before you can run anything in ECS, you need a task definition. Think of it as a blueprint that says: "Here's my Docker image URL, here's how much CPU and memory each task should get, here are the environment variables, and here's the IAM role the container needs."

💡 New word Task definition is a JSON template describing how to run one or more Docker containers. It includes image URLs, port mappings, resource limits, environment variables, logging configuration, and IAM role references.

Once you have a task definition, creating a service is straightforward. You pick the task definition, name the service, choose how many task copies to run initially (e.g., start with 1 or 3), and then configure networking.

For networking on Fargate, you select which VPC subnets the tasks land in, create a security group allowing inbound traffic on your application port, and optionally request a public IP. Then you attach an Application Load Balancer to route traffic to the tasks. The ALB automatically discovers which tasks are running and sends traffic to them.

Once the service is running, scaling up is as simple as updating the service's desired task count. From 1 task to 10 tasks—you just change one number, and Fargate instantly provisions the capacity. The load balancer automatically routes traffic to all healthy tasks, so users don't notice any disruption.

🏭 In real companies This "desired task count" is the variable that auto scaling rules automatically adjust. When CPU usage spikes, a target tracking policy increases the task count. When traffic drops, it decreases. The whole cycle—spin up new tasks, distribute traffic, shut down tasks—happens without human intervention.

To temporarily pause a demo without deleting the service, set the desired task count to 0. The tasks stop immediately and you stop paying for compute. To wind down the cluster entirely, delete the service (which cleans up the load balancer), then delete the cluster.

5ECS Service Auto Scaling

ECS Service Auto Scaling (powered by AWS Application Auto Scaling) automatically adjusts how many tasks are running based on metrics you choose. The three main options are CPU utilization of the service, memory utilization of the service, or ALB request count per target.

You define a target value—for example, "keep CPU at 70%"—and ECS handles the rest. If actual CPU climbs to 80%, it spins up more tasks. If it drops to 50%, it removes some. This is called target tracking scaling and it's the easiest to set up.

⚠️ Common confusion Scaling your ECS service (adding more task copies) is different from scaling the underlying EC2 cluster capacity (adding more EC2 instances). Fargate removes this confusion entirely since there's no EC2 layer. But on EC2 launch type, if you run out of instance capacity, you need a second scaling policy that grows the EC2 fleet itself. Use ECS Cluster Capacity Provider—it's smarter than manually scaling the Auto Scaling Group, because it automatically spins up new instances only when tasks can't fit on existing ones.

You can also use Scheduled Scaling for workloads with predictable patterns. For example, "scale up to 10 tasks every morning at 8 AM, then back down at 6 PM."

6ECS Rolling Updates

When you deploy a new version of your application, ECS doesn't stop all old tasks and start all new ones at once. That would cause downtime. Instead, it does a gradual rollover controlled by two settings: minimum healthy percent and maximum percent.

Say you have 4 running tasks and you want to update them all to a new version. Minimum healthy percent controls the lowest number of tasks that must stay running during the update. If you set it to 100%, at least 4 tasks must always be healthy. Maximum percent controls the temporary peak—if you set it to 150%, ECS allows up to 6 tasks running during the transition (4 old, 2 new, for example).

With minimum 50% and maximum 100%, you dip below full capacity temporarily. With minimum 100% and maximum 150%, you overprovision temporarily but never lose capacity.

With minimum healthy percent set to 50% and maximum to 100%, ECS terminates old tasks first (down to 2), then creates new tasks back up to 4. Capacity temporarily dips, which saves money but exposes you to slightly reduced redundancy. With minimum 100% and maximum 150%, ECS creates new tasks first (up to 6), then terminates old ones. Capacity never dips, ensuring zero downtime, but you temporarily pay for more tasks.

Choose based on what matters most: money-saving, zero-downtime updates, or a balance between the two.

7ECS Solution Architectures

S3 event → ECS task → DynamoDB

A user uploads a file to S3. S3 publishes an event to EventBridge. A rule in EventBridge matches the event and triggers an ECS task (or Fargate task). The task container, running with an appropriate IAM task role, processes the file and writes results to DynamoDB. Entire pipeline is serverless and event-driven.

Scheduled batch processing

EventBridge can run on a schedule—every hour, every day, whatever you set. Use it to trigger a Fargate task that processes batch data. The task pulls data from S3, processes it, and stores results back to DynamoDB or a data warehouse. No servers to manage, you pay only when the task runs.

ECS + SQS with auto scaling

Your ECS service polls an SQS queue for work. Enable auto scaling on the service so the task count grows as the queue fills up. When messages pile up during a traffic spike, the service automatically scales to process them faster. When the queue empties, tasks scale back down.

Monitoring task lifecycle events

EventBridge watches your ECS cluster and can capture events when tasks change state—starting, stopping, failing. Route those events to an SNS topic to alert your team. This is how you build monitoring and alerting around your containers without polling.

8ECS Task Definitions — Deep Dive

A task definition is JSON (though the AWS console provides a UI to build it without editing JSON directly). It describes everything ECS needs to know to launch a container: which Docker image, how much CPU and memory, which ports, environment variables, IAM role, and logging setup.

One task definition can describe up to 10 containers. This is useful when you need a main application container plus sidecars—a logging agent, a monitoring agent, or a proxy—all running together and sharing network namespace and storage.

Port mapping: container vs host

The port your application listens on inside the container is the container port. On EC2 launch type, that maps to a random port on the EC2 instance's network interface—the host port. The load balancer knows how to follow these dynamic mappings because it queries ECS constantly for the current state.

On Fargate, this complexity vanishes. Each task gets its own network interface (ENI) with its own private IP. There's no shared host to map ports through. The task listens on port 80 (or whatever), the load balancer routes traffic to that IP and port, and everything just works.

EC2 tasks share the EC2 instance's IP and get random host ports. Fargate tasks each have their own private IP, so port numbers don't conflict.
⚠️ Security group gotcha On EC2 launch type with an Application Load Balancer, the EC2 instance's security group must allow traffic from the ALB's security group on any port (since the host port is random). On Fargate, the task's ENI security group just needs to allow the actual container port (e.g., 80) from the ALB's security group. This detail matters for troubleshooting connectivity issues.

IAM roles for containers

Task definitions reference an IAM task role. Every container launched from that task definition assumes that role, automatically. Different task definitions can have different roles, letting you apply fine-grained permissions—one task reads S3, another writes to DynamoDB—without embedding any credentials in the image.

Environment variables and secrets

You can hardcode non-secret environment variables directly in the task definition. For sensitive values—API keys, database passwords—pull them from AWS Secrets Manager or Systems Manager Parameter Store. ECS resolves them and injects them at task startup time. This keeps secrets out of your images and logs.

You can also bulk-load environment variables from an S3 object if you have many to configure at once.

Sharing data between containers

A single task can run multiple containers. To let them share files, define a bind mount in the task definition. On EC2 launch type, the bind mount points to the EC2 instance's storage—tied to that instance's lifecycle. On Fargate, it uses ephemeral storage (20 GB to 200 GB depending on task size)—tied to the task's lifecycle and disappears when the task stops.

This is how you run a logging sidecar in the same task as your main app. Both containers write to a shared /var/logs directory. The logging sidecar picks up the main app's logs and ships them to CloudWatch.

10ECS Task Placement

⚠️ Fargate doesn't have placement Task placement strategies and constraints only apply to EC2 launch type. Fargate hides the infrastructure entirely, so there's no instance to place a task onto—AWS decides for you.

On EC2 launch type, ECS has to decide which container instance gets each new task. It does this in three steps: identify instances with enough CPU and memory for the task, filter by any placement constraints you defined, then pick the instance that best matches the placement strategy.

Placement strategies

binpack fills one instance before moving to the next. It packs tasks tightly to minimize the number of EC2 instances in use, which saves money.

random just picks an instance randomly with no optimization. It's simple but wasteful.

spread distributes tasks evenly across a chosen dimension—availability zones, instance IDs, or other attributes. Use it to maximize availability so one AZ failure doesn't knock out all your tasks.

Strategies can be combined. For example: "spread tasks across availability zones, then within each AZ, binpack by memory." This gives you both high availability and cost efficiency.

Placement constraints

distinctInstance ensures each task lands on a different container instance. Never two tasks on the same instance. Useful for load distribution.

memberOf only places tasks on instances matching a specific expression—for example, only t2 instance types, or only instances in a specific availability zone. It's a filter before the strategy kicks in.

binpack saves money by packing tasks tightly. spread prioritizes availability by distributing across zones. random is simple but inefficient.

11ECS Clean Up — Hands On

To shut down an ECS setup, follow this order: First, set the service's desired task count to 0, then delete the service itself. Confirm the deletion. Behind the scenes, CloudFormation removes the load balancer, target groups, security groups, and listeners.

Once the service is gone, delete the cluster. Again, CloudFormation cleans up: the capacity provider, the Auto Scaling Group (if you were on EC2 launch type), and the cluster itself.

Task definitions are free to leave around—they're just definitions, not running resources. But if you want to clean house, you can deregister them manually through the console.

12Amazon ECR

Now you know how to run containers in ECS. But where do the Docker images come from? That's what ECR does.

💡 New word Amazon ECR (Elastic Container Registry) is AWS's managed Docker image repository. You can push your images here and pull them into ECS tasks. ECR is private by default (only your account sees your images), but you can publish images to the public ECR gallery too.

Under the hood, ECR stores images in S3. You don't see the S3 bucket—ECR abstracts it away. Access to ECR is controlled by IAM. If an EC2 instance or Lambda function needs to pull an image from your ECR repository, it needs an IAM policy granting ECR permissions.

ECR also offers optional image vulnerability scanning (scanning images for known security issues before you deploy them), image versioning, and lifecycle policies to clean up old images automatically.

Public vs private repositories

Private repositories are the default. Only people (or services with the right IAM permissions) can see or pull your images. Use this for proprietary application code.

Public repositories are published to the ECR Public Gallery. Anyone on the internet can pull your image. This is useful if you want to share open-source tools or base images.

🏭 In real companies Most organizations keep application images private in ECR. Open-source libraries and base images often live in Docker Hub or the ECR Public Gallery. When an ECS task starts, it pulls from ECR using the EC2 instance's IAM role (EC2 launch type) or the task's IAM role (Fargate), so credentials never need to be embedded anywhere.
Task definition references an image URL in ECR. ECS pulls it using the instance's IAM role. The image becomes a running container.

13Amazon ECR — Hands On

To push an image to ECR, first authenticate the Docker CLI to your ECR repository. Use this command:

aws ecr get-login-password | docker login --username AWS --password-stdin [your-account-id].dkr.ecr.[region].amazonaws.com

This works because your local AWS credentials (configured via aws configure) prove you're authorized. Docker stores the login token temporarily.

Next, create a private repository in ECR (just give it a name). Pull an existing Docker image—either from Docker Hub or from your local machine if you've built one:

docker pull ubuntu:latest

Now retag it to match your ECR repository. The tag format is important—it must include your ECR repository's full URI:

docker tag ubuntu:latest [your-account-id].dkr.ecr.[region].amazonaws.com/my-repo:latest

Push it to ECR:

docker push [your-account-id].dkr.ecr.[region].amazonaws.com/my-repo:latest

Docker recognizes the ECR URI in the tag name and pushes it to your repository. Now when you create an ECS task definition, you can reference this image URL.

⚠️ Common error Push or pull fails with an "access denied" message. This is almost always an IAM permissions issue. Check that your user or role has the right ECR permissions (ecr:GetDownloadUrlForLayer, ecr:BatchGetImage, ecr:PutImage, etc.). Fix the IAM policy, re-authenticate with docker login, and try again.

14Amazon EKS

ECS is AWS-specific. But what if your organization already uses Kubernetes on-premises or in multiple clouds? What if you want container orchestration that isn't locked into one vendor?

💡 New word Amazon EKS (Elastic Kubernetes Service) is AWS's managed way to run Kubernetes, an open-source container orchestration system. It's cloud-agnostic—Kubernetes also runs on Azure, Google Cloud, and on-premises—so you're not vendor-locked.

EKS follows the same Fargate serverless model as ECS. You can run worker nodes on EC2 (self-managed or AWS-managed), or go completely serverless with Fargate. The API is different (Kubernetes YAML manifests instead of ECS task definitions), but the end result is the same: containers running securely at scale.

In Kubernetes terminology, a "pod" is roughly equivalent to an ECS task. A pod can hold one or more containers. You define pods in YAML manifests instead of JSON task definitions. The Kubernetes control plane (which AWS manages for you in EKS) decides where to schedule pods, how many replicas to keep, and when to scale.

For node types on EKS, you can use AWS-managed node groups (AWS creates and manages the EC2 nodes as part of an Auto Scaling Group), self-managed nodes (you bring your own EC2 instances or use the EKS-optimized AMI), or Fargate for serverless pods.

Storage on EKS

Kubernetes uses StorageClass manifests to attach volumes. EKS supports Amazon EBS, Amazon EFS (the only option that works with Fargate), Amazon FSx for Lustre, and Amazon FSx for NetApp ONTAP—all via Container Storage Interface (CSI) drivers.

🏭 Why choose EKS over ECS? Use EKS if your team is already familiar with Kubernetes, if you run containers in multiple clouds, or if you need the advanced orchestration features Kubernetes provides. Otherwise, ECS is simpler and tighter integration with other AWS services usually makes it the better choice.

📋 Cheat Sheet

Core Concepts

  • Docker packages applications into portable containers that run identically anywhere.
  • ECS Task is a running Docker container inside ECS. ECS Cluster groups compute resources (EC2 or Fargate) where tasks run.
  • ECS Service keeps a desired number of tasks running and replaces failed ones.
  • Fargate is serverless compute—you define tasks, AWS runs them without you managing servers.
  • Task definition is a JSON blueprint describing how to run one or more containers: image URL, CPU, memory, IAM role, ports, environment variables.
  • ECR (Elastic Container Registry) stores your Docker images privately. Backed by S3, access controlled by IAM.
  • EKS is managed Kubernetes—use if you already know Kubernetes or need multi-cloud portability.

Key Architecture Patterns

  • EventBridge → ECS task: User uploads to S3, event triggers a Fargate task to process and write to DynamoDB. Fully serverless.
  • ECS + SQS + auto scaling: Service polls SQS queue. Task count scales with queue depth. Handles traffic spikes automatically.
  • Load-balanced service: ECS service with multiple tasks. ALB distributes traffic. Tasks scale based on CPU/memory/request metrics.
  • Scheduled batch job: EventBridge schedule triggers a Fargate task hourly. Task processes data and exits. Pay only when running.

IAM Roles: EC2 vs Task

  • EC2 Instance Profile: Used only on EC2 launch type. Lets the ECS Agent make API calls to ECS, pull images from ECR, write logs to CloudWatch.
  • ECS Task Role: Used by application code inside the container. Defined at task definition level. Lets Task A read S3, Task B write to DynamoDB. Fine-grained per-task permissions.

Rolling Updates

  • Minimum healthy percent: Lowest number of tasks that must stay running during update (100% = never dip below capacity).
  • Maximum percent: Temporary peak during update (150% = temporarily run 50% more tasks than desired).
  • Min 100% / Max 150%: Zero downtime, higher cost. Creates new tasks before terminating old ones.
  • Min 50% / Max 100%: Saves money, brief capacity dip. Terminates old before launching new.

Auto Scaling Triggers

  • Service CPU utilization (whole service, not per-task).
  • Service memory utilization.
  • ALB request count per target.
  • Scheduled scaling for predictable patterns.
  • Note: On EC2 launch type, also scale the instance fleet using ECS Cluster Capacity Provider (not plain ASG scaling).

Port Mapping Rules

  • EC2 + ALB: Dynamic host port mapping. EC2 security group must allow ANY port from ALB security group.
  • Fargate: Each task gets its own ENI. No mapping needed. ENI security group allows container port (e.g., 80) from ALB security group.

Task Placement (EC2 only)

  • binpack: Fill one instance before moving to next. Minimizes instance count (cost optimization).
  • spread: Distribute across AZ or instance ID. Maximizes availability. One instance failure doesn't take down all tasks.
  • random: No logic. Simple but wasteful.
  • distinctInstance: Each task on different instance. No two tasks on same instance.
  • memberOf: Filter to specific instances (e.g., only t2 types, or specific AZ).

When to Use What

  • Simplest container hosting: ECS + Fargate.
  • Full control over instances: ECS + EC2 launch type.
  • Already using Kubernetes: EKS.
  • Store private Docker images: ECR.
  • Share files between sidecars: Bind mount in task definition.
  • Persistent shared storage across AZs: EFS.
  • Zero-downtime deployments: Min 100% / Max 150% rolling update.
  • Cost optimization with EC2: binpack placement strategy + Cluster Capacity Provider.
