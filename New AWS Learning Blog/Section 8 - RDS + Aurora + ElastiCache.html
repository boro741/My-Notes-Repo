1Amazon RDS Overview

Say you build an app and it needs a real database. You could install MySQL yourself on a server. But then you own everything that comes with it: patching the operating system, watching disk space, taking backups, and waking up at 3am when the disk fills up. None of that has anything to do with your actual product.

RDS exists to take that work off your plate. RDS stands for Relational Database Service. It's AWS's managed version of the classic SQL databases you already know.

💡 New word Managed service means AWS runs the boring, repetitive parts of a system for you — patching, backups, monitoring, hardware failures — so you only have to deal with your own data and application.

RDS supports the database engines most teams already use. The AWS exam wants you to know this list cold:

  • PostgreSQL
  • MySQL
  • MariaDB
  • Oracle
  • Microsoft SQL Server
  • IBM DB2
  • Aurora — AWS's own database engine, covered in detail later on this page.

Once you pick an engine, RDS quietly hands you a long list of things you never have to build yourself:

  • Automated setup and OS security patching.
  • Continuous automated backups, with Point-in-Time Restore — you can roll your data back to an exact second in the past.
  • Built-in CloudWatch monitoring dashboards.
  • Read Replicas, to handle heavier read traffic (more on this next).
  • Multi-AZ deployment, for staying online through a failure (also covered next).
  • Scheduled maintenance windows for software upgrades.
  • Both vertical scaling (a bigger server) and horizontal scaling (more read replicas).
  • Storage backed by AWS EBS volumes.
Gotcha: you can never SSH into an RDS server. AWS owns the underlying operating system completely — that's exactly what "managed" means here.

Storage Auto Scaling — what happens when you run out of room

Imagine your app suddenly gets popular and starts writing far more data than you expected. Should you have to notice that yourself, at 2am, before your database fills up and starts rejecting writes?

No — RDS watches this for you. When you first create a database, you pick a starting storage size, say 20 GB. RDS then expands that storage automatically, with zero downtime, once all three of these are true at the same time:

  • Free storage space drops below 10% of the total allocated storage.
  • That low-storage state has lasted more than 5 minutes.
  • At least 6 hours have passed since the last time storage was expanded.

You can also set a Maximum Storage Threshold, which caps how far this can grow. The feature works the same way across every RDS engine.

🏭 In real companies Teams set that Maximum Storage Threshold on purpose, not as an afterthought. Storage that silently keeps growing overnight, with no ceiling, is exactly the kind of thing that turns into an ugly surprise on next month's AWS bill.

2RDS Read Replicas vs Multi-AZ

These two RDS features get mixed up constantly, on the exam and in real conversations. They sound similar, but they solve two completely different problems: one is about speed, the other is about survival.

Core rule to memorize: Read Replicas scale read performance. Multi-AZ gives you high availability and disaster recovery. Never swap these two on the exam.

Read Replicas — for when reads are the bottleneck

💡 New word A Read Replica is a copy of your database that only answers read queries (SELECT). It never accepts writes.

Picture a normal production app: customers hit the main database constantly, and separately, an analytics team wants to run heavy reporting queries against that same data. If both go to the same database, the reporting queries slow everything down for real customers.

Read Replicas fix that. You can create up to 15 of them from one main database, and they can live in the same Availability Zone, a different Availability Zone in the same Region, or even a completely different Region.

💡 New word An Availability Zone (AZ) is one physically separate data center inside an AWS Region. A Region usually contains several of them, so one AZ having a bad day doesn't have to take everything down.

Data flows from the main database to each replica asynchronously — meaning the replica doesn't wait for confirmation before moving on. That has one side effect worth knowing: a replica can lag slightly behind the main database, so it's described as eventually consistent. Read a replica one second after a write to the main database, and you might briefly see the old value.

A replica can also be promoted into a standalone database of its own — but that permanently breaks its link back to the original.

The main database handles reads and writes, then replicates asynchronously to two read-only replicas.
Gotcha: Read Replicas only accept SELECT queries. Trying to run INSERT, UPDATE, or DELETE against one will fail.
🏭 In real companies Sending reporting and analytics queries to a Read Replica, instead of the primary database, is one of the most standard patterns in the industry for scaling read-heavy workloads. It keeps slow, expensive analytics queries from ever competing with the customers actually using the live product.

One more detail worth knowing: replicating to a different AZ within the same Region is free — AWS doesn't charge for that data transfer. Replicating across Regions does incur AWS's normal inter-region network charges.

Multi-AZ — for when the whole database needs to survive a failure

💡 New word Multi-AZ means AWS keeps a standby copy of your database running in a different Availability Zone, ready to take over instantly if the main one fails.

With Multi-AZ turned on, AWS runs a Primary database in one AZ and a Standby in another. This time, replication is synchronous — a write isn't confirmed as successful until both the Primary and the Standby have safely stored it. That's slower than async replication, but it means the Standby is never behind.

💡 New word Failover is the automatic switch from a failed system to a healthy backup, with no human stepping in to flip the switch.

Your application only ever talks to one DNS address. If the Primary fails — a dead instance, a storage problem, an entire data center outage — RDS fails over to the Standby automatically. Your application code doesn't have to change at all.

Multi-AZ: one DNS address, synchronous replication, with the standby activated only on failover.
Gotcha: you cannot read from, or write to, the Standby directly. It exists purely as a failover target, not as extra read capacity.
🏭 In real companies Multi-AZ failover is the standard mechanism companies lean on so that one data center having a bad night doesn't turn into a full production outage. It's treated as a baseline requirement for any database real customers depend on, not an optional extra.
Best practice: these two features aren't a choice between one or the other. A common real setup uses Read Replicas for scaling, with Multi-AZ turned on too — so you get both speed and resilience at once. This combination shows up on the exam constantly.

Switching an existing database from Single-AZ to Multi-AZ is a zero-downtime change. RDS takes a snapshot of your Primary, restores it into a second AZ, and wires up synchronous replication — all without taking your database offline.

3Amazon RDS — Hands-On

Here's what actually clicking through and launching an RDS database in the console looks like, step by step:

  • Engine choice: MySQL, for simplicity (PostgreSQL, MariaDB, Oracle, and SQL Server are also on offer).
  • Deployment template: Free Tier uses Single-AZ. The Production template unlocks Multi-AZ, as either a 2-node Instance or a 3-node Cluster.
  • Credentials: either a self-managed master password, or hand it off to AWS Secrets Manager to store and rotate.
  • Instance class: db.t4g.micro or db.t3.micro — both Free Tier eligible.
  • Storage: 20 GB to start, with Storage Auto Scaling enabled up to a 1,000 GB ceiling.
  • Connectivity: public accessibility turned on for testing, with a Security Group opened on port 3306 (MySQL's default port).

After that, connecting is straightforward: point a SQL client at the database's Endpoint URL, port 3306, username admin, and the master password. From there, ordinary SQL — CREATE TABLE, INSERT, SELECT — works exactly like any other MySQL database.

Once it's running, the console lets you:

  • Create Read Replicas directly, in Single-AZ or Multi-AZ.
  • Watch CPU, memory, and active connection counts through CloudWatch.
  • Take manual snapshots, restore to a point in time, or copy a snapshot into another Region.
Deleting an RDS instance safely: Modify the instance → turn off Deletion Protection → Apply Immediately → then choose Delete. You can skip creating a final snapshot if you're sure you don't need one.

4Amazon Aurora

What if you could keep every driver, every tool, and every line of code you already wrote for MySQL or PostgreSQL — but run it on a database engine built from scratch by AWS to be faster, and to repair itself?

That's Aurora. It's AWS's own cloud-native relational database, built to be fully compatible with both MySQL and PostgreSQL. Your existing drivers and application code just work, unchanged.

AWS reports these performance numbers for Aurora, compared to running the same engine on plain RDS:

  • 5x the throughput of standard MySQL on RDS.
  • 3x the throughput of standard PostgreSQL on RDS.
  • Roughly 20% pricier than standard RDS — but AWS says it becomes more cost-efficient as you scale up.

Storage that grows and heals itself

Aurora's storage expands automatically in 10 GB steps, all the way up to 256 TB. You never manually resize a disk.

Every write gets copied into 6 copies spread across 3 different Availability Zones, automatically. Aurora then uses a quorum rule to decide when an operation counts as done:

  • 4 out of 6 copies must confirm a write.
  • 3 out of 6 copies are enough to serve a read.

Because of that spread, Aurora can lose an entire Availability Zone and keep running. It also repairs itself in the background: if a disk block gets damaged, Aurora's storage layer fixes it using peer-to-peer replication, without anyone noticing.

Aurora supports up to 15 Read Replicas, each staying within roughly 10 milliseconds of the primary. If the primary fails, Aurora promotes one of them automatically — usually in under 30 seconds.

Writer and Reader endpoints

An Aurora cluster has one Master Writer at any given time, handling all writes. If it fails, Aurora promotes a replica to take its place — but your application shouldn't have to track which instance is currently in charge.

That's what the two built-in endpoints solve. The Writer Endpoint is a fixed DNS name that always points at whichever instance is currently the master. The Reader Endpoint is a second fixed DNS name that spreads read connections across all the active replicas. Point your app's write traffic at one, and its read traffic at the other, and failovers happen invisibly underneath.

The Writer Endpoint tracks the active Master; the Reader Endpoint load-balances across replicas. All instances share one self-scaling storage layer.

A few more Aurora features worth knowing: automated failover, continuous backups, zero-downtime engine patching, custom endpoints, and Backtrack — the ability to instantly rewind a database's data to an earlier point in time, without restoring anything from a backup.

🏭 In real companies Teams running MySQL or PostgreSQL on plain RDS commonly migrate to Aurora once traffic grows enough that raw throughput and self-healing storage start to matter more than the roughly 20% price difference. It's positioned squarely as the "want more performance from the same SQL you already know" option.

5Amazon Aurora — Hands-On

Setting up an Aurora cluster involves a few choices that don't exist on plain RDS:

  • Engine: MySQL-compatible or PostgreSQL-compatible.
  • Storage class: Aurora Standard for typical workloads, or I/O-Optimized if your workload is heavy on both reads and writes.
  • Serverless v2: automatically scales database capacity units (ACUs) up and down as traffic spikes and settles.
  • Availability: add Aurora Replicas across different AZs for instant failover and extra read capacity.
  • Local Write Forwarding: if a write accidentally lands on a reader instance, it gets forwarded to the writer automatically instead of failing.
  • Authentication: a standard password, IAM database authentication, or Kerberos.

Once deployed, you get a cluster with separate writer and reader connection strings, ready to drop into your application.

Some other cluster-level features worth knowing: auto-scaling policies for read replicas (for example, targeting 60% CPU and scaling from 1 up to 15 replicas), Cross-Region Read Replicas and Aurora Global Database for low-latency reads and disaster recovery across Regions, and the same Point-in-Time Restore and snapshot exports you'd expect from RDS.

Deleting an Aurora cluster, in order: delete every reader instance first, then delete the master writer instance, and only then delete the cluster container itself.

6RDS & Aurora Security

A database usually holds the most sensitive data in the whole system — customer records, payment details, everything. RDS and Aurora give you several independent layers to lock that down.

Gotcha worth knowing early: encryption at rest has to be turned on when you first launch the database. You can't just flip it on later — and if your main database is unencrypted, none of its Read Replicas can be encrypted either.

If you launched a database unencrypted and need to fix that, the workaround is: take a snapshot of the unencrypted database, copy that snapshot while enabling KMS encryption, then restore the encrypted copy as a brand-new database.

💡 New word KMS (Key Management Service) is the AWS service that creates and controls the encryption keys used to lock up your data, both here and across most other AWS services.

Here's the fuller picture of what RDS and Aurora protect, and how:

Security DomainHow it works
Encryption at restUses AWS KMS keys. Must be enabled at initial launch. An unencrypted master can never have encrypted replicas.
Encrypting an existing unencrypted DBSnapshot the unencrypted DB → copy the snapshot with KMS encryption on → restore that copy as a new, encrypted database.
Encryption in flightTLS/SSL is on by default. Clients verify the server's identity using AWS-provided root certificates.
AuthenticationA normal username and password, or IAM Database Authentication — e.g. letting an EC2 instance's IAM role log in with no hardcoded password at all.
Network protectionVPC Security Groups restrict access by IP address, port (3306, 5432, and so on), or by Security Group ID.
SSH accessBlocked, since it's a managed service — unless you're using RDS Custom, which trades some management away for OS-level control.
Audit loggingDatabase logs can be exported straight to AWS CloudWatch Logs, for long-term retention and audits.

7RDS Proxy

Say your app runs on AWS Lambda, and it suddenly gets a spike of 500 requests at once. Lambda scales to handle that instantly — but every one of those 500 executions wants to open its own database connection. Your database has a hard limit on how many connections it can hold. What happens next isn't pretty: timeouts, dropped connections, and a database pinned at 100% CPU just from managing all those open connections.

💡 New word Connection pooling means keeping a small, stable set of database connections open and reusing them, instead of opening a brand-new connection for every single request.

RDS Proxy sits between your application and your RDS or Aurora database, doing exactly that. Every client connects to the Proxy instead of the database directly. The Proxy holds a much smaller pool of real connections open to the database, and shares them out efficiently.

🏭 Why this exists — a real, documented scenario This exact Lambda-plus-database problem is the textbook reason AWS built RDS Proxy. Serverless functions can scale up far faster than a traditional server fleet ever would, and without something in front of the database managing connections, that burst of scaling can exhaust the database's connection limit and take down everyone else using it too.

Beyond just pooling, RDS Proxy brings a few other things:

  • Keeps the database's CPU and memory from getting eaten alive by connection churn and timeouts.
  • Fully serverless, auto-scaling, and spread across multiple Availability Zones on its own.
  • Cuts failover switch time by up to 66%, because the Proxy manages the failover itself without dropping client sessions.
  • Works with MySQL, PostgreSQL, MariaDB, SQL Server, and Aurora.
  • Needs zero code changes — you just repoint your connection string at the Proxy's endpoint instead of the database's.
  • Can enforce IAM Authentication, using credentials stored in AWS Secrets Manager.
  • Is never reachable from the public internet — only from inside your VPC.
Lambda functions scale rapidly and open hundreds of connections; RDS Proxy consolidates them into a small pool the database can handle.
Classic exam scenario: "Lambda functions are overwhelming the database with connections." The answer is almost always RDS Proxy.

8ElastiCache Overview

Even a perfectly tuned database has one hard limit: reading data off disk takes real time. Now imagine the exact same question — "what are today's top 10 products?" — gets asked thousands of times a second. Answering that from disk, every single time, is wasteful.

💡 New word ElastiCache is AWS's managed in-memory data store. Instead of reading from disk, it keeps data in RAM, which makes reads come back in well under a millisecond.

ElastiCache runs one of two engines:

💡 New word Redis is an in-memory data store with built-in replication, backups, and support for more than just plain key-value pairs (lists, sets, sorted sets, and more).
💡 New word Memcached is a simpler in-memory key-value store. It has no built-in replication or persistence — if a node restarts, whatever it held is just gone.

ElastiCache is managed the same way RDS is: AWS handles the hardware, security patching, monitoring, failure recovery, and backups.

Important: ElastiCache isn't a switch you flip on a database. Using it means changing your application's code — your code has to explicitly ask the cache first, and only fall back to the database on a miss.

The caching pattern in plain terms

Your application asks ElastiCache for something first. If the data is there — a cache hit — it comes back instantly, and the database never even hears about the request. If it's not there — a cache miss — your code reads it from the real database, then saves a copy into ElastiCache so the next request gets a cache hit instead.

Since the same data now lives in two places, you need a plan for keeping the cached copy from going stale once the real data changes. That plan is a cache invalidation strategy, and it's the whole subject of the next section.

Using it for session storage

Caching database reads isn't the only job ElastiCache does. Say a user logs in, and their next request happens to land on a completely different web server. If that server has no memory of the login, the user gets logged out for no reason.

Store the session token in ElastiCache instead, and any server can pick it up instantly. That's what lets a whole fleet of web servers stay stateless — none of them need to personally remember anything about any one user.

🏭 In real companies Twitter has publicly discussed relying heavily on Memcached-style caching to survive its read-heavy traffic — and even open-sourced its own tooling built around that pattern. At that scale, a caching layer isn't an optimization; it's the difference between the site staying up and the database falling over under read traffic.

Redis vs Memcached, side by side

FeatureRedisMemcached
High AvailabilityMulti-AZ with automatic failoverNo native replication or HA (except Serverless)
Scaling ReadsRead Replicas supportedSharding (partitioning data across nodes)
Persistence & BackupDisk persistence (AOF); snapshots & backupsNo persistence (data cleared on restart)
Data StructuresStrings, sets, sorted sets, hashes, listsSimple key-value store only
ArchitecturePrimary node replicated to replica nodesMulti-threaded, multi-node memory partitioning

In short: reach for Redis when you need the data to survive a node failing, or when you need more than plain key-value storage. Reach for Memcached when you want the simplest possible cache and don't mind losing it on a restart.

9ElastiCache — Hands-On

Creating an ElastiCache cluster in the console involves choices like these:

  • Engine: Valkey (AWS's recommended open-source Redis replacement), Memcached, or Redis OSS.
  • Deployment type: Serverless, or a traditional node-based cluster.
  • Cluster mode: Disabled (one primary node, up to 5 read replicas) or Enabled (data split across multiple shards).
  • Multi-AZ: turns on automatic failover for high availability.
  • Subnet group: the private VPC subnets your cache nodes actually live in.
  • Security & encryption: encryption at rest (via a KMS key) and in transit, which also unlocks Redis AUTH token authentication.
  • Security groups: control which ports can reach the cluster — Redis defaults to 6379, Memcached to 11211.

Once deployed, you get both a primary endpoint and a reader endpoint URL to plug into your application.

Cleaning up: select the cluster → Actions → Delete → skip the final snapshot if you don't need one → type the cluster's name to confirm.

10ElastiCache Strategies

Before bolting a cache onto your app, it's worth asking a few honest questions — because caching the wrong thing can cause more problems than it solves. Nobody wants a bank balance that's a few seconds stale.

  1. Is this data actually safe to cache? Fine for data that can tolerate being slightly out of date. A bad fit for anything that must always be exactly right, like a bank balance.
  2. Will caching actually help? Great for data that changes slowly but gets read constantly. Not much use for data that changes every second.
  3. Is the data shaped for it? Caches work best with key-value pairs, or results you've already pre-computed.
  4. Which caching pattern fits — Lazy Loading, or Write Through?

Lazy Loading (the Cache-Aside pattern)

💡 New word Cache-aside (also called Lazy Loading) means your application only puts something into the cache after it's actually been asked for, once.
On a cache miss: read from the RDS database, then store the result in ElastiCache for next time.

On a cache miss, your app reads from the database and then writes that result into ElastiCache, so the next request for the same thing hits the cache instead.

🏭 In real companies Cache-aside is one of the most standard, widely used caching patterns in the entire industry. It's usually the default choice, precisely because a cache outage doesn't take your app down with it — every request just falls back to hitting the database directly, a little slower, until the cache comes back.

What you gain: only the data that's actually requested ever takes up cache memory. And if the cache goes down entirely, requests still work — they just fall back to the database.

What it costs you: a cache miss takes three network hops instead of one (app to cache, cache miss, app to database, then app back to cache to store the result). There's also a real risk of serving stale data if the database changes without the cache being told.

def get_user(user_id):
    record = cache.get(user_id)
    if record is None:
        # Cache miss
        record = db.query("SELECT * FROM users WHERE id = ?", user_id)
        cache.set(user_id, record)
    return record

Write Through

The opposite approach: every time your app writes to the database, it writes the same update into the cache at the same moment, whether anyone has asked for that data yet or not.

What you gain: the cache is never stale, because it's updated the instant the database is.

What it costs you: every write now does double duty — one write to the database, one to the cache — which adds a small delay to every write. You'll also end up caching data nobody actually reads, wasting cache memory.

def save_user(user_id, values):
    record = db.query("UPDATE users SET ... WHERE id = ?", user_id, values)
    cache.set(user_id, record)
    return record

Getting rid of old data

Cache memory is limited, so old entries have to go eventually. There are a few ways that happens:

  • Your own application code deletes it explicitly.
💡 New word LRU (Least Recently Used) is an eviction rule: when the cache runs low on memory, it throws out whatever hasn't been touched in the longest time.
💡 New word TTL (Time To Live) means an entry automatically expires after a set amount of time — say, 5 minutes or 1 hour — whether anyone touched it or not.

11Amazon MemoryDB for Redis

Everything ElastiCache does is built on one assumption: it's fine to lose the cache. Worst case, you just rebuild it from the real database. But what if you want Redis's speed and its data structures — and you also need to actually trust it as your one real source of data?

💡 New word MemoryDB is a Redis-compatible database built to be durable enough to serve as your primary database, not just a disposable cache.
  • Handles over 160 million requests per second.
  • Guarantees zero data loss using a Multi-AZ transactional log.
  • Scales from a few gigabytes up to hundreds of terabytes.
🏭 In real companies Teams reach for MemoryDB when they want Redis's exact commands and speed — for things like real-time leaderboards, session stores, or gaming state — but can't accept losing that data if a node restarts. That's the one line that separates it from ElastiCache: ElastiCache is explicitly disposable, MemoryDB is not.

Key Facts Worth Remembering

  • RDS engines: PostgreSQL, MySQL, MariaDB, Oracle, SQL Server, IBM DB2, Aurora.
  • No SSH access to RDS or Aurora servers — it's a managed service.
  • Storage Auto Scaling fires when free space is under 10%, that's lasted over 5 minutes, and 6+ hours have passed since the last expansion.
  • Read Replicas: up to 15, async, eventually consistent, SELECT only, free cross-AZ replication within a Region.
  • Multi-AZ: sync replication, one DNS address, automatic failover, standby is not directly readable or writable.
  • Aurora: 6 copies across 3 AZs (4/6 for writes, 3/6 for reads), up to 15 replicas at sub-10ms lag, storage up to 256 TB, plus Backtrack for instant rewinds.
  • RDS Proxy: pools connections, cuts failover time up to 66%, supports IAM auth, VPC-only — never public.
  • ElastiCache: Redis (HA, replicas, persistence, rich data structures) vs Memcached (simple key-value, multi-threaded, no HA).
  • Lazy Loading caches only what's asked for; Write Through keeps the cache always fresh but slows every write.
  • MemoryDB: a durable primary database that speaks the Redis API.

The One-Paragraph Version

RDS takes the operational grind out of running a SQL database — patching, backups, and monitoring, handled for you. Read Replicas scale read traffic; Multi-AZ keeps you online through a failure — they solve different problems and often get used together. Aurora is AWS's own faster, self-healing take on MySQL and PostgreSQL. RDS Proxy stops serverless traffic bursts from overwhelming your database's connection limit. ElastiCache adds an in-memory layer — Redis or Memcached — in front of your database, using either Lazy Loading or Write Through to decide when data gets cached. And MemoryDB is what you reach for when you want Redis's speed but need to trust the data as your real source of truth, not a disposable copy.
