1SAM: Simpler Infrastructure for Serverless

CloudFormation gives you total control. You write a template that describes every resource — Lambda functions, API gateways, databases, permissions — and CloudFormation creates and updates them all together. But for serverless applications, most of that template is boilerplate. SAM (Serverless Application Model) exists to cut that boilerplate down.

💡 New word SAM (Serverless Application Model) is a framework that lets you write shorter CloudFormation templates for serverless apps. You write simpler YAML, SAM expands it into full CloudFormation behind the scenes, and then deploys it all.

How SAM actually works

When you write a SAM template, it starts with a special header called Transform. This tells CloudFormation, "Hey, this isn't a plain CloudFormation template — it's SAM, so expand it first." CloudFormation then runs the SAM transformation, which takes your short template and generates the much longer, equivalent raw CloudFormation. Finally, it deploys the expanded template as a regular stack.

💡 New word Transform is a CloudFormation header that tells CloudFormation to process the template through a macro — in SAM's case, the macro that expands simple serverless constructs into full resources and permissions.
Your short SAM template gets expanded into full CloudFormation, then deployed like any other stack.

What SAM gives you

Instead of writing AWS CloudFormation resources, you write simpler SAM constructs. A single AWS::Serverless::Function in SAM becomes a Lambda function plus its execution role, plus environment variables, plus event sources — all the plumbing that raw CloudFormation would make you spell out by hand.

💡 New word AWS::Serverless resources are the building blocks SAM provides: Function (for Lambda), Api (for API Gateway), SimpleTable (for DynamoDB), and a few others. Each one expands into several CloudFormation resources under the hood.
SAM constructExpands into
AWS::Serverless::FunctionLambda function + execution role (IAM)
AWS::Serverless::ApiAPI Gateway + stages + methods
AWS::Serverless::SimpleTableDynamoDB table with provisioned throughput
🏭 In real companies Teams that deploy Lambda-based applications regularly choose between SAM and CDK (another infrastructure-as-code tool). SAM is simpler for pure serverless apps — write a YAML file, deploy it with one command. CDK is more powerful but requires writing code. Many companies use SAM for quick microservices and CDK for complex multi-service infrastructure.

Key SAM features

  • Local testing: SAM can emulate Lambda, API Gateway, and DynamoDB on your own machine, so you test before deploying.
  • One-command deploy: sam deploy packages your code, uploads it to S3, and creates or updates your CloudFormation stack — all in one step.
  • Policy templates: Instead of hand-writing IAM policy JSON, you reference pre-built permission sets by name.
  • CodeDeploy integration: SAM can orchestrate safe Lambda deployments using traffic shifting and automated rollback.
  • Environment support: Manage dev, staging, and production deployments from a single template using configuration files.

2Your First SAM Project

Getting a SAM project running takes three commands. First, you scaffold a new project. Then you build it locally. Finally, you deploy it to AWS.

Step 1: Scaffold a project

Run sam init and choose a quick-start template (the "Hello World" example is perfect for learning). SAM asks for your runtime (Python, Node, Java, etc.) and project name, then generates a directory structure with everything you need.

Key files that get created:

FilePurpose
template.yamlYour SAM template — describes the Lambda function, API Gateway, and any other resources. Starts with Transform: AWS::Serverless-2016-10-31.
hello_world/app.py (or .js, .java, etc.)Your actual Lambda function code. The handler function lives here.
requirements.txt (or package.json, pom.xml)Dependency list for your runtime. For Python, pip reads this file.
samconfig.tomlConfiguration file that stores deployment settings (stack name, region, S3 bucket) so you don't have to type them every time.
💡 New word sam cli (SAM Command Line Interface) is the tool you run from your terminal. Commands like sam init, sam build, and sam deploy all come from it.

Step 2: Build locally

Run sam build. This command reads your template, installs dependencies from your requirements file, and prepares everything in a .aws-sam/build directory. Think of it as compilation — you're getting your code ready to run.

Step 3: Deploy to AWS

Run sam deploy --guided. The first time, --guided walks you through each choice: What should the stack be named? Which AWS region? Should SAM create an IAM role? It saves your answers to samconfig.toml so next time you can just run sam deploy without the questions.

Behind the scenes, SAM uploads your code to an S3 bucket, creates the expanded CloudFormation template, and submits it to CloudFormation. A few seconds later, your Lambda function exists, API Gateway is set up, and you get back a URL you can hit with your browser or curl.

SAM creates a few supporting resources on your first deploy: an S3 bucket to store your code artifacts, and an IAM role to let SAM do its work. These exist once and persist across deploys — you don't recreate them each time.
Remember to clean up: When you're done experimenting, run sam delete to remove your entire stack and avoid surprise AWS charges.

3SAM with Databases — Full CRUD Example

The "serverless API" quick-start template in sam init includes a more complete example: multiple Lambda functions, a DynamoDB table, and the permissions connecting them together. This is your first taste of how SAM shortcuts the permissions problem.

What the template includes

The example has Lambda functions for common operations: getting all items, adding a new item, updating an item, and deleting one. Each function declares which events trigger it — a GET request on a path, a POST on another path, and so on. SAM automatically wires those into API Gateway.

There's also a AWS::Serverless::SimpleTable resource — a DynamoDB table with a partition key. Each function that needs to read or write the table references that table by its logical name in the template.

💡 New word Implicit API (from API Gateway) means SAM automatically creates the API Gateway setup for you. You define which events (GET on /items, POST on /items) trigger your functions, and SAM connects them — you never need to configure API Gateway by hand.

How SAM handles permissions

Each function declares a CRUD policy on the table: "this function needs to create, read, update, and delete items in this specific table." In raw CloudFormation, you'd write an IAM policy document by hand. In SAM, it's just a few lines referencing the table's name.

This is SAM's biggest convenience win: you don't touch IAM policy JSON. You declare what each function needs in plain language, and SAM generates the policies for you.

Testing before deployment

The template comes with sample events in an events/ folder — one JSON file per operation (put, get, etc.). You can run sam local invoke PutItemFunction --event events/event-put-item.json to test a single function with a realistic payload, all on your laptop. Or run sam local start-api to launch a local HTTP server that emulates your entire API — you can then curl http://localhost:3000/items and watch your functions run.

🏭 In real companies A developer's workflow is usually: write code locally, test against the local SAM emulator, commit to git, and let a CI/CD pipeline handle the actual AWS deployment. The SAM local commands eliminate the "I have to deploy to AWS to see if this works" problem that slows down development.

4Policy Templates: Pre-Built Permissions

Instead of letting you hand-write IAM policy JSON, SAM provides a library of policy templates. Each template is a named set of permissions that you attach to a Lambda function in a single line.

💡 New word Policy templates are pre-written IAM permission sets in SAM. You reference them by name (like S3ReadPolicy or DynamoDBCrudPolicy) and optionally specify which resource (which S3 bucket, which DynamoDB table) they apply to.

Common policy templates include:

Template nameWhat it grants
S3ReadPolicyRead-only access to objects in a specified S3 bucket
S3CrudPolicyFull create, read, update, delete on objects in a bucket
SQSPollerPolicyPermission to poll a queue and delete messages (for Lambda triggers)
DynamoDBCrudPolicyFull CRUD operations on a specified DynamoDB table
KMSDecryptPolicyPermission to decrypt with a KMS key

Why this matters

Imagine you need to give a Lambda function permission to read from a specific S3 bucket. In raw CloudFormation, you'd write a policy document with the right actions, resource ARN, and effect. In SAM, you write one line: Policies: [S3ReadPolicy: {BucketName: my-bucket}]. SAM expands that into the full IAM policy.

You don't need to memorize every policy template. Learn to recognize the pattern (names are usually self-explanatory), and you'll know they exist as a shortcut whenever you need a common permission.
Policy templates are convenient but limited: They cover common scenarios. If you need custom logic — like "allow this function to read from bucket A but only objects matching a path prefix" — you'll write a policy document by hand and attach it alongside the templates.

5Safer Lambda Deployments with CodeDeploy

Rolling out new Lambda code to production carries risk. If your new version has a bug, users hit it immediately. SAM integrates with CodeDeploy to deploy gradually, so a small group of users sees the new version first, and if metrics look bad, it rolls back automatically.

💡 New word CodeDeploy is AWS's deployment orchestration service. SAM can use CodeDeploy to shift Lambda traffic from the old version to the new one gradually, with automated rollback if anything goes wrong.

How gradual deployment works

Behind the scenes, Lambda deployments use aliases. An alias is a pointer to a specific version of your function. Instead of clients calling the function directly, they call the alias, and the alias routes traffic. SAM can update the alias gradually: send 10% of traffic to the new version for 10 minutes, monitor metrics, then send 100% if all looks good.

💡 New word Lambda alias is a named pointer to a specific version of your function. It lets you shift traffic between versions without changing what clients call.

Deployment strategies

SAM supports three strategies, which you declare in the template:

StrategyWhat happens
CanaryShift a small percentage (e.g., 10%) to the new version for a window (e.g., 10 minutes), then 100% if metrics are good. Good for catching issues early with minimal blast radius.
LinearGradually increase traffic in equal increments over time (e.g., 10% every 10 minutes for an hour total). Smoother than canary but slower.
AllAtOnceSwitch all traffic immediately. Only use this if you're very confident or it's a low-risk change.
💡 New word Canary deployment is a release pattern: deploy the new version to a small percentage of users (the "canaries") first, watch for problems, then roll out to everyone if it looks safe.

Optional validation and rollback

You can configure pre-traffic and post-traffic validation hooks — Lambda functions that run tests after each traffic shift. If a test fails, SAM rolls back automatically. You can also attach CloudWatch alarms: if an alarm breaches during the deployment, SAM cancels the rollout.

🏭 In real companies Teams deploying to production typically enable both validation hooks and CloudWatch alarms. The hooks run smoke tests (call the API, check the response). The alarms watch for spikes in errors or latency. If either signal bad health, the old version is restored and the new code never reaches all your users.

6Testing Locally Before You Deploy

SAM's local testing tools let you iterate without touching AWS. You can invoke a single function with a test event, or start a full API server on your laptop.

💡 New word sam local is a set of SAM CLI commands that emulate AWS services on your machine: Lambda, API Gateway, and DynamoDB all run locally so you can test without deploying.

Testing a single function

Run sam local invoke FunctionName --event events/event.json. This invokes your function once with the provided event payload, runs it in a local Docker container (SAM uses Docker to match the real Lambda environment), and prints the response. Use --profile your-profile if the function calls other AWS services — SAM will use those AWS credentials.

Testing the whole API

Run sam local start-api. This starts a local HTTP server (usually on localhost:3000) that emulates API Gateway. You can then use curl or your browser to hit the local API, and it routes requests to your local Lambda functions. The best part: SAM watches your code files and reloads on changes, so you can edit and test in seconds.

Generating test events

Run sam local generate-event service-name event-type to create a realistic test event. For example, sam local generate-event apigateway aws-proxy generates a valid API Gateway proxy event that you can use with sam local invoke. This saves you from manually writing JSON event structures.

The local start-api server is a huge productivity boost. You get instant feedback, can debug with print statements, and never need to wait for a CloudFormation deployment to test a small change.
Local testing has limits: The local DynamoDB emulator is basic — it doesn't support all DynamoDB features. For complex queries or edge cases, test against the real AWS DynamoDB in a dev account.

7Multiple Environments from One Template

Most projects have multiple environments: development (where you experiment), staging (the final test before production), and production (real users). Rather than maintaining separate templates, SAM lets you define all environments in one template and switch between them at deploy time.

💡 New word samconfig.toml is the configuration file that stores your deployment settings. It can have multiple named sections, each representing an environment with its own stack name, region, S3 bucket, and parameter values.

How it works

In samconfig.toml, you define sections like [dev.deploy.parameters] and [prod.deploy.parameters]. Each section specifies the stack name, region, and any parameters the template accepts (environment variables, memory size, table name, etc.). When you deploy, you specify which environment with a flag: sam deploy --config-env dev or sam deploy --config-env prod.

SAM reads the matching section, applies those settings, and deploys. You get separate stacks in AWS — one for dev, one for prod — each configured exactly as you specified.

🏭 In real companies Keeping dev and prod in separate AWS accounts is actually the safest pattern. But even within one account, separating stacks by environment (with different Lambda memory sizes, DynamoDB throughput, or API Gateway throttling) is standard. SAM's multi-environment config makes this easy.

Parameter overrides

If your template declares parameters (values you can override at deploy time), you can set different values per environment in the config file. For example, the dev environment might have a DynamoDB table with small provisioned throughput, while prod has larger capacity — both driven by the same template.

You can also override settings on the command line, but storing them in samconfig.toml means your team doesn't have to remember the right values — they're checked into git and consistent across developers.

8Fast Code Iteration with SAM Accelerate

CloudFormation deployments take time. Even a simple code change requires SAM to build, upload to S3, and create or update the stack — usually a minute or more. SAM Accelerate speeds this up for the common case where you're only changing code, not infrastructure.

💡 New word SAM Accelerate (sam sync) is a faster deployment mode. Instead of going through CloudFormation, it can bypass it entirely and update Lambda directly via the AWS API — much faster for pure code changes.

When to use sam sync

Use sam sync --code when you've only changed your function code, not the template. It updates Lambda directly without touching CloudFormation — deployments take seconds instead of a minute. Use plain sam sync if you changed both code and infrastructure — it still goes through CloudFormation but uses a streamlined process.

CommandWhat it updatesSpeed
sam sync --codeOnly Lambda function code (skips CloudFormation)Seconds
sam syncCode + infrastructure (via CloudFormation)Seconds to minutes
sam deployCode + infrastructure (standard CloudFormation)Minutes

Watch mode for real-time updates

Add --watch to run SAM sync in the background, continuously watching your source files. Change a file, and the function updates automatically — no command to type between changes. This is perfect for iterating rapidly during development.

sam sync --code --watch is the fastest development loop: save a file, and it's running on AWS within a few seconds. Use it heavily while developing, then do a full sam deploy before committing to make sure everything (template + code) deploys cleanly.
sam sync bypasses validation: It skips some of CloudFormation's safety checks. For final production deployments, always use sam deploy to ensure the template is valid and can roll back safely.

📋 Cheat Sheet

What SAM Is

SAM is a simplified layer on top of CloudFormation for building serverless applications. You write shorter YAML templates using serverless-specific constructs (Function, Api, SimpleTable), SAM expands them into full CloudFormation, and then deploys like normal. The benefit: less boilerplate, built-in local testing, policy templates instead of hand-written IAM, and CodeDeploy integration for safe deployments.

Core Concepts

  • Transform: The CloudFormation header that tells CloudFormation to run the SAM macro on your template.
  • AWS::Serverless::Function: Defines a Lambda function plus its role and event triggers.
  • AWS::Serverless::Api: Creates API Gateway with implicit routing — you declare events, SAM wires them.
  • AWS::Serverless::SimpleTable: A DynamoDB table with a simple partition key.
  • Policy templates: Pre-built permission sets (S3ReadPolicy, DynamoDBCrudPolicy, etc.) that you attach to functions by name.
  • Lambda alias: A pointer to a function version, used by CodeDeploy to gradually shift traffic during deployments.

The Development Workflow

  1. sam init — scaffold a new project with a quick-start template.
  2. sam build — compile and prepare dependencies locally.
  3. sam local start-api — run a local API server to test everything before AWS.
  4. sam deploy --guided — deploy to AWS for the first time (saves settings in samconfig.toml).
  5. sam deploy — deploy again (uses saved settings).
  6. sam delete — clean up the stack when done.

Fast Iteration

  • sam sync --code --watch — automatically redeploy code as you save files (seconds, skips CloudFormation).
  • sam local invoke FunctionName --event events/event.json — test a single function offline.
  • sam local generate-event service-name event-type — create realistic test payloads.

Multi-Environment Deployments

  • Define [dev.deploy.parameters], [staging.deploy.parameters], [prod.deploy.parameters] in samconfig.toml.
  • Deploy to a specific environment: sam deploy --config-env dev.
  • Each environment gets its own CloudFormation stack with separate resources and settings.

Safe Production Deployments

  • Set AutoPublishAlias in your function to tell SAM to auto-publish versions.
  • Set DeploymentPreference to Canary, Linear, or AllAtOnce to control traffic shifting.
  • Add CloudWatch alarms or pre/post-traffic validation hooks for automated rollback if something goes wrong.

Key Facts to Remember

  • SAM is just CloudFormation with boilerplate pre-written — everything it does, CloudFormation can do too.
  • Local testing with SAM is one of its biggest wins — you iterate on your laptop, not in AWS.
  • Policy templates eliminate most hand-written IAM JSON for serverless apps.
  • sam sync --code is your friend for rapid development; use sam deploy for final, validated pushes to production.
  • Canary and Linear deployments with CodeDeploy make production Lambda updates safer.
