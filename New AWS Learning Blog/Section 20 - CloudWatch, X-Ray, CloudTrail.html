1Monitoring Overview in AWS

Your users don't care how you built the system or what tools you chose. They only care that it works: requests come back fast, nothing breaks at 3am, and they never have to call a help desk to complain. Monitoring is the discipline of answering three crucial questions before your users have to ask: Is something wrong? How bad is it? Where exactly is the problem?

Three complementary tools that together give you complete visibility. CloudWatch watches the health of your application, X-Ray traces individual requests through your architecture, and CloudTrail audits every API call made in your account.

Why this matters

When something goes wrong — a spike in error rates at 2am, a performance cliff nobody expected, or a sudden spike in your bill — you need answers fast. Without monitoring, you're flying blind. With it, you go from "everything is broken, I don't know why" to "this specific database query is timing out and here's the exact Lambda function calling it" in minutes, not hours.

2CloudWatch Metrics

Every AWS service automatically sends metrics — numbers that describe what's happening — to CloudWatch the moment something happens in your account. An EC2 instance sends CPU usage every few seconds. An RDS database sends query latency. A Lambda function sends invocation count.

💡 New word Metric — a time-stamped number that measures something. Examples: CPU percentage, disk usage, request count, error count, latency in milliseconds. Every metric has a name (e.g. "CPUUtilization"), belongs to a service (e.g. EC2), and can have dimensions (attributes like which instance, which environment).

How metrics work

A metric lives inside a namespace (usually the service name like "AWS/EC2") and has dimensions — key-value pairs that let you slice the data. For example, an EC2 instance sends its CPU metric with dimensions like InstanceId=i-12345 and InstanceType=t3.medium. You can visualize any metric on a CloudWatch Dashboard, export it as CSV, or set an alarm on it.

EC2 monitoring granularity

ModeFrequencyCost
DefaultEvery 5 minutesFree
Detailed monitoringEvery 1 minuteAdditional cost
Critical gotcha: Even if you enable detailed monitoring, memory usage (RAM) is never sent automatically — it must be sent as a custom metric by an agent running on the instance. Many people discover this the hard way when they need to debug memory problems and find no data.
🏭 In real companies The moment an on-call engineer joins a company, one of the first questions they ask is "what's on the dashboards?" — usually a dozen graphs showing CPU, latency, error rates, and queue depths. This combination tells you, in seconds, whether a problem is localized to one service or systemic. Most cloud teams spend weeks getting this right.

3CloudWatch Custom Metrics

AWS services send you their own metrics for free. But what if you need to track something AWS doesn't know about — like the number of active users logged into your application, or how many items are sitting in a backlog, or the size of your database cache? That's where custom metrics come in.

💡 New word Custom metric — a metric you create and push to CloudWatch yourself using the PutMetricData API call. You decide the name, the namespace, the dimensions, and the values.

You push a custom metric from your application using the AWS SDK. Give it a name (e.g. "ActiveSessions"), a value (e.g. 1523), a namespace (usually your company name or app name), and optional dimensions (e.g. Environment=prod, Region=us-east-1).

Two resolution options

Standard resolution means you push a value once a minute — fine for slow-moving numbers like queue depth or user count. High resolution lets you push every 1, 5, 10, or 30 seconds — useful for things like request latency where you want more granular data and are willing to pay for it.

Exam tip CloudWatch accepts metric timestamps up to 2 weeks in the past or 2 hours in the future without error. If your EC2 instance's clock is wildly out of sync, your historical metrics will look wrong, or alarms won't trigger when they should.

Under the hood, the CloudWatch Unified Agent (which we'll cover later) uses this same PutMetricData API to push detailed system metrics like RAM usage and disk I/O from your servers.

4CloudWatch Logs

Metrics give you the big picture. But when something goes wrong, you need to read the actual log lines — the "error: connection timeout at line 42" entries that your application wrote. That's what CloudWatch Logs does: stores logs in one centralized place instead of scattered across a dozen servers.

💡 New word Log group — a named container for logs from one logical source. Usually one per application. Inside it live log streams.
💡 New word Log stream — one source of logs within a group. Usually one per instance, container, or Lambda invocation. Each stream contains timestamped log events (individual log lines).
A log group (usually one per application) contains multiple log streams. Each stream is one source — an EC2 instance, a Lambda function, a Docker container — and sends its own sequence of timestamped log events.

What logs end up here

CloudWatch Logs receives logs from Lambda functions (automatic), EC2 instances (via agent), Elastic Beanstalk, ECS containers, VPC Flow Logs, API Gateway, and Route 53 DNS queries. You can also send custom logs from your own application using the SDK.

Storage and retention

Set a retention policy for each log group: logs can expire after 1 day, 1 week, 1 month, 1 year, or never expire. Encrypted by default; use a custom KMS key if your compliance requires it. You can export logs to S3 for long-term archival, or stream them in real-time to Kinesis, Lambda, or OpenSearch for analysis.

CloudWatch Logs Insights

💡 New word Logs Insights — a query engine built into CloudWatch that lets you search, filter, and analyze logs with its own SQL-like query language. Automatically detects fields (e.g. timestamp, severity, message), supports filtering, aggregation, sorting, and saved queries.

You can query across multiple log groups in a single search, and even across AWS accounts. But remember: Logs Insights is not real-time. It searches historical data when you run a query; it doesn't stream live events to a dashboard.

How to export logs

MethodTimingBest for
CreateExportTask → S3Batch (up to 12 hours to complete)Bulk archival, compliance record-keeping
Subscription filter → Kinesis/Firehose/LambdaReal-time / near real-timeLive processing, cross-account aggregation, triggering actions

For cross-account log aggregation, you create a destination in the recipient account (representing, say, a Kinesis stream), attach a destination access policy to allow the sender account to write, and the sender sets up a subscription filter pointing at that destination.

5CloudWatch Logs Hands-On & Live Tail

Let's walk through the console. You create a log group (give it a name like /aws/lambda/payment-processor), set retention and encryption, and wait. Log streams populate as your application sends logs — each stream contains a sequence of timestamped log events, usually one log line per event.

Three useful log group actions

  • Create a metric filter: Turn matching log lines into a CloudWatch metric. For example, count how many lines contain the word "error" and create a metric called "ErrorCount". This metric can then trigger an alarm.
  • Export to S3: Batch-export logs for compliance or long-term archival.
  • Start tailing: Open a real-time log viewer and watch logs stream in as they're written — perfect for debugging a live issue.

Live Tail

CloudWatch's real-time log viewer. Pick a log group (and optionally a specific log stream), and matching log events appear live as they're written. Filter by text, search for specific fields, and close the session when done. You get a free allowance; excessive use has a small cost.

Pro tip: Always close your Live Tail session when you're done debugging. It's easy to forget and rack up unexpected charges.

6CloudWatch Agent & Logs Agent

By default, an EC2 instance sends zero logs to CloudWatch. Nothing. You need to install an agent — a small program that runs on the server, reads local log files, and pushes them to CloudWatch. AWS provides two options; one is old and being phased out, the other is the standard choice.

AgentLogs?Metrics?Status
CloudWatch Logs Agent (old)YesNoBeing phased out
CloudWatch Unified Agent (new)YesYes — detailed (CPU subcategories, disk I/O, RAM, swap, per-process data, netstat)Standard choice; centrally configurable via SSM Parameter Store
🏭 In real companies Once you have a few dozen EC2 instances, manually installing and configuring an agent on each one becomes a nightmare. Most teams use Systems Manager (AWS's systems administration service) to centrally push agent configuration — called "Parameter Store" — to all instances at once. This way, changing where logs go, what to monitor, or thresholds happens in one place.

Out-of-the-box EC2 metrics

EC2 gives you disk usage, CPU usage, and network metrics for free (at 5-minute intervals). It does not give you memory (RAM) or swap usage. If you need those, you must run the Unified Agent.

Important: The EC2 instance needs an IAM role with permissions to write logs to CloudWatch. If you skip this, the agent will fail silently and you'll see no logs.

7CloudWatch Logs Metric Filters

You have logs coming into CloudWatch. But reading through hundreds of lines manually isn't scalable. Enter metric filters: a pattern matcher that turns log lines into numbers.

💡 New word Metric filter — watches for a pattern in incoming log events (e.g., the word "error", or an IP address, or a phrase) and increments a metric when it finds a match. That metric can then trigger an alarm.
A metric filter watches log events coming in. When lines match the pattern, the filter counts them and feeds the count into a metric, which can then trigger an alarm or notification.

Key limitations

Metric filters are not retroactive — they only count new log events that arrive after the filter is created. If you created a filter today, it won't count errors from yesterday. You can define up to 3 dimensions per metric filter to slice the data (e.g. by Environment or Service).

8CloudWatch Alarms

A metric is a number over time. An alarm is "if that number crosses this line, do something." And doing something usually means: notify me, or auto-fix it, or both.

💡 New word Alarm — an automated action triggered when a metric crosses a threshold. An alarm has three states: OK (good), INSUFFICIENT_DATA (not enough samples yet), and ALARM (threshold breached).

Where alarms send notifications

  • EC2 action: Stop, terminate, reboot, or recover an instance.
  • Auto Scaling action: Scale out (add capacity) or scale in (reduce it).
  • SNS notification: Which can then trigger a Lambda function for custom logic, send you an email, post to Slack, PagerDuty, etc.

Composite Alarms for less noise

💡 New word Composite Alarm — combines multiple underlying alarms with AND/OR logic instead of triggering on a single metric. Example: only alert if CPU is high AND disk I/O is high (not either alone), reducing false alarms.
Instead of two alarms going off separately and sending noise, a composite alarm only fires when both conditions are met. This catches real problems while cutting false alarms.

EC2 status checks and recovery

EC2 publishes three types of status checks: instance status (the VM itself), system status (the underlying hardware), and attached EBS status (storage health). An alarm on these can trigger EC2 instance recovery — AWS moves the instance to new hardware while preserving its IPs, metadata, and placement, so your application barely notices.

Testing trick: Use the CLI command set-alarm-state to manually force an alarm into ALARM state without waiting for a real threshold breach. Confirms your downstream actions (Lambda invocation, SNS notification) actually work.

9CloudWatch Synthetics

You monitor your application's CPU and latency. But what if a bug sneaks in that only breaks the checkout flow? You might not catch it for days. Synthetics Canary simulates what a real customer would do, so you find problems before they do.

💡 New word Canary — a scripted test that reproduces user behavior (e.g., visit home page, log in, add item to cart, checkout) on a schedule. Built on Node.js or Python with a headless browser, it runs every minute (or however often you choose), takes screenshots, measures latency, and alerts you on failure.

Blueprints let you get started without writing code: Heartbeat Monitor (ping a URL), API Canary (test an API endpoint), Broken Link Checker, Visual Monitoring (compare screenshots to a baseline to catch UI regressions), Canary Recorder (record your actions, auto-generate the script), and GUI Workflow Builder (drag-and-drop automation).

Example: Your Canary detects the checkout button is returning 500 errors → triggers a CloudWatch alarm → invokes a Lambda that automatically fails over traffic to your backup region. You're paged, but the damage is already contained.

10Amazon EventBridge

EventBridge (formerly called CloudWatch Events) is a routing engine: events happen across your AWS account (an EC2 instance starts, an S3 object is created, a schedule fires), and EventBridge routes matching events to targets (Lambda, SNS, SQS, a custom application, etc.).

💡 New word EventBridge — listens for events (state changes, API calls, or scheduled times) and routes matching events to targets. It replaces the older CloudWatch Events service and is now the standard for event-driven AWS automation.
Event sources (AWS services, schedules, API calls) send events to EventBridge. Rules filter for matching patterns, and matching events route to targets.

Event bus types

Default: events from AWS services. Partner: SaaS partners like Datadog, Auth0, Zendesk send their events here. Custom: your own applications send their own events.

Two powerful features

  • Archive and replay: Save events for later, then replay them through a rule (great for debugging — fix a Lambda bug, then replay yesterday's events to test the fix).
  • Schema Registry: Auto-infers the JSON shape of events, generates code for your application to consume them correctly, and versions schemas for compatibility.

You can also attach resource-based policies to an event bus for cross-account/cross-region event routing — the foundation of centralized event aggregation.

11EventBridge Multi-Account Aggregation

You have multiple AWS accounts (dev, staging, prod). Each one has EC2 instances and databases firing events. You want to see them all in one central place. EventBridge's cross-account routing makes this possible.

How it works

  1. In the central account, attach a resource-based policy to the event bus accepting events from the other accounts.
  2. In each source account, create an event rule whose target is the central account's event bus (instead of the usual targets like Lambda).
  3. On the central bus, create your own rule(s) to react once events land (send to SNS, invoke Lambda, etc.).
🏭 In real companies Large companies with dozens of accounts use this pattern to centralize observability. One team runs the "event hub" account; all other accounts forward their critical events there. One dashboard shows failures and state changes across the entire infrastructure. Security teams also use this to centrally collect audit events.

12X-Ray Overview

CloudWatch Logs and metrics tell you something is broken. But in a microservices architecture with 20 different services, hunting through logs scattered across a dozen places is a nightmare. X-Ray gives you a visual map of your entire request flow, showing exactly which service is slow, where errors occur, and the latency at each hop.

💡 New word X-Ray — a distributed tracing service. It collects timing and error data from every service a request touches, stitches it together, and shows you one cohesive trace. Includes a service map visualization and latency analysis.
The service map shows every hop. If DynamoDB returns an error, X-Ray highlights it in red. Instead of grep-ing through logs, you see the entire flow visually and instantly know which service failed.

Why it matters

Without tracing, a slow request is a mystery: was it the database, the API, the downstream service? With X-Ray, you click on a request and see every call it made, how long each took, and which one timed out. You go from "production is slow" to "the payment service is calling an external API that's down" in seconds.

How to enable it

  1. Instrument your code: Import the X-Ray SDK (available for Java, Python, Go, Node.js, .NET) so it auto-captures AWS SDK calls, HTTP requests, and database queries.
  2. Run the X-Ray daemon: A small UDP server that collects trace data from your application and forwards it to AWS. Lambda runs it automatically; on EC2 you install it yourself.
  3. Grant IAM permissions: Your application needs permission to write traces to X-Ray.
Common failure: "It works locally but not on EC2" almost always means the X-Ray daemon isn't running on the EC2 instance. Your local machine has it, but the cloud instance doesn't. The application will silently drop traces if it can't reach the daemon.

13X-Ray — Hands-On

The X-Ray console lives inside CloudWatch (look for Service map and Traces sections). A demo application (running on ECS, using DynamoDB and SNS) was deployed, generating real traces.

What you see

The service map shows all components as boxes and their dependencies as arrows. A component in error (e.g., SNS calls failing) is highlighted in red or orange. Click a node to see its latency distribution, fault count, and request rate. The Traces section lists individual requests — filter by service name, latency, or trace ID to find the one slow request among millions, then drill into its step-by-step breakdown: which calls happened, in what order, how long each took.

Debugging workflow: (1) Service map shows DynamoDB is red. (2) Click DynamoDB node, see 50% of requests are failing. (3) Go to Traces, filter by "Service: DynamoDB AND Status: Fault", see a trace. (4) Trace detail shows the query is timing out on a specific table. (5) You know exactly what to fix.

14X-Ray Concepts & Instrumentation

Instrumentation means measuring performance and collecting trace data. Usually it's done by adding the X-Ray SDK to your code — sometimes just one line of config, sometimes with custom interceptors/middleware for more control.

💡 New word Segment — one component's contribution to a request trace. Your API Lambda sends a segment, the database sends a segment, etc. Each segment has timing and error info.
💡 New word Subsegment — a finer-grained breakdown within a segment. Example: your Lambda makes multiple database calls; each call is a subsegment inside the Lambda's segment.
💡 New word Trace — all segments from one end-to-end request, stitched together. One trace = one customer request flowing through all your services.

Annotations vs. Metadata

TypeSearchable?Use for
AnnotationsYes (indexed)Customer ID, order ID, environment, anything you'll filter by
MetadataNoFull request body, verbose debug info, anything you won't search on
Exam trap If you add data as metadata and then try to search for it, you'll get nothing. Use annotations when you need to filter traces by that data.

X-Ray also supports cross-account tracing — the daemon can assume a role in another account and send traces there. Useful for large organizations where teams own separate accounts but want centralized tracing.

15X-Ray Sampling Rules

X-Ray could trace every single request, but that would cost a fortune (storage, API calls, processing). So it samples — sends only a subset of requests to X-Ray. And the cool part: you can change sampling rules without restarting your application.

💡 New word Sampling — selecting which requests to trace. Reduces cost while still capturing enough data to spot problems.

Default sampling rule

The default samples 1 request per second guaranteed (the "reservoir") to each service, then 5% of everything above that. This balances cost and coverage — you'll always see at least one trace per second per service, but you're not tracing every request.

You can create custom rules targeting specific services, HTTP methods, or URL paths — e.g., sample 100% of POST requests to your payment API while sampling only 1% of GET requests to your static content API.

Good to know: Changing sampling rules in the console takes effect immediately. No restart needed. The daemon fetches the new rules automatically.

17X-Ray with Beanstalk & ECS

Elastic Beanstalk

Beanstalk platforms include the X-Ray daemon already. Just enable it: Configuration → Monitoring → enable X-Ray daemon (or add a config file). Your application still needs to import the X-Ray SDK and instrument its code. The EC2 instance profile needs IAM permission to write to X-Ray (Beanstalk's default role includes this).

ECS: three deployment patterns

On EC2-backed clusters, you can run one daemon per instance (shared by all app containers) or one per app container (sidecar pattern). On Fargate (serverless containers), sidecar is the only option since there's no shared EC2 host.

Three patterns for running X-Ray daemon in ECS. On EC2 you have two choices; on Fargate only sidecar works.

The daemon container listens on port 2000/UDP. Your app container needs the environment variable AWS_XRAY_DAEMON_ADDRESS=xray-daemon:2000 so it knows where to send traces. The two containers must be linked so the app can resolve the daemon's hostname.

18AWS Distro for OpenTelemetry

OpenTelemetry is an open-source standard for distributed tracing and metrics collection. AWS provides its own production-grade implementation (the Distro). Think of it as a modern alternative to X-Ray with more flexibility.

💡 New word AWS Distro for OpenTelemetry — AWS's managed version of the OpenTelemetry project. Similar to X-Ray conceptually but uses open standards, works on EC2/ECS/EKS/Fargate/Lambda/on-premises, and can send traces to multiple destinations simultaneously.

Unlike X-Ray (which only sends to X-Ray), the Distro can send traces and metrics to X-Ray AND CloudWatch AND Amazon Managed Service for Prometheus AND third-party tools like Datadog — all at once. No code changes required to switch destinations.

When to use it: If you want to standardize on open-source APIs, or need to send observability data to multiple backends at once, the Distro is worth considering over X-Ray alone.

19CloudTrail

You've monitored your application's health. You've traced requests. But there's one more thing: who changed what, and when? CloudTrail keeps an immutable record of every API call made in your account — by humans via the console, by CI/CD pipelines via CLI, by Lambda functions, by anyone or anything.

💡 New word CloudTrail — logs every API call made in your AWS account. Always enabled by default. Retains events for 90 days; forward to S3 or CloudWatch Logs for longer retention. Essential for compliance and auditing.
Every API call is logged by CloudTrail. Forward to CloudWatch Logs for real-time analysis or S3 for long-term compliance archival.

Three types of events

TypeOn by default?Examples
Management EventsYesIAM AttachRolePolicy, CreateSubnet, anything that changes config
Data EventsNo (high volume)S3 object-level: GetObject, PutObject, DeleteObject; Lambda Invoke
CloudTrail InsightsNo (opt-in, paid)Anomaly detection: unusual API patterns, policy changes, rate spikes

Event retention and archival

CloudTrail retains events in its own searchable interface for 90 days by default. For longer-term compliance records, forward events to S3 (indefinite storage) and query them later with Athena (SQL-based log analysis). This is the standard pattern: 90 days of hot searchable data, then everything goes to cold S3 storage.

CloudTrail Insights (optional, paid)

An optional add-on that analyzes your normal activity to build a baseline, then flags anomalies: unusual resource provisioning, hitting service limits, bursts of permission changes, gaps in expected activity. Useful for security — tells you when something weird is happening. Insight events also generate EventBridge events so you can auto-respond (page an on-call engineer, etc.).

🏭 In real companies When someone says "we need to comply with SOC 2 / ISO 27001 / HIPAA," the first thing on the compliance checklist is "archive API logs." CloudTrail to S3 is the standard solution, and auditors expect to see it configured before they sign off.

20CloudTrail & EventBridge Integration

Here's a powerful pattern: every API call logged by CloudTrail also appears as an event in EventBridge. This means you can react to specific API calls in near real-time.

Example use cases: get an SNS alert whenever someone calls DynamoDB DeleteTable, or IAM AssumeRole, or EC2 AuthorizeSecurityGroupIngress (opening inbound ports). Instead of waiting 24 hours to review logs, you're notified the moment it happens.

Exam pattern "I want to alert when <specific API call> happens" → Use CloudTrail to log it, route to EventBridge, and trigger SNS/Lambda. This is a classic exam question.

21CloudTrail vs CloudWatch vs X-Ray

All three are about observability, but they answer very different questions.

ServiceAnswersUse it to...
CloudWatch"Is the system healthy? (CPU, latency, errors?)"Monitor application and infrastructure health over time. Set alarms when metrics breach thresholds.
X-Ray"Where exactly in my service mesh did it fail, and why is it slow?"Debug distributed systems. Trace a single request through 10 services and pinpoint which one is the bottleneck.
CloudTrail"Who did what, and when?"Audit API calls. Prove compliance. Investigate security incidents. Detect unauthorized changes.
Mental model: Use CloudWatch for continuous health monitoring. Use X-Ray when you're debugging a specific slow or broken request. Use CloudTrail when you're answering "who changed this resource?" or proving compliance to auditors. Together, they form the three pillars of AWS observability.

📋 Cheat Sheet

The Big Three

  • CloudWatch: Metrics (CPU, latency, custom), Logs (storage + querying), Alarms (threshold-based actions), Dashboards (visualizations).
  • X-Ray: Distributed tracing showing how requests flow through microservices, latency per hop, errors pinpointed to exact service.
  • CloudTrail: Immutable audit log of every API call; retained 90 days by default, archived to S3 for compliance.

CloudWatch Essentials

  • EC2: Free 5-min metrics (CPU, disk, network) → detailed monitoring (1-min) costs extra. Memory is never free; always custom metric.
  • Custom metrics: Push via PutMetricData; accepts timestamps up to 2 weeks in past / 2 hours in future.
  • Logs: Log group (named container) → log streams (per instance/container) → log events (individual lines). Retention policy per group.
  • Unified Agent > old Logs Agent: Sends logs + detailed metrics (RAM, swap, processes). Centrally configurable via SSM Parameter Store.
  • Metric filters: Not retroactive; only count events after creation. Convert log patterns to metrics to drive alarms.
  • Alarms: States = OK / INSUFFICIENT_DATA / ALARM. Targets = EC2 action, ASG action, SNS. Composite alarms combine multiple alarms with AND/OR logic.
  • Synthetics: Scheduled canary scripts (Node.js/Python + headless Chrome) simulate user journeys, catch issues before customers do.

EventBridge Essentials

  • Routes events from sources (EC2 state changes, S3 objects, schedules, CloudTrail API calls) to targets (Lambda, SNS, SQS, Step Functions).
  • Archive + replay: Save events, replay them for debugging or re-testing.
  • Cross-account: Resource-based policies on event bus allow other accounts to send events centrally.

X-Ray Essentials

  • Needs: (1) SDK-instrumented code, (2) X-Ray daemon running (or built-in like Lambda), (3) IAM permission to write.
  • Segments: One component's trace data. Subsegments: finer breakdown. Trace: all segments stitched together = one end-to-end request.
  • Annotations: Indexed, searchable. Metadata: Not searchable. Use annotations for anything you'll filter on.
  • Sampling: Default = 1/sec guaranteed + 5% of rest. Customizable per service/method/path. Changes take effect immediately, no restart.
  • ECS + X-Ray: Daemon per EC2 instance or sidecar per container on EC2; sidecar only on Fargate. Port 2000/UDP. Env var AWS_XRAY_DAEMON_ADDRESS.

CloudTrail Essentials

  • On by default. Management Events logged automatically. Data Events (S3 GetObject, Lambda Invoke) and Insights are opt-in.
  • 90-day retention in CloudTrail interface. Archive to S3 (+ Athena for querying) for long-term compliance.
  • Integration: Every CloudTrail event becomes an EventBridge event → enables real-time alerting on specific API calls.

Decision Tree

  • "Is my app healthy?" → CloudWatch metrics + alarms.
  • "What did my app log?" → CloudWatch Logs + Logs Insights queries.
  • "Why is this request slow?" → X-Ray service map and traces.
  • "Who deleted this resource?" → CloudTrail event history.
  • "React to an event in real-time" → EventBridge.
  • "Simulate user journeys" → CloudWatch Synthetics.
