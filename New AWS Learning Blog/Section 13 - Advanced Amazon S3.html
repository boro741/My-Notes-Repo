1S3 Lifecycle Rules & S3 Analytics

Files sitting in Amazon S3 get older. And older files are accessed less. If you keep everything in the fastest (and most expensive) storage class forever, your bill climbs unnecessarily. Lifecycle rules let you move files between storage tiers automatically on a schedule, or delete them when they're no longer needed.

💡 New word Lifecycle rule — an AWS policy that automatically transitions objects to cheaper storage classes after a certain number of days, or deletes them entirely. It works without you lifting a finger after you set it up.

The Storage-Tier Staircase

S3 offers multiple storage classes, each trading speed for cost. A typical journey looks like this: when a file is brand new, store it in Standard (instant access, highest price). After 60 days, move it to Standard-IA (slower access, cheaper). After 180 days, move it to Glacier Instant Retrieval (much slower, much cheaper). After a year, archive it to Deep Archive (extremely slow, lowest price).

Lifecycle rules move objects rightward through cheaper tiers as they age. Cost drops at each step.

What a Lifecycle Rule Can Do

Every lifecycle rule contains two types of actions, which you can combine:

💡 New word Transition action — moves an object from one storage class to a cheaper one after N days. The object stays; only its tier changes.
💡 New word Expiration action — deletes an object permanently after N days, or cleans up incomplete multi-part uploads. This saves space entirely.

Rules can target the entire bucket, a specific folder path (called a prefix), or only objects with particular tags.

Real-World Example 1: Thumbnails and Source Photos

An app uploads user profile photos and auto-generates thumbnails. Thumbnails can be remade from the original photo if needed, so they're cheap to delete. Original photos need instant access for 60 days (users might edit their profile), then can take up to 6 hours to retrieve (cold storage is fine for old photos users rarely request).

Solution: Store original photos in Standard. Create one lifecycle rule to transition them to Glacier Instant after 60 days. Store thumbnails in a separate folder, keep them in One-Zone-IA (cheaper than Standard-IA, but accepts the risk of single-zone failure), and expire them after 60 days.

Real-World Example 2: Compliance and Deletion Holds

Your company's compliance rule: deleted files must be recoverable for 30 days, but only on request (so Standard-IA speed is acceptable). After 365 days total, delete them permanently.

Solution: Enable S3 Versioning so that deleting a file just marks it deleted but keeps old versions. Then add a lifecycle rule: move non-current (old) versions to Standard-IA after 30 days, move them to Deep Archive after 180 days, and permanently delete all versions after 365 days.

🏭 In real companies Lifecycle rules are the standard way production teams manage logs and backups. A logging system writes gigabytes of logs per day to S3. Without lifecycle rules, your bill is catastrophic. With them, logs roll through Standard (live queries), then Standard-IA (past-week analysis), then Glacier (compliance archive). After a year, delete them. This is so common that many companies automate it with a standard lifecycle policy applied to all new buckets.

Using S3 Analytics to Find the Right Timing

💡 New word S3 Analytics — a tool that watches your bucket's real usage patterns and recommends when to transition files to cheaper tiers. It generates daily CSV reports.

If you're unsure whether to transition files after 30, 60, or 90 days, enable S3 Analytics. It tracks how often files of each age are accessed and suggests the right timing. Fair warning: it only works for Standard and Standard-IA transitions (not for Glacier or Deep Archive). And it takes 24 to 48 hours after you enable it to start showing meaningful data.

2S3 Lifecycle Rules Hands-On

Create a lifecycle rule inside your bucket's Management tab. After naming it and choosing its scope (all objects, or a specific prefix/tag), you select from five core actions:

ActionWhat It Does
Transition current versionsMoves the active version of files through tiers. Example: Standard → Standard-IA after 30 days, then Glacier Instant after 90 days, then Deep Archive after 365 days.
Transition non-current versionsMoves old, replaced versions (only matters if Versioning is on). Example: move to Glacier Flexible Retrieval after 90 days since they're rarely accessed.
Expire current versionsDelete the active version after N days. Example: delete active logs after 700 days.
Expire non-current versionsPermanently remove old versions after N days to free space. Example: delete non-current versions after 700 days.
Delete expired delete markers & incomplete uploadsHousekeeping. Removes leftover temporary data and ghost markers from deleted files.

The AWS Console shows a timeline preview before you save, so you can see exactly when each file version gets moved or deleted. You can chain multiple transitions in one rule — Standard → Standard-IA → Glacier → Deep Archive — all in a single policy.

3S3 Event Notifications

S3 can watch for specific events inside a bucket — file uploaded, file deleted, file restored from archive, replication completed — and send an alert message to another AWS service. You can filter by file type too (e.g., trigger only for .jpg files).

💡 New word S3 Event Notification — S3 sends a message describing what happened in the bucket to a destination service (SNS, SQS, Lambda, or EventBridge). The destination then reacts: processes the file, logs the event, triggers a workflow, etc.

Destinations: Three Direct Paths, Plus EventBridge

You can send notifications directly to SNS (Simple Notification Service — a pub/sub messaging system), SQS (Simple Queue Service — a message queue), or Lambda (serverless code execution). All three paths require a resource-based policy on the destination that grants S3 permission to deliver messages.

S3 notifications can go directly to SNS, SQS, or Lambda. Or send everything to EventBridge for advanced routing and filtering.

💡 New word EventBridge — an event routing service that can receive S3 notifications and forward them to 18+ AWS destinations, with advanced filtering and transformation rules. It's more flexible than the direct SNS/SQS/Lambda paths.

How to Grant Permission

S3 does not use an IAM Role to send event notifications. Instead, the destination resource (SNS topic, SQS queue, or Lambda function) must have its own resource-based policy that explicitly allows S3 to deliver to it. Think of it like a lock on the receiving end.

Common exam trap: Many people mistakenly think S3 needs an IAM Role to send notifications. It doesn't. The destination needs the permission, not S3 itself. If your SNS topic, SQS queue, or Lambda function doesn't have a policy allowing S3 to send messages, the notification will fail silently or throw an error when you try to configure it.
🏭 In real companies Image upload workflows are the textbook use case. User uploads a photo to S3. S3 sends an event to an SQS queue. A background worker listening to that queue picks up the message, resizes the photo into thumbnail and medium versions, and writes them back to S3 — all automatically. Without event notifications, you'd have to poll S3 constantly asking "did anything change?" With them, S3 pushes the change to you.

4S3 Event Notifications Hands-On

Open your bucket's Properties → Event notifications tab. You can either create a direct notification to SNS/SQS/Lambda, or enable the EventBridge integration toggle to stream all events to EventBridge instead.

Step-by-Step: Send a Notification to SQS When Files Are Uploaded

  1. Create an SQS queue first (e.g., DemoS3Notifications).
  2. In your S3 bucket, create an event notification with event type All object create events, and select your SQS queue as the destination.
  3. Before saving, edit the SQS queue's Access Policy to allow S3 to send messages. The policy should permit sqs:SendMessage from the S3 service principal.
  4. Save the notification. AWS will send a test message to confirm the queue is reachable.

Upload a real file to the bucket. Within seconds, a message arrives in the SQS queue describing the upload event, including the object key and timestamp. Your application can now consume that message and react — resize an image, index the filename in a database, whatever you need.

Important: If the SQS queue policy is not set correctly, S3 will reject the notification configuration with an error. AWS validates that S3 has permission before it saves your settings.

5S3 Performance

Understanding Baseline Limits

S3 is designed to handle massive scale. But it has per-prefix limits on request rates. A prefix is the folder path in the object key.

Baseline request rates per prefix:

  • 3,500 PUT / COPY / POST / DELETE requests per second, per prefix
  • 5,500 GET / HEAD requests per second, per prefix

Here's the key insight: there is no limit on how many prefixes you can create. So if you need 10,000 GET requests per second, create two prefixes and balance traffic across them. Problem solved.

💡 New word Prefix — the folder path part of an S3 object key. In the key my-app/logs/2024-01-15/file.log, the prefix is my-app/logs/2024-01-15/. Each prefix gets its own request rate quota.

Speeding Up Large Uploads: Multi-Part Upload

Uploading a 5 GB file over a standard internet connection is slow. Multi-part upload splits the file into smaller chunks and uploads them in parallel.

💡 New word Multi-part upload — S3 feature that breaks a large file into smaller parts, uploads them simultaneously over multiple connections, and reassembles them on the server side. Recommended for files over 100 MB, required for files over 5 GB.

Why it matters: Your laptop might upload one part at a time over a single connection. If that connection drops after uploading 50% of the file, you restart from zero. With multi-part upload, you only re-upload the failed part. Plus, multiple parts upload in parallel, so your effective bandwidth is higher.

Multi-part upload splits one large file into parts, uploads them in parallel, and S3 stitches them back together.

Speeding Up Long-Distance Transfers: S3 Transfer Acceleration

💡 New word S3 Transfer Acceleration — routes your upload or download through the nearest AWS Edge Location using CloudFront's global network, then over AWS's private high-speed backbone to the bucket. Faster for geographically distant uploads.

Imagine you're uploading files from Mumbai to an S3 bucket in Northern Virginia. Standard upload goes over the public internet. Transfer Acceleration routes you through the Mumbai edge location (nearby), then uses AWS's fiber-optic private network (extremely fast) to reach Virginia. Result: much faster transfer, especially for large files.

Transfer Acceleration works with multi-part upload for maximum speed on huge files.

Speeding Up Large Downloads: S3 Byte-Range Fetches

💡 New word S3 Byte-range fetch — requests specific byte ranges of a file (e.g., bytes 0-999, 1000-1999) in parallel GET requests. Downloads specific chunks simultaneously instead of downloading the entire file sequentially.

Real uses: Download a 10 GB video file by requesting bytes 0-1GB, 1GB-2GB, etc. in parallel. Download only the first 100 bytes of a file to read its header without fetching the rest. If a single byte-range request fails, retry only that chunk instead of the entire file.

6S3 Object Tags & Metadata

Two Ways to Label Objects

User-Defined Metadata

Custom key-value pairs you assign to an object during upload. Metadata keys must start with the prefix x-amz-meta- to distinguish them from AWS system metadata (like Content-Length or Content-Type).

Example: x-amz-meta-source: mobile-app or x-amz-meta-user-id: 12345.

Object Tags

Key-value pairs attached to objects independently. Tags are useful for organizing objects, controlling access via IAM policies, and tracking costs.

Example: Project: AlphaRelease, Confidential: True, CostCenter: Engineering.

💡 New word Object tags — AWS-managed key-value labels on S3 objects used for fine-grained IAM access control, lifecycle rule targeting, and cost allocation. They're different from user-defined metadata.

A Critical Limitation: No Built-In Search

Important: S3 cannot search objects by metadata or tag values. There is no built-in "find all objects with Department=Finance" query in S3.

If you need to search objects by tags or metadata, build an external searchable index in a database like Amazon DynamoDB. When uploading a file to S3, also write its key, tags, and metadata to DynamoDB. Your application then queries DynamoDB (which is fast and searchable), gets back matching object keys, and fetches those objects from S3.

S3 itself can't search metadata. Build a separate index in DynamoDB, query it to find matching object keys, then fetch from S3.

📋 Cheat Sheet

Core Concepts

FeatureWhat It Does

Key Facts

  • Lifecycle rules move objects through tiers to reduce cost: Standard → Standard-IA → Glacier Instant → Deep Archive.
  • S3 Analytics generates recommendations but only for Standard ↔ Standard-IA transitions. Takes 24-48 hours to start providing data.
  • Event Notification destinations (SNS, SQS, Lambda) require resource-based policies allowing S3 to deliver messages. S3 itself doesn't need an IAM Role.
  • Performance baseline: 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD requests per second, per prefix. No limit on prefix count.
  • Multi-part upload is recommended for files over 100 MB, required for files over 5 GB.
  • Transfer Acceleration speeds up transfers to buckets in distant regions via Edge Locations.
  • S3 metadata and tags cannot be searched directly. Build an external DynamoDB index to enable searching.

When to Use Each Feature

  • Lifecycle Rules: Managing logs, backups, or any files that get older and cheaper to access over time.
  • Event Notifications: Triggering automated workflows (image resizing, indexing, notifications) when objects are uploaded or deleted.
  • Multi-Part Upload: Uploading files larger than 100 MB where speed and resume capability matter.
  • Transfer Acceleration: Uploading or downloading from geographically distant regions where public internet speed is a bottleneck.
  • Byte-Range Fetches: Downloading large files where parallel chunks and partial header reads save time.
  • Object Tags: Fine-grained access control via IAM, organizing objects, and cost tracking by business unit.
