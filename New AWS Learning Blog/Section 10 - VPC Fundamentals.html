107Section Introduction: Why Networking Matters

Every server you launch on AWS has to live inside a network. Up to now in this course, AWS quietly gave you one for free, without asking. But a real production system can't run on autopilot defaults forever — sooner or later you need to control exactly which servers the internet can reach, and which ones must stay completely hidden. That's the whole job of this section.

This section covers VPC (Virtual Private Cloud), AWS's networking service, at a beginner level. If you're studying for the AWS Solutions Architect or SysOps exams, VPC is a huge, deep topic on its own. For the AWS Certified Developer Associate exam, you only need the big picture — usually just one to three questions touch this topic at all.

By the end of this section, you'll understand subnets, Internet Gateways, NAT Gateways, security groups, network ACLs, VPC Flow Logs, VPC Peering, VPC Endpoints, Site-to-Site VPN, and Direct Connect — and how real engineering teams wire all of it together into one working design.

Relax and take it slow: focus on understanding what each piece does and why it exists. Nobody expects you to memorize exact configuration steps at this stage.

108VPC, Subnets, Internet Gateways & NAT Gateways

Say your company runs a web server and a database on AWS. The web server needs to be reachable by customers on the internet. The database absolutely must not be. If both sit on one open network with no rules between them, a single misconfigured setting is all it takes for a stranger to reach your customer data directly. A VPC is how AWS lets you draw a hard line between "reachable from outside" and "hidden inside."

💡 New word VPC stands for Virtual Private Cloud. It's your own private, isolated network inside AWS, where you decide exactly which servers can be reached from outside and which ones stay hidden.

A VPC always belongs to one AWS Region — a physical geographic area where AWS runs data centers, like Mumbai or Singapore. A VPC you build in Mumbai and a VPC you build in Singapore are two completely separate networks. They never overlap or share anything automatically.

Inside a VPC, you carve out smaller network sections called subnets. Each subnet must live inside exactly one Availability Zone — one specific, physically separate data center location within that Region.

💡 New word Availability Zone (AZ) is one physically isolated data center location inside an AWS Region. Most Regions have three or more AZs, so a failure in one doesn't automatically take down the others.

Subnets come in two flavors, and the difference is exactly the reachability problem from a moment ago. A public subnet can be reached from the internet. A private subnet cannot — nobody outside your VPC can dial straight into it. Web servers usually sit in a public subnet. Databases almost always sit in a private one.

What actually decides whether a subnet counts as "public" or "private" isn't a checkbox somewhere — it's the route table attached to it.

💡 New word Route table is a set of rules attached to a subnet that says where network traffic should go next, based on where it's headed. A subnet only becomes public if its route table sends internet-bound traffic to an Internet Gateway.
💡 New word CIDR (Classless Inter-Domain Routing) is just the notation AWS uses to write an IP address range, like 10.0.0.0/16. A VPC and every subnet inside it each get their own CIDR range, and those ranges can't overlap with each other.
A VPC covers a whole AWS Region. Subnets sit inside specific Availability Zones and are marked as public or private.
Gotcha: AWS creates a default VPC automatically in every Region, and every subnet inside that default VPC is public. That's exactly why the EC2 instances you may have launched earlier in this course were reachable from the internet without you configuring anything at all.
🏭 In real companies Production teams almost never keep using AWS's default VPC once a project gets serious. They build a custom VPC instead — usually through infrastructure-as-code tools like Terraform or AWS CloudFormation — with a deliberate mix of public and private subnets spread across multiple Availability Zones, so the network layout is documented, repeatable, and reviewed like any other code change, not just clicked together once and forgotten.

Internet Gateway: The Door to the Internet

Something has to physically connect your VPC to the internet at all — that's the job of the Internet Gateway.

💡 New word Internet Gateway (IGW) is the component you attach to a VPC to let traffic flow between that VPC and the public internet. Without one attached, nothing inside your VPC can reach the internet, no matter what else you configure.

A subnet only becomes "public" once its route table sends internet-bound traffic to the IGW. Both steps matter: attach the IGW to the VPC, then point a specific subnet's route table at it.

NAT Gateway: Outbound Access Without Being Reachable

Now here's the harder problem. Your database sits in a private subnet on purpose — nobody outside should reach it directly. But that same database server still needs to download security patches and software updates from the internet sometimes. How does a server get outbound internet access without ever becoming reachable from the outside?

💡 New word NAT Gateway (NAT stands for Network Address Translation) is an AWS-managed component that lets servers in a private subnet start connections out to the internet, while blocking anyone on the internet from starting a connection back in.

Traffic only ever flows one way through a NAT Gateway: out, and the reply that comes back — never a fresh connection started from the internet's side. A NAT Gateway itself actually sits inside a public subnet, and every private subnet's route table is pointed at it.

FeatureNAT GatewayNAT Instance
Managed byAWS handles everything (fully managed)You handle it (you manage an EC2 instance)
ScalingScales automaticallyYou must upgrade or scale manually
Main PurposeAllows private subnet servers to download updates from the internet while keeping them safe from incoming internet attacks

AWS also offers an older option called a NAT Instance — a regular EC2 (Elastic Compute Cloud) server configured to do the same job by hand. Almost nobody chooses this anymore; a NAT Gateway is fully managed by AWS, scales on its own, and never needs patching. NAT Instances mostly show up in exams as "the old way," so it's worth recognizing the term if you see it.

Traffic flow: Private Subnet → NAT Gateway (placed in Public Subnet) → Internet Gateway → Internet. Only outbound traffic is allowed.
🏭 In real companies NAT Gateways are the standard real-world mechanism that lets private-subnet servers reach the internet for software updates, without ever being directly reachable from it. Most production VPC designs that include private subnets also include one NAT Gateway per Availability Zone, so a single zone going down doesn't take away every private server's internet access at once.

109Security Groups, NACLs & VPC Flow Logs

Putting a database in a private subnet blocks direct access from the internet. But inside your own VPC, servers can normally still talk to each other freely by default — and that's not always what you want either. AWS gives you two more layers of filtering to control exactly who can talk to what: the Network ACL and the Security Group.

Any traffic reaching an EC2 instance has to pass through both layers, in order: the Network ACL first, guarding the whole subnet, and then the Security Group, guarding that one specific instance.

Incoming traffic must pass through the Network ACL (subnet level) first, and then the Security Group (instance level) before hitting your EC2 server.

Network ACL: Filtering at the Subnet Level

💡 New word NACL (Network Access Control List) is a firewall attached to an entire subnet. Every server inside that subnet is affected by the same NACL rules.

A NACL can do something a Security Group can't: it supports both Allow rules and explicit Deny rules. That matters if you ever need to block one specific troublesome IP address outright, instead of just leaving it out of an allow list.

NACL rules only look at IP addresses, and — this is the part that trips people up — a NACL is stateless. An allowed inbound request does not automatically get an allowed outbound response. You have to write separate rules for traffic going in and traffic going out.

Gotcha: the default NACL that ships with every VPC allows all inbound and outbound traffic by default. If you've never had to touch NACLs directly in this course so far, that's why — your Security Groups were doing all the actual filtering the whole time.

Security Group: Filtering at the Instance Level

💡 New word Security Group is a firewall attached directly to an EC2 instance — technically to its network card, called an ENI (Elastic Network Interface). It controls exactly what traffic can reach that one server.

Unlike a NACL, a Security Group supports Allow rules only — there's no explicit deny. Anything not allowed is simply blocked by default. It can filter by IP address, or by pointing at another Security Group entirely, which is handy when you want "anything running in my application tier" to reach "my database," without hardcoding IP addresses that might change later.

A Security Group is also stateful: if you allow a request in, the reply is automatically allowed back out. You don't have to write a matching outbound rule for every inbound one.

FeatureSecurity GroupNetwork ACL (NACL)
Where it worksInstance / Network Interface (ENI) levelSubnet level
Rule types allowedAllow rules onlyBoth Allow and Deny rules
State memoryStateful (reply traffic is auto-approved)Stateless (must configure inbound and outbound separately)
Rules can targetIP addresses or other Security GroupsIP addresses only
🏭 Why this matters — a real incident Section 4 of this course covered the 2019 Capital One data breach from the IAM (Identity and Access Management) angle: an AWS role with far more access than it needed. This is the network-layer side of that same story. The attacker reached Capital One's internal systems through a misconfigured web application firewall running on an EC2 instance, using a technique called SSRF (Server-Side Request Forgery) to trick that server into fetching its own role's temporary credentials from AWS's internal metadata service. Tight Security Groups and properly segmented private subnets don't make an application bug impossible — but they shrink how much damage one compromised server can do, which is exactly the point of network segmentation.

VPC Flow Logs: Recording Every Connection

Say a request is mysteriously failing, and you can't tell whether it's being blocked by a Security Group, a NACL, or something else entirely. You need a record of what actually happened on the wire. That's what VPC Flow Logs are for.

💡 New word VPC Flow Logs record metadata about every bit of network traffic moving through your VPC, a specific subnet, or one network interface — where it came from, where it went, and whether it was accepted or rejected.

You can enable Flow Logs for AWS services too, not only plain EC2 instances — things like load balancers, RDS (Amazon Relational Database Service) databases, and ElastiCache (a managed in-memory caching service) all support them. The logs themselves can be sent to Amazon S3 (Simple Storage Service), CloudWatch Logs, or Kinesis Data Firehose for further processing.

Exam tip: whenever a question describes debugging a network block, or explaining why traffic was denied, the answer is VPC Flow Logs.

110VPC Peering, VPC Endpoints, VPN & Direct Connect

VPC Peering: Connecting Two VPCs Privately

Say your company has one VPC for a shared internal analytics platform, and a separate VPC for a product team's application. The application team wants to send data to analytics, but nobody wants that traffic to leave AWS's private network and touch the public internet at all. VPC Peering solves exactly this.

💡 New word VPC Peering is a private connection between two VPCs that lets servers in each one talk to the other directly, over AWS's own internal network, as if they were on the same network.

Two rules matter here. First, the two VPCs being peered can't have overlapping CIDR ranges — AWS can't route traffic correctly if both networks claim the same IP addresses. Second, and easy to miss: peering is not transitive. If VPC A is peered with VPC B, and VPC B is peered with VPC C, that does not mean A can reach C. A and C would need their own separate, direct peering connection.

VPC Peering is non-transitive. To connect every VPC together, each pair needs its own separate peering setup.
Gotcha: non-transitive peering catches people constantly. Peering connections don't chain together automatically — every pair of VPCs that needs to talk to each other needs its own direct peering connection.
🏭 In real companies Companies that split work across many AWS accounts — one per team, or one per environment — end up needing a lot of these direct connections fast. Once that gets unwieldy, most move to a separate AWS service called Transit Gateway, which acts as a central hub, so every VPC only needs one connection — to the hub — instead of one connection per peer. That's a more advanced topic for later, but it exists specifically because plain VPC Peering doesn't scale past a handful of VPCs.

VPC Endpoints: Reaching AWS Services Without the Public Internet

Your private-subnet server needs to read a file from Amazon S3. Normally, calling S3 means the request leaves your VPC, crosses the public internet, and comes back — even though both your server and S3 are already inside AWS. A VPC Endpoint skips that trip entirely.

💡 New word VPC Endpoint is a private connection from your VPC straight to an AWS service, staying entirely inside AWS's own network instead of going out over the public internet.

There are two kinds, and which one you need depends on the service:

Endpoint TypeSupported AWS ServicesHow it attaches
Gateway EndpointAmazon S3 and DynamoDB onlyAdded directly to your route table
Interface EndpointMost other AWS services (like CloudWatch, EC2 API)Uses a private network card (ENI) inside your subnet

A Gateway Endpoint gets added straight into your route table, since S3 and DynamoDB are old enough AWS services to support that simpler mechanism. Everything else uses an Interface Endpoint, which shows up as its own network interface — that same ENI concept from Security Groups — sitting inside your subnet.

With a VPC Endpoint, your private EC2 instance accesses AWS services safely without going over the public internet.
Exam tip: if a question asks how to reach an AWS service from a private subnet without touching the public internet, the answer is a VPC Endpoint.
🏭 In real companies This isn't just a security nicety — it's also a cost decision. Traffic routed out through a NAT Gateway is billed per gigabyte processed. Traffic to S3 or DynamoDB through a Gateway Endpoint is not. Teams moving meaningful volumes of data to S3 from private subnets often add Gateway Endpoints specifically to cut their NAT Gateway bill, on top of the security benefit.

Connecting Your Own Data Center to AWS

Not every server lives in AWS. Plenty of companies still run real hardware in their own office or data center, and need it to talk to their AWS VPC securely. There are two standard ways to do that.

💡 New word Site-to-Site VPN (Virtual Private Network) creates an encrypted tunnel between your on-premises network and your AWS VPC, running over the ordinary public internet.
💡 New word Direct Connect is a dedicated, private physical cable connection between your data center and AWS that never touches the public internet at all.
FeatureSite-to-Site VPNAWS Direct Connect (DX)
Network PathRuns over the public internet using encryptionDedicated private physical cable line
Setup TimeTakes just a few minutesTakes about 1 month to set up physically
Security LevelEncrypted tunnel over the internetPrivate cable line (never touches the public internet)
Best Used ForQuick setup, short-term needs, lower costHigh-speed, reliable production connections with stable speed
VPN provides quick encrypted access over the internet. Direct Connect gives a private physical cable for maximum performance.
🏭 In real companies The trade-off is speed of setup versus long-term stability. A Site-to-Site VPN can be running within minutes, and is the standard starting point or a solid choice for lighter, less critical traffic. Direct Connect takes roughly a month to physically provision the cable, so companies typically only invest in it once they have a steady, heavy, latency-sensitive flow of data between their own data center and AWS — a large enterprise migrating a big on-premises system gradually, for example — where a stable dedicated line pays for itself over time.

112Putting It Together: Three-Tier Architecture

Everything in this section — public and private subnets, Internet Gateways, NAT Gateways, security groups — exists to build one standard shape. It's called the three-tier architecture, and it's one of the most well-documented, widely used network designs in the entire tech industry, not just on AWS.

🏭 In real companies This exact three-tier pattern — a public subnet for load balancers, a private subnet for application servers, and a further-isolated private subnet for the database — is the default secure network layout taught and used across the industry. If you understand this one diagram, you understand the reasoning behind almost every VPC design you'll come across.
3-Tier Design: Public Load Balancer → Private Application Servers → Private Database & Cache Layer.

Here's how a request actually flows through it, tier by tier.

  1. Tier 1 — Web tier: a user's request goes through Route 53, AWS's DNS (Domain Name System) service — essentially the internet's phonebook, turning a web address into a real network location. Route 53 points to an Elastic Load Balancer (ELB) sitting in a public subnet, spread across multiple Availability Zones.
  2. Tier 2 — Application tier: the load balancer spreads incoming requests across a group of EC2 servers, managed by an Auto Scaling Group that adds or removes servers automatically as demand changes. These servers sit in private subnets — nobody from the internet can reach them directly.
  3. Tier 3 — Data tier: a separate, even more isolated private subnet holds the actual data — an Amazon RDS database, often with an ElastiCache in-memory cache in front of it to serve frequent reads faster.
Exam tip: "public load balancer → private application servers → private database subnet" is the single most common architecture shown in scenario-based exam questions. Recognize this shape instantly.

A Concrete Example: The LAMP Stack

One classic way to build the application tier is the LAMP stack — a set of technologies that have been running production web apps since long before AWS even existed.

LetterTechnologyRole
LLinuxOperating system running on the EC2 server
AApacheWeb server handling HTTP requests
MMySQLDatabase for app data (e.g. running on Amazon RDS)
PPHPProgramming language for application code

You can drop ElastiCache in front of the database to cache frequently requested data, and attach EBS (Elastic Block Store) volumes to each EC2 instance for local storage.

A Real Complication: WordPress on AWS

WordPress follows this same app-tier-plus-database-tier shape, with one added wrinkle: once you run more than one WordPress server for redundancy, they all need to share the same uploaded images and media files. If each server only kept its own local copy, a photo uploaded through one server would simply be missing on the others.

💡 New word Amazon EFS (Elastic File System) is a shared network file system that multiple EC2 instances can mount and read from at the same time, across different Availability Zones.

That's exactly what solves the WordPress problem: every WordPress server mounts the same EFS file system, so uploaded media is visible to all of them immediately, no matter which server originally received the upload.

All WordPress EC2 servers share uploaded images from a central Amazon EFS file system.

📋 Cheat Sheet

Core Building Blocks

ConceptPlain-English meaning
VPCYour own private network inside AWS, scoped to one Region.
SubnetA slice of a VPC's IP range, living inside exactly one Availability Zone. Public or private.
Internet GatewayConnects a VPC to the public internet. Required before any subnet can be public.
NAT GatewayLets private-subnet servers reach the internet outbound, without being reachable from it.
Route TableRules deciding where a subnet's traffic goes next.

Key Facts Worth Remembering

  • A VPC spans a whole Region. A subnet lives inside exactly one Availability Zone.
  • The default VPC in every Region contains only public subnets.
  • Security Groups are stateful (reply traffic is auto-allowed). NACLs are stateless (inbound and outbound must both be configured).
  • Security Groups support Allow rules only. NACLs support both Allow and Deny.
  • VPC Peering is never transitive — every pair that needs to talk needs its own direct connection.
  • Gateway Endpoints only work for S3 and DynamoDB. Everything else uses an Interface Endpoint.
  • VPC Flow Logs are the answer whenever a question is about debugging blocked network traffic.
  • Site-to-Site VPN sets up in minutes over the internet. Direct Connect takes about a month to lay a private physical line.

The One-Paragraph Version

A VPC is your private network inside one AWS Region, divided into public and private subnets across Availability Zones. An Internet Gateway lets public subnets reach the internet; a NAT Gateway lets private subnets reach out without being reachable from outside. Security Groups filter traffic per instance and remember state; NACLs filter per subnet, allow explicit denies, and forget state between requests. VPC Flow Logs record what actually happened on the wire. VPC Peering and VPC Endpoints connect VPCs and AWS services privately, while Site-to-Site VPN and Direct Connect connect your own data center to AWS. Put together with public load balancers, private application servers, and a further-isolated private database subnet, that's the three-tier architecture — the standard shape behind most production AWS networks.
