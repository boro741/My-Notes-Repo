1Serverless Introduction

The word "serverless" is misleading. There are always servers somewhere. What it means is that you don't see them, don't manage them, don't pay for them when they're idle, and don't get paged at 3 AM because one fell over. Originally serverless meant Lambda. Now it describes any AWS service where you hand off a task and AWS handles the infrastructure — databases, queues, storage, all of it.

💡 New word Serverless means you never provision or manage servers. You write code (or use a fully managed service), tell AWS what should trigger it, and AWS scales and runs it for you. You pay only for what you actually use.
A typical serverless architecture: static files from S3 and CloudFront, authentication through Cognito, a REST API fronted by API Gateway invoking Lambda functions, which read and write to DynamoDB. Not a single server in sight.

Other serverless services mentioned in this course include SQS for reliable queues, SNS for message broadcasting, Kinesis Data Firehose for data streaming, Aurora Serverless for variable-load databases, Step Functions for workflow orchestration, and Fargate as the serverless option for container workloads.

2Lambda Overview & First Hands-On

Lambda is AWS's compute service for code that runs on demand. You upload a function, AWS provisions the runtime, and the function executes when something triggers it — whether that's an API request, an event from another service, a schedule, or an explicit invocation. You pay per request and per millisecond of execution. Nothing runs when nothing's happening.

💡 New word Lambda is a serverless compute service where you upload code, configure triggers, and AWS executes it on demand without you managing any infrastructure. It's called a "function" — a discrete unit of code, not a running process.

Here's how Lambda differs from EC2, the traditional compute alternative:

EC2Lambda
ServersYou provision them; they run continuously whether used or notNo servers to manage; AWS invokes your code only when needed
ScalingManual or via Auto Scaling Groups — you set policiesFully automatic; AWS scales without any configuration
BillingCharged while the instance is running, even if idleCharged only during actual execution, in 1-millisecond increments
Execution timeNo limit; runs as long as you needMaximum 15 minutes per invocation

Pricing that makes sense

AWS gives you a free tier that covers 1 million requests per month, plus 400,000 GB-seconds of compute time. After that, you pay $0.20 for every million requests, plus a small fee for execution time based on memory. The more RAM you allocate, the more CPU you get implicitly — it's usually still far cheaper than running an EC2 instance that sits idle most of the time.

Languages and runtimes

Lambda supports Node.js, Python, Java, C# with .NET Core, and Ruby out of the box. You can also use Rust, Go, and others through a custom runtime API. For truly complex workloads, you can package your function as a container image, even a 10 GB one.

Memory and CPU

You choose how much RAM your function needs — anywhere from 128 MB to 10 GB. AWS doesn't let you pick CPU separately; instead, more RAM means more vCPU. At 1,792 MB, you get one full vCPU. Beyond that, you can use multi-threading to benefit from the extra cores.

Two classic patterns

A common pattern is serverless thumbnail generation: someone uploads an image to S3, S3 triggers a Lambda function, the function generates a thumbnail, uploads it back to S3, and writes metadata to DynamoDB. All happens invisibly; no server was ever waiting for work.

Another is serverless cron: instead of running an EC2 instance 24/7 to execute a job once an hour, use EventBridge to trigger a Lambda function on a schedule. The function runs when it's needed; the rest of the time, AWS isn't charging you anything.

🏭 In real companies Companies like Netflix, Pinterest, and Slack run millions of Lambda invocations per day. Entire services — recommendation engines, background job processing, event handling — are built entirely on Lambda because the scaling is automatic and the cost tracks actual usage instead of peak-time provisioning.

Getting started: the console walkthrough

Create a function from a blueprint (AWS provides templates), assign it an execution role (like an EC2 instance role, but for Lambda), test it in the console with sample JSON events, and watch the logs appear in CloudWatch Logs. That execution role is crucial — it determines what the function is allowed to access. The basic role only lets it write logs.

3Synchronous Invocations

When a Lambda function is invoked synchronously, the caller waits for the result. The caller sends the request, Lambda runs the code, and the caller receives the response immediately. If something goes wrong, the caller sees the error and must decide what to do about it — retry, backoff, fail the whole request, whatever.

💡 New word Synchronous invocation means the caller waits right there for the result. Lambda runs your code and hands back the response (or error). The caller is responsible for handling any failures.

The services that invoke Lambda this way include the CLI and SDK (when you run a function from your terminal or application code), Application Load Balancer, API Gateway, and CloudFront (for Lambda@Edge). When you click the "Test" button in the Lambda console, that's also a synchronous invocation — you wait for the result JSON to appear on your screen.

Synchronous flow: the caller sends an invoke request, waits, and receives back the result (success or error). The caller must handle any failures or retries itself.
Testing a Lambda function from the console or via aws lambda invoke is itself a synchronous invocation. You see the response immediately — either the JSON output or an error.

4Lambda & Application Load Balancer

If you already run an Application Load Balancer (ALB) and want to add Lambda-backed endpoints without introducing API Gateway, you can register a Lambda function directly as a target in an ALB target group. The ALB translates incoming HTTP requests into JSON for Lambda, and translates Lambda's JSON responses back into real HTTP responses.

💡 New word Application Load Balancer (ALB) is a Layer 7 load balancer for HTTP(S) traffic. It can distribute requests to EC2 instances, containers, or Lambda functions.
The ALB translates HTTP (method, path, query string, headers, body) into a JSON event structure; Lambda responds with JSON (statusCode, headers, body, isBase64Encoded); the ALB translates it back to HTTP.

Your Lambda response must include statusCode, headers, body, and isBase64Encoded. Always set the Content-Type header — for example, text/html — so the browser renders the body instead of downloading it as a file. There's also a target group setting for multi-value headers that preserves repeated headers and query string parameters as arrays instead of throwing away all but one.

The ALB is granted permission to invoke your Lambda function automatically — AWS adds a resource-based policy to the function visible under Configuration → Permissions.

5Asynchronous Invocations & DLQ

Some services don't have the luxury of waiting for a response. When S3 finishes uploading a file, it doesn't sit around waiting for a Lambda function to finish processing it. Instead, S3 sends the event to an internal queue inside Lambda, and AWS handles the function invocation on its own schedule. The caller (S3) immediately gets back an HTTP 202 "Accepted" response and moves on.

💡 New word Asynchronous invocation means the caller sends the event and does not wait. Lambda queues it internally, invokes the function, and if something goes wrong, retries automatically. The caller never sees the result or error directly.
Asynchronous flow: events queue internally. Lambda retries automatically (immediately, then after 1 minute, then after 2 more minutes). If all retries fail, the event lands in a DLQ for manual inspection.

Because AWS retries automatically, your function must be idempotent. That means processing the same event twice should produce the same result. Duplicate log entries and duplicate processing are expected behavior, not bugs — that's just how async systems work.

💡 New word Idempotent means running the same operation twice produces the same outcome as running it once. In Lambda, this is critical for async functions because AWS retries automatically.

Services that invoke Lambda asynchronously include S3 event notifications, SNS, and EventBridge. Set up a DLQ (Dead-Letter Queue) — either SQS or SNS — to catch events that fail even after all retries. Configure the number of retry attempts (0, 1, or 2) in the function's asynchronous invocation settings. The failed message includes the error cause and request ID for debugging.

When you test an asynchronous function from the console, it always returns 202 (Accepted), whether the function ultimately succeeds or fails. You can't tell from that response alone. Instead, check CloudWatch Logs or look in the DLQ to see what actually happened.

6Lambda & EventBridge

EventBridge is an event bus that can be triggered on a schedule or in response to patterns of events. Attach a Lambda function as a target, and EventBridge will invoke it asynchronously whenever the schedule fires or the pattern matches.

Two common scenarios: create a rate-based schedule (e.g., every hour, every minute for testing) with Lambda as the target, or create a rule that matches specific event patterns like CodePipeline state changes. EventBridge automatically creates an execution role allowing it to invoke the Lambda function. The event it passes includes metadata like the schedule's source, your AWS account, the region, and the resource that triggered it.

Set up a test schedule (like 1-minute intervals) to verify your function works — then disable it immediately. An active 1-minute schedule will invoke your function forever and could rack up a bill.

7Lambda & S3 Event Notifications

When something happens to an object in S3 — an upload, a delete, any modification — S3 can notify interested services. Those notifications can go to SNS (for broadcasting to multiple subscribers), SQS (for Lambda to poll), or directly invoke a Lambda function asynchronously.

S3 events typically arrive within seconds, but are not guaranteed to be immediate. If two writes to the same object happen at the exact same instant, you might only get one notification instead of two — that's a limitation of S3's event delivery model. If you need to catch every event without gaps, enable bucket versioning so each write creates a new version and generates its own notification.

🏭 In real companies Image processing pipelines commonly use this pattern: photo uploads trigger Lambda via S3 events, Lambda generates thumbnails and variations, uploads them back to S3, and writes metadata to DynamoDB. The whole flow is event-driven and serverless, with no servers waiting idle between uploads.

Set up an S3 bucket event notification (for example, on all object-create events) targeting a Lambda function directly. S3 is granted invoke permission via a resource-based policy automatically added to the Lambda function. The event payload includes the bucket name, region, object key, size, and ETag — enough for your function to call GetObject and process the file.

8Event Source Mapping

The third invocation category covers sources where Lambda must actively poll for records: Kinesis Data Streams, SQS (both standard and FIFO), and DynamoDB Streams. Because these are streaming sources, Lambda needs a piece called the Event Source Mapping — a background worker that constantly polls the source, batches up records, and invokes your function synchronously with each batch.

💡 New word Event Source Mapping is the AWS component that polls streaming sources (Kinesis, SQS, DynamoDB Streams) and invokes your Lambda function synchronously with batches of records. It's invisible but essential for streaming patterns.
The Event Source Mapping polls the stream or queue continuously, batches records, and synchronously invokes Lambda with each batch. Lambda processes the batch and returns.

Streams (Kinesis, DynamoDB Streams)

A stream has shards; each shard maintains an iterator that reads records in order. One Event Source Mapping per shard reads records (starting from new, from the beginning, or from a specific timestamp). The key constraint is ordering: within a single shard, records are processed in order. You can run up to 10 parallel batch processors per shard, but once you do, ordering guarantee moves down to the partition key level, not the whole shard.

If your function fails processing a batch, the entire batch is retried by default — this can block a shard while retrying the same batch over and over. Mitigation strategies include discarding old events, limiting retry attempts, splitting the batch on errors, or routing failed records to a separate destination.

Queues (SQS Standard and FIFO)

Lambda polls SQS using long polling, pulling 1–10 messages per request. A critical piece of tuning: set the queue's visibility timeout to at least 6× the Lambda function's timeout. If your Lambda function times out before it finishes, the message becomes visible again and another process might pick it up, causing duplicate processing.

Standard SQS has no ordering guarantee but scales extremely fast — Lambda can add up to 16 new instances per minute, up to 1,000 concurrent batch processes. Occasionally the same message might be received twice even without an error.

FIFO SQS maintains strict order per message group ID, which means Lambda scales only to the number of active message groups — much slower than Standard, but order is guaranteed.

DLQ for SQS-sourced Lambda is configured on the SQS queue itself, not on Lambda. That's because this is a synchronous invocation (the event source mapping is doing the invoking). If you want to capture failures, either set up SQS's own DLQ or use a Lambda Destination instead.

9Event & Context Objects

Every Lambda function receives two objects inside its handler function: event and context. Understanding what each contains is crucial.

ObjectWhat it contains
eventThe actual data from the invoking service. JSON is automatically converted to a native object (Python dict, JavaScript object, etc.). This is the payload your function processes.
contextMetadata about the invocation itself: the AWS request ID, the function name and ARN, memory limit, CloudWatch log group and stream names, remaining execution time. Used for internal plumbing, not data processing.

On the exam, if a question asks "where would I find X" — data about what triggered the event → event; data about the function's own execution environment → context.

10Lambda Destinations

Lambda Destinations are a newer pattern (introduced in November 2019) for routing the result of an invocation somewhere else. They're like an enhanced version of DLQs — where DLQs only capture failures, Destinations can capture both success and failure, and send them to richer targets.

DLQDestinations
CoversFailures onlyBoth success and failure
Target optionsSQS, SNSSQS, SNS, another Lambda, EventBridge
Applies toAsynchronous invocationsAsynchronous invocations (success/failure) and Event Source Mapping (discarded batches)

Configure separate success and failure destinations in the function's asynchronous invocation settings. The success message includes the full request context and response payload. The failure message includes the error cause, invocation count, the record that caused the failure, and a stack trace — way more information than a DLQ message alone.

Destinations let you route successful and failed invocations to SQS, SNS, another Lambda, or EventBridge. Much richer than DLQs, which only capture failures and support SQS/SNS.

11Permissions: IAM Roles & Resource Policies

Permissions for Lambda break into two directions. An execution role is what Lambda uses when calling outward — it determines what AWS services and resources the function can touch. A resource-based policy is what controls inbound access — it says who is allowed to invoke this Lambda function.

💡 New word Execution role is an IAM role that Lambda assumes when your function runs. It controls what your code is allowed to do — read S3, write to DynamoDB, call other AWS APIs. It's outbound permission.
💡 New word Resource-based policy is a policy attached directly to the Lambda function that says who can invoke it. S3, SNS, EventBridge, ALB — if they invoke your function, this policy grants them permission. It's inbound permission.
Execution RoleResource-Based Policy
DirectionLambda → other AWS services (Lambda is the caller)Other accounts/services → Lambda (Lambda is the callee)
Use caseReading from SQS, Kinesis, DynamoDB Streams; calling S3 GetObject, writing to DynamoDBS3, SNS, EventBridge invoking your function; cross-account access
Common managed policiesAWSLambdaBasicExecutionRole (CloudWatch Logs), AWSLambdaKinesisExecutionRole, AWSLambdaDynamoDBExecutionRole, AWSLambdaSQSQueueExecutionRole, AWSLambdaVPCAccessExecutionRole, AWSXRayDaemonWriteAccess—

Best practice: create one execution role per function, scoped to only what it needs. This embodies the principle of least privilege — a function that only reads from S3 shouldn't have DynamoDB write permissions.

🏭 In real companies When a function is invoked by S3 or EventBridge, AWS automatically creates resource-based policy statements. When a function polls SQS, no resource policy is needed — the execution role grants permission to poll. Understanding which is which prevents hours of debugging "Access Denied" errors.

12Environment Variables

Environment variables are key-value string pairs that let you adjust function behavior without touching the code. Change an environment variable from dev to prod, and the function behaves differently on the next invocation — no redeployment needed.

Lambda injects its own system environment variables alongside yours. For secrets — API keys, database passwords — you can encrypt values with KMS. Either use the Lambda service's own key, or bring your own customer-managed key. The function needs kms:Decrypt permission to read encrypted values.

13Monitoring & X-Ray Tracing

Lambda logs automatically to CloudWatch Logs (as long as the execution role has logs:CreateLogGroup and logs:PutLogEvents permission — the basic execution role includes these). Metrics appear in CloudWatch: invocations, duration, concurrent executions, errors, success rate, throttles, async delivery failures, and for stream-based sources, iterator age (how far behind you are in reading a stream).

For deeper visibility, enable X-Ray Active Tracing in the function's configuration. AWS starts the X-Ray daemon for you. You still need the X-Ray SDK in your code and the AWSXRayDaemonWriteAccess permission. Once enabled, you can see the service map in the X-Ray console — which calls succeeded (green) and which failed (red), with full stack traces per request.

Enabling X-Ray tracing plus attaching S3 read permissions lets you see in the X-Ray service map exactly which API calls succeeded and which failed — incredibly useful for debugging integrations with other AWS services.

14Lambda@Edge & CloudFront Functions

Both Lambda@Edge and CloudFront Functions let you run code at AWS edge locations, close to users, either before or after a request reaches your origin. They're for global-scale logic: request modification, URL rewriting, JWT validation, A/B testing, DDoS protection.

💡 New word Lambda@Edge lets you run Node.js or Python Lambda functions at CloudFront edge locations. It's invoked synchronously for viewer and origin requests/responses with up to 10 seconds execution time.
CloudFront FunctionsLambda@Edge
LanguageJavaScript onlyNode.js, Python
ScaleMillions of requests per secondThousands of requests per second
Trigger pointsViewer request / response only (2 hooks)Viewer request/response + origin request/response (all 4 hooks)

Lambda@Edge functions must be authored in us-east-1 and are automatically replicated globally by CloudFront. CloudFront Functions are lighter-weight and faster but much more limited in what they can do.

15Lambda in a VPC

By default, Lambda runs in an AWS-owned VPC isolated from your own. If your function needs to reach resources in your VPC — a private RDS database, ElastiCache, an internal ALB — you must explicitly attach Lambda to your VPC by specifying subnets and a security group. Lambda then gets an Elastic Network Interface (ENI) in each subnet, allowing it to reach private resources.

💡 New word Elastic Network Interface (ENI) is a virtual network card with a private IP address. When Lambda attaches to a VPC, it gets an ENI so it can reach other resources in that VPC.
When attached to a VPC, Lambda gets an ENI and can reach private resources. To access the internet, it needs a NAT gateway in a public subnet. For AWS service access without internet, use VPC Endpoints.
Critical exam point: unlike EC2, deploying a Lambda function in a public subnet does NOT give it internet access or a public IP. To reach the internet from a VPC-attached Lambda, deploy it in a private subnet with a NAT gateway or instance in a public subnet.

VPC-attached Lambda requires the AWSLambdaVPCAccessExecutionRole so the function can create and manage ENIs. CloudWatch Logs still work from inside a VPC with no NAT or endpoint needed — AWS has internal routes for that. But external APIs require a NAT gateway, and AWS services like DynamoDB can be accessed privately via VPC Endpoints, saving the NAT gateway cost.

🏭 In real companies Many teams attach Lambda to a VPC for data isolation — all traffic stays internal, never touches the public internet. VPC Endpoints for S3 and DynamoDB eliminate NAT gateway costs while maintaining privacy. This is standard practice in regulated industries like finance and healthcare.

16Function Performance

You control two main settings for Lambda function performance: memory and timeout.

SettingRangeDetails
Memory (RAM)128 MB – 10,240 MB (10 GB)More RAM means more implicit vCPU. At 1,792 MB, you get one full vCPU. Beyond that, multi-threading lets you use extra cores.
Timeout3 seconds (default) – 900 seconds (15 minutes)Any workload needing longer than 15 minutes doesn't belong in Lambda; use Fargate/ECS/EC2 instead.
💡 New word Execution context is Lambda's runtime environment for your code. It includes the runtime itself, your code, any libraries, and initialized global state. AWS reuses contexts between invocations when possible to improve performance.

Reusing execution contexts for speed

Lambda keeps a temporary runtime environment ("execution context") alive between invocations. If your next invocation happens while a context is still warm, your code starts immediately. That's why initializing expensive things outside the handler function matters — database connections, HTTP clients, SDK objects, dependency loading — all happen once per context, not once per invocation. Put them outside the handler, and warm invocations reuse them.

Code inside the handler runs every invocation. Code outside the handler (but inside your function file) runs once per execution context and is shown as "Init Duration" in logs. Put anything slow to set up outside the handler.

Ephemeral storage: /tmp

Lambda provides up to 10 GB of ephemeral disk space at /tmp. It's persisted while the execution context is alive (so it can be reused across warm invocations) but deleted once the instance is destroyed. Useful for large temporary files or cache; for real persistence, use S3. There's no built-in encryption — if you need to encrypt files in /tmp, use KMS yourself.

17Lambda Layers

Lambda Layers solve two problems: they let you add custom runtimes (for languages AWS doesn't support natively), and much more commonly, they let you externalize heavy dependencies so you don't repackage them with every code change.

💡 New word Lambda Layers are packages of code or libraries that get automatically extracted into the function's runtime at startup. Multiple functions can share layers, reducing code duplication and deployment time.
Heavy, slow-changing dependencies live in shared layers. Multiple functions reference them, reducing code duplication and deployment time. Only the small app code changes frequently.

You can attach up to 5 layers per function, with 250 MB total size limit. AWS provides pre-built layers for common libraries like Pandas, Requests, and the AWS SDK. Layers are immutable once created and can be versioned.

🏭 In real companies Teams with dozens of Lambda functions use layers to share custom utilities, pre-built libraries, and vendored dependencies. Updating a layer in one place and instantly having all functions use the new version is far cleaner than redeploying everything.

18File System Mounting (EFS)

A VPC-deployed Lambda function can mount an Amazon EFS (Elastic File System) file system to a local directory at startup. This is useful if you need a shared file system across multiple function invocations or instances.

Each concurrent Lambda instance opens its own EFS connection. With many instances spinning up at once, you can hit EFS connection limits or connection burst limits. Plan accordingly.

19Concurrency & Cold Starts

Lambda scales automatically by creating new instances. Every AWS account gets a default pool of 1,000 concurrent executions shared across all functions in a region. If you hit the limit, new invocations get throttled — synchronous ones get a 429 error immediately; asynchronous ones retry automatically and eventually land in the DLQ.

💡 New word Reserved concurrency is a per-function cap on how many instances can run simultaneously. It protects important functions from being starved by other functions using the shared account pool.
💡 New word Cold start is the extra latency your function experiences when Lambda has to create a fresh execution environment — load the runtime, load your code, run initialization code. Warm invocations reuse a cached environment and skip this overhead.
Without reserved concurrency set, one function hammering the shared pool can throttle every other function in your account. Set reserved concurrency deliberately on important, production functions to protect them from noisy neighbors.

Provisioned concurrency: pre-warming instances

Cold starts add latency. For a user-facing API, 500ms cold start is unacceptable. Provisioned concurrency pre-allocates warm instances ahead of traffic, so no request ever pays the cold start cost. It can be managed manually or automatically via Application Auto Scaling (based on schedule or target tracking). However, provisioned concurrency can only be applied to a published version or alias, not $LATEST.

A cold start happens once per execution context: load the runtime, load code, run initialization. Provisioned concurrency pre-warms instances so no request pays that cost.
VPC cold starts used to be a major performance problem but were dramatically improved by AWS in late 2019. They're no longer a blocker for most workloads.

20External Dependencies

If your function needs libraries, package them alongside your code: node_modules for Node.js (managed by npm), pip-installed packages for Python, or .jar files for Java. Zip everything together. If the zip is under 50 MB, upload it directly; otherwise upload to S3 first and reference it from there.

Native libraries (anything compiled from C, C++, etc.) must be compiled on Amazon Linux to work in Lambda. Use Lambda Layers to externalize large, rarely-changing dependencies so you don't repackage them every time your actual code changes.

The AWS SDK comes bundled with every Lambda runtime already — no need to package it yourself if that's all you need.

21Lambda & CloudFormation

You can define Lambda functions inside CloudFormation templates in two ways. Inline code (using Code.ZipFile) puts the code directly in the template — fine for simple functions but no dependencies. For anything with dependencies, store the zip in S3 and reference it via S3Bucket, S3Key, and optionally S3ObjectVersion.

If you update the zip in S3 but don't change the S3ObjectVersion in the template, CloudFormation won't detect the update and won't redeploy the function. Enable bucket versioning and bump the object version reference to force an update.

For cross-account deployment, attach a bucket policy on Account 1's S3 bucket allowing Accounts 2 and 3 to read from it, and give each account's CloudFormation an execution role with Get/List permissions on that bucket.

22Lambda Container Images

Lambda can also be deployed as a container image from ECR — up to 10 GB, compared to the 250 MB unzipped limit for zip deployments. This is useful for functions with huge dependency sets or for unifying your build/deploy workflow across ECS and Lambda.

The container must implement the Lambda Runtime API. AWS provides base images for Python, Node.js, Java, .NET, Go, Ruby. You can also build your own. Test locally with the Lambda Runtime Interface Emulator.

Container best practices

  • Use AWS-provided base images (Amazon Linux 2, already cached by Lambda).
  • Use multi-stage Docker builds: build in a large intermediate image, copy only the final artifacts into a small final image.
  • Order Dockerfile layers from stable to frequently changing so early layers are cached more.
  • Use a single ECR repository for functions sharing large layers — ECR deduplicates them automatically.

23Versions & Aliases

Lambda functions go through changes over time. Versions are immutable snapshots of your code and configuration at a point in time — once published, a version never changes and gets its own ARN. Aliases are mutable pointers to versions, used to give end users and triggers a stable name (like dev, test, prod) that can point anywhere. You move the alias to a new version when ready.

💡 New word Version is an immutable snapshot of a Lambda function at a specific point in time. Code + configuration freeze once published. Each version gets its own ARN and exists forever.
💡 New word Alias is a mutable pointer to a version. It gives users/triggers a stable name that you can point to different versions over time. Used for staged deployments (dev, test, prod).
Versions are immutable. Aliases point to versions and can split traffic by weight between two versions (e.g. 90/10) for a canary-style rollout.

Aliases can even split traffic between two versions by percentage — prod might send 90% of traffic to v1 and 10% to v2. Over time, gradually shift more traffic to v2, giving you a safe canary rollout pattern.

🏭 In real companies Aliases are how teams roll out changes safely. Set up prod → v1 (100%). Deploy v2. Test it. Move prod to prod → 90% v1 / 10% v2. Monitor metrics. Gradually shift the weights over hours until it's 100% v2. If something looks wrong, flip it back instantly.

24Lambda & CodeDeploy

CodeDeploy automates traffic shifting between Lambda versions and aliases. Instead of manually adjusting alias weights, define a deployment strategy (Linear, Canary, or All at Once) and CodeDeploy gradually shifts traffic automatically, with optional rollback if CloudWatch alarms trigger.

StrategyBehavior
LinearGrow traffic by a fixed percentage every N minutes until 100% (e.g. Linear10PercentEvery3Minutes)
CanaryHold at X% for a period, then jump to 100% (e.g. Canary10Percent5Minutes)
All at onceImmediate full cutover — fastest, riskiest

Define pre-traffic and post-traffic hooks that test the new version. If they fail, CodeDeploy rolls back automatically. Key fields in AppSpec.yml: Name (function name), Alias, CurrentVersion, TargetVersion.

25Lambda Function URL

A Function URL is a dedicated, permanent HTTPS endpoint for a Lambda function — no API Gateway or ALB needed. It's useful for quick APIs or one-off functions. It supports IPv4 and IPv6, public internet only (no private option), and CORS configuration.

Attach it to a function alias or $LATEST, never to a specific version. Two auth options: NONE for public, unauthenticated access (secured entirely by the function's resource-based policy, which must allow lambda:InvokeFunctionUrl for principal *); or AWS_IAM to require the caller to be authenticated via IAM. Cross-account access with AWS_IAM requires both an identity-based and resource-based policy.

Use reserved concurrency to throttle a publicly exposed Function URL if you need to protect it from runaway costs.

Exam clue: if a requirement says "we need 30 GB RAM" or "this takes 30 minutes to run" or "we have a 5 GB file to process," Lambda is the wrong tool. Think Fargate, ECS, or EC2 instead.

Best practices that stick

  • Initialize expensive things outside the handler function — database connections, HTTP clients, SDK instances. They get reused across warm invocations.
  • Use environment variables for anything that changes between environments. Never hardcode connection strings or bucket names. Encrypt sensitive values with KMS.
  • Keep deployment packages minimal. Use Lambda Layers for shared and reusable dependencies.
  • Never let a Lambda function recursively call itself. You'll hit throttle limits, rack up massive bills, and cascade failures.
  • Test your function's memory settings under realistic load. More RAM is often cheaper than less RAM that times out and retries.

📋 Cheat Sheet

The three invocation models

  • Synchronous: caller waits for result. CLI/SDK, ALB, API Gateway. Errors go to the caller.
  • Asynchronous: internal queue, 3 automatic retries, DLQ for failures. S3, SNS, EventBridge. Requires idempotency.
  • Event Source Mapping: Lambda polls streaming sources (Kinesis, SQS, DynamoDB Streams). Invocation is synchronous; polling is continuous.

Key performance concepts

  • More RAM = more implicit CPU. Only lever for CPU performance.
  • Initialize slow things outside the handler to reuse them across warm invocations.
  • Cold start = extra latency when creating a fresh execution context. Provisioned concurrency pre-warms instances to eliminate it.
  • Reserved concurrency caps one function's usage to protect it from account-wide throttling.

Permissions and access

  • Execution role = Lambda calling out (to S3, DynamoDB, etc.). Resource-based policy = something calling Lambda (S3, SNS, etc.).
  • Lambda in VPC needs a private subnet + NAT gateway to reach the internet. Private subnet alone gives it no internet access.
  • VPC Endpoints let Lambda reach AWS services (S3, DynamoDB) privately without a NAT gateway.

Deployment and versioning

  • Versions are immutable snapshots. Aliases are mutable pointers to versions, used for staged rollouts.
  • Aliases can split traffic by weight (e.g. 90/10) for canary deployments.
  • CodeDeploy automates traffic shifting with automatic rollback on alarm triggers.
  • Layers externalize shared dependencies so you don't repackage them every time.

Hard limits to remember

  • 15-minute max execution time (anything longer: use Fargate/EC2).
  • 10 GB max RAM (anything larger: use Fargate/EC2).
  • 4 KB max environment variables.
  • 10 GB /tmp ephemeral storage per instance.
  • 50 MB zipped, 250 MB unzipped for zip deployments (10 GB for container images).
  • 1,000 concurrent executions account-wide (increasable via support).
