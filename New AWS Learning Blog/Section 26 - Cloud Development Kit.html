1CDK Overview: From Code to CloudFormation

CloudFormation templates are powerful — but writing them in YAML or JSON feels like reaching back to the 1990s. You're forced to repeat yourself constantly, you can't use loops or functions, and a single typo blows up the entire deployment. AWS CDK (Cloud Development Kit) fixes this by letting you write infrastructure the way you write code.

💡 New word CDK stands for Cloud Development Kit. It is a framework that lets you define AWS infrastructure using real programming languages — TypeScript, Python, Java, or .NET — instead of YAML or JSON templates.

When you run CDK, it compiles your code down to a CloudFormation template behind the scenes. That template is exactly what gets deployed. CDK is not a replacement for CloudFormation — it's a more developer-friendly way to author the same templates.

CDK code compiles down to a CloudFormation template via cdk synth, then that template is deployed with cdk deploy. The final result is identical to hand-written CloudFormation.

Here's what this means in practice. You define constructs — reusable components like a VPC, a Lambda function, or an entire web application — as plain code objects. Because it's real code, you get type safety: if your code doesn't even compile, the template can never be generated. You catch mistakes before deployment, not after.

💡 New word Construct — a reusable, composable component that represents one or more AWS resources. It is the basic building block of CDK applications. Examples include an S3 bucket, a Lambda function with a role, or an entire ECS cluster with auto-scaling.

You can also deploy infrastructure and application code together. If you're building a Lambda function, you write the function's code right next to the construct that defines it. The framework handles linking them automatically.

CDK vs SAM: Which tool to use?

Both CDK and SAM generate CloudFormation under the hood, but they solve different problems.

SAM (Serverless Application Model)CDK
Best forQuick serverless apps (Lambda, DynamoDB, API Gateway)Any AWS service — full superset of CloudFormation
LanguageDeclarative YAML/JSONReal programming language (TypeScript, Python, Java, .NET)
What it generatesCloudFormation templatesCloudFormation templates

If you're prototyping a simple Lambda-based API, SAM is faster. If you're building anything with multiple services, or you want type checking and real language features, CDK wins. And you can actually use both in the same project — run cdk synth to get a CloudFormation template, then use sam local invoke to test a Lambda locally against that template.

Good to know: SAM and CDK can work together. Generate your CDK template with cdk synth, then test Lambda functions locally using SAM.
🏭 In real companies Many teams use CDK specifically because the code is version-controlled, testable, and reviewable like any other code. An infrastructure change goes through the same code review process as an application change. That transparency and traceability is exactly what enterprises need for compliance and auditing.

2CDK in Practice — A Real Example

What we'll build

An S3 bucket that triggers a Lambda function whenever an image is uploaded. The Lambda function calls Amazon Rekognition (AWS's image analysis service) to identify what's in the picture, then saves the detected labels to a DynamoDB table. All of this — the bucket, the function, the database, the permissions — is defined in a single CDK script.

Getting started

Install the CDK library and scaffold a new app:

npm install aws-cdk-lib
cdk init app --language javascript

CDK creates a project structure with a lib/ folder. Your main infrastructure code lives in lib/<app>-stack.js.

Defining the stack

Inside that file, you import CDK constructs and define resources as code. For our example:

const bucket = new s3.Bucket(this, 'ImageBucket', {
  removalPolicy: cdk.RemovalPolicy.DESTROY
});

const table = new dynamodb.Table(this, 'Labels', {
  partitionKey: { name: 'id', type: dynamodb.AttributeType.STRING }
});

const lambdaRole = new iam.Role(this, 'LambdaRole', {
  assumedBy: new iam.ServicePrincipal('lambda.amazonaws.com')
});

const lambdaFn = new lambda.Function(this, 'RekognitionFunction', {
  runtime: lambda.Runtime.PYTHON_3_9,
  handler: 'index.handler',
  code: lambda.Code.fromAsset('lambda'),
  environment: {
    BUCKET_NAME: bucket.bucketName,
    TABLE_NAME: table.tableName
  }
});

bucket.grantReadWrite(lambdaFn);
table.grantWriteData(lambdaFn);
bucket.addEventNotification(s3.EventType.OBJECT_CREATED, new s3n.LambdaDestination(lambdaFn));

Notice the convenience methods like bucket.grantReadWrite(lambdaFn) and table.grantWriteData(lambdaFn). These replace hand-writing the equivalent IAM policy JSON — CDK generates it for you, correctly scoped to exactly what the function needs.

Running it

First, bootstrap your AWS environment (more on this in a moment):

cdk bootstrap

Then, see what will be deployed by synthesizing the template:

cdk synth

This prints the full CloudFormation template. It includes the S3 bucket, the DynamoDB table, the Lambda function, the IAM role, and all the event-source mappings — everything CDK inferred from your code.

Finally, deploy it:

cdk deploy

CDK creates a CloudFormation stack and deploys all the resources. Within minutes, the infrastructure is live.

Testing it

Upload an image to the S3 bucket via the AWS console. S3 immediately triggers the Lambda function. The function calls Rekognition, which returns labels like "penguin," "bird," and "person." These labels are written into the DynamoDB table. You can view them by opening the table in the console.

Bootstrap first: Run cdk bootstrap once per account and region before your first deploy in a new environment. This provisions a support stack (an S3 bucket and IAM roles) that CDK itself depends on to function.

Cleaning up

Empty the S3 bucket first — CDK-managed buckets with destroy policies still require the bucket to be empty before deletion. Then run:

cdk destroy

This tears down the entire CloudFormation stack and removes all the resources.

3CDK Constructs and Abstraction Levels

A construct encapsulates everything needed to produce part of a CloudFormation stack — anything from a single resource to a group of related ones working together. All constructs come from one of two places: the Construct Library (built into CDK, covering every AWS service) or the Construct Hub (a registry of AWS-built, third-party, and community constructs).

💡 New word Construct Library — the built-in collection of constructs covering every AWS service. You use these to build your infrastructure.
💡 New word Construct Hub — a registry where AWS, third parties, and the community publish additional constructs beyond the built-in library.

Constructs come in three layers. Each layer trades manual control for convenience.

Each layer trades away manual control for convenience. L1 mirrors CloudFormation exactly, L2 adds sensible defaults and helper methods, L3 hands you entire pre-wired architectures.

Layer 1: CloudFormation Resources

These constructs have a Cfn prefix: CfnBucket, CfnTable, CfnFunction. They are 1:1 mirrors of CloudFormation resource properties. You have maximum control but must specify every required property yourself. This layer is useful if you're migrating an existing CloudFormation template into CDK piece by piece.

Layer 2: AWS Constructs

These are the ones you'll use most: s3.Bucket, dynamodb.Table, lambda.Function. They come with sensible defaults (like versioning for S3, encryption at rest for DynamoDB) and convenience methods like grantReadWrite that do the IAM wiring for you. You get control when you need it, but CDK does the boring stuff automatically.

Layer 3: Patterns

These are pre-wired combinations of resources. A pattern might give you an Application Load Balancer (ALB) correctly connected to an ECS cluster with auto-scaling, or a Lambda REST API with all the wiring done. You hand CDK the bare minimum — maybe just container image and desired count — and it provisions everything. You trade away fine-grained control for speed.

Exam point: Layer 1 constructs are recognizable by the Cfn prefix. This is useful when migrating an existing CloudFormation template into CDK resource by resource.

4The Core CDK Commands

A few commands make up the entire CDK workflow. Knowing each one's job saves time during troubleshooting.

CommandWhat it does
cdk initInitialize a new CDK app from a template. You choose the language (Python, TypeScript, Java, .NET).
cdk synthSynthesize the CloudFormation template from your CDK code and print it to the terminal. This is how you see what will actually be deployed.
cdk bootstrapProvision the resources CDK itself needs. Run this once per account and region before your first deploy in a new environment.
cdk deployDeploy the CloudFormation stack to your AWS account.
cdk diffCompare your local CDK code against what's actually deployed. Shows additions, changes, and deletions.
cdk destroyTear down the CloudFormation stack and delete all resources.

Understanding bootstrap

An environment in CDK terminology is an account plus region combination. Before deploying to a new environment, you must bootstrap it:

cdk bootstrap aws://ACCOUNT_ID/REGION

This creates a CloudFormation stack called CDKToolkit. That stack contains an S3 bucket (for staging large CloudFormation templates during deployment) and IAM roles (so CDK has permission to create resources on your behalf). Without bootstrapping, your first deploy will fail with a cryptic error about invalid principals.

💡 New word Bootstrap — the process of preparing an AWS account and region for CDK deployments. It creates the CDKToolkit stack containing S3 bucket and IAM roles that CDK depends on.
Don't skip this step: Attempting to deploy to a new account/region without bootstrapping causes a cryptic error: "policy contains a statement with one or more invalid principal." The required IAM role from the bootstrap stack doesn't exist yet.
🏭 In real companies Bootstrap is typically done once as part of initial account setup, often by an infrastructure or platform team. Once the bootstrap stack exists, any developer can run deployments without needing to bootstrap again. This also means bootstrap resources (especially the S3 bucket) become audit and cost points — many organizations have policies about who can modify or delete them.

5Testing Your Infrastructure Code

One huge advantage of CDK over hand-written CloudFormation: your infrastructure is code, so you can test it like code. The CDK assertions module lets you write unit tests using familiar frameworks like Jest (for JavaScript) or Pytest (for Python).

💡 New word Assertion — in testing, a statement that checks whether a condition is true. CDK assertions let you check properties of generated CloudFormation templates.

Two kinds of tests

You can write fine-grained assertions that check specific properties of specific resources. For example: "This Lambda function has runtime Node.js 14.x," or "This SNS topic has exactly one subscription." This is useful when you want to verify that a specific configuration choice was applied correctly.

Or you can write snapshot tests. A snapshot test compares the full generated CloudFormation template against a baseline that you've committed to version control. If the template changes unexpectedly, the test fails. This catches accidental infrastructure changes.

Test typeBest for
Fine-grained assertionChecking specific properties (e.g. "Lambda has runtime X," "SNS topic has exactly one subscription")
Snapshot testDetecting unexpected changes to the generated template

Entry points for testing

The assertions module provides two ways to load a template for testing:

MethodUse when
Template.fromStack(myStack)Testing a stack defined inside your own CDK app
Template.fromString(myString)Testing an external CloudFormation template not defined in CDK

If you're testing your own infrastructure code, use fromStack. If you're validating someone else's CloudFormation template, use fromString.

Exam tip: Remember these two entry points by name — fromStack vs fromString. This distinction shows up on certification exams.
🏭 In real companies Many organizations use CDK assertions to enforce infrastructure standards. For example, a test might verify that every Lambda function has a VPC configuration, or that every database is encrypted. New infrastructure goes through a pull request, the tests run, and only if they pass does the merge go through. This is infrastructure as code done right.

Key Facts Worth Remembering

  • CDK compiles down to CloudFormation — the template generated by cdk synth is what actually gets deployed.
  • SAM is for serverless-first, YAML-based infrastructure; CDK is for everything, code-first, and supports type checking.
  • Three construct layers: L1 (CfnX, 1:1 with CloudFormation), L2 (sensible defaults, helper methods), L3 (pre-wired patterns).
  • Always run cdk bootstrap once per account/region before your first deploy — it creates the CDKToolkit stack that CDK depends on.
  • Core workflow: cdk init → write code → cdk synth (preview) → cdk deploy (deploy). Also cdk diff and cdk destroy.
  • Infrastructure code can be unit tested using the CDK assertions module with Jest or Pytest. Two entry points: Template.fromStack() (your own stacks) and Template.fromString() (external templates).

Decision Guide

ScenarioUse
Building a serverless app (Lambda/API Gateway/DynamoDB) fast with minimal boilerplateSAM
Building anything else, or want type-safe, testable infrastructure as codeCDK
Migrating an existing CloudFormation template piece by pieceCDK Layer 1 (CfnX) constructs

The One-Paragraph Version

CDK is CloudFormation with the "write YAML by hand" straightjacket removed. You write infrastructure in a real programming language, get type checking for free, and the framework compiles everything down to the same CloudFormation templates you'd otherwise write by hand. The three construct layers let you dial between power and convenience — go low-level (L1) when you need exact control, or high-level (L3) when you want speed. And because it's all code, you can test it, version it, and code-review it exactly like the rest of your application.
