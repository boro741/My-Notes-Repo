11IAM Introduction: Users, Groups, Policies

Every AWS account starts out as a blank slate with one all-powerful login. If nobody locks that down, anyone who gets hold of it can delete a database, launch expensive servers, or read data they were never supposed to see. IAM is the AWS service that exists to stop that from happening.

💡 New word IAM stands for Identity and Access Management. It is the part of AWS that checks who you are, and controls exactly what you are allowed to do once you're in.

IAM is a global service. That means the users, groups, and rules you set up work the same way everywhere in AWS — you never have to pick one.

💡 New word Region — a physical area where AWS runs data centers, like Mumbai or N. Virginia. Most AWS services live inside one Region at a time. IAM is one of the few that doesn't; it works everywhere at once.

When you first create an AWS account, you get one login called the Root user. It has complete, unlimited power over the account. Real companies treat this login like a spare house key kept in a safe: used once to set things up, then locked away and almost never touched again. Day-to-day work happens through separate logins, called IAM Users, created one per real person.

🏭 In real companies Most security teams require the Root login to have a physical hardware security key (not just an app code), a long unique password stored in a password manager, and its email inbox actively monitored for sign-in alerts. Usually only one or two senior people ever touch it.

Users and Groups

Most companies don't run everything in a single AWS account. They split work across several — one for development, one for staging, and one for production.

💡 New word Staging is a copy of the real system, used to test a change one last time before it reaches actual customers — like a dress rehearsal. Production is the real, live system customers actually use.

This split is AWS's own recommended pattern, and it matters because a mistake made while testing in the dev account can never touch real customer data sitting in the prod account.

Inside each of those accounts, IAM Groups make it fast to hand out the same access to many people at once. A group is simply a named bucket of users — "Developers," "Admins," whatever makes sense — that you give a set of permissions to a single time. Every user placed inside that bucket instantly gets everything the group has.

A typical real setup looks something like this:

  • prod-readonly — most engineers. They can look at logs and dashboards, but can't change anything.
  • prod-deployers — the automated deployment system, plus on-call engineers, allowed to publish new code.
  • staging-admins — wider access, because a mistake here is cheap to fix.
  • platform-admins — a very small group, often just two to four people, with full control.

When a new engineer joins a team, nobody writes them a custom rulebook by hand — they just get added to the right group. When they leave, removing them from that one group removes every bit of that access at once. Companies that skip this, and hand out permissions to people one at a time, are the ones who discover months later that someone who left the company still has a working login into production.

A group can only ever hold users — never another group. But one user, like Charles, can sit inside more than one group at the same time. Fred belongs to none, which is exactly the situation companies try to avoid.

How Permissions Are Actually Granted — IAM Policies

Being inside a group doesn't grant power by itself — a Policy attached to that group does. A policy is a text file, written in a format called JSON, that spells out exactly what a user or group can and cannot do.

💡 New word JSON (short for JavaScript Object Notation) is just a plain, structured text format for writing rules and data. AWS uses it constantly, not only for IAM.
🏭 Why this matters — a real incident In 2019, Capital One suffered a major data breach. The root cause traced back to an AWS role that had far more permissions than its job actually needed. An attacker used an unrelated bug to get hold of that role's access, and because the role could reach more than it should have, the attacker was able to read tens of millions of customer records. We'll come back to exactly how, later in this page — but it's the clearest real example of why the next rule exists.
Principle of Least Privilege: Never give a person or a system more access than their job requires. It's tempting to just grant full admin access to everyone to avoid support tickets — but that turns one mistake, or one stolen password, into a full account takeover.

12-13Creating Users & Signing In

Creating an IAM user, step by step

  1. Open the IAM Console → click Users → click Create user (e.g. username Stephane), and check the box for AWS Management Console access.
  2. Choose "I want to create an IAM user" — this is the traditional method, and the one the AWS Cloud Practitioner exam expects you to know.
  3. Set up a password. For a teammate, auto-generate one and force a reset on first login. For your own testing, a custom password is fine.
  4. Set permissions by clicking Add user to group and attaching an existing group — don't attach permissions straight to the person.
  5. Optionally add Tags — simple labels like Department = Engineering — to help track who owns what later.

Once created, the user's permissions page will show that their access is inherited from the group, not attached directly. That's the whole point — it keeps things easy to audit later.

🏭 What actually happens at scale Once a company grows past a handful of engineers, most stop creating individual IAM users for people entirely. Instead they connect a central identity system — AWS calls this IAM Identity Center (its older name was AWS SSO) — so employees sign in once with their normal company account, and AWS hands them temporary access based on their team. Nobody's password ends up stored inside AWS itself. For a small project, a learning account, or the exam, though, plain IAM Users are still the standard starting point.

Signing in as an IAM user

  • AWS gives every account a unique sign-in URL that includes your 12-digit account ID.
  • You can set a custom Account Alias (like my-company-aws) so people use a friendly link instead of the raw ID number.
  • To stay logged into both the Root account and an IAM user at once, open one of them in an incognito or private browser window.
Important: Guard your credentials carefully. Getting locked out of both the Root user and your admin IAM user at the same time can make recovery genuinely difficult.

Multi-session sign-in

The AWS console supports having several sessions open at once. You can be logged into the Root account and two different IAM users, each in its own browser tab, inside the very same browser window, without any of them logging the others out.

14What's Actually Inside a Policy

Where you attach a policy decides who feels its effect:

  • Group-level policy: applies to every single user inside that group, automatically.
  • Inline / user policy: attached directly to one specific person.
  • Combined permissions: if someone belongs to two groups and also has a personal policy, AWS simply adds all of it together — whatever any of those allow, they can do.

Structure of a policy document

Every policy has a Version, an optional Id, and one or more Statements. The Statement is where the real rule lives.

In plain terms, each field means:

  • Version — just the policy language version. In practice this is always "2012-10-17".
  • Statement — the actual rule (or rules). Inside it:
    • Effect — either "Allow" or "Deny".
    • Principal — who this rule is about (a specific account, user, or role).
    • Action — which specific AWS operations this covers, e.g. s3:GetObject.
    • Resource — exactly which AWS resource(s) this applies to.
    • Condition (optional) — extra rules for when the statement applies, e.g. only if MFA was used, or only from a specific IP address.

Here's what a real one looks like in practice — the kind of policy an actual deployment pipeline is given:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowDeployToOneBucketOnly",
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:GetObject"],
      "Resource": "arn:aws:s3:::my-company-prod-deploys/*"
    }
  ]
}
💡 New word ARN (Amazon Resource Name) — the unique ID AWS gives every single resource, like one specific S3 bucket or one specific role, so a policy can point at exactly that one thing and nothing else.

Notice this pipeline can only read and write files inside one bucket used for deployments. It cannot touch any other bucket, and it cannot delete anything. That narrowness is the entire point — it's least privilege, written down as JSON.

Exam tip: memorize the four core statement fields — Effect, Principal, Action, Resource. Together they answer one question: who can do what, to which resource.

15Policies Hands-On

Testing permissions for real

  1. Removed the user Stephane from the admin group — every admin privilege disappeared instantly.
  2. Refreshed the IAM page — got an Access Denied error on iam:ListUsers. Permissions are enforced immediately, not on next login.
  3. Attached the AWS-managed policy IAMReadOnlyAccess directly to the user — could view IAM resources again, but creating a new user still failed with Access Denied.
  4. Added the user back to the admin group to restore full access.
🏭 In real companies This exact test — remove access, then confirm it's actually blocked — is what security teams call an access review. It's usually not optional: certifications like SOC 2 or ISO 27001 (common security standards that business customers ask vendors to prove they follow) require documented proof that access gets reviewed on a regular schedule, not just set once and forgotten.

Understanding AWS Managed Policies

Policy NameWhat it actually does
AdministratorAccessAction: *, Resource: * — every action, on every resource. Full power.
IAMReadOnlyAccessUses wildcards like Get* and List* — can look at everything, change nothing.

You can also use the Visual Editor in the console — tick services and actions with checkboxes, and AWS writes the JSON for you. Useful while you're still getting comfortable with the format.

Troubleshooting tip: if a user can't do something they should be able to, check every layer — their personal policy, every group they belong to, and any role involved. The block could be hiding in any of them.

16MFA — Why One Password Is Never Enough

Securing an AWS account really comes down to two layers working together.

1. A strong password policy

  • Set a minimum length and require a mix of character types.
  • Decide whether users can change their own password.
  • Force periodic expiration, e.g. a reset every 90 days.
  • Block reusing old passwords.

2. Multi-Factor Authentication

💡 New word MFA (Multi-Factor Authentication) means logging in needs two different things: your password (something you know), and something you physically have — your phone, or a small security key.

Password-only logins are broken by design. People reuse passwords across sites, and passwords leak in unrelated data breaches constantly — completely outside AWS's control. MFA closes that gap, because a stolen password by itself is no longer enough to get in.

🏭 In the real world Google once required all of its own employees — over 85,000 of them — to switch from app codes to physical security keys for logging in. After making it mandatory, Google reported that not one employee was successfully phished for their login again. It's one of the few security controls that removes an entire category of attack outright, which is exactly why AWS pushes so hard for MFA on any account with real access.
MFA doesn't replace your password — it adds a second, physical layer on top of it.

MFA device options

Device TypeDetails
Virtual MFA (Google Authenticator)Phone app that generates a fresh 6-digit code every 30 seconds.
Virtual MFA (Authy)Phone/desktop app, can sync across multiple devices and manage several accounts.
U2F Security Key (YubiKey)Small physical USB key you plug into your laptop.

17MFA Hands-On

  1. Password policy: Account Settings → Password Policy → use AWS defaults or set your own rules.
  2. Enable MFA on the Root user: click your account name → Security Credentials → Assign MFA Device.
  3. Name the device (e.g. "My iPhone"), and choose Authenticator app.
  4. Scan the QR code shown on screen with an app like Google Authenticator or Authy.
  5. Enter two consecutive 6-digit codes from the app to prove it's synced, then click Add MFA.
Important: keep the device tied to your MFA safe. Lose the phone or key attached to it, and you risk being locked out of your own AWS account.

18Access Keys, CLI & SDK

There are three different ways to actually work with AWS, and it helps to see them side by side.

All three roads lead to the exact same underlying AWS APIs. They only differ in how you log in and where you run them.
💡 New word CLI (Command Line Interface) — controlling AWS by typing text commands into a terminal, instead of clicking through a website. Every command starts with aws.
💡 New word SDK (Software Development Kit) — a code library your own application calls directly, in whatever language you're writing in (Python, Java, JavaScript, and others), to talk to AWS.

Access Keys are what the CLI and SDK use to prove who they are, since there's no human typing a password. A key has two parts: an Access Key ID (works like a username) and a Secret Access Key (works like a password — never share it, ever).

🏭 In real companies Engineers barely touch the AWS Console for repeated work. A deploy pipeline that runs every time code is pushed calls the CLI or SDK directly — for example, running aws s3 sync to publish a website, or a backend service using the Python SDK (nicknamed Boto3) to read a file from storage. The console is mostly for looking around and one-off changes.
🏭 A common real incident Access keys accidentally committed to a public GitHub repository get found and abused within minutes — automated bots constantly scan GitHub for exactly this pattern, then use the stolen keys to launch expensive cryptocurrency-mining servers on the victim's bill. This happens so often that both AWS and GitHub now run automatic scanners specifically to catch and disable leaked keys fast.
Fun fact: the AWS CLI itself is written in Python, and it's built on top of Boto3.

19-21Installing the AWS CLI

Installing AWS CLI v2 is a short process on any operating system.

On macOS: download the official .pkg installer, follow the setup wizard, then open a terminal and confirm it worked:

aws --version

A successful install prints something like aws-cli/2.x.x.

Rule of thumb: only download installers from AWS's own documentation, and always confirm success with aws --version before moving on.

22AWS CLI Hands-On

  1. Generate access keys: go to your user → Security Credentials → Create access key.
  2. Copy or download the Secret Access Key right away — AWS only shows it to you once.
  3. Run aws configure in your terminal, and enter your Access Key ID, Secret Access Key, a default region (e.g. ap-south-1 for Mumbai), and a default output format (JSON works well).
  4. Test it: run aws iam list-users and you should see your account's users printed out as JSON.
💡 New word STS (Security Token Service) — the AWS service that hands out short-lived, temporary credentials instead of permanent ones.
🏭 In real companies A long-lived access key sitting on a developer's laptop is a real risk — if that laptop is lost or the key leaks, it keeps working until someone manually notices and revokes it, which could take months. This is why many companies now avoid handing people permanent keys at all, and instead issue short-lived, auto-expiring credentials through STS.
Same permissions, every time: the CLI enforces the exact same IAM policies as the console. If a user is denied in the browser, the same command from their terminal fails with the identical Access Denied error.

23AWS CloudShell

AWS CloudShell is a free, browser-based terminal built directly into the AWS Management Console.

  • Nothing to install — the AWS CLI is pre-installed and already logged in as your current session.
  • Automatically uses whatever Region you currently have selected in the console.
  • Comes with persistent storage — files you create stick around between sessions.
  • Supports uploading and downloading files, and multiple tabs.
🏭 Why this matters in practice Plenty of companies lock down corporate laptops tightly enough that installing new software — including the AWS CLI — needs an IT approval ticket. CloudShell skips that problem completely, since it just runs in a browser tab.

24IAM Roles — Permissions for Machines, Not People

People aren't the only ones who need AWS permissions. A server, or a piece of running code, often needs to call other AWS services too — and handing it a permanent username and password would be a bad idea. That's what IAM Roles are for.

💡 New word IAM Role — a set of permissions that something (an AWS service, or even a trusted outside account) can pick up temporarily. It works like a policy, but instead of belonging permanently to one user, it gets "assumed" — borrowed — by whatever needs it, for as long as it's running.
The EC2 server assumes the role and gets temporary permission to call AWS APIs — with no long-lived access keys stored anywhere on the machine.
🏭 Why this exists — the full real story Earlier we mentioned the 2019 Capital One breach. Here's the exact mechanism, because it's the clearest real reason IAM Roles work the way they do. A web server had a bug that let an attacker trick it into asking the server's own metadata service — an internal address every EC2 server can reach, normally used safely by the server's own software — for its role's temporary credentials. The server handed them over, because that's exactly what the metadata service is designed to do. The real problem wasn't that the server had a role at all; it's that the role could reach far more S3 data than that server's job ever needed. That's the whole lesson: roles remove permanent keys from the machine, but least privilege still has to be applied to the role itself, or the protection barely matters.

The most common real examples are EC2 Instance Roles and Lambda Function Roles — both let running code reach other AWS services safely, without a single password ever being typed or stored.

25IAM Roles Hands-On

  1. Go to the IAM Console → click Roles → click Create role.
  2. Choose AWS service as the trusted entity, then pick EC2.
  3. Attach the policy it needs (e.g. IAMReadOnlyAccess).
  4. Name it (e.g. DemoRoleForEC2) and create it.

Once created, this role can be attached to an EC2 instance, letting that server talk to AWS APIs securely — with no hardcoded access keys anywhere in its application code.

26IAM Security Tools

Security ToolScopeWhat it tells you
IAM Credentials ReportWhole accountA downloadable CSV listing every user and their security details — passwords, MFA status, key age.
IAM Access AdvisorPer userWhich services a specific user can access, and exactly when they last actually used each one.
🏭 In real companies This exact check — who has access, and are they actually using it — is usually a recurring item on a security team's calendar, often quarterly, sometimes required by an outside auditor for a security certification. Access Advisor is what turns "we think Dave doesn't need S3 access anymore" into "Dave hasn't touched S3 in 214 days, safe to remove."

27Security Tools Hands-On

Credentials Report

Go to IAM → Credential report → Download Report. It's a CSV with every user's creation date, password status, MFA status, key rotation history, and last activity.

Access Advisor

Open any IAM user → the Access Advisor tab. It lists every service that user can reach, next to a timestamp like "accessed 2 days ago" or "never accessed." That's the exact data you use to safely trim unused permissions.

28IAM Best Practices

  • Don't use the Root account for daily tasks — reserve it for one-time account setup.
  • One IAM user per real person. Never share a single login between two people.
  • Manage permissions at the group level, not the individual level.
  • Turn on a strong password policy and require MFA everywhere it's available.
  • Use IAM Roles for AWS services — never store long-lived keys on a server.
  • Keep access keys secret, and rotate them on a schedule.
  • Audit access regularly with the Credentials Report and Access Advisor.
Never commit access keys or passwords into a public code repository like GitHub. It will be found.

29The Shared Responsibility Model

💡 New word Shared Responsibility Model — AWS's rule for who secures what. AWS secures the cloud itself (the hardware, the data centers, the network). You secure what you build and configure inside it — your users, your permissions, your data.
AWS secures the cloud (the infrastructure). You secure what's in the cloud (your IAM setup and data).
🏭 The one idea to take away This split is exactly why the Capital One breach we've referenced twice in this page was officially classified as a customer misconfiguration, not an AWS failure. AWS's infrastructure worked exactly as designed the entire time. The weak point was the customer's own IAM setup — a role with too much access. That single idea is arguably the most important thing in this whole section: AWS can't protect you from the permissions you hand out yourself.

📋 Cheat Sheet

Core Building Blocks

ConceptPlain-English meaning
IAM UserOne real person; logs in with a password or access keys.
IAM GroupA named bucket of users only — never another group. Grant permissions once, everyone inside inherits them.
IAM PolicyA JSON rulebook stating what's allowed or denied.
IAM RoleTemporary permissions borrowed by an AWS service (EC2, Lambda) or a trusted account.
Access KeysAccess Key ID + Secret Access Key, used by the CLI and SDK instead of a password.

Key Facts Worth Remembering

  • IAM is a global service — no Region to pick.
  • Groups hold only users, never other groups.
  • A policy is built from Version + Statement(s), and each statement's core fields are Effect, Principal, Action, Resource.
  • Least privilege = grant only what's actually needed, nothing extra.
  • MFA = password (something you know) + device (something you have).
  • CloudShell = a free, zero-setup terminal built into the console.
  • Credentials Report = account-wide CSV. Access Advisor = per-user, last-used dates.

The One-Paragraph Version

The Root account exists only to set things up, once. Everyday work happens through IAM Users, organized into Groups. Policies (written in JSON) define exactly what each Group or User can do. Roles do the same job for machines instead of people — no permanent keys required. MFA protects human logins; access keys protect CLI/SDK access. And the Credentials Report and Access Advisor exist so you can keep proving, on a schedule, that nobody has more access than they actually use.
