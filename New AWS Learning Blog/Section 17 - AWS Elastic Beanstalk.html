1Elastic Beanstalk Overview

Most web applications follow the same pattern: a load balancer distributes traffic to a group of EC2 instances that scale up and down based on demand, and usually there's a database in the back. Building this manually every single time — choosing instance types, creating auto scaling groups, configuring load balancers, setting up health checks — is repetitive and error-prone. AWS Elastic Beanstalk exists to solve that exact problem.

💡 New word Elastic Beanstalk is a Platform as a Service (PaaS) that automates the provisioning of infrastructure for your application. You upload your code, choose a few high-level settings, and Beanstalk creates and manages EC2 instances, load balancers, auto scaling groups, and more — letting you focus on writing code instead of wiring up AWS components.

Beanstalk itself is free. You only pay for the underlying AWS resources it creates for you — the EC2 instances, load balancers, databases, and any other services it provisions on your behalf.

How Beanstalk organizes your work

Beanstalk uses a three-level hierarchy to organize your application.

💡 New word Application — the top-level container that holds all the versions of your code and all the environments where those versions might run. Think of it as your project name inside Beanstalk.
💡 New word Application Version — a snapshot of your code at one point in time. Version 1 might be your initial release, version 2 might be after you fixed a bug, and so on. Each version gets stored in S3 behind the scenes so you can roll back to it later.
💡 New word Environment — a collection of AWS resources (EC2 instances, load balancer, database, security groups, scaling policies) running one specific application version at a time. You typically have separate environments for development, staging, and production.

The typical workflow is: create an application → upload a version → create an environment and deploy that version to it → upload new versions and redeploy to update.

Supported platforms

Beanstalk runs on many platforms: Go, Java SE, Java with Tomcat, .NET Core on Linux, .NET on Windows, Node.js, PHP, Python, Ruby, Packer Builder, and Docker (single or multi-container). Choose the one that matches your codebase.

Two deployment architectures: Web tier vs Worker tier

Beanstalk gives you two fundamentally different ways to structure your application, and the choice matters for how your application scales.

💡 New word Web tier — a load balancer sits in front of EC2 instances that serve user requests. This is the standard web server setup. Traffic arrives from the internet, hits the load balancer, gets distributed to instances, which respond with web pages or API responses.
💡 New word Worker tier — EC2 instances don't face users directly. Instead, they pull messages from an SQS queue and process them. This tier scales based on the number of messages waiting, not on HTTP traffic. Perfect for background jobs, batch processing, or any work that doesn't need to respond to a user immediately.
Web tier handles user traffic through a load balancer. Worker tier pulls jobs from a queue and scales based on queue depth.
🏭 In real companies Real teams use web tier for customer-facing websites and APIs. They use worker tier for background tasks — image processing, report generation, sending emails, indexing data. The two can work together: a web app receives an upload and puts a message on a queue, then workers process it asynchronously. This separation lets the web tier respond quickly to users while heavy work happens in the background.

Two deployment scales: Single instance vs High availability

Beanstalk offers two preset configurations that determine how your environment scales.

Single instance is for development. It creates one EC2 instance with an Elastic IP (a static, public IP address) so you can access it. No load balancer. This is cheap and fast to set up, but if that instance goes down, your app is down. AWS marks this as free-tier eligible, so it's ideal for learning.

High availability is for production. It creates a load balancer, an auto scaling group that spans multiple availability zones, and multiple EC2 instances. If one zone fails, traffic automatically moves to the others. You pay more, but your application stays up even when infrastructure fails.

2First Environment — Hands On

Creating your first Beanstalk environment is straightforward. Choose Web server (not Worker), pick a platform like Node.js, and select the Single instance preset to keep costs low while you explore. Beanstalk will ask you to set up service access — it needs an IAM role so the environment itself has permission to read its configuration, and an EC2 instance profile so the instances inside can call other AWS services if your code needs to.

Once launched, Beanstalk assigns your environment a domain name. Visit it and you'll see the "Congratulations, you are now running Elastic Beanstalk" page, proving the infrastructure is working. From there, you get tabs for Health (is your app responsive), Logs (application and system logs), Monitoring (CPU, memory, request count), and Configuration (where you can tweak every setting Beanstalk created).

Behind the scenes, Beanstalk creates a CloudFormation stack for you. You can watch it happen in the CloudFormation console and see every component it provisions — security groups, launch configurations, Elastic IPs, everything is tracked there.
💡 New word CloudFormation is AWS's infrastructure-as-code service. It takes a template describing resources and creates them as a coordinated unit called a stack. Beanstalk uses CloudFormation internally to reliably provision and manage all the components of your environment.

3Second Environment — Hands On

Creating a second environment with the High Availability preset reveals a lot more configuration than the simple single-instance setup. You choose which VPC and subnets to use, decide whether to create a database (and what type), configure the load balancer (Classic vs Application vs Network load balancer), set auto scaling limits (minimum and maximum instances), and decide whether to use On-Demand or Spot pricing for instances.

Once you hit launch, Beanstalk provisions all of it automatically. A real load balancer gets created across multiple availability zones, target groups are configured with health checks, security groups are set up so the load balancer can talk to instances and instances can talk back, and an auto scaling group is created with scaling policies that adjust capacity based on CPU or request count. All of that infrastructure springs into being from just uploading your code and making a few choices.

🏭 In real companies Production teams start with High Availability. The infrastructure cost is real but small compared to the cost of downtime. Auto scaling means the system adapts to traffic spikes without manual intervention. Health checks mean instances that start failing are automatically replaced. This is why Beanstalk is popular — it automates the operational practices that mature teams have learned the hard way.

4Deployment Modes

When you upload a new version of your application to an existing environment, Beanstalk doesn't just stop everything and start the new version. It offers several deployment strategies that trade off speed, downtime, and cost. Picking the right one depends on whether you can accept downtime and how much you're willing to spend temporarily.

💡 New word Deployment policy (or deployment mode) is the strategy Beanstalk uses when updating instances to a new application version. Options range from fastest (but with downtime) to safest (but most expensive).
ModeDowntime?Extra cost?Best for
All at onceYesNoDevelopment. Fast, but app is down during update.
RollingNoNoMost production cases. No downtime, no extra cost.
Rolling with additional batchNoSmallWhen you need full capacity during the entire deployment.
ImmutableNoHigherWhen you need zero downtime and super-fast rollback.
Blue/GreenNoHigherManual cutover. Test a whole new environment, then switch.
Traffic splitting (canary)NoHigherAutomated canary testing with safe rollback.

All at once: fastest but risky

All at once stops every instance at the same time and starts the new version on all of them. It's the fastest way to deploy, but every instance is down simultaneously. Users see errors. Don't use this in production unless you're okay with downtime.

Rolling: the safe default

Rolling updates instances one group (or bucket) at a time. While instances in bucket 1 are being updated, instances in bucket 2 keep serving the old version. So some capacity is always available, and users stay connected. It's slower than all-at-once, but there's no downtime. This is the most common production choice.

All at once updates all instances simultaneously, causing downtime. Rolling updates one bucket at a time, keeping the app available.

Immutable: the safest way

Immutable launches a brand-new temporary auto scaling group with the new version. Once those instances are healthy, they get merged into the main group and the old instances are terminated. If something goes wrong, rollback is instant — just terminate the new instances and swap back. The trade-off is that you temporarily double your capacity, which doubles cost during the deployment.

Immutable: new instances launched separately and verified first, then merged into the main group. Old instances removed after new ones are proven healthy.

Blue/Green: the manual way

💡 New word Blue/Green deployment is not built into Beanstalk, but it's a pattern you can implement manually. You run two full environments — "blue" (the current one) and "green" (the new one). You deploy to green, test it thoroughly, then swap traffic over using Route 53 DNS or a load balancer. If something goes wrong, you swap back instantly.

Traffic splitting (canary): the automated way

💡 New word Traffic splitting, also called canary deployment, is Beanstalk's automated version of blue/green. A temporary ASG is launched with the new version. Traffic is gradually shifted to it (10%, 50%, 100%). If errors spike, Beanstalk automatically rolls back. It's like a safety net for deployments.
Both send initial traffic to the new version first. Blue/Green is manual (two environments, DNS swap). Traffic splitting is automated (one environment, gradual shift with rollback).
On the exam, when you see "canary testing," it refers to traffic splitting — the automated mechanism where a small percentage of traffic gets the new version first to catch errors before full rollout.

5Deployment Modes — Hands On

To set which deployment policy an environment uses, go to Configuration → Updates, monitoring, and logging → Rolling updates and deployments. Choose your policy and set a batch size — either a fixed number of instances (e.g., 1) or a percentage (e.g., 30%). The policy takes effect the next time you upload a new application version.

Another useful feature is environment swapping. After you clone an environment and deploy a new version there, you can swap the DNS names between the two environments. This instantly promotes the test environment to become production without redeploying anything. DNS changes usually propagate within a few minutes.

6Beanstalk CLI & Deployment Process

The EB CLI is a command-line tool for Beanstalk that lets you create environments, check status, view logs, and deploy updates from your terminal. Commands like eb create, eb deploy, eb health, and eb open are powerful for automating deployment pipelines. It's more important for the DevOps exam than the Developer exam, but knowing it exists is useful.

Regardless of whether you use the console or EB CLI, the deployment process is always the same. First, describe your dependencies — a requirements.txt for Python, package.json for Node.js, etc. Package your code and the dependency file as a zip. Upload the zip to Beanstalk, which stores it in an S3 bucket behind the scenes and creates a new application version. Finally, deploy that version to your environment. Beanstalk copies the zip to each EC2 instance, installs dependencies, and starts your application.

7Lifecycle Policy

Beanstalk stores every application version you ever upload. Over time, if you deploy frequently, the count grows. AWS limits each account to 1,000 application versions per application. Once you hit that limit, you can't deploy new versions until you clean up old ones.

Beanstalk stores at most 1,000 application versions per account. Old versions pile up if you don't clean them up. A lifecycle policy automates this cleanup so you never hit the limit.
💡 New word Lifecycle policy automatically removes old application versions based on age or count. For example, keep only versions from the last 180 days, or keep a maximum of 200 versions. Versions currently in use by any environment are never deleted.

You can also choose whether to delete the source bundle from S3 or keep it. Keeping old bundles costs a bit for storage but lets you restore old versions later if needed.

8Beanstalk Extensions

Beanstalk's console UI lets you configure many settings, but not everything. If you want to tweak something advanced — like changing log streaming settings, adding environment variables, or provisioning additional AWS resources like ElastiCache or DynamoDB — you use Beanstalk Extensions.

💡 New word .ebextensions are configuration files bundled with your source code that let you customize your environment via code instead of clicking through the console. Files go in a .ebextensions/ directory at the root of your source zip, must be named with a .config extension, and are written in YAML or JSON.

You can modify default Beanstalk settings via option_settings, or use raw CloudFormation resources to add AWS services that aren't directly configurable through the console. For example, you could add an RDS instance, an ElastiCache cluster, or an S3 bucket as part of your environment provisioning.

Any AWS resource created via .ebextensions is tied to your environment's lifecycle. If you delete the environment, that resource gets deleted too. If you're adding a database that must outlive the environment, don't add it via .ebextensions — add it separately and point your environment at it.

A common use case is setting environment variables without hardcoding them. A file like .ebextensions/env-vars.config can define database connection strings or API keys, which then appear in the environment's Configuration tab, exactly as if you'd typed them in manually.

9Beanstalk & CloudFormation

Every Beanstalk environment is built on top of a CloudFormation stack. You can see this by going to the CloudFormation console and looking at the stacks that Beanstalk created. Each environment has its own stack, and inside that stack is every resource Beanstalk provisioned — the auto scaling group, launch configuration, load balancer, target groups, security groups, scaling policies, CloudWatch alarms, everything.

This matters because it means Beanstalk's reliability comes from CloudFormation's ability to create and coordinate multiple resources as a single, manageable unit. If you inspect a Beanstalk stack in CloudFormation, you can see exactly what infrastructure was created. And if you're using .ebextensions to add raw CloudFormation resources, you're not limited to what Beanstalk exposes in the UI — you can provision virtually anything.

10Beanstalk Cloning

Imagine you want to test a new version of your application in an environment that matches production exactly — same load balancer type, same auto scaling settings, same instance types, same everything. Creating a new environment and manually matching all those settings is tedious and error-prone.

💡 New word Clone Environment creates a brand-new environment with the exact same configuration as an existing one. The new environment starts with zero instances, but has identical settings for load balancing, auto scaling, instance types, and environment variables.

After cloning, you're free to customize the new environment. Deploy a new application version to it, test it thoroughly, and once you're confident it works, you can promote it to production by swapping environment domains. Cloning is a low-cost way to create a test copy of production without having to rebuild the configuration manually.

Note: cloning copies the environment configuration but not the database. If the original environment has an RDS database, the clone won't include its data. But you can reconfigure the clone to point at the same database, which is actually useful — you get a fresh environment pointing at real production data.

11Beanstalk Migrations

As your application evolves, you might need to migrate to a different infrastructure setup. The most common scenarios are changing load balancer types and decoupling the database.

Changing load balancer type

Once you create a Beanstalk environment, the load balancer type is locked in. You can't change a Classic Load Balancer to an Application Load Balancer after the fact. If you need a different load balancer type, you must create a new environment with the right type, deploy your application there, and shift traffic over.

Load balancer type cannot be changed after environment creation. You must create a new environment if you want a different type. Migration requires deploying to the new environment and updating DNS.

Decoupling RDS from the environment

When you add a database to a Beanstalk environment, its lifecycle becomes tied to the environment. Delete the environment and the database gets deleted too. This is fine for development, but risky for production — you might accidentally delete your production database while trying to tear down the app environment.

The solution is to decouple the database. Create it separately outside of Beanstalk, then point your environment at it via a connection string. Here's how:

  1. Snapshot your existing RDS database as a safety net.
  2. Enable deletion protection on the database so it can't be accidentally deleted.
  3. Create a new Beanstalk environment with the same configuration as the current one, but don't provision an RDS database inside it.
  4. Configure the new environment to point at the existing database via environment variables or a configuration file.
  5. Deploy your application to the new environment and test it.
  6. Swap environment domains so the new one becomes production.
  7. Terminate the old environment. Because the database has deletion protection enabled, Beanstalk can't delete it, so it's safe.
Decoupling RDS: snapshot first, protect the DB, stand up a new environment pointing at it, swap traffic, then remove the old environment.
After step 7, the old Beanstalk stack will be in Delete Failed state because CloudFormation can't delete the protected RDS instance. You need to go into the CloudFormation console and manually delete that stack to clean up.

12Beanstalk Cleanup

When you're done with a Beanstalk application, delete it from the console. Go to the application level, click Actions, and choose Delete application. Confirm by typing the name. This deletes all environments in the application, which in turn tells CloudFormation to tear down every resource it created — load balancers, auto scaling groups, security groups, etc. One action cleans up everything, so you stop paying for unused infrastructure.

📋 Cheat Sheet

Core building blocks

  • Elastic Beanstalk — Platform as a Service that automatically provisions and manages EC2, load balancers, auto scaling, and databases. You pay for the resources it creates, not for Beanstalk itself.
  • Application — the top-level container for your code and environments.
  • Application Version — a snapshot of your code at one point in time, stored in S3.
  • Environment — the running infrastructure (EC2 instances, load balancer, database) executing one application version.
  • Web tier — load balancer facing users, EC2 instances serving requests.
  • Worker tier — EC2 instances pulling jobs from SQS, scales based on queue depth.

Deployment modes ranked by safety and cost

  • All at once — fastest, causes downtime. Dev only.
  • Rolling — no downtime, no extra cost. Most common production choice.
  • Rolling with additional batch — maintains full capacity, small extra cost.
  • Immutable — safest with instant rollback, higher cost (doubles capacity temporarily).
  • Blue/Green — manual, two full environments, complete control, highest cost.
  • Traffic splitting (canary) — automated version of blue/green with health monitoring and auto-rollback.

Key operational concepts

  • Beanstalk is built on CloudFormation stacks — each environment is a stack containing all provisioned resources.
  • Lifecycle policy automatically cleans up old application versions (max 1,000 per account); versions in use are never deleted.
  • .ebextensions (files ending in .config in a .ebextensions/ folder) let you configure anything via code, including adding raw CloudFormation resources.
  • Clone environment copies all configuration but starts with zero instances and zero database data.
  • Load balancer type cannot be changed after creation; changing it requires a new environment and traffic cutover.
  • RDS provisioned inside a Beanstalk environment dies when the environment dies; decouple it for production by creating it separately and pointing your environment at it.
  • Environment swapping exchanges DNS between two environments — used to promote a tested clone to production instantly.

The one idea

Elastic Beanstalk is a developer-friendly automation layer over CloudFormation that assembles standard application infrastructure (load balancer, auto scaling group, security groups) from high-level choices like platform, tier, and deployment mode. It's popular because it saves the repetitive work of hand-building the same architecture for every application while still letting you drop down into configuration details or raw CloudFormation whenever you need to.
