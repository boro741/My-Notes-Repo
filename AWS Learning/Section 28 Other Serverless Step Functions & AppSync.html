1 Step Functions Overview

Step Functions let you model a workflow as a state machine — one state machine per workflow (order fulfillment, data processing, a web app, anything). You define what happens, what happens next, and what happens based on a condition, all in a JSON document written in the Amazon States Language (ASL). That JSON gives you a visual diagram of the workflow, which you can then execute and watch step-by-step, with a full execution history.

Each step in the workflow is typically a Lambda function, a DynamoDB write, an ECS task, etc. — Step Functions is simply the thing orchestrating all of it.

A minimal state machine: a Choice branches the flow, and each step is a small, orchestrated unit of work.

How a workflow starts

  • An SDK/API call
  • API Gateway
  • Amazon EventBridge (CloudWatch Events)
  • Manually, from the console

Task states — the actual work

A Task state does one unit of work: invoke a Lambda function, run a Batch job, run an ECS task and wait for it, insert an item into DynamoDB, publish to SNS/SQS, or even start another Step Functions workflow.

A task can also be an Activity — a worker (EC2, ECS, on-premises server) that polls Step Functions for work to do, rather than being invoked directly. More on this later.

Other state types

StatePurpose
ChoiceTests a condition, branches to a specific state or a default
Fail / SucceedStops the execution with a failure or a success
PassPasses input straight to output, or injects fixed data — no real work done
WaitDelays for a set duration, or until a specific date/time
MapDynamically iterates a set of steps
ParallelBegins parallel branches of execution
Exam point You don't need to write ASL by hand for the exam, but do know the Task and Parallel states — those are the ones most likely to come up.

2 Step Functions — Hello World Hands On

The Workflow Studio lets you drag and drop components (Lambda, Choice, Parallel, Map, and ready-made patterns like "process a JSON file in S3") onto a visual canvas. Once you're done, Studio generates the equivalent ASL JSON for you — the visual flow and the JSON are two views of the exact same thing. Configuration also covers the state machine name, whether it's a Standard or Express workflow, the execution role's permissions, and logging.

The console's Hello World example: initialize variables, branch on a Choice, wait, run parallel steps, increment a checkpoint counter, then summarize and succeed (or fail on the false branch).

  • The initial Pass state sets output values and assigns variables (e.g. IsHelloWorldExample = true, ExecutionWaitTimeInSeconds = 3, CheckpointCount = 0) — it does no real work, just produces an output.
  • The Choice state evaluates IsHelloWorldExample == true: true goes to Wait for X seconds, anything else goes to the default Fail the execution branch.
  • After waiting, CheckpointCount is incremented and the flow moves into a Parallel state, then repeats a checkpoint increment, then summarizes the execution and succeeds.
  • Each step in the console execution view shows its input, output, any variables, and the reason things happened — plus a full Event History tab.
Try it Flip IsHelloWorldExample to false in the code, save, and re-run — the execution now takes the left branch straight into the failed state.

3 Step Functions — Invoke Lambda Hands On

Starting from a blank state machine (or pasting a pre-written ASL JSON), this workflow invokes a Lambda function and branches on its output.

Invoke a Lambda, then branch on whether its output contains the expected name.

  • A simple Node.js Lambda ("HelloFunction") reads a who key from the event and returns Hello, <who>! — tested directly in the console before wiring it up.
  • Its ARN is pasted into the Lambda Invoke state's function name field.
  • Because the state machine invokes Lambda (and optionally X-Ray), Step Functions automatically creates an execution role with the permissions it needs.
  • Running with who: "Stephane Maarek" → output contains "Stephane" → IsTeacher → Woohoo!
  • Running with who: "John Doe" → output doesn't contain "Stephane" → NotTeacher → fails with the custom error message.

4 Step Functions — Error Handling

Step Functions execute many small tasks that each do very little work — error handling should live in the state machine itself, not inside the tasks (e.g. don't try/catch inside a Lambda function). Errors can come from a state machine definition issue (no matching Choice branch), a task failure (a Lambda exception), or a transient failure (e.g. a network partition).

Why it matters Defining retries and catches in the JSON — instead of in application code — keeps your Lambda functions simple and fast, and lets you change error-handling logic without redeploying any code. You also get the full retry/catch history for free in the execution history.

Predefined error types

ErrorMeaning
States.ALLMatches any error name
States.TimeoutTask ran longer than its timeout, or no activity heartbeat received
States.TaskFailedThe task itself failed execution (e.g. an uncaught Lambda exception)
States.PermissionsInsufficient permissions to execute the task

Retry

Evaluated top-to-bottom against fields: ErrorEquals (which error(s) this rule matches), IntervalSeconds (initial wait before retrying), BackoffRate (multiplier applied to the interval each retry — e.g. 2 for exponential backoff), and MaxAttempts (default 3; 0 means never retry). Once all attempts for a matching rule are exhausted, control falls through to Catch.

Catch

Also evaluated top-to-bottom: ErrorEquals plus Next (the fallback state to transition to). A ResultPath (e.g. $.error) controls how the error details get merged into the input before being passed to that next state — so if the input was {"foo":"bar"}, the output becomes {"foo":"bar", "error": {...}}, letting the next state (e.g. send an alert email) inspect what went wrong.

Retry with backoff until attempts are exhausted, then Catch routes by error type to a fallback state — all defined outside the task itself.

Hands-on: seeing it run

  • A Lambda blueprint throws a CustomError. The state machine's Retry rules give it different backoff/attempt settings per error type (CustomError, States.TaskFailed, States.ALL), and its Catch rules route to CustomErrorFallback, ReservedTypeFallback, or CatchAllFallback respectively.
  • Running it with the original CustomError: quick retries (short interval), then falls into CustomErrorFallback once exhausted.
  • Changing the Lambda to throw a different, uncaught error type instead: the retry cadence is much longer (30s, then 60s...), and it falls into a different branch — ReservedTypeFallback — entirely.
Exam point Different error types can have completely different retry/backoff/catch behavior, all defined purely in the state machine's JSON — no code changes needed to adjust error handling.

5 Wait For Task Token

Sometimes a task needs to wait on something external: another AWS service finishing its work, a human approval, a third-party integration, or a legacy system. Appending .waitForTaskToken to a task's Resource field tells Step Functions to pause that task until it receives a matching task token back via SendTaskSuccess or SendTaskFailure.

A push-based callback: Step Functions hands off work (with a task token attached) and waits until it gets that same token back.

This is a push pattern — Step Functions pushes an event out (e.g. to SQS), and whatever picks it up must remember to call back with the token when it's done.

6 Activity Tasks

Activity workers (EC2 instances, Lambda functions, mobile devices, anything) regularly poll a step function for work using the GetActivityTask API. If there's work, they do it, then respond with SendTaskSuccess or SendTaskFailure — the same API calls used for Wait For Task Token.

Activity Tasks are pull-based — the worker reaches out to Step Functions, unlike the push-based callback pattern above.

Exam point Activity Tasks = pull (worker polls Step Functions directly — simple network setup, just needs outbound connectivity). Wait For Task Token = push (Step Functions pushes to something like SQS, which then needs its own consumer to pull and call back).
  • TimeoutSeconds — how long an in-progress task can run before it's considered failed.
  • HeartbeatSeconds + the SendHeartbeat API — the worker periodically signals it's still alive. With regular heartbeats, an Activity Task can run for up to one year.

Max durationUp to 1 yearUp to 5 minutesUp to 5 minutes
Execution modelExactly-onceAt-least-onceAt-most-once
Throughput~2,000 executions/secOver 100,000 executions/secOver 100,000 executions/sec
Execution history90 days in console, or forever via CloudWatch LogsCloudWatch Logs onlyCloudWatch Logs only
PricingPer state transitionPer execution, duration, memoryPer execution, duration, memory
Waits for result?N/A (long-running)No — fire and forgetYes — blocks for the result

Important Because Express Async is at-least-once, the same action can run twice on retry — your workflow must handle idempotency itself. Express Sync is at-most-once — on failure, Step Functions does not restart the workflow for you; that's on your application logic.
Exam point Remember the three execution guarantees exactly: Standard = exactly-once, Express Async = at-least-once, Express Sync = at-most-once.

8 AppSync Overview

AWS AppSync is a managed service for building GraphQL APIs. GraphQL lets a client ask for exactly the fields it needs and get back exactly that — nothing more — and can combine data from multiple sources (NoSQL stores, relational databases, HTTP APIs) into a single graph.

The client asks for exactly the fields it wants; AppSync's resolvers fetch from whichever backend(s) are configured and return matching JSON.

Beyond GraphQL APIs, AppSync also offers real-time WebSocket/MQTT integration for live data feeds, and mobile offline data access + synchronization — the modern replacement for the older, now-deprecated Cognito Sync.

Security — authorization modes

ModeUse for
API_KEYGenerated keys handed out to users, like the API Gateway
AWS_IAMIAM users/roles, including cross-account access
OPENID_CONNECTAn OIDC provider + JSON Web Tokens
AMAZON_COGNITO_USER_POOLAn existing Cognito User Pool (can federate to social logins too)

Multiple authorization modes can be combined on the same API. Integrated with CloudWatch Metrics and Logs. For a custom domain with HTTPS, put CloudFront in front of AppSync.

9 AppSync Hands On

  1. Create a GraphQL API, designed from scratch (as opposed to importing from DynamoDB or building a real-time API).
  2. Define a type backed by a DynamoDB table — e.g. a Student model with fields id (required), name (string), age (int), certified (boolean) — and choose the table name and primary key.
  3. AppSync auto-generates the GraphQL schema and creates the backing DynamoDB table for you.

Console sections: Schema (the generated GraphQL schema), Data sources (the linked DynamoDB table), Functions, and Queries — where you can run generated mutations/queries directly, e.g. createStudent to add a record and listStudents to fetch them all back. Records created this way show up immediately in the DynamoDB table's item explorer too.

Good to know Caching options include full request caching, per-resolver caching, or none. Settings expose the GraphQL endpoint, API ID, real-time endpoint, authorization mode(s) (including creating new API keys), monitoring, and custom domain configuration.

Cleanup: delete the API by typing its name to confirm, then separately delete the DynamoDB table it created (no backup needed).

10 AWS Amplify

AWS Amplify is a set of tools for building mobile and web applications fast — think of it as Elastic Beanstalk for mobile and web apps. It bundles: Amplify Studio (visually build the full stack — front end and back end), the Amplify CLI (same thing, via commands like amplify add ...), the Amplify Libraries (connect app code to Cognito, S3, and other AWS services), and Amplify Hosting (build, deploy, and serve the app quickly).

Amplify is a front door over Cognito, AppSync/DynamoDB, S3, and CloudFront — plus ready-made front-end libraries for React, Vue, JS, iOS, Android, and Flutter.

Key features

  • amplify add auth — Cognito-backed sign-up/sign-in/account recovery/MFA/social login, with pre-built UI components and fine-grained authorization.
  • amplify add api — DataStore, powered by AppSync (GraphQL) + DynamoDB: work with data locally, get automatic cloud sync, offline and real-time capable, and can be modeled visually in Amplify Studio.
  • amplify add hosting — CI/CD (build, test, deploy), pull request previews, custom domains, monitoring, redirects/custom headers, password protection — comparable to Netlify or Vercel, but everything stays inside your own AWS account.

Testing

Two levels: unit tests at build time (catch code-level issues), and end-to-end tests using the Cypress framework, defined as build steps in amplify.yml and run against the deployed app — simulating real clicks and interactions to catch regressions before they reach production.

11 AWS Amplify Hands On

  1. Create a new app from a starter template (e.g. a React to-do app) — Amplify clones a starter repo to your own GitHub.
  2. Connect the GitHub provider, authorize Amplify to read the repo, pick the cloned repo/branch, accept the default build settings, and let Amplify auto-create a service role.
  3. Deploying bootstraps the CDK toolkit and deploys several nested CloudFormation stacks behind the scenes — visible under CloudFormation while it builds.
  4. Once built, the app is reachable at the generated domain.

Per-branch UI sections: Deployments, Data Manager (view/create/edit records backed directly by DynamoDB, plus CSV export), User management (Cognito-backed, once an authentication branch is added), Storage (S3-backed), Functions (Lambda-backed), and a UI Library (pre-built components, including Figma-to-React).

Good to know Any code change triggers CI/CD automatically — build and deploy happen without manual intervention.

Cleanup: in App settings → General, delete the app (typing "delete" to confirm) to remove all associated resources; optionally also delete the GitHub repository.

✓ Cheat Sheet

Key facts to remember

  • Step Functions = one state machine per workflow, defined in JSON (Amazon States Language), visualized and executed with full history in the console.
  • Know the state types — Task, Choice, Pass, Wait, Fail/Succeed, Map, Parallel — with Task and Parallel most likely on the exam.
  • Error handling belongs in the state machine (Retry/Catch), not in application code — this keeps Lambda simple and lets error logic change without redeployment.
  • Retry: ErrorEquals, IntervalSeconds, BackoffRate, MaxAttempts (default 3), evaluated top-to-bottom; Catch kicks in once retries are exhausted.
  • Catch: ErrorEquals, Next, and ResultPath (e.g. $.error) to merge error details into the next state's input.
  • .waitForTaskToken = push-based callback (external worker finishes, then calls SendTaskSuccess/Failure with the token).
  • Activity Tasks = pull-based (worker calls GetActivityTask, then SendTaskSuccess/Failure); TimeoutSeconds + HeartbeatSeconds/SendHeartbeat let a task run up to a year.
  • Standard = exactly-once, up to 1 year, ~2,000 exec/sec, priced per state transition — for non-idempotent work like payments.
  • Express Async = at-least-once, fire-and-forget, must handle idempotency yourself. Express Sync = at-most-once, waits for the result, good for a synchronous API response.
  • AppSync = managed GraphQL, direct resolvers for DynamoDB/Aurora/OpenSearch, Lambda/HTTP for anything else, real-time WebSocket support, 4 auth modes (API key, IAM, OIDC, Cognito User Pools) that can be combined.
  • Amplify = CLI/Studio/Libraries/Hosting bundled to build and host full-stack mobile/web apps, backed by Cognito, AppSync + DynamoDB, and S3, with built-in CI/CD and unit + Cypress end-to-end testing.

Mental model

Step Functions turns a scattered set of Lambda calls, DynamoDB writes, and ECS tasks into one visual, auditable state machine — with retries and error handling defined declaratively outside your code, and a choice between exactly-once (Standard) or high-throughput (Express) execution depending on whether you're processing payments or ingesting IoT streams. AppSync answers a different need: a single GraphQL front door over multiple data sources, so clients fetch exactly the shape of data they want. Amplify then wraps the common combination of these — auth, data, and hosting — into one CLI/console experience so you can ship a full-stack app without hand-wiring each AWS service yourself.
