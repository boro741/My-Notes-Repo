1 CloudFormation Overview

CloudFormation lets you outline your entire AWS infrastructure as code. You declare what you want (a security group, two EC2 instances using it, Elastic IPs, an S3 bucket, a load balancer, etc.) and CloudFormation figures out the right order to create everything and links it all together — no manual clicking around.

Why use it

  • Infrastructure as code — nothing created manually, everything version-controlled (e.g. in Git), every change reviewed as a code change.
  • Cost visibility — resources in a stack are tagged with an identifier, so you can see stack-level cost, and even estimate costs from a template before deploying.
  • Savings strategies — e.g. auto-delete a dev environment at 5pm and recreate it at 8am, safely and repeatably.
  • Productivity — destroy and recreate infrastructure on demand; only pay for what's running.
  • Auto-generated diagrams of your architecture, and declarative programming — you don't need to figure out creation order yourself.
  • Separation of concerns — separate stacks for network/VPC, applications, etc.
  • Reuse — leverage existing templates and documentation instead of starting from scratch.

How it works

Templates are uploaded to S3, then referenced from CloudFormation to create a stack — the set of AWS resources it manages as one unit.

  • To update a template, you can't edit the old one in place — upload a new version and update the stack with it.
  • Stacks are identified by name within a region. Deleting a stack deletes everything it created.

2 Stack Hands On: Create, Update & Delete

Don't forget Use us-east-1 (Northern Virginia) for these hands-on templates — AMI IDs are region-specific and the examples are built for that region.

Creating a stack

  • You can start from an existing template, a sample template, or build directly in Application Composer — which lets you visualize a template's resources as connected boxes on a canvas (e.g. a WebServerSecurityGroup, LaunchConfig, database instance, etc.), alongside the raw YAML/JSON code.
  • A minimal template just needs Resources — e.g. one AWS::EC2::Instance named MyInstance with a few properties (availability zone, AMI ID, instance type).
  • Uploading the template file stores it in S3; CloudFormation references it and creates the stack.
  • Once CREATE_COMPLETE, the Resources tab shows each resource's Physical ID, linking straight to it in its own console (e.g. the EC2 console for an instance).
  • Every resource CloudFormation creates gets tagged automatically with the stack ID, logical ID, and stack name.

Updating a stack

  • You can only update by replacing the current template with a new one (or reusing the current one as-is, unmodified).
  • Updating may prompt for new parameters (e.g. a security group description).
  • Before applying, you get a change set preview — a list of what will be added, modified, or replaced. Replacement: true means the old resource is destroyed and a new one created to replace it; false means it can be changed in place.
  • CloudFormation figures out the right order on its own — e.g. creating new security groups and an Elastic IP before replacing the EC2 instance that references them.

Deleting a stack

Clicking Delete on the stack (not manually terminating individual resources) removes every resource it created, in the correct order automatically — much cleaner than trying to manually track down and delete each piece yourself.

3 YAML Crash Course

CloudFormation templates can be written in YAML or JSON — YAML is generally much easier to read (no heavy string interpolation), and is what's used throughout this course.

  • Key-value pairs are the basic building block (e.g. invoice: 1234).
  • Nested objects are created via indentation (e.g. a bill-to key containing given, family, address, etc.).
  • Arrays/lists use a leading dash (-) — e.g. a list of products, or a list of security groups.
  • Multi-line strings use a vertical bar (|).
  • Comments start with #.

In a CloudFormation template, Resources is itself a nested object, each resource (e.g. MyInstance) is a nested object with a Type (string) and a Properties block (another nested object) — and things like SecurityGroups use the dash-list syntax to hold multiple entries.

4 Resources

Resources are the core of any template and the only mandatory section. They represent the AWS components to create/configure, can reference each other, and CloudFormation figures out create/update/delete order for you.

  • There are 700+ resource types, identified as service-provider::service-name::data-type-name (e.g. AWS::EC2::Instance).
  • The CloudFormation documentation for any resource type shows its full syntax, properties (which are required vs optional, their type, and whether changing them causes replacement or no interruption), return values (for Ref / GetAtt), and usage examples in both YAML and JSON.

5 Parameters

Parameters let a template accept inputs from whoever launches it — useful for reusing the same template across teams/environments when the right values can't be known ahead of time.

Exam point Ask yourself: is this configuration likely to change, or impossible to know in advance? If yes to either, make it a parameter — so updating the value never requires re-uploading the whole template.

Parameter settings

Type (String, Number, CommaDelimitedList, List<Number>, AWS-specific type, SSM parameter, etc.), Description, ConstraintDescription, Min/MaxLength, Min/MaxValue, Default, AllowedValues, AllowedPattern (regex), NoEcho, and more.

SettingExample use
AllowedValuesRestrict an InstanceType parameter to only t2.micro/t2.small/t2.medium — gives the user a dropdown, gives you control
NoEcho: trueHide a sensitive parameter value (e.g. a database password) from logs and the console

Referencing parameters: !Ref

The !Ref function (shorthand for Fn::Ref) reads a parameter's value — and can also reference other resources in the template (e.g. !Ref SSHSecurityGroup to reference a security group resource by its logical name).

Don't forget Because !Ref works for both parameters and resources by name, make sure your resource names never collide with your parameter names.

Pseudo parameters

AWS provides built-in values you can !Ref without defining anything: AWS::AccountId, AWS::Region, AWS::StackId, AWS::StackName, AWS::NotificationARNs, AWS::NoValue. Handy so a template can figure out its own account/region without asking the user.

6 Mappings

Mappings are fixed, hardcoded lookup tables in a template — great for differentiating between environments (dev/prod) or regions, when you already know every possible value in advance.

Classic example: a RegionMap giving a different AMI ID per region + architecture combination (since AMIs are region-specific). You look values up with !FindInMap [RegionMap, !Ref "AWS::Region", HVM64] — combining a mapping lookup with a pseudo parameter so the right AMI is chosen automatically based on where the stack is launched.

Use when
MappingsAll possible values are known in advance and can be deduced from things like region, AZ, account, or environment — safer, more controlled
ParametersThe value truly depends on what the user wants at runtime — maximum flexibility

7 Outputs & Exports

The optional Outputs section declares values you want visible after stack creation — viewable in the console or CLI — and, if exported, importable into other stacks.

One stack exports a named output (e.g. a security group ID or VPC ID); another stack imports it with Fn::ImportValue — a clean way to let teams collaborate across separate, focused stacks.

  • Export names must be unique per region.
  • Use Fn::ImportValue (or its shorthand) in the importing template to reference the exported value.
Important You cannot delete a stack whose output is still being imported by another stack — all importing stacks must stop referencing it first.

8 Conditions

Conditions control whether a resource (or output) gets created, based on a condition — e.g. only create an EBS volume in a "prod" stack, but not in a "dev" stack.

  • Common conditions are based on environment (dev/test/prod), region, or a parameter value.
  • Built using functions like And, Equals, If, Not, Or — e.g. CreateProdResources: !Equals [!Ref EnvType, prod].
  • Apply a condition to a resource via its Condition: field — if true, it's created; if false, it isn't.
Good to know For the exam, you just need to know conditions exist and roughly how they're used — you don't need to be able to write complex ones from scratch.

Exam point !Ref vs Fn::GetAtt: Ref gives you the resource's ID; GetAtt gives you a specific documented attribute (e.g. you'd use GetAtt MyInstance.PublicDnsName to create a Route 53 CNAME record pointing at an EC2 instance).

10 Rollbacks

Stack creation failure

OptionBehavior
Roll back all stack resources (default)Everything gets deleted — check the logs to see what failed, but resources are gone
Preserve successfully provisioned resourcesKeeps whatever succeeded, rolls back only the failed resources — useful for troubleshooting, but you must delete the stack afterward rather than fix-and-update it

Stack update failure

By default, the stack automatically rolls back to the last known working state, deleting anything newly created during the failed update.

A failed update normally rolls back automatically; if the rollback itself fails (e.g. due to manually-changed resources), you must fix things by hand and explicitly retry with ContinueUpdateRollback.

Important A rollback failure usually means some resource was manually changed outside of CloudFormation. Fix the resource by hand, then trigger ContinueUpdateRollback (console, API, or CLI) to tell CloudFormation to try rolling back again.

11 Service Role

A CloudFormation service role is an IAM role dedicated to CloudFormation, letting it create/update/delete stack resources on your behalf — useful when you want users to be able to manage stacks without granting them direct permissions on the underlying resources.

The user only needs permission to invoke CloudFormation and pass it the service role; CloudFormation then uses that role's own permissions (e.g. full S3 access) to actually create resources — least-privilege for the user.

Exam point The user must have the iam:PassRole permission — this is what's required to hand a role over to an AWS service like CloudFormation.

If no service role is specified on a stack, CloudFormation just uses your own personal IAM permissions instead.

12 Capabilities

Whenever a template creates or updates IAM resources (users, roles, groups, policies), CloudFormation requires you to explicitly acknowledge it via a capability.

CapabilityWhen to use
CAPABILITY_IAMTemplate creates IAM resources without custom names
CAPABILITY_NAMED_IAMTemplate creates IAM resources with custom names
CAPABILITY_AUTO_EXPANDTemplate uses macros or nested stacks that may transform/change the template before deployment
Don't forget If you get an InsufficientCapabilitiesException, it means the template needs a capability you haven't acknowledged — re-submit with the correct capability checked (console checkbox, or an extra argument in the API/CLI call).

13 Deletion Policy

DeletionPolicy controls what happens to a resource when it's removed from the template or the whole stack is deleted — a way to protect or back up important resources.

Three deletion behaviors: fully delete, keep the resource around untouched, or take a last snapshot before deleting it.

Don't forget DeletionPolicy: Delete on an S3 bucket only works if the bucket is empty — otherwise the delete fails. You'd need to empty it manually first, or use a Custom Resource to empty it automatically.

Snapshot is supported by EBS volumes, ElastiCache Cluster/ReplicationGroup, RDS DBInstance/DBCluster, Redshift, Neptune, DocumentDB, and more.

14 Stack Policy & Termination Protection

Stack Policy

By default, a stack update can change any resource. A Stack Policy (a JSON document) restricts which update actions are allowed on which resources during updates — protecting critical resources from unintentional changes.

Example: Allow Update:* on everything, then Deny Update:* specifically on a resource named ProductionDatabase — everything is updatable except that one protected resource.

Exam point Once you set a Stack Policy, all resources are protected by default — you must add explicit Allow statements for anything you still want to be updatable.

Termination Protection

A simple toggle on a stack that prevents accidental deletion — while enabled, attempting to delete the stack fails until you first disable termination protection.

15 Custom Resources

Custom Resources let you define resources CloudFormation doesn't natively support, or run custom logic during create/update/delete — including things outside CloudFormation entirely (on-premises resources, third-party resources) via Lambda functions.

  • Defined with type Custom::MyCustomResourceTypeName, backed by either a Lambda function (most common) or an SNS topic (must be in the same region).
  • A ServiceToken property points to the Lambda/SNS ARN; input data parameters can pass values into the Lambda.

Classic exam use case: CloudFormation can't delete a non-empty S3 bucket, so a Custom Resource backed by Lambda empties it first — only then can CloudFormation successfully delete the (now-empty) bucket.

16 StackSets

StackSets let you create, update, or delete stacks across multiple accounts and regions from a single operation/template.

A single StackSet operation fans out the same stack to many accounts and regions at once — updating the StackSet updates every stack instance in every target account/region.

  • A very common use case is applying a StackSet to all accounts within an AWS Organization.
  • Only an administrator account (or a designated administrator) within the organization can create StackSets — otherwise it would be a security risk.

✓ Cheat Sheet

Key facts to remember

  • Resources is the only mandatory template section; templates upload to S3 and CloudFormation references them to create a stack.
  • YAML is preferred over JSON for readability; nested objects via indentation, lists via -.
  • Use a Parameter when a value might change or can't be known in advance; use a Mapping when all values are already known (e.g. per-region AMI IDs).
  • Outputs + Export let one stack's values be imported into another via Fn::ImportValue — you can't delete a stack whose export is still imported elsewhere.
  • Conditions (And/Equals/If/Not/Or) control whether a resource gets created.
  • !Ref → parameter value or resource physical ID. Fn::GetAtt → a specific documented attribute of a resource.
  • Stack creation failure → rolls back (deletes) everything by default, or optionally preserves successful resources for troubleshooting. Stack update failure → auto-rollback; if the rollback itself fails, fix manually + ContinueUpdateRollback.
  • Service Role = an IAM role CloudFormation assumes to act on your behalf; the user just needs iam:PassRole — least-privilege for users creating stacks.
  • Capabilities (CAPABILITY_IAM / CAPABILITY_NAMED_IAM / CAPABILITY_AUTO_EXPAND) must be acknowledged when a template creates IAM resources or uses macros/nested stacks.
  • DeletionPolicy: Delete (default; S3 buckets must be empty first), Retain (keep it), Snapshot (final backup then delete — EBS, RDS, ElastiCache, etc.).
  • Stack Policy protects specific resources from updates (deny-by-default once set); Termination Protection guards the whole stack from accidental deletion.
  • Custom Resources (backed by Lambda or SNS) handle anything CloudFormation can't natively do — classic example: emptying an S3 bucket before stack deletion.
  • StackSets deploy/update/delete the same stack across many accounts and regions at once — only an admin account in an AWS Organization can create them.

Mental model

CloudFormation turns "click around the console" into "describe what you want in a file" — you write resources (the only required piece), optionally make parts configurable (parameters), fixed-but-varying-by-context (mappings), conditional (conditions), or exposed for reuse (outputs); CloudFormation then figures out ordering, handles safe rollbacks when things go wrong, and — through service roles, capabilities, deletion policies, stack policies, and termination protection — gives you fine-grained control over who can change what and how safely resources are removed. Custom Resources and StackSets extend that same declarative model to things CloudFormation doesn't natively support, and to entire fleets of accounts and regions at once.
