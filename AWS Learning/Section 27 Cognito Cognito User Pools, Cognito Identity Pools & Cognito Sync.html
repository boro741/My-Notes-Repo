1 Cognito Overview

Cognito gives an identity to users outside your AWS account, so they can interact with your web/mobile applications. IAM is for people/systems inside your AWS account; Cognito is for the (potentially huge number of) end users of your app.

ServicePurpose
Cognito User Pools (CUP)Sign-in/sign-up for app users — integrates natively with API Gateway and ALB
Cognito Identity Pools (Federated Identities)Issues temporary AWS credentials to app users so they can access AWS resources directly
Exam point Look for keywords like "hundreds/thousands of app users," "mobile users," or "authenticate with SAML/social login" — that's Cognito, not IAM.

2 Cognito User Pools

A serverless user database for your web/mobile app — handles sign-up, sign-in, password reset, email/phone verification, MFA, and social/SAML login ("Federated Identities" at the login level).

  • Can block sign-in if a user's credentials were found compromised elsewhere on the web.
  • On successful login, returns a JWT (JSON Web Token).

Users log in directly against the user pool (or via a federated social/SAML/OIDC provider) and get back a JWT to use with the rest of the app.

AWS integrations

  • API Gateway — user authenticates with CUP, gets a JWT, passes it to API Gateway, which validates it before allowing the backend call.
  • Application Load Balancer — ALB listener rules can authenticate against CUP directly before forwarding to the target group (EC2/Lambda/ECS).

3 User Pools — Hands On

  • Create a user pool: choose app type (traditional web app, SPA, mobile, machine-to-machine), sign-in option (email/phone/username), required attributes, and a post-signup redirect URL.
  • Console sections: Users (manually add/view), Groups, Authentication methods (email/SMS verification, password policy, passkeys), Sign-in experience (MFA required/optional), Sign-up (verification, custom attributes), Federated identity providers (Google/Facebook/Amazon/Apple/SAML/OIDC), Extensions (Lambda triggers), Security (WAF, threat protection, log streaming), Branding (custom domain, Managed Login styling).
Good to know Cognito's own email sending is capped at 50/day — meant for testing only. Use Amazon SES for production email verification.

The Managed Login (formerly "Hosted UI") gives you a ready-made, customizable sign-in page — no need to build your own auth screens. Testing it: sign up with an email → Cognito sends a verification code → entering it flips the user from unconfirmed/unverified to confirmed/verified in the Users list, then redirects to your configured callback URL.

4 User Pools — Other Features

Custom messageCustomize the text of verification/notification messages

Custom domains

Important exam point A custom domain for the Hosted UI/Managed Login requires an ACM certificate in us-east-1 — regardless of which region your user pool actually lives in.

Adaptive authentication

Each sign-in gets a risk score (low/medium/high) based on factors like device, location, and IP address. A normal login proceeds as usual; a suspicious one can be blocked or prompted for MFA — all visible in CloudWatch Logs (sign-in attempts, risk scores, failed challenges).

JWT structure

A JWT is three Base64-encoded parts; the payload holds user info (e.g. the "sub" UUID = the user's ID in the Cognito database), but you must verify the signature before trusting anything in it.

Use the sub (UUID) from the payload to look up additional stored attributes (email, name, phone, custom attributes) back in the Cognito user pool database.

5 ALB User Authentication

An ALB can authenticate users itself — offloading that responsibility from your application entirely.

MethodUse for
authenticate-cognitoCognito User Pools — social logins (Amazon/Facebook/Google) or corporate (SAML/LDAP/Microsoft AD) via CUP federation
authenticate-oidcAny OIDC-compliant identity provider directly, without Cognito
  • Requires an HTTPS listener.
  • For unauthenticated requests, choose: prompt to authenticate (default), deny, or allow (useful for a login page itself, which must be reachable before authentication).

With Cognito integration, the ALB authenticates the user and forwards the request to the backend enriched with the authenticated user's info — your app doesn't need to implement auth itself.

The OIDC path is more involved: ALB redirects to the IdP's authorization endpoint → gets an auth code → exchanges it at the token endpoint for ID/access tokens → calls the user info endpoint for claims → forwards the original request + claims to the backend.

6 Cognito Identity Pools

Identity Pools (aka Federated Identities) give app users temporary AWS credentials so they can call AWS services directly (S3, DynamoDB, etc.) — without creating an IAM user per app user (doesn't scale, doesn't make sense for untrusted external users).

The app logs in with any supported provider, exchanges that token with the identity pool, which calls STS to mint scoped temporary AWS credentials for the app to use directly.

  • Supported login sources: Cognito User Pools, social providers (Amazon/Facebook/Google/Apple), OIDC, SAML, or a custom developer-authenticated backend.
  • Also supports fully unauthenticated guest access via a guest IAM role/policy.
  • API call behind the scenes: STS's AssumeRoleWithWebIdentity — the IAM role must trust Cognito Identity Pools.

Fine-grained access with policy variables

Scope a role's IAM policy to the individual user via a policy variable — e.g. restrict S3 access to only objects under a prefix matching the user's ID, or restrict DynamoDB access to only rows where the partition key equals the user's ID (row-level security).

7 Identity Pools — Hands On

  1. Create an identity pool, enabling authenticated access (choose a source — e.g. an existing Cognito User Pool) and/or guest access.
  2. Create an authenticated role and an unauthenticated (guest) role — these define what each type of user can actually do in AWS.
  3. Specify the CUP's pool ID + app client ID if using it as the login source; choose whether all authenticated users share one role, or use rules/attribute mapping to assign different roles per user.

The actual app-side flow (SDK auth → exchange for credentials) happens in application code. In the console, the important piece is going to IAM → Roles and editing the two auto-created Cognito roles to attach the exact permissions (inline or managed policies) your authenticated/guest users should have.

The classic combo: User Pool handles "who are you," Identity Pool converts that verified identity into scoped, temporary AWS access.

Exam point A mobile app that just needs a user database → Cognito User Pools. A mobile app whose users need to call DynamoDB/S3 directly → Cognito Identity Pools (typically fed by a User Pool for the login step).

✓ Cheat Sheet

Key facts to remember

  • Cognito = identity for users outside your AWS account (app/mobile users), not to be confused with IAM (which is for principals inside your account).
  • User Pools = authentication (login database + JWT); Identity Pools = authorization (temporary AWS credentials via STS).
  • User Pools support social login (Google/Facebook/Amazon/Apple), SAML, and OIDC federation, plus MFA, adaptive (risk-based) authentication, and Lambda triggers at nearly every stage of the auth/signup flow.
  • Custom domains for the Hosted UI/Managed Login always need an ACM cert in us-east-1, regardless of the pool's actual region.
  • ALB can authenticate users directly via authenticate-cognito (CUP-backed) or authenticate-oidc (any OIDC IdP) — offloading auth from your app entirely.
  • Identity Pools issue credentials via STS's AssumeRoleWithWebIdentity; IAM policies can use policy variables (e.g. the user ID) for per-user, row/prefix-level access control in S3/DynamoDB.
  • Identity Pools support guest (unauthenticated) access with their own dedicated IAM role.
  • The classic combo: User Pool authenticates → its token is exchanged with an Identity Pool → Identity Pool calls STS → app gets scoped, temporary AWS credentials.

Mental model

Cognito answers two separate questions for people outside your AWS account: "who are you" (User Pools — a managed login database with JWTs, MFA, and social/SAML federation) and "what can you touch in AWS" (Identity Pools — exchanging a verified identity for scoped, temporary AWS credentials via STS). They're bundled under one product name but solve genuinely different problems, and the standard pattern chains them together: authenticate with a User Pool, then trade that token for real AWS access through an Identity Pool — with IAM policy variables keeping each user confined to only their own data.
