1 SAM Overview

SAM (Serverless Application Model) is a framework for developing and deploying serverless applications — you write a simpler YAML template, and SAM generates the (much more verbose) CloudFormation behind it.

A short SAM template, tagged with a Transform header, expands into the equivalent (much longer) raw CloudFormation — you write less, get the same result.

  • Supports everything CloudFormation does (outputs, mappings, parameters, resources) plus simpler serverless-specific constructs:
SAM constructBecomes
AWS::Serverless::FunctionLambda function
AWS::Serverless::ApiAPI Gateway
AWS::Serverless::SimpleTableDynamoDB table
  • Behind the scenes SAM can use CodeDeploy to deploy Lambda functions, and can run Lambda/API Gateway/DynamoDB locally for testing.
  • Deployment: sam deploy (used to be sam package + sam deploy separately — now just one command that packages and deploys).

SAM Accelerate

sam sync reduces deployment latency by (optionally) bypassing CloudFormation for pure code changes, updating Lambda directly via its service API — much faster than a full stack update.

CommandWhat it syncs
sam syncCode + infrastructure (via CloudFormation)
sam sync --codeOnly code (bypasses CloudFormation, updates in seconds)
sam sync --watchRuns in the background, auto-syncs on file changes

2 SAM — Hands On

  • sam init scaffolds a new project — choose a quick-start template (e.g. "Hello World"), runtime (e.g. Python), and project name.

Key generated files

FilePurpose
hello_world/app.pyYour actual Lambda function code
requirements.txtPython dependencies
samconfig.tomlSAM CLI config (stack name, build params, etc.)
template.yamlThe SAM template itself — starts with a Transform header, defines Serverless::Function resources with code URI, handler, runtime

Workflow

  1. sam build — builds the application locally (pulls dependencies, prepares a .aws-sam/build directory).
  2. sam deploy --guided — walks you through stack name, region, confirming changes, IAM role creation, and saves your answers to samconfig.toml for next time.
Good to know The first guided deploy also provisions supporting resources for SAM itself (an S3 bucket for artifacts, an IAM role) before deploying your actual application stack.

End result: a Lambda function + API Gateway are created automatically — hitting the API's invoke URL (via browser or curl) returns your function's response.

3 SAM with DynamoDB — Hands On

Using the "serverless API" quick-start template generates a fuller example: multiple Serverless::Function resources (e.g. getAllItemsFunction, a "put" function), each with its own runtime, memory, policy, and API event (GET/POST on a path) — plus an AWS::Serverless::SimpleTable resource (a DynamoDB table, with primary key and provisioned RCU/WCU) that the functions reference.

Exam point Defining a DynamoDB CRUD policy on a function, referencing the table by name, is a single short block in SAM — compare that to writing the equivalent IAM policy JSON by hand in raw CloudFormation.

SAM's local capabilities let you test without deploying: sample events live in an events/ folder, which you can feed into sam local invoke, or run sam local start-api to get a local HTTP server hosting your whole API (requires Docker).

Don't forget If you deploy this example to try it out, clean up afterward with sam delete.

4 SAM Policy Templates

Policy templates are pre-built, named permission sets you can attach to a Lambda function in SAM — instead of writing raw IAM policy JSON yourself.

TemplateGrants
S3ReadPolicyRead-only access to objects in S3
SQSPollerPolicyPermission to poll an SQS queue
DynamoDBCrudPolicyCreate, Read, Update, Delete on a DynamoDB table

You just reference the template name plus the target resource (e.g. a queue name) in your SAM template, and SAM transforms it into the equivalent IAM policy attached to the function's execution role — much less to reason about than hand-writing IAM JSON.

Good to know You don't need to memorize the full list — just recognize the pattern once (name is usually self-explanatory) and know these templates exist as a SAM shortcut for common permissions.

5 SAM with CodeDeploy

SAM can use CodeDeploy under the hood to update Lambda functions via alias traffic-shifting, with optional pre/post-traffic validation hooks and automated rollback via CloudWatch alarms.

SAM/CodeDeploy shifts an alias from v1 to v2 gradually, optionally running validation Lambda functions before and after the shift, with a CloudWatch alarm able to trigger a rollback.

Key template settings

SettingPurpose
AutoPublishAliasTells SAM to auto-publish a new version + update the named alias whenever new code is deployed
DeploymentPreference.TypeCanary, Linear, or AllAtOnce (e.g. Canary10Percent10Minutes)
AlarmsCloudWatch alarms that trigger an automatic rollback if breached
HooksPre/post-traffic Lambda functions for custom validation

Hands-on: with Canary10Percent10Minutes configured, redeploying updated code creates v2, shifts 10% of traffic to it via the alias for 10 minutes (visible live in the CodeDeploy console as a blue/green Lambda deployment), then automatically completes the cutover to 100% once that window passes.

6 SAM Local Capabilities

CommandPurpose
sam local start-lambdaRuns a local Lambda emulator as an endpoint — useful for automated tests against it
sam local invokeInvokes a function once with a given payload, then exits — good for one-off test cases; use --profile if the function calls other AWS services
sam local start-apiStarts a local HTTP server hosting your whole API — auto-reloads functions as you edit code
sam local generate-eventGenerates a sample event payload for a given source (S3, API Gateway, SNS, Kinesis, DynamoDB, etc.) — pipe it straight into sam local invoke
Good to know This lets you iterate entirely on your own machine — writing code, testing against local Lambda/API Gateway emulation — and only deploy to AWS once you're happy.

7 SAM Multiple Environments

Manage separate deploy targets (dev, prod, etc.) using named sections in samconfig.toml — each with its own stack name, S3 bucket, region, capabilities, and parameter overrides.

Separate named sections in samconfig.toml hold different deployment parameters per environment, selected at deploy time with a single flag.

Deploy to a specific environment with:

  • sam deploy --config-env dev
  • sam deploy --config-env prod

You can define as many environments as you need — SAM CLI picks the matching section from samconfig.toml automatically.

✓ Cheat Sheet

Key facts to remember

  • SAM = a simplified YAML layer on top of CloudFormation, specifically for serverless apps (Lambda, API Gateway, DynamoDB).
  • Every SAM template needs a Transform header identifying it as a SAM template.
  • Core constructs: Serverless::Function (Lambda), Serverless::Api (API Gateway), Serverless::SimpleTable (DynamoDB).
  • Workflow: sam init → sam build → sam deploy --guided (or plain sam deploy once samconfig.toml exists).
  • sam sync (SAM Accelerate) speeds up dev-loop deployments; --code bypasses CloudFormation entirely for pure code changes.
  • Policy templates (S3ReadPolicy, SQSPollerPolicy, DynamoDBCrudPolicy, etc.) simplify granting Lambda functions specific permissions without hand-writing IAM JSON.
  • SAM integrates with CodeDeploy for Lambda alias traffic-shifting (AutoPublishAlias + DeploymentPreference: Canary/Linear/AllAtOnce), with optional pre/post-traffic hooks and CloudWatch alarm-triggered rollback.
  • Local testing: sam local start-lambda, sam local invoke, sam local start-api, sam local generate-event — all runnable without deploying anything.
  • Multiple environments are managed via named sections in samconfig.toml, selected with sam deploy --config-env <name>.

Decision guide

NeedUse
Write less boilerplate than raw CloudFormation for a serverless appSAM templates
Grant a Lambda function common permissions quicklySAM policy templates
Roll out a new Lambda version safely with automatic rollbackSAM + CodeDeploy (Canary/Linear DeploymentPreference)
Test Lambda/API Gateway without deployingSAM local commands
Deploy the same app to dev and prod with different settingssamconfig.toml + --config-env
Fast dev-loop iteration on code-only changessam sync --code --watch

Mental model

SAM is CloudFormation with the serverless-specific boilerplate pre-written for you: a handful of simple constructs (function, API, table) expand into the full stack of resources, permissions, and wiring that raw CloudFormation would otherwise require you to spell out by hand. Everything else in this section — policy templates, CodeDeploy integration, local emulation, multi-environment configs — exists to make the developer loop (write code → test locally → deploy safely → repeat for each environment) as short as possible without ever leaving the SAM CLI.
