1 S3 Encryption Overview

There are four ways to encrypt objects in S3. The exam wants you to know exactly when to use which.

MethodWho manages the keyRequired headerNotes
SSE-S3AWS (you never see the key)x-amz-server-side-encryption: AES256Default for new buckets/objects. Encryption type is AES-256.
SSE-KMSYou, via AWS KMSx-amz-server-side-encryption: aws:kmsYou control the key; usage is logged in CloudTrail. Reading/writing needs KMS API calls (GenerateDataKey, Decrypt), which count against KMS quotas.
SSE-CYou, entirely outside AWSKey passed in HTTP headers, every requestS3 never stores your key — it's used once then discarded. Must use HTTPS.
Client-side encryptionYou, fullyN/A — nothing sent to AWS about encryptionData is encrypted before it ever leaves the client, and decrypted after download, all client-side (e.g. via the Client-Side Encryption Library).

The four encryption paths differ only in who holds the key and where encryption happens — S3, KMS, the client with a custom key, or the client entirely on its own.

Exam point SSE-KMS can hit API throttling on very high-throughput buckets, because every encrypt/decrypt is a call to KMS (5,000–30,000 requests/sec depending on region, though this can be raised via Service Quotas).

Encryption in transit (SSL/TLS)

  • S3 has both an HTTP endpoint (unencrypted) and an HTTPS endpoint (encrypted in flight).
  • SSE-C requires HTTPS — you can't use it over plain HTTP.
  • To force HTTPS-only access, attach a bucket policy that denies any request where aws:SecureTransport is false.
Good to know A short companion note in the transcript mentions DSSE-KMS ("double" SSE-KMS, released June 2023) — essentially KMS encryption applied twice for extra strength. The instructor doesn't teach it in depth since it wasn't (at time of recording) an exam topic.

2 S3 Encryption Hands On

  • When creating a bucket, you must choose a default encryption: SSE-S3, SSE-KMS, or DSSE-KMS.
  • Uploaded objects inherit the bucket's default encryption — visible under the object's Properties → Server-side encryption settings.
  • You can override the encryption for an individual object (Properties → Edit). If versioning is enabled, editing the encryption creates a new version of the object rather than modifying it in place.
  • For SSE-KMS, you pick a KMS key — either your own (costs money monthly) or the default aws/s3 key AWS provides for free.
  • SSE-KMS has a Bucket Key option that reduces KMS API calls (and therefore cost) — enabled by default. It has no effect if you're just using SSE-S3.
Don't forget SSE-C is not available in the console at all — you can only use it via the CLI/SDK. Client-side encryption also isn't a console setting, since it happens entirely outside AWS before upload.

3 S3 Default Encryption vs Bucket Policies

  • Every bucket now defaults to SSE-S3 automatically for new objects — but you can change the default to something else, like SSE-KMS.
  • You can also force encryption using a bucket policy — e.g. deny any PutObject call that's missing the correct encryption header (like the KMS or SSE-C header).
Exam point Bucket policies are evaluated before default encryption settings. So a policy can reject an upload outright if it doesn't meet your encryption requirements, regardless of what the bucket's default encryption is set to.

4 S3 CORS

CORS = Cross-Origin Resource Sharing — a browser-level security mechanism, not an S3-specific one. It comes up as one exam question, so it's worth understanding properly.

  • An origin = scheme (protocol) + host (domain) + port. E.g. for https://www.example.com, the port is implied to be 443, protocol is HTTPS, and the host is www.example.com.
  • Two URLs share the same origin only if scheme, host, and port all match.
  • If a browser on one origin tries to fetch resources from a different origin, that request will be blocked unless the other origin explicitly allows it via Access-Control-Allow-Origin headers.

Before fetching a resource from a different origin, the browser sends a preflight request asking permission; only if the target origin's CORS headers allow it does the real request go through.

How this applies to S3

If a static website hosted on one S3 bucket needs to pull assets (images, etc.) from another S3 bucket, that's a cross-origin request. Unless the asset bucket's CORS configuration explicitly allows the website's origin, the browser will block the request.

Exam point Quick fix: configure CORS on the target S3 bucket to allow the specific origin, or use * to allow all origins.

5 S3 CORS Hands On

  1. Bucket A hosts a static website (index.html) that fetch()es an extra-page.html file.
  2. While extra-page.html lives in the same bucket, the fetch works fine — same origin, no CORS needed.
  3. Move extra-page.html to a different bucket (in another region, made public, also hosting a static website) and point index.html's fetch at that bucket's URL instead.
  4. Reloading the page now shows no visible error, but the browser's developer console reveals: Cross-Origin Request Blocked — missing Access-Control-Allow-Origin header.
Don't forget The fix is to add a CORS configuration (JSON) on the bucket being fetched from, listing the requesting bucket's website URL (no trailing slash) under AllowedOrigins.

After saving the CORS config, refreshing the page loads the extra page successfully. In the browser's Network tab, the response now includes Access-Control-Allow-Methods: GET and Access-Control-Allow-Origin matching the requesting bucket's origin — proof CORS is now correctly configured.

6 S3 MFA Delete

MFA Delete forces a user to provide a code from their MFA device (phone app, hardware token, etc.) before certain destructive operations can happen.

OperationMFA required?
Permanently delete an object versionYes
Suspend versioning on the bucketYes
Enable versioningNo
List deleted versionsNo
Don't forget Versioning must already be enabled to use MFA Delete. And crucially: only the bucket owner (root account) can enable or disable MFA Delete — and it can only be done via the CLI, not the console UI.

Hands-on recap

  • Requires setting up an MFA device on the root account beforehand, plus temporary root access keys just for this one operation (delete them immediately afterward!).
  • Enable via CLI: put bucket versioning with MfaDelete=Enabled, passing the MFA device ARN and a current MFA code.
  • Once enabled, normal object deletes (adding a delete marker) still work fine — but permanently deleting a specific version ID is blocked unless a valid MFA code is supplied via the CLI.
  • Disabling it uses the same CLI command with MfaDelete=Disabled (and a fresh MFA code).
Important Using the root account and root access keys is generally discouraged — this is one of the few legitimate reasons to do so. Deactivate/delete the temporary root access keys as soon as you're done.

7 S3 Access Logs

For audit purposes, S3 can log every request made to a bucket (authorized or denied, from any account) into log files stored in another S3 bucket. You can then analyze those logs with a tool like Amazon Athena.

  • The logging (target) bucket must be in the same AWS region as the bucket being monitored.
  • Enabling logging automatically updates the target bucket's policy to allow the S3 logging service to write into it.
  • Logs aren't instant — it can take a while (the instructor mentions a couple of hours) before the first log files show up.
Don't forget Never set a bucket's logging destination to be itself. That creates an infinite logging loop — every log write generates another log entry, which generates another, and so on — and your storage costs will explode.

8 S3 Pre-signed URLs

A pre-signed URL is a temporary, signed link to a specific S3 object. Whoever holds the URL inherits the permissions of whoever generated it (for a GET or a PUT) — even if the bucket/object is otherwise private.

Generated viaMax expiration
S3 ConsoleUp to 12 hours
CLIUp to 168 hours

The owner signs a URL carrying their own permissions, then hands it to someone who otherwise has no access — the URL works only until it expires.

Use cases

  • Only allow logged-in users to download a premium video from a private bucket.
  • Dynamically generate download links for an ever-changing list of users.
  • Temporarily allow a specific user to upload a file to a specific location, while keeping the bucket private overall.

Hands-on: generating one from the console

  1. Select the object → Object actions → Share with a pre-signed URL.
  2. Pick an expiration (minutes or hours).
  3. The generated URL can be shared with anyone — they get access to that one object until it expires, even though the bucket stays private.

9 S3 Access Points

A bucket with lots of different data (finance, sales, etc.) and lots of different user groups can end up with one giant, unmanageable bucket policy. S3 Access Points solve this by splitting security management into smaller, focused pieces.

Each access point has its own policy scoped to a prefix and permission level — finance and sales teams each get their own door, analytics gets a read-only door into both.

  • Each access point gets its own DNS name and its own attached policy (very similar in structure to a bucket policy).
  • An access point can be reachable from the internet or scoped to a VPC for private traffic only.
  • Result: a much simpler bucket policy overall, plus individually scoped, easier-to-manage access point policies — this is how you scale S3 access management.

VPC origin for access points

  • To let an EC2 instance in a VPC reach an access point privately (without going over the public internet), create a VPC endpoint.
  • The VPC endpoint has its own policy that must allow access to both the target bucket and the access point.
  • End result: three layers of security working together — the VPC endpoint policy, the access point policy, and the S3 bucket policy.

10 S3 Object Lambda

What if different applications need different versions of the same object — without duplicating the whole bucket? S3 Object Lambda builds on access points to transform objects on the fly, as they're retrieved.

One bucket, one set of objects — but different apps get different transformed versions on the fly via S3 Object Lambda, instead of storing multiple copies.

How it works

  1. App calls an S3 Object Lambda access point (instead of the bucket/regular access point directly).
  2. This invokes a Lambda function, which fetches the original object from S3 and runs custom code on it.
  3. The transformed result is what the calling app actually receives.

Use cases

  • Redact PII (personally identifiable information) for analytics or non-production environments.
  • Convert data formats on the fly (e.g. XML → JSON).
  • Resize or watermark images dynamically — even with a watermark specific to the requesting user.
  • Enrich objects with extra data (e.g. looking up a customer loyalty database) for a marketing app, without duplicating the bucket.

✓ Cheat Sheet

Key facts to remember

  • 4 encryption types: SSE-S3 (AWS key, default), SSE-KMS (your KMS key, CloudTrail logging, watch KMS quotas), SSE-C (your own key, HTTPS required, CLI/SDK only), client-side (fully outside AWS).
  • Bucket policies are evaluated before default encryption settings — a policy can force/require encryption regardless of the default.
  • CORS is a browser security feature; fix cross-bucket asset loading by adding a CORS config on the bucket being fetched from, allowing the requesting origin (or *).
  • MFA Delete guards permanent version deletes and versioning suspension; only the root account can toggle it, and only via CLI.
  • Access logs go to a bucket in the same region; never point a bucket's logs at itself (infinite loop).
  • Pre-signed URLs inherit the signer's permissions; console max 12 hours, CLI max 168 hours.
  • Access Points let you split one bucket policy into many smaller, scoped policies (per prefix, per user group); each has its own DNS name and can be internet- or VPC-facing.
  • S3 Object Lambda = access point + Lambda function, to transform objects on the fly (redact, enrich, convert, watermark) without duplicating data.

Mental model

This section is all about controlling exactly who can touch your S3 data, and how it's protected while at rest and in transit: encryption (in its four flavors) protects the bytes themselves; CORS controls which websites' browsers are allowed to fetch your objects; MFA Delete and access logs are safety nets against accidental or malicious changes and give you an audit trail; pre-signed URLs let you hand out narrow, time-boxed access without touching bucket-wide permissions; and access points (plus Object Lambda on top) let a single bucket serve many different teams and use cases securely, each with their own door and — if needed — their own on-the-fly transformed view of the data.
