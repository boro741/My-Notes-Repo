1 S3 Encryption Overview

Encryption scrambles your plain data into secret code so unauthorized users cannot read it. Encryption at Rest protects data sitting on physical disks inside AWS data centers. Amazon S3 provides four main ways to encrypt objects at rest. The exam tests whether you know exactly when to use each method.

Encryption MethodWho Manages the KeyRequired HTTP HeaderKey Details
SSE-S3AWS manages keys completelyx-amz-server-side-encryption: AES256Default encryption for all new S3 buckets/objects. Uses military-grade AES-256 encryption. Fully automatic and free.
SSE-KMSYou manage keys via AWS KMSx-amz-server-side-encryption: aws:kmsYou control key access policies and audit usage via AWS CloudTrail logs. Each upload/download calls KMS APIs (GenerateDataKey, Decrypt), which count towards KMS quota limits.
SSE-CYou manage keys outside AWSKey provided in HTTP headers on every requestAWS never stores your encryption key. S3 uses the key to encrypt/decrypt once and discards it immediately. Requires HTTPS connection.
Client-Side EncryptionYou manage everything locallyNone (S3 receives already encrypted data)Data is encrypted on your local machine/app before uploading to S3, and decrypted locally after downloading. AWS sees only scrambled bytes.

The 4 encryption options differ by who holds the key and where encryption occurs — inside S3, via KMS, on client with custom key header, or fully on client side.

Exam Point High-volume applications using SSE-KMS can hit KMS API Throttling limits (5,000 to 30,000 requests/sec depending on region). This is because every read/write triggers a call to KMS to generate or decrypt data keys.

Encryption in Transit (SSL/TLS)

  • Encryption in Transit protects data traveling over the internet between client and S3 using SSL/TLS (HTTPS).
  • S3 provides unencrypted HTTP endpoints and encrypted HTTPS endpoints. SSE-C strictly requires HTTPS.
  • To force HTTPS-only connections, attach an S3 bucket policy denying requests where aws:SecureTransport condition is false.
Good to Know AWS also supports DSSE-KMS (Dual-layer Server-Side Encryption with KMS), which applies two layers of KMS encryption for high-security compliance needs.

2 S3 Encryption Hands On

  • When creating an S3 bucket, you set default encryption to SSE-S3 or SSE-KMS.
  • Uploaded objects automatically inherit the bucket's default encryption settings, visible under object Properties → Server-side encryption settings.
  • You can override default encryption for individual objects. If S3 Versioning is enabled, changing an object's encryption type creates a new object version.
  • When selecting SSE-KMS, you can use your custom KMS Customer Managed Key (CMK) or AWS's default aws/s3 key.
  • Enabling the S3 Bucket Key setting for SSE-KMS reduces KMS API request volume and cuts KMS costs up to 99%.
Important Warning SSE-C is not available in the AWS Management Console UI. It can only be configured via AWS CLI or SDK code. Similarly, client-side encryption is handled entirely in application code before uploading.

3 S3 Default Encryption vs Bucket Policies

  • Every S3 bucket automatically applies SSE-S3 default encryption to newly uploaded objects unless configured otherwise.
  • You can enforce strict encryption rules using an S3 Bucket Policy — for example, denying s3:PutObject requests that lack proper encryption headers (such as requiring SSE-KMS headers).
Exam Point S3 Bucket Policies are evaluated before default encryption settings. If an incoming file upload violates a bucket policy encryption condition, S3 denies the upload immediately before default encryption can process it.

4 S3 CORS (Cross-Origin Resource Sharing)

CORS is a standard web browser security rule that restricts web pages from requesting resources from a different domain origin than the one serving the web page.

  • An Origin consists of: Scheme (Protocol) + Host (Domain) + Port Number.
    Example: In https://www.example.com:443, Scheme = https, Host = www.example.com, Port = 443.
  • Two URLs share the same origin only when their scheme, host domain, and port number match exactly.
  • If a browser running a web app on www.example.com attempts to fetch images or assets from www.other-domain.com, the browser blocks the request unless www.other-domain.com returns explicit Access-Control-Allow-Origin CORS headers permitting access.

Before requesting assets across different domains, the browser sends an HTTP OPTIONS preflight request. If CORS headers approve, the main request executes.

How CORS Applies to S3

If a static website hosted on one S3 bucket fetches images, fonts, or scripts from a second S3 bucket, web browsers block the fetch call as cross-origin. To fix this, configure the second S3 bucket's CORS Configuration to allow requests from the first website's origin URL.

Exam Point "Website on S3 Bucket A cannot load images from S3 Bucket B due to browser error." → Fix by configuring CORS on Bucket B to explicitly allow Bucket A's origin domain (or * for all origins).

5 S3 CORS Hands On

  1. Bucket A hosts a static website running JavaScript fetch() to load extra-page.html.
  2. When extra-page.html resides in the same bucket (Bucket A), requests succeed because they share the same origin.
  3. Moving extra-page.html to a different bucket (Bucket B) causes the browser developer console to log a Cross-Origin Request Blocked error due to missing CORS headers.
  4. To resolve the error, add a JSON CORS Configuration to Bucket B, putting Bucket A's website origin URL under AllowedOrigins:
CORS JSON Configuration Example [{"AllowedHeaders":["*"],"AllowedMethods":["GET"],"AllowedOrigins":["http://bucket-a.s3-website.us-east-1.amazonaws.com"],"ExposeHeaders":[]}]

Once saved, refreshing Bucket A's webpage allows it to fetch extra-page.html successfully. Response headers include Access-Control-Allow-Origin matching Bucket A's URL.

6 S3 MFA Delete

MFA (Multi-Factor Authentication) Delete requires entering an 6-digit OTP code from an authenticator device (like Google Authenticator app or hardware token) before performing destructive bucket operations.

S3 Bucket OperationIs MFA Code Required?
Permanently deleting an object versionYes
Suspending Versioning on the bucketYes
Enabling Versioning for the first timeNo
Listing deleted object versionsNo
Crucial Requirement S3 Versioning must be enabled on the bucket to use MFA Delete. Crucially: ONLY the Root Account owner can enable or disable MFA Delete — and it can ONLY be configured via AWS CLI (not via the AWS Console UI).

Step-by-Step Implementation

  • Configure MFA on your AWS Root Account and generate temporary root access keys (delete access keys immediately after setup!).
  • Run the AWS CLI command aws s3api put-bucket-versioning with --versioning-configuration Status=Enabled,MFADelete=Enabled, passing the root MFA device serial number and live 6-digit code.
  • Once active, standard object deletion (which adds a soft Delete Marker) works normally. However, permanently deleting a specific version ID is blocked unless authorized with a valid root MFA code via CLI.

7 S3 Access Logs

For compliance and security auditing, S3 Server Access Logging records every request made to your bucket (authorized access, access denied, reads, writes, across any AWS account). Logs are saved as log files in a target S3 bucket, which you can query using Amazon Athena (SQL analytics service).

  • The target logging bucket must reside in the same AWS Region as the source bucket being monitored.
  • Enabling logging automatically updates the target bucket policy to permit S3's logging service write access.
  • Log delivery takes time to appear (typically 1 to 2 hours for initial log files to populate).
Critical Warning NEVER set a bucket's access log destination to be itself! Doing so creates an infinite logging loop — writing a log file generates a new request event, which writes another log file, causing massive unnecessary storage charges!

8 S3 Pre-signed URLs

A Pre-signed URL is a temporary, cryptographically signed URL link that grants temporary access to a specific private S3 object. Whoever holds the pre-signed link inherits the IAM permissions of the user who generated it (for file download GET or file upload PUT requests).

Generation MethodMaximum URL Expiration Lifetime
AWS Management Console UIUp to 12 hours max
AWS CLI / SDK CodeUp to 168 hours (7 days) max

The object owner generates a pre-signed URL carrying their credentials and hands it to a user. The user accesses the file until the link expires.

Common Real-World Use Cases

  • Allow logged-in premium website subscribers to download private video files.
  • Generate temporary, time-bound download links dynamically inside a web application.
  • Allow an external user to upload a file directly to a private S3 bucket without opening public bucket write access.

9 S3 Access Points

When an S3 bucket holds shared data accessed by multiple teams (such as Finance, Sales, and Analytics), managing access through one single S3 Bucket Policy becomes extremely complex. S3 Access Points simplify security management by creating dedicated access endpoints with distinct policies.

Each Access Point features its own DNS domain name and policy restricted to specific folder prefixes and permissions, keeping bucket management clean.

  • Each Access Point gets a unique DNS domain name and its own attached policy (structured like a bucket policy).
  • Access Points can be configured as Internet-facing or restricted to a private VPC Origin.
  • VPC Access Points: Combine with an S3 Interface VPC Endpoint to allow EC2 instances inside a private subnet to reach S3 Access Points without traversing the public internet.

10 S3 Object Lambda

What if different applications require different versions or formats of the same S3 object? Instead of duplicating files across multiple buckets, S3 Object Lambda processes and transforms files on the fly during retrieval.

A single S3 bucket stores original data, while S3 Object Lambda automatically transforms data on the fly based on which app makes the request.

How Object Lambda Works

  1. An application calls an S3 Object Lambda Access Point.
  2. This automatically triggers an AWS Lambda function, which fetches the original object from S3 and executes custom code on it.
  3. The transformed result is returned to the requesting application.

Key Use Cases

  • Automatically redact PII (Personally Identifiable Information like Aadhaar/PAN numbers or email addresses) for analytics or testing environments.
  • Convert file data formats on the fly (e.g., converting XML files to JSON format).
  • Resize or add dynamic watermarks to images based on requesting user identity.

✓ Cheat Sheet

Key Facts to Remember

  • 4 Encryption Methods: SSE-S3 (AWS keys, default), SSE-KMS (user KMS keys, CloudTrail audit logs, watch API limits), SSE-C (customer keys passed in headers over HTTPS, CLI/SDK only), and Client-Side Encryption (encrypt locally before upload).
  • Policy Evaluation: S3 Bucket Policies are evaluated before default bucket encryption rules.
  • CORS: Browser security mechanism. Resolve cross-bucket file fetching issues by adding a CORS configuration to the target bucket allowing the requester's origin.
  • MFA Delete: Protects against permanent version deletion and versioning suspension. Requires versioning enabled, Root Account credentials, and AWS CLI commands.
  • Access Logs: Record all bucket requests to a target bucket in the same AWS region. Never log a bucket to itself! Analyze logs with Athena.
  • Pre-signed URLs: Grant temporary access inheriting creator permissions. Console max 12 hours, CLI/SDK max 168 hours (7 days).
  • Access Points: Simplify multi-team bucket permissions by creating prefix-scoped access endpoints with unique DNS names and policies.
  • Object Lambda: Combines Access Points with Lambda functions to transform or sanitize S3 object content dynamically during retrieval without storing duplicates.

Mental Model

S3 security focuses on data protection, access governance, and content transformation. Encryption (SSE-S3, SSE-KMS, SSE-C, Client-side) protects data at rest and in transit. CORS controls cross-origin web browser permissions. MFA Delete and Access Logs protect data integrity and maintain audit trails. Pre-signed URLs grant temporary access without altering bucket policies. Finally, Access Points and Object Lambda allow large enterprise buckets to scale access control cleanly and deliver dynamically processed data to different applications.
