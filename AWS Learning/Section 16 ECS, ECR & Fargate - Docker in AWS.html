1 Docker Introduction

Docker is a platform for packaging and running apps in containers — standardized units that run the same way regardless of the machine or OS underneath. No compatibility issues, predictable behavior, easier to maintain and deploy — works with any language, OS, or technology.

  • Common use cases: microservice architectures, lift-and-shift from on-premises to the cloud, or just "I need to run a container."
  • A server runs a Docker agent/daemon, and you start containers on top of it — e.g. one container running a Java app, another running Node.js. You can run multiple instances of the same container too (and even databases like MySQL in containers).

Docker vs a Virtual Machine

VMs each carry a full guest OS on top of a hypervisor (isolated, heavier); Docker containers share the host OS via the Docker daemon (lighter, more containers per server, slightly less isolated).

Where Docker images live

  • Docker Hub — public repository, base images for lots of technologies/OSes (Ubuntu, MySQL, etc.).
  • Amazon ECR (Elastic Container Registry) — for private images, plus a public option via the ECR Public Gallery.

The basic Docker workflow

  1. Write a Dockerfile — starts from a base image, adds your files.
  2. Build it into a Docker image.
  3. Push the image to a repository (Docker Hub or ECR).
  4. Pull the image back down wherever you need it.
  5. Run it — the image becomes a running Docker container.

2 Amazon ECS Overview

ECS = Elastic Container Service. You launch Docker containers as an ECS Task on an ECS Cluster. There are two launch types.

EC2 launch type: you manage the fleet of EC2 instances tasks land on. Fargate: you just define tasks and AWS runs them — no server management at all.

EC2 Launch TypeFargate Launch Type
InfrastructureYou provision & maintain EC2 instances, each running the ECS Agent to register with the clusterFully serverless — no EC2 instances to manage
ScalingYou manage instance capacity tooJust increase the number of tasks
Exam guidance—The exam pushes Fargate a lot — it's simpler to manage

IAM Roles for ECS

RoleUsed byPurpose
EC2 Instance ProfileThe ECS Agent (EC2 launch type only)Make API calls to ECS (register instance), CloudWatch Logs, ECR (pull images), Secrets Manager/SSM Parameter Store
ECS Task RoleEach individual task (both EC2 and Fargate)Lets that specific task call other AWS services — e.g. Task A → S3, Task B → DynamoDB. Defined in the task definition, so different tasks can have different permissions.

Load Balancer integration

  • Application Load Balancer (ALB) — supports most use cases, works with Fargate. Good default choice.
  • Network Load Balancer (NLB) — only if you need very high throughput/performance, or need AWS PrivateLink.
  • Classic Load Balancer — old generation, not recommended, doesn't support Fargate.

Persistent data: EFS

To share data across tasks (regardless of AZ), mount an Amazon EFS file system — it's compatible with both EC2 and Fargate launch types since it's a network file system.

Tip The "ultimate combo" for a fully serverless setup: Fargate for compute + EFS for shared storage — no servers to manage anywhere, pay-as-you-go.

3 Creating an ECS Cluster — Hands On

When creating a cluster, under Infrastructure you choose how to get capacity:

  • Fargate only — fully serverless.
  • Fargate + AWS-managed instances — AWS manages the EC2 instances behind the scenes for you (you just create an instance profile + infrastructure role).
  • Fargate + self-managed instances — the older way: you create your own Auto Scaling Group, choose the AMI/instance type, etc.

Creating a cluster with self-managed instances actually spins up an Auto Scaling Group behind the scenes (e.g. named Infra-ECS-Cluster). Inside the cluster, you'll see capacity providers:

  • FARGATE — launch Fargate tasks.
  • FARGATE_SPOT — launch Fargate tasks on Spot capacity.
  • An ASG provider — launch tasks on the EC2 instances managed by your Auto Scaling Group.

Bumping the ASG's desired capacity spins up an EC2 instance that registers itself as a container instance in the cluster, showing available CPU/memory — that's the capacity tasks can be placed into.

4 Creating an ECS Service — Hands On

Before creating a service, you need a task definition: name it, choose Fargate or EC2, OS/architecture, task size (vCPU + memory), and:

  • Task role — optional IAM role if the container needs to call AWS services.
  • Task execution role — created automatically if it doesn't exist yet.
  • Container — name, image URL (e.g. pulled straight from Docker Hub), port mappings (e.g. container port 80), resource limits, env vars, logging.
  • Storage — Fargate provides some ephemeral storage by default.

Launching the service

  • Pick the task definition + revision, name the service, choose Fargate as the compute config.
  • Deployment configuration: replica — set how many tasks you want running (e.g. start with 1).
  • Networking — pick subnets, create a security group allowing HTTP from anywhere, enable a public IP.
  • Load balancing — create an ALB + target group so traffic reaches the tasks on port 80.
Good to know Scaling up is as simple as updating the service's desired task count (e.g. 1 → 3) — Fargate automatically provisions whatever resources are needed behind the scenes, and the ALB load-balances traffic across all running tasks (refreshing the page shows a different container IP each time).

To wind a demo down without deleting anything: update the service's desired task count to 0, and (if using EC2 launch type) set the ASG's desired capacity to 0 too.

5 ECS Service Auto Scaling

ECS Service Auto Scaling (via AWS Application Auto Scaling) can automatically increase/decrease the number of tasks based on:

  • CPU Utilization of the ECS service
  • Memory Utilization of the ECS service
  • ALB Request Count Per Target

Scaling types: Target Tracking (track a target value for one of the metrics above), Step Scaling, or Scheduled Scaling (for predictable load changes).

Exam point Scaling your ECS service (task count) is not the same as scaling the underlying EC2 cluster capacity (if you're on the EC2 launch type). That's exactly why Fargate makes auto scaling simpler — there's no separate instance layer to scale.

Scaling the EC2 instances themselves (EC2 launch type only)

MethodHow it works
Auto Scaling Group ScalingScale the ASG directly (e.g. on CPU utilization) — adds EC2 instances over time
ECS Cluster Capacity Provider (recommended)Smarter — automatically scales the paired ASG as soon as the cluster lacks capacity to place new tasks

6 ECS Rolling Updates

When updating an ECS service (e.g. v1 → v2), two settings control how tasks get replaced: minimum healthy percent and maximum percent (defaults: 100% and 200%).

Lower minimum-healthy% allows terminating old tasks first (dips below 100% capacity); higher maximum% allows creating new tasks first (temporarily exceeds 100%) before removing the old ones.

  • Min 50% / Max 100%: terminates old tasks down to 50%, then creates new ones back up to 100%, repeating until fully replaced.
  • Min 100% / Max 150%: creates new tasks first (up to 150%), then terminates old ones back to 100%, repeating until fully replaced — capacity never dips below 100%.

7 ECS Solution Architectures

1. EventBridge-triggered processing (S3 → ECS → DynamoDB)

User uploads to S3 → S3 events go to EventBridge → a rule runs an ECS/Fargate task → the task (using an ECS task role) processes the object and writes results to DynamoDB. Fully serverless image/object processing.

2. Scheduled batch processing

An EventBridge schedule (e.g. every hour) triggers an ECS/Fargate task with a task role granting S3 access — the task does batch processing on a schedule, fully serverless.

3. ECS + SQS with auto scaling

An ECS service polls an SQS queue for messages. Enable ECS Service Auto Scaling so the number of tasks grows with the number of queued messages.

4. Reacting to task lifecycle events

EventBridge can also capture events from your ECS cluster — e.g. "task state change: stopped" with a reason — which you can route to an SNS topic to alert administrators.

8 ECS Task Definitions — Deep Dive

A task definition (written in JSON, with a console UI to help) tells ECS how to run one or more Docker containers. Key fields: image name, port bindings, CPU/memory, environment variables, networking, IAM role, and logging config. You can define up to 10 containers per task definition.

Container port vs host port

EC2 launch type: each task shares the host's IP but gets a random host port (only the ALB — not the Classic LB — knows how to follow this). Fargate: every task gets its own private IP via an ENI, so container ports don't need remapping.

Exam point Dynamic host port mapping (EC2 launch type + ALB) means the EC2 instance's security group must allow any port from the ALB's security group, since the host port isn't known in advance. On Fargate, since every task gets its own ENI, the ENI security group just needs to allow the container's actual port (e.g. 80) from the ALB.

IAM roles

ECS Task Roles are assigned at the task definition level, not at the service level — every task launched from that definition inherits that role. Different task definitions can have different roles (e.g. one with S3 access, another with DynamoDB access).

Environment variables

SourceUse for
Hardcoded in the task definitionFixed, non-secret values (e.g. a URL)
SSM Parameter Store / Secrets ManagerSensitive values (API keys, DB passwords) — resolved and injected at task launch time
Bulk load from an S3 fileLoading many environment variables at once from a file

Sharing data between containers (bind mounts)

A task can hold multiple containers — e.g. an app container plus a sidecar for logging/metrics. To let them share files, mount a shared data volume ("bind mount") accessible to both, e.g. at /var/logs.

  • EC2 tasks: the bind mount is the EC2 instance's own storage — tied to that instance's lifecycle.
  • Fargate tasks: uses ephemeral storage (20GB–200GB available) — tied to the task's lifecycle; disappears when the task does.

10 ECS Task Placement

Important Task placement strategies and constraints only apply to the EC2 launch type. On Fargate, AWS decides where to run tasks for you — there's no backend instance to place onto.

How ECS decides where to place a task

  1. Identify instances that satisfy the task's CPU/memory/port requirements.
  2. Filter by any task placement constraints.
  3. Pick the instance that best matches the task placement strategy (best-effort, not guaranteed).

Placement strategies

StrategyBehaviorGood for
binpackFills one instance's CPU/memory before moving to the nextCost saving — fewer instances in use
randomNo logic, purely random placementSimple, not optimal
spreadEvenly distributes tasks across a value (e.g. AZ, instance ID)High availability

Strategies can be combined (e.g. spread across AZ, then binpack on memory within each AZ).

Placement constraints

ConstraintMeaning
distinctInstanceEach task must land on a different container instance — never two tasks on the same instance
memberOfOnly place tasks on instances matching a cluster query language expression (e.g. only t2 instance types)

11 ECS Clean Up — Hands On

  1. Set the service's desired task count to 0, then delete the service (type Delete to confirm). This kicks off a CloudFormation stack deletion behind the scenes — removing the ECS service, load balancer listener, load balancer, security group, and target groups.
  2. Once the service is fully gone, delete the cluster — this also triggers CloudFormation to remove the capacity provider, Auto Scaling Group, cluster, and launch templates.
  3. Task definitions can be left as-is (they're free, just definitions) or explicitly deregistered if you want to clean them up too.

12 Amazon ECR

ECR = Elastic Container Registry — stores and manages Docker images on AWS.

  • Private repositories — for your own account(s) only.
  • Public repositories — published to the ECR Public Gallery.
  • Fully integrated with ECS — images are backed by S3 under the hood.
  • Access is controlled via IAM — e.g. an EC2 instance needs an IAM role permitting it to pull images.

The EC2 instance uses its IAM role to authenticate and pull the image from ECR, then starts the container from it.

Extra ECR features: image vulnerability scanning, versioning, image tags, and image lifecycle policies.

Exam point Anytime the exam mentions "storing Docker images" on AWS — think ECR.

13 Amazon ECR — Hands On

  1. Authenticate Docker CLI to ECR: aws ecr get-login-password piped into docker login (username AWS).
  2. Create a private repository (options include tag immutability to block overwriting the same tag twice, and image scan-on-push — though registry-level scanning via Amazon Inspector is the modern recommended approach).
  3. docker pull an existing image (e.g. from Docker Hub).
  4. docker tag it to match your ECR repository's URI + tag.
  5. docker push — Docker recognizes the retagged name and pushes it into your ECR repository.
Don't forget If push/pull fails, it's almost always an IAM permissions issue — check your policies.

Once pushed, you can point a new task definition at this image URL instead of pulling from Docker Hub.

14 Amazon EKS

EKS = Elastic Kubernetes Service — AWS's managed way to run Kubernetes, an open-source container orchestration system. It's an alternative to ECS with the same general goal but a different (and cloud-agnostic) API.

  • Supports both EC2 launch mode (worker node EC2 instances) and Fargate mode (serverless).
  • Use EKS if your company already uses Kubernetes on-prem or on another cloud, or wants to stay cloud-agnostic (Kubernetes also runs on Azure, Google Cloud, etc.) for easier multi-cloud migration.

EKS "pods" (Kubernetes' equivalent of ECS tasks) run on worker node EC2 instances you manage, or serverlessly via Fargate mode.

Node types

TypeDetails
Managed Node GroupsAWS creates/manages the EC2 nodes as part of an ASG; supports On-Demand & Spot
Self-managed nodesYou create and register your own nodes into the cluster (can use the EKS-optimized AMI or build your own); more control, more work; supports On-Demand & Spot
Fargate modeNo nodes at all — fully serverless, no maintenance

Storage on EKS

Attach data volumes via a StorageClass manifest, using a Container Storage Interface (CSI) compliant driver. Supported: Amazon EBS, Amazon EFS (the only one that works with Fargate), Amazon FSx for Lustre, and Amazon FSx for NetApp ONTAP.

✓ Cheat Sheet

Key facts to remember

  • ECS launch types: EC2 (you manage instances + ECS Agent) vs Fargate (serverless, exam-favorite).
  • EC2 Instance Profile → used by the ECS Agent. ECS Task Role → used by individual tasks, defined at the task definition level.
  • ALB works with Fargate and supports dynamic host port mapping (EC2 launch type); Classic LB does not support either.
  • EFS is the shared-storage option compatible with both EC2 and Fargate launch types (and the only EKS storage class that works with Fargate).
  • Service Auto Scaling metrics: CPU utilization, memory utilization, ALB request count per target. Use ECS Cluster Capacity Provider (not plain ASG scaling) to also scale the EC2 fleet.
  • Rolling updates are controlled by minimum healthy percent and maximum percent.
  • Task placement (EC2 launch type only): binpack (cost saving), random (simple), spread (high availability); constraints: distinctInstance, memberOf.
  • Up to 10 containers per task definition; sidecars share data via bind mounts.
  • ECR stores Docker images (private or public gallery), backed by S3, access controlled by IAM; supports vulnerability scanning, tags, lifecycle policies.
  • EKS = managed Kubernetes; cloud-agnostic API; supports EC2 or Fargate mode, and Managed/self-managed node groups.

Mental model

Docker packages your app into a portable container; ECS (or EKS if you need Kubernetes) is the orchestrator that decides where those containers run and keeps them healthy; Fargate removes the "where" entirely by making compute serverless; ECR is simply where your container images live before ECS pulls and runs them. Everything else in this section — task definitions, IAM task roles, placement strategies, rolling updates, auto scaling — is really about answering one question as cleanly as possible: how many copies of my container should run, where, with what permissions, and how do I change that safely over time.
