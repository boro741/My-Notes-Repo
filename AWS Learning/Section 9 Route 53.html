1 What is a DNS?

DNS = Domain Name System. Its whole job is to translate human-friendly hostnames (like www.google.com) into the IP address of the server you actually need to talk to.

Domain names are hierarchical, read right to left in importance:

  • Root — the invisible dot at the very end of every domain
  • TLD (top level domain) — .com, .org, .gov
  • Second level domain — example.com
  • Subdomain — www.example.com
  • FQDN (fully qualified domain name) — api.www.example.com

Key terms

  • Domain registrar — where you buy/register a domain name (Route 53, GoDaddy, etc.)
  • DNS records — entries that map names to values (A, AAAA, CNAME, NS...)
  • Zone file — contains all the DNS records for a domain
  • Name servers — the servers that actually answer DNS queries

How a DNS lookup actually works

This is the important mental model — a query gets passed along a chain until someone knows the exact answer, and each server just points you closer:

Each server doesn't know the final answer — it just knows who to ask next. The local DNS server does the legwork recursively, then caches the final answer.
Analogy Think of it like asking for directions in an unfamiliar city. You ask a local (root server) who doesn't know your exact destination but says "that street is in this district" (.com). You go to that district and ask again, and someone there says "that building is managed by this company" (example.com's own server), who finally gives you the exact address.
Best practice DNS is the backbone of the internet — you use it every single time you type a website name, even though it's invisible. Understanding this recursive lookup chain makes TTL, caching, and troubleshooting DNS issues much easier later.

2 Route 53 Overview & Hosted Zones

Amazon Route 53 is a highly available, scalable, fully managed, and authoritative DNS service. "Authoritative" just means: you, the customer, have full control to update the DNS records.

  • Route 53 is also a domain registrar — you can buy domains directly through it (e.g. example.com)
  • It can check the health of your resources (more on this later)
  • It's the only AWS service with a 100% availability SLA
Where the name comes from "53" refers to port 53 — the traditional port used by DNS services. Hence, Route 53.

What's inside a record

Every DNS record you create in Route 53 contains:

  • Name — the domain/subdomain, e.g. example.com
  • Type — e.g. A, AAAA, CNAME
  • Value — e.g. 12.34.56.78
  • Routing policy — how Route 53 responds to queries
  • TTL — how long resolvers should cache the answer

Record types you must know for the exam

TypeMaps toNotes
AHostname → IPv4 addressThe classic record
AAAAHostname → IPv6 addressSame idea as A, just IPv6
CNAMEHostname → another hostnameCan't be used at the zone apex (root domain)
NSName servers for the hosted zoneControls which servers answer for your zone

Hosted zones: public vs private

A hosted zone is a container of records that defines how traffic is routed for a domain and its subdomains.

Both types work the same way internally — the only difference is who is allowed to ask them questions.
Don't forget Route 53 is not free. Every hosted zone costs $0.50/month, and registering a domain name costs a minimum of $12/year.

3 Registering a Domain (Hands-On)

Steps to register a domain directly through Route 53:

  1. Go to Register Domains and search for an available name
  2. Add it to your basket, choose a duration (e.g. 1 year) and whether to auto-renew
  3. Fill in contact info (registrant / admin / tech contact — can all be the same)
  4. Enable privacy protection so your personal info isn't public
  5. Review and submit — this actually charges you money

After registration (can take minutes to hours), a hosted zone is automatically created with two default records: an NS record (which name servers to use) and an SOA record. From this point, Route 53 is the source of truth for that domain's DNS records.

Don't forget If you turn off auto-renew and forget to renew manually, someone else can register your domain once it expires.

4 First Records & Demo Infrastructure

Creating a record is simple: give it a name (e.g. test.example.com), pick a type (e.g. A), give it a value (an IP), set a TTL, and choose a routing policy (start with Simple).

To actually verify DNS is working from a terminal, two commands are used throughout this section:

  • nslookup <domain> — works well on Windows
  • dig <domain> — works well on Mac/Linux, and shows more detail (including TTL)

On AWS CloudShell (Amazon Linux), you may need to install them first:

sudo yum install -y bind-utils

Demo infrastructure used for the rest of this section

To demonstrate routing policies later, three EC2 instances were launched (Amazon Linux 2, t2.micro, security group allowing SSH + HTTP from anywhere), each with a bootstrap script that returns a "Hello World" page showing its Availability Zone:

  • One in eu-central-1 (Frankfurt)
  • One in us-east-1 (N. Virginia)
  • One in ap-southeast-1 (Singapore)

An Application Load Balancer (ALB) was also created in eu-central-1, pointing to a target group containing the Frankfurt instance. This whole setup is reused across the TTL, CNAME/Alias, and routing policy demos.

Exam-style key point Loading a raw IP address directly in the browser works even before any DNS record exists — DNS just gives you a friendlier way to reach the same server.

5 TTL (Time To Live)

TTL tells DNS resolvers (and clients) how long they're allowed to cache the answer to a query before asking again.

While cached, changes to the record won't be seen by clients — they only refresh once the TTL window ends.
High TTL (e.g. 24h)Low TTL (e.g. 60s)
Traffic / cost to Route 53Lower — fewer queries reach Route 53Higher — more queries reach Route 53
Speed of propagating a record changeSlow — clients may hold stale data up to 24hFast — clients pick up changes quickly
Best practice If you're planning to change a record's value soon, temporarily lower its TTL first, wait for the old TTL window to fully expire everywhere, then make the change — this minimizes the number of clients seeing stale data.
Don't forget TTL is mandatory for every record type except Alias records — Route 53 manages that automatically.

In the demo, this was verified with dig: the "seconds left" number counts down from the TTL, and a record's underlying value change was invisible to the browser/CLI until the old TTL window fully expired.

6 CNAME vs Alias

Both let you point one hostname at another. But they behave differently, and this is a favorite exam topic.

CNAMEAlias
Points toAny hostnameSpecific AWS resources only
Works at zone apex (root domain)?❌ No✅ Yes
CostNormal (or provider) pricingFree
TTLYou set itSet automatically by Route 53
Health check awarenessNoNative, built-in
Record typeCNAMEAlways A or AAAA
Alias records extend DNS to solve the exact problem CNAME can't: pointing your root/apex domain at an AWS resource.

What Alias records can target

  • Elastic Load Balancers (ALB/CLB/NLB)
  • CloudFront Distributions
  • API Gateway
  • Elastic Beanstalk environments
  • S3 websites (not plain S3 buckets)
  • VPC Interface Endpoints
  • Global Accelerator
  • Another Route 53 record in the same hosted zone
Don't forget You cannot create an alias record pointing to a plain EC2 instance's DNS name. Alias only works for the AWS-managed resource types listed above.

Demo confirmed: trying to create a CNAME at the zone apex gave "CNAME is not permitted at apex of this zone" — the fix was to instead create an A record with Alias enabled, pointing to the ALB, which worked fine.

7 Routing Policies & Simple Routing

Route 53 supports 7 routing policies: Simple, Weighted, Latency, Failover, Geolocation, Geoproximity, IP-based, and Multi-Value Answer.

Analogy "Routing" here does not mean traffic passes through Route 53 like a router or load balancer. DNS never touches your actual HTTP traffic — it only answers the question "which IP should I use?" The client then goes directly to that IP.

Simple routing

Routes to a single resource — or if a record has multiple values, the client picks one at random. No health checks are supported with simple routing. If used as an Alias, only one AWS resource can be the target.

Demo: a record with two IPs in one Simple record returned both values on dig, and the browser picked one at random on each fresh lookup (once the TTL expired).

8 Routing Policy: Weighted

Lets you control what percentage of traffic goes to each resource, using relative weights.

Formula: traffic % to a record = record's weight ÷ sum of all weights. Weights don't need to add up to 100 — they're just relative to each other.

Thicker line = more traffic. 70% of DNS answers point to us-east-1, 20% to eu-central-1, 10% to ap-southeast-1.

Use cases

  • Load balancing across regions
  • Canary-testing a new app version by sending it a small % of traffic
  • Setting a weight of 0 to stop sending traffic to a resource entirely
Exam-style key point All records in a weighted set must share the same name and type. If every record has weight 0, they're all returned with equal weight.

Demo confirmed: with weights 70/20/10 and a 3-second TTL, refreshing repeatedly mostly landed on us-east-1, with occasional hits to the other two — exactly matching the weight ratios.

9 Routing Policy: Latency-Based

Routes users to whichever AWS region gives them the lowest latency — not necessarily the geographically closest one. Useful when latency is your main concern for user experience.

Each record must be tagged with the AWS region it represents (Route 53 can't infer that from a raw IP), and latency records can be combined with health checks.

Analogy It's less "which region is on the map closest to me" and more "which region actually responds to me fastest right now" — usually the same thing, but not guaranteed.

Demo confirmed with a VPN: from Europe → routed to eu-central-1; connected via Canada → routed to us-east-1; connected via Hong Kong → routed to ap-southeast-1. Note: switching location cleared the local DNS cache, which is why the browser updated immediately, but dig from a fixed CloudShell location kept returning the same region since that machine's location never changed.

10 Health Checks

Health checks let Route 53 monitor whether your resources are actually healthy, so it can automatically stop sending traffic to broken ones.

Health checkers run from ~15 locations worldwide and hit your endpoint on a schedule, checking for a passing status code.

Configuration options

  • Interval: standard (30s) or fast (10s, costs more)
  • Protocols: HTTP, HTTPS, TCP
  • Failure threshold: how many failures before marked unhealthy
  • String matching: can check the first 5,120 bytes of the response for specific text
  • Passing codes are 2xx or 3xx
Don't forget Health checkers live on the public internet — your security group / firewall must explicitly allow inbound traffic from Route 53's health checker IP ranges, or checks will time out (which looks like a firewall/security-group problem, and usually is).

Three types of health checks

TypeWhat it monitors
Endpoint health checkA public endpoint directly (app, server, AWS resource)
Calculated health checkCombines other ("child") health checks using AND / OR / NOT logic — up to 256 children, useful for maintenance windows without failing everything
CloudWatch alarm health checkWatches a CloudWatch alarm — the only way to health-check private resources, since checkers can't reach inside a VPC
Analogy For a private resource, Route 53 can't personally knock on its door (it's not on the public internet). Instead, it relies on a CloudWatch alarm as a middleman — like asking a neighbor who does have access to check for you.

Hands-on: three health checks were created (one per region). Removing the HTTP inbound rule on ap-southeast-1's security group caused that health check to go unhealthy within a short wait, and the "last failed check" view reported a connection timeout — confirming a firewall/security-group cause.

11 Routing Policy: Failover

Used for active/passive setups: one primary resource and one secondary (disaster recovery) resource.

A health check on the primary is mandatory — if it fails, Route 53 automatically starts answering with the secondary record instead.
Exam-style key point There can only be one primary and one secondary per failover set. The health check on the primary is mandatory; on the secondary it's optional.

Demo confirmed: with a healthy primary (eu-central-1), requests always answered from eu-central-1. After removing the HTTP inbound rule (making the health check unhealthy), requests automatically failed over to the secondary (us-east-1) — no manual change to the record was needed.

12 Routing Policy: Geolocation

Routes based on where the user is located — by continent, country, or even US state. The most specific matching location wins. This is different from Latency-based, which cares about speed, not geography.

  • Always create a default record for when there's no location match
  • Can be combined with health checks

Use cases

  • Website localization (serve the German version to German users)
  • Restricting content distribution by region
  • Geography-based load balancing
Don't forget If a user's location doesn't match any rule (e.g. Mexico when you only defined "Asia" and "United States"), they fall through to the default record — not an error.

Demo confirmed via VPN: connecting from India → routed to ap-southeast-1; from the United States → routed to us-east-1; from Mexico (no matching rule) → fell through to the default record in eu-central-1.

13 Routing Policy: Geoproximity

Routes based on the geographic location of both users and resources, and lets you shift traffic between regions using a number called the bias.

  • Increase bias (positive number) → expand the region's reach, pulling in more traffic
  • Decrease bias (negative number) → shrink the region's reach, sending less traffic there
  • For AWS resources: specify the region. For non-AWS resources (e.g. on-prem): specify latitude/longitude
  • Requires Route 53 Traffic Flow (the advanced/visual policy editor) to use bias
Increasing the bias on a region visually "expands" its territory on the map, pulling more users toward it.
Exam-style key point Remember Geoproximity for one thing: shifting traffic from one region to another by tuning the bias value.

14 Routing Policy: IP-Based

Routes based on the client's IP address, using CIDR ranges you define. You tell Route 53: "traffic from this IP range should go to this location."

Use cases

  • Optimize performance when you know your users' ISP/IP ranges ahead of time
  • Reduce network costs by directing specific ISPs to specific endpoints

Example: CIDR block starting with 203... → routed to 1.2.3.4; CIDR block starting with 200... → routed to 5.6.7.8. Whichever CIDR range a client's IP falls into determines the answer they get.

15 Routing Policy: Multi-Value Answer

Returns up to 8 healthy records per query, and the client picks one. This gives basic client-side load balancing — but it is not a substitute for a real load balancer (ELB).

  • Can be associated with health checks — only records tied to a healthy health check are returned
  • Different from Simple routing with multiple values, because Simple cannot use health checks — so an unhealthy resource could still be handed to a client

Demo: three multi-value A records (US, Asia, EU) each tied to a health check. dig initially returned all 3 IPs. After inverting the EU health check to unhealthy, dig returned only 2 IPs — confirming unhealthy records are automatically excluded.

16 3rd Party Domains & Route 53

Important distinction: a domain registrar (where you buy the name) and a DNS service (what manages the records) are different things — even though most registrars bundle both.

You can mix and match:

  • Buy your domain from Amazon, but use a different DNS service
  • Buy your domain from a 3rd party (e.g. GoDaddy), but still use Route 53 to manage DNS records

How to use Route 53 with a domain bought elsewhere

  1. Create a public hosted zone in Route 53 for your domain
  2. Copy the 4 name servers Route 53 gives you for that hosted zone
  3. On the 3rd-party registrar's site (e.g. GoDaddy), update the domain's custom name server settings to point to those 4 Route 53 name servers
Best practice This is a fully supported and common combination — buy cheap/wherever, manage DNS in Route 53 if you want AWS-native features like Alias records and health checks.

★ Cheat Sheet

Key facts to remember

  • DNS translates hostnames → IPs, recursively, through root → TLD → domain servers, with caching at each hop
  • Route 53 = authoritative DNS + domain registrar, 100% availability SLA, named after port 53
  • Hosted zone costs $0.50/month; domain registration starts at $12/year
  • A/AAAA = hostname → IP. CNAME = hostname → hostname (not allowed at zone apex). NS = which servers answer for the zone
  • Alias records: free, work at the zone apex, only point to specific AWS resources, TTL is automatic, health-check aware. Cannot target a raw EC2 DNS name
  • TTL = how long a resolver caches an answer. High TTL = less cost, slower propagation. Low TTL = more cost, faster propagation
  • Health checks: ~15 global checkers, >18% healthy = healthy, 2xx/3xx = pass. Types: endpoint, calculated (AND/OR/NOT of children), CloudWatch alarm (for private resources)

Mental model recap

Route 53 never touches your actual application traffic — it's purely a phone book that answers "which IP should I use?" All the routing policies are just different rules for how that phone book picks an answer: always the same resource (Simple), by percentage (Weighted), by speed (Latency), by failover status (Failover), by user location (Geolocation/Geoproximity), by client IP (IP-based), or by returning several healthy options at once (Multi-Value) — and Alias records are Route 53's special free, apex-friendly way of pointing that phone book directly at AWS-managed resources.
