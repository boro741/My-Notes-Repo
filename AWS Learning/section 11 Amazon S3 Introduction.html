1 S3 Overview

S3 is one of the core building blocks of AWS — it's advertised as "infinitely scaling storage" and a huge chunk of the web actually runs on it (many sites use it as a backbone, and lots of AWS services integrate with it directly).

Common use cases

  • Backup and storage (files, disks, etc.)
  • Disaster recovery — replicate data to another region so you're covered if a region goes down
  • Archival — cheap long-term storage you retrieve later
  • Hybrid cloud storage — extend on-prem storage into the cloud
  • Hosting applications, media (video/images), static websites
  • Data lakes for big data analytics
  • Delivering software updates
Real examples NASDAQ stores 7 years of data in S3 Glacier (the archival tier). Sysco runs analytics on its data stored in S3 to get business insights.

Buckets

  • Buckets are like directories in the cloud — you store objects (files) inside them.
  • Buckets are created at the region level. The S3 console UI is global (shows buckets from all regions), but each bucket itself lives in one specific region.

Bucket naming

Historically, bucket names had to be globally unique across every AWS account and region in the world. AWS recently added the account regional namespace option — it lets you reuse the same bucket name across your own regions/accounts, because AWS appends a unique suffix behind the scenes.

Naming rules No uppercase letters, no underscores, can't look like an IP address. Must start with a lowercase letter or number. Can't start with prefix xn--. Can't end with suffix -s3alias. Basically: keep it simple — lowercase letters and numbers.

Objects

  • Objects are just files. Each has a key — the full path of the file.
  • A key is made of a prefix + an object name. Example: for my_folder1/another_folder/my_file.txt, the prefix is my_folder1/another_folder and the object name is my_file.txt.
  • S3 doesn't actually have real "directories" — the console just displays them that way. Under the hood, everything is one long key name with slashes in it.
  • Max object size: 50 TB.
  • Files larger than 5 GB must use multi-part upload (split into parts). E.g. a 5 TB file needs at least 1,000 parts of 5 GB each.
  • Objects can have metadata (key/value pairs, set by system or user), tags (up to 10 Unicode key/value pairs — useful for security & lifecycle rules), and a version ID if versioning is enabled.
Analogy Think of an S3 key like a full file path on your computer — Documents/2024/report.pdf. There's no real "Documents" or "2024" folder on disk in S3's world — it's really just one long name with slashes that the console renders as folders for convenience.

2 S3 Hands On

Walkthrough of creating a bucket and uploading files in the console.

Creating a bucket

  • Choose the region (e.g. Ireland eu-west-1).
  • Bucket type: General purpose (recommended default) vs Directory (low-latency use cases).
  • Namespace: Global (needs a globally unique name) vs Account Regional (AWS appends a suffix so any name works).
  • Object Ownership: ACLs disabled (recommended default).
  • Block Public Access: left enabled for max security.
  • Bucket Versioning: disabled for now (covered later).
  • Default encryption: server-side encryption with an Amazon S3 managed key, with Bucket Key enabled.

Uploading and viewing objects

Uploaded coffee.jpg to the bucket, then opened the Object page to see its properties, size, type, and an Object URL.

Don't forget Clicking "Open" in the console works because the console generates a signed request for you. But copying the plain Object URL and pasting it into a browser gives AccessDenied — the bucket isn't public by default.

The console's "Open" link actually uses a pre-signed URL — a long URL containing an embedded signature/credentials proving you are allowed to view the object. That's why it works while the plain object URL doesn't.

Folders

You can create folders (e.g. images/) and upload into them (e.g. images/beach.jpg) — visually just like Google Drive/Dropbox. Deleting a folder deletes everything inside it (type permanently delete to confirm).

3 S3 Security: Bucket Policy

Ways to secure S3

MechanismWhat it is
User-based (IAM policies)Controls which API calls a specific IAM user is allowed to make
Resource-based (Bucket policies)Bucket-wide rules set directly on the bucket; can allow cross-account access or make a bucket public
Object Access Control List (ACL)Finer-grained, can be disabled
Bucket ACLLess common, can be disabled
EncryptionEncrypt objects using encryption keys
Exam point An IAM principal can access an S3 object if: IAM permissions allow it OR the resource (bucket) policy allows it — AND there's no explicit Deny anywhere.

Anatomy of a bucket policy

Bucket policies are JSON documents with a few key parts:

  • Resource — which bucket/objects the policy applies to (e.g. arn:aws:s3:::example-bucket/* = every object in the bucket)
  • Effect — Allow or Deny
  • Action — the API calls being allowed/denied (e.g. s3:GetObject)
  • Principal — who the policy applies to (* = anyone)

A policy with Principal: *, Effect: Allow, Action: s3:GetObject on bucket/* makes every object in the bucket publicly readable.

Access scenarios

Four ways to grant access to an S3 bucket, depending on who's asking: public visitor, IAM user, EC2 instance, or a user in another AWS account.

Block Public Access settings

Important "Block Public Access" is a bucket (or account-level) safety switch designed to prevent data leaks. Even if your bucket policy would make the bucket public, these settings override it and keep the bucket private. Leave them on unless you specifically intend to make a bucket public.

4 Bucket Policy Hands On

Steps to make the coffee.jpg object publicly accessible via its plain URL:

  1. Go to the bucket's Permissions tab and edit Block Public Access — untick it to allow public access (AWS shows a warning since this is a risky action).
  2. Use the AWS Policy Generator to build a bucket policy: Type = S3 Bucket Policy, Effect = Allow, Principal = *, Action = GetObject, Amazon Resource Name = the bucket ARN + /* (the /* represents all objects inside the bucket).
  3. Paste the generated JSON policy into the bucket policy editor and save.
  4. Now the object URL loads directly — no more AccessDenied.
Don't forget Making a bucket public is a real risk — never do this with buckets that hold real company/production data. Only unblock public access when you deliberately want a public policy (e.g. hosting a static website).

5 S3 Static Website Hosting

S3 can host static websites directly and serve them over the internet. The website URL format depends on the AWS region.

A browser hits the S3 static website endpoint, which serves files straight out of the bucket — but only if the bucket allows public reads.

Important Static website hosting will not work unless public reads are enabled on the bucket (via a bucket policy). A 403 Forbidden error after enabling website hosting means your bucket still isn't public — attach an S3 bucket policy that allows public GetObject.

Hands-on setup

  1. Upload your site files (e.g. beach.jpg, coffee.jpg, index.html).
  2. Go to bucket Properties → Static website hosting → Edit, enable it, and set the index document to index.html.
  3. Save — the bucket gets a bucket website endpoint URL.
  4. Because the bucket policy already allows public reads, visiting the endpoint URL loads the page and its images correctly.

6 S3 Versioning

Versioning is a bucket-level setting. Once enabled, every time you upload to the same key, S3 keeps the old copy and creates a new version instead of overwriting it.

Best practice Enable versioning on your buckets. It protects against unintended deletes (a "delete" just adds a delete marker, so you can restore the previous version) and lets you easily roll back to an earlier version of a file.
  • Any file that existed before versioning was enabled has version ID null.
  • Suspending versioning does not delete previous versions — it's a safe operation.

Hands-on behavior

  • Enable versioning under bucket Properties.
  • Re-uploading index.html with new content creates a new version ID — the old version is still there if you toggle "Show versions" in the console.
  • Deleting a specific version ID = a permanent delete (type permanently delete to confirm) — this is destructive and cannot be undone.
  • Deleting an object normally (without "Show versions") just adds a delete marker on top — the underlying object/version is still there. The page appears to be gone (404) but it isn't actually erased.
  • To restore the object, permanently delete the delete marker itself — this brings back the previous version.
Analogy A delete marker is like putting a "removed" sticky note on top of a file instead of shredding it. Peel off the sticky note (delete the delete marker) and the original file is right there again. A permanent delete of a specific version ID, on the other hand, is the shredder — no getting it back.

7 S3 Replication

Two flavors of replication, both asynchronous and both requiring versioning enabled on both source and destination buckets:

TypeMeaningTypical use cases
CRR — Cross-Region ReplicationSource and destination buckets are in different regionsCompliance, lower-latency access to data, replicating across accounts
SRR — Same-Region ReplicationSource and destination buckets are in the same regionAggregating logs from multiple buckets, live replication between prod and test accounts

Buckets can be in different AWS accounts. S3 needs proper IAM permissions to read from the source and write to the destination.

New objects uploaded to the origin bucket are copied asynchronously to the replica bucket, keeping the same version IDs.

Important notes

Important Only new objects get replicated after you turn replication on. To replicate objects that already existed, you need S3 Batch Replication — a separate feature that also handles objects that previously failed replication.
  • Delete marker replication is optional (off by default). If enabled, delete markers get replicated too.
  • Permanent deletes of a specific version ID are never replicated — this is intentional, to prevent malicious/accidental deletes from cascading to the replica.
  • No chaining: if Bucket 1 → Bucket 2 and Bucket 2 → Bucket 3, objects from Bucket 1 do not flow through to Bucket 3.

Hands-on recap

  1. Create origin and target buckets (can be different regions for CRR), enable versioning on both.
  2. On the origin bucket, go to Management → Replication rules → Create rule. Scope = all objects, destination = target bucket, and create/select an IAM role for it.
  3. Choose whether to replicate existing objects (this triggers a Batch Operation) — for a normal setup, choose no.
  4. Uploading a new file to the origin bucket → after a short delay, it appears in the replica bucket with the same version ID.
  5. Deleting a file (adding a delete marker) replicates the delete marker if that setting is enabled — the file "disappears" in both buckets but is recoverable via "Show versions."
  6. Permanently deleting a specific version in the origin bucket does not remove it from the replica bucket.

8 S3 Storage Classes

You choose a storage class per object at upload time, can change it manually later, or automate transitions with Lifecycle rules.

Durability vs Availability

  • Durability = how likely you are to lose an object. All S3 classes offer 11 nines (99.999999999%) durability — on average you'd lose 1 object out of 10 million once every 10,000 years.
  • Availability = how readily the service responds. This varies by class — e.g. S3 Standard is 99.99% available (~53 minutes of downtime/errors per year).
Exam point Durability is the same (11 nines) across every storage class. Availability is what differs between classes.

The classes

ClassAvailabilityNotes / Use case
S3 Standard99.99%Default, frequently accessed data, low latency & high throughput. Survives 2 concurrent facility failures. Big data, mobile/gaming apps, content distribution.
S3 Standard-IA (Infrequent Access)99.9%Cheaper storage, cost on retrieval, rapid access when needed. Disaster recovery, backups.
S3 One Zone-IA99.5%Stored in a single AZ only — lost if that AZ is destroyed. Secondary backup copies, recreatable data.
Glacier Instant Retrieval—Millisecond retrieval. Min storage duration 90 days. Good for data accessed ~once a quarter.
Glacier Flexible Retrieval—Retrieval tiers: Expedited (1–5 min), Standard (3–5 hrs), Bulk (5–12 hrs, free). Min storage duration 90 days.
Glacier Deep Archive—Retrieval tiers: Standard (12 hrs), Bulk (48 hrs). Lowest cost. Min storage duration 180 days. Long-term archival.
S3 Intelligent-Tiering—Auto-moves objects between tiers based on usage. Small monthly monitoring/auto-tiering fee. No retrieval charges.
Analogy Think of the Glacier tiers like ordering something online: Instant Retrieval is same-day delivery, Flexible Retrieval is choosing standard vs express shipping, and Deep Archive is the cheapest "it'll get there in a couple of days" option — you save money the more patient you're willing to be.

S3 Intelligent-Tiering tiers

  • Frequent Access — automatic, default tier.
  • Infrequent Access — automatic, for objects not accessed for ~30 days.
  • Archive Instant Access — automatic, for objects not accessed over 90 days.
  • Archive Access — optional, configurable from 90 to 700+ days.
  • Deep Archive Access — optional, configurable from 180 to 700+ days.

The idea: you "sit back and relax" and let S3 move objects between tiers automatically as access patterns change.

Example lifecycle rule: an object automatically transitions to cheaper storage classes as it ages.

Hands-on recap

  • You can set an object's storage class at upload, or change it later via Properties → Edit storage class.
  • Lifecycle rules (under bucket Management) automate these transitions — e.g. move to Standard-IA after 30 days, Intelligent-Tiering after 60 days, Glacier Flexible Retrieval after 180 days.
  • Reduced Redundancy storage class is deprecated — not covered further.

✓ Cheat Sheet

Key facts to remember

  • Buckets are regional; names need to be unique (globally, or per-account with the new account regional namespace).
  • An object's key = prefix + object name. S3 has no real "directories," just long key names.
  • Max object size 50 TB; multi-part upload required above 5 GB.
  • Access to an S3 object requires IAM permission or a resource (bucket) policy allowing it, and no explicit deny — plus Block Public Access must not be blocking it.
  • Static website hosting needs the bucket to allow public reads, or you'll get a 403.
  • Versioning: normal delete = adds a delete marker (recoverable); deleting a specific version ID = permanent (not recoverable).
  • Replication needs versioning on both buckets; only new objects replicate automatically (use Batch Replication for existing ones); permanent deletes never replicate; no chaining across 3+ buckets.
  • All storage classes share 11 nines durability — only availability and retrieval speed/cost differ.

Storage class decision guide

If you need...Use...

Cheaper storage, accessed rarely but needs fast accessS3 Standard-IA
Same as above but data is re-creatable / non-criticalS3 One Zone-IA
Don't know the access pattern, want AWS to manage tieringS3 Intelligent-Tiering

Mental model

S3 is just a big, regional key-value store for files: every object lives at a "key" inside a bucket, secured by a mix of IAM policies and bucket policies (with Block Public Access as a safety net), optionally versioned so nothing is really ever lost by accident, optionally replicated to another bucket/region for redundancy, and optionally aged automatically into cheaper storage classes as it gets accessed less — all while keeping the same rock-solid 11-nines durability no matter which tier it's sitting in.
