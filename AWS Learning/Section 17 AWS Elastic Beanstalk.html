1 Elastic Beanstalk Overview

This is one of the trickier exam sections, but a genuinely useful one: Elastic Beanstalk lets you deploy applications easily, quickly, and safely — instead of manually wiring up load balancers, auto scaling groups, and databases every single time.

Most web apps end up with the same shape: a load balancer → an Auto Scaling Group spread across AZs → EC2 instances → maybe an RDS database and ElastiCache in the back. Recreating that by hand for every app is a pain. Beanstalk gives you a developer-centric view: you focus on your code, and Beanstalk provisions and manages EC2, ASG, ELB, RDS, capacity, scaling, health monitoring, and instance configuration for you — while you still retain full control over each component's configuration if you need it.

Good to know Beanstalk itself is free — you only pay for the underlying resources it creates (EC2, ELB, RDS, etc.).

Core concepts

TermMeaning
ApplicationA collection of Beanstalk components — environments, versions, configurations
Application VersionOne iteration of your code (v1, v2, v3...)
EnvironmentA collection of resources running one specific application version at a time

Typical flow: create an application → upload a version → launch an environment → manage its lifecycle → upload new versions and redeploy to update.

Beanstalk supports many platforms: Go, Java SE, Java + Tomcat, .NET Core (Linux) / .NET (Windows), Node.js, PHP, Python, Ruby, Packer Builder, and Docker (single or multi-container, or pre-configured).

Web tier vs Worker tier

Web tier: a load balancer sends user traffic straight to EC2 instances. Worker tier: EC2 instances instead pull messages off an SQS queue and scale based on queue length — the two can be connected by having the web tier push messages the worker tier consumes.

Deployment modes

ModeBest for
Single instanceDevelopment — one EC2 instance with an Elastic IP (can include an RDS DB)
High availability (load balanced)Production — load balancer + ASG across multiple AZs, optionally a Multi-AZ RDS database

2 First Environment — Hands On

  • Choose Web server environment (vs Worker environment) to run a website.
  • Pick a managed platform (e.g. Node.js) and a sample application to start from.
  • Presets: Single instance (free-tier eligible), High availability, or Custom configuration. Start with Single instance to keep things simple.
  • Configure service access: create a service role (for the Beanstalk environment itself) and an EC2 instance profile (for Beanstalk Compute) if they don't already exist.
Good to know Behind the scenes, Beanstalk creates and manages a CloudFormation stack for you — you can watch it in the CloudFormation console and even visualize it in Application Composer (security groups, launch configuration, Elastic IP, etc. all show up there).

Once launched, you get a domain name — visiting it shows your running sample app ("Congratulations, you are now running Elastic Beanstalk"). From the environment you also get tabs for Health, Logs, Monitoring, Alarms, Managed updates, and Configuration (to view/modify everything Beanstalk set up).

Exam point Beanstalk is centered around code + environments; CloudFormation (which Beanstalk uses internally) is the more general-purpose service for deploying arbitrary infrastructure stacks.

3 Second Environment — Hands On

Creating a second environment (e.g. "prod") using the High Availability preset exposes a lot more configuration up front:

  • Networking — which VPC/subnets to launch into (all subnets, for high availability); no public IPs needed since traffic comes through a load balancer.
  • Database — optional; if added, its lifecycle is tied to the environment (deleting the environment deletes the DB, unless you snapshot first).
  • Instances — root volume, security groups.
  • Auto Scaling Group — min/max capacity (e.g. 1–4), fleet composition (On-Demand/Spot), instance types, scaling triggers.
  • Load balancer — public/private, subnets, ALB vs NLB, dedicated vs shared across environments (to save cost), listeners.
  • Health reporting, rolling updates, platform software (X-Ray, CloudWatch log streaming) — all configurable here too.
Good to know Once launched, this creates a real load balancer across multiple AZs, a target group with healthy EC2 instances, correctly configured security groups (LB allows port 80 from anywhere; instances allow port 80 only from the LB's security group), and an ASG with dynamic scaling policies — all automatically, from just uploading code and choosing "High Availability."

4 Deployment Modes

When updating an app version, Beanstalk offers several deployment policies, each trading off speed, downtime, and cost differently.

ModeDowntime?Extra cost?Notes
All at onceYesNoFastest — updates every instance simultaneously
RollingNo (runs below capacity briefly)NoUpdates one "bucket" of instances at a time
Rolling with additional batchNoSmallAdds extra instances first so capacity never drops
ImmutableNoHigher (doubles capacity temporarily)New version deployed to a brand-new temporary ASG; very safe/fast rollback
Blue/GreenNoHigher (whole new environment)Not a built-in Beanstalk feature — manual, using a new environment + Route 53 weighted routing
Traffic splitting (canary)NoHigher (temporarily doubles capacity)Automated canary testing with a temporary ASG

All at once vs Rolling

All-at-once takes everything down together (fast, but downtime); rolling updates one bucket at a time so some capacity always stays on the old version.

Immutable deployments

Immutable: new instances are validated in a separate temporary ASG first, then merged into the main ASG once healthy, and only then are the old instances removed — very safe, quick rollback (just terminate the temp ASG), but temporarily doubles capacity/cost.

Blue/Green & Traffic Splitting (Canary)

Both send a small slice of traffic to the new version first — Blue/Green does it across two full separate environments (manual, via DNS); Traffic Splitting (canary) does it within one environment via a temporary ASG, with automated health monitoring and rollback.

Exam point "Canary testing" on the exam = traffic splitting. It's largely an automated improvement on the manual blue/green technique — same idea (test with a slice of traffic first), but Beanstalk handles the monitoring and rollback for you.

5 Deployment Modes — Hands On

  • Deployment policy is set under Configuration → Updates, monitoring, and logging → Rolling updates and deployments.
  • For Rolling / Rolling with additional batch, you set a batch size — either fixed (e.g. 1 instance) or a percentage (e.g. 30%).
  • App-specific customization can live in a .ebextensions directory in your source zip (covered later) — e.g. changing a background color via config.

Watching an immutable deployment happen

  1. Beanstalk launches one instance first on a temporary ASG to verify health.
  2. Once healthy, it launches the rest of the new instances, attaches them to the load balancer.
  3. New instances are detached from the temporary ASG and merged into the permanent ASG.
  4. Old instances and the temporary ASG are terminated — deployment complete.

Environment swapping

Swap environment domains exchanges the DNS/URL mapping between two environments (e.g. prod ↔ dev) — handy after cloning an environment, testing a new version there thoroughly, then promoting it to be the "real" prod without redeploying anything. DNS propagation can take a few minutes.

6 Beanstalk CLI & Deployment Process

The EB CLI is a dedicated command-line tool for working with Beanstalk (eb create, eb status, eb health, eb events, eb logs, eb open, eb deploy, eb config, eb terminate, and more) — useful for automating deployment pipelines.

Good to know Not required for the Developer exam — it matters more for the DevOps exam. No hands-on for it in this course, just know it exists.

Deployment process, regardless of tool

  1. Describe your dependencies (e.g. requirements.txt for Python, package.json for Node.js).
  2. Package your code + dependency file as a zip.
  3. Upload the zip to Beanstalk — this creates a new application version and gets stored in an Amazon S3 bundle behind the scenes.
  4. Deploy that version via the console or CLI — Beanstalk pushes the zip to each EC2 instance, resolves dependencies, and starts the app.

7 Lifecycle Policy

Important Beanstalk can store at most 1,000 application versions per account. If you never clean up old ones, you'll eventually be unable to deploy new versions.

A lifecycle policy automatically phases out old versions, based on either:

  • Age — e.g. only keep versions from the last 180 days.
  • Count — e.g. keep a maximum of 200 versions.
  • Versions currently in use by any environment are never deleted, regardless of the policy.
  • You can choose whether to also delete the source bundle from S3, or retain it (useful if you might want to restore an old version later).

All application version source bundles live in an S3 bucket that Beanstalk creates automatically for your applications.

8 Beanstalk Extensions

.ebextensions let you configure things via code instead of the console UI — anything you can set in the UI (and more) can be defined in config files bundled with your source code.

  • Files must live in a .ebextensions/ directory at the root of your source bundle.
  • Written in YAML or JSON, but the file extension must always be .config (e.g. logging.config).
  • Modify default settings via option_settings, or add extra AWS resources (RDS, ElastiCache, DynamoDB, etc.) that aren't directly configurable through the console.
Don't forget Any resource created via .ebextensions is tied to the environment's lifecycle — if you delete the Beanstalk environment, that resource (e.g. an ElastiCache cluster) gets deleted too.

Example: setting environment variables via .ebextensions

A file like .ebextensions/environment-variables.config can define option_settings under aws:elasticbeanstalk:application:environment to set variables like DB_URL or DB_USER — useful for pointing your app at an external RDS database without hardcoding connection info. After deploying, these show up under the environment's Configuration → Environment properties, exactly as if you'd typed them into the console.

9 Beanstalk & CloudFormation

Under the hood, every Beanstalk environment is provisioned via a CloudFormation stack — that's how it can reliably create and coordinate multiple AWS resources as one unit.

  • Each environment gets its own stack (e.g. one for "dev," one for "prod") — you can inspect these directly in the CloudFormation console and see every resource created: ASG, launch configuration, Elastic IP, security groups, scaling policies, CloudWatch alarms, load balancer, listener rules, target groups, etc.
Good to know Because .ebextensions can include raw CloudFormation resources, you're not limited to what the Beanstalk console UI exposes — you can provision virtually anything (ElastiCache, DynamoDB, S3 buckets, etc.) as part of your environment.

10 Beanstalk Cloning

Clone Environment creates a brand-new environment with the exact same configuration as an existing one — load balancer type/config, RDS database type (though not its data), environment variables, etc.

Good to know Great for spinning up a test copy of production with identical settings — deploy and test a new version there, then use environment swapping to promote it once you're happy.

After cloning, you're free to customize the new environment's settings via its Configuration tab.

11 Beanstalk Migrations

Changing load balancer type

Important Once an environment is created, you cannot change its load balancer type (e.g. Classic → Application), only its configuration. Cloning doesn't help here either, since cloning copies the same LB type.

To migrate load balancer types:

  1. Manually create a new environment with the same configuration, but the new load balancer type.
  2. Deploy your application to the new environment.
  3. Shift traffic over via a CNAME swap or Route 53 DNS update.

Decoupling RDS from a Beanstalk environment

RDS provisioned directly inside a Beanstalk environment is fine for dev/test, but risky for production — its lifecycle is tied to the environment's. Deleting the environment deletes the database too. The fix: separate the database from the environment.

Decoupling RDS: snapshot as a safety net, protect the DB from deletion, stand up a new environment pointing at the same existing database via a connection string, swap traffic over, then remove the old environment.

Don't forget Because RDS deletion protection is enabled, terminating the old environment will leave its CloudFormation stack in a Delete Failed state (it can't delete the protected RDS instance) — you need to go into CloudFormation and manually delete that stack afterward.

12 Beanstalk Cleanup

To avoid ongoing cost from running environments: go to the application level, choose Actions → Delete application, and confirm by typing the name.

Good to know Deleting the application deletes all its environments, which in turn tells CloudFormation to tear down every resource it created for them (load balancers, ASGs, security groups, etc.) — one action cleans up everything.

✓ Cheat Sheet

Key facts to remember

  • Beanstalk = developer-centric PaaS: you supply code, it provisions EC2/ASG/ELB/RDS via CloudFormation under the hood. The service itself is free — you pay for what it creates.
  • Two tiers: Web server (load balancer → EC2) and Worker (SQS queue → EC2 workers, scales on queue depth).
  • Two deployment presets: Single instance (dev) vs High availability (load balanced, prod).
  • Deployment modes, in order of increasing cost/safety: All at once → Rolling → Rolling with additional batch → Immutable → Blue/Green (manual) / Traffic Splitting (automated canary).
  • "Canary testing" on the exam = traffic splitting.
  • Max 1,000 application versions per account — use a lifecycle policy (by age or count) to clean up unused ones; in-use versions are never deleted.
  • .ebextensions (in a .ebextensions/ folder, files ending in .config, YAML/JSON) let you configure anything via code, including raw CloudFormation resources.
  • Load balancer type cannot be changed after environment creation — only its configuration. Changing type requires a new environment + traffic cutover.
  • RDS inside a Beanstalk environment is tied to that environment's lifecycle — decouple it for production by snapshotting, enabling deletion protection, and pointing a new environment at the existing DB via a connection string.
  • Cloning copies an environment's exact configuration (not RDS data) into a new environment — handy for spinning up test copies of prod.
  • Swap environment domains exchanges DNS between two environments — the mechanism behind promoting a tested clone to become the new prod.

Mental model

Elastic Beanstalk is a thin, developer-friendly layer over CloudFormation: you hand it code and a few high-level choices (platform, single-instance vs. high-availability, deployment mode), and it assembles the same load-balancer-plus-auto-scaling-group architecture you'd otherwise build by hand — while still letting you drop down into .ebextensions and CloudFormation whenever you need something the console doesn't expose. Everything else in this section — deployment modes, lifecycle policies, cloning, migrations — is really about answering one question safely: how do I roll out a new version (or a new architecture) without breaking what's already running for users.
