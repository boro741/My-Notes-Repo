1 Introduction to CI/CD in AWS

Manually deploying things (like we did with Elastic Beanstalk earlier) works, but it's error-prone and doesn't scale. The goal of CI/CD is to push code and have it automatically tested, and then automatically deployed — safely, and through stages (dev → test → staging → prod), possibly with manual approval gates before production.

Continuous Integration (CI)

Developers push code often into a central repo (GitHub, CodeCommit, Bitbucket). A build/test server immediately checks the code and reports back pass/fail. Benefits: bugs found early, faster delivery, more frequent deploys, happier developers.

Continuous Delivery/Deployment (CD)

Every push that passes testing flows automatically all the way to live application servers — shifting from "one release every 3 months" to multiple releases a day.

2 CodeCommit Overview

CodeCommit is AWS's private, fully managed Git repository service.

  • No repo size limit, highly available, fully within your AWS account/VPC (increased security/compliance vs. third-party hosting).
  • Encrypted at rest (KMS) and in transit (HTTPS/SSH); access controlled entirely by IAM.
  • Integrates with standard CI tools (Jenkins, CodeBuild, etc.).
  • Cross-account access uses an IAM role + STS AssumeRole rather than sharing credentials/SSH keys directly.

CodeCommit vs GitHub

3 CodeCommit — Hands On

  • Create a repo, then add files either through the console (one at a time) or by cloning it and using standard git commands.
  • The default/first branch is called master; you can create additional branches for collaboration.
  • Pull requests merge changes from one branch into another (e.g. a feature branch into master).
  • Notification rules (comments, approvals, pull request/branch/tag events) can target an SNS topic or Slack (via Chatbot) — good for team alerting.
  • Triggers react to specific code events (push to a branch, create/delete branch or tag) and can invoke SNS or Lambda.

Connecting via Git

  1. Install Git (or use CloudShell, which has it pre-installed) and the git-remote-codecommit package.
  2. git clone using the connection URL from the console (HTTPS, SSH, or HTTPS GRC — SSH only shows if you're using an IAM user, not root).
  3. Configure git config user.email / user.name, then the usual git add / git commit / git push workflow.

4 CodePipeline Overview

CodePipeline is the visual workflow tool that orchestrates your whole CI/CD process across sources, builds, tests, and deployments.

PhaseOptions
SourceCodeCommit, ECR, S3, Bitbucket, GitHub
BuildCodeBuild, Jenkins, CloudBees, TeamCity
TestCodeBuild, Device Farm, or third-party
DeployCodeDeploy, Beanstalk, CloudFormation, ECS, S3
InvokeLambda, Step Functions

A pipeline is made of stages, each containing sequential and/or parallel actions — including a manual approval action, e.g. requiring sign-off before deploying to production.

How artifacts flow between stages

Each stage's output ("artifacts") is stored in S3, and the next stage picks it up from there — so CodeBuild, for instance, never needs direct access to CodeCommit; CodePipeline hands it the code via S3.

Troubleshooting: use CloudWatch Events/EventBridge for pipeline/stage state changes (e.g. alert on a failed pipeline), check the pipeline's IAM service role if an action can't be performed, and CloudTrail to audit denied API calls.

5 CodePipeline — Hands On

  • Prerequisite: two Elastic Beanstalk environments (e.g. env for dev, prod) to deploy into.
  • Create a pipeline with source = GitHub (v2, via a connection/app installation), triggered on push to the main branch; deploy target = the dev Beanstalk environment.
  • The pipeline's service role may need extra permissions manually attached (e.g. Beanstalk admin access) if deployment fails on permissions.

Adding a second stage with a manual approval action before the prod deploy means every production release needs a human to click "approve" first — reviewing the dev deployment before it goes further.

  • Editing the pipeline lets you add a new stage (e.g. "DeployToProd") containing two sequential action groups: a Manual Approval action, then a Deploy to Beanstalk (prod) action.
  • Pushing a new commit automatically triggers the whole pipeline — the dev deploy happens immediately, then the pipeline pauses at the manual approval step until someone reviews and approves it, only then deploying to prod.

6 CodeBuild Overview

CodeBuild takes source code (CodeCommit, S3, Bitbucket, GitHub) plus a set of build instructions and runs them in a container.

Exam point The build instructions file is named buildspec.yml and must live at the root of your repo (best practice — you can also enter commands manually in the console, but the exam focuses on buildspec.yml).

CodeBuild pulls a language-specific (or custom) Docker image, runs every phase defined in buildspec.yml against your source, then ships logs and artifacts out to CloudWatch/S3.

buildspec.yml structure

SectionPurpose
envEnvironment variables — plaintext, or pulled from SSM Parameter Store / Secrets Manager
phases.installInstall packages/dependencies
phases.pre_buildCommands before the actual build
phases.buildThe actual build/test commands
phases.post_buildFinishing touches (e.g. zipping output)
artifactsWhich files to extract and send to S3
cacheWhich files (usually dependencies) to cache in S3 to speed up future builds

Pre-built environments exist for Java, Ruby, Python, Go, Node.js, Android, .NET Core, PHP — or extend your own Docker image for anything else. Build Projects can be defined directly in CodeBuild or invoked from CodePipeline.

7 CodeBuild — Hands On

  • Create a build project pointed at a GitHub repo, choose a managed image (e.g. Ubuntu Standard), and reference buildspec.yaml in the source root.
  • Without a buildspec.yaml present, the build fails immediately ("no yaml file exists").
  • Adding a buildspec.yaml with a test command like grep -Fq "Congratulations" index.html turns CodeBuild into a real test gate — the build only succeeds if that text is actually present.
Good to know A GitHub webhook can trigger CodeBuild directly on every push — but once CodeBuild is wired into a CodePipeline stage instead, remove that webhook so CodePipeline (not GitHub) is the one triggering builds.

Integrated into the pipeline as a "TestCode" stage between Source and Deploy: if the grep test fails (e.g. someone removes "Congratulations" from the page), the pipeline stops there and never reaches the deploy stage — demonstrating the whole point of a CI gate.

8 CodeDeploy Overview

CodeDeploy automates deploying an application version to EC2/on-premises, Lambda, or ECS — and can automatically roll back on failure or a triggered CloudWatch alarm.

Controlled by an appspec.yml file, and deployment speed is configurable: AllAtOnce, HalfAtATime, OneAtATime, or custom.

EC2/on-premises: in-place vs blue/green

In-place upgrades existing instances in batches (some downtime risk per batch); blue/green stands up an entirely new fleet and only cuts traffic over once it's healthy.

  • Requires the CodeDeploy agent installed on each target instance (manually, or automated via Systems Manager), plus an IAM role/instance profile with S3 read access (the application revision is stored in S3).

Lambda: traffic shifting between aliases

StrategyBehavior
LinearGrow traffic by a fixed % every N minutes (e.g. LambdaLinear10PercentEvery3Minutes)
CanaryHold at a small % for a period, then jump to 100% (e.g. LambdaCanary10Percent5Minutes)
AllAtOnceImmediate full cutover — fastest, no chance to test first

This is fully integrated into the SAM framework (covered later in the course).

ECS: blue/green only

A new target group runs the new ECS task definition at the same capacity; the ALB shifts traffic from the old (blue) to the new (green) target group using the same Linear/Canary/AllAtOnce strategies.

9 CodeDeploy — Hands On

  1. Create two IAM roles: one for the CodeDeploy service itself, one for the EC2 instance (needs S3 read access to pull the application revision).
  2. Create a CodeDeploy application (compute platform: EC2/on-premises).
  3. Launch an EC2 instance, install the CodeDeploy agent on it (a Ruby-dependent install script), and verify it's running.
  4. Tag the instance (e.g. Environment: Development) — CodeDeploy uses these tags to define a deployment group.
  5. Upload the application bundle (containing appspec.yml + your files) as a zip to S3.
  6. Create a deployment pointing at that S3 zip, targeting the tag-matched deployment group.
Don't forget A deployment fails if the EC2 instance is missing its IAM instance profile (needed to pull from S3) — attach it via Actions → Security → Modify IAM role, then retry the deployment.

appspec.yml defines: which files go where (e.g. index.html → /var/www/html), and lifecycle hooks like BeforeInstall (install dependencies), ApplicationStart (start the server), and ApplicationStop (stop it before updating). The deployment lifecycle you'll see in the console: ApplicationStop → DownloadBundle → BeforeInstall → Install → AfterInstall → ApplicationStart → ValidateService.

10 CodeDeploy for EC2 & ASG

  • In-place with an ASG: existing instances get updated in place, and any new instance the ASG launches later automatically gets the current deployed revision too — very convenient.
  • Blue/green with an ASG: a brand-new ASG is created (settings copied from the original), the new version is deployed to it, you choose how long to keep the old ASG around, and the load balancer cuts over from the old target group to the new one.
Exam point A CodeDeploy rollback is not "going back in time" — it's a brand-new deployment of the last known-good revision. Rollbacks can be automatic (on deployment failure or a triggered CloudWatch alarm) or manual, and can be disabled entirely for a given deployment.

11 CodeArtifact Overview

CodeArtifact is a secure, scalable artifact/dependency management service — integrates with Maven, Gradle, npm, yarn, twine, pip, and NuGet.

CodeArtifact proxies requests to public package repositories and caches everything it fetches — so your build stays working even if a public package later disappears.

  • A domain is a set of repositories (typically one per company); repositories can have upstream repos, including a public one for proxying.
  • Two benefits of proxying: (1) developers/CodeBuild never talk to the public internet directly (network security), (2) fetched packages get cached, so they're still available even if removed upstream.
  • You can also publish your own packages into CodeArtifact for internal reuse.
  • Package events (created/modified/deleted) go to EventBridge, which can trigger Lambda, SNS, SQS, or even CodePipeline — e.g. auto-rebuild and redeploy when a dependency updates.
Exam point In-account access to CodeArtifact uses IAM policies as usual. Cross-account access requires a resource policy — and it's all-or-nothing per repo: you can't grant access to only some packages within it.

12 CodeArtifact — Hands On

  1. Create a repository with an upstream connection to the public PyPI store, inside a new domain (encrypted with a KMS key).
  2. Get a CodeArtifact authorization token (valid ~12 hours) and configure pip/pip3 to use it.
  3. pip3 install <package> now pulls through CodeArtifact — the package (and its dependencies) get cached in both the connected repo and the upstream repo.
  4. Installing a different version of the same package caches that version too — multiple versions can coexist in the repo.

Repository policies (read-only, read+publish, or full access) and domain policies can be applied for fine-grained access control across accounts/principals.

✓ Cheat Sheet

Key facts to remember

  • CI = test code automatically on every push; CD = automatically deploy code that passes tests, often through dev → test → staging → prod with optional manual approval gates.
  • CodeCommit: private, fully managed Git in your AWS account, IAM-controlled, no size limit.
  • CodePipeline orchestrates source → build → test → deploy stages; artifacts move between stages via S3, so services never need direct access to each other.
  • CodeBuild reads buildspec.yml (must be at repo root) with install/pre_build/build/post_build phases; runs in a container (prebuilt language image or your own Docker image).
  • CodeDeploy targets EC2/on-premises, Lambda, or ECS. EC2: in-place (batched updates) or blue/green (new ASG + cutover). Lambda/ECS: traffic-shifting via Linear/Canary/AllAtOnce between aliases or target groups.
  • A CodeDeploy rollback = a fresh deployment of the last known-good revision, not literally reverting time.
  • CodeArtifact proxies + caches public package repos (npm, pip, Maven, NuGet, etc.) inside your own domain/repos; cross-account access needs a resource policy and is all-or-nothing per repo.
  • appspec.yml (CodeDeploy) defines file mappings + lifecycle hooks (BeforeInstall, ApplicationStart, ApplicationStop, etc.); the EC2 instance needs the CodeDeploy agent + an IAM role with S3 read access.

Mental model

These four services map directly onto the four stages of CI/CD: CodeCommit is where code lives, CodeBuild is where it gets tested/compiled according to a checked-in recipe (buildspec.yml), CodeDeploy is where a tested build actually lands on real infrastructure (with in-place or blue/green safety nets and automatic rollback), and CodePipeline is the conductor that wires all of it — plus manual approval gates — into one repeatable, automatic path from "developer pushes code" to "code is safely running in production." CodeArtifact is a supporting player: it makes sure the dependencies all of this relies on are cached, secure, and won't vanish out from under a future build.
