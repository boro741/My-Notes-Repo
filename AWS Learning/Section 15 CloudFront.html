1 CloudFront Overview

CloudFront is AWS's CDN (Content Delivery Network). Whenever you see "CDN" on the exam, think CloudFront.

  • It caches your website/content at edge locations around the world, so users get content from somewhere close to them → lower latency, better experience.
  • Made up of hundreds of points of presence globally (edge locations + caches).
  • Because content is spread globally, CloudFront also provides DDoS protection — an attack hitting one location doesn't take down everything, and it works alongside AWS Shield and WAF (covered later in the security section).

The first user in a region pulls content from the origin through their nearest edge location; every later user nearby gets served straight from that edge's cache.

Origins CloudFront can connect to

  • Amazon S3 bucket — for distributing/caching files, or even uploading files to S3 through CloudFront. Secured via Origin Access Control (OAC).
  • VPC origin — connect privately to things inside your VPC: private application load balancers, network load balancers, or EC2 instances.
  • Custom origin over HTTP — e.g. an S3 static website (must be enabled as a website first) or any public HTTP backend, like a public load balancer.

How it works at a high level

A client's HTTP request hits an edge location. If the content is already cached there, it's served immediately. If not, the edge location fetches it from the origin, serves it, and caches it locally so the next request for the same content doesn't need to go back to the origin.

CloudFront vs S3 Cross-Region Replication

CloudFrontS3 Cross-Region Replication
CoverageGlobal edge network (~216 points of presence)Only the specific regions you set up
FreshnessCached, e.g. for about a dayUpdated near real-time, no caching
DirectionRead (caching)Read-only replicated copy
Best forStatic content that needs to be fast everywhereDynamic content that changes often, needed at low latency in a few regions

2 CloudFront Hands On

  • Create an S3 bucket, upload some files (private by default) — trying the plain Object URL gives Access Denied; the console's "Open" link works because it generates a pre-signed URL.
  • Create a CloudFront distribution: choose a plan (the Free plan covers plenty — enough requests/month, always-on DNS protection, geographic traffic blocking, global CDN, free TLS certs). Paid plans add things like edge key-value store, advanced DDoS protection, uptime SLA.
  • Set origin type = Amazon S3, point it at your bucket, and allow CloudFront private access to the bucket using the recommended origin/cache settings.
Good to know Creating the distribution automatically updates your S3 bucket policy to allow access only from your CloudFront distribution — you can see this new statement under the bucket's Permissions tab.
  • Once deployed, visiting the CloudFront domain name directly gives Access Denied (there's no default file at the root) — but a specific path like /coffee.jpg or /index.html loads correctly, even though the underlying S3 objects are private.
  • Reloading a previously-requested file (like /beach.jpeg) is near-instant — that's the cache doing its job.

3 Caching & Cache Policies

  • Cache lives at each edge location — as many caches as edge locations.
  • Every cached object is identified by a Cache Key. By default, that's just the hostname + resource path of the URL (e.g. mywebsite.com + /content/stories/example-story.html).
  • Goal: maximize the cache hit ratio (minimize requests back to the origin).

A cache miss forwards the request to the origin, then stores the response at the edge so the next matching request is served instantly.

Enhancing the Cache Key: Cache Policy

Sometimes content varies by user, device, language, or location — so you may want to include more than just hostname + path in the Cache Key. A CloudFront Cache Policy lets you configure:

  • Headers — none, a whitelist of specific headers, all, or all-except.
  • Cookies — none, whitelist, all, or all-except.
  • Query strings — none, whitelist, all, or all-except.
  • TTL — from 0 seconds up to 1 year (also controllable via Cache-Control or Expires headers).
Exam point Whatever headers/cookies/query strings you include in the Cache Key are automatically forwarded to the origin too. E.g. whitelisting a language header means it's both part of the cache key and sent to the origin so it can respond in the right language.
Don't forget The more you include in the Cache Key (especially "all" query strings/cookies/headers), the worse your cache hit ratio gets — more variations mean fewer requests share a cached entry.

Origin Request Policy

What if you want to forward extra data to the origin without it affecting the Cache Key? That's what an Origin Request Policy is for — it can add extra headers, cookies, or query strings to the origin request (even ones the viewer never sent, like a secret API key), but none of that extra data is part of the cache key.

Analogy Think of the Cache Policy as deciding what goes on the "label" you use to file something away (so similar requests find the same cached copy), while the Origin Request Policy is extra info stapled to the request when you actually go ask the origin for something — it helps the origin do its job, but doesn't change how things get filed in the cache.

4 Cache Invalidations

If you update your origin content, edge locations won't know until the cached copy's TTL expires. If you need the update to show up immediately, you can force a refresh — that's a CloudFront invalidation.

  • You pass in a file path — either /* to invalidate everything, or something scoped like /images/*.
  • Invalidated files are removed from every edge location's cache — the next request for them forces a fresh fetch from the origin.
Tip Invalidate only what changed (e.g. /index.html and /images/*) rather than always nuking the whole cache with /*, to avoid unnecessary origin load.

5 Cache Behaviors

You can route different URL path patterns to different origins or apply different caching rules per path. E.g. /images/* → S3, /api/* → your app origin, /* (the default cache behavior) → whatever's left.

Exam point The default cache behavior (/*) is always evaluated last — more specific path patterns are checked first, and if nothing matches, it falls back to the default.

Cache behaviors route requests to different origins based on the path — most specific pattern wins, default (/*) always catches whatever's left.

Use case: gating access with a login page

Set up a cache behavior for /login that goes to an EC2 instance which generates CloudFront signed cookies. The user then uses those signed cookies to access the default cache behavior (everything else, e.g. an S3 bucket). If they try to access content without logging in first, the default behavior can be configured to require signed cookies, redirecting them back to /login.

Use case: maximizing cache hits

Static content (e.g. from S3) can use a simple cache policy with no headers/cookies to maximize hits. Dynamic content (e.g. a REST API behind a load balancer + EC2) may need headers/cookies in the cache policy to serve correctly personalized responses.

6 Caching & Invalidations Hands On

  • In the distribution's default behavior, you can create a Cache Policy (set TTL min/max/default, choose which headers/cookies/query strings go into the cache key) and, optionally, an Origin Request Policy (extra headers/cookies/query strings forwarded to the origin only).
  • You can add a new cache behavior (e.g. for /images/*) pointing to a different origin, with its own cache key and origin request policy — multiple behaviors coexist, most specific wins.

Demonstrating TTL + invalidation

  1. Edit index.html, re-upload it to S3 (overwriting, since versioning isn't enabled here).
  2. Opening the file directly from S3 shows the updated content immediately.
  3. Refreshing the CloudFront URL still shows the old content — because it's cached and the TTL (1 day) hasn't expired yet.
  4. Creating an invalidation for /* clears the cache, and refreshing the CloudFront URL now shows the updated content, freshly fetched from S3.

7 ALB/EC2 as an Origin

The new, better way: VPC origins

Lets CloudFront deliver content directly from apps hosted in your private subnets — private ALBs, NLBs, or EC2 instances — without exposing anything to the public internet.

VPC origins let CloudFront reach private ALBs, NLBs, or EC2 instances directly — nothing needs to be exposed to the public internet.

The old way (before VPC origins existed)

  • Your EC2 instance or ALB had to be public.
  • You'd look up the full list of CloudFront's public edge-location IPs and configure your security group to allow traffic only from those IPs.
Don't forget The old method was tedious (manually tracking CloudFront's IP list) and riskier — if someone accidentally loosens the security group, your instance becomes exposed to more than just CloudFront. VPC origins avoid this risk entirely since the backend never needs a public IP.

8 Geo Restriction

Restrict who can access your distribution based on the country they're connecting from (determined via a third-party geo-IP database).

  • Allow list — only approved countries can access.
  • Block list — banned countries are denied.
  • Use case: enforcing copyright restrictions on content by region.
Don't forget Geo restriction (like other security options) wasn't available on the Free plan at the time of recording — you needed a paid plan or "Pay as You Go" billing to access it under the distribution's Security settings.

9 Signed URL / Signed Cookies

Want to make a CloudFront distribution private, but still give specific people access to premium/paid content — while knowing who has access to what? Use a CloudFront signed URL or signed cookie.

When creating either, you attach a policy defining:

  • Expiration — when it stops working.
  • IP ranges allowed to use it (if you know your clients' IPs).
  • Trusted signers — which accounts are allowed to create signed URLs/cookies.
Signed URLSigned Cookie
ScopeOne URL per fileOne cookie can unlock many files
Best forSharing individual filesGiving access to a batch of content (e.g. a whole premium section of a site)

The app authenticates the user, generates a signed URL via the AWS SDK, and hands it back — the client then uses it directly against CloudFront.

CloudFront Signed URL vs S3 Pre-signed URL

CloudFront Signed URLS3 Pre-signed URL
Works withAny origin (S3, HTTP backend, etc.)S3 only
Key managementAccount-wide key pair or key group; can be managed by any sufficiently-permissioned IAM user (key groups) — or root only (old key pair method)Issued using the signer's own IAM credentials/permissions
FilteringBy IP, path, date, expirationLimited lifetime only
CachingLeverages all of CloudFront's cachingNo caching layer
Use whenCloudFront sits in front of S3 (bucket policy restricts direct S3 access to CloudFront/OAC)Users access S3 directly, no CloudFront involved

10 Signed URL — Key Groups & Hands On

Two ways to manage signing keys

MethodDetails
Trusted key group (recommended)Manage via APIs, rotate keys, secure with IAM. Any sufficiently-permissioned IAM user can manage it.
Account CloudFront key pair (old method)Requires the root account and the AWS console — no APIs, can't be automated, not recommended.

Hands-on: setting up a trusted key group

  1. Generate an RSA key pair, 2,048-bit (private key + public key).
  2. The private key goes on your application (e.g. EC2 instances) — used to sign URLs. Keep it secret.
  3. The public key gets uploaded into CloudFront (under Key Management → Public Keys) — used to verify signatures.
  4. Create a Key Group and add up to 5 public keys to it.
  5. CloudFront references this key group to validate signed URLs/cookies generated by your app.
Exam point The old CloudFront key-pair method (root account, AWS console, security credentials page) still exists, but the recommended, current approach is public keys + key groups, since it supports IAM permissions and API automation.

11 Advanced Concepts

Pricing & Price Classes

Data transfer cost out of CloudFront varies by continent/region — e.g. the first 10TB out of the US/Canada/Mexico costs ~$0.08/GB, while the same in India costs about ~$0.17/GB. Cost per GB also drops the more total data you transfer (e.g. over 5PB out of the US drops to ~$0.02/GB).

To control cost, you can limit which edge locations serve your distribution using a Price Class:

Price ClassCoverage
Price Class AllAll edge locations worldwide — best performance, highest cost
Price Class 200Most regions, excludes the priciest ones
Price Class 100Only the least expensive regions (e.g. North America & Europe)

Multiple Origins vs Origin Groups

These solve different problems:

  • Multiple origins + cache behaviors — route by path/content type, e.g. /api/* → Application Load Balancer, everything else → S3.
  • Origin Groups — high availability / failover. One primary + one secondary origin; if the primary errors out, CloudFront retries the same request against the secondary.

In an origin group, CloudFront automatically retries a failed request against the secondary origin — e.g. two S3 buckets in different regions kept in sync via replication, giving region-level disaster recovery.

Field-Level Encryption

Adds extra protection for specific sensitive fields (e.g. credit card numbers) on top of HTTPS encryption in transit — using asymmetric encryption.

Only the sensitive field (e.g. a credit card number) gets its own layer of encryption at the edge — everything in between (CloudFront, the load balancer) passes it along encrypted, and only the web server holding the private key can decrypt it.

  • Up to 10 fields can be marked for field-level encryption per request.
  • Only the origin/web server with the private key can decrypt those fields — CloudFront and any load balancer in between never see the plaintext.

12 Real-Time Logs

CloudFront can stream every request it receives, in real time, into a Kinesis Data Stream — useful for monitoring, analyzing, and reacting to content delivery performance.

  • For near-real-time (batch) processing instead, send the same stream through Kinesis Data Firehose to a destination like S3 or OpenSearch.
  • You control the sampling rate — the percentage of requests captured (useful to avoid overwhelming the stream on high-traffic endpoints).
  • You can also choose which fields and which cache behaviors/path patterns get logged (e.g. only requests to /images/*).

✓ Cheat Sheet

Key facts to remember

  • CDN on the exam = CloudFront. Caches content at edge locations globally, lowering latency and adding DDoS resilience.
  • Origins: S3 (via OAC), VPC origin (private ALB/NLB/EC2 — the modern secure way), or custom HTTP origin.
  • CloudFront vs S3 CRR: CloudFront = global caching (~1 day TTL) for static content; CRR = near-real-time, read-only, region-to-region replication for dynamic content.
  • Default Cache Key = hostname + resource path; extend it with headers/cookies/query strings via a Cache Policy — but anything you add is also forwarded to the origin and hurts your hit ratio.
  • Need to forward extra data to the origin without affecting the cache key? Use an Origin Request Policy.
  • Force fresh content immediately (before TTL expires) with a Cache Invalidation — scope it (e.g. /images/*) rather than always using /*.
  • Cache behaviors route by path pattern to different origins; the default (/*) always evaluates last.
  • Geo restriction: allow-list or block-list by country (via geo-IP lookup).
  • Signed URL = one file per URL; Signed cookie = many files per cookie. Trusted key groups are the modern way to manage signing keys (vs. the old root-only CloudFront key pair).
  • CloudFront Signed URL works with any origin type; S3 Pre-signed URL only works directly against S3 (no CloudFront in front).
  • Price classes trade off edge location coverage vs. cost (All / 200 / 100).
  • Origin groups (primary + secondary) give automatic failover / high availability — different purpose than multi-origin path-based routing.
  • Field-level encryption protects specific sensitive fields end-to-end, decryptable only by the origin holding the private key.
  • Real-time logs stream requests to Kinesis Data Stream (optionally onward via Firehose), with configurable sampling rate and field/path filtering.

Mental model

CloudFront is a global cache sitting in front of your real backend (S3, ALB, EC2, or any HTTP origin): it decides what to cache and how (cache policies, cache keys), how to invalidate stale content, how to route different paths to different places (cache behaviors and origin groups), how to keep things private and controlled (VPC origins, signed URLs/cookies, geo restriction, field-level encryption), and how to keep costs down by choosing how far around the world you actually need edge coverage (price classes) — all while giving you visibility into what's happening through real-time logs.
