1 CloudFront Overview

Amazon CloudFront is AWS's Content Delivery Network (CDN) service. On the exam, whenever a scenario asks for a global CDN or caching network to improve user speed, CloudFront is the answer.

  • It caches website static content (images, videos, HTML/CSS) at hundreds of global Edge Locations (Points of Presence) close to users. This drastically reduces latency (network lag and delay).
  • Because content is distributed across AWS's global edge network, CloudFront also offers built-in DDoS Protection (Distributed Denial of Service attack defense) in combination with AWS Shield and AWS WAF.

The first user in a region pulls file content from the origin server through their nearest Edge Location. Subsequent users nearby get served instantly from that Edge Location's cache.

Origins Supported by CloudFront

  • Amazon S3 Bucket: Store and cache files globally. Secured using Origin Access Control (OAC) to block direct public access to S3.
  • VPC Origin: Securely fetch data from private backend resources inside a VPC (Application Load Balancer, Network Load Balancer, or EC2 instances) without exposing them to the internet.
  • Custom HTTP Origin: Any public HTTP web server, such as an S3 Static Website endpoint or an external web server.

High-Level Architecture

When a client requests a file, the HTTP request arrives at the nearest CloudFront Edge Location. If the file is cached locally (Cache Hit), it returns instantly. If not (Cache Miss), the Edge Location fetches the file from the Origin backend server, caches it locally for future requests, and delivers it to the user.

2 CloudFront Hands On

  • Create a private S3 bucket and upload media files. Accessing the direct S3 Object URL yields an Access Denied error.
  • Create a CloudFront distribution. Pick an appropriate distribution plan (the Free Tier plan includes generous monthly request quotas, free TLS certificates, and basic protection).
  • Select your S3 bucket as the origin and configure Origin Access Control (OAC) to grant CloudFront exclusive access.
Good to Know Configuring OAC automatically generates an S3 Bucket Policy snippet that allows read requests coming only from your CloudFront distribution ID.
  • Once deployed, visiting the bare CloudFront distribution domain returns Access Denied (since no root default file is set), but visiting explicit file paths like /coffee.jpg loads immediately.
  • Reloading previously requested files yields near-instant response times because CloudFront serves them straight from its local Edge Location cache.

3 Caching & Cache Policies

  • Every CloudFront Edge Location maintains its own local cache store.
  • Each cached file is indexed by a unique Cache Key. By default, the Cache Key consists of the Domain Name (Hostname) + URL Path (e.g., mywebsite.com/images/banner.jpg).
  • The main objective of caching is to maximize the Cache Hit Ratio (serving requests from the edge while minimizing backend origin calls).

A Cache Miss sends the request to the origin, then stores the response at the edge so subsequent matching requests are served instantly.

Customizing the Cache Key: Cache Policies

When web content varies based on user language, device type, or session cookies, you can include extra request elements in the Cache Key using a Cache Policy:

  • HTTP Headers: Include specific headers (e.g., Accept-Language) in the Cache Key.
  • Cookies: Include session or user cookies in the Cache Key.
  • Query Strings: Include URL parameters in the Cache Key.
  • TTL (Time To Live): Define minimum, maximum, and default caching durations (also configurable via HTTP Cache-Control response headers).
Exam Point All HTTP Headers, Cookies, or Query Strings included in a Cache Policy are automatically forwarded to the origin backend server.
Warning on Cache Hit Ratio Including too many parameters (or choosing "All" headers/cookies) in your Cache Policy lowers your Cache Hit Ratio because fewer requests will share exact matching Cache Keys.

Origin Request Policy

If your backend origin server requires specific HTTP headers, cookies, or query strings to process requests, but you do NOT want them to affect caching, use an Origin Request Policy. It forwards necessary data to the origin without altering the Edge Cache Key.

Everyday Analogy Think of a Cache Policy as the filing label on a library book (determining where the book is stored and found on the shelf). Think of an Origin Request Policy as a sticky note with extra instructions handed directly to the librarian (origin) when ordering a new book — it helps the librarian fulfill the request without changing how books are filed on the shelf.

4 Cache Invalidations

When you update files on your origin backend server, CloudFront Edge Locations continue serving old cached versions until their TTL (Time To Live) expires. To force CloudFront to serve new content immediately, perform a Cache Invalidation.

  • Specify file path patterns to invalidate — e.g., /* to clear all cached files, or targeted paths like /images/* or /index.html.
  • Invalidated files are removed from all global Edge Location caches, forcing subsequent user requests to fetch fresh copies from the origin.
Best Practice Tip Target specific updated file paths (e.g., /index.html) during invalidations rather than clearing the full cache with /* to avoid unnecessary load spikes on your origin server.

5 Cache Behaviors

Cache Behaviors allow routing different URL path patterns to different origin servers or applying separate caching rules per path. For example, route /images/* to an S3 bucket, /api/* to an Application Load Balancer, and /* (Default Cache Behavior) to a main web server.

Exam Point The Default Cache Behavior (/*) is always evaluated LAST. CloudFront checks specific path patterns first, and falls back to the default behavior only if no specific pattern matches.

Cache behaviors direct incoming request paths to matching origins. Specific rules take priority, and the default behavior catches remaining traffic.

6 Caching & Invalidations Hands On

  • Within distribution settings, configure a Cache Policy (setting TTL boundaries and Cache Key headers/cookies) and optionally attach an Origin Request Policy.
  • Add custom Cache Behaviors (such as /images/*) to direct specific paths to secondary origins with tailored rules.

Hands-On Walkthrough: Cache TTL & Invalidation

  1. Edit index.html and upload the revised file to S3.
  2. Viewing the object directly via S3 shows updated text immediately.
  3. Refreshing the CloudFront URL continues showing old cached text because the 24-hour TTL has not expired.
  4. Creating a Cache Invalidation for /* purges Edge caches. Refreshing CloudFront now retrieves and displays the updated page from S3.

7 ALB/EC2 as an Origin

Modern Approach: CloudFront VPC Origins

VPC Origins allow CloudFront to connect directly and securely to private backend applications hosted inside private subnets (Private ALBs, Private NLBs, or EC2 instances) without assigning public IP addresses or exposing backends to the internet.

VPC Origins connect CloudFront directly to private VPC resources, eliminating public internet exposure for backend servers.

Legacy Approach (Before VPC Origins)

  • Required making ALB or EC2 instances public.
  • Required maintaining Security Group rules restricted exclusively to CloudFront's public IP address prefix lists.

8 Geo Restriction

Control access to your distribution based on the geographical country of connecting users (determined via Geo-IP location lookup):

  • Allow List: Only specified approved countries can access content.
  • Block List: Denies access to users from blacklisted countries.
  • Use Case: Enforce copyright and licensing territorial restrictions.

9 Signed URL / Signed Cookies

To restrict access to premium or paid website content while serving data through CloudFront, use CloudFront Signed URLs or Signed Cookies.

A Signed URL or Cookie carries an attached signature policy specifying:

  • Expiration Date/Time: When access permission expires.
  • Allowed IP Addresses: Restricts usage to specific client IP ranges.
  • Trusted Signers: AWS accounts authorized to issue signed signatures.
FeatureCloudFront Signed URLCloudFront Signed Cookie
Access ScopeGrants access to one individual fileGrants access to multiple files or entire site sections
Best Use CaseSingle premium file downloadsBatch content access (e.g., subscriber-only video catalog)

The application authenticates the user, generates a Signed URL, and returns it. The client uses the Signed URL directly with CloudFront.

10 Signed URL — Key Groups & Hands On

Two Ways to Manage Signing Keys

Management MethodKey Details
Trusted Key Groups (Recommended)Manage public keys via AWS APIs, rotate keys seamlessly, and control permissions via IAM. Supported for devops automation.
Account CloudFront Key Pairs (Legacy)Requires Root Account console access. Cannot be automated via APIs. Not recommended.

Setup Steps for Trusted Key Groups

  1. Generate a 2,048-bit RSA Public/Private Key Pair locally on your system.
  2. Keep the Private Key secret on your web application server (used by code to sign URLs).
  3. Upload the Public Key to CloudFront under Key Management → Public Keys (used by CloudFront to verify signatures).
  4. Create a Key Group and add the public key to it. Attach the Key Group to your CloudFront Cache Behavior.
Exam Point The modern, recommended AWS practice for CloudFront URL signing is Public Keys + Key Groups because it supports automation via AWS APIs and standard IAM access control.

11 Advanced Concepts

Price Classes

Outbound data transfer costs vary across continents. To optimize cost, select a Price Class that restricts edge locations used by your distribution:

Price ClassEdge Location Coverage
Price Class AllAll global Edge Locations (highest performance, highest cost)
Price Class 200Includes most regions, excluding expensive locations
Price Class 100Includes only lowest-cost regions (North America & Europe)

Multiple Origins vs Origin Groups

  • Multiple Origins + Cache Behaviors: Route traffic by request path pattern (e.g., /api/* to ALB, /* to S3).
  • Origin Groups (Failover): Combine a Primary Origin and a Secondary Origin. If the primary fails with HTTP errors (e.g., 500, 502, 503, 504), CloudFront automatically retries against the secondary origin.

An Origin Group automatically routes failed requests from the primary origin to a secondary backup origin for high availability.

Field-Level Encryption

Encrypts specific sensitive POST data fields (such as credit card numbers or PAN/Aadhaar numbers) at the CloudFront Edge Location before transmitting across the network.

Field-level encryption encrypts sensitive fields at the edge. Intermediary servers (load balancers) cannot read the data; only the backend server holding the private key decrypts it.

  • Supports encrypting up to 10 specific fields per HTTP request payload.
  • Only the target backend origin holding the private key can decrypt the data fields.

12 Real-Time Logs

CloudFront can stream request telemetry in real time directly to an Amazon Kinesis Data Stream for monitoring and analytics.

  • Stream data through Kinesis Data Firehose to deliver log files to S3 buckets or OpenSearch.
  • Configure custom sampling rates (percentage of requests logged) to manage throughput.
  • Filter logging to specific fields and Cache Behaviors.

✓ Cheat Sheet

Key Facts to Remember

  • CDN: CloudFront caches content at global Edge Locations to reduce latency and protect against DDoS attacks.
  • Origins: Amazon S3 (via OAC), VPC Origins (private ALBs, NLBs, EC2), or Custom HTTP servers.
  • Cache Policy vs Origin Request Policy: Cache Policy defines parameters included in the Cache Key (which are also sent to origin). Origin Request Policy forwards extra headers/cookies to origin without altering the Cache Key.
  • Invalidations: Purge cached files from edge locations before TTL expiration.
  • Cache Behaviors: Route paths to different origins; default (/*) evaluates last.
  • Geo Restriction: Whitelist or blocklist traffic by country location.
  • Signed URLs & Cookies: Secure private distribution files. Use Key Groups for modern automated key management.
  • Origin Groups: Provide automated primary-to-secondary failover.
  • Field-Level Encryption: Protects sensitive payload fields end-to-end using edge public key encryption.

Mental Model

CloudFront acts as a high-speed global caching shield in front of backend origins. Cache Policies govern what gets cached at the edge. VPC Origins and OAC secure backend infrastructure. Signed URLs, Cookies, Geo Restriction, and Field-Level Encryption enforce data privacy and security, while Origin Groups deliver fault-tolerant origin failover.
