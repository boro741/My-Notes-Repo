58High Availability and Scalability

Scalability means your web application can easily handle higher user traffic by adjusting its computing power. There are two main ways to scale:

  • Vertical scaling — making a single server bigger and more powerful (scaling up or down).
  • Horizontal scaling (elasticity) — adding more servers to share the total workload (scaling out or in).
🏢 Call center analogy:
• Vertical scaling = Replacing a junior operator (handles 5 calls/min) with a senior expert (handles 10 calls/min). It is the same desk, just a more powerful worker.
• Horizontal scaling = Hiring 5 extra operators to share incoming customer calls. More people share the work.
• High Availability (HA) = Running call centers in two different cities (like Mumbai and Bangalore). If the Mumbai office loses power, the Bangalore office keeps answering calls seamlessly.
ConceptMeaningEveryday Example & Use Case
Vertical scalingUpgrading to a bigger EC2 instance (e.g. t2.micro → t2.large with more CPU & RAM).Single databases (like RDS or ElastiCache) that cannot split work across servers easily. Has a hardware limit.
Horizontal scalingAdding more EC2 instances (scale out) or removing extra ones (scale in).Modern web applications. Very easy in the cloud because you can launch new EC2 servers in seconds.
High Availability (HA)Running your app across ≥ 2 Availability Zones (separate physical data centers in a region).Ensures your system stays online even if an entire data center experiences a power cut or disaster.
Exam tip: High Availability can be passive (e.g., RDS Multi-AZ standby database sitting idle until the main DB fails) or active (e.g., horizontal scaling where all EC2 instances process user traffic simultaneously). HA does not always mean all servers are active.

EC2 Size Range: AWS provides a wide range of virtual server sizes — from the smallest t2.nano (0.5 GB RAM, 1 vCPU) to massive servers like u-12tb1.metal (12.3 TB RAM, 450 vCPUs).

59Elastic Load Balancing (ELB) Overview

A load balancer is a dedicated server (or managed group of servers) that receives incoming web traffic and distributes it evenly across multiple backend EC2 instances (virtual computers rented in the cloud). Users only ever visit one single front door — the load balancer — and never know which backend server answered them.

Every user connects to one central entry point (the load balancer). The load balancer spreads incoming requests across backend EC2 instances.

Why use a load balancer?

  • Single front door: Gives your app one single web address (DNS hostname).
  • Automatic fault tolerance: Uses health checks to detect failed servers and stop sending traffic to them.
  • SSL termination: Handles secure HTTPS encryption centrally.
  • Sticky sessions: Uses cookies to keep a user attached to the same backend server if needed.
  • High Availability: Spreads traffic smoothly across multiple Availability Zones (data centers).
  • Network security: Keeps backend EC2 servers hidden inside a private network safe from direct public internet access.

ELB is a fully managed service — AWS automatically handles server maintenance, security upgrades, and high availability for you. It is cheaper and more reliable than managing your own load balancing software, and connects directly with EC2, ASG, ECS, ACM, CloudWatch, Route 53, WAF, and Global Accelerator.

Health Checks

The load balancer regularly pings a port and a web route on each server (e.g. HTTP:80/health). If an instance replies with a 200 OK status, it is healthy. If it fails to respond correctly, ELB marks it unhealthy and immediately stops sending web traffic to it.

The 4 Types of AWS Load Balancers

Load BalancerSinceOSI LayerProtocolsStatus

Load balancers can be configured as internal (private within your network) or external / internet-facing (accessible to the public internet).

Security Group Setup (Crucial AWS Architecture Pattern!)

Security Group = A virtual security guard standing at the door.

  • Load Balancer's Security Group: Allow incoming HTTP (port 80) and HTTPS (port 443) traffic from anywhere on the internet (0.0.0.0/0).
  • EC2 Instance's Security Group: Allow HTTP traffic only from the Load Balancer's Security Group ID (not directly from public IP addresses!).
Exam tip: This is a very common exam pattern — backend EC2 instances must only accept traffic originating from the ELB's Security Group ID, blocking direct public access.

60Note: About the Classic Load Balancer (CLB)

The Classic Load Balancer is deprecated and has been retired from the AWS Console and AWS Certification exams. Therefore, hands-on practice for CLB is skipped.

61Application Load Balancer (ALB)

ALB operates at Layer 7 (the application layer handling HTTP/HTTPS web traffic). It inspects web requests and routes traffic to backend servers grouped into target groups.

Key Features

  • Load balance across multiple applications running on the same EC2 server (using Docker containers / Amazon ECS).
  • Supports modern web protocols like HTTP/2 and WebSockets.
  • Supports automatic web redirects (e.g. redirecting unencrypted HTTP traffic to secure HTTPS).
  • Supports intelligent routing rules:
    • Path-based routing: Send example.com/users to User servers and example.com/posts to Post servers.
    • Host-based routing: Send one.example.com and other.example.com to different target groups.
    • Query string / header routing: Route requests based on URL parameters (e.g. ?platform=mobile vs ?platform=desktop).

ALB is ideal for microservices and containerized applications (supporting dynamic port mapping with Amazon ECS). Unlike CLB (which required 1 load balancer per app), a single ALB can manage web traffic for many apps at once.

One ALB routes /user web requests to one target group and /search requests to a completely separate target group.

Target Groups Can Contain:

  • EC2 instances (managed automatically by an Auto Scaling Group)
  • Amazon ECS tasks (Docker containers)
  • AWS Lambda functions (serverless backend code)
  • Private IP addresses (on-premises physical servers)

Health checks operate at the target group level, so an ALB can monitor different backend services independently.

Important Details to Know

  • ALB provides a fixed DNS hostname (web link), not a static IP address.
  • Your backend EC2 server sees the Load Balancer's private IP as the request origin. To get the user's real IP, your app code reads the X-Forwarded-For HTTP header.
  • Headers X-Forwarded-Port and X-Forwarded-Proto report the original port and protocol (HTTP/HTTPS) used by the client.
  • The load balancer performs connection termination: client → LB (over public IP), then LB → EC2 (over private network).

62-63Application Load Balancer — Hands-On

Part 1: Basic Setup

  1. Launch 2 EC2 instances (Amazon Linux 2, t2.micro) with a user-data startup script that serves "Hello World" over HTTP.
  2. Verify each instance returns "Hello World" individually using its public IP address.
  3. Create an ALB (DemoALB) — internet-facing, IPv4, deployed across all Availability Zones.
  4. Create a security group for the ALB (demo-sg-load-balancer) allowing incoming HTTP traffic from anywhere.
  5. Create a target group (demo-tg-alb) — HTTP protocol on port 80 — and register both EC2 instances.
  6. Link the target group to the ALB's listener on port 80.
  7. Once ALB status is active, visit its DNS name in your browser. Refreshing shows responses alternating between both instances = load balancing works cleanly! ✅
Health check proof: Stop one EC2 instance → it becomes "unhealthy" in the target group within ~30s → ALB only routes traffic to the remaining healthy instance. Start it back up → after passing health checks, it rejoins traffic rotation automatically.

Part 2: Security Tightening & Routing Rules

  • Restrict direct EC2 access: Edit the EC2 security group's HTTP rule — remove public internet access and allow traffic only from the ALB's security group ID. Direct access to the EC2 public IP now times out, while access via ALB DNS works perfectly.
  • Listener Rules: Add a custom rule on the ALB listener:
    • Condition: Path = /error
    • Action: Return a fixed HTTP response — status 404, body "Not found, custom error"
    • Priority: e.g. 5 (lower number = higher priority)
    Now visiting <alb-dns>/error immediately returns the custom 404 response without sending traffic to backend target groups.

Available condition types: host-header, HTTP method, source IP, query string, HTTP header.

Available action types: forward to target group(s), redirect to URL, or return a fixed response.

64Network Load Balancer (NLB)

NLB is a Layer 4 load balancer that handles high-speed TCP and UDP network traffic.

Exam trigger words: When a question mentions "UDP", "TCP", "extreme/ultra performance — millions of requests per second", "ultra-low latency (milliseconds)", or "static IP address per AZ" → choose Network Load Balancer.

Key Features

  • Ultra-high performance: handles millions of requests per second with ultra-low latency (in milliseconds).
  • Provides one static IP address per Availability Zone — you can also assign an Elastic IP per AZ for a fixed public IP.

Target Groups Can Contain:

  • EC2 instances
  • Private IP addresses (pointing to your on-premises servers)
  • An Application Load Balancer (NLB in front of ALB gives you static IP addresses combined with ALB's smart Layer 7 HTTP routing rules!)

Health checks on NLB target groups support 3 protocols: TCP, HTTP, and HTTPS.

65Network Load Balancer — Hands-On

  1. Create an NLB (DemoNLB) — internet-facing, IPv4, across all AZs. Each AZ gets a fixed static IPv4 address.
  2. Attach a security group (demo-sg-nlb) — allow HTTP (port 80) from anywhere.
  3. Configure Listener: TCP on port 80 → forward to target group.
  4. Create target group (demo-tg-nlb) — TCP on port 80, health check protocol = HTTP, and register the 2 EC2 instances.
Troubleshooting note: After creating the NLB, target instances appeared "unhealthy". Reason: the EC2 security group only allowed traffic from the ALB's security group. Fix: add an inbound rule allowing HTTP traffic from the NLB's security group ID. After that, health checks passed and load balancing worked cleanly.

Cleanup: Delete the NLB and associated resources when finished to avoid unnecessary cloud charges.

66Gateway Load Balancer (GWLB)

GWLB is used to deploy, scale, and manage a fleet of third-party network virtual appliances in AWS — such as firewalls, intrusion detection and prevention systems (IDPS), and deep packet inspection tools.

Operates at Layer 3 (Network IP packet layer) — lower than ALB (L7) or NLB (L4). It performs two major roles in one service:

  • Transparent network gateway: Acts as a single entry and exit point for all network traffic entering your VPC.
  • Load balancer: Distributes network traffic across a target group of virtual security appliances.
GWLB routes all incoming VPC network traffic through security inspection appliances first. Approved traffic continues to your app; harmful traffic is dropped.

Target Groups Can Contain:

  • EC2 instances (registered by instance ID)
  • Private IP addresses
Exam tip: GWLB uses the GENEVE protocol on port 6081. When an exam question mentions GENEVE protocol or port 6081, choose Gateway Load Balancer.

67Sticky Sessions (Session Affinity)

Normally, an ELB distributes each web request evenly across backend servers. With sticky sessions, once a user connects to a specific server, all their subsequent requests are routed back to that same server. This prevents losing session state (e.g. login credentials or shopping cart items).

Supported on: CLB, ALB, and NLB. Works using a browser cookie with a defined expiration time.

🛒 Analogy: Like going to a supermarket billing counter. Instead of jumping to a different cashier for every item in your shopping basket, you stick with the same cashier until your billing is complete.
Trade-off: Sticky sessions can cause an uneven load distribution if some users are much more active than others on a single server.

Three Types of Cookies

TypeGenerated ByCookie NameNotes
Application-based cookieYour application codeCustom name (per target group)Cannot use reserved names: AWSALB, AWSALBAPP, AWSALBTG
Application cookie (LB-generated)The ALB itselfAWSALBAPPAutomated application cookie
Duration-based cookieThe load balancerAWSALB (ALB) / AWSELB (CLB)Expiration period controlled by load balancer

Hands-On Steps

  1. Navigate to Target Group → Actions → Edit attributes → Stickiness.
  2. Enable stickiness, select cookie type (Load balancer generated or Application-based).
  3. Set expiration duration (range: 1 second to 7 days; default: 1 day).
  4. Save settings → refresh the ALB web link repeatedly → the exact same EC2 instance continues answering (verified via browser inspect tools → Network tab → Cookies).

68Cross-Zone Load Balancing

When you have an uneven number of EC2 instances across Availability Zones (AZs), does each load balancer node send traffic only to local instances in its own AZ, or spread traffic evenly across all instances in all AZs?

Uneven setup: AZ1 has 2 instances, AZ2 has 8 instances. Cross-zone balancing determines whether traffic stays within each local AZ or distributes across all 10 instances equally.
SettingBehavior
Cross-zone ONEach LB node distributes traffic evenly across all registered instances in all AZs (each of the 10 instances gets 10% of total traffic).
Cross-zone OFFEach LB node sends traffic only to instances in its own AZ. (Instances in AZ1 receive 25% traffic each, while instances in AZ2 receive only 6.25% traffic each).

Default Settings per Load Balancer Type

Load BalancerDefault SettingData Transfer Fees?
ALBAlways ONNo extra charge
NLB / GWLBOFFYes, inter-AZ data transfer fees apply if enabled
CLBOFFNo extra charge if enabled
For ALB, you can customize cross-zone load balancing at the target group level.

69-70SSL/TLS Certificates

SSL (Secure Sockets Layer) encrypts data in transit over the internet. TLS (Transport Layer Security) is the modern, secure version of SSL. People often say "SSL" out of habit, but AWS uses modern TLS.

Public SSL certificates are issued by trusted Certificate Authorities (CAs) like DigiCert, Let's Encrypt, or AWS Certificate Manager (ACM). Certificates expire and must be renewed regularly.

SSL Termination: Client-to-LB traffic is encrypted (HTTPS); LB-to-EC2 traffic can travel as plain HTTP over the secure private VPC network.
  • Load balancers use an X.509 certificate, managed seamlessly via AWS Certificate Manager (ACM).
  • An HTTPS listener requires a default certificate, plus an optional list of additional certificates for multi-domain support.

SNI — Server Name Indication

Problem it solves: How do you host multiple SSL certificates on a single load balancer so it can serve multiple different website domains?

How it works: The client specifies which website domain (hostname) it wants to reach during the initial SSL handshake. The load balancer reads this and selects the matching SSL certificate.

SNI works on modern load balancers: ALB, NLB, and CloudFront. It does NOT work on Classic Load Balancer.
SNI enables a single ALB to serve the correct SSL certificate and route to the correct target group based on the domain requested by the client.

SSL Support Summary

Load BalancerMultiple SSL Certificates Support?
CLBOnly 1 cert (requires multiple CLBs for multiple domains)
ALBYes — supports multiple listeners, certs, and SNI
NLBYes — supports multiple listeners, certs, and SNI

71Connection Draining

Also known as Deregistration Delay on ALB/NLB. Gives active, in-flight requests time to complete before an EC2 instance is fully taken out of service (deregistered or marked unhealthy).

A draining instance completes existing active requests; new users are routed exclusively to remaining healthy instances.
  • Active connections on draining instances are given time to finish processing.
  • New incoming connections are directed exclusively to healthy instances.
  • Configurable delay range: 1 to 3,600 seconds (default: 300 seconds / 5 minutes).
  • Set delay to 0 to disable connection draining completely.
Your Traffic PatternRecommended Draining Delay
Short requests (< 1 sec)Low (e.g. 30 seconds) — instances are deregistered quickly.
Long requests (file uploads, active sessions)High — gives active uploads time to complete safely.

72Auto Scaling Groups (ASG) Overview

An Auto Scaling Group (ASG) automatically adds (scales out) or removes (scales in) EC2 instances to match changing user traffic demand seamlessly.

Core Capacity Settings

  • Minimum Capacity: Fewest instances allowed in the group.
  • Desired Capacity: Target number of instances running right now.
  • Maximum Capacity: Most instances allowed in the group.

ASG Key Capabilities

  • Automatically registers newly launched instances with a linked load balancer.
  • Automatically terminates unhealthy instances and replaces them with fresh ones.
  • ASG service is completely FREE — you pay only for the underlying EC2 instances it provisions.
ELB + ASG Architecture: ELB distributes web traffic and monitors health; ASG replaces unhealthy servers and adjusts server count up or down.

Launch Template

A blueprint defining how ASG provisions new EC2 instances: AMI ID, instance type, user data startup script, EBS storage volumes, security groups, SSH key pairs, IAM roles, and subnet configurations.

CloudWatch Alarms + ASG

A CloudWatch alarm (e.g. "average CPU utilization exceeds 70%") triggers an automated scaling policy in your ASG:

  • Scale-out policy: Increases instance count when traffic surges.
  • Scale-in policy: Decreases instance count when traffic subsides to save costs.

73Auto Scaling Groups — Hands-On

  1. Clean up existing EC2 instances.
  2. Create a Launch Template (my demo template) — Amazon Linux 2, t2.micro, security group allowing HTTP, user data script.
  3. Create the ASG (Demo ASG) using the launch template.
  4. Select VPC and multiple Availability Zones.
  5. Attach the ASG to the existing ALB Target Group (demo-tg-alb).
  6. Enable both EC2 health checks and ELB health checks.
  7. Set initial capacity: Desired = Min = Max = 1.

Verification & Behavior

  • Check the Activity tab — records "Launching a new EC2 instance" as ASG scales from 0 to 1 instance.
  • Instance registers in the Target Group — initially "unhealthy" during bootstrapping (startup script execution), then becomes "healthy" once ready.
  • Refreshing the ALB DNS returns "Hello World" — confirming traffic is being served through the load balancer cleanly.
Troubleshooting tip: If ASG instances continually fail health checks and get terminated/replaced in an endless loop, check: (1) security group configuration, or (2) broken user-data startup scripts.

Manual Scaling Test

  • Edit ASG: set Desired = 2 (and raise Max) → a 2nd instance launches and joins the target group.
  • Edit ASG: set Desired = 1 → ASG terminates and deregisters 1 instance, returning capacity to 1.

74-75Auto Scaling Groups — Scaling Policies

Types of Scaling Policies

Policy TypeHow It Works
Dynamic — Target TrackingSimplest policy. Pick a metric (e.g. average CPU utilization) and target value (e.g. 40%). ASG automatically scales out/in to maintain that target metric.
Dynamic — Step ScalingTriggers multi-step responses based on CloudWatch alarm thresholds (e.g. CPU > 50% → add 1 instance; CPU > 80% → add 3 instances).
Dynamic — Simple ScalingOne alarm triggers one fixed action (e.g. add 2 instances).
Scheduled ScalingFor predictable traffic patterns (e.g. "raise minimum capacity to 10 every Friday at 5 PM").
Predictive ScalingUses Machine Learning to analyze historical traffic patterns and scale capacity ahead of expected demand surges.

Good Metrics for Auto Scaling

  • CPU Utilization: Most common general-purpose metric.
  • RequestCountPerTarget: Application-specific (e.g. keep requests per server at ~1,000).
  • Average Network In/Out: For bandwidth-heavy applications (video uploads/downloads).
  • Custom CloudWatch Metrics: Custom metrics exported directly from your app code.

Scaling Cooldown

After scaling out or scaling in, the ASG enters a cooldown period (default: 300 seconds / 5 minutes). During cooldown, ASG blocks additional scaling actions, giving metrics time to stabilize.

Optimization tip: Use custom AMIs with pre-installed software so instances start faster. This permits shorter cooldown periods and faster auto-scaling responses.

Hands-On: Target Tracking Demo

  1. Create a Target Tracking policy: metric = Average CPU Utilization, target = 40%.
  2. Set ASG max capacity higher than min (e.g. min=1, max=3) to allow room for scaling.
  3. SSH into instance via EC2 Instance Connect, install the stress tool, run stress -c 4 to push CPU utilization to 100%.
  4. Observe CloudWatch Alarms: two alarms auto-created — AlarmHigh (CPU > 40% → scale out) and AlarmLow (CPU < ~28% → scale in).
  5. When AlarmHigh triggers, ASG Activity log records new instances launching (1 → 2 → 3).
  6. Reboot stressed instance to restore normal CPU → AlarmLow triggers after ~15 minutes → ASG scales capacity back down (3 → 2 → 1).
Remember to delete the test scaling policy after completing hands-on verification.

76Auto Scaling Groups — Instance Refresh

Instance Refresh updates an entire ASG to a new launch template (e.g. after updating an AMI ID) with zero application downtime.

How It Works

  1. Update your Launch Template to a new version.
  2. Click Start Instance Refresh.
  3. Set a Minimum Healthy Percentage (e.g. 60%) to ensure sufficient active capacity throughout the update.
  4. ASG gradually terminates old instances and provisions new instances running the updated template.
  5. Optionally configure a warm-up time — period to wait before marking a new instance as ready to serve traffic.
Over time, every instance running the old launch template gets replaced — with no downtime, since the minimum healthy percentage ensures enough capacity stays up throughout.

  • ASG Scaling Cooldown: Default 300s.
  • GWLB Protocol: GENEVE on port 6081.
  • Cross-Zone Balancing Defaults: ALB = ON (free), NLB/GWLB = OFF (paid cross-AZ data), CLB = OFF (free).

Mental Model Recap

  • Vertical scaling = Bigger server. Horizontal scaling = More servers. High Availability = Multi-AZ deployment.
  • ELB = Front-door entry point + health checks + traffic distribution across EC2 instances.
  • ASG = Automatically maintains correct server count and replaces failed instances using CloudWatch alarms.
  • ELB + ASG combined = Classic AWS architecture for scalable, highly available web applications.
