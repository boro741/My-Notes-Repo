58High Availability and Scalability

Scalability = your system can handle more load by adapting. Two types:

  • Vertical scaling — make one instance bigger (scale up/down)
  • Horizontal scaling (elasticity) — add more instances (scale out/in)
🏢 Call center analogy:
• Vertical scaling = replacing a junior operator (5 calls/min) with a senior operator (10 calls/min). Same person, better/bigger.
• Horizontal scaling = hiring more operators (2, 3, 6...) instead of upgrading one. More people sharing the work.
• High availability = having operators in two different buildings (New York + San Francisco) so if one building loses power, the other keeps working.
ConceptMeaningTypical use case
Vertical scalingBigger instance (e.g. t2.micro → t2.large)Non-distributed systems like databases (RDS, ElastiCache). Has a hardware limit.
Horizontal scalingMore instances (scale out/in)Distributed / modern web apps. Easy in the cloud (just launch more EC2s).
High Availability (HA)Run across ≥ 2 Availability Zones (data centers)Survive the loss of one data center.
Exam tip: HA can be passive (e.g. RDS Multi-AZ standby, only takes over on failure) or active (e.g. horizontal scaling, all instances working at the same time). Don't assume HA always means "active."

EC2 size range: smallest = t2.nano (0.5 GB RAM, 1 vCPU) → biggest = u-12tb1.metal (12.3 TB RAM, 450 vCPUs).

59Elastic Load Balancing (ELB) Overview

A load balancer is a server (or a group of servers) that spreads incoming traffic across multiple backend EC2 instances. Users only ever talk to one address — the load balancer — and never know which actual EC2 instance answered them.

Each user connects to one endpoint (the load balancer). Each request is spread across different backend EC2 instances.

Why use a load balancer?

  • Single point of access (one DNS name for your app)
  • Seamlessly handles failure of downstream instances (via health checks)
  • Provides SSL termination (HTTPS)
  • Enforces stickiness with cookies
  • High availability across zones
  • Separates public traffic from private traffic

ELB is a managed service — AWS handles upgrades, maintenance, and HA for you. It's cheaper and easier than running/managing your own load balancer, and integrates with EC2, ASG, ECS, ACM, CloudWatch, Route 53, WAF, Global Accelerator, and more.

Health Checks

The load balancer checks a port and a route (e.g. HTTP:4567/health). If the instance doesn't respond with 200 OK, it's marked unhealthy and traffic stops going to it.

The 4 Types of AWS Load Balancers

Load BalancerSinceLayerProtocolsStatus
Classic Load Balancer (CLB)20094 & 7HTTP, HTTPS, TCP, SSLDeprecated
Application Load Balancer (ALB)20167HTTP, HTTPS, WebSocketRecommended
Network Load Balancer (NLB)20174TCP, TLS, UDPRecommended
Gateway Load Balancer (GWLB)20203IPNewest

Load balancers can be internal (private) or external / internet-facing (public).

Security Groups Setup (important pattern!)

  • Load Balancer's Security Group: allow HTTP(80)/HTTPS(443) from 0.0.0.0/0 (anywhere)
  • EC2 Instance's Security Group: allow HTTP(80) traffic only from the Load Balancer's Security Group (not from an IP range!)
Exam tip: This is a very common exam pattern — EC2 instances should only accept traffic that comes from the ELB, referenced by security group, not by CIDR range.

60Note: About the Classic Load Balancer (CLB)

The Classic Load Balancer is deprecated and being removed from the AWS Console. It's also removed from the exam, so this course (and these notes) skip its hands-on and deep detail.

61Application Load Balancer (ALB)

ALB is a Layer 7 (HTTP/HTTPS only) load balancer. It routes traffic to multiple applications, grouped into target groups.

Key Features

  • Load balance to multiple applications on the same EC2 instance (via containers/ECS)
  • Supports HTTP/2 and WebSockets
  • Supports redirects (e.g. HTTP → HTTPS)
  • Supports routing rules:
    • Path-based: example.com/users vs example.com/posts
    • Host-based: one.example.com vs other.example.com
    • Query string / header based: e.g. ?platform=mobile vs ?platform=desktop

ALB is great for microservices and container-based apps (dynamic port mapping with ECS). Unlike CLB (1 load balancer per app), a single ALB can front many applications.

One ALB routes /user requests to one microservice and /search requests to a completely different microservice.

Target Groups can be:

  • EC2 instances (can be managed by an Auto Scaling Group)
  • ECS tasks
  • Lambda functions (yes — serverless!)
  • Private IP addresses (on-premises servers)

Health checks happen at the target group level, so an ALB can front a mix of AWS EC2 instances and on-premises servers in different target groups.

Good to know

  • ALB gives you a fixed DNS hostname (not an IP)
  • Your app never sees the client's real IP directly — it's in the X-Forwarded-For header
  • X-Forwarded-Port and X-Forwarded-Proto tell you the port and protocol used
  • The load balancer performs connection termination: client → LB (public IP), then LB → EC2 (private IP)

62-63Application Load Balancer — Hands-On

Part 1: Basic setup

  1. Launch 2 EC2 instances (Amazon Linux 2, t2.micro, no key pair needed — use EC2 Instance Connect) with a user-data script that serves "Hello World" via HTTP
  2. Confirm each instance individually returns "Hello World" via its public IP
  3. Create an ALB (DemoALB) — internet-facing, IPv4, deployed across all AZs
  4. Create a new security group for the ALB (demo-sg-load-balancer) allowing HTTP from anywhere
  5. Create a target group (demo-tg-alb) — protocol HTTP, port 80 — and register both EC2 instances
  6. Link the target group to the ALB's listener on port 80
  7. Once ALB is active, use its DNS name — refreshing shows the response alternating between both instances = load balancing works ✅
Health check proof: Stop one EC2 instance → it becomes "unhealthy" in the target group within ~30s → ALB only responds from the healthy instance. Start it again → after health checks pass, it's back in rotation.

Part 2: Security tightening + routing rules

  • Restrict direct EC2 access: edit the EC2 security group's inbound HTTP rule — remove "anywhere," instead allow traffic only from the ALB's security group. After this, hitting the EC2 public IP directly times out, but the ALB still works fine.
  • Listener Rules: Add a custom rule on the ALB listener:
    • Condition: Path = /error
    • Action: Return a fixed response — status 404, body "Not found, custom error"
    • Priority: e.g. 5 (lower number = higher priority; default rule has lowest priority)
    Now visiting <alb-dns>/error returns the custom 404 instead of hitting a target group.

Other condition types available: host-header, HTTP request method, source IP, query string, HTTP header.

Other action types available: forward to target group(s), redirect to a URL, or return a fixed response.

64Network Load Balancer (NLB)

NLB is a Layer 4 load balancer — handles TCP and UDP traffic.

Exam trigger words: "UDP", "TCP", "extreme/ultra performance — millions of requests/sec, low latency", or "static IP" → think Network Load Balancer.

Key Features

  • Extremely high performance: millions of requests/sec, ultra-low latency
  • One static IP per Availability Zone — you can also assign an Elastic IP per AZ

Target Groups can be:

  • EC2 instances
  • IP addresses (must be private — can point to your own on-prem data center servers)
  • An Application Load Balancer (!) — NLB in front of ALB gives you fixed IPs and ALB's smart HTTP routing rules together

Health checks on NLB target groups support 3 protocols: TCP, HTTP, HTTPS.

65Network Load Balancer — Hands-On

  1. Create NLB (DemoNLB) — internet-facing, IPv4, across all AZs. Each AZ gets a fixed IPv4 (or you can use an Elastic IP)
  2. Attach a security group (demo-sg-nlb) — allow HTTP (port 80) from anywhere
  3. Listener: TCP on port 80 → forward to target group
  4. Create target group (demo-tg-nlb) — TCP on port 80, health check protocol = HTTP (since our app is HTTP), register the 2 EC2 instances
Gotcha encountered: After creating the NLB, targets showed "unhealthy." Reason: the EC2 security group only allowed traffic from the ALB's security group, not the NLB's. Fix: add an inbound rule allowing HTTP from the NLB's security group too. After that, health checks passed and traffic load-balanced correctly between both instances.

Cleanup: Delete the NLB (and optionally its target group/security group) when done, to avoid ongoing costs.

66Gateway Load Balancer (GWLB)

Used to deploy, scale, and manage a fleet of third-party network virtual appliances in AWS — e.g. firewalls, intrusion detection/prevention systems (IDPS), deep packet inspection tools.

Operates at Layer 3 (network layer, IP packets) — lower than ALB (L7) or NLB (L4). It has two jobs in one:

  • Transparent network gateway — single entry/exit point for all traffic in the VPC
  • Load balancer — distributes that traffic across a target group of virtual appliances
GWLB routes all VPC traffic through inspection appliances first (via modified route tables). Accepted traffic continues to the app; rejected traffic is dropped.

Target Groups can be:

  • EC2 instances (registered by instance ID)
  • IP addresses (must be private)
Exam tip: GWLB uses the GENEVE protocol on port 6081. If you see that mentioned, think Gateway Load Balancer. No deep hands-on needed for the exam — just understand the diagram above.

67Sticky Sessions (Session Affinity)

Normally, an ELB spreads every request across all backend instances. With sticky sessions, once a client is routed to an instance, all of that client's future requests go back to the same instance — useful so users don't lose session data (e.g. login state).

Supported on: CLB, ALB, and NLB. Works via a cookie with an expiration date — once it expires, the client may be sent to a different instance.

Trade-off: Sticky sessions can cause an imbalanced load if some users are much "stickier"/more active than others.

Two types of cookies

TypeGenerated byCookie nameNotes
Application-based cookieYour application (custom)Custom name (per target group)Cannot use reserved names: AWSALB, AWSALBAPP, AWSALBTG
Application cookie (LB-generated)The ALB itselfAWSALBAPP—
Duration-based cookieThe load balancerAWSALB (ALB) / AWSELB (CLB)Expiry set by the load balancer

Hands-On steps

  1. Go to Target Group → Actions → Edit attributes → Stickiness
  2. Turn stickiness ON, choose type: Load balancer generated cookie or Application-based cookie (needs a custom cookie name)
  3. Set duration (1 second – 7 days); default used: 1 day
  4. Save → refresh the ALB URL repeatedly → same instance keeps responding (verified via browser dev tools → Network tab → cookies)

68Cross-Zone Load Balancing

Question: when you have an uneven number of EC2 instances across AZs, does each load balancer node send traffic only to instances in its own AZ, or spread it across all AZs?

Uneven setup: AZ1 has 2 instances, AZ2 has 8 instances. Cross-zone balancing decides whether traffic stays within each AZ or spreads across all 10 instances.
SettingBehavior
Cross-zone ONEach LB node distributes evenly across all registered instances in all AZs (e.g. each of the 10 instances gets 10% of total traffic)
Cross-zone OFFEach LB node only sends to instances in its own AZ (so with an uneven split, instances in the smaller AZ get more traffic each — e.g. 25% per instance vs a lot less in the busier AZ)

Defaults per Load Balancer type

Load BalancerDefaultCharges for cross-AZ data if enabled?
ALBAlways ON (can't fully disable at LB level, but can override per target group)No charge
NLB / GWLBOFFYes, you pay for inter-AZ data transfer
CLBOFFNo charge even if enabled
For ALB, you can override cross-zone balancing per target group (inherit / force on / force off).

69-70SSL/TLS Certificates

SSL (Secure Sockets Layer) encrypts data in transit ("in-flight encryption"). TLS (Transport Layer Security) is the newer, actually-used version — but people (including the instructor) still often say "SSL" out of habit.

Public certificates are issued by Certificate Authorities (CAs) like Comodo, Symantec, GoDaddy, GlobalSign, DigiCert, Let's Encrypt. They expire and must be renewed.

SSL/TLS termination: client-to-LB is encrypted (HTTPS); LB-to-EC2 can be plain HTTP since it stays inside the private VPC network.
  • Load balancer uses an X.509 certificate, managed via ACM (AWS Certificate Manager) — you can also upload your own
  • An HTTPS listener needs a default certificate, plus an optional list of extra certs for multiple domains

SNI — Server Name Indication

Problem it solves: how do you load multiple SSL certs on one server so it can serve multiple websites?

How: the client tells the server which hostname it wants during the initial SSL handshake, so the server knows which certificate to load.

SNI only works on newer load balancers: ALB, NLB, and CloudFront. It does NOT work on the Classic Load Balancer.
SNI lets one ALB use the right SSL certificate and route to the right target group, based on which hostname the client asked for.

SSL support summary

Load BalancerMultiple SSL certs?
CLBOnly 1 cert — need multiple CLBs for multiple certs/hostnames
ALBYes — multiple listeners, multiple certs, uses SNI
NLBYes — multiple listeners, multiple certs, uses SNI

Hands-On

  • ALB: Add listener → HTTPS, port 443 → forward to target group → set security policy → attach certificate from ACM (or IAM, or import directly)
  • NLB: Add listener → TLS → forward to target group → security policy → certificate from ACM/IAM/import → optional ALPN (Application Layer Protocol Negotiation) setting

71Connection Draining

Also called Deregistration Delay on ALB/NLB (only called "Connection Draining" on CLB). Gives in-flight requests time to complete before an instance is fully taken out of service (deregistered / marked unhealthy).

Draining instance finishes existing requests; new users are routed only to healthy instances.
  • Existing connections to the draining instance are given time to finish
  • New connections are routed to other healthy instances only
  • Configurable: 1 – 3,600 seconds (default: 300 seconds / 5 min)
  • Set to 0 to disable draining completely
Your traffic patternRecommended draining time
Short requests (< 1 sec)Low, e.g. 30 seconds — instance can be removed quickly
Long requests (uploads, long-lived connections)High — but instance takes longer to fully go away

72Auto Scaling Groups (ASG) Overview

An ASG automatically adds (scale out) or removes (scale in) EC2 instances to match changing load.

Core capacity settings

  • Minimum capacity — fewest instances allowed
  • Desired capacity — the target number right now
  • Maximum capacity — most instances allowed

ASG "superpowers"

  • Auto-registers new instances with a linked load balancer
  • Auto-terminates unhealthy instances and replaces them with new ones
  • ASG itself is free — you only pay for the underlying EC2 instances (and other resources) it creates
ASG + ELB combo: ELB spreads traffic and reports health; ASG uses that health info to replace bad instances and scale count up/down.

Launch Template

Defines how new EC2 instances in the ASG should be created: AMI, instance type, user data script, EBS volumes, security groups, SSH key pair, IAM role, network/subnet info, load balancer info.

Note: "Launch configurations" are the old/deprecated way — use Launch Templates now.

CloudWatch Alarms + ASG

A CloudWatch alarm (e.g. "average CPU too high") can trigger a scaling action in the ASG — this is the "auto" in Auto Scaling Group. Based on the alarm, you define:

  • Scale-out policy — increase instance count
  • Scale-in policy — decrease instance count

73Auto Scaling Groups — Hands-On

  1. Terminate any leftover EC2 instances first (start clean)
  2. Create a Launch Template (my demo template) — Amazon Linux 2, t2.micro, key pair, existing security group, same user-data script used before
  3. Create the ASG (Demo ASG) using that launch template
  4. Choose VPC + multiple AZs, AZ distribution = "balanced best effort"
  5. Attach to the existing ALB target group (demo-tg-alb) from earlier lectures
  6. Enable both EC2 health checks and load balancer health checks
  7. Set desired = min = max = 1 initially (no auto scaling policy yet)

What happens after creation

  • Check the Activity tab — shows "Launching a new EC2 instance" as the ASG brings capacity from 0 → 1
  • New instance registers into the target group — initially "unhealthy" while bootstrapping, then "healthy" once ready
  • Refreshing the ALB now returns "Hello World" — proof the ASG-created instance is serving traffic through the load balancer
Troubleshooting tip: If instances keep failing health checks and get terminated/replaced in a loop, the usual causes are: (1) a security group misconfiguration, or (2) a broken EC2 user-data script.

Manual scaling test

  • Edit ASG: desired = 2 (and raise max to allow it) → a 2nd instance launches and joins the target group
  • Edit ASG: desired = 1 again → ASG picks one instance to terminate and deregister, back down to 1

74-75Auto Scaling Groups — Scaling Policies

Types of scaling policies

TypeHow it works
Dynamic — Target TrackingSimplest. Pick a metric (e.g. CPU utilization) + target value (e.g. 40%). ASG automatically scales out/in to keep the metric near that target. Creates CloudWatch alarms for you automatically.
Dynamic — Step ScalingYou define a CloudWatch alarm + different "steps" of response depending on how far over the threshold the alarm is (e.g. way over → add 10 units, slightly over → add 1 unit).
Dynamic — Simple ScalingOne CloudWatch alarm → one fixed action (e.g. add 2 units, or add 10% of group size).
Scheduled ScalingFor known, predictable patterns — e.g. "every Friday at 5 PM, raise min capacity to 10."
Predictive ScalingMachine-learning based — continuously forecasts load from historical data and schedules scaling ahead of time. Good for cyclical/recurring traffic patterns.

Good metrics to scale on

  • CPU Utilization — most common, general-purpose metric
  • RequestCountPerTarget — application-specific (e.g. "each instance handles 1,000 requests optimally")
  • Average Network In/Out — for network-bound apps (heavy uploads/downloads)
  • Custom CloudWatch metric — anything specific to your app

Scaling Cooldown

After any scale-out/scale-in activity, the ASG enters a cooldown period (default 300 seconds / 5 min) during which it won't launch or terminate more instances — this lets metrics stabilize after the change.

Tip: Use a pre-baked/ready-to-use AMI so new instances are ready to serve traffic faster — this lets you use a shorter cooldown and get more responsive scaling. Also enable detailed monitoring (1-minute metric granularity) for faster reactions.

Hands-On: Target Tracking demo

  1. Create a Target Tracking policy: metric = Average CPU Utilization, target = 40%
  2. Set ASG max capacity higher than min (e.g. min=1, max=3) so it has room to scale
  3. SSH into an instance via EC2 Instance Connect, install the stress tool, run stress -c 4 to push CPU to 100%
  4. Watch CloudWatch → Alarms: two alarms auto-created — AlarmHigh (CPU > 40% for 3 datapoints in 3 min → scale out) and AlarmLow (CPU < ~28% for 15 datapoints → scale in)
  5. Once AlarmHigh triggers, ASG activity log shows a new instance launching (1 → 2, then even 2 → 3 while CPU was still high)
  6. Reboot the stressed instance(s) to bring CPU back down → after ~15 minutes AlarmLow triggers → ASG scales back in (3 → 2 → 1), terminating instances one at a time
Remember to delete the scaling policy after testing to avoid leaving it running.

76Auto Scaling Groups — Instance Refresh

Instance Refresh lets you update an entire ASG to use a new launch template (e.g. after updating the underlying AMI) — without manually terminating instances one by one and waiting.

How it works

  1. Update your Launch Template (e.g. new AMI version)
  2. Call Start Instance Refresh
  3. Set a minimum healthy percentage (e.g. 60%) — controls how many instances can be taken down at once
  4. ASG terminates old instances gradually and launches new ones (with the new template) to replace them
  5. Optionally set a warm-up time — how long to wait before assuming a new instance is ready to serve traffic
Over time, every instance running the old launch template gets replaced — with no downtime, since the minimum healthy percentage ensures enough capacity stays up throughout.

Load Balancer decision guide

If you need...Use
HTTP/HTTPS, path/host-based routing, microservices, containers, Lambda targetsALB
TCP/UDP, extreme performance, static IP per AZNLB
Firewall/IDS inspection of all network trafficGWLB
Legacy / old exam questions onlyCLB (deprecated, avoid)

Key numbers to remember

  • Security groups: LB allows 80/443 from 0.0.0.0/0; EC2 allows 80 only from LB's security group
  • Sticky session cookie names: AWSALB (duration), AWSALBAPP (app cookie, LB-generated), custom name for fully custom app cookie
  • Connection Draining / Deregistration Delay: default 300s, range 1–3600s, 0 = disabled
  • ASG scaling cooldown: default 300s
  • GWLB protocol: GENEVE on port 6081
  • Cross-zone balancing default: ALB = ON (free), NLB/GWLB = OFF (costs $ if turned on), CLB = OFF (free if turned on)

Mental model recap

  • Vertical scaling = bigger instance. Horizontal scaling = more instances. High Availability = spread across multiple AZs.
  • ELB = single entry point + health checks + traffic spreading across EC2s.
  • ASG = automatically keeps the right number of healthy EC2 instances running, and can react to CloudWatch alarms to scale in/out.
  • ELB + ASG together = the classic AWS pattern for a scalable, highly available web application.
