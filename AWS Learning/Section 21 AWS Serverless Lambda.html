1 Serverless Introduction

Serverless doesn't mean there are no servers — it means you don't manage or provision them. Originally "serverless" meant Function-as-a-Service (Lambda), but it now covers anything remotely managed: databases, messaging, storage — as long as you never provision a server yourself.

A typical serverless reference architecture: static content from S3/CloudFront, auth via Cognito, a REST API through API Gateway invoking Lambda, which reads/writes DynamoDB — no servers provisioned anywhere.

Other serverless AWS building blocks already covered in this course: SQS, SNS, Kinesis Data Firehose, Aurora Serverless, Step Functions, and Fargate (the serverless flavor of ECS).

Pricing

  • Free tier: 1 million requests + 400,000 GB-seconds of compute time per month.
  • Pay per request (first 1M free, then $0.20 per extra 1M) + per duration in 1ms increments.
  • More RAM = fewer free seconds included, but also more CPU — it's usually still very cheap.

Languages & runtimes

Node.js, Python, Java, C# (.NET Core/PowerShell), Ruby natively; Rust/Go and others via a custom runtime API; and container images (must implement the Lambda Runtime API).

Exam point Even though Lambda supports some level of custom Docker images, running Docker workloads is generally preferred on ECS/Fargate over Lambda from an exam perspective.

RAM

Up to 10GB of RAM per function — and more RAM also improves CPU and network performance.

Classic patterns

  • Serverless thumbnail generation: S3 upload → event notification → Lambda generates a thumbnail → uploads it back to S3 + writes metadata to DynamoDB.
  • Serverless cron: an EventBridge scheduled rule triggers a Lambda function on a schedule (e.g. hourly) — no EC2 instance sitting idle between runs.

Hands-on basics

Create a function from a blueprint, give it an execution role (like an EC2 instance role, but for Lambda), test it with a sample JSON event, and view its logs directly in CloudWatch Logs. The role determines what the function can access — e.g. the basic execution role only allows writing to CloudWatch Logs.

3 Synchronous Invocations

Synchronous means the caller waits for the result — and must handle any errors itself (retry, backoff, etc.).

Synchronous invocation: the caller blocks until Lambda finishes and hands back a result — errors are the caller's responsibility.

Services that invoke Lambda synchronously: CLI/SDK, Application Load Balancer, API Gateway, CloudFront (Lambda@Edge), plus (not covered hands-on here) S3 Batch, Cognito, Step Functions, Lex, Alexa, Kinesis Data Firehose.

Good to know Testing a function from the console ("Test" button) or via aws lambda invoke in the CLI is itself a synchronous invocation — you wait right there for the response JSON.

4 Lambda & Application Load Balancer

To expose a Lambda function as an HTTP(S) endpoint without API Gateway, register it in an ALB target group (target type = Lambda function). The ALB converts the HTTP request into a JSON document for Lambda, and converts Lambda's JSON response back into HTTP.

The ALB translates the HTTP method, path, query string, headers, and body into a JSON event; the Lambda response (status code, headers, body) gets converted back into a real HTTP response.

  • The Lambda response must include statusCode, headers, body, and isBase64Encoded.
  • Set the Content-Type header (e.g. text/html) so the browser renders the body instead of downloading it.
  • Multi-value headers: an ALB target group setting that preserves repeated headers/query string keys as arrays instead of picking just one value.

The ALB is authorized to invoke the function via a resource-based policy automatically attached to the Lambda function (visible under Configuration → Permissions).

5 Asynchronous Invocations & DLQ

Services like S3, SNS, and EventBridge invoke Lambda asynchronously — events land in an internal event queue first.

Asynchronous invocations queue internally and retry automatically (immediately, then after 1 minute, then after 2 more) before optionally landing in a dead-letter queue.

Important Because of automatic retries, your function must be idempotent — processing the same event twice should produce the same result, since duplicate log entries and duplicate processing are expected behavior, not a bug.
  • Asynchronous invocation is used when the service has no other choice, or when you want to fire off many jobs in parallel without waiting on each individually.
  • Asynchronous services: S3 event notifications, SNS, EventBridge/CloudWatch Events (also CodeCommit, CodePipeline, CloudWatch Logs, SES, CloudFormation, Config, IoT — less central to this course).
  • A synchronous test invocation of a function set up for async processing always returns 202 whether it ultimately succeeds or fails — you can't tell from that response alone; check CloudWatch Logs or the DLQ.

Configure a DLQ (SQS or SNS) under the function's asynchronous invocation settings, along with the number of retry attempts (0, 1, or 2). The failed message includes the error cause and request ID for debugging.

6 Lambda & EventBridge

Two common patterns: a serverless cron/rate schedule (e.g. every hour, or every minute for testing) invoking a Lambda function, or a rule that reacts to a specific event pattern (e.g. a CodePipeline state change).

Hands-on: create an EventBridge Schedule (rate- or cron-based, one-time or recurring) with target = Lambda: Invoke. EventBridge automatically creates an execution role granting itself permission to invoke your function. The event passed to Lambda includes the schedule's source, account, region, and the triggering resource.

Don't forget Disable test schedules when you're done — an active 1-minute schedule will keep invoking your function forever.

7 Lambda & S3 Event Notifications

S3 events can go to SNS (for fan-out to multiple SQS queues), SQS (Lambda polls it), or directly invoke Lambda asynchronously.

Don't forget S3 event delivery is usually within seconds but can occasionally take longer. If two writes to the same object happen at the exact same instant, you may only get one notification instead of two — enable bucket versioning to avoid missing an event.

Hands-on: an S3 bucket's event notification (all object-create events) targets a Lambda function directly. S3 is granted invoke permission via a resource-based policy automatically added to the function. The event payload includes the bucket name, region, object key, size, and ETag — enough for the function to call GetObject and process the file.

8 Event Source Mapping

The third invocation category — for sources where Lambda must actively poll: Kinesis Data Streams, SQS/SQS FIFO, and DynamoDB Streams. Despite the polling, the actual function invocation is synchronous.

The Event Source Mapping is the piece that actively polls Kinesis/SQS/DynamoDB Streams, then synchronously invokes your Lambda function with a batch of records.

Streams (Kinesis, DynamoDB Streams)

  • One iterator per shard; items processed in order at the shard level. Choose to read new items, from the beginning, or from a timestamp.
  • Items are not removed from the stream after processing — other consumers can still read them.
  • Up to 10 parallel batch processors per shard — in-order processing is then guaranteed at the partition key level, not the whole shard.
  • On error, by default the entire batch is retried until it succeeds or expires — this can block the affected shard. Mitigate with: discard old events, limit retries, split the batch on errors, or send failures to a destination.

Queues (SQS, SQS FIFO)

  • Polled using long polling; batch size 1–10 messages.
  • Recommended: set the queue's visibility timeout to 6× the Lambda function's timeout.
  • DLQ for SQS-sourced failures is set on the SQS queue itself, not on Lambda — Lambda's own DLQ setting only applies to asynchronous invocations, and this is a synchronous one (or use a Lambda destination for failures instead).
  • Standard queue: no ordering guarantee, Lambda scales as fast as possible (+60 instances/min... actually +16 instances/min, up to 1,000 batches/sec). Occasionally the same message may be received twice even without an error.
  • FIFO queue: strict order per message group ID; Lambda scales up to the number of active message groups.
Exam point Kinesis/DynamoDB Streams scaling = 1 invocation per shard (or up to 10 parallel batches per shard). SQS Standard scales up fast (adds ~16 instances/min, up to 1,000 batches/sec concurrently). SQS FIFO scales to the number of active message groups.

10 Lambda Destinations

A newer (Nov 2019) alternative/complement to DLQs — send the result (success or failure) of processing somewhere, with richer targets than a DLQ alone.

DLQDestinations
CoversFailures onlyBoth success and failure
TargetsSQS, SNSSQS, SNS, Lambda, EventBridge
Applies toAsync invocationsAsync invocations (success/failure) and Event Source Mapping (discarded batches)

Destinations let you route the outcome of an async invocation (success or failure) to any of SQS, SNS, another Lambda function, or an EventBridge bus — richer than the DLQ's SQS/SNS-only, failure-only scope.

Hands-on: configure separate success and failure destinations (e.g. two SQS queues). The success message includes the full request context and response payload; the failure message includes the error cause, invoke count, the record that caused the failure, and a stack trace.

12 Environment Variables

Key-value string pairs that adjust function behavior without code changes. Lambda also injects its own system environment variables alongside yours. Can be encrypted with KMS (the Lambda service key, or your own CMK) for secrets.

Hands-on: reading os.getenv("ENVIRONMENT_NAME") and changing its value from dev to prod in the console changes the function's output without touching the code — demonstrating the whole point of environment variables.

13 Monitoring & X-Ray Tracing

  • Lambda execution logs go to CloudWatch Logs automatically (given the right IAM permission).
  • CloudWatch Metrics: invocations, duration, concurrent executions, error count, success rate, throttles, async delivery failures, and (for streams) iterator age — how far behind you are in reading a stream.
  • X-Ray: enable "Active Tracing" in configuration — runs the X-Ray daemon for you. You still need the X-Ray SDK in your code and the AWSXRayDaemonWriteAccess permission. Relevant env vars include AWS_XRAY_DAEMON_ADDRESS (where the daemon is).

Hands-on: enabling active tracing + attaching the S3-read permission lets you see, in the X-Ray service map, exactly which calls succeeded (green) and which failed (e.g. a 403 Access Denied on ListBuckets) — with full stack traces per request.

15 Lambda in a VPC

By default, Lambda runs in an AWS-owned VPC — it cannot reach resources in your own VPC (private RDS, ElastiCache, internal ALB, etc.) unless you explicitly attach it.

Attaching Lambda to a VPC gets it an ENI to reach private resources, but that same VPC attachment removes internet access unless you route through a NAT gateway/instance in a public subnet — or use a VPC endpoint for private access to AWS services like DynamoDB.

Important exam point Unlike EC2, deploying a Lambda function in a public subnet does NOT give it internet access or a public IP. To reach the internet, deploy it in a private subnet with a NAT gateway/instance in a public subnet.
  • Requires defining VPC ID, subnets, and a security group; the function needs the AWSLambdaVPCAccessExecutionRole to create the ENI.
  • CloudWatch Logs still work from inside a VPC with no NAT or endpoint needed.

Exam point Need a faster/more powerful CPU for a Lambda function? The only lever is increasing memory — there's no independent CPU setting.

Execution context reuse

Lambda keeps a temporary runtime environment ("execution context") alive between invocations when possible. Initialize database connections, HTTP/SDK clients, etc. outside the handler function so they're reused across warm invocations instead of reconnecting every single time.

Don't forget Code inside the handler runs on every invocation; code outside it only runs once per execution context (shown as "Init Duration" in logs) — put anything slow to set up (DB connections, SDK clients) outside the handler.

/tmp storage

Up to 10GB of ephemeral disk space at /tmp, persisted for the life of the execution context (so it can survive across warm invocations) but gone once the instance is destroyed. Useful for large temp files; for true persistence use S3. No built-in encryption for /tmp — you'd need to use KMS to encrypt data yourself before writing it there.

17 Lambda Layers

Layers let you (1) add custom runtimes (e.g. C++, Rust) and (2) — more commonly — externalize heavy dependencies so you don't have to repackage them every time your actual code changes.

Heavy, slow-changing dependencies live in shared layers; your small, frequently-changing app code references them — multiple functions can reuse the same layers.

Hands-on: adding an AWS-provided layer (e.g. AWSSDKPandas-Python313) gave a function access to the Pandas library without packaging it yourself.

18 File System Mounting (EFS)

A VPC-deployed Lambda function can mount an EFS file system (via an EFS Access Point) to a local directory at startup.

Don't forget Each concurrent Lambda instance opens its own EFS connection — watch out for hitting EFS connection limits or connection burst limits if many instances spin up at once.

19 Concurrency & Cold Starts

  • Reserved concurrency: a per-function cap on concurrent executions (default account-wide pool is 1,000, shared across all functions).
  • Going over the limit triggers a throttle: synchronous invocations get a 429 error immediately; asynchronous ones retry automatically, then go to the DLQ if still failing.
Important Without reserved concurrency set, one function hammering the shared 1,000-execution pool can throttle every other function in the account. Set reserved concurrency deliberately on important functions to protect them from noisy neighbors.

Cold starts & provisioned concurrency

The first request to a new function instance pays the "cold start" cost of loading code and running init logic; provisioned concurrency pre-warms instances so no request ever pays that cost.

  • Provisioned concurrency pre-allocates warm instances ahead of invocation — no cold start, lower latency. Manage it with Application Auto Scaling (schedule or target tracking).
  • Provisioned concurrency can only be applied to a published version or alias, not $LATEST.
  • VPC cold starts used to be a major concern but were dramatically improved by AWS in late 2019.

20 External Dependencies

  • Package dependencies alongside your code and zip them together: node_modules for Node.js (npm), pip target installs for Python, .jar files for Java.
  • Upload the zip directly if under 50MB; otherwise upload to S3 first and reference it from there.
  • Native libraries must be compiled on Amazon Linux to work.
  • The AWS SDK comes bundled with every Lambda runtime already — no need to package it yourself if that's all you need.

Hands-on: using CloudShell, npm install aws-xray-sdk populates node_modules, zip everything together, then deploy via the CLI (aws lambda create-function with a role ARN). Combined with S3 read permissions and X-Ray tracing enabled, this produced a fully working function whose calls (and their successes/failures) were visible in the X-Ray service map.

Cross-account deployment

To deploy the same Lambda code from Account 1's S3 bucket into Accounts 2 and 3: attach a bucket policy on Account 1's bucket allowing those accounts, and give each account's CloudFormation an execution role permitting Get/List on that bucket.

22 Lambda Container Images

Deploy Lambda as a container image (up to 10GB) from ECR — good for packing complex/large dependencies. The base image must implement the Lambda Runtime API; AWS provides base images for Python, Node.js, Java, .NET, Go, Ruby, or you can build your own.

  • Test locally with the Lambda Runtime Interface Emulator.
  • Gives a unified build/publish workflow — the same container tooling works whether the target is ECS or Lambda.

Best practices

  • Use AWS-provided base images (Amazon Linux 2, already cached by the Lambda service).
  • Use multi-stage builds — build in a large intermediate image, copy only the final artifacts into a small final image.
  • Order layers from stable → frequently changing (put things that rarely change earliest in the build).
  • Use a single ECR repository for functions sharing large layers, so ECR can dedupe them.

23 Versions & Aliases

Aliases point to versions and can even split traffic by weight between two versions (e.g. 90/10) for a canary-style rollout — you shift the weight over time instead of flipping a single pointer.

Hands-on: dev alias → $LATEST, test → v2, prod → v1; then editing prod to a weighted split (e.g. 50/50 between v1 and v2) causes invocations to alternate between the two versions.

24 Lambda & CodeDeploy

CodeDeploy automates traffic shifting between Lambda aliases (built on top of versions/aliases) — practiced later in the SAM framework section.

StrategyBehavior
LinearGrow traffic by a fixed % every N minutes until 100% (e.g. Linear10PercentEvery3Minutes)

Pre/post-traffic hooks (and CloudWatch alarms) can trigger an automatic rollback to the previous version if something looks wrong. Key AppSpec.yml fields: Name, Alias, CurrentVersion, TargetVersion.

25 Lambda Function URL

A dedicated, permanent HTTPS endpoint for a function — no API Gateway or ALB needed. Supports IPv4/IPv6, public internet access only (no private option), and CORS configuration.

  • Can be attached to a function alias or $LATEST — not to a specific published version.
  • AuthType NONE: public, unauthenticated access — controlled entirely by the function's resource-based policy (which must explicitly allow lambda:InvokeFunctionUrl for principal *).
  • AuthType AWS_IAM: caller must be authenticated via IAM. Same-account access needs either the identity-based or resource-based policy to allow it; cross-account access needs both.
  • Use reserved concurrency to throttle a publicly exposed function URL if needed.

Hands-on: publish a version, create an alias (e.g. dev), enable Function URL with AuthType NONE — the console auto-attaches the permissive resource policy — and the URL immediately serves the function's HTTP-shaped response.

26 Limits & Best Practices

Exam point "We need 30GB RAM" / "30 minutes of execution" / "a 3GB file to process" → all signal that Lambda is the wrong tool — think Fargate/ECS/EC2 instead.

Best practices

  • Do heavy/slow initialization (DB connections, SDK clients, dependency loading) outside the handler.
  • Use environment variables for anything that changes (connection strings, bucket names) — never hardcode; encrypt sensitive values with KMS.
  • Keep deployment packages minimal; use Lambda Layers for shared/reusable dependencies.
  • Never let a Lambda function recursively call itself — runaway cost and cascading failures.

✓ Cheat Sheet

Key facts to remember

  • Three invocation models: Synchronous (caller waits — CLI/SDK, ALB, API Gateway), Asynchronous (internal queue + 3 automatic retries, needs idempotency — S3, SNS, EventBridge), Event Source Mapping (Lambda polls — Kinesis, SQS, DynamoDB Streams; invocation itself is synchronous).
  • Async invocations support DLQ (SQS/SNS, failures only) or the newer Destinations (SQS/SNS/Lambda/EventBridge, success + failure).
  • Execution role = Lambda calling out; resource-based policy = something else calling Lambda.
  • More RAM = more (implicit) vCPU — the only lever for CPU performance; 1,792MB ≈ 1 full vCPU.
  • Initialize slow things (DB connections, SDK clients) outside the handler to reuse them across warm invocations.
  • Lambda in a public subnet still has no internet access — need a private subnet + NAT gateway/instance, or a VPC endpoint for private AWS service access.
  • Layers: externalize shared/heavy dependencies (up to 5 layers, 250MB total); immutable once created.
  • Reserved concurrency caps one function's usage from the shared account pool (default 1,000) to protect other functions; provisioned concurrency pre-warms instances to avoid cold starts.
  • Versions are immutable snapshots; aliases are mutable pointers to versions (never to other aliases) — used for stable endpoints and weighted canary rollouts.
  • Function URLs give a permanent public HTTPS endpoint per function/alias, secured via AuthType NONE (resource policy) or AWS_IAM (identity + resource policy, both needed cross-account).
  • Lambda@Edge (Node.js/Python, all 4 CloudFront hooks, up to 10s) vs CloudFront Functions (JS only, viewer hooks only, <1ms, millions of req/sec).
  • Hard limits: 15 min max execution, 10GB max RAM, 4KB env vars, 10GB /tmp, 50MB/250MB deployment package (zipped/unzipped).

Mental model

Lambda is code that only exists while it's running: you pay per invocation and per millisecond, and everything else in this section is really about answering how that code gets triggered (sync, async, or polling), how it reaches other things (IAM roles out, resource policies in, VPC networking for private resources), how it stays fast (RAM/CPU, warm execution contexts, layers, provisioned concurrency), and how you evolve it safely over time (versions, aliases, weighted rollouts, CodeDeploy). Once you can answer "who invokes this, how does it get permission, and how is this specific version reached," you understand Lambda end to end.
