1 Introduction to Messaging

Once you're running more than one application, they need to talk to each other. There are two patterns for that.

Synchronous: services call each other directly. Asynchronous/event-based: a middleware (queue, topic, or stream) sits between them, so neither side has to talk to the other directly.

Exam point Synchronous communication can be fragile — a sudden spike on one side (e.g. 1,000 videos to encode instead of 10) can overwhelm the other and cause outages. When traffic is spiky or unpredictable, decouple your applications so the middleware absorbs the load and each side scales independently.

Three decoupling tools, covered in this section:

  • SQS — a queue model
  • SNS — a pub/sub model
  • Kinesis — real-time streaming for big data

2 SQS Standard Queues Overview

SQS (Simple Queue Service) is AWS's oldest service (10+ years old) — a fully managed queue used to decouple applications. Whenever you see "application decoupling" on the exam, think SQS.

Producers send messages into the queue; consumers poll for messages, process them, and delete them — the queue is the buffer that decouples the two sides.

Key characteristics

PropertyValue
ThroughputUnlimited — as many messages/second as you want, unlimited queue size
Retention4 days by default, up to 14 days max — unprocessed messages are lost after that
Latency<10ms on publish and receive
Message sizeUp to 256 KB per message
DeliveryAt-least-once (possible duplicates)
OrderingBest-effort (can be out of order) — unless you use FIFO queues

Producers & consumers

  • Producers send messages via the SDK, using the SendMessage API.
  • Consumers can run on EC2, on-premises servers, or Lambda. They poll (ReceiveMessage, up to 10 messages at a time), process, then call DeleteMessage to remove it — otherwise other consumers could see it again.
  • Multiple consumers can process messages from the same queue in parallel for horizontal scaling.
Common exam architecture Auto Scale your consumer fleet on the ApproximateNumberOfMessages CloudWatch metric (queue length) — a CloudWatch alarm bumps your ASG's desired capacity as the queue backs up, so more EC2 instances appear to help drain it.

Decoupling application tiers

Classic use case: a video-processing app. Instead of one monolithic app handling both the upload request and the (slow) encoding, split it into a front-end tier (takes the request, drops a message in SQS) and a back-end tier (its own ASG, polls SQS, does the heavy processing, e.g. on GPU instances). Each tier scales independently, and SQS's unlimited throughput/capacity makes the whole thing robust.

Security

  • In-flight encryption via HTTPS API; at-rest encryption via KMS; client-side encryption if you implement it yourself.
  • IAM policies regulate the SQS API; SQS access policies (resource policies, like S3 bucket policies) handle cross-account access or letting other services (SNS, S3) write to your queue.

3 SQS Standard Queue — Hands On

  • Creating a queue: choose Standard or FIFO. Configure visibility timeout, delivery delay, wait time, retention period (up to 14 days), max message size (up to 256 KB).
  • Encryption: disabled, SSE-SQS (Amazon-managed key, like S3's SSE-S3), or SSE-KMS (choose a CMK, optionally set a data key reuse period to limit KMS API calls).
  • Access policy: define who can send/receive — just the queue owner, or specific accounts/users/roles — generates a JSON resource policy just like an S3 bucket policy.

In the console's Send and receive messages panel: sending a message makes it available; polling retrieves it (with metadata like message ID, receive count, size, and the body). If you poll again without deleting, the message reappears after its visibility timeout and the receive count increments — deleting it is what signals "processed" to SQS.

Other queue options: Purge (delete all messages — type "purge" to confirm; great for dev, not for prod), monitoring (queue depth, oldest message age — useful for scaling decisions), and dead-letter redrive status.

4 SQS Queue Access Policy

SQS access policies are JSON resource policies attached directly to a queue — similar in spirit to S3 bucket policies. Two common use cases:

  1. Cross-account access — e.g. an EC2 instance in Account B needs to poll a queue in Account A. Attach a policy on the queue in Account A allowing sqs:ReceiveMessage for principal 111122223333 (Account B).
  2. Allowing another AWS service to write — e.g. S3 event notifications need to send messages into an SQS queue. The policy must allow sqs:SendMessage from principal *, conditioned on the source ARN matching the specific bucket and the source account matching the bucket owner.
Don't forget Without the right access policy, attempting to save an S3 event notification pointing at an SQS queue fails with an error saying the destination configuration can't be validated — the queue simply hasn't granted S3 permission to write to it yet.
Exam point Both cross-account access to an SQS queue and letting AWS services (S3, SNS) publish into an SQS queue are done the same way: an SQS access policy.

5 Message Visibility Timeout

When a consumer polls and receives a message, that message becomes invisible to other consumers for the duration of the visibility timeout (default 30 seconds).

A received message hides from other consumers for the visibility timeout; if it isn't deleted before that window ends, it becomes visible again and could be picked up (and processed) a second time.

  • If a consumer needs more time to finish processing, it should call ChangeMessageVisibility to extend the timeout, rather than risk the message being picked up again.
Timeout settingRisk
Too high (e.g. hours)If the consumer crashes, the message won't reappear for a long time
Too low (e.g. seconds)Message may be read multiple times by different consumers before it's actually processed — duplicate processing

Configurable from 0 seconds up to 12 hours per queue.

6 Dead Letter Queues

If a consumer keeps failing to process a message, it keeps bouncing back into the queue after each visibility timeout — a failure loop. A Dead Letter Queue (DLQ) catches messages that exceed a maxReceiveCount threshold, moving them out of the main queue for later inspection.

Messages that repeatedly fail get moved to a DLQ for debugging; once the underlying issue is fixed, a redrive sends them back to the source queue for reprocessing.

  • A FIFO queue's DLQ must also be FIFO; a Standard queue's DLQ must also be Standard.
  • Set a long retention period on the DLQ (e.g. 14 days) so you have time to investigate before messages expire.
  • Redrive to source lets you send messages from the DLQ back into the original queue once you've fixed the consumer — reprocessing happens transparently.

Hands-on recap

Create a DLQ, then on the source queue enable "Dead-letter queue" pointing at it, with a Maximum receives value (e.g. 3). After a message is received that many times without being deleted, it moves to the DLQ. From the DLQ, Start DLQ redrive sends it back to the source queue.

7 Delay Queues

A delay queue hides new messages from consumers for a set period (up to 15 minutes) after they're sent.

  • Default delay is 0 seconds (immediately visible).
  • Set a default at the queue level, or override per-message using the DelaySeconds parameter on SendMessage.
Good to know Just know this feature exists for the exam — it's a simple setting, not a complex mechanism.

8 SQS Developer Concepts

Long polling

Instead of immediately returning empty when the queue has nothing, a consumer can wait for a message to arrive (1–20 seconds, 20 is preferred). This reduces the number of API calls (cheaper, less CPU) and reduces latency (message is delivered to the consumer as soon as it exists).

  • Set at the queue level, or per API call via ReceiveMessageWaitTimeSeconds.
Exam point If a scenario mentions a consumer making too many API calls (cost, CPU, latency) — the answer is long polling.

SQS Extended Client (large messages)

Max message size is 256 KB. To send bigger payloads (e.g. a 1GB video), use the SQS Extended Client (a Java library, but the pattern can be replicated in any language): the large payload goes into an S3 bucket, and SQS only carries a small metadata message pointing to it. The consumer reads the pointer and fetches the real payload from S3.

Key API calls

APIPurpose
CreateQueue / DeleteQueueCreate a queue (with MessageRetentionPeriod) / delete it and its messages
PurgeQueueDelete all messages in a queue
SendMessageSend a message (supports DelaySeconds)
ReceiveMessagePoll for messages (MaxNumberOfMessages up to 10, ReceiveMessageWaitTimeSeconds for long polling)
DeleteMessageRemove a processed message
ChangeMessageVisibilityExtend the visibility timeout for a message being processed

SendMessage, DeleteMessage, and ChangeMessageVisibility all have batch versions to cut down on API call volume and cost.

9 FIFO Queues

FIFO (First-In-First-Out) queues guarantee message order — something Standard queues don't. Queue names must end in .fifo.

FeatureStandardFIFO
OrderingBest-effortStrictly preserved (per message group)
DeliveryAt-least-once (duplicates possible)Exactly-once
ThroughputUnlimited~300 msg/sec (3,000 with batching)

Deduplication

Within a 5-minute deduplication interval, duplicate messages are dropped, using either:

  • Content-based deduplication — SQS computes a SHA-256 hash of the message body; identical bodies within the window are deduplicated automatically.
  • Explicit deduplication ID — you provide your own ID; a repeated ID within the window is dropped.

Message grouping

Every FIFO message needs a message group ID. Messages sharing the same group ID are strictly ordered and consumed by a single consumer; different group IDs can be processed by different consumers in parallel — ordering across groups isn't guaranteed, only within a group.

Using a per-customer (or per-entity) message group ID lets you keep strict ordering where it matters while still processing many groups in parallel.

10 Amazon SNS

SNS (Simple Notification Service) implements the pub/sub pattern: a producer publishes once to an SNS topic, and every subscriber gets a copy — instead of the producer having to integrate with each receiver individually.

  • Up to (roughly) 12 million+ subscriptions per topic, and up to 100,000 topics per account (soft limits, can be raised — not something the exam tests directly).
  • Subscriber types: email, SMS, mobile push, HTTP/HTTPS endpoints, and direct AWS integrations — SQS, Lambda, Kinesis Data Firehose.
  • Many AWS services can publish into SNS directly: CloudWatch Alarms, Auto Scaling notifications, CloudFormation state changes, Budgets, S3, DMS, Lambda, DynamoDB, RDS events, and more.

Publishing methods

  • Topic publish — create a topic, add subscriptions, publish — every subscriber gets it automatically.
  • Direct publish — for mobile apps: create a platform application + platform endpoint, publish directly to a device via Google GCM, Apple APNS, or Amazon ADM.

Security

Same shape as SQS: in-flight HTTPS encryption, at-rest KMS encryption, optional client-side encryption; IAM policies regulate the API, and SNS access policies (resource policies, like S3 bucket policies) handle cross-account access or letting services like S3 publish into a topic.

11 SNS + SQS Fan-Out Pattern

Need one message delivered reliably to multiple SQS queues? Publishing to each queue individually is fragile (partial failures, needing to add more queues later). Instead: publish once to an SNS topic, and subscribe as many SQS queues as you like.

Publishing once to an SNS topic and fanning out to multiple SQS queues gives full decoupling, no data loss (SQS persists/retries), and lets you add more consumers later without touching the producer.

  • Requires the SQS access policy on each queue to allow the SNS topic to write to it.
  • Works cross-region — an SNS topic in one region can fan out to SQS queues in others.

Other fan-out use cases

  • Multiple S3 event targets: S3 only allows one event rule per (event type + prefix) combination — fan out via SNS to reach multiple SQS queues from a single S3 event.
  • SNS → Kinesis Data Firehose → S3: direct integration lets SNS messages land in S3 (or any KDF-supported destination) without extra glue code.

SNS FIFO

SNS also has a FIFO mode: ordering by message group ID, deduplication (explicit or content-based) — but its subscribers can only be SQS queues (Standard or FIFO), and throughput matches SQS FIFO limits. Use it when you need fan-out plus ordering plus deduplication together.

Message filtering

A JSON filter policy on a subscription restricts which messages that subscriber receives (default: no filter = receive everything). E.g. filter on State: Placed for one SQS queue, State: Cancelled for another, and no filter at all for a queue that should see every message — all fed from the same topic.

12 SNS — Hands On

  • Creating a topic: choose Standard (best-effort ordering, at-least-once, highest throughput, supports SQS/Lambda/HTTPS/SMS/email/mobile) or FIFO (strict ordering, exactly-once, up to 300 pub/sec, subscribers limited to SQS).
  • Access policy works the same as SQS's — controls who/what can publish and subscribe.
  • Add a subscription: choose a protocol (Kinesis Data Firehose, SQS, Lambda, Email, Email-JSON, HTTP, HTTPS, SMS) and an endpoint (e.g. an email address).
  • Email subscriptions require confirmation — click the confirmation link sent to that address before messages will actually arrive.
  • Publishing a test message delivers it to every confirmed subscriber — in this case, straight to the inbox.

13 Kinesis Data Streams

Kinesis Data Streams collects and stores real-time streaming data — click-streams, IoT device data, server metrics/logs, etc. Exam keyword: real-time.

  • Producers: your own application code (SDK), or the Kinesis Agent installed on servers for metrics/logs.
  • Consumers: your own application code, Lambda, Amazon Data Firehose, or Managed Service for Apache Flink (for analytics).

Key characteristics

PropertyValue
RetentionUp to 365 days — data persists, so consumers can replay it; you can't delete data early, only wait for it to expire
Record sizeUp to 1 MB, but typically used for lots of small real-time records
OrderingGuaranteed for records sharing the same partition key (same shard)
SecurityAt-rest KMS encryption, in-flight HTTPS

High-throughput producer/consumer code should use the Kinesis Producer Library (KPL) and Kinesis Client Library (KCL) respectively.

Shards & capacity modes

Provisioned mode requires you to size and manually scale shards yourself; on-demand mode auto-scales but has no free tier either — pick based on how predictable your traffic is.

14 Kinesis Data Streams — Hands On

  • Creating a stream: choose On-demand (no capacity planning, but no free tier) or Provisioned (choose shard count — 1 shard = cheapest, enough for a demo).
  • Producing (low-level CLI): aws kinesis put-record --stream-name ... --partition-key ... --data ... (with --cli-binary-format raw-in-base64-out for text data).
  • Consuming (low-level CLI): first describe-stream to find the shard ID, then get-shard-iterator (e.g. TRIM_HORIZON to read from the very start of the stream), then get-records using that iterator — data comes back Base64-encoded. Each response includes a NextShardIterator to continue consuming from where you left off.
Good to know This low-level shard-by-shard consumption is the shared (standard) consumption mode. In real applications, the Kinesis Client Library (KCL) handles all this shard-iterator bookkeeping for you.

15 Amazon Data Firehose

Amazon Data Firehose (formerly Kinesis Data Firehose) loads streaming data from sources into target destinations — fully managed, auto-scaling, and near real-time (exam keyword) because of an internal buffer.

Firehose ingests from streams/agents/AWS services, optionally transforms records with Lambda, buffers them, then batch-delivers to S3, Redshift, OpenSearch, third-party tools, or any custom HTTP endpoint.

  • Buffer flushes based on size or time — whichever threshold hits first.
  • Supports CSV, JSON, Parquet, Avro, text, or binary input; can convert to Parquet/ORC and compress with gzip/Snappy; use Lambda for custom transformations (e.g. CSV → JSON).
  • Failed (or all) records can optionally be backed up to an S3 bucket.

Kinesis Data Streams vs Amazon Data Firehose

16 Amazon Data Firehose — Hands On

  • Create a delivery stream: source = Kinesis Data Stream (or Direct PUT, or another AWS service), destination = S3 (also remember: OpenSearch and Redshift are supported directly, plus third-party and custom HTTP destinations).
  • Optional Lambda transform step for filtering/converting records; optional record format conversion (e.g. to Parquet/ORC).
  • Buffer hints: set a buffer size (e.g. 1 MB) and interval (e.g. 60 seconds) — whichever condition is met first triggers delivery. Smaller/faster settings mean quicker delivery but less batching efficiency.
  • Optional compression (gzip, Snappy, Zip, Hadoop-compatible Snappy) and encryption.
  • Firehose automatically creates an IAM role with the permissions it needs to read from the source and write to the destination.
Don't forget Firehose only picks up new data sent after the delivery stream is created — old records already sitting in the source Kinesis stream won't retroactively flow through. Send fresh test data after setup, then wait out the buffer interval before checking the destination.

17 Managed Service for Apache Flink

Formerly "Kinesis Data Analytics for Apache Flink." Apache Flink is a framework (Java, SQL, or Scala) for processing data streams in real time.

  • Reads from Kinesis Data Streams or Amazon MSK (managed Apache Kafka).
  • Runs on a fully managed cluster — AWS handles compute provisioning, parallel computation, auto scaling, and application backups (checkpoints/snapshots).
Exam trap Flink can read from Kinesis Data Streams but cannot read directly from Amazon Data Firehose.

✓ Cheat Sheet

Key facts to remember

  • Sync communication = direct calls, fragile under spikes; async = middleware (queue/topic/stream) decouples and lets each side scale independently.
  • SQS: unlimited throughput, 256KB max message size, 4-day default / 14-day max retention, at-least-once delivery, best-effort ordering (unless FIFO).
  • Visibility timeout (default 30s) hides a received message from other consumers; extend it with ChangeMessageVisibility if you need more time.
  • Dead Letter Queues catch messages exceeding maxReceiveCount; redrive them back to the source once fixed. FIFO DLQ ↔ FIFO source; Standard DLQ ↔ Standard source.
  • Delay queues hide new messages for up to 15 minutes (queue-level default or per-message DelaySeconds).
  • Long polling (1–20s) cuts API calls and latency — use it over short polling whenever possible.
  • Messages over 256KB → SQS Extended Client pattern (payload in S3, pointer in SQS).
  • FIFO queues/topics: strict ordering (per message group ID), exactly-once via deduplication (content-based or explicit ID, 5-minute window), lower throughput than Standard.
  • SNS = pub/sub; combine with SQS for the fan-out pattern (one publish, many durable queues) — needs an SQS access policy allowing SNS to write.
  • SNS message filtering (JSON filter policy) lets different subscribers receive different subsets of a topic's messages.
  • Kinesis Data Streams = real-time, replayable (up to 365 days), ordered per shard/partition key, provisioned or on-demand capacity.
  • Amazon Data Firehose = near real-time, fully managed, buffers then batch-delivers to S3/Redshift/OpenSearch/third-party/HTTP — no storage or replay of its own.
  • Managed Service for Apache Flink reads from Kinesis Data Streams or MSK — not from Firehose.

Mental model

This section is about breaking the assumption that your applications must talk to each other directly. SQS gives you a durable buffer so a burst of work never overwhelms the thing processing it; SNS gives you a megaphone so one event reaches any number of independent listeners, and combining the two (fan-out) gets you both breadth and durability at once; Kinesis (Streams, Firehose, and Flink on top) is the toolkit for when "messages" become "continuous real-time data" — ingesting, buffering, transforming, and finally landing that data somewhere useful, at a scale queues and topics aren't built for.
