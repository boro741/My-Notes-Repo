Section 29 — Advanced Identity

The story of how AWS decides "yes" or "no" — temporary badges, policy math, and where your company's people actually live.

Before we start: why does this whole section exist?

By this point you already know the basics: an IAM user has permanent credentials, a role can be assumed, a policy grants or denies actions. That works fine for a simple app with three developers.

Now scale it up. What happens when an outside contractor needs access for exactly one hour, and you never want to hand them a permanent password? What happens when your S3 bucket policy says "allow" but the IAM policy attached to the user says nothing at all — does the request succeed or fail? What happens when you have 5,000 employees and each one needs their own private folder — do you really write 5,000 policies? What happens when a junior developer is allowed to launch EC2 instances — can they quietly attach an admin role to one and escalate their own privilege? And what happens when your company already has thousands of Windows user accounts sitting in an on-premise Active Directory — do you recreate all of them by hand in AWS?

Every topic below exists to answer exactly one of those five questions. That's the story we're going to walk through.

1 STS — The Temporary Badge Office

The problem before this existed Imagine hard-coding a permanent AWS access key into a mobile app or handing one to a contractor. That key never expires on its own, it's easy to leak (screenshots, GitHub commits, decompiled apps), and if it does leak, you have to hunt it down and manually revoke it. Permanent credentials for temporary needs is a liability sitting in your codebase.
Who is STS? STS (Security Token Service) is the front-desk receptionist of AWS. You don't get to keep a master key to the building — you show your ID, the receptionist checks whether you're allowed in, and if so, prints you a visitor badge that expires in 15 minutes to an hour. Once it expires, it's just a useless piece of plastic. No one has to chase you down to take it back.

That's the whole idea: STS hands out short-lived credentials so that a caller can act as a role without ever holding a permanent secret key for that role.

You call sts:AssumeRole→ STS checks trust policy→ STS checks permissions→ Temporary credentials (15min–1hr)

The little orange dots are the request "traveling" through the system — same mechanism works for cross-account access to another AWS account's role.

You'd probably ask "What if my task takes longer than an hour?" — you simply call AssumeRole again before the badge expires. AWS deliberately makes credentials short-lived so a leak is only dangerous for a small window, not forever.

The full STS toolbox

Exam point The four to know cold: AssumeRole, GetSessionToken, GetCallerIdentity, and DecodeAuthorizationMessage.

Why STS + MFA exist together

Some actions are dangerous enough (terminating production instances, deleting a bucket) that a password alone shouldn't be enough. So IAM lets you attach a condition — "aws:MultiFactorAuthPresent": true — onto a policy. But that condition needs something to check against. That's where GetSessionToken comes in: after the user proves their identity with an MFA device, this call returns an access key, a secret key, and a session token (all three travel together) plus an expiry — and only credentials obtained this way carry the "yes, MFA was present" flag the policy is checking for.

Misconception: MFA is checked by IAM every time you type a password.
Reality: the MFA flag is embedded in the temporary session returned by STS. The policy condition checks the session, not the login screen directly.

2 How AWS Actually Decides Yes/No

The problem before this existed A single IAM user can have several policies attached at once — one from their group, one attached directly, maybe an inline one too. If one policy says "allow S3 delete" and another says "deny S3 delete," which one wins? Without a strict, predictable rule, permissions would be a coin flip — and security systems can never be a coin flip.

AWS resolves this with one deterministic algorithm, evaluated every single time:

Decision always starts at Deny. An explicit Deny anywhere short-circuits everything else. Only if no deny exists does an explicit Allow get a chance to matter.

Walk it through: a user tries to create a DynamoDB table. AWS starts from a default of deny, gathers every policy attached to that user (group policies, directly attached policies, inline policies — all of them), and checks: is there an explicit deny anywhere in that pile for this action? If yes — done, denied, no further discussion. Only if there's no explicit deny does AWS look for an explicit allow. Found one → allowed. Found none → still denied, because "deny" was always the starting point.

Important An explicit allow and an explicit deny for the same action, in different policies attached to the same user? The deny always wins. There is no "allow overrides deny somewhere else" — deny is checked first and ends the conversation.
Misconception: if I attach a policy that allows an action, it's allowed no matter what.
Reality: one explicit deny anywhere in the user's policy set beats any number of allows.

3 IAM Policy + S3 Bucket Policy — Two Votes, One Door

The problem before this existed IAM policies are attached to people (users, roles, groups) inside your account. But S3 buckets are often shared across accounts, or you want the bucket itself to carry its own rules regardless of who's asking. If only IAM policies mattered, a bucket owner in a different account could never grant access to someone else's IAM user directly. So S3 needed its own policy attached to the resource itself.

Now that two policies can both talk about the same S3 action, AWS needs a rule for combining them. The rule: take the union — anything either policy allows is allowed — unless an explicit deny shows up in either one, which (as you just learned in section 2) always wins.

The effective S3 permission is the union (the overlap plus both outer regions) of what the IAM policy allows and what the bucket policy allows — either one granting access is enough, unless an explicit deny appears.

Exam point Removing S3 permissions from an EC2 instance's IAM role doesn't necessarily block it from S3 — if the bucket policy separately allows that role, access still works, because it's the union of both that counts.

4 Dynamic Policies — One Policy, Thousands of People

The problem before this existed Say every employee needs a private /home/<username> folder in a shared S3 bucket, readable and writable only by themselves. The naive approach: write one IAM policy per person. Fine for 5 people. Unmanageable for 5,000 — every new hire means writing, testing, and attaching a brand-new policy, forever.
Think of it like a mail-merge letter Instead of writing 5,000 individual letters, you write one template with a placeholder — "Dear <name>" — and the mail-merge fills it in per recipient at print time. A dynamic policy does exactly that with the policy variable ${aws:username}: it gets substituted with the actual caller's username at the moment the request is evaluated.

One single policy, granting access to /home/${aws:username}, gets attached to every user — and because the variable resolves differently for each caller, each person automatically lands in only their own folder. No per-user policies, no drift, one thing to maintain.

Why it matters One policy, attached to everyone, that behaves differently per person — instead of a growing pile of near-identical, per-user policies that someone has to keep in sync by hand.

5 Policy Types — Who's Allowed to Edit the Rulebook

The problem before this existed Not every policy should be maintained the same way. Some permissions (like "read-only access to everything") are so common that you'd rather AWS keep them current as new services launch. Others are highly specific to your company and need version history and rollback. And sometimes you just need a quick, throwaway rule tied to exactly one user that disappears when they leave.
TypeWho maintains itNotes
AWS managed policyAWSGood for power users, admins, job-function policies; AWS updates it as new services/APIs appear — but you have zero control over the content
Customer managed policyYouBest practice for granular control; reusable across many principals; supports versioning/rollback and central change tracking
Inline policyYouStrict one-to-one link to a single principal; no version control, hard to reuse; auto-deleted if the principal is deleted; capped at 2 KB
Watch out Inline policies are capped at 2 KB per principal — a broad policy (e.g. every EC2 "List" permission) can be too large to save inline, forcing a trim or a switch to a managed policy.

6 Passing a Role — The Two-Lock Problem

The problem before this existed Suppose a developer is allowed to launch EC2 instances. If they could attach any IAM role to that instance — including an admin role — they could quietly hand their own EC2 instance god-mode permissions and use it as a backdoor. That's privilege escalation, and AWS needed a way to stop it without stopping developers from launching EC2 instances at all.

The fix is two independent locks that must both open before a role can be attached to a service:

  1. The user's own permission: iam:PassRole, which can be scoped to one specific role ARN — e.g. full EC2 permissions, but PassRole restricted to only the S3Access role. That's the only role this user could ever hand to an instance.
  2. The role's own trust policy: even if the user is allowed to pass a role, the role itself has to declare (in its trust relationships) which service principal — ec2.amazonaws.com, lambda.amazonaws.com, codepipeline.amazonaws.com — is allowed to assume it in the first place.

Two gates, both must open: the user needs iam:PassRole to hand the role to a service, and the role's trust policy must name that service as an allowed principal.

You'd probably ask "Why not just rely on one of these locks?" — because PassRole alone controls who can hand out the role, but says nothing about which services are trustworthy recipients; trust policy alone would mean any user with any permissions could hand any role to any service that role trusts. You need both: a gate on the giver and a gate on the receiver.

7 Directory Services — Where Do People Actually Live?

The problem before this existed Large companies already have thousands of employee accounts sitting in an on-premise Microsoft Active Directory — logins, computers, printers, file shares, all centrally managed. Moving to AWS shouldn't mean recreating every one of those accounts by hand as an IAM user. AWS needed a way to either extend that existing directory into the cloud, or stand up something AD-compatible without duplicating effort.

Microsoft Active Directory (AD) itself is a database of objects — user accounts, computers, printers, file shares, security groups — with centralized security management, normally running on Windows Server. Objects are organized into trees, a group of trees is a forest, and a domain controller lets any connected Windows machine validate a login against that same shared set of credentials.

AWS gives you three characters to choose from, each solving a slightly different version of the problem:

Character 1 — AWS Managed Microsoft AD

A real Microsoft AD, run by AWS, with its users living natively in the cloud. It can optionally set up a two-way trust with your on-premise AD, so users can be validated on either side. Supports MFA.

Character 2 — AD Connector

Not a directory at all — a proxy. It holds no users of its own; every login request is forwarded straight back to your on-premise AD, which stays the single source of truth. Supports MFA.

Character 3 — Simple AD

A standalone, AD-compatible directory living only in AWS — same API surface as AD, but not real Microsoft AD under the hood. No trust relationship with an on-premise AD is possible, and no MFA.

FlavorUsers managedOn-premise trust?MFA?
AWS Managed Microsoft ADLocally in AWSYes — two-way trust with on-premise ADYes

Exam point Need to proxy users straight to on-premise → AD Connector. Need to manage users in the cloud with MFA and an optional on-premise trust → AWS Managed Microsoft AD. No on-premise AD at all → Simple AD.

✓ Recap, Mental Models & Interview Prep

One-minute recap

This whole section is about the fine print behind identity in AWS. STS turns "who you are" into short-lived, scoped credentials, so nobody has to hold a permanent key for a temporary job. IAM's policy evaluation always starts at deny and lets an explicit deny anywhere win instantly — and for S3 specifically, it's the union of the IAM policy and the bucket policy that counts, not either one alone. Dynamic policies and the three policy types (managed / customer / inline) exist to scale that model to thousands of people without duplicating rules by hand. Passing a role to a service is really two locks that both need to open: your permission to pass it, and the role's own trust policy accepting that service — this is what stops privilege escalation. And Directory Services is simply about deciding where your Windows-world identities actually live: in AWS, on-premise, or standalone.

Mental models — one analogy per character

  • STS — the front-desk receptionist who prints expiring visitor badges instead of handing out master keys.
  • Policy evaluation — a courtroom where the default verdict is "guilty" (deny) unless proven otherwise, and a single objection ("deny") ends the case immediately.
  • IAM + S3 union — two people voting on the same door; either one saying "let them in" is enough, unless someone shouts "absolutely not."
  • Dynamic policies — a mail-merge template that fills in each person's name automatically.
  • Policy types — AWS-managed is a rental car (maintained for you, no customization); customer-managed is your own car (full control, you service it); inline is a bicycle bolted to one specific person (goes wherever they go, disappears with them).
  • PassRole — handing someone your car keys (PassRole) only works if the car's owner's manual (trust policy) says that person is allowed to drive it.
  • Directory Services — Managed Microsoft AD is a satellite office with a direct phone line to HQ; AD Connector is just a phone forwarding all calls to HQ; Simple AD is a brand-new office with no connection to HQ at all.

Cheat sheet — key facts

  • STS issues temporary credentials (15 min – 1 hour); know AssumeRole, GetSessionToken (used with MFA), GetCallerIdentity, and DecodeAuthorizationMessage.
  • Policy evaluation: default deny → explicit deny anywhere wins immediately → otherwise needs an explicit allow → else deny.
  • For S3, the effective permission is the union of the IAM policy and the S3 bucket policy — either can grant access, but an explicit deny in either one always wins.
  • Dynamic policies use ${aws:username} (and similar variables) so one policy behaves differently per user — e.g. scoping each user to their own S3 folder.
  • Three policy types: AWS managed (maintained by AWS), customer managed (best practice — versioned, reusable, auditable), inline (1:1 with a principal, no versioning, 2 KB cap).
  • Assigning a role to a service needs two things: the user's iam:PassRole permission, and the role's own trust policy naming that service as an allowed principal.
  • AWS Directory Service flavors: Managed Microsoft AD (cloud users + optional two-way on-prem trust + MFA), AD Connector (pure proxy to on-prem, no local users), Simple AD (fully standalone, AD-compatible API only, no MFA, no on-prem link).

Common AWS Developer Associate-style interview questions

Q: A user has one policy that explicitly allows s3:DeleteObject and another that explicitly denies it. What happens?
A: The request is denied. An explicit deny in any applicable policy always wins over an explicit allow elsewhere.
Q: An EC2 instance's IAM role has no S3 permissions at all, but the target bucket's policy explicitly allows that role to read/write. Can it access the bucket?
A: Yes. S3 access is the union of the IAM policy and the bucket policy — the bucket policy's allow is enough on its own, as long as there's no explicit deny anywhere.
Q: How would you give 10,000 IAM users each access to only their own folder in a shared S3 bucket, without writing 10,000 policies?
A: A single dynamic policy using the ${aws:username} policy variable, attached to all users (or their group), scoping each to /home/${aws:username}.
Q: A developer can launch EC2 instances but should not be able to attach an admin role to one. How do you enforce that?
A: Restrict their iam:PassRole permission to only the specific, non-privileged role ARNs they're allowed to pass — never grant PassRole on *.
Q: Your company wants to keep all AD user accounts strictly on-premise but still let AWS resources check logins against them. Which Directory Service flavor fits?
A: AD Connector — it's a pure proxy with no local users, forwarding every request back to the on-premise AD.

Common misconceptions, gathered in one place

"An explicit allow anywhere always wins." → An explicit deny anywhere always wins first; allow is only checked if no deny exists.
"Removing a role's S3 permissions always blocks S3 access." → Not if the bucket policy separately grants that role access — the union still applies.
"PassRole alone is enough to attach a role to a service." → The role's own trust policy must also name that service as an allowed principal — both locks must open.
"Simple AD is just a smaller version of Managed Microsoft AD." → Simple AD isn't real Microsoft AD at all (just AD-compatible API), can't trust an on-premise AD, and has no MFA — it's a different tool, not a smaller one.
"Inline policies are just a lightweight version of customer managed policies." → They're not reusable across principals and vanish automatically when the principal is deleted — good for exceptions, not for anything you want to maintain long-term.
