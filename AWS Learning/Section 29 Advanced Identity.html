1 STS Overview

STS (Security Token Service) hands out temporary security credentials — valid from 15 minutes up to one hour — so a caller can access AWS resources directly, without long-lived credentials.

APIPurpose
AssumeRoleAssume a role within your account or across accounts
AssumeRoleWithSAMLGet temporary credentials for users signed in via SAML
AssumeRoleWithWebIdentityGet temporary credentials for users signed in via Facebook/Google/OIDC — largely superseded by Cognito Identity Pools now
GetSessionTokenGet temporary credentials, typically combined with MFA for an IAM user or the root account
GetFederationTokenGet temporary credentials for a federated user
GetCallerIdentityReturn details about the IAM user/role making the current call — "who am I?"
DecodeAuthorizationMessageDecode an error message returned when an AWS API call is denied
Exam point The most important ones to know: AssumeRole, GetSessionToken, GetCallerIdentity, and DecodeAuthorizationMessage.

AssumeRole: STS validates the caller can assume the target role, then returns short-lived credentials to act as that role — works the same way for cross-account access to another account's role.

STS with MFA

To require MFA before an action, add the condition "aws:MultiFactorAuthPresent": true to the IAM policy — e.g. only allow stopping/terminating instances when this condition is true. The user first calls GetSessionToken after authenticating with an MFA device, which returns an access key ID, a secret key, and a session token (all three are needed for the subsequent API call), plus an expiration time so you know when to renew.

2 Advanced IAM — Policy Evaluation Logic

A simplified model of how AWS evaluates whether a request is allowed:

Decision starts at Deny by default; an explicit Deny anywhere wins immediately; otherwise an explicit Allow is needed, or the request stays denied.

Concretely: if a user tries to create a DynamoDB table, the decision starts as deny. All policies attached to the user are evaluated together. If any of them has an explicit deny for that action, the final decision is deny, full stop. Only if there's no explicit deny does an explicit allow get checked — if found, the final decision is allow; otherwise, deny.

Important If a policy set contains both an explicit allow and an explicit deny for the same action, the deny always wins — it's evaluated first.

3 Advanced IAM — IAM Policies + S3 Bucket Policies

IAM policies attach to users/roles/groups; S3 bucket policies attach to buckets — and both can define what a principal can do on a bucket. When evaluating an S3 action, AWS considers the union of the IAM policy and the S3 bucket policy together (unless there's an explicit deny in either, which always wins).

The effective S3 permission is the union of what the IAM policy allows and what the bucket policy allows — either one granting access is often enough, unless an explicit deny appears.

Explicit denyAllows read/writeCannot read/write — explicit deny wins
Exam point Removing S3 permissions from an EC2 instance's IAM role doesn't necessarily block it from S3 — if the bucket policy separately allows that role, access still works, because it's the union of both that counts.

4 Advanced IAM — Dynamic Policies

Say you want each IAM user to have their own /home/<username> folder in an S3 bucket, readable/writable only by them. Writing one IAM policy per user doesn't scale — every new hire means a new policy.

Instead, a dynamic policy uses the policy variable ${aws:username}, which gets substituted at runtime with the caller's actual username. One single policy — granting access to /home/${aws:username} — can be attached to every user, and each user automatically only reaches their own folder.

Why it matters One policy, attached to everyone, that behaves differently per user — instead of maintaining a growing pile of near-identical, per-user policies.

5 Advanced IAM — Policy Types

Inline policyYouStrict one-to-one link to a single principal; no version control, hard to reuse; deleted automatically if the principal is deleted; capped at 2 KB per policy
Watch out Inline policies have a small size limit (2 KB per user) — a broad policy (e.g. every EC2 "List" permission) can be too large to save as inline, forcing you to trim it down or use a managed policy instead.

6 Granting Permission to Pass a Role

Every time you assign an IAM role to a service — an EC2 instance, a Lambda function, CodePipeline — you're passing a role to that service so it can assume it and act on your behalf. Doing this requires the iam:PassRole permission (often paired with iam:GetRole to view the role first).

An IAM policy can restrict which specific role a user is allowed to pass — e.g. full EC2 permissions, but iam:PassRole limited to only one specific role ARN (like an S3Access role), so that's the only role the user could ever attach to an EC2 instance.

Trust policies gate who can assume a role

Not just any service can assume any role — a role's trust policy defines which service principal (e.g. ec2.amazonaws.com, codepipeline.amazonaws.com, lambda.amazonaws.com) is allowed to assume it. This is visible in the IAM console under a role's Trust relationships tab.

Two gates must both open: the user needs iam:PassRole to hand the role to a service, and the role's own trust policy must name that service as an allowed principal.

7 AWS Directory Services

Microsoft Active Directory (AD) is a database of objects (user accounts, computers, printers, file shares, security groups) with centralized security management, found on Windows Server with AD Domain Services. Objects are organized into trees, and a group of trees is a forest. A domain controller lets any connected Windows machine validate a login against the same shared set of credentials.

AWS Directory Service gives you an active directory in AWS, in three flavors:

FlavorUsers managedOn-premise trust?MFA?
AWS Managed Microsoft ADLocally in AWSYes — two-way trust with on-premise ADYes
AD ConnectorSolely on-premise (this is just a proxy)Proxies every request back on-premiseYes
Simple ADLocally in AWS (AD-compatible API, not real Microsoft AD)No — cannot join an on-premise ADNo

Managed Microsoft AD shares users both ways with on-premise AD; AD Connector is purely a proxy with no local users; Simple AD stands entirely alone.

Exam point Need to proxy users straight to on-premise → AD Connector. Need to manage users in the cloud with MFA and an optional on-premise trust → AWS Managed Microsoft AD. No on-premise AD at all → Simple AD.

✓ Cheat Sheet

Key facts to remember

  • STS issues temporary credentials (15 min – 1 hour); know AssumeRole, GetSessionToken (used with MFA), GetCallerIdentity, and DecodeAuthorizationMessage.
  • Policy evaluation: default deny → explicit deny anywhere wins immediately → otherwise needs an explicit allow → else deny.
  • For S3, the effective permission is the union of the IAM policy and the S3 bucket policy — either can grant access, but an explicit deny in either one always wins.
  • Dynamic policies use ${aws:username} (and similar variables) so one policy can behave differently per user — e.g. scoping each user to their own S3 folder.
  • Three policy types: AWS managed (maintained by AWS), customer managed (best practice — versioned, reusable, auditable), inline (1:1 with a principal, no versioning, 2 KB cap).
  • Assigning a role to a service needs two things: the user's iam:PassRole permission, and the role's own trust policy naming that service as an allowed principal.
  • AWS Directory Service flavors: Managed Microsoft AD (cloud users + optional two-way on-prem trust + MFA), AD Connector (pure proxy to on-prem, no local users), Simple AD (fully standalone, AD-compatible API only, no MFA, no on-prem link).

Mental model

This section is about the fine print behind identity in AWS: STS is the mechanism that turns "who you are" into short-lived, scoped credentials; IAM's policy evaluation always favors an explicit deny, and for S3 specifically it's the union of IAM and bucket policies that counts, not either one alone. Dynamic policies and the three policy types (managed/customer/inline) are about scaling that model to many users without duplicating rules. Passing a role to a service is really two locks that both need to open — your permission to pass it, and the role's own trust policy accepting that service. And Directory Services is simply about deciding where your Windows-world identities actually live: in AWS, on-premise, or standalone.
