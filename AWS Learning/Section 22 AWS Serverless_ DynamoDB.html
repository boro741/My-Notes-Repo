1 DynamoDB Overview

DynamoDB is a fully managed, serverless NoSQL database — highly available with multi-AZ replication out of the box.

Relational databases give you rich querying (joins, aggregations) but scale mostly vertically; NoSQL databases like DynamoDB trade that querying power for near-unlimited horizontal scale.

Key features

  • Fully distributed — scales to millions of requests/sec, trillions of rows, hundreds of TB.
  • Fast, consistent, low-latency performance; fully integrated with IAM.
  • Event-driven via DynamoDB Streams.
  • Low cost with auto scaling; Standard and Standard-IA table classes for storage tiering.

Basics

  • Made of tables, each with a primary key decided at creation time.
  • Infinite items (rows) per table; each item has attributes (like columns, but nestable), which can be added over time and can be null.
  • Max item size: 400 KB.
  • Data types: scalar (string, number, binary, boolean, null), document (list, map), and set (string/number/binary sets).

Choosing a primary key

A simple partition key must be unique per item; a partition+sort key combo lets multiple items share a partition key (e.g. many games per user) as long as the pair is unique.

Exam point Choosing a partition key: pick the one with the highest cardinality and best distribution (e.g. movie_id over movie_language, which would skew heavily toward one value like "English").

2 Basics — Hands On

  • DynamoDB has no "create database" step — you just create tables directly.
  • Table class: DynamoDB Standard (default, most use cases) vs Standard-IA (infrequently accessed data, cost optimized).
  • Capacity mode: On-demand or Provisioned (the latter is within the free tier).
Good to know Adding a new attribute to one item doesn't require updating the schema or every other item — other rows simply don't have that attribute (it reads as missing/null). This flexibility is core to NoSQL, but also a risk if you're not disciplined about your data model.

With a partition-key-only table, inserting a second item with the same key fails (must be unique). With a partition key + sort key table (e.g. user_id + post_timestamp), the same user_id can appear many times as long as each sort key value differs — letting one user have many posts.

3 WCU & RCU — Throughput

ModeHow it worksCost
ProvisionedYou specify RCU/WCU ahead of time (optionally with auto scaling)Pay for what's provisioned, every hour
On-demandScales automatically, no capacity planningPay per request — ~2.5× more expensive than provisioned

You can switch between modes once every 24 hours.

Write Capacity Units (WCU)

1 WCU = 1 write/sec for an item up to 1 KB (rounded up). E.g. 10 items/sec × 2KB = 20 WCU; 6 items/sec × 4.5KB (rounds to 5KB) = 30 WCU.

Read Capacity Units (RCU) & consistency

Writes replicate across internal servers; reading right after a write can hit an un-replicated copy (eventually consistent) unless you explicitly request a strongly consistent read (set ConsistentRead: true).

1 RCU = 1 strongly consistent read/sec, or 2 eventually consistent reads/sec, for an item up to 4 KB (rounded up).

  • 10 strongly consistent reads/sec × 4KB = 10 RCU
  • 16 eventually consistent reads/sec × 12KB = (16÷2) × (12÷4) = 24 RCU
  • 10 strongly consistent reads/sec × 6KB (rounds to 8KB) = 10 × (8÷4) = 20 RCU

Partitions & throttling

  • RCU/WCU are spread evenly across partitions — a "hot" partition key or very large items can exhaust a single partition's share and trigger ProvisionedThroughputExceededException, even if the table's total capacity looks fine.
  • Fixes: exponential backoff, better partition key distribution, or DAX for read-heavy hot keys.

On-demand mode uses RRU (read request units) and WRU (write request units) instead — same math, just billed per request with no throttling and no capacity planning.

Hands-on: Auto scaling lets you set min/max capacity and a target utilization %, and DynamoDB adjusts provisioned RCU/WCU automatically — similar in spirit to EC2 Auto Scaling.

4 Basic Operations & APIs

Write (partial)UpdateItemEdits specific attributes, or creates the item if missing — used with atomic counters

Exam point Need to wipe an entire table? Use DeleteTable, not a Scan + delete loop.

Batch operations

  • BatchWriteItem: up to 25 PutItem/DeleteItem operations, 16MB total (no UpdateItem in a batch).
  • BatchGetItem: up to 100 items across one or more tables, 16MB total, retrieved in parallel.
  • Failed items come back as UnprocessedItems/UnprocessedKeys — retry with exponential backoff, or add capacity if it keeps happening.

PartiQL (mentioned here, detailed later)

PartiQL lets you use SQL-like syntax (select/insert/update/delete) against DynamoDB — same underlying capabilities, just a different syntax for people more comfortable with SQL. No joins.

5 Conditional, Concurrent & Atomic Writes

Write typeWhat happens
Concurrent writes (no protection)Two clients update the same item at once — both "succeed," but one silently overwrites the other. Not usually desired.
Conditional writes (optimistic locking)Each write includes a condition (e.g. "only if value = 0"); whichever write lands first succeeds, the other fails because the condition no longer holds
Atomic writesE.g. two clients each "increase value by N" — both apply, and the total reflects both increments correctly
Batch writesOne client writing/updating many items at once — no special concurrency behavior, just efficiency

Optimistic locking in practice

Add a version attribute to your items. Each client conditions its update on the version it last read (e.g. "update only if version = 1"). Whichever write applies first bumps the version to 2 — the second client's write then fails because the version condition no longer matches, telling it to re-fetch and retry.

Condition expression building blocks

  • attribute_exists / attribute_not_exists / attribute_type
  • contains / begins_with (string checks)
  • IN (match a set of values), BETWEEN :low AND :high, > / <
  • size (check string/attribute length)
Exam point Filter expressions apply to reads (Query/Scan results); condition expressions apply to writes (Put/Update/Delete/TransactWrite) and determine whether the write happens at all.

Common pattern to never overwrite existing data: condition the write on attribute_not_exists(partition_key) (and the sort key too, if present) — the write only succeeds if the item doesn't already exist.

6 Indexes: GSI & LSI

Local Secondary Index (LSI)Global Secondary Index (GSI)
Partition keySame as base tableCan be different
Sort keyDifferent (alternative sort key)Can be different
When createdOnly at table creation timeAnytime — added or modified later
CapacityShares the base table's RCU/WCUHas its own provisioned RCU/WCU
LimitUp to 5 per tableNo fixed small limit
Throttling behaviorNo special considerationsIf the GSI is throttled, the main table is throttled too — even if the base table's own WCU is fine

An LSI just gives you an alternative sort key on the same partition key; a GSI gives you a whole different partition (and optionally sort) key, with its own dedicated capacity.

Hands-on: creating an LSI at table creation lets you query by the same partition key with a different sort key; creating a GSI afterward (with its own RCU/WCU) lets you query by an entirely different partition key (e.g. game_id instead of user_id).

7 PartiQL

A SQL-compatible query language for DynamoDB, usable from the console, NoSQL Workbench, the API, CLI, or SDK. Supports select/insert/update/delete (including batch operations) and can query across multiple tables — but still no joins.

Hands-on: SELECT * FROM users scans a table; SELECT * FROM demo_indexes WHERE user_id = '123' queries by partition key; you can also query a named index directly (SELECT * FROM demo_indexes.game_id_index).

8 DAX

DynamoDB Accelerator (DAX) is a fully managed, highly available in-memory cache for DynamoDB — microsecond latency for cached reads, fully API-compatible (no application logic changes needed).

The app talks to the DAX cluster instead of DynamoDB directly; DAX serves cached results (default 5-minute TTL) or fetches and caches on a miss.

  • Solves hot key problems — repeated reads of the same popular item no longer hammer DynamoDB's RCU.
  • Up to 10 nodes per cluster; recommended 3 nodes across AZs for production HA.
  • Secure: encryption at rest, IAM, VPC security groups, CloudTrail integration.

DAX vs ElastiCache

DAXElastiCache
Caches individual objects, queries, and scans directly from DynamoDBCaches the results of application-side computation (e.g. after aggregating/filtering DynamoDB data yourself)

The two can be used together: DAX for simple query/object caching, ElastiCache for storing the results of more complex app-side logic.

9 DynamoDB Streams

An ordered list of item-level modifications (create/update/delete) on a table, retained for 24 hours.

Every create/update/delete lands in the stream; Lambda (via an Event Source Mapping) or a Kinesis Client Library app can consume it in near real-time.

  • View types: KEYS_ONLY, NEW_IMAGE, OLD_IMAGE, or NEW_AND_OLD_IMAGES.
  • Made of shards, just like Kinesis — but AWS manages shard provisioning automatically.
  • Use cases: welcome emails on new signup, analytics, derivative tables, feeding OpenSearch for search, or powering Global Tables cross-region replication.
Important exam point Enabling a stream is not retroactive — you only get events for changes that happen after enabling it, nothing from before.

Hands-on: enabling a stream on a table + adding a Lambda trigger (with DynamoDB read permissions) logs every insert/modify/remove — including both the new and old image of the item — directly to CloudWatch Logs.

10 TTL

Time To Live automatically deletes items after a defined expiration timestamp (a Unix epoch number attribute) — at no extra WCU cost.

  • DynamoDB periodically scans for expired items and deletes them — usually within a day, but the docs note it can take longer.
  • Expired-but-not-yet-deleted items still show up in reads/queries/scans until actually removed — filter client-side if this matters.
  • TTL deletes also propagate to indexes (LSI/GSI) and appear in the DynamoDB Stream as delete events — so you can still react to or recover them.

Use cases: session data expiry, cost/storage reduction by keeping only current items, regulatory data retention limits.

11 CLI & Pagination

Good to know --page-size and --max-items solve different problems: page-size keeps individual API calls small (avoiding timeouts) while still returning everything; max-items caps how much you actually see per command, requiring the returned token to page through the rest.

12 Transactions

DynamoDB transactions give an all-or-nothing write (or a consistent read) across multiple items/tables — full ACID guarantees.

ModeOptions
ReadEventual consistency, strong consistency, or transactional (consistent view across multiple tables at once)
WriteStandard (some writes can fail independently) or transactional (all succeed or none do)
Important Transactions consume 2× the WCU/RCU of an equivalent non-transactional operation (DynamoDB prepares, then commits, for every item).
  • TransactGetItems — one or more GetItem reads as a single transaction.
  • TransactWriteItems — one or more PutItem/UpdateItem/DeleteItem writes as a single transaction.

Example calculations: 3 transactional writes/sec × 5KB = 3 × 5 × 2 = 30 WCU. 5 transactional reads/sec × 5KB (rounds to 8KB) = 5 × (8÷4) × 2 = 20 RCU.

Use cases: financial transactions, order management, multiplayer games — anywhere multiple related writes must succeed or fail together (e.g. updating an account balance and recording a bank transaction atomically).

14 Write Sharding

Problem: a voting app with only two candidates (A, B) as the partition key means all data lands in just two partitions — a classic hot partition.

Appending a random or hashed suffix to a low-cardinality partition key artificially spreads writes across many more partitions, avoiding hot-partition throttling.

Two methods to generate the suffix/prefix: a random suffix, or a value calculated via a hashing algorithm — either works, the goal is just better key distribution.

15 Patterns with S3

Pattern 1: Store large objects in S3, metadata in DynamoDB

Since DynamoDB items max out at 400KB, store the actual large file (image, video) in S3, and keep only a small pointer (the S3 object key/URL) plus metadata in DynamoDB. Reads fetch the metadata from DynamoDB first, then the object from S3.

Pattern 2: Use DynamoDB to index S3 object metadata

An S3 upload triggers a Lambda function (via event notification) that writes the object's metadata (size, date, creator, etc.) into a DynamoDB table. This lets you answer queries S3 alone can't efficiently do — "find objects by timestamp," "total storage per customer," "objects uploaded in a date range" — by querying DynamoDB, then fetching the actual objects from S3.

Analogy S3 is like a warehouse full of boxes with no labels visible from outside; DynamoDB is the label/catalog system that tells you which shelf (S3 key) to go pull a specific box from.

17 Security & Fine-Grained Access

  • VPC endpoints keep DynamoDB traffic off the public internet.
  • Access fully controlled by IAM; encryption at rest (KMS) and in transit (SSL/TLS).
  • Backup/restore: Point-in-Time Recovery (PITR) (no performance impact) or manual backup/restore.
  • Global Tables: multi-region, multi-active, fully replicated tables — requires DynamoDB Streams to be enabled.
  • DynamoDB Local: a local simulation of DynamoDB for development/testing without hitting the real service.
  • AWS DMS can migrate data to/from DynamoDB (e.g. MongoDB → DynamoDB, or DynamoDB ↔ Oracle/MySQL/S3).

Fine-grained access control

Clients authenticate via an identity provider, exchange that identity for temporary AWS credentials tied to a restricted IAM role — never long-lived IAM users handed out to end users.

The IAM role's policy uses a condition on dynamodb:LeadingKeys, tied to a Cognito identity pseudo-variable, to restrict a user to only rows where the partition key matches their own identity — row-level security. You can similarly restrict which attributes (columns) a user can see.

✓ Cheat Sheet

Key facts to remember

  • Choose a partition key with the highest cardinality/distribution; partition + sort key lets multiple related items share a partition key.
  • 1 WCU = 1 write/sec up to 1KB; 1 RCU = 1 strongly consistent read/sec (or 2 eventually consistent) up to 4KB — always round item size up.
  • Strongly consistent reads cost 2× the RCU of eventually consistent reads.
  • RCU/WCU are split evenly per partition — hot keys/large items can throttle one partition even if total table capacity is fine.
  • LSI: alternate sort key, same partition key, must be created at table creation, shares base table capacity, max 5 per table.
  • GSI: alternate partition (+sort) key, created anytime, own dedicated capacity — throttling on the GSI throttles the whole table.
  • Conditional writes = optimistic locking (version-based concurrency control); atomic writes (e.g. counters) always combine correctly; concurrent writes without protection silently overwrite.
  • DAX caches individual objects/queries/scans (microsecond latency, 5-min default TTL); ElastiCache is better for caching your own app-side computed results.
  • Streams retain 24 hours of item-level changes; NOT retroactive when first enabled; power Lambda triggers and Global Tables.
  • TTL deletes are free (no WCU), not instant, still visible in reads until actually deleted, and show up in Streams.
  • Transactions cost 2× RCU/WCU and give full ACID guarantees across items/tables (TransactGetItems / TransactWriteItems).
  • Write sharding (random/hashed suffix on the partition key) fixes low-cardinality hot partitions.
  • Large objects → store in S3, reference from DynamoDB; S3 metadata → index it in DynamoDB for queryability.
  • Fine-grained access uses federated identity + temporary credentials + an IAM policy condition on dynamodb:LeadingKeys for row-level security.

Mental model

DynamoDB trades the rich querying of SQL (joins, aggregations) for near-unlimited horizontal scale, and almost everything in this section is about designing around that trade: pick a partition key that spreads load evenly, model your access patterns up front since indexes (especially LSIs) are hard to bolt on later, understand exactly what a read or write costs (RCU/WCU math) so you can provision correctly, and reach for the right extension — DAX for hot reads, Streams for reacting to changes, TTL for free cleanup, transactions for correctness, S3 for anything too big — rather than fighting the core model. Get the partition key and capacity math right, and most of DynamoDB's exam surface falls into place.
