Amazon RDS Overview

RDS = Relational Database Service. It's AWS's managed service for SQL databases. "Managed" is the key word — AWS handles the boring, risky operational work so you can just use the database.

Engines RDS supports (memorize this list — it comes up on the exam):

  • PostgreSQL
  • MySQL
  • MariaDB
  • Oracle
  • Microsoft SQL Server
  • IBM DB2
  • Aurora — AWS's own proprietary database engine (covered in its own section below)

Why use RDS instead of just installing a database yourself on an EC2 instance? Because RDS gives you, for free (well, included):

  • Automated provisioning + OS patching
  • Continuous backups + Point-in-Time Restore (roll back to a specific timestamp)
  • Monitoring dashboards
  • Read Replicas (scale reads)
  • Multi-AZ (disaster recovery)
  • Maintenance windows for upgrades
  • Vertical scaling (bigger instance type) and horizontal scaling (add read replicas)
  • Storage backed by EBS
Don't forget You cannot SSH into an RDS instance. It's a managed service — AWS owns the underlying EC2 box, not you. That's the trade-off for all the automation you get.

RDS Storage Auto Scaling

You pick an initial storage size (say 20 GB) when creating the DB. If your app writes a lot of data and you're about to run out of space, RDS can automatically grow the storage for you — no downtime, no manual resizing.

Auto scaling kicks in when all of these are true:

  • Free storage is less than 10% of allocated storage
  • The low-storage condition has lasted more than 5 minutes
  • At least 6 hours have passed since the last storage modification

You also set a maximum storage threshold so it doesn't grow forever. Works across all RDS engines. Great for apps with unpredictable workloads.

Analogy Storage Auto Scaling is like a phone plan that automatically bumps your data allowance when you're about to hit your cap — instead of you manually calling to upgrade every time.

RDS Read Replicas vs Multi-AZ

Exam key point This is one of the most heavily tested topics. Read Replicas = scaling reads. Multi-AZ = disaster recovery. Don't mix them up.

Read Replicas

Read Replicas help you scale reads. You can create up to 15 read replicas, and they can be:

  • Within the same Availability Zone
  • Cross-AZ (different AZ, same region)
  • Cross-Region

Replication from the main (source) database to the replicas is asynchronous — meaning replicas are eventually consistent. If your app reads from a replica right after a write, it might read slightly stale data because replication hasn't caught up yet.

A replica can also be promoted to become its own standalone database (it then leaves the replication relationship permanently).

One main database taking reads/writes, replicating asynchronously to two read replicas that only serve reads.

Important Read Replicas only accept SELECT statements. You cannot run INSERT, UPDATE, or DELETE on them.

Classic use case: a production app hits the main DB. A new analytics/reporting team wants to run heavy queries on the same data. Instead of pointing them at the production DB (which would slow it down), spin up a Read Replica and point the reporting app there. Production stays fast and unaffected.

Networking cost: replication traffic between the main DB and a replica in a different AZ but same region is free (RDS is a managed service, so AWS absorbs that cross-AZ cost). Replication to a cross-region replica does incur a network fee.

Multi-AZ

Multi-AZ is mainly for Disaster Recovery, not scaling. There's one Master (in AZ A) and one Standby (in AZ B). Replication here is synchronous — a write isn't considered complete until the standby has it too.

Your app connects to a single DNS name. If the Master fails (AZ outage, instance failure, storage failure), RDS automatically fails over to the standby — same DNS name, no code changes needed.

Don't forget Nobody can read from or write to the standby directly. It exists purely as a failover target — it is not for scaling reads.

Multi-AZ: one DNS name, synchronous replication to a standby that only activates on failover.

Good to know You can combine both — set up a Read Replica and make it Multi-AZ for disaster recovery. Common exam question.

Switching a database from Single-AZ to Multi-AZ is a zero-downtime operation — just click "Modify" and enable Multi-AZ. Behind the scenes: RDS takes a snapshot of the main DB, restores it as a new standby, then establishes synchronous replication between the two.

Amazon RDS — Hands-On

Quick walkthrough of creating an RDS database from the console:

  • Engine: chose MySQL for simplicity (Aurora, PostgreSQL, etc. also available)
  • Template: Free Tier → only Single-AZ deployment available. Production template unlocks Multi-AZ instance (2 instances) or Multi-AZ cluster (3 instances)
  • Credentials: self-managed password, or let AWS Secrets Manager manage it (more secure, but costs extra)
  • Instance class: db.t4g.micro / db.t3.micro (free tier eligible)
  • Storage: 20 GB, with the option to enable Storage Auto Scaling up to a max (e.g. 1000 GB)
  • Connectivity: public access = yes (so you can connect from your laptop), new security group created, port 3306 (MySQL default)

Connected using a MySQL client (SQL Electron) with the endpoint, port 3306, username admin, and the initial database name. Ran basic CREATE TABLE / INSERT / SELECT statements — just to prove the connection works (this SQL syntax itself is out of exam scope).

Other things doable straight from the console:

  • Create a Read Replica directly, optionally as Multi-AZ
  • View monitoring metrics: CPU utilization, DB connection count, etc.
  • Take snapshots → restore to a point in time, or migrate a snapshot to a different region
Cleanup steps To delete an RDS instance: Modify → disable Delete/Termination Protection → Apply immediately → then Delete (optionally skip the final snapshot).

Amazon Aurora

Aurora is AWS's own proprietary database engine (not open-source), built to be wire-compatible with PostgreSQL and MySQL — meaning your existing drivers just work.

Because it's cloud-optimized, Aurora claims:

  • 5x performance over MySQL on RDS
  • 3x performance over PostgreSQL on RDS
  • ~20% more expensive than RDS, but more cost-efficient at scale

Storage

Aurora storage auto-grows: starts at 10 GB, scales automatically up to 256 TB. You never manually manage disk sizing.

Every write is stored as 6 copies across 3 AZs. Aurora only needs:

  • 4 out of 6 copies for a write to succeed
  • 3 out of 6 copies for a read to succeed

This means Aurora can lose an entire AZ and keep working. It also self-heals — corrupted data blocks get repaired automatically via peer-to-peer replication in the background, across hundreds of storage volumes (not just one).

Up to 15 read replicas, replication lag typically sub-10ms (faster than MySQL replication). Failover is near-instant — much faster than RDS Multi-AZ failover.

Writer & Reader Endpoints

There's one Master that takes all writes. If it fails, failover happens in under 30 seconds on average, and one of the read replicas gets promoted.

Because the Master can change after a failover, Aurora gives you a writer endpoint — a stable DNS name that always points at whichever instance is currently the master. Similarly, a reader endpoint automatically load-balances connections across all read replicas (load balancing happens at the connection level, not per-statement).

Writer endpoint always tracks the current master; reader endpoint load-balances across all replicas. All instances share one auto-expanding storage volume.

Other Aurora features: automatic failover, backups, isolation/security, one-click ("push-button") scaling, zero-downtime patching, advanced monitoring, and Backtrack — rewind the database to any point in time without relying on backups (and you can change your mind about the target time and rewind again).

Amazon Aurora — Hands-On

Key options seen while creating an Aurora cluster:

  • Engine: MySQL-compatible or PostgreSQL-compatible
  • Storage config: Aurora Standard (cost-effective) vs I/O-Optimized (for high read/write workloads)
  • Serverless v2: instead of picking an instance type, you set a min/max ACU (Aurora Capacity Unit) range and it scales automatically between them
  • Availability: option to add an Aurora Replica (reader) in a different AZ for HA + fast failover + read scaling
  • Local write forwarding: writes sent to a reader get auto-forwarded to the writer instance — simplifies connection management
  • Authentication: username/password, IAM-based, or Kerberos-based

After creation you get a regional cluster with separate writer and reader instances in different AZs, each with its own endpoint, plus the cluster-level writer/reader endpoints your app should actually use.

Extra console features worth knowing:

  • Add more readers to scale read capacity
  • Create a cross-region read replica
  • Restore to a point in time
  • Replica auto-scaling policy — e.g. "keep average replica utilization at 60%; scale between 1 and 15 replicas"
  • Global database feature — add other AWS regions (requires a compatible instance size, e.g. "large")
Cleanup steps Delete order matters: delete the reader instance first, then the writer instance, and only then can you delete the whole cluster.

RDS Proxy

RDS Proxy sits between your application and your RDS/Aurora database and pools and shares connections. Instead of every app instance opening its own connection to the database, they all connect to the proxy, and the proxy maintains a smaller pool of actual connections to the database.

Analogy Think of RDS Proxy like a receptionist for the database. Instead of a hundred visitors all trying to squeeze through one office door at once, they check in with the receptionist, who manages a handful of open doors efficiently.

Why it matters:

  • Reduces stress on DB resources (CPU/RAM) by minimizing open connections and timeouts
  • Fully serverless, auto-scaling, and highly available across multiple AZs
  • Reduces failover time by up to 66% — the proxy absorbs the failover, so your app just keeps talking to the proxy without needing to handle reconnect logic itself
  • Supports MySQL, PostgreSQL, MariaDB, Microsoft SQL Server, and Aurora (MySQL/PostgreSQL)
  • No application code changes needed — just point your connection string at the proxy instead of the DB
  • Can enforce IAM authentication, with credentials stored securely in AWS Secrets Manager
  • RDS Proxy is never publicly accessible — only reachable from within your VPC

Many short-lived clients (e.g. Lambda functions) connect to RDS Proxy, which pools those connections down into far fewer actual database connections.

Common exam scenario Lambda functions can spin up in huge numbers and open a connection each time — this floods a database with connections. RDS Proxy is the standard fix: Lambdas connect to the proxy, and the proxy pools those into a manageable number of real DB connections.

ElastiCache Overview

Just like RDS gives you managed relational databases, ElastiCache gives you managed Redis or Memcached — in-memory data stores with very high performance and low latency.

Main use cases:

  • Reduce database load for read-heavy workloads by caching common query results
  • Make applications stateless by storing user session data in the cache instead of on a specific server

AWS handles the same managed-service benefits as RDS: OS patching, setup, monitoring, failure recovery, backups.

Important ElastiCache is not a switch you just flip on. It requires real application code changes — your app needs logic to check the cache before/after hitting the database.

Caching architecture (query caching)

App checks ElastiCache first. If the data's there → cache hit, return it directly (database untouched). If not → cache miss, read from the database, then write the result into the cache so the next request for the same data is a hit.

Because data now lives in two places, you need a cache invalidation strategy so stale data doesn't get served — this is the fundamentally hard part of caching.

Session storage architecture

User logs in → session data gets written to ElastiCache. If the user's next request lands on a different server/instance of your app, that instance can still fetch the session from ElastiCache — so the user stays logged in. This is what "stateless application" means in practice.

Redis vs Memcached

RedisMemcached

Analogy Redis is like a small team with a backup member who has copies of everything — if the lead is out, the backup steps in with no data loss. Memcached is like splitting the work across many independent desks — fast and simple, but if one desk's drawer gets knocked over, that portion of the data is just gone.
Exam note The exam rarely asks you to choose Redis vs Memcached directly, but it's useful reference knowledge for use-case-based questions.

ElastiCache — Hands-On

Creating a cluster from the console:

  • Engine choice: Valkey (recommended Redis replacement), Memcached, or Redis OSS
  • Deployment option: serverless, or node-based cluster
  • Cluster mode disabled: single shard, one primary node, up to 5 read replicas. Cluster mode enabled: multiple shards across multiple servers
  • Multi-AZ: for HA / automatic failover of the primary node (costs more)
  • Subnet group: defines which subnets the cache can run in
  • Encryption: at-rest (needs a KMS key) and in-transit; enabling in-transit unlocks access control via Redis AUTH token or a user group ACL
  • Security groups control which applications can reach the cluster over the network
  • Backups, maintenance windows, and log export to CloudWatch — same idea as RDS

Once created, you get a primary endpoint (and a reader endpoint if replicas exist) that your application code connects to.

Cleanup Action → Delete on the cluster, skip the backup, type the cluster name to confirm.

ElastiCache Strategies

Before caching anything, ask:

  1. Is it safe to cache? Some data can tolerate being slightly stale (eventually consistent); some can't.
  2. Is caching effective for this data? Good fit: data that changes slowly and only a few keys are frequently requested. Bad fit: data that changes very fast and you need the full key space every time.
  3. Is the data structured correctly for caching? e.g. key-value pairs or pre-computed aggregations work well.
  4. Which caching design pattern fits best? — this is the main one, covered below.

Lazy Loading (a.k.a. Cache-Aside, Lazy Population)

All three names mean the same strategy: only cache data that was actually requested.

On a cache miss: read from RDS, then write the result into ElastiCache so the next identical request is a hit.

Pros: only requested data gets cached (efficient), and if the cache is wiped it's not fatal — just slower until it "warms up" again (every read has to hit RDS and get re-cached).

Cons: a cache miss costs 3 network round trips (app→cache miss, app→DB read, app→cache write) — worse latency than going straight to the DB. Also risk of stale data if RDS is updated but the cache isn't.

Pseudocode:

def get_user(user_id):
    record = cache.get(user_id)
    if record is None:
        # Cache miss
        record = db.query("SELECT * FROM users WHERE id = ?", user_id)
        cache.set(user_id, record)
    return record

Write Through

Update (or add to) the cache at the same time you update the database.

Pros: data in the cache is never stale — every RDS write is immediately mirrored to the cache. Users generally expect writes to take a little longer than reads anyway, so the extra cost is well-hidden.

Cons: a write penalty — each write now needs 2 calls (DB + cache) instead of 1. Also, data is missing from the cache until it's actually written — so Write Through is usually combined with Lazy Loading to also handle reads. That combination can lead to cache churn: lots of data ends up cached that may never actually get read (a problem if your cache is small).

Pseudocode:

def save_user(user_id, values):
    record = db.query("UPDATE users SET ... WHERE id = ?", user_id, values)
    cache.set(user_id, record)
    return record

Cache Eviction & TTL

Caches have limited size, so data eventually gets evicted:

  • Explicit deletion
  • LRU (Least Recently Used) — evicted when memory is full and the item hasn't been touched recently
  • TTL (Time To Live) — item auto-expires after a set duration (seconds to days depending on the data — leaderboards, comments, activity streams, etc.)

If you're seeing too many evictions, your cache is undersized — scale it up or out.

Practical recommendations Start with Lazy Loading — it's simple and works as a foundation for most read-heavy cases. Add Write Through only as a targeted optimization if staleness is a real problem. Use TTL almost everywhere except when Write Through is already keeping data fresh. And only cache data where staleness is acceptable — e.g. user profiles and blog content, not pricing or bank balances.
Worth remembering "There are two hard things in Computer Science: cache invalidation, and naming things." Caching sounds simple but gets genuinely tricky fast.

Amazon MemoryDB for Redis

A Redis-compatible, durable, in-memory database — not just a cache. The key difference from Redis/ElastiCache: Redis is designed as a cache with some durability bolted on; MemoryDB is designed to actually be your database, with a Redis-compatible API.

  • Ultra-fast: over 160 million requests/second
  • Durable via a Multi-AZ transaction log
  • Scales from tens of GB up to hundreds of TB

Use cases: web/mobile apps, online gaming, media streaming — anywhere you have lots of microservices needing fast, Redis-compatible, durable data access.

Analogy ElastiCache Redis is a helpful sticky note next to your real filing cabinet (RDS). MemoryDB is the filing cabinet itself — just built to be blazingly fast, using the same Redis "language" you already know.

Cheat Sheet

Key facts to remember

  • RDS engines: PostgreSQL, MySQL, MariaDB, Oracle, SQL Server, IBM DB2, Aurora
  • No SSH into RDS/Aurora (managed service) — except RDS Custom
  • Storage Auto Scaling: triggers at <10% free, lasting >5 min, with 6h cooldown since last change
  • Read Replicas: up to 15, asynchronous, eventually consistent, SELECT-only, free replication within-region across AZs, paid cross-region
  • Multi-AZ: synchronous, one DNS name, automatic failover, standby is not for reads/writes, zero-downtime to enable
  • Aurora: 6 copies across 3 AZs, needs 4/6 for writes and 3/6 for reads, up to 15 replicas, sub-10ms replica lag, storage auto-grows to 256 TB, has writer + reader endpoints, Backtrack for point-in-time rewind
  • RDS Proxy: pools connections, cuts failover time up to 66%, enforces IAM auth, VPC-only (never public), no app code changes needed
  • ElastiCache: Redis (HA, replicas, durability, sorted sets) vs Memcached (sharding, multi-threaded, no HA except serverless)
  • Lazy Loading = cache-aside = only cache what's requested; Write Through = cache never stale but write penalty; combine both for reads + freshness
  • MemoryDB for Redis = a full durable database with a Redis API, not just a cache

Mental model

RDS takes the operational pain out of running a relational database — patching, backups, scaling — and gives you two separate levers: Read Replicas for scaling reads, and Multi-AZ for surviving failures. Aurora is RDS's more powerful, cloud-native cousin that bakes in fast self-healing storage and near-instant failover by design. RDS Proxy sits in front of any of these to keep connection counts sane. ElastiCache and MemoryDB then add a fast in-memory layer in front of (or instead of) your database — ElastiCache as a bolt-on cache your app has to explicitly manage (with real tradeoffs between speed and staleness), and MemoryDB as a durable, Redis-speaking database in its own right.
