Amazon RDS Overview

RDS stands for Relational Database Service. It is AWS's managed database service for traditional SQL databases. "Managed" means AWS takes care of routine operational tasks so you can focus on building your application.

Database engines supported by RDS (memorize this list for the AWS exam):

  • PostgreSQL
  • MySQL
  • MariaDB
  • Oracle
  • Microsoft SQL Server
  • IBM DB2
  • Aurora — AWS's proprietary database engine (covered in detail below)

Why use RDS instead of manually installing a database on an EC2 instance? RDS includes these automated features out-of-the-box:

  • Automated database setup and OS security patching
  • Continuous automated backups with Point-in-Time Restore (rollback data to an exact second in time)
  • Built-in CloudWatch monitoring dashboards
  • Read Replicas (to scale read query performance)
  • Multi-AZ deployment (for high availability and disaster recovery)
  • Maintenance windows for scheduled software upgrades
  • Vertical scaling (upgrading CPU/RAM size) and horizontal scaling (adding read replicas)
  • Storage backed by AWS EBS volumes
Important Limitation You cannot SSH into an RDS database server. Because RDS is a managed service, AWS maintains full ownership of the underlying OS and server infrastructure.

RDS Storage Auto Scaling

When creating a database, you assign an initial storage size (e.g. 20 GB). If your application writes heavy data and approaches storage limits, RDS automatically expands your database storage without causing downtime.

Storage Auto Scaling triggers when all three conditions are met:

  • Free storage space drops below 10% of total allocated storage.
  • The low-storage condition persists for more than 5 minutes.
  • At least 6 hours have passed since the previous storage expansion.

You can define a Maximum Storage Threshold to control cost limits. Supported across all RDS engines.

Real-World Analogy RDS Storage Auto Scaling is like a mobile data plan that automatically tops up your data allowance when you reach 90% usage — saving you from manual intervention or service disconnection.

RDS Read Replicas vs Multi-AZ

AWS Exam Core Concept Read Replicas = Scaling read performance. Multi-AZ = High availability and disaster recovery. Never confuse these two features on the exam!

Read Replicas

Read Replicas help scale heavy read query traffic. You can create up to 15 Read Replicas for a master database across:

  • The same Availability Zone
  • Different Availability Zones within the same Region (Cross-AZ)
  • Different AWS Regions (Cross-Region)

Data replication from the master database to replicas is asynchronous — meaning replicas are eventually consistent. A read query made to a replica immediately after a write to the master might briefly return slightly old data until replication catches up.

A Read Replica can also be promoted to a standalone master database (which breaks the replication link permanently).

Master database handles read/write queries and replicates asynchronously to two read-only replicas.

Important Rule Read Replicas accept SELECT queries only. You cannot execute INSERT, UPDATE, or DELETE statements directly on a Read Replica.

Primary Use Case: Production application users hit the master database for normal operations. An analytics team wants to run heavy reporting queries on the same dataset. Point the reporting queries at a Read Replica so production performance remains fast and unaffected.

Network Data Transfer Costs: Data replication between a master DB and a replica in a different AZ within the same Region is free of charge (AWS covers cross-AZ data fees for RDS). Replication to a Cross-Region replica incurs standard AWS inter-region network charges.

Multi-AZ Deployment

Multi-AZ is designed for High Availability and Disaster Recovery. AWS provisions one Primary Master database in AZ-A and a Standby replica in AZ-B. Replication between Primary and Standby is synchronous — a write operation is confirmed only after both databases store it safely.

Your application connects using a single database DNS address. If the Primary Master fails (due to data center outage, instance failure, or storage issues), RDS automatically switches (fails over) connection routing to the Standby — requiring zero application code changes.

Important Rule Applications cannot read from or write to the Standby database directly. The Standby exists strictly as an automatic failover target — it does NOT scale read traffic.

Multi-AZ Architecture: Single database DNS address with synchronous replication to a standby database activated only on failover.

Best Practice You can combine both features — set up a Read Replica and configure it as Multi-AZ for high availability. Common exam scenario.

Modifying a database from Single-AZ to Multi-AZ is a zero-downtime operation. RDS takes a snapshot of the primary database, restores it in a secondary AZ, and establishes synchronous replication.

Amazon RDS — Hands-On

Step-by-step summary of launching an RDS database from the AWS Console:

  • Engine Choice: MySQL selected for simplicity (PostgreSQL, MariaDB, Oracle, SQL Server available).
  • Deployment Template: Free Tier (Single-AZ). Production template unlocks Multi-AZ Instance (2 nodes) or Multi-AZ Cluster (3 nodes).
  • Credentials: Self-managed master password or integration with AWS Secrets Manager.
  • Instance Class: db.t4g.micro / db.t3.micro (Free Tier eligible).
  • Storage: 20 GB allocated storage with Storage Auto Scaling enabled up to 1,000 GB maximum limit.
  • Connectivity: Public accessibility enabled (allows direct client connection), Security Group configured to allow port 3306 (MySQL default port).

Connected using a SQL client (SQL Electron) via database Endpoint URL, Port 3306, Username admin, and master password. Verified basic table creation (CREATE TABLE), data insertion (INSERT), and retrieval (SELECT).

Console Operations Available:

  • Create Read Replicas directly (Single-AZ or Multi-AZ).
  • Monitor CPU utilization, memory, and active DB connections via CloudWatch metrics.
  • Take manual DB Snapshots, perform Point-in-Time Restores, or copy snapshots across AWS Regions.
Deletion Steps To safely delete an RDS instance: Modify instance → Disable Deletion Protection → Apply Immediately → Select Delete (optionally skip final snapshot creation).

Amazon Aurora

Amazon Aurora is AWS's cloud-native relational database engine, engineered to be fully compatible with PostgreSQL and MySQL. Existing drivers and application code work without modification.

Cloud optimization benefits claimed by AWS:

  • 5x performance throughput over standard MySQL on RDS
  • 3x performance throughput over standard PostgreSQL on RDS
  • ~20% higher cost than standard RDS, but significantly more cost-efficient at scale

Storage Architecture

Aurora storage grows automatically in 10 GB increments up to 256 TB. You never need to manage disk allocation or volume resizing manually.

Every write operation is replicated automatically into 6 copies across 3 Availability Zones. Aurora quorum rules:

  • 4 out of 6 copies required for a successful write operation
  • 3 out of 6 copies required for a successful read operation

Aurora easily survives the complete loss of an Availability Zone. It also features self-healing storage — damaged disk blocks are repaired automatically in the background via peer-to-peer storage replication.

Supports up to 15 Read Replicas with sub-10ms replication lag. Failover is automated and completes in under 30 seconds.

Writer & Reader Endpoints

An Aurora cluster contains one Master Writer instance for write operations. If the Master fails, Aurora promotes one of the Read Replicas automatically.

To keep connections simple after failover, Aurora provides a Writer Endpoint (a static DNS name pointing to the active master) and a Reader Endpoint (a static DNS name load-balancing read connections across all active read replicas at the connection level).

Writer Endpoint tracks the active Master; Reader Endpoint load-balances queries across replicas. All instances share a unified, self-scaling storage layer.

Additional Aurora Features: Automated failover, continuous backups, zero-downtime engine patching, custom endpoint creation, and Backtrack (rewind database data to a past timestamp instantly without restoring from backups).

Amazon Aurora — Hands-On

Key configuration choices during Aurora cluster deployment:

  • Engine Choice: MySQL-compatible or PostgreSQL-compatible.
  • Storage Class: Aurora Standard (cost-effective) vs I/O-Optimized (for heavy read/write workloads).
  • Serverless v2: Automatically scales database capacity units (ACUs) up or down based on real-time traffic spikes.
  • Availability: Add Aurora Replicas across different Availability Zones for instant failover and read scaling.
  • Local Write Forwarding: Write operations sent to reader instances automatically forward to the writer instance.
  • Authentication: Standard password, IAM database authentication, or Kerberos.

Deploying provisions a regional cluster with separate writer and reader endpoints for application connection strings.

Important Cluster Features:

  • Auto-scaling policies for read replicas (e.g., target 60% CPU utilization, scale from 1 to 15 replicas).
  • Cross-Region Read Replicas and Aurora Global Database for low-latency global reads and cross-region disaster recovery.
  • Point-in-Time Restores and snapshot exports.
Proper Deletion Sequence To delete an Aurora Cluster: Delete reader instances first → Delete the master writer instance → Delete the overall Cluster container.

RDS Proxy

RDS Proxy is a fully managed, highly available database proxy that sits between your applications and your RDS/Aurora database to pool and share database connections. Instead of every client opening individual connections, they connect to RDS Proxy, which reuses a smaller pool of stable database connections.

Real-World Analogy RDS Proxy acts like an office receptionist. Instead of 100 visitors trying to squeeze into an executive room at once, they check in with the receptionist, who coordinates entrance through a few open doors efficiently.

Key Benefits:

  • Prevents database CPU/RAM exhaustion from connection flooding and frequent timeouts.
  • Fully serverless, auto-scaling, and deployed across multiple Availability Zones.
  • Reduces database failover switch time by up to 66% because RDS Proxy handles connection failovers without dropping client sessions.
  • Supports MySQL, PostgreSQL, MariaDB, Microsoft SQL Server, and Aurora engines.
  • Requires zero application code changes — update your connection string to point at the proxy endpoint.
  • Enforces IAM Authentication securely with credentials saved in AWS Secrets Manager.
  • Strictly private: RDS Proxy is never publicly accessible over the internet; reachable only within your VPC.

AWS Lambda functions scale rapidly and open hundreds of connections; RDS Proxy consolidates them into a small pool of database connections.

Classic AWS Exam Scenario Serverless AWS Lambda functions scale instantly and risk overwhelming database connection limits. Solution: Route Lambda database traffic through RDS Proxy to manage connection pooling safely.

ElastiCache Overview

While RDS manages relational SQL databases on disk, ElastiCache provides managed Redis or Memcached in-memory data stores that deliver ultra-high performance and sub-millisecond response times.

Primary Use Cases:

  • Reduce database load: Cache frequent read queries in memory so backend databases perform fewer expensive disk operations.
  • Stateless application architecture: Store user session data (like shopping cart or login state) in ElastiCache so any web server can handle subsequent user requests.

Managed Benefits: Automated hardware setup, security patching, monitoring, failure recovery, and automated backups.

Code Integration Requirement ElastiCache is not an automatic database toggle. Using ElastiCache requires application code changes — your code must explicitly query the cache before falling back to the database.

Query Caching Pattern

Application queries ElastiCache first. If data exists → Cache Hit (return data immediately, database untouched). If data is missing → Cache Miss (read data from relational database, then store it in ElastiCache so future queries hit the cache).

Because data lives in two places, you must implement a cache invalidation strategy to prevent serving outdated (stale) data.

Session Storage Pattern

User logs in → session token stored in ElastiCache. When the user's next request hits a different application instance, that instance retrieves session data from ElastiCache instantly. This makes application servers completely stateless.

Real-World Analogy Redis is like a working group with a dedicated assistant making duplicate copies — if the manager is absent, the assistant steps in without losing data. Memcached is like splitting files across separate drawers — fast, but if a drawer breaks, that specific partition of data disappears.

ElastiCache — Hands-On

Creating an ElastiCache Cluster from the AWS Console:

  • Engine Options: Valkey (AWS recommended Redis replacement), Memcached, or Redis OSS.
  • Deployment Type: Serverless or Node-based cluster.
  • Cluster Mode: Disabled (single primary node, up to 5 read replicas) vs Enabled (multi-shard distribution).
  • Multi-AZ: Enable automatic failover for high availability.
  • Subnet Group: Specifies private VPC subnets hosting cache nodes.
  • Security & Encryption: Encryption at-rest (KMS key) and in-transit; unlocks Redis AUTH token authentication.
  • Security Groups: Controls network access ports (default Redis port: 6379, Memcached port: 11211).

Deployment yields primary and reader endpoint URLs for integration into application code.

Cleanup Steps Select cluster → Actions → Delete → Skip final snapshot → Type cluster name to confirm deletion.

ElastiCache Strategies

Four evaluation questions before implementing caching:

  1. Is data safe to cache? Suitable for data tolerant of brief eventual consistency; avoid caching data requiring real-time accuracy (e.g. bank balances).
  2. Is caching effective? Highly effective for slow-changing data with high read frequency. Poor fit for rapidly changing datasets.
  3. Is data structured properly? Formatted as key-value pairs or pre-computed summaries.
  4. Which caching pattern fits? (Lazy Loading vs Write Through).

Lazy Loading (Cache-Aside Pattern)

Strategy: Cache data only when explicitly requested by an application user.

On a cache miss: Read from RDS database, then store result in ElastiCache for future queries.

Pros: Efficient cache memory usage (only requested data is cached). Cache failures are not fatal — requests fall back to database.

Cons: Cache misses incur 3 network hops (App→Cache Miss → App→DB Read → App→Cache Write). Risk of serving stale data if database updates occur without cache eviction.

Pseudocode Implementation:

def get_user(user_id):
    record = cache.get(user_id)
    if record is None:
        # Cache miss
        record = db.query("SELECT * FROM users WHERE id = ?", user_id)
        cache.set(user_id, record)
    return record

Write Through Pattern

Strategy: Update or insert data into the cache simultaneously whenever a database write occurs.

Pros: Data in cache is never stale. Write latency overhead is acceptable to users who expect writes to take time.

Cons: Write latency penalty (2 write operations per update: DB + Cache). Unrequested data fills cache memory (cache churn).

Pseudocode Implementation:

def save_user(user_id, values):
    record = db.query("UPDATE users SET ... WHERE id = ?", user_id, values)
    cache.set(user_id, record)
    return record

Cache Eviction Policies & TTL

Because cache memory is limited, old data is evicted using:

  • Explicit deletion via application code.
  • LRU (Least Recently Used): Evicts items that haven't been accessed recently when memory fills up.
  • TTL (Time To Live): Items auto-expire after a set duration (e.g. 5 minutes or 1 hour).

Amazon MemoryDB for Redis

Amazon MemoryDB for Redis is a Redis-compatible, durable in-memory database designed to serve as a primary database (not just an ephemeral cache).

  • Ultra-fast performance: Handles over 160 million requests per second.
  • High durability: Uses a Multi-AZ transactional log for zero data loss guarantees.
  • Seamless scaling: Scales from gigabytes to hundreds of terabytes of memory.
Real-World Analogy ElastiCache Redis is like keeping a quick sticky note next to your main file cabinet (RDS). MemoryDB is the main file cabinet itself — engineered to be blazingly fast using the exact same Redis commands.

Cheat Sheet

Key Facts to Remember

  • RDS Engines: PostgreSQL, MySQL, MariaDB, Oracle, SQL Server, IBM DB2, Aurora.
  • No SSH access to RDS/Aurora servers (managed service).
  • Storage Auto Scaling: Triggers when free storage <10%, low storage duration >5 min, and >6 hours since last change.
  • Read Replicas: Up to 15, asynchronous replication, eventually consistent, SELECT queries only, free within-region cross-AZ data replication.
  • Multi-AZ: Synchronous replication, single DNS address, automatic failover, standby database is not accessible for read/write queries.
  • Aurora: Replicates 6 copies across 3 AZs (requires 4/6 for writes, 3/6 for reads), up to 15 read replicas with sub-10ms lag, auto-expanding storage up to 256 TB, features Writer and Reader Endpoints, includes Backtrack for instant rewind.
  • RDS Proxy: Pools database connections, cuts failover time by up to 66%, enforces IAM authentication, VPC-only private access.
  • ElastiCache: Redis (high availability, replicas, disk persistence, data structures) vs Memcached (multi-threaded, pure key-value, no HA).
  • Lazy Loading (Cache-Aside): Caches only requested data. Write Through: Keeps cache fresh on every DB write.
  • MemoryDB for Redis: A fully durable primary database with a Redis API.
