1 CDK Overview

AWS CDK (Cloud Development Kit) lets you define cloud infrastructure using a real programming language — JavaScript/TypeScript, Python, Java, or .NET — instead of YAML/JSON.

CDK code compiles down to a CloudFormation template, which is what actually gets deployed — CDK is really a code-first way of authoring CloudFormation.

  • You define constructs (high-level components) — e.g. a VPC, an ECS cluster, an ALB-fronted Fargate service — as real code with real objects and parameters.
  • Because it's real code, it's type-safe: if it doesn't compile, the template can't even be generated — catching mistakes far earlier than a YAML typo would in raw CloudFormation.
  • Lets you deploy infrastructure and application runtime code together — great for Lambda functions and Docker containers on ECS/EKS.

Example app built in this section: an S3 bucket that triggers a Lambda function on upload, which calls Amazon Rekognition to analyze the image and saves the results to DynamoDB — all defined in one CDK script.

2 CDK — Hands On

  1. Install the CDK library (npm install aws-cdk-lib), then cdk init app --language javascript to scaffold a new app.
  2. The main logic lives in lib/<app>-stack.js — imports CDK constructs (S3, IAM, Lambda, DynamoDB), then defines resources as plain code: an S3 bucket (with a removal policy), an IAM role (with addToPolicy), a DynamoDB table, and a Lambda function wired to both via environment variables and an S3 event source.
  3. Convenience methods like bucket.grantReadWrite(function) replace hand-writing the equivalent IAM policy JSON.
  4. The actual Lambda code (e.g. index.py) lives separately and is referenced by the construct.
Don't forget Run cdk bootstrap once per account/region before your first deploy in a new environment — it provisions a support stack (S3 bucket, IAM roles) that CDK needs to function.
  1. cdk synth — generates and previews the full CloudFormation template (S3 bucket, notifications, Lambda function, IAM role, etc.).
  2. cdk deploy — actually deploys that template as a real CloudFormation stack.

Testing it: uploading an image to the S3 bucket triggers the Lambda function, which calls Rekognition and writes detected labels (e.g. "penguin," "bird," "person") into the DynamoDB table — visible immediately by exploring the table's items.

Cleanup Empty the S3 bucket first (CDK-managed buckets with a "destroy" removal policy still need to be empty), then run cdk destroy to tear down the whole stack.

3 CDK Constructs

A construct encapsulates everything CDK needs to produce part of the final CloudFormation stack — anywhere from a single resource to a whole group of related ones. They come from the Construct Library (built into CDK, covering every AWS resource) or the Construct Hub (AWS + third-party + open-source community constructs).

Each layer trades away manual control for convenience — L1 mirrors CloudFormation exactly, L2 adds sane defaults and helper methods, L3 hands you entire pre-wired architectures (like an ALB correctly connected to a Fargate service).

Exam point Layer 1 constructs are recognizable by their Cfn prefix (e.g. CfnBucket) — useful if migrating an existing CloudFormation template into CDK resource-by-resource.

4 CDK Commands & Bootstrapping

CommandPurpose
cdk initInitialize a new app from a template (choose language: Python, JavaScript, etc.)
cdk synthSynthesize and print the generated CloudFormation template
cdk bootstrapProvision the resources CDK itself needs, once per account+region
cdk deployDeploy the stack
cdk diffCompare your local CDK code against what's actually deployed
cdk destroyTear down the stack

Bootstrapping

An environment in CDK = an account + region combination. Before deploying to a new environment, you must run:

cdk bootstrap aws://ACCOUNT_ID/REGION

This creates a CDKToolkit CloudFormation stack containing an S3 bucket and IAM role(s) that CDK deployments depend on.

Don't forget Skipping bootstrap in a new environment causes a deploy failure like "policy contains a statement with one or more invalid principal" — because the required IAM role from the bootstrap stack doesn't exist yet.

5 CDK Unit Testing

Because CDK infrastructure is just code, you can test it like any other code — using the CDK assertions module alongside familiar test frameworks (Jest for JavaScript, Pytest for Python).

Test typeWhat it checks
Fine-grained assertionSpecific resources have specific properties (e.g. "this Lambda has runtime nodejs14.x," "this SNS topic has exactly one subscription")
Snapshot testThe generated CloudFormation template matches a previously stored baseline template
MethodUse when
Template.fromStack(myStack)Testing a stack defined within your own CDK app
Template.fromString(myString)Testing an external CloudFormation template not defined in CDK
Exam point Remember these two entry points by name — fromStack vs fromString — as this is a recurring exam detail.

✓ Cheat Sheet

Key facts to remember

  • CDK = define infrastructure in a real language (TypeScript, Python, Java, .NET); it compiles down to CloudFormation via cdk synth.
  • SAM = serverless-focused, declarative YAML; CDK = general-purpose, code-first, superset of CloudFormation. Both ultimately generate CloudFormation, and can be used together (cdk synth + sam local invoke).
  • Three construct layers: L1 (CfnX, 1:1 with CloudFormation), L2 (sane defaults + helper methods), L3 (whole pre-wired architecture patterns).
  • Core commands: cdk init → cdk bootstrap (once per account/region) → cdk synth → cdk deploy; also cdk diff and cdk destroy.
  • Bootstrapping creates a CDKToolkit stack (S3 bucket + IAM roles) required before any deploy in a new account/region combo.
  • Unit testing uses the CDK assertions module with Jest/Pytest; test entry points are Template.fromStack() (in-app) and Template.fromString() (external template); tests are either fine-grained assertions or snapshot comparisons.

Decision guide

NeedUse
Building a serverless app (Lambda/API Gateway/DynamoDB) quicklySAM
Building anything else, or want type-safe infra-as-codeCDK
Migrate an existing CloudFormation template piece by pieceCDK Layer 1 (CfnX) constructs
Get sensible defaults without losing controlCDK Layer 2 constructs
Stand up a whole common architecture (ALB + Fargate, REST API) fastCDK Layer 3 patterns
Verify your infrastructure code before deployingCDK assertions (fine-grained or snapshot tests)

Mental model

CDK is CloudFormation with the "declarative YAML" straightjacket removed: you get real variables, loops, functions, and type-checking, and the framework compiles all of it down into the same CloudFormation templates you'd otherwise write by hand. The three construct layers are really a dial between control and convenience — go as low-level (L1) or high-level (L3) as the task demands — and because it's all just code, you can test it, version it, and reason about it exactly like the rest of your application.
