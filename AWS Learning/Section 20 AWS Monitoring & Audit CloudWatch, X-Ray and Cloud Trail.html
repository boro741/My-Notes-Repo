1 Monitoring Overview in AWS

Users don't care how you deployed your app — they only care that it works: low latency, no outages, no need to call IT to complain. The goal of monitoring is to catch and fix problems before your users do, understand performance/cost trends, and learn from what happened.

Three complementary tools: CloudWatch watches health, X-Ray traces individual requests through your architecture, and CloudTrail audits who did what.

2 CloudWatch Metrics

  • Every AWS service provides metrics automatically (e.g. CPU Utilization, NetworkIn) — the name usually tells you what it measures.
  • Metrics belong to namespaces, and have dimensions (attributes like instance ID, environment) — up to 30 dimensions per metric.
  • Metrics have timestamps and can be visualized on CloudWatch Dashboards (line, stacked area, number, pie chart, etc.), filtered by time range, exported as CSV, or shared.

EC2 monitoring granularity

ModeFrequencyCost
DefaultEvery 5 minutesFree
Detailed monitoringEvery 1 minuteAdditional cost
Don't forget Even with detailed monitoring, memory (RAM) usage is not pushed by default — it must be sent as a custom metric.

3 CloudWatch Custom Metrics

Push your own metrics (e.g. RAM usage, disk usage, logged-in users) using the PutMetricData API call.

  • Add dimensions (e.g. InstanceId, Environment) as you like.
  • Resolution: standard (push every 60 seconds) or high-resolution (every 1, 5, 10, or 30 seconds), set via the StorageResolution parameter.
Exam point You can push a metric with a timestamp up to 2 weeks in the past or 2 hours in the future — CloudWatch accepts it without error. Make sure your EC2 instance's clock is properly synced if you want accurate timestamps.

The CloudWatch Unified Agent uses this same PutMetricData API under the hood to push metrics regularly from your servers.

4 CloudWatch Logs

The place to store application logs in AWS.

A log group (e.g. one per application) contains multiple log streams (e.g. one per instance/container/log file).

  • Set a retention policy: never expire, or 1 day up to 10 years.
  • Encrypted by default; optional custom KMS key.
  • Export destinations: batch to S3, or stream to Kinesis Data Streams/Firehose, Lambda, OpenSearch.

Who sends logs here

CloudWatch Unified Agent (the old CloudWatch Logs Agent is deprecated), Elastic Beanstalk, ECS (from containers), Lambda (from functions), VPC Flow Logs, API Gateway, CloudTrail (filtered), and Route 53 (DNS query logs).

CloudWatch Logs Insights

A query engine (its own query language) for searching and analyzing log data — auto-detects fields, supports filtering, aggregate stats, sorting, saved queries, and dashboards. Can query multiple log groups across accounts at once.

Important Logs Insights is a query engine, not real-time — it only searches historical data at the moment you run a query.

Exporting logs

MethodNatureUse for
CreateExportTask → S3Batch (can take up to 12 hours)Bulk archival
Subscription filter → Kinesis Data Streams/Firehose/LambdaReal-time / near real-timeLive processing, cross-account/region log aggregation

Cross-account log aggregation works via a destination in the recipient account (representing e.g. a Kinesis stream), a destination access policy allowing the sender account to write, and an IAM role in the recipient account the sender can assume.

5 CloudWatch Logs — Hands On & Live Tail

  • Create a log group with your own name, retention, storage class, and optional KMS key / deletion protection.
  • Log streams populate over time (e.g. one per Lambda invocation batch) — each contains timestamped log lines.
  • You can create a metric filter directly from a log group to turn matching log lines (e.g. containing "info" or "start") into a CloudWatch metric — useful groundwork for alarms.
  • Other log group actions: edit retention, export to S3, start tailing (see logs as they happen), set up subscription filters (OpenSearch, Kinesis, Firehose, Lambda), and run Logs Insights queries.

Live Tail

A real-time log viewer: filter by log group (and optionally log stream), and matching log events appear live as they're written — great for active debugging.

Good to know Live Tail has a free usage allowance (roughly an hour a day) — remember to stop/close your Live Tail session when done to avoid extra cost.

6 CloudWatch Agent & Logs Agent

By default, no logs flow from an EC2 instance to CloudWatch — you need to install and run an agent. This also works on on-premises servers (e.g. VMware).

AgentSends logs?Sends metrics?Notes
CloudWatch Logs Agent (old)YesNoOlder, being phased out
CloudWatch Unified Agent (new)YesYes — much more granular (CPU sub-metrics, disk, RAM, netstat, processes, swap)Configurable centrally via SSM Parameter Store
Good to know Out of the box, EC2 gives you disk, CPU, and network metrics — not memory or swap. For that level of granularity, you need the CloudWatch Unified Agent.

The EC2 instance also needs an IAM role permitting it to send data to CloudWatch Logs.

7 CloudWatch Logs Metric Filters

A metric filter turns a pattern match in your logs (e.g. the word "error", or an IP address) into a real CloudWatch metric — which can then drive an alarm.

A metric filter watches for a pattern in log lines, turns matches into a metric, and an alarm on that metric can notify you (e.g. via SNS).

Don't forget Metric filters are not retroactive — they only count log events that arrive after the filter is created, never historical ones. You can define up to 3 dimensions per metric filter.

8 CloudWatch Alarms

Alarms trigger actions based on a metric crossing a threshold. Three states: OK, INSUFFICIENT_DATA, ALARM. You set an evaluation period (e.g. every 5 minutes, or down to 10/30 seconds for high-resolution custom metrics).

Alarm targets

  • EC2 actions — stop, terminate, reboot, or recover an instance.
  • Auto Scaling actions — scale out or in.
  • SNS notification — which can trigger a Lambda function for custom logic.

Composite Alarms

A single alarm only watches one metric. A Composite Alarm combines multiple underlying alarms with AND/OR logic — great for reducing alarm noise (e.g. only alert if CPU is high and IOPS is high, not either alone).

A composite alarm only fires when its combined condition across multiple underlying alarms is met — much quieter than alerting on either alarm individually.

EC2 status checks & recovery

  • Instance status check — the VM itself.
  • System status check — the underlying host hardware.
  • Attached EBS status check — attached volume health.

An alarm on these can trigger EC2 instance recovery — moves the instance to new hardware while preserving its private/public/elastic IP, metadata, and placement group.

Tip Use the SetAlarmState CLI call to manually force an alarm into the ALARM state for testing — confirms your downstream actions actually work without waiting for a real threshold breach.

9 CloudWatch Synthetics

Synthetics Canary runs a configurable script (Node.js or Python, with a headless Chrome browser) that reproduces what a real customer would do — e.g. visit a product page, add to cart, check out — on a schedule or one-off, so you find problems before your users do.

  • Can check endpoint availability/latency, store load-time data, and take UI screenshots.
  • Blueprints: Heartbeat Monitor, API Canary, Broken Link Checker, Visual Monitoring (compare screenshots to a baseline), Canary Recorder (record your actions, auto-generate the script), GUI Workflow Builder.

Example architecture: Canary detects a failure → triggers a CloudWatch alarm → invokes a Lambda function → Lambda updates a Route 53 record to fail over to a healthy region.

10 Amazon EventBridge

Formerly "CloudWatch Events." Reacts to events happening across AWS (or on a schedule) and routes them to targets.

Sources (AWS services, schedules, CloudTrail-captured API calls) feed events into EventBridge, which filters and routes matching events to a wide range of targets.

  • Event bus types: default (AWS service events), partner (SaaS partners like Zendesk, Datadog, Auth0), custom (your own applications).
  • Events can be archived (indefinite or set retention) and later replayed — great for fixing a bug in a Lambda consumer and re-testing against real past events.
  • Schema Registry infers the JSON shape of events and can generate code for your application to consume them correctly; schemas are versioned.
  • Resource-based policies on an event bus control cross-account/region access — the basis for centralized event aggregation.

Hands-on recap

Create a rule with an event pattern (e.g. react to EC2 Instance State-change Notification where state = shutting-down or terminated) targeting an SNS topic. Or create a schedule (one-time or recurring, cron or rate-based) that invokes a target like a Lambda function every hour.

11 EventBridge Multi-Account Aggregation

To centrally capture events (e.g. EC2 state changes) from multiple AWS accounts into one central account:

Each account's event rule targets the central account's event bus (an event rule's target can be an event bus in another account); a resource policy on the central bus allows those accounts to send events.

  1. Attach a resource-based policy to the central account's event bus, accepting events from the other accounts.
  2. In each source account, define the event pattern and create a rule whose target is the central account's event bus.
  3. On the central bus, create your own rule(s) to react (e.g. SNS notification, Lambda function) once events land there.

12 X-Ray Overview

X-Ray gives a visual, end-to-end analysis of your application — instead of hunting through scattered logs across microservices, you get a service map showing exactly how requests flow and where errors/latency originate.

The service map visually shows every hop a request makes — including which specific downstream dependency is actually causing the error, without digging through raw logs.

Advantages

  • Troubleshoot performance bottlenecks; understand microservice dependencies visually.
  • Pinpoint which service is causing issues; find errors/exceptions per request.
  • Check if you're meeting latency SLAs; identify which service throttles you; see which users are impacted.

Compatible with Lambda, Beanstalk, ECS, ELB, API Gateway, EC2, and any application server (even on-premises).

Concepts

  • Segments — each component handling a request adds its own segment; segments can have subsegments for more granularity.
  • Trace — all segments collected together = an end-to-end view of one request.
  • Sampling — controls how many requests get traced (reduces cost).
  • Security: IAM authorization; KMS encryption at rest.

How to enable it

  1. Instrument your code — import the X-Ray SDK (Java, Python, Go, Node.js, .NET) so it captures AWS SDK calls, HTTP(S) requests, and database calls (MySQL, PostgreSQL, DynamoDB).
  2. Run the X-Ray daemon — a small UDP packet interceptor program (Linux/Windows/Mac). Some services (like Lambda) run it for you automatically.
  3. Your application needs IAM permissions to write to X-Ray.
Don't forget "It works locally but not on EC2" is almost always because the X-Ray daemon isn't running on the EC2 instance (only on your local machine).

13 X-Ray — Hands On

  • The X-Ray console now lives inside the CloudWatch console (Service map and Traces sections).
  • A demo app (ECS-based, using DynamoDB and SNS) was deployed via CloudFormation to generate real traces.
  • The service map visually shows all components and their dependencies — a component in error (e.g. SNS calls failing) is highlighted, e.g. in orange.
  • Clicking a node shows latency graphs, request counts, faults, and response time distribution.
  • Traces can be filtered/queried by node (e.g. only requests touching a specific DynamoDB table) — useful for finding the one slow request among many and drilling into its full breakdown (which calls happened, in what order, how long each took).

14 X-Ray Instrumentation & Concepts

Instrumentation = measuring performance, diagnosing errors, and writing trace data — done by adding the X-Ray SDK to your code (sometimes just a config change, sometimes custom interceptors/filters/handlers/middleware for more control).

TermMeaning
SegmentWhat one component/service sends per request
SubsegmentMore granular detail within a segment
TraceAll segments together = end-to-end view of one request
AnnotationsKey-value pairs that ARE indexed — searchable/filterable
MetadataKey-value pairs that are NOT indexed — not searchable
Exam point Use annotations (not metadata) whenever you need to search or filter traces by that data.

The X-Ray daemon can also be configured to send traces across accounts (assuming an IAM role) — useful for centralized tracing.

15 X-Ray Sampling Rules

Sampling rules control how much data gets sent to X-Ray (and therefore, cost) — without changing your code.

Default sampling rule: guarantee 1 trace per second per service (the reservoir), then sample only 5% of everything above that (the rate).

  • You can create custom rules with your own reservoir/rate, targeting a specific service, HTTP method, and/or URL path (e.g. sample 100% of a specific service's POST requests for deep debugging).
  • Priority ranges 1–9,999 — lower number = higher priority.
Good to know Changing sampling rules in the console takes effect automatically — no need to restart your application or the X-Ray daemon.

17 X-Ray with Beanstalk & ECS

Elastic Beanstalk

  • Beanstalk platforms already include the X-Ray daemon — just flip one setting (Configuration → Monitoring → enable X-Ray daemon), or add an .ebextensions/x-ray-daemon.config file.
  • Your EC2 instance profile still needs the right IAM permissions (Beanstalk's default web-tier role already includes them).
  • Your application code still needs to be instrumented with the X-Ray SDK.

ECS — three patterns

On EC2-backed clusters you can share one daemon per instance or run one per app container (sidecar); on Fargate, sidecar is the only option since there's no shared host to run a daemon on.

  • The daemon container maps container port 2000/UDP.
  • Your app container needs the env var AWS_XRAY_DAEMON_ADDRESS pointing at xray-daemon:2000.
  • The two containers must be linked from a networking standpoint so the app container can resolve the daemon's hostname.

18 AWS Distro for OpenTelemetry

OpenTelemetry is an open-source project providing a single set of APIs/libraries/agents/collectors for distributed traces and metrics. AWS provides its own secure, production-ready distribution of it.

  • Very similar to X-Ray conceptually — auto-instrumented agents collect traces without code changes.
  • Works across EC2, ECS, EKS, Fargate, Lambda, or on-premises apps.
  • Traces/metrics can be sent to multiple destinations simultaneously: X-Ray, CloudWatch, Amazon Managed Service for Prometheus, or partner tools (e.g. Datadog).
Good to know Consider migrating from X-Ray to the AWS Distro for OpenTelemetry if you want to standardize on open-source APIs, or need to send trace data to multiple destinations at once — something X-Ray alone doesn't do.

19 CloudTrail

CloudTrail gives governance, compliance, and audit — a history of every API call made in your account (console, SDK, CLI, other AWS services). Enabled by default.

Every API call is logged by CloudTrail; forward to CloudWatch Logs or S3 to retain it beyond the default 90 days.

Event types

TypeLogged by default?Examples
Management EventsYesIAM AttachRolePolicy, creating a subnet — split into Read (no changes) and Write (modifies resources)
Data EventsNo (high volume)S3 object-level activity (GetObject/PutObject/DeleteObject), Lambda Invoke
CloudTrail Insights EventsNo (opt-in, paid)Detected unusual activity — see below

CloudTrail Insights

Analyzes your normal Management Event activity to build a baseline, then flags anomalies — inaccurate resource provisioning, hitting service limits, bursts of IAM actions, gaps in maintenance activity. Insight events show up in the console and can also trigger an EventBridge event (e.g. for automated alerting).

Important Events are retained in CloudTrail for 90 days by default. For longer retention, log events to S3, then query them with Athena when needed.

Hands-on recap

Terminating an EC2 instance shows up in CloudTrail's Event history as a TerminateInstances API call — with the event source, access key used, region, and full event details.

20 CloudTrail + EventBridge Integration

Every API call logged by CloudTrail also becomes an event in EventBridge — letting you react to specific API calls in near real-time.

  • E.g. get an SNS notification whenever someone calls DynamoDB's DeleteTable, IAM's AssumeRole, or EC2's AuthorizeSecurityGroupIngress (changing inbound security group rules).
Exam point "Alert me whenever <specific API call> happens" → CloudTrail logs the call → EventBridge rule matches it → SNS (or Lambda, etc.) reacts.

✓ Cheat Sheet

Key facts to remember

  • EC2 gives metrics every 5 min by default, every 1 min with detailed monitoring (paid) — RAM/memory is never included, always a custom metric.
  • Custom metrics accept timestamps up to 2 weeks in the past / 2 hours in the future.
  • CloudWatch Logs: log group → log streams → log events; export via batch (S3, up to 12h) or subscription filter (real-time, to Kinesis/Firehose/Lambda).
  • CloudWatch Unified Agent > old Logs Agent — sends both logs and much more granular metrics (RAM, swap, per-process, netstat).
  • Metric filters are not retroactive — only count events after creation; feed into alarms.
  • Alarms: OK / INSUFFICIENT_DATA / ALARM; targets = EC2 action, ASG action, or SNS. Composite alarms combine multiple alarms with AND/OR to cut noise.
  • Synthetics Canary = scripted, scheduled synthetic user journeys to catch issues before customers do.
  • EventBridge (formerly CloudWatch Events): default/partner/custom event buses, archive + replay, Schema Registry, resource policies for cross-account routing.
  • X-Ray needs (1) SDK-instrumented code and (2) a running daemon (or built-in integration, e.g. Lambda) with IAM permission to write.
  • Annotations are indexed/searchable in X-Ray; metadata is not.
  • X-Ray sampling: reservoir (guaranteed rate) + rate (% of the rest) — customizable per service/method/path, no restart needed.
  • ECS + X-Ray: daemon-per-instance or sidecar-per-container on EC2; sidecar-only on Fargate. Needs port 2000/UDP, the AWS_XRAY_DAEMON_ADDRESS env var, and container linking.
  • CloudTrail is on by default; Management Events logged by default, Data Events and Insights are opt-in (high volume/cost). 90-day retention unless exported to S3 (+ Athena for querying).
  • CloudTrail → EventBridge lets you react to specific API calls (e.g. DeleteTable, AssumeRole) in near real-time.

QuestionTool

Mental model

Think of these three services as answering three different questions about your running application. CloudWatch answers "is something wrong, and how bad" — via metrics, logs, and alarms that watch numbers and text over time. X-Ray answers "where exactly, in this web of services, did it go wrong" — by stitching every hop of a single request into one visual trace. CloudTrail answers "who did this, and when" — an immutable record of every API call, which becomes even more powerful when wired into EventBridge to react to specific actions the moment they happen. Together they turn "my manager is calling me at 2am" into "I already knew, and I already know why."
