11IAM Introduction: Users, Groups, Policies

IAM = Identity and Access Management. It's a global service — users and groups you create aren't tied to any one region.

When you first make an AWS account, you get a root user automatically. The only thing the root account should be used for is initial account setup — after that, stop using it and never share it. Instead, create individual IAM users: one IAM user = one physical person in your organization.

Users and Groups

  • Users can be collected into groups to make managing permissions easier (e.g. a "Developers" group).
  • Groups can only contain users — never other groups.
  • A user doesn't have to belong to a group (allowed, but not best practice).
  • A user can belong to multiple groups at once.
Groups only ever contain users. A user (like Charles or David) can belong to more than one group at the same time; Fred belongs to none.

Policies — how permissions actually get granted

Users and groups get permissions through IAM Policies — JSON documents that describe, in a fairly plain way, what a user or group is allowed (or not allowed) to do. You don't need to be a programmer to read one.

Least privilege principle: never give a user more permissions than their job needs. Letting everyone do everything is a security and cost risk — a careless new user could launch expensive resources or break things.

12-13Users & Groups Hands-On + Multi-Session Sign-In

Creating a user

  1. IAM console → Users → create user (e.g. Stephane), give console access.
  2. Choose "create an IAM user" (simpler, and the one the exam cares about) rather than IAM Identity Center.
  3. Set a password — for a real teammate, leave it auto-generated and force a change on first login; for yourself, set a custom one.
  4. For permissions, it's better to create/attach a group (e.g. group admin with the AdministratorAccess policy) than to attach a policy straight to the user.
  5. Tags (optional key/value metadata, e.g. department = engineering) can be attached to most AWS resources, including users.

Once created, the user's permissions page shows AdministratorAccess as inherited via the group, not attached directly — this is exactly why grouping users is the recommended pattern.

Signing in as an IAM user

  • Your account has a Sign-in URL built from your account ID — you can replace the ID with a custom, unique account alias to make the URL friendlier.
  • To be logged in as root and as an IAM user at the same time, open a private/incognito browser window for the second login.
Don't lose access to both logins. If you lose your root account login and your admin login, you're in serious trouble — AWS support can't always bail you out.

Multi-session sign-in (newer console feature)

Instead of juggling private browser windows, you can turn on multi-session support in the console and add multiple sessions (root, different IAM users, even different accounts) as tabs inside the same browser window. Each session is fully isolated — resources created in one session's account don't show up in another's.

14IAM Policies (Structure)

Where a policy is attached changes who it affects:

  • Attached at the group level → applies to every member of that group.
  • Inline policy → attached directly to one specific user, regardless of which group(s) they're in.
  • A user in more than one group (or with an inline policy on top) simply inherits and combines permissions from every source — e.g. Charles gets whatever Developers has, plus whatever Audit Team has.

Anatomy of a policy document

Every IAM policy is Version + optional Id + one or more Statements. Each statement needs Effect, Principal, Action, and Resource to make sense.
Exam tip: know Effect, Principal, Action, and Resource cold — these are the parts that actually decide who can do what to which resource.

15IAM Policies Hands-On

Watching permissions disappear (and come back)

  1. Removed the Stephane user from the admin group → immediately lost admin access.
  2. Refreshing the IAM console then threw Access Denied for iam:ListUsers — proof the permission really was gone.
  3. Fixed it by attaching the managed policy IAMReadOnlyAccess directly to the user — enough to view users/groups again, but not enough to create a group (tried it, got denied) — a clean demo of least-privilege in action.
  4. Re-added the user to the admin group to restore full admin rights, and cleaned up the test group afterwards.

Reading existing managed policies

PolicyWhat its JSON actually says
AdministratorAccessAction: *, Resource: * — allow literally everything on everything
IAMReadOnlyAccessA defined list like Get* and List* on Resource: * — the * groups many related API calls together (e.g. Get* covers GetUser, GetGroup, etc.)

You can also build your own custom policy with the visual editor — pick a service (e.g. IAM), tick specific actions (e.g. ListUsers, GetUser), choose which resources it applies to, and AWS generates the matching JSON for you automatically.

Tip: a user's final permissions can be the sum of several sources at once — one or more groups plus any policy attached directly to the user. Check all of them when troubleshooting "why can/can't this user do X."

16IAM MFA Overview

Two layers of defense for your accounts:

1. Password policy

  • Minimum password length, required character types (uppercase, lowercase, number, non-alphanumeric).
  • Allow (or not) users to change their own password.
  • Force password expiration (e.g. every 90 days).
  • Prevent password reuse.

2. Multi-Factor Authentication (MFA)

MFA combines something you know (your password) with something you have (a physical or virtual device). Even if a password is stolen, the account stays safe because the attacker also needs the physical device.

MFA doesn't replace the password — it adds a second, physical requirement on top of it.

MFA device options

Device typeNotes
Virtual MFA (Google Authenticator)App-based, works with one account at a time per phone
Virtual MFA (Authy)App-based, supports multiple accounts/tokens on a single device — root, IAM users, other accounts, all together
U2F Security Key (e.g. YubiKey by Yubico)Physical key, third-party to AWS; one key can serve multiple root/IAM users
Hardware key fob (e.g. by Gemalto)Physical device, third-party to AWS
GovCloud hardware fob (by SurePassID)Third-party, only for the US government AWS GovCloud

17IAM MFA Hands-On

  1. Password policy: Account Settings → Password Policy → use the IAM default or customize length, character requirements, expiration, and reuse rules.
  2. MFA on the root user: account name → Security Credentials → assign an MFA device.
  3. Name the device (e.g. "my iPhone"), choose Authenticator app as the type.
  4. Scan the QR code shown by AWS using a compatible app (e.g. Twilio Authy).
  5. Enter two consecutive codes from the app — this proves the device is set up correctly and in sync — then click Add MFA.
  6. From then on, logging in needs your password and the current code from the app.
Real risk: students have locked themselves out of their AWS accounts by losing the phone/device tied to their MFA. If you're at real risk of losing your device, don't enable MFA casually — keep the device safe, and remember you can remove an MFA device later if needed.

18Access Keys, CLI & SDK

There are three ways to access AWS:

All three paths ultimately hit the same AWS APIs — they just differ in how you authenticate and where you're calling from.
  • Access keys = Access Key ID (like a username) + Secret Access Key (like a password). Generated per-user from the console, and treated exactly like credentials — never shared, never someone else's.
  • CLI (Command Line Interface) — open-source, lets you manage AWS from a terminal and script/automate tasks; an alternative to the web console. Every command starts with aws.
  • SDK (Software Development Kit) — language-specific libraries (JavaScript, Python, PHP, .NET, Ruby, Java, Go, Node.js, C++, plus Mobile and IoT SDKs) so your own application code can call AWS APIs directly, secured with the same access keys.
Fun fact: the AWS CLI itself is built on top of Boto, the AWS SDK for Python.

19-21AWS CLI Setup (Windows / Mac / Linux)

The Windows and Linux setup lectures were pure screen-recording walkthroughs of AWS's official installers, with no extra narration beyond following AWS's own install guide for each OS.

On macOS: search for "installing the AWS CLI version 2 on macOS," download the .pkg graphical installer, click through Continue → Agree → Install (choose "install for all users"), then open a terminal (e.g. iTerm) and confirm with:

aws --version

A correct install returns something like aws-cli 2.0.10.

General rule regardless of OS: install the official AWS CLI v2 package for your platform, then verify with aws --version before moving on.

22AWS CLI Hands-On

  1. Create access keys: user → Security Credentials → Create access key. AWS will nudge you toward alternatives (CloudShell, IAM Identity Center) first — for learning purposes, confirm you understand the recommendation and create the key anyway.
  2. The secret key is only shown once at creation time — save it immediately.
  3. Configure the CLI locally: aws configure, then enter the Access Key ID, Secret Access Key, a default region (e.g. eu-west-1), and a default output format.
  4. Test it: aws iam list-users — returns the same kind of information (username, UserId, ARN, created date) you'd see in the console.
Permissions are identical everywhere. Removing a user from their permission-granting group blocks them in the console and makes the same CLI call fail with a permissions error — the CLI isn't a backdoor around IAM.

23AWS CloudShell

CloudShell is a free, browser-based terminal built into the AWS console (icon top-right) — an alternative to installing the CLI locally. It's not available in every region, so if you want to use it, pick one of the regions where it's supported.

  • Comes with the AWS CLI pre-installed and already authenticated as whichever identity you're logged in as — no aws configure needed.
  • Default region = whichever region your CloudShell session is currently in (rather than needing --region flags).
  • Gives you a small persistent file storage area — files you create (e.g. via echo) stick around even after restarting the session.
  • Supports uploading and downloading files, adjustable font size/theme, and multiple tabs/split panes.
Bottom line: if CloudShell is available in your region and works for you, it's a convenient zero-setup alternative to a local terminal. If not, your locally configured CLI works exactly the same for the rest of the course.

24IAM Roles for AWS Services

Some AWS services need to perform actions on your behalf — and just like users, they need permissions to do so. That's what an IAM Role is for: an identity meant to be used by an AWS service (like an EC2 instance or a Lambda function), not by a person.

The EC2 instance assumes the role, and the role's attached policy decides what it's allowed to call.

Common examples: EC2 instance roles, Lambda function roles, CloudFormation roles — any service that needs to act against AWS on its own.

25IAM Roles Hands-On

  1. IAM console → Roles → Create role.
  2. Choose "AWS service" as the trusted entity type, then pick which service (e.g. EC2).
  3. Attach a policy (e.g. IAMReadOnlyAccess) defining what the role can do.
  4. Name it (e.g. DemoRoleForEC2) and confirm — the trusted entity setup is what allows the EC2 service specifically to assume this role.

The role isn't actually put to use yet — it'll get attached to a real EC2 instance later in the course — but the role itself is ready with its permissions in place.

26IAM Security Tools

ToolScopeWhat it shows
IAM Credentials ReportAccount-levelAll users in the account and the status of their various credentials
IAM Access AdvisorPer-userWhich service permissions a user has, and when each was last actually used
Why it matters: Access Advisor directly supports the least-privilege principle — it shows you which granted permissions are actually unused, so you can trim them down.

27IAM Security Tools Hands-On

Credentials Report

IAM → Credential report → Download — generates a CSV with one row per user (including root), showing: when the user was created, whether a console password is set and when it was last used/changed, upcoming password rotation, whether MFA is active, whether access keys exist and when they were last rotated/used.

Great for spotting stale accounts or credentials that deserve a security review.

Access Advisor

User → Access Advisor tab shows every service the user has permission to access and whether/when they actually used it (e.g. IAM, EC2, Organizations accessed; Alexa for Business never touched). It can also tell you which attached policy granted access to a given service — handy for untangling permissions that came from multiple sources.

Practical use: if Access Advisor shows a user has permissions to dozens of services but only ever touches a handful, that's your signal to tighten their policy down to just what they actually use.

28IAM Best Practices

  • Don't use the root account except for initial account setup.
  • One AWS user = one physical person — never share your login with a friend or colleague; create them their own user instead.
  • Put users in groups and manage permissions at the group level.
  • Set a strong password policy.
  • Enable and enforce MFA.
  • Use roles (not shared credentials) to give permissions to AWS services, including EC2 instances.
  • If accessing AWS via CLI/SDK, generate access keys and keep them just as secret as a password.
  • Regularly audit permissions with the IAM Credentials Report and IAM Access Advisor.
Never, ever, ever share your IAM user credentials or access keys. This is repeated for a reason — it's the most common way accounts get compromised.

29Shared Responsibility Model for IAM

A recurring exam topic: knowing what AWS handles versus what you handle.

AWS secures the infrastructure underneath IAM; everything about how you configure and use IAM is on you.

In short: AWS is responsible for the infrastructure itself; you're responsible for how you configure and use it — creating identities, enabling MFA, rotating keys, and reviewing who has access to what.

📋 Cheat Sheet

Lecture 30's own recap lines up with everything above: IAM users map to real people; groups collect users (never other groups); policies (JSON documents) grant permissions to users, groups, or roles; roles are identities for AWS services; MFA and password policies protect accounts; the CLI/SDK (via access keys) give programmatic access; and credential reports plus Access Advisor let you audit it all.

Core building blocks

ConceptWhat it is
IAM UserOne physical person; has console password and/or access keys
IAM GroupCollection of users only (never other groups); a way to share policies
IAM PolicyJSON document granting/denying permissions — attachable to users, groups, or roles
IAM RoleAn identity for AWS services (EC2, Lambda, CloudFormation, etc.), not people
Access KeysAccess Key ID + Secret Access Key — credentials for CLI/SDK access

Key facts to remember

  • IAM is a global service — no region selection.
  • Groups contain only users, never other groups; a user can be in multiple groups.
  • Policy structure: Version + optional Id + Statement(s) — each statement needs Effect, Principal, Action, Resource (Condition optional).
  • Least privilege: never grant more access than the job requires.
  • MFA = password (know) + device (have); options include Google Authenticator/Authy (virtual), YubiKey (U2F), hardware key fobs, and a GovCloud-specific fob.
  • Three access paths: Console (user/pass + MFA), CLI (access keys, terminal), SDK (access keys, in-app code) — the AWS CLI is itself built on the Python SDK, Boto.
  • CloudShell = free browser-based terminal, pre-authenticated, but region-limited.
  • Audit tools: IAM Credentials Report (account-wide credential status) and IAM Access Advisor (per-user, last-accessed services).

Mental model recap

Root account is for setup only — everything day-to-day happens through IAM users, grouped for easy permission management, with policies spelling out exactly what's allowed. Roles do the same job as users but for AWS services instead of people. MFA and strong password policies protect the login; access keys protect programmatic access via the CLI/SDK — and both deserve the same secrecy as a password. Credentials reports and Access Advisor are how you keep checking that nobody has more access than they actually use.
