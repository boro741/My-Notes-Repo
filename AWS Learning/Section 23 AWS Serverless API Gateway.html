1 API Gateway Overview

API Gateway is AWS's serverless way to build public, manageable REST APIs — instead of exposing Lambda directly (needs IAM permissions) or fronting it with an ALB (just gives you an HTTP endpoint, nothing more).

API Gateway sits between clients and any of three backend types — Lambda, HTTP endpoints, or direct AWS service integrations — adding a full feature set on top.

Features

  • Fully serverless, no infrastructure to manage; supports WebSocket for real-time streaming.
  • API versioning, multiple environments (dev/test/prod), authentication/authorization, API keys, request throttling.
  • Import/export via Swagger/OpenAPI 3.0; request/response transformation & validation; SDK generation; response caching.

Why front an AWS service directly?

E.g. clients send HTTP requests straight into API Gateway, which forwards them into Kinesis Data Streams — no AWS credentials ever given to the client, and no servers to manage on either side.

Endpoint types

TypeDescription
Edge-Optimized (default)Single-region API, but requests are routed through CloudFront edge locations globally for lower latency
RegionalNo edge routing — for clients mostly within the same region; can pair with your own CloudFront distribution for more control
PrivateOnly accessible from within your VPC via an interface VPC endpoint; access controlled by a resource policy

Security building blocks

  • IAM roles — for internal apps (e.g. EC2) already in your AWS account.
  • Amazon Cognito — for external users (mobile/web apps).
  • Custom (Lambda) authorizer — your own logic.
  • HTTPS via a custom domain requires an ACM certificate (must be in us-east-1 for Edge-Optimized; same region as the stage for Regional) and a Route 53 CNAME/alias record.

2 Basics — Hands On

  • Create a REST API (Regional, for simplicity), then a resource and a method (e.g. GET) on it, integrated with a Lambda function using Lambda proxy integration.
  • Lambda's own timeout can be up to 15 minutes, but API Gateway always caps at 29 seconds regardless.
  • Creating the method automatically adds a resource-based policy on the Lambda function, granting the specific API Gateway route permission to invoke it.
  • You can Test a method directly in the console (with execution logs shown) before ever deploying it publicly.
  • The full event (path, method, headers, query strings) gets passed to Lambda as JSON — visible by printing/logging the event object.
Don't forget Nothing is publicly reachable until you Deploy API to a stage (e.g. dev) — that deployment produces the actual invoke URL clients use.

3 Stages & Deployment

Common mistake Changes to an API are not live until you explicitly deploy them to a stage. Forgetting this step is a classic source of "why isn't my change showing up" confusion.
  • You can have as many stages as you want, named however you like (e.g. dev/test/prod, or v1/v2) — each with its own config and full deployment history (for rollback).

Separate stages let a breaking backend change ship as a new version (v2) while existing v1 clients keep working, until they're migrated and v1 is retired.

Stage variables

Like environment variables, but for API Gateway stages — change config (e.g. which Lambda alias to invoke) without redeploying. Accessed in mapping templates as $stageVariables.variableName, and passed into the Lambda context object.

Common pattern A stage variable holding a Lambda alias name (e.g. dev/test/prod) lets each stage automatically invoke the right Lambda version/alias — including a weighted alias (e.g. 95% v1 / 5% v2) — without ever touching the API Gateway config itself.

Hands-on: three Lambda versions (v1, v2, latest) mapped to three aliases (PROD→v1, TEST→v2, DEV→latest); the integration ARN references ${stageVariables.LambdaAlias}, and each deployed stage sets that variable to the matching alias name — so /prod, /test, and /dev each hit a different Lambda version automatically.

Stage configuration options

Cache settings, throttling (rate/burst), client certificates, CloudWatch logging/tracing (log level: errors only, info, or full request/response — careful, this can expose sensitive data), detailed metrics, stage variables, deployment/documentation history, canary settings, and tags.

4 Canary Deployments

Test a small % of production traffic against a new version before fully committing — API Gateway's equivalent of Lambda's weighted aliases, applied at the stage level.

A canary splits stage traffic by percentage between the current deployment and the new one — with separate metrics/logs — and can be promoted to 100% once you're confident.

  • Metrics and logs are kept separate for the canary vs. the main stage, for cleaner monitoring.
  • You can override stage variables specifically for the canary.
  • Once satisfied, promote the canary — it becomes the new 100% deployment for that stage.

This is functionally equivalent to a blue/green deployment for Lambda + API Gateway.

5 Integration Types & Mapping Templates

Integration typeBehavior
MockReturns a response without ever calling the backend — for testing/dev only
Lambda / HTTP (non-proxy)You configure separate integration request/response — supports mapping templates to transform data both ways
Lambda ProxyFull request passed as-is to Lambda; Lambda is fully responsible for both request parsing and response shape — no mapping templates possible
HTTP ProxySame idea as Lambda proxy but for an HTTP backend — no mapping templates, though you can inject extra headers (e.g. a hidden API key) between gateway and backend
AWS ServiceDirect integration with an AWS service (SQS, Step Functions, etc.), also supports mapping templates

Mapping templates

Written in VTL (Velocity Template Language) — only usable with non-proxy integrations. Let you rename/reshape query strings, headers, and body content on the way in or out.

  • Classic use case: bridging a SOAP (XML) backend behind a JSON-speaking REST API — extract data from the request, build the SOAP XML message, call the backend, then transform the XML response back to JSON.
  • Another use case: renaming query string parameters into different JSON keys before they reach Lambda.
  • Requires setting Content-Type to application/json or application/xml.

Hands-on: an integration response mapping template took the Lambda's raw JSON output ({"example": "hello world"}) and reshaped it into a differently-named key ({"my key": "my value", "renamed key": "hello world"}) using $input.json('$.example').

6 OpenAPI

API Gateway has tight OpenAPI 3.0 (or Swagger) integration — define methods, integration requests/responses, and AWS-specific extensions entirely as code (YAML/JSON), then import it to build the whole API at once.

  • You can also export an existing API as an OpenAPI spec — useful for generating client SDKs (Android, JavaScript, iOS, Java, Ruby, etc.).
  • OpenAPI specs also drive request validation: check required parameters/headers, or validate the body against a JSON Schema — invalid requests get an immediate 400 without ever reaching the backend.

Configured via x-amazon-apigateway-request-validator in the spec — can validate params-only, body-only, or both, and can be scoped to all methods or specific ones.

Hands-on: importing AWS's example "Pet Store" OpenAPI definition instantly builds out the full API structure; exporting an existing API (from a stage, choosing Swagger/OpenAPI 3, JSON/YAML) produces a portable spec file and can auto-generate an SDK.

7 Caching

EncryptionOptional
Don't forget The cache is expensive — generally worth it only in production/pre-production, not dev/test where request volume is low anyway.

Cache invalidation

  • Invalidate the whole cache instantly from the console.
  • Clients can invalidate it themselves by sending the Cache-Control: max-age=0 header — but this requires IAM authorization for the InvalidateCache permission, or else any client could wipe your cache at will.

Hands-on: enabling the cache on a stage makes repeated identical requests return from cache instead of re-invoking Lambda — noticeably faster, and you can override TTL/invalidation rules per individual method.

8 Usage Plans & API Keys

Used to monetize/meter an API for external customers.

  • Usage plan: defines who can access which stages/methods, how fast (throttling), and how much (quota — e.g. 10,000 requests/month).
  • API key: a string distributed to a customer, sent in the x-api-key header, used to identify and meter their usage against a plan.

Setup order (important!)

  1. Create the API(s), configure which methods require an API key, and deploy to stages.
  2. Generate/import API keys to give to your developers/customers.
  3. Create a usage plan with the desired throttle/quota limits.
  4. Associate the API stages and API keys with the usage plan — miss this step and nothing actually gets enforced.

Throttling limits apply at the API key level; quota limits are the overall request cap for that key.

9 Monitoring, Logging & Tracing

  • CloudWatch Logs integration (per stage, log level ERROR/INFO/DEBUG) captures request/response bodies — be mindful of sensitive data exposure.
  • X-Ray tracing gives full request tracing when enabled on both API Gateway and Lambda.

Key CloudWatch metrics

MetricMeaning
CacheHitCount / CacheMissCountHow effective the API cache is
CountNumber of API requests in a period
IntegrationLatencyTime spent waiting on the backend to respond
LatencyTotal time from request in to response out — includes IntegrationLatency plus auth checks, cache lookups, mapping templates, etc.
4XXErrorClient-side errors
5XXErrorServer-side (backend) errors
Exam point Latency is always ≥ IntegrationLatency. Both are capped by the hard 29-second API Gateway timeout — exceed it and you get a 504.

Throttling & errors

  • Default account-wide soft limit: 10,000 requests/second across all APIs (can be raised) — one overloaded API can throttle the others unless you set per-stage/per-method/per-usage-plan limits.
  • Throttled requests return 429 Too Many Requests — retriable with exponential backoff.
  • 4xx = client errors (400 Bad Request, 403 Access Denied/WAF block, 429 throttled); 5xx = server errors (502 bad Lambda proxy response, 503 backend unavailable, 504 integration timeout after 29s).

10 CORS

Enable CORS whenever your API needs to accept calls from a browser on a different domain — same browser security concept covered for S3/CloudFront.

  • API Gateway responds to an OPTIONS preflight request with the CORS headers: Access-Control-Allow-Methods, Access-Control-Allow-Headers, Access-Control-Allow-Origin — all configurable from the console.
Exam point Just remember: enable CORS on the API Gateway resource whenever the calling web page's origin differs from the API's origin.

11 Authentication & Authorization

MethodBest forHow it works
IAM permissionsInternal callers already in your AWS account (EC2, Lambda, IAM users)Caller signs the request with SigV4; API Gateway checks the IAM policy. Combine with a resource policy for cross-account access, IP allow/deny lists, or VPC-only access.
Cognito User PoolsExternal web/mobile users, no custom code neededClient authenticates with Cognito, gets a token, passes it to API Gateway, which validates it directly against the User Pool
Lambda Authorizer (custom)Third-party identity systems (e.g. Auth0) or fully custom logicClient passes a bearer token (JWT/OAuth); a Lambda function validates it and returns an IAM policy, which gets cached

Three authorization paths into the same API Gateway: raw IAM signing, Cognito-issued tokens, or a Lambda authorizer validating a third-party token and returning a cacheable IAM policy.

Exam point Lambda Authorizer is the most flexible but the most work — you write both the token validation and the authorization logic yourself, and you still pay for the Lambda invocation even with caching. Cognito is preferred when you don't need a custom identity system, since no custom authentication code is required.

13 WebSocket API

WebSocket = two-way, persistent, interactive communication between client and server — the server can push data without the client asking first. Used for chat apps, collaboration tools, multiplayer games, trading platforms.

A persistent connection ID is established once and reused for every message; the server can push data back at any time via a signed POST to the connection's callback URL.

  • On connect, a $connect Lambda fires (e.g. persist the connection ID + user info in DynamoDB); on disconnect, $disconnect fires; regular messages ("frames") route to other backends based on a route selection expression (e.g. $request.body.action) matched against a route key table.
  • To push data to the client without them asking: POST (SigV4-signed) to .../@connections/{connectionId}. GET checks connection status; DELETE disconnects the client.
  • Unmatched routes fall back to the default route.

14 Microservices Architecture

API Gateway can act as a single unified entry point across many backend microservices, hiding their complexity from clients.

One API Gateway routes different paths to entirely different backends (ECS, S3, EC2 ASGs), fronted by a custom Route 53 domain and SSL cert — clients see one clean URL regardless of backend complexity.

You can register custom domains via Route 53 (even per-customer subdomains like customer1.example.com), attach the right SSL certificates, and apply forwarding/transformation rules — all centralized at the API Gateway layer.

✓ Cheat Sheet

Key facts to remember

  • API Gateway integrates with Lambda, any HTTP backend, or AWS services directly — always via a serverless proxy, adding auth, caching, throttling, and versioning on top.
  • Endpoint types: Edge-Optimized (global, via CloudFront), Regional (single region), Private (VPC-only via resource policy).
  • Changes are invisible until deployed to a stage; stage variables let one API config point at different backends (e.g. Lambda aliases) per stage without redeploying.
  • Canary deployments split a stage's traffic by percentage between current and new versions, with separate metrics, before a full promotion.
  • Proxy integrations (Lambda proxy, HTTP proxy) pass requests/responses through untouched — no mapping templates possible; non-proxy integrations support VTL mapping templates to reshape data both ways.
  • OpenAPI specs can build/import/export APIs and drive request validation (missing params/headers, bad JSON schema → 400 before hitting the backend).
  • Caching is per-stage (overridable per-method), 0–3,600s TTL, 0.5–237GB — invalidation via console or a Cache-Control: max-age=0 header (needs IAM authorization or anyone can wipe it).
  • Usage plans + API keys meter/throttle/quota external customers — must associate keys and stages with the plan or nothing is enforced.
  • Hard 29-second timeout on every API Gateway request, regardless of Lambda's own timeout — exceeding it is a 504.
  • Default account throttle: 10,000 req/sec across all APIs (soft limit) — one overloaded API can throttle others unless scoped with stage/method/usage-plan limits.
  • Auth options: IAM (+resource policy for cross-account/IP/VPC rules), Cognito User Pools (no custom code), Lambda Authorizer (most flexible, most work, still costs an invocation even when cached).
  • HTTP APIs are cheaper/simpler (proxy-only, native OIDC/OAuth2, built-in CORS) but lack usage plans, API keys, resource policies, and mapping templates that REST APIs have.
  • WebSocket APIs keep a persistent connection ID; routing is based on a JSON field in the incoming message (route selection expression); server-to-client push uses a signed POST to @connections/{connectionId}.

Mental model

API Gateway is the front door that turns a Lambda function, an HTTP service, or a raw AWS API into a manageable, secure, versioned product: stages and canaries let you evolve the backend safely; mapping templates and OpenAPI validation let you shape and guard the data crossing the boundary; caching, usage plans, and throttling protect both your backend and your business model; and IAM/Cognito/Lambda authorizers decide who's allowed through the door in the first place. Once you can name which of these levers solves a given problem, the API Gateway exam surface is mostly memorization of specifics (timeouts, metric names, setup order) layered on that same mental frame.
