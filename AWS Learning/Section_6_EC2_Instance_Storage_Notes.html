1EBS Overview

EBS = Elastic Block Store. It's a network drive you attach to an EC2 instance while it's running. It exists so your data can outlive the instance — terminate the instance, keep the volume, attach it to a new instance, and your data is right there.

💾 Analogy: An EBS volume is like a network USB stick. You "plug it in" to a computer, but the connection travels over the network instead of a physical port — which is also why there's a tiny bit of latency compared to a directly attached disk.

Core rules to remember

  • One EBS volume ↔ one instance at a time (Multi-Attach is the advanced exception — see Lecture 9)
  • An EBS volume is locked to one Availability Zone. A volume created in us-east-1a can only attach to instances in us-east-1a — never us-east-1b
  • Because it's network-based, it can be detached and reattached quickly — great for failover
  • It's provisioned: you set size (GB) and IOPS up front, and pay for what you provision — not just what you use. You can resize later
  • A volume doesn't need to be attached to anything — you can create one and leave it ready to attach on demand
An EBS volume is locked to its Availability Zone — it can never attach to an instance in a different AZ.

Delete on Termination

An attribute on the EBS volume controlling whether AWS auto-deletes it when its EC2 instance is terminated.

VolumeDefault "Delete on Termination"Behavior
Root volumeEnabled (Yes)Deleted automatically when instance is terminated
Any extra attached volumeDisabled (No)Survives instance termination
Exam scenario: "How do I preserve the root volume's data after terminating an instance?" → Disable Delete on Termination for the root volume before terminating.

2EBS Hands-On

Practical walkthrough of managing volumes in the AWS console.

  1. View attached volumes: EC2 instance → Storage tab → shows root device + any block devices
  2. Create a new volume: EC2 console → Volumes → Create Volume → choose type, size, and — critically — the same AZ as your target instance
  3. Attach it: Select the volume ("available" state) → Actions → Attach Volume → pick the instance
  4. Confirm: Refresh the instance's Storage tab — now shows two block devices
Proven the hard way: Creating a volume in a different AZ than your instance makes "Attach Volume" simply refuse to offer that instance. Live proof that EBS volumes are AZ-bound.

Actually formatting/mounting the raw block device inside the OS is outside CCP exam scope, but the AWS doc to search is: "make an Amazon EBS volume available for use on Linux."

Interesting termination behavior

Terminate the instance → the root volume (Delete on Termination = Yes) disappears from the Volumes list along with it. The extra volume (Delete on Termination = No) stays behind as an orphaned, still-billable volume.

3EBS Snapshots

A snapshot is a point-in-time backup of an EBS volume. Detaching first isn't required, but recommended for a fully consistent backup.

Since a live EBS volume can't move AZs on its own, snapshot → restore is the mechanism to relocate data across AZs or Regions.
Why snapshots matter: They can be copied across AZs and Regions — this is the only way to relocate EBS data since the volume itself can't move.

Three snapshot features to know

FeatureWhat it doesTrade-off
Archive TierMoves a snapshot to cheaper storage — up to 75% savingsRestoring takes 24–72 hours
Recycle BinDeleted snapshots land here instead of vanishing foreverRetention configurable 1 day – 1 year
Fast Snapshot Restore (FSR)Forces full initialization so there's zero latency on first useExpensive — use sparingly

4EBS Snapshots Hands-On

  1. Create: Volume → Actions → Create Snapshot → add description → Create
  2. Copy across region: Snapshot → right-click → Copy Snapshot → pick destination region — useful for a Disaster Recovery strategy
  3. Restore into a volume: Snapshot → Actions → Create Volume From Snapshot → pick a different AZ than the original (e.g. restore an eu-west-1a snapshot into eu-west-1b) — this is the real mechanism for "moving" data between AZs
  4. Recycle Bin setup: Create a Retention Rule (resource type "EBS Snapshots", apply to all resources, set retention e.g. 1 day) → deleted snapshots now recover instead of disappearing
  5. Storage Tiers: Move a snapshot from Standard to Archive from the console — remember the 24–72 hr restore delay
Demo takeaway: Delete a snapshot → it disappears from Snapshots list → check Recycle Bin → Resources → it's sitting there → Recover Resources → it's back.

5AMI Overview

AMI = Amazon Machine Image. A template of everything that makes up an EC2 instance's software: OS, installed applications, monitoring agents, configuration — a "pre-baked" instance you can stamp out repeatedly.

🐳 Analogy: An AMI is like a Docker image for a virtual machine — build it once with everything installed, then spin up as many instances from it as you want, each already configured with no re-installation needed.

Where AMIs come from

  • Public AMI — provided by AWS (e.g. Amazon Linux 2, used throughout this course)
  • Your own AMI — build and maintain it yourself (can be automated)
  • AWS Marketplace AMI — built and sold by third-party vendors, pre-configured with commercial software (you can sell your own too)
Stopping the instance first ensures data integrity before AWS captures the image. Creating an AMI generates EBS snapshots behind the scenes.

Once created, launch new instances from that AMI anywhere in the Region (or copy the AMI to another Region).

Why it matters: Instances launched from a custom AMI boot much faster — the software is already baked in, no install step at boot time.

6AMI Hands-On

  1. Launch an EC2 instance (Amazon Linux 2, t2.micro) with a user-data script that installs Apache (httpd) — but don't create an index.html yet, since we want a clean, reusable base image
  2. Wait ~1–2 minutes for the script to actually finish (status "running" ≠ script done)
  3. Verify Apache works by hitting the instance's public IP over HTTP
  4. Create the AMI: right-click instance → Image and templates → Create Image → name it → Create
  5. Wait for AMI status: pending → available
  6. Launch a new instance from that AMI (via "My AMIs" tab) — this time User Data only needs to echo a new index.html, no need to reinstall httpd
  7. Result: the second instance serves the page noticeably faster on boot since the heavy install step is skipped
Key exam idea: Whenever a scenario needs faster, standardized instance boot-up across many EC2 launches (fleet scaling, golden images), think custom AMI.

7EC2 Instance Store

EBS is a network drive — great, but not the fastest option possible. Some EC2 instance types have a disk physically attached to the underlying hardware server. That's an EC2 Instance Store.

EBS trades a bit of speed for durability; Instance Store trades durability for maximum speed.
The critical trade-off: Instance Store = ephemeral storage. Stop or terminate the instance → the data is gone. Not for durable, long-term storage — that's EBS's job.

When to use it

  • Buffers, caches, scratch data, temporary/session data
  • Anywhere you need extremely high I/O throughput and can tolerate data loss

Also: if the underlying hardware server fails, the physically attached storage fails with it — backup/replication responsibility is entirely on you.

Storage TypeExampleRead/Write IOPS
EC2 Instance Store (I3 family)Physically attached NVMe SSDUp to ~3.3M read / ~1.4M write IOPS
EBS gp2Network volumeUp to ~32,000 IOPS
Exam pattern: "Very high performance, hardware-attached, disappears if the instance stops" → EC2 Instance Store.

8EBS Volume Types

Six volume types, grouped into two families: SSD (transactional, small random I/O) and HDD (large, sequential, throughput-heavy).

FamilyTypesBoot Volume?Best For

gp2 vs gp3 — the important distinction

gp2 ties performance to size; gp3 lets you set size and performance independently — which is why it's the current recommended default.

Provisioned IOPS (io1 / io2 Block Express)

  • For apps needing sustained, very high IOPS (>16,000) — e.g. large relational databases
  • io1: 4 GB–16 TB, up to 64,000 IOPS on Nitro instances (32,000 on others), IOPS set independently of size
  • io2 Block Express: up to 64 TB, sub-millisecond latency, up to 256,000 IOPS (ratio: 1,000 IOPS per GB)
  • io1/io2 are the only families supporting EBS Multi-Attach (Lecture 9)

9EBS Multi-Attach

Allows the same EBS volume to be attached to multiple EC2 instances at the same time — but only within the same AZ, and only for io1/io2 volumes.

Multiple instances share one io1/io2 volume — all within the same AZ, up to 16 instances.

Key facts

  • Every attached instance gets full read and write access simultaneously
  • Use case: higher availability for clustered Linux applications (e.g. Teradata) or apps that manage their own concurrent write coordination
  • Same AZ only — cannot span AZs
  • Max 16 EC2 instances can attach to one volume at a time
  • Requires a cluster-aware file system — regular XFS or EXT4 won't handle concurrent writes safely
Exam number to memorize: 16 instances max for Multi-Attach.

10Amazon EFS

EFS = Elastic File System — a managed NFS (Network File System). Unlike EBS, it isn't locked to one AZ or one instance: it can be mounted by many EC2 instances simultaneously, across multiple AZs.

EFS spans multiple AZs — every instance in every AZ can read and write to the same file system at once.

Key characteristics

  • Highly available, highly scalable — grows automatically to petabyte scale
  • Pay-per-use: no capacity to provision in advance (unlike EBS)
  • ~3× the cost of a gp2 EBS volume per GB — you pay for the convenience of sharing
  • Linux-only — uses the POSIX filesystem API, not compatible with Windows
  • Encryption at rest available via KMS
  • Access controlled through a Security Group attached to the EFS mount targets
  • Use cases: content management, web serving/hosting (e.g. WordPress), shared data across a fleet

Performance Mode (set at creation, can't change later)

11Amazon EFS Hands-On

Step 1 — Create the file system

  • Choose VPC, then Customize to see full options
  • File system type: Regional (multi-AZ, production) vs. One Zone (single AZ, dev/cost-saving)
  • Enable automatic backups (recommended)
  • Lifecycle management: e.g. "not accessed in 30 days → move to Infrequent Access", "not accessed in 90 days → move to Archive", "on first access → back to Standard"
  • Enable encryption

Step 2 — Performance settings

Throughput mode options in the console: Bursting, Provisioned, and Enhanced (a category containing Elastic and Provisioned). Functionally there are three real choices: Bursting, Elastic, Provisioned — with Elastic being AWS's current recommended default. Performance mode (General Purpose vs Max I/O) is only selectable with Bursting or Provisioned; Elastic always uses General Purpose.

Step 3 — Network access

  • Choose a VPC and mount targets — Regional type gives one mount target per AZ (subnet), each needing a Security Group
  • Create a dedicated Security Group for EFS (e.g. sg-efs-demo) — AWS auto-configures inbound rules when you attach EFS via the EC2 launch wizard

Step 4 — Mount EFS directly from the EC2 launch wizard

  1. Select a subnet (AZ) first — required before adding a file system
  2. Under "File systems," add the EFS file system → mount point defaults to /mnt/efs/fs1
  3. AWS auto-creates and attaches the correct Security Groups for both EFS and the instance, and auto-generates the user data script to mount it — no manual commands needed

Step 5 — Prove it's shared across AZs

Launch Instance A (AZ-a) and Instance B (AZ-b), both mounting the same EFS file system.

# On Instance A:
sudo su
echo "hello world" > /mnt/efs/fs1/hello.txt
cat /mnt/efs/fs1/hello.txt
# → hello world

# On Instance B (different AZ):
ls /mnt/efs/fs1/
cat /mnt/efs/fs1/hello.txt
# → hello world   (same file, visible instantly)
What this proves: A file written from one AZ is immediately visible from an instance in a different AZ — this is the defining behavior that separates EFS from EBS.

Cleanup checklist for this demo

  1. Terminate both EC2 instances
  2. Delete the EFS file system (requires typing its File System ID to confirm)
  3. Delete the auto-created security groups (only possible after dependent instances are fully terminated)

Don't forget the snapshot performance impact: Taking an EBS snapshot consumes I/O — avoid running one while your app is under heavy load, since it can degrade performance.

And EC2 Instance Store, for completeness

Physically attached to the host hardware → highest performance, but lost entirely if the instance is stopped or terminated. Use only for ephemeral/temporary data.

Three storage options, three different trade-offs between sharing, durability, and speed.

One-line mental model for all three

EBS = your personal network hard drive (one instance, one AZ).
EFS = a shared network drive for a whole team of instances across AZs.
Instance Store = the fastest local disk you'll ever get — but it forgets everything when the machine turns off.

13EFS and EBS Clean-Up

Housekeeping checklist to avoid ongoing charges after finishing hands-on labs, in the correct dependency order:

  1. Delete the EFS file system — Actions → Delete → confirm by pasting the File System ID
  2. Terminate all running EC2 instances
  3. Delete all EBS volumes that are in "available" (unattached) state
  4. Delete all EBS snapshots — otherwise you keep paying for stored snapshot data
  5. Delete extra Security Groups (keep "default"). A security group tied to still-running instances can't be deleted until those instances fully terminate — retry after waiting
Practical tip: Deletion order matters because of dependencies — EFS mount targets and their security groups can't be removed while instances still reference them. If a delete fails, something upstream hasn't finished terminating yet — just wait and retry.

📋 Cheat Sheet

Storage decision guide

If you need...Use
Persistent storage for one instance, in one AZEBS
Shared storage across many instances / many AZs (Linux only)EFS
Maximum raw speed, don't care about durabilityInstance Store
Same volume shared by clustered app instances (same AZ)EBS Multi-Attach (io1/io2)
Reusable, pre-configured instance templateAMI

Key numbers to remember

  • EBS Multi-Attach: max 16 instances, same AZ only, io1/io2 only
  • gp3 baseline: 3,000 IOPS / 125 MB/s, decoupled from size
  • io2 Block Express: up to 256,000 IOPS, up to 64 TB
  • Snapshot archive tier restore: 24–72 hours
  • EFS cost: roughly 3× EBS gp2 per GB (tiering can offset this by up to 90%)

Mental model recap

  • EBS = network USB stick, locked to one AZ, one instance at a time (usually)
  • Snapshots = the only way to move EBS data across AZs/Regions
  • AMI = a saved template (OS + software) for launching pre-configured instances fast
  • Instance Store = fastest but disappears when the instance stops/terminates
  • EFS = shared NFS file system across many instances and AZs, Linux only
