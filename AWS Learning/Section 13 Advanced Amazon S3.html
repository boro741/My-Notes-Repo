1 S3 Lifecycle Rules & S3 Analytics

Think of an Amazon S3 Bucket as an unlimited digital locker in the cloud. Over time, stored files (objects) get older and are used less frequently. You can move these files between different storage classes to save money — either manually or automatically using Lifecycle Rules.

Objects move step-by-step through cheaper storage tiers — e.g., Standard → Standard-IA → Intelligent-Tiering → One-Zone-IA → Flexible Retrieval / Deep Archive.

What a Lifecycle Rule Can Do

  • Transition Actions — automatically move an object to a cheaper storage class after a specific number of days. (Example: Move files to Standard-IA after 60 days, or to S3 Glacier after 180 days).
  • Expiration Actions — automatically delete files after a set period to save space. (Example: Delete log files after 365 days, delete old file versions, or clean up incomplete multi-part uploads older than 14 days).
  • Targeting Rules — rules can apply to the entire bucket, a specific folder/prefix (path), or only to objects carrying specific tags.

Exam-Style Scenarios

Scenario 1 An application running on EC2 creates small thumbnails from uploaded profile photos. Thumbnails can be remade easily if lost and are only needed for 60 days. Source photos need instant access for 60 days, after which users can wait up to 6 hours for retrieval. Solution: Store original photos in Standard, then transition them to S3 Glacier after 60 days. Put thumbnails under a separate prefix folder, store them in One-Zone-IA (cheaper, single data-center storage), and set an expiration rule to auto-delete them after 60 days.
Scenario 2 Company rule: Deleted files must be instantly recoverable for 30 days, and recoverable within 48 hours for up to 365 days. Solution: Enable S3 Versioning (deleting a file only attaches a "delete marker", keeping old versions safe). Next, add a lifecycle rule to move non-current (old) versions to Standard-IA after 30 days, and then to S3 Glacier Deep Archive for long-term storage up to 365 days.

S3 Analytics

If you do not know the exact number of days to wait before moving files, S3 Analytics helps you decide by giving smart recommendations. However, it only works for Standard and Standard-IA storage classes (not One-Zone-IA or Glacier).

  • Generates daily CSV reports containing file usage statistics and transition recommendations.
  • Takes 24 to 48 hours after enabling to start displaying useful data.
Tip Always check the S3 Analytics CSV report to plan your lifecycle rules accurately instead of guessing transition days.

2 S3 Lifecycle Rules Hands On

You can create lifecycle rules under the Management tab of your S3 bucket. After naming the rule and selecting its scope (such as all objects or specific folders), you can pick from five main rule actions:

ActionWhat It Does
Move current versions between storage classesMoves the latest (active) version of a file to cheaper tiers — e.g., to Standard-IA after 30 days, Intelligent-Tiering after 60 days, Glacier Instant Retrieval after 90 days, Flexible Retrieval after 180 days, and Deep Archive after 365 days.
Move non-current versions between storage classesMoves older or overwritten versions of files — e.g., straight to Glacier Flexible Retrieval after 90 days since they are rarely accessed.
Expire current versions of objectsAutomatically deletes the current active version of files after N days (e.g., 700 days).
Permanently delete non-current versionsPermanently removes old, replaced versions after N days (e.g., 700 days) to free up storage space.
Delete expired objects / delete markers / incomplete multi-part uploadsHousekeeping cleanup action to remove leftover temporary data and hidden delete markers.

You can combine multiple transition stages in a single rule. The AWS console displays a helpful timeline preview showing exact timeline shifts for current and old file versions before you save.

3 S3 Event Notifications

S3 can trigger automatic notification alerts whenever specific events occur inside a bucket — such as uploading a new object, deleting an object, restoring an object, or completing a replication. You can also filter events (for example, triggering alerts only for .jpeg files).

Real-world example: Automatically resize and create a thumbnail image every time a user uploads a new photo to S3.

Where Event Notifications Can Go

S3 events can be sent directly to SNS, SQS, or Lambda. Additionally, all events can flow into EventBridge to reach 18+ AWS destinations with advanced filtering.

Direct Destination Targets: SNS, SQS, Lambda

  • S3 does not use an IAM Role to deliver event notifications. Instead, the destination resource must have a Resource-based Policy attached that grants S3 permission to communicate with it:
    • SNS (Simple Notification Service - Pub/Sub messaging service) — Attach an SNS Access Policy allowing S3 to publish messages.
    • SQS (Simple Queue Service - Message queue service) — Attach an SQS Access Policy allowing S3 to send messages into the queue.
    • Lambda (Serverless code execution) — Attach a Lambda Resource Policy allowing S3 to invoke the function.
  • This functions similarly to an S3 Bucket Policy, but is attached directly to the target destination service.
  • Notifications are usually delivered within seconds, though occasional delays of a minute or more can happen.
Exam Point Remember the 3 direct Event Notification targets: SNS, SQS, and Lambda. Also remember that all S3 events can additionally stream into Amazon EventBridge. This enables advanced rule filtering (by file size, name, or metadata), sending to multiple destinations at once, and features like event archiving and replay.

4 S3 Event Notifications Hands On

To configure an event notification in the AWS Console, open your bucket's Properties → Event notifications tab. You have two main approaches:

  1. Create an event notification directly to send alerts to SNS, SQS, or Lambda, or
  2. Enable the EventBridge integration toggle to stream all events to Amazon EventBridge instead.

Step-by-Step: Send Notification to SQS on File Creation

  1. Create an SQS queue first (e.g., named DemoS3Notification).
  2. In S3, create an event notification, select the event type "All object create events", and pick your SQS queue as the target destination.
Important Warning Saving the event notification will fail with an error if the SQS queue policy does not explicitly permit S3 to send messages into it! You must edit the queue's Access Policy (Effect = Allow, Principal = Service: s3.amazonaws.com, Action = sqs:SendMessage, Resource = Queue ARN) before S3 can validate and deliver messages.
  • After granting proper policy permissions, saving the notification automatically sends a test message to the SQS queue to confirm connectivity.
  • Uploading an actual file (e.g., coffee.jpg) sends a real event message containing eventName: ObjectCreatedPut along with the object key — perfect for triggering automated background tasks like image processing.

5 S3 Performance

Baseline Performance Limits

  • S3 automatically scales to handle huge request volumes with very low latency (the delay before data transfer starts: 100–200ms for the first byte).
  • 3,500 PUT / COPY / POST / DELETE requests per second, per prefix.
  • 5,500 GET / HEAD requests per second, per prefix.
  • There is no limit on the number of prefixes you can create in an S3 bucket. You can easily boost total performance by distributing files across multiple prefixes.
Everyday Analogy A "prefix" is simply the folder path between the bucket name and file name — e.g., in my-bucket/photos/vacation/pic.jpg, the prefix is photos/vacation/. Think of each prefix as a separate billing counter at a supermarket (like DMart). Each counter can process 3,500 writes or 5,500 reads per second independently. Opening more counters (prefixes) allows you to serve vastly more total customers per second!

Example: Distributing files across 4 distinct prefixes yields a combined read speed of 22,000 GET/HEAD requests per second (4 prefixes × 5,500 requests/sec).

Speeding Up Uploads: Multi-Part Upload

  • Recommended for uploading files larger than 100 MB, and mandatory for files larger than 5 GB.
  • Splits a large file into smaller chunks and uploads them in parallel (simultaneously) using available network bandwidth. Once all chunks arrive, S3 reassembles them into the original file.

Multi-part upload breaks a large file into smaller pieces, uploads them simultaneously in parallel, and S3 stitches them back together.

Speeding Up Long-Distance Transfers: S3 Transfer Acceleration

  • Accelerates both file uploads and downloads over long geographical distances. Fully compatible with Multi-part upload.
  • Routes data through the nearest AWS Edge Location (over 200 worldwide points of presence) via a fast local hop, then uses AWS's high-speed private fiber-optic backbone network to reach the target S3 bucket region.

Transfer Acceleration minimizes public internet latency by connecting to a nearby AWS Edge Location and traveling across AWS's private high-speed global network.

Speeding Up Downloads: S3 Byte-Range Fetches

  • Parallelize GET requests by downloading specific byte ranges (chunks) of a large file simultaneously.
  • Improves download resilience — if a single byte-range request fails, you retry only that failed chunk instead of restarting the full download.
  • Allows fetching partial data — e.g., downloading just the first 50 bytes of a file to read metadata headers without downloading the rest of the file.

6 S3 Object Tags & Metadata

User-Defined Metadata

  • Custom key-value pairs assigned to an object during file upload.
  • Custom metadata keys must begin with x-amz-meta- to distinguish them from standard AWS system metadata (such as Content-Length or Content-Type).
  • Example: x-amz-meta-origin: mumbai.

Object Tags

  • Key-value pairs attached to S3 objects, used widely across AWS services.
  • Useful for configuring fine-grained IAM permissions (e.g., allowing access only to objects tagged Department: Finance) and for cost allocation / analytics grouping.
  • Example: Project: Alpha, Confidential: True.
Critical Limitation Neither metadata nor tags are searchable within Amazon S3! You cannot query or search objects by metadata or tag values directly inside S3.

How to Search S3 Objects by Tags or Metadata?

To enable search capability, build an external searchable index using a database service like Amazon DynamoDB. Save object metadata/tags into DynamoDB when uploading files to S3. You can then quickly query DynamoDB, which returns pointers to the matching S3 objects.

Because S3 cannot search metadata/tags directly, application queries search an external database index (like DynamoDB), which points to the target files in S3.

Exam Point "How do you make S3 object metadata or tags searchable?" → Create an external searchable index in a database like DynamoDB that mirrors the metadata/tags, and query that database to locate S3 objects.

✓ Cheat Sheet

Key Facts to Remember

  • Lifecycle Rules: Combine transition actions (moving files across storage classes) and expiration actions (deleting objects, old versions, or incomplete multi-part uploads). Rules can target the full bucket, a prefix (folder path), or object tags.
  • S3 Analytics: Provides storage transition recommendations, but works ONLY for Standard ↔ Standard-IA. Reports refresh daily and take 24–48 hours to start displaying data.
  • S3 Event Notifications: Send alerts directly to SNS, SQS, or Lambda (each requires a Resource Policy granting access to S3), or to Amazon EventBridge (which unlocks 18+ destinations and advanced filtering).
  • Baseline Performance: Supports 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD requests per second per prefix. Buckets can have unlimited prefixes.
  • Multi-Part Upload: Recommended for files over 100 MB, required for files over 5 GB. Uploads chunks in parallel for maximum speed.
  • Transfer Acceleration: Routes traffic through nearby AWS Edge Locations over AWS's private high-speed backbone to speed up long-distance transfers.
  • Byte-Range Fetches: Downloads file chunks in parallel to speed up GET requests, resume broken downloads, or fetch partial file headers.
  • Metadata & Tags: Key-value attributes on objects. Neither is searchable directly in S3. Tags are useful for fine-grained IAM permissions and cost reporting.
  • Searching S3: Build an external database index (e.g., DynamoDB) to store and search object tags or metadata.

Mental Model

Advanced S3 centers on managing object storage efficiently at scale. Lifecycle rules automate moving and deleting aging objects to save costs. Event notifications allow AWS services to react instantly to bucket activity. Performance features (Multi-part upload, Transfer Acceleration, Byte-Range fetches) let you bypass single-connection speed limits by parallelizing transfers and using AWS's edge network. Finally, tags and metadata help organize data, but since S3 cannot search them directly, real-world searching requires building an external database index like DynamoDB.
