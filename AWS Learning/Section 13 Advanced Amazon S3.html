1 S3 Lifecycle Rules & S3 Analytics

Objects can move between storage classes over time — either manually, or automatically using Lifecycle Rules.

Objects can transition through storage classes in many valid orders — e.g. Standard → Standard-IA → Intelligent-Tiering → One-Zone-IA → Flexible Retrieval / Deep Archive.

What a lifecycle rule can do

  • Transition actions — move an object to another storage class after N days. E.g. move to Standard-IA after 60 days, or to Glacier after 6 months.
  • Expiration actions — delete objects after N days (e.g. delete log files after 365 days), delete old versions of objects if versioning is enabled, or clean up incomplete multi-part uploads older than a certain age (e.g. 2 weeks).
  • Rules can apply to the whole bucket, to a specific prefix (path), or to objects with specific tags.

Exam-style scenarios

Scenario 1 An app on EC2 creates thumbnails from uploaded profile photos. Thumbnails are easy to recreate and only need to be kept 60 days; source images need instant access for 60 days, then users can tolerate up to a 6-hour wait. Solution: keep source images on Standard, transition to Glacier after 60 days. Use a prefix to separate thumbnails, store them on One-Zone-IA (infrequently accessed, recreatable), and expire them after 60 days.
Scenario 2 Company policy: deleted objects must be recoverable instantly for 30 days, then recoverable within 48 hours for up to 365 days. Solution: enable versioning (deletes just add a delete marker, so the object is recoverable), then set a rule to transition non-current versions to Standard-IA, and later to Glacier Deep Archive for long-term archival.

S3 Analytics

Not sure what the "right" number of days is for a transition? S3 Analytics gives recommendations — but only for Standard and Standard-IA (not One-Zone-IA or Glacier).

  • Produces a CSV report with statistics and recommendations.
  • Updated daily; takes 24–48 hours to start showing useful data.
Tip Use the S3 Analytics CSV report as your starting point for designing (or improving) lifecycle rules, rather than guessing at transition timings.

2 S3 Lifecycle Rules Hands On

Lifecycle rules are created under a bucket's Management tab. Once you name a rule and choose its scope (e.g. all objects in the bucket), you get five possible rule actions:

ActionWhat it does
Move current versions between storage classesTransitions the most recent (displayed) version of an object — e.g. to Standard-IA after 30 days, Intelligent-Tiering after 60, Glacier Instant Retrieval after 90, Flexible Retrieval after 180, Deep Archive after 365
Move non-current versions between storage classesTransitions older/overwritten versions — e.g. straight to Glacier Flexible Retrieval after 90 days since they likely won't be needed
Expire current versions of objectsDeletes the current version after a set number of days (e.g. 700 days)
Permanently delete non-current versionsCleans up old versions after a set number of days (e.g. 700 days)
Delete expired objects / delete markers / incomplete multi-part uploadsHousekeeping cleanup action

You can stack as many transitions as you like, and the console shows a timeline preview of what will happen to current vs. non-current versions of your objects before you save the rule.

3 S3 Event Notifications

S3 can notify other services when things happen in a bucket — object created, object removed, object restored, replication events, etc. You can also filter events (e.g. only react to .jpeg files).

Use case example: automatically generate a thumbnail every time an image is uploaded to S3.

Where events can go

S3 events can go directly to SNS, SQS, or Lambda — and every event also lands in EventBridge, which can fan it out to 18+ other AWS services with more advanced filtering.

Direct targets: SNS, SQS, Lambda

  • S3 doesn't use an IAM role to deliver events. Instead, the target needs a resource policy that allows S3 to talk to it:
    • SNS — attach an SNS resource access policy allowing S3 to publish messages.
    • SQS — attach an SQS resource access policy allowing S3 to send messages.
    • Lambda — attach a Lambda resource policy allowing S3 to invoke the function.
  • This works the same way conceptually as an S3 bucket policy — just attached to the other resource instead.
  • Events are typically delivered within seconds, but can occasionally take a minute or more.
Exam point Remember the three direct Event Notification targets: SNS, SQS, and Lambda. Also remember that every S3 event can additionally flow into EventBridge, unlocking advanced filtering (by metadata, object size, name), multiple simultaneous destinations, and features like event archiving/replay.

4 S3 Event Notifications Hands On

Setting up an event notification (bucket Properties → Event notifications) gives you two paths:

  1. Create an event notification directly (to SNS, SQS, or Lambda), or
  2. Enable the EventBridge integration toggle to send everything to EventBridge instead.

Walkthrough: notify SQS on object creation

  1. Create an SQS queue first (e.g. DemoS3Notification).
  2. Create the event notification, choose event type "All object create events", and pick the SQS queue as the destination.
Don't forget Saving the notification will fail with an error if the SQS queue doesn't yet allow S3 to send messages into it. You must edit the queue's access policy (via the SQS Policy Generator: Effect = Allow, Principal = anyone, Action = SendMessage, Resource = the queue ARN) before S3 can successfully validate and deliver to it.
  • Once the access policy is fixed, saving the notification triggers an automatic test event in the queue to confirm connectivity.
  • Uploading a real file (e.g. coffee.jpg) then generates an actual event message in the queue with eventName: ObjectCreatedPut and the object's key — exactly the kind of message you'd use to trigger something like thumbnail generation.

5 S3 Performance

Baseline performance

  • S3 automatically scales to a very high request volume with low latency — 100–200ms to get the first byte.
  • 3,500 PUT/COPY/POST/DELETE requests per second, per prefix.
  • 5,500 GET/HEAD requests per second, per prefix.
  • There's no limit on the number of prefixes in a bucket, so performance scales by spreading objects across more prefixes.
Analogy A "prefix" is just everything between the bucket name and the object name — e.g. for bucket/folder1/sub1/file, the prefix is folder1/sub1. Each distinct prefix gets its own 3,500/5,500 allowance, like each checkout lane at a store having its own throughput — more lanes (prefixes) means more total customers served per second.

Example: 4 objects spread across 4 different prefixes, read evenly, can together achieve 22,000 GET/HEAD requests/second (4 × 5,500).

Speeding up uploads: Multi-part upload

  • Recommended for files over 100 MB, required for files over 5 GB.
  • Splits a file into parts and uploads them in parallel, maximizing bandwidth use; S3 reassembles the parts once all are uploaded.

Multi-part upload splits a large file into chunks that upload in parallel, then S3 reassembles them.

Speeding up transfers over distance: S3 Transfer Acceleration

  • Works for both upload and download. Compatible with multi-part upload.
  • Routes your transfer through the nearest AWS edge location (200+ worldwide) instead of the public internet all the way to the target region.

Transfer acceleration minimizes the distance traveled over the public internet by routing through a nearby edge location, then uses AWS's fast private backbone the rest of the way.

Speeding up downloads: S3 Byte-Range Fetches

  • Parallelize GET requests by fetching specific byte ranges of a file at once.
  • Improves resilience too — if one byte-range request fails, you can retry just that smaller range instead of the whole file.
  • Also useful to fetch just part of a file — e.g. reading only the first 50 bytes to grab a header, without downloading the whole thing.

6 S3 Object Tags & Metadata

User-defined metadata

  • Key-value pairs attached to an object, set at upload time.
  • User-defined metadata keys must start with x-amz-meta- (to distinguish them from AWS-generated metadata like Content-Length or Content-Type).
  • Example: x-amz-meta-origin: paris.

Object tags

  • Also key-value pairs, but more commonly used — same concept as tags elsewhere in AWS.
  • Useful for fine-grained permissions (e.g. only allow access to objects with a specific tag) and for analytics (e.g. group S3 Analytics results by tag).
  • Example: Project: Blue, PHI: True.
Important Neither metadata nor tags are searchable in Amazon S3. You cannot filter or query objects by metadata or tag values directly on S3.

How do you search, then?

Build an external index in a database — e.g. DynamoDB — that stores the metadata/tags in a searchable form. You query that index, and the search results point you to the matching objects in S3.

Since S3 can't search metadata/tags itself, queries hit an external index (like DynamoDB) which then points to the matching objects stored in S3.

Exam point "How would you make S3 objects searchable by metadata/tags?" → build an external searchable index (e.g. DynamoDB) that mirrors the metadata/tags, then resolve search results back to S3 objects.

✓ Cheat Sheet

Key facts to remember

  • Lifecycle rules = transition actions (move between storage classes) + expiration actions (delete objects, old versions, or incomplete multi-part uploads); can target a whole bucket, a prefix, or specific tags.
  • S3 Analytics gives transition recommendations, but only for Standard ↔ Standard-IA; report updates daily and takes 24–48 hrs to populate.
  • S3 Event Notifications can go directly to SNS, SQS, or Lambda (each needs a resource policy authorizing S3), or to EventBridge (all events flow there too, unlocking 18+ destinations and advanced filtering).
  • Baseline performance: 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD requests per second, per prefix — no limit on number of prefixes.
  • Multi-part upload: recommended over 100MB, required over 5GB — parallelizes uploads.
  • Transfer Acceleration: routes through edge locations to minimize public-internet travel; works for upload & download; compatible with multi-part upload.
  • Byte-Range Fetches: parallelize/resume GETs, or fetch just part of a file (like a header).
  • Metadata (x-amz-meta-*) and tags are both key-value pairs on objects, but neither is searchable — tags are also useful for fine-grained permissions and analytics grouping.
  • To search S3 objects by metadata/tags, build an external searchable index (e.g. DynamoDB) that mirrors that data.

Mental model

This section is about running S3 efficiently at scale: lifecycle rules automate moving or deleting objects as they age so you're not manually managing storage tiers; event notifications let other AWS services react instantly when something happens in a bucket; performance features (multi-part upload, transfer acceleration, byte-range fetches) exist because S3 itself scales extremely well per-prefix but a single connection or single request doesn't — so you parallelize and route smartly; and tags/metadata add context to objects, but since S3 can't search on them, real search means building your own index elsewhere and using S3 purely as the object store.
