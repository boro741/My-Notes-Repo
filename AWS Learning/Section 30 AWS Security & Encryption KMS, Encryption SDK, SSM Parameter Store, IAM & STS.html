1 Encryption 101

There are three encryption patterns you'll see across AWS services.

In-flight protects data crossing the network; at-rest server-side lets the server manage the key; client-side means the storage layer never even sees the plaintext or the key.

TypeWhere encryption/decryption happensProtects against
In-flight (TLS/SSL)Client encrypts before sending; server decrypts after receivingMan-in-the-middle attacks on public networks — this is what HTTPS means
At rest — server-sideServer encrypts on receipt (using a data key), decrypts before serving it backAnyone reading the storage medium directly, but the server itself can still decrypt
Client-sideClient encrypts and decrypts; the server/storage only ever holds ciphertextA storage service you don't fully trust — it can never decrypt your data

2 KMS Overview

KMS (Key Management Service) manages encryption keys for you. It's fully integrated with IAM for authorization, and every API call made against a key is logged in CloudTrail for auditing. Most AWS services with an "enable encryption" checkbox are using KMS under the hood — and you can also call KMS directly (CLI/SDK) to encrypt your own application secrets instead of ever storing them in plain text.

Symmetric keys are the default — the key itself is never exposed. Asymmetric keys let someone without KMS API access encrypt data with the public half.

Types of KMS keys

Key typeCostNotes
AWS owned keysFreeInvisible to you — used for things like SSE-S3 or a DynamoDB-owned key
AWS managed keysFreeNamed aws/<service> (e.g. aws/rds); usable only from within that service
Customer managed keys$1/month (+ $1/month if imported)Full control — custom key policies, rotation settings, cross-account sharing
  • Pricing for API calls: roughly 3 cents per 10,000 requests.
  • Rotation: AWS managed keys rotate automatically every year; customer managed keys can have automatic rotation on a period you set, or on-demand rotation; imported keys can only be rotated manually (via an alias).
  • KMS keys are regional. Moving an encrypted resource (e.g. an EBS snapshot) to another region means: snapshot it (still encrypted with the original key) → copy the snapshot to the target region, re-encrypting it with a different KMS key there → restore a new volume from that copy.
Exam point A KMS key policy is required for anyone to use the key at all — unlike IAM, there's no implicit account-wide access without one. The console's default key policy grants the whole account access (still gated by ordinary IAM permissions); a custom key policy lets you name specific principals, including other AWS accounts, directly.

3 KMS Hands On (CLI)

Creating a customer managed key involves choosing: symmetric or asymmetric; key usage (encrypt/decrypt vs sign/verify); key origin (KMS-generated, External for an imported key, or a Custom key store backed by CloudHSM); single-region or multi-region; an alias; key administrators; key users; and optionally other AWS accounts to grant access to. Leaving the "who can use this key" step untouched creates the default key policy (whole account, gated by IAM).

Once created, you can view the key policy (as JSON, or a friendlier default summary), enable automatic rotation (a period from 90 up to 2,560 days) or trigger rotation on demand, and see the rotation history.

Encrypt / decrypt via the CLI

  1. aws kms encrypt --key-id alias/tutorial --plaintext fileb://ExampleSecretFile.txt --query CiphertextBlob --output text --region ... → a base64 ciphertext blob.
  2. Base64-decode that blob to get the raw encrypted binary file — this is the artifact you'd actually share/store.
  3. aws kms decrypt --ciphertext-blob fileb://... --query Plaintext --output text --region ... → KMS automatically knows which key to use, since that's embedded in the ciphertext blob itself.
  4. Base64-decode the result to recover the original plaintext.
Good to know You never have to tell decrypt which key was used — that information travels along with the encrypted blob.

4 Envelope Encryption & Encryption SDK

KMS's basic Encrypt/Decrypt calls are capped at 4 KB of data. For anything bigger, use envelope encryption via the GenerateDataKey API.

KMS only ever generates the small data key; all the heavy encryption/decryption of the actual file happens client-side, using local CPU.

To decrypt: send just the small encrypted DEK to KMS's Decrypt API (well under the 4 KB limit) to get back the plaintext DEK, then use that locally to decrypt the big file — no size limit on the file itself, since KMS never touches it directly.

AWS Encryption SDK

Implementing this pattern by hand is fiddly, so AWS provides the Encryption SDK (a CLI tool, plus libraries for Java, Python, C, and JavaScript) that automates it. It also adds data key caching — reusing a DEK across multiple encryptions instead of calling GenerateDataKey every time — via a LocalCryptoMaterialsCache, bounded by max age, max bytes, or max messages per key.

Trade-off Data key caching means fewer (cheaper) KMS calls, but the same DEK now protects more data — a deliberate security-vs-cost trade-off, still widely used in practice.
APIPurpose
EncryptEncrypt up to 4 KB of data directly through KMS
GenerateDataKeyReturns both a plaintext DEK and an encrypted copy of it — the one to use for envelope encryption
GenerateDataKeyWithoutPlaintextReturns only the encrypted DEK, for use later — needs an extra decrypt step before use, so it's not what you call to start envelope encryption right now
DecryptDecrypt up to 4 KB — including decrypting an envelope's DEK
GenerateRandomReturn a random byte string
Exam trap GenerateDataKeyWithoutPlaintext sounds similar but is the wrong choice for immediate envelope encryption — you want GenerateDataKey, which hands you the plaintext DEK right away.

Hands-on: Encryption SDK CLI

Installed via pip install aws-encryption-sdk-cli. With a CMK ARN exported as an environment variable, encrypt a file (e.g. over 1 MB) against that key — it produces an encrypted output file plus a metadata JSON (showing the algorithm, data key info, key provider, and encryption context). The paired decrypt command recovers the original file exactly.

5 KMS Limits

Exceeding KMS's request quota returns a ThrottlingException. All cryptographic operations — Encrypt, Decrypt, GenerateDataKey, GenerateRandom, etc. — share one combined quota per account, per region, and this includes calls other services make on your behalf (e.g. S3 using SSE-KMS).

  • Symmetric CMK quota is typically 5,500–10,000 requests/sec shared across all operations, up to 30,000/sec in some regions.
Three ways to handle throttling (1) Exponential backoff, for transient spikes. (2) Reduce KMS calls with the Encryption SDK's data key caching. (3) Request a service quota increase via API or an AWS Support ticket.

6 KMS + Lambda Practice

The problem: never hardcode a secret (e.g. a DB password) directly in Lambda code. Plain environment variables are better, but anyone with console access to the function's configuration can still read them in plain text.

The fix: in the environment variable's encryption configuration, enable encryption helpers and pick a KMS key — Lambda encrypts the value and only ever displays/stores the ciphertext. At runtime, the function's code calls the KMS Decrypt API (via the SDK) on that ciphertext to recover the plaintext value.

Watch out This decrypt call needs the Lambda's execution role to have an explicit kms:Decrypt permission scoped to that specific key ARN (an inline policy is fine) — otherwise the call fails with AccessDeniedException. Also budget a little extra time in the function's timeout setting, since the KMS round-trip takes longer than the 3-second default.

7 S3 Bucket Key

An S3 Bucket Key is an SSE-KMS optimization that can cut the number of calls S3 makes to KMS — and your KMS cost — by up to 99%, with no loss of security.

Without a bucket key, every object upload calls KMS directly. With it, KMS generates one data key periodically, and S3 reuses it locally to encrypt many objects — far fewer KMS calls.

Enabled per-bucket alongside SSE-KMS (on by default in the console). Trade-off-free from a security standpoint — just fewer direct KMS API calls and, as a side effect, fewer KMS-related CloudTrail events for that bucket.

8 KMS Key Policies & IAM Principals

A key policy decides who can touch a KMS key — with no key policy at all, nobody can use the key, which is different from ordinary IAM's default-deny-until-granted model. The default (console-created) key policy allows the whole account access, still gated by regular IAM permissions on each user/role.

A custom key policy can name specific principals directly, without needing a separate IAM grant for them:

Principal typeExample
Account / root userThe whole account, with IAM policies still applying on top
Specific IAM roleA role ARN named directly in the policy's principal block
IAM role sessionsAn assumed role, or an identity federated in (e.g. via Cognito or SAML)
Specific IAM userA named user, in your account or another account
Federated user sessionsA specific federated user
AWS service principalAllow a specific service (e.g. logs.amazonaws.com) to use the key
Everyone"AWS": "*"
Exam point This is exactly the mechanism behind cross-account KMS access — e.g. sharing an encrypted EBS snapshot with another account requires naming that account (or a role in it) directly in the key's policy.

9 CloudHSM Overview

With KMS, AWS manages the encryption software and (for AWS-owned/managed keys) can touch the underlying key material. With CloudHSM, AWS provisions dedicated, tamper-resistant hardware (an HSM device, FIPS 140-2 Level 3 compliant) — and you manage your own encryption keys entirely; AWS has no access.

  • Supports both symmetric and asymmetric keys (e.g. SSL/TLS keys).
  • No free tier; requires the CloudHSM client software to connect.
  • Integrates with Redshift for database encryption, and is a strong fit for SSE-C on S3, since you fully control your own keys.
  • Clusters span multiple AZs for high availability — clients can connect to either.

A KMS custom key store bridges CloudHSM into services that only know how to talk to KMS — calls still get logged in CloudTrail.

10 SSM Parameter Store

SSM Parameter Store is secure, serverless, scalable, durable storage for configuration and secrets. Values are optionally encrypted with KMS; updates are version-tracked; access is controlled by IAM; EventBridge can send notifications; and it integrates with CloudFormation.

Parameters are organized hierarchically by path, so IAM policies can scope access to a whole app, a whole environment, or one specific value.

You can also reference a Secrets Manager secret through the Parameter Store API, and pull AWS-published public parameters (e.g. the latest Amazon Linux AMI ID for a region).

Standard tierAdvanced tier
CostFree$0.05/month per parameter
Max parameters10,000100,000
Max size4 KB8 KB
Parameter policiesNoneTTL/expiration, no-change notifications

Parameter policies (advanced only): a TTL/expiration forces rotation of stale secrets (EventBridge notifies ahead of the deadline so you can update in time), and a no-change notification alerts you if a value hasn't been updated in X days.

CLI hands-on

  • aws ssm get-parameters --names /my-app/dev/db-url /my-app/dev/db-password --with-decryption — --with-decryption is required to get plaintext back for a SecureString.
  • aws ssm get-parameters-by-path --path /my-app --recursive --with-decryption — fetches everything under a hierarchy in one call.

11 Secrets Manager

Secrets Manager is purpose-built for secrets: it supports forced automatic rotation on a schedule via a Lambda function (AWS provides ready-made rotation Lambdas for RDS, Redshift, and DocumentDB, or you write your own), has tight native integration with those databases (storing and rotating the username + password directly), and mandates KMS encryption.

Native rotation: Secrets Manager invokes a Lambda on a schedule, which updates both the secret's value and the actual database credential.

Also supports multi-region secrets — replicated from a primary region and kept in sync — useful for multi-region apps, disaster recovery, or promoting a replica to standalone if the primary region has an issue.

Hands-on: create a secret as a database credential type (attachable directly to RDS/Redshift/DocumentDB) or a generic key/value or plaintext secret; choose a KMS key; optionally enable rotation on a schedule (e.g. every 60 days) tied to a Lambda; retrieve it at runtime via a get_secret_value-style SDK call. Pricing is roughly $0.40/secret/month plus $0.05 per 10,000 API calls, with a 30-day free trial per secret.

13 CloudFormation — Secrets Manager & SSM Integration

Dynamic references let a CloudFormation template pull a live value from SSM or Secrets Manager at create/update/delete time, using {{resolve:service-name:reference-key}}:

PrefixSource
ssmA plaintext value in SSM Parameter Store
ssm-secureA SecureString value in SSM Parameter Store
secretsmanagerA secret value in Secrets Manager

Example uses: resolving an S3 bucket's access-control setting from an SSM parameter, an IAM user's password from an SSM SecureString, or an RDS instance's master username/password directly from Secrets Manager.

RDS/Aurora specifics

  • Setting ManageMasterUserPassword: true on the DB resource makes RDS itself create and manage the Secrets Manager secret implicitly — retrieve its ARN in the template's outputs via GetAtt.
  • Alternatively, define the secret explicitly in the template (using GenerateStringKey to auto-generate a password), reference it into the DB instance with a dynamic reference, and add a secret-target attachment resource linking the two — this keeps the secret rotating in sync with the actual database credential.

14 CloudWatch Logs Encryption

CloudWatch Logs can be encrypted with a KMS key at the log group level (not per log stream). This can only be done via the CLI/SDK — associate-kms-key for an existing log group, or create-log-group with a key ID for a new one — not through the console.

Watch out Association fails with an access-denied error unless the KMS key's policy explicitly grants the logs.<region>.amazonaws.com service principal permissions (encrypt, decrypt, re-encrypt, generate data key, describe) — this has to be added manually to the key policy first.

15 CodeBuild Security

  • CodeBuild runs outside your VPC by default, but can be launched inside your VPC to reach VPC-only resources.
  • Never store secrets as plaintext CodeBuild environment variables. Instead, define an environment variable whose value is a reference to an SSM Parameter Store parameter or a Secrets Manager secret — CodeBuild resolves it and injects the real value into the build container at runtime.
  • The CodeBuild project's IAM role needs the matching SSM/Secrets Manager read permissions for this to work.

16 AWS Nitro Enclaves

For processing highly sensitive data (PII, healthcare, financial, credit card data) in a fully isolated compute environment — without hand-rolling a locked-down VPC — use Nitro Enclaves.

The enclave shares the host's CPU and memory but is otherwise walled off — no persistent storage, no interactive access, no external networking.

  • Cryptographic attestation ensures only your signed code can run inside the enclave.
  • Combined with KMS encryption, you can guarantee that only the enclave (nothing else) is able to decrypt the sensitive data.
  • Setup: launch a Nitro-compatible EC2 instance with EnclaveOptions: true, package the app into an Enclave Image File (EIF) with the Nitro CLI, then launch the enclave from that image.
  • Use cases: private key processing, credit card processing, secure multi-party computation.

✓ Cheat Sheet

Key facts to remember

  • Three encryption patterns: in-flight (TLS/SSL, protects against MITM), at-rest server-side (server manages the key), client-side (server/storage never sees plaintext or key).
  • KMS symmetric keys are never exposed — only usable via API calls; asymmetric keys let you download the public key for encryption outside AWS, or sign/verify.
  • Three kinds of underlying keys: AWS owned (free, invisible), AWS managed (free, aws/<service>), customer managed ($1/month — needed for custom key policies, custom rotation, and cross-account sharing).
  • KMS Encrypt/Decrypt caps out at 4 KB — bigger data needs envelope encryption via GenerateDataKey (returns plaintext + encrypted DEK); GenerateDataKeyWithoutPlaintext is the exam trap since it needs an extra decrypt step.
  • All KMS cryptographic operations share one quota per account/region; handle throttling with exponential backoff, data key caching, or a quota increase request.
  • S3 Bucket Keys cut SSE-KMS API calls (and cost) by up to 99%, with no security downside.
  • A KMS key policy is mandatory — no policy means no access at all; custom policies can name specific principals (users, roles, services, other accounts) directly, which is how cross-account key sharing works.
  • CloudHSM = dedicated, single-tenant, tamper-resistant hardware fully under your control (no AWS access); a KMS custom key store bridges it into services that only speak "KMS."
  • SSM Parameter Store: hierarchical config/secrets, optional KMS encryption, no native rotation, Standard (free, 4 KB) vs Advanced ($0.05/mo, 8 KB, parameter policies/TTL).
  • Secrets Manager: built for secrets specifically — native scheduled rotation via Lambda, mandatory KMS encryption, deep RDS/Redshift/DocumentDB integration, multi-region replication.
  • CloudFormation dynamic references ({{resolve:...}}) pull live SSM/Secrets Manager values at deploy time via the ssm, ssm-secure, and secretsmanager prefixes.
  • CloudWatch Logs encryption is per log group, CLI/SDK-only, and needs the log service principal explicitly added to the KMS key's policy.
  • Nitro Enclaves give you an isolated, no-storage, no-SSH, no-network VM for the most sensitive data processing, gated by cryptographic attestation and KMS.

Mental model

Everything in this section boils down to one question: who is allowed to see the plaintext, and when? In-flight, at-rest, and client-side encryption answer that for data in motion vs. at storage vs. never-trust-the-server. KMS is the key-management backbone underneath almost every AWS encryption feature — symmetric keys you never see directly, a hard 4 KB ceiling that pushes you toward envelope encryption for anything bigger, and a key policy model where silence means "nobody gets in." Parameter Store and Secrets Manager both hold configuration and secrets, but solve different problems: one is cheap and general-purpose, the other is built specifically around automatic rotation and database integration. CloudHSM and Nitro Enclaves sit at the far end of the trust spectrum — dedicated hardware and fully isolated compute for the cases where "AWS manages it for you" isn't good enough.
