1 EC2 Instance Metadata (IMDS)

IMDS (Instance Metadata Service) lets an EC2 instance learn about itself — without needing an IAM role just to ask "who am I?". The instance talks to a special local URL:

http://169.254.169.254

  • From this URL you can get things like the instance name, public IP, private IP, and more.
  • You can also retrieve the IAM role name attached to the instance, and even get temporary credentials for that role.
  • You cannot see what IAM policy is attached to the role — just the role's credentials.
Terminology Metadata = information about the instance itself. User data = the launch script you gave the instance at boot. Both are accessible through this same base URL, but this lecture is only about the metadata side.

IMDSv1 vs IMDSv2

VersionHow it worksNotes
IMDSv1Query the metadata URL directlySimple, but less secure
IMDSv2Two steps: (1) PUT a request to get a session token, (2) pass that token as a header when calling the metadata URLMore secure, enabled by default since 2023; more overhead but AWS made this the default for security reasons

IMDSv2 flow: the instance first requests a session token, then uses that token as a header to read its own metadata or IAM role credentials.

2 IMDS Hands On

  • When launching an EC2 instance, under Advanced details there's a Metadata version setting: V1 and V2 or V2 only.
  • Amazon Linux 2023 defaults to V2 only. Older AMIs like Amazon Linux 2 let you choose either.
Don't forget On Amazon Linux 2023, trying IMDSv1 directly (plain curl against the metadata URL) returns 401 Unauthorized. You must use the IMDSv2 token flow instead.

Using IMDSv2 from the instance

  1. Get a token: TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 21600") (the exact command is looked up from AWS docs).
  2. Use the token as a header on subsequent requests: curl -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/
  3. A trailing slash means you're looking at a "directory" (more data inside); no trailing slash means you get an actual value.
  4. Examples: .../meta-data/hostname returns the hostname, .../meta-data/local-ipv4 returns the private IP.

Getting IAM role credentials via IMDS

  • Path: .../meta-data/iam/security-credentials/
  • With no IAM role attached to the instance, this returns 404 Not Found.
  • After attaching a role (EC2 console → Actions → Security → Modify IAM role) and waiting ~30 seconds, querying .../security-credentials/<role-name> returns a JSON blob with an Access Key ID, Secret Access Key, Session Token, and an expiration (roughly an hour or so out).
Good to know You never have to do this by hand in real usage — the AWS CLI and SDK automatically call IMDS behind the scenes to get an instance's IAM role credentials. This lecture is just showing you what's happening under the hood.

3 AWS CLI Profiles

If you work with multiple AWS accounts, profiles let you store separate sets of credentials locally and switch between them on the command line.

  • Your ~/.aws/credentials file normally has a [default] section with an access key + secret key. ~/.aws/config has matching [default] settings like region.
  • To add another account, run aws configure --profile <name> (e.g. aws configure --profile my-other-aws-account) and enter that account's access key, secret key, region, and output format.
  • This creates a new named section (e.g. [my-other-aws-account]) in both the credentials and config files, alongside [default].

Using a profile

  • aws s3 ls — runs against the default profile.
  • aws s3 ls --profile my-other-aws-account — runs against that specific profile instead.
Real-world tip Not an exam topic, but genuinely useful: once you're juggling multiple AWS accounts, always set up named profiles and pass --profile explicitly so you don't accidentally run commands against the wrong account.

4 AWS CLI with MFA

To use Multi-Factor Authentication with the CLI/SDK, you need a temporary session, obtained via the API call sts get-session-token.

Exam point Remember the API name: STS GetSessionToken. You pass it your MFA device's serial number, the current token code from the device, and how long you want the credentials to last. It returns a temporary Access Key ID, Secret Access Key, and Session Token.

Hands-on steps

  1. In IAM → your user → Security credentials, assign a virtual MFA device (scan the QR code with an app like Authy, enter two consecutive MFA codes to confirm).
  2. Note the MFA device's ARN — you'll need it as the serial number.
  3. Run: aws sts get-session-token --serial-number <mfa-arn> --token-code <current-code>
  4. This returns temporary credentials (expiring in about an hour).
  5. Create a new profile for them: aws configure --profile mfa (enter the temporary access key + secret key).
  6. Manually edit ~/.aws/credentials to add a line under that profile: aws_session_token = <token> (the configure command doesn't have a prompt for the session token, so you add it directly in the file).
  7. Now aws s3 ls --profile mfa makes calls using your temporary, MFA-backed credentials.
Key takeaway Even if the hands-on steps feel fiddly, the one thing to remember is: STS GetSessionToken is the API for generating temporary, MFA-authenticated credentials (access key + secret key + session token).

5 AWS SDK Overview

The SDK (Software Development Kit) lets you call AWS services directly from your application's code, instead of going through the CLI.

  • AWS provides official SDKs for many languages: Java, .NET, Node.js, PHP, Python, Go, Ruby, C++ (and the list keeps growing).
  • You use the SDK whenever your code needs to make API calls to AWS services — e.g. DynamoDB or Amazon S3.
Fun fact The AWS CLI itself is written in Python and uses the Python SDK, Boto3, under the hood. So every time you've been running CLI commands in this course, you've indirectly been using an SDK already.

The exam expects you to know when to reach for an SDK (i.e., when you're building an application that needs to call AWS programmatically) — deeper hands-on SDK practice comes later in the course, in the Lambda functions section.

6 Exponential Backoff & Service Limit Increase

AWS has two types of limits ("quotas"):

TypeWhat it limitsExample
API rate limitsHow many times you can call a specific API per secondDescribeInstances (EC2): 100 calls/sec. GetObject (S3): 5,500 GETs/sec per prefix.
Service quotas (service limits)How many resources you can run at onceOn-Demand Standard instances: up to 1,152 vCPUs per account
  • Going over an API rate limit gets you throttled (intermittent errors) — the fix is an exponential backoff retry strategy.
  • If you're consistently hitting rate limits due to real heavy usage, request an API throttling limit increase from AWS.
  • Going over a service quota means requesting a service limit increase (open a support ticket, or call the Service Quotas API programmatically).
Exam point Whenever you see a "throttling exception" in an exam question, the answer is almost always: implement exponential backoff.

How exponential backoff works

Each time a request is throttled, you retry — but you wait double the time before the next retry: 1s → 2s → 4s → 8s → 16s...

Each retry waits twice as long as the last one — this spreads out the load so a server under pressure gets breathing room instead of getting hit even harder.

Good to know If you use the AWS SDK, exponential backoff retry logic is already built in. If you're calling the raw AWS API yourself, you are responsible for implementing it yourself.

7 AWS Signature v4 Signing (SigV4)

Every AWS HTTP API call needs to be signed so AWS knows who's making the request and whether they're authorized. Signing uses your credentials (access key + secret key) and the signing process itself is called SigV4 (Signature Version 4).

Good to know You don't need to know how to manually compute a SigV4 signature (it's a complicated 4-step process) — the CLI and SDK do this automatically for every request. Some requests, like reading a public S3 object, don't need to be signed at all; most other API calls do.

Two ways to send the signature

MethodHow
Authorization headerThe computed signature is sent in the HTTP Authorization header. This is what the CLI does by default.
Query stringThe signature is embedded directly in the URL, under the X-Amz-Signature query parameter.

Two valid places to carry a SigV4 signature: baked into the Authorization header, or appended to the URL as a query parameter.

Example from the console: opening an S3 object generates a browser URL containing a security token, the algorithm (AWS4-HMAC-SHA256 / SigV4), a date, an expiration, AMZ credentials (which account, etc.), and the AMZ signature itself — all passed as query string parameters so the browser can fetch the object without a separate Authorization header.

✓ Cheat Sheet

Key facts to remember

  • IMDS base URL: 169.254.169.254. IMDSv2 requires a token (via PUT) passed as a header on every subsequent request; IMDSv1 is direct but less secure and disabled by default on newer AMIs (e.g. Amazon Linux 2023).
  • You can read an instance's IAM role credentials from IMDS at .../iam/security-credentials/<role>, but never the policy attached to the role.
  • Use aws configure --profile <name> and --profile <name> on commands to manage multiple AWS accounts from one machine.
  • STS GetSessionToken is the API for getting temporary, MFA-backed credentials (access key, secret key, session token).
  • The CLI is built on the Python SDK (Boto3) — SDKs exist for many languages and are how applications call AWS programmatically.
  • Throttling exception → think exponential backoff. SDK includes this automatically; raw API usage means you implement it yourself.
  • Two kinds of AWS limits: API rate limits (calls/sec, fixed with backoff or a throttling limit increase) vs service quotas (resource counts, fixed with a service limit increase / Service Quotas API).
  • Every signed AWS API request uses SigV4; the signature travels either in the Authorization header or as an X-Amz-Signature query string parameter.

Mental model

This section is all about the plumbing behind every AWS request: an EC2 instance can ask a special local address who it is and borrow its IAM role's credentials (IMDS); a person can juggle multiple accounts and even prove their identity with MFA to get short-lived credentials (CLI profiles + STS); code talks to AWS the same way the CLI does, just through an SDK instead of a terminal; every request that reaches AWS gets rate-limited and needs to be signed with SigV4 so AWS can trust it; and when things get throttled, the fix is simply to back off exponentially rather than everyone hammering the API harder.
