Chapter One

What system design actually is

There are dozens of tools available to any engineer today — databases, caches, CDNs, load balancers, servers. But system design is the skill of choosing the right ones and putting them in the right place to solve an actual problem, like letting people share photos with each other.

This shows up as a real shift in what's expected of you as you grow in your career. A junior engineer builds one feature where the input and output are already known. A mid-level engineer gets handed a problem and has to figure out the approach themselves. And a senior engineer designs the system itself, making the calls on how the whole thing should work.

💡 What's a "server," exactly?

Nothing mysterious — it's just a computer sitting in someone else's data center whose entire job is answering requests from your app's visitors. You can rent one for a few dollars a month.

The best way to learn how senior engineers think isn't to memorize a list of tools. It's to watch a system get designed — and watch it fail — one piece at a time. That's exactly what we're going to do, starting with the simplest possible version of a photo-sharing app.

Chapter Two

Your first server, and how it breaks

You write the code for a photo-sharing app and rent one server for $10 a month. The web app, the database, and every uploaded photo — all of it lives on this one machine. Honestly, this is a great setup to start with. It's simple, it's easy to reason about, and when something breaks, there's only one place to look.

Then your app gets featured somewhere, and 10,000 people show up in a single day. That one server wasn't built for this. Even if it doesn't crash outright, it can turn painfully slow. Let's look at exactly how it fails — because every failure here has a name, and a fix, and that list of fixes is basically the whole field of system design.

🔥
CPU & RAM run outFixed by adding a load balancer and a second server
🗄️
Database gets hammeredFixed by adding a cache for popular answers
💀
The machine just diesFixed by replicas and external storage like S3

Failure one: every visitor opening their feed means your CPU is resizing images and running database queries at the same time. Pages that loaded in 200 milliseconds now take 10 seconds. The obvious fix is a second server, splitting people between the two. But that creates a new question: when someone opens your site, which of the two servers should answer? You need a traffic officer standing in front, deciding where each request goes — a load balancer.

Failure two: most of those 10,000 visitors are asking for the same things — the same trending photos, the same popular profiles — and your database re-runs the identical query from scratch every single time. The fix is to keep popular answers sitting in fast memory so you don't have to hit the database again. That fast memory layer is a cache.

Failure three: a disk fails, a power supply gives out, someone unplugs the wrong cable. Because everything lived on one box, your app goes down and every photo anyone uploaded could be gone. This has a name too — a single point of failure. The fix is keeping data on more than one machine: a replica of the database on a different server, and moving the actual photo files to external object storage built to keep multiple copies automatically.

📌 The pattern to notice

In all three fixes, we never rewrote the app or made the code smarter. We only split the work across machines and decided where each piece should live. That's really what system design is — and every fix brings a new problem of its own. The load balancer can die too. The cache can serve stale data. The replica can fall behind. That chain — fix something, get a new problem, fix that — is the rest of this article.

Chapter Three

Zooming in vs. zooming out: HLD & LLD

You'll hear two terms constantly in system design: HLD and LLD — high-level design and low-level design. Our photo app is a good way to see the difference.

High-Level Design

the zoomed-out view
  • The big pieces: app servers, database, cache, queue, CDN
  • How a request moves between them
  • Where does data live? What breaks first? How do we fix it?
  • "Design Instagram" is almost always asking for this

Low-Level Design

the zoomed-in view
  • One small feature — say, the like button
  • Which function handles the tap? Which class stores what?
  • How do you avoid counting the same like twice?
  • "Design an in-memory cache" is almost always asking for this

This is why interviewers say mismatched altitude is one of the most common ways candidates lose an interview. They rarely stop you — they just let you spend 20 minutes at the wrong height. So when someone says "design Instagram," say one sentence up front: "I'll stay at the high level — components, data flow, and trade-offs — and we can zoom into any one piece later if you want." That single sentence already shows you understand the difference. Most candidates just start going deep immediately.

Chapter Four

What vs. how well: requirements

Before designing anything, you need to answer two very different questions: what should the app do, and how well must it do it. The first is a functional requirement. The second is a non-functional requirement.

Functional

features you can point at and test
  • Sign up
  • Upload a photo
  • Follow another user
  • Scroll a feed
  • Like and comment

Non-Functional

qualities nobody demos, but everybody feels
  • Speed — does the feed load in 0.5s or 8s?
  • Durability — does a photo survive a disk failure?
  • Scale — does it work for a million users on a Saturday?
  • Availability and cost

Here's the part that actually matters: a photo app you build for your family and Instagram have nearly the same functional requirements. You can upload, follow, scroll, and like on both. What separates them entirely is non-functional requirements — one serves 10 people who'll tolerate a slow day, the other serves a billion people who leave after two seconds of lag. Every component we add from here on — load balancer, cache, replicas, queue — exists to meet a non-functional requirement. No user ever asks for a cache. Users ask for a fast app. The cache is just how you deliver that.

One warning: non-functional requirements fight with each other. Faster systems cost more money. An app that never goes down needs spare machines sitting idle, and idle machines still cost money every month. You can't add whatever you want — you have to decide what this specific app actually needs.

Chapter Five

Five questions before you draw anything

You can't design the right system if you don't know who it's for. Before touching a diagram, ask these five questions. For the rest of this piece, we'll assume our photo app has 10,000 users today, doubling every few months — so we design for the millions we're heading toward, not the 10,000 we have now.

1
How many users, and how fast are they growing?A thousand users and 50 million users are not the same system.
2
Read-heavy or write-heavy?People scroll hundreds of photos a month but post two or three. Reads dominate — so optimize the feed path hardest.
3
What can you never lose, and what can you afford to lose?Losing a photo loses a customer forever. A like-count off by three for a few seconds bothers nobody.
4
How much latency can we afford?The feed must feel instant, under ~200ms. An upload can take a few seconds — uploading already feels like "work" to a user.
5
What does it cost?Every extra server and every copy of your data is a monthly bill. The right design meets the first four answers for the least money.

Answer these for our photo app and a shape emerges immediately: build for millions, expect heavy reads, never lose a photo, make the feed feel instant, keep the bill sane. We haven't drawn a single box yet, but we already know the feed is the hard part and photos need the strongest durability. Anyone can say "add a cache." The real skill is being able to say why this app needs a cache and what the extra cost buys you.

🎯 In an interview

The first five minutes of a design interview aren't about design at all — they're about whether you ask these questions before you start drawing. The interviewer's answers become your pillars: every component you add later, you justify with one of them. "I'm adding a cache because we said reads dominate" is the kind of sentence interviewers remember.

Chapter Six

One codebase or many: monolith vs. microservices

In a monolith, the whole app — signup, uploads, feed, likes, comments — is one codebase deployed as one unit. Change the signup page, and you redeploy the whole thing. In microservices, that one program is split into many small, separately deployed programs — one for uploads, one for the feed, one for notifications — each with its own codebase, talking to each other over the network.

Monolith

the right call for our app today
  • Everything talks via direct function calls — nothing to fail over the network
  • One thing to deploy, one thing to test, one place to look when it breaks
  • A small team moves fast because there's less complexity

Microservices

earns its complexity at scale
  • Scale the feed to 10 servers without dragging uploads along too
  • 40 engineers can ship without stepping on each other's changes
  • Costs you: network calls that can fail, and debugging across services

Everyone assumes microservices are "the real deal" and monolith is something to be embarrassed about — that's just wrong. With only a few thousand users, the monolith is the correct choice for our photo app. Companies split off microservices for two real reasons: independent scaling (our feed is read-heavy and might need 10 servers while uploads need two — a monolith forces you to scale both together) and team size (40 engineers all deploying one codebase start queuing behind each other). Most companies you'll actually join run a monolith plus a handful of services that got split off for a specific reason — not one giant program, and not 300 tiny ones.

Chapter Seven

A bigger box, or more boxes

Your one server is maxing out — CPU at 80%, feeds loading slower than usual. There are exactly two ways to get more power.

Vertical Scaling

Make the server bigger — more CPU, more RAM, a faster disk. Zero code changes. But there's a ceiling, and the price stops scaling in a straight line.

Horizontal Scaling

Run many small servers instead of one big one. No upper limit, no single point of failure — need more capacity, add an 11th machine.

Vertical scaling is genuinely the right first move — if a bigger box buys you another year, take it. But once you've bought the biggest machine on the market, you're stuck, and going from the second-biggest to the biggest can double your bill for only 20% more power. Worse, one big server is still one server: if it goes down, your whole app goes down with it.

Horizontal scaling avoids both problems, but creates a new one immediately: with 10 servers running your app, which one should answer when a user opens it? That needs a load balancer standing in front. And those 10 servers can't each keep their own copy of the data — a photo uploaded to server 3 has to be visible when the next request lands on server 7. The rule of thumb: scale up vertically first because it's simple, then scale out horizontally when you hit the ceiling or can't afford a single point of failure. Jumping straight to a fleet of servers for an app that 50 people touch a day buys you nothing but complexity.

🎯 In an interview

"Your app is slow — why not just buy a bigger server?" The strong answer starts with vertical scaling (simple, zero code changes, buys you time), then names its ceiling and single-point-of-failure risk, then moves to horizontal scaling. Bonus points for being specific: a 50-user internal tool should stay vertical; a consumer app heading for a million users needs horizontal. Most real systems end up using both.

Every machine on the internet has an IP address — its phone number. Nobody types numbers, though, so the first stop is always a lookup.

💡 DNS, HTTP, and HTTPS in plain English

DNS (the domain name system) is the internet's phone book — the phone asks "where is photoapp.com?" and DNS answers with an IP address. Once the phone knows where to go, it needs a shared language to talk to the server: that's HTTP. You'll almost never see plain HTTP anymore, though — you'll see HTTPS, where the "S" means the whole conversation is scrambled. Without it, anyone on the same coffee-shop Wi-Fi can read your passwords in plain text as they travel past.

Two more terms get mixed up constantly. Latency is how long one round trip between user and server takes. Bandwidth is how much data you can push through at once — the width of the pipe. Here's why the difference matters: a feed showing 30 thumbnails isn't slow because thumbnails are large — they're tiny. It's slow because of round trips. Fetch 30 thumbnails one by one across half the planet, and you get 30 round trips, even on fast Wi-Fi. Two of the biggest components we'll add later — a cache that skips the trip to the database, and a CDN that answers from somewhere nearby — exist to fight exactly this.

There's one thing wrong with the journey above, though: the DNS answer points at one server, and we just decided we're running 10 of them. Which one should the phone actually talk to? That's the next chapter.

Chapter Nine

Load balancers, up close

Here's the trick: the IP address DNS hands back doesn't point at any of your 10 app servers. It points at the load balancer. The request lands there first, and the load balancer — which is really just another server running an application whose only job is forwarding traffic — sends it on to one healthy server.

Load Balancer + Health Checks

Every few seconds, the load balancer quietly pings each server: "still alive?" The moment one stops answering, traffic stops flowing to it — and users never see an error.

Any server sitting in front like this, taking requests on behalf of others, has a general name: a reverse proxy. A load balancer is just the most common kind you'll meet. So how does it decide who gets the next request?

🔁
Round robinServer one, then two, then three, then back to one — simple and good enough for a lot of apps
📊
Least connectionsSend the next request to whichever server currently has the fewest requests pending
⚖️
WeightedIf two servers are twice as big as the rest, give them a bigger share of the traffic

Most companies don't build their own load balancer — they use battle-tested ones like Nginx or HAProxy, or a managed one like AWS's Elastic Load Balancer. But this raises an obvious question: what if the load balancer itself dies? Every server behind it becomes unreachable. That's why real production systems never run just one — they run several, so if one fails, another takes over. How multiple load balancers coordinate with each other is a deeper problem we won't unpack here.

Chapter Ten

Stateless vs. stateful

Your app now runs on 10 servers behind a load balancer, traffic nicely spread out — and users start reporting they keep getting logged out. You didn't touch the login code. What's happening?

The bug

stateful servers
  • Allen logs in — the request lands on Server 1
  • Server 1 saves his login session in its own memory
  • His next click gets routed to Server 5
  • Server 5 has never heard of Allen: "please log in"

The fix

stateless servers + shared store
  • No server keeps anything important in its own memory
  • Login sessions move to one shared store (often Redis)
  • Any server checks the same store and finds Allen instantly
  • Servers become disposable — add one, kill one, nobody feels it

This is the single biggest thing that breaks when you go from one server to many. On one machine, keeping a login session in local memory worked fine because every request hit the same box. The moment a load balancer spreads users across servers, their data has to spread with them — except it doesn't, unless you move it somewhere shared. A server that keeps memory of previous requests is called stateful; one that forgets everything the instant it answers is stateless.

You'll hear people suggest sticky sessions instead — tell the load balancer to always send Allen back to Server 1. The problem is this brings back the exact issue you were escaping: if Server 1 dies, Allen loses his session anyway, and the load balancer can no longer spread traffic evenly since some users are now pinned to specific machines.

💡 A simple test for "stateful"

Ask one question: if this server vanished right now, would any user lose something? If yes, that data has no business living on the server — move it to a shared store. Note that storing photos in a database or cloud storage does not make a server stateful, because those files live outside the server. Stateful specifically means the server is keeping something in its own memory or local disk. Uploading, downloading, applying a filter, searching — all stateless. Login is the one call that genuinely needs memory between requests.

Chapter Eleven

Data modeling: features into records

Data modeling means deciding what information you need to store, breaking it into organized pieces, and figuring out how those pieces connect. Before picking a database, you have to know your access patterns — the questions your users will keep asking your app thousands of times a day.

For our photo app: show me a user's profile, show me all photos a user uploaded, show me my home feed, upload a photo, like a photo, comment on a photo, follow another user. That list is basically your whole app written down as questions — and once you have the questions, the data almost designs itself.

Notice the pattern: every connection is just a pair of IDs plus a little extra content. When Allen likes photo 42, we don't copy his name or the photo anywhere — we store a tiny record with his ID, the photo's ID, and a timestamp. Want the like count? Count the records that carry photo 42's ID. This is exactly why every user and every photo gets an ID in the first place — the IDs are what stitch the whole data model together. And notably, the actual image file never goes into the photo record — it just holds a small link to where the file actually lives (more on why in a later chapter).

A data model isn't a database choice yet — we haven't picked SQL or NoSQL. It just says what we store and how it connects. Take the access pattern "show me my home feed": to build it, the app has to find everyone Allen follows, pull recent photos from each of them, and sort everything by time. That one question touches the follows data, the photos data, and needs sorting — and it happens to be the single most common thing users do in this app. You'd only discover that by starting from the access patterns, not by picking a database first.

Chapter Twelve

SQL or NoSQL?

It boils down to one question: is your data structured or unstructured? Structured data gets an SQL database. Unstructured, free-shaped data gets a NoSQL database.

SQL

e.g. Postgres, MySQL
  • Data lives in fixed-shape tables — rows and columns, like a spreadsheet
  • Built to join tables together (follows → photos, in one query)
  • Gives you transactions — an ACID guarantee: a group of writes either all happen, or none do

NoSQL

e.g. MongoDB, DynamoDB, Elasticsearch
  • Loosens the structure — every record can have a different shape
  • Built to spread across hundreds of machines effortlessly
  • Great for things like raw user-behavior events, where every entry looks different

💡 What's a "transaction"?

Say Allen deletes a photo. You need to delete the photo record and every like and comment tied to it. Group all of that as one unit — a transaction — and either all of it succeeds, or none of it does. That's what stops you from ever ending up with orphaned likes pointing at a photo that no longer exists. This guarantee is part of what people mean when they say "ACID."

Our photo app's data is structured — photos always need the same fields — and full of relationships: users, photos, likes, and follows all need to connect. That points straight at SQL, and specifically Postgres. But real systems use both. User preferences (theme, notification settings, language) change shape often and rarely need to be joined with anything, so those go to NoSQL — in our case, MongoDB. It's just an if-condition in the app code deciding which database to ask, nothing magical. If you're ever unsure which to reach for, start with SQL — it'll take you further than most people expect.

Chapter Thirteen

Indexing: the book's back page

As your user base grows, some queries quietly get slow. "Show me all of Allen's photos" used to be instant. Now the database has to check every single row — was this one Allen's? No. This one? No. — one by one, through millions of rows.

Full Scan vs. Indexed Lookup
Without an indexchecks every row
With an indexjumps straight there

Think of the index at the back of a textbook: it doesn't make you read every page to find "mitochondria" — it just tells you it's on pages 1, 100, and 125.

An index does exactly that for a database column. Create one on the "posted by" column, and the database now knows Allen's photos sit at row 822, then 15,000, then 100,000 — and it jumps straight there instead of scanning everything.

So should you index every column? No — creating and maintaining an index is real work. Every new signup, every new photo, means the index has to be rewritten to include it. More indexes means more of that upkeep on every single write. For our photo app, we'd index "posted by" (fast per-user lookups) and "upload time" (fast sorting for the feed).

Don't guess
Find your actually-slow queries first, then index the columns behind them
3–5

Chapter Fourteen

Caching: don't ask twice

Say a public figure with millions of followers posts a photo. Millions of people now ask the database for the exact same record, over and over. It doesn't make sense to fetch identical data that many times — so we add a cache: a small, blazing-fast store of popular items, sitting in front of the database.

Typical read speed
Cache (e.g. Redis)< 1 ms
Database20–30 ms

Here's how it plays out: a request comes in for the trending photo. First, the app checks the cache. If it's there — a cache hit — the answer comes straight back, and the database never even hears about the request. If it's not there — a cache miss — the app fetches it from the database, writes a copy into the cache, and returns it. Every request after that first one is served straight from the cache.

Request→Cache ✓→Userhit, <1ms
Request→Cache ✗→Database→Usermiss, writes cache on the way back

Good cache entries share three properties: small, read constantly, and rarely changing — trending photos, popular profile cards, and (as it turns out) login sessions too. Redis, the same shared store we used for sessions in Chapter Ten, usually ends up doing both jobs at once.

But now you have two copies of the same data — one in the cache, one in the database — and you have to answer the hard question: what happens when one changes and the other doesn't? Two tools handle this.

TTL

time to live — the lazy fix
  • Write data into the cache with an expiry, e.g. "good for 60 seconds"
  • After it expires, the next request misses, fetches fresh data, refills the cache
  • Fine for a trending feed. Not fine for something that must be correct instantly.

Active invalidation

the moment data changes, delete the old copy
  • User edits their bio → app writes the new bio and deletes the cached one
  • Next request misses on purpose, pulls the fresh value
  • More bookkeeping, but zero window of stale data
🏠
Home feed~30s TTL
👤
Profile carda few minutes TTL
🔥
Trending list~60s TTL
🔒
Privacy settingsno TTL — active invalidation only

⚠️ Cache stampede

When a genuinely popular entry expires and thousands of requests miss the cache at the exact same instant, they all slam the database with the identical query at once — a cache stampede. One defense: stagger TTLs slightly so hot entries don't all expire together. Another: let one request rebuild the entry while everyone else briefly gets the old value. And when the cache fills up, the standard eviction rule is LRU — least recently used — throwing out whatever nobody has touched in the longest time. Bringing up the stampede before an interviewer asks is a strong signal: it shows you've thought about the failure, not just the feature.

Chapter Fifteen

Replication: don't bet it all on one machine

We've only added one database so far. If it goes down, we lose everything — a single point of failure again. The fix is replication: keep exact copies of the database on other machines. The industry standard is two replicas, so you end up with three total copies — one primary, two replicas.

Primary → Replicas
🗄️ Primary Database
Replica 1streams from primary
Replica 2streams from primary

Replicas keep an open connection to the primary and continuously stream its changes — which means they're always a few milliseconds behind. That gap is called replication lag.

Since you're paying for three databases, use all three: distribute reads across all of them (with a small load balancer of their own), while all writes go only to the primary. Why only the primary? Because if two different writes landed on two different databases at the same moment, you'd have no way to know which value was actually correct. Writing in exactly one place avoids that entirely.

The bug replication lag creates

Allen uploads a new photo — the write lands on the primary. Half a second later he refreshes his own profile. That read gets routed to Replica 2, which hasn't received the new photo yet. For a brief moment, Allen's own profile shows no new photo — even though the photo was never lost, just sitting safely on the primary the whole time.

The database world calls this eventual consistency — the replica doesn't have the newest write yet, but it will. The fix for Allen's case: when a user reads their own recent data, send that read to the primary, where you're guaranteed the latest value. That's strong consistency. Everyone else viewing Allen's profile can keep reading from the replicas — if a stranger sees his new photo half a second late, nobody's hurt. Most of a photo app is perfectly happy with eventual consistency; deciding which slice needs strong consistency instead is a real design skill.

Replication also solves the original single-point-of-failure problem: if the primary dies, one replica gets promoted to take its place — a process called failover. But here's the single most dangerous misunderstanding people have about replicas: if someone runs a bad delete query on the primary and wipes a million records, the replicas will faithfully copy that mistake too, within milliseconds. Replication protects you from hardware dying. It does not protect you from human error — that's what real backups (snapshots kept away from the live system) are for.

Chapter Sixteen

Sharding: when one machine isn't enough

Fast-forward to 50 million users and billions of photos, comments, and likes. Eventually the data is simply too big to fit on one database machine — and replicas can't save you here, because every replica has to hold the exact same data as the primary. The answer is sharding: split the data across many databases, where each one — a shard — holds only a slice.

You pick one field to split on — the shard key. For our photo app, that's the user ID. A simple rule: divide the user ID by the number of shards, and the remainder tells you which shard to use. Allen's ID is 10; 10 ÷ 4 leaves a remainder of 2, so Allen lives on shard 2.

4 shards — user IDs split by ID mod 4
Shard 0
Shard 1
Shard 2
Shard 3

Two things commonly go wrong here. First, a hot shard: if every celebrity account happens to land on the same shard by bad luck, that one machine gets crushed while the others sit idle. The fix is picking a shard key that scatters big accounts evenly. Second, and worse: what happens when you add a fifth shard?

5 shards — the naive rule (ID mod 5) reshuffles almost everyone
Shard 0
Shard 1
Shard 2
Shard 3
Shard 4

Your rule changes from "divide by 4" to "divide by 5" — and the remainder changes for almost every single user ID, meaning nearly all of your data would need to physically move between machines. Moving billions of photos just because you added one server is a nightmare. The industry fix is consistent hashing: each shard owns a small, fixed range, so adding a new shard only takes over a slice from one neighbor — the rest stay exactly where they are. Databases like MongoDB already build this in, so you rarely have to implement it by hand. And as a rule, use sharding as late as possible — once data is split across shards, joining it back together is the hardest thing to undo.

Notice what never happened anywhere in this list: we never made the code cleverer. We only decided where each piece of work and each piece of data should live — and we only added a component once a specific, named failure forced our hand. That habit, more than any diagram, is what separates someone who designs systems from someone who just collects components.
