Chapter One

The one-server app, and how it dies

Imagine you built a photo-sharing app. You rented one server for $10 a month — think of a server as just a computer sitting in someone else's data center, whose only job is to answer requests from your users. The web app, the database, and every uploaded photo all live on this one machine.

Honestly? This is a great way to start. It's simple, cheap, and easy to debug — if something breaks, there's only one place to look. Almost every real app in the world started exactly like this.

Then one day your app gets featured somewhere, and 10,000 people show up in a single day. Your one server starts falling apart in three specific ways — and every one of these failures has a name and a fix. That list of fixes is basically the entire field of system design.

Three ways a single server fails
flowchart TD
    A["10,000 users show up at once"] --> B["Failure 1: Server runs out of CPU/RAM
Pages that took 200ms now take 10s"]
    A --> C["Failure 2: Database gets hammered
Same popular query, run again and again"]
    A --> D["Failure 3: The machine just dies
Disk fails, power goes, cable unplugged"]
    B --> E["Fix: Add a 2nd server + Load Balancer"]
    C --> F["Fix: Add a Cache in front of the DB"]
    D --> G["Fix: Replicate DB + store photos in external storage (S3)"]

Notice something important: at no point did we rewrite the app or make the code "smarter." We simply split the work across machines and decided where each piece should live. That's the real definition of system design. And every fix creates a brand new mini-problem of its own — the load balancer can die too, the cache can serve stale data, the replica can fall behind. That endless chain of "fix something → get a new problem → fix that" is exactly what the rest of this course (and this blog) is about.

🧑‍💻 Junior vs Senior, in one line

A junior engineer builds one known feature. A mid-level engineer is handed a problem and figures out how it fits the existing system. A senior engineer designs the system itself — deciding how the whole thing should work.

Chapter Two

High-Level Design vs Low-Level Design (HLD vs LLD)

You'll hear these two terms constantly, so let's nail them down using our photo app.

  • High-Level Design (HLD) is the zoomed-out view — the big blocks: app servers, database, cache, queue, CDN, and how a request moves between them. When someone says "design Instagram," they usually want HLD: where does data live, what breaks first, how do we fix it.
  • Low-Level Design (LLD) zooms into one small feature, like the "like" button. Which function handles the tap? How do we avoid counting the same user's like twice? This is about classes, functions, and data structures inside one box.

🎯 Interview tip

The moment you're asked "design Instagram," say out loud: "I'll stay at the high level — components, data flow, and trade-offs — and we can zoom into any one part later." One sentence, and you've already shown you understand altitude. Interviewers say answering at the wrong altitude (going deep into code when they wanted the big picture, or vice versa) is one of the most common ways candidates quietly lose the interview — the interviewer often won't even stop you, they'll just let you spend 20 minutes at the wrong height.

Chapter Three

What should it do vs. how well should it do it

Before designing anything, you must separate two very different questions.

Functional RequirementsNon-Functional Requirements
Sign upFeed loads in < 200ms, not 8 seconds
Upload a photoPhoto survives even if a disk fails
Follow a userWorks for 1 million users on a Saturday, not just 100
Scroll the feedStays affordable to run every month
Like / commentAvailable even during a traffic spike

Here's the twist: a photo app you build for your family and Instagram can have the exact same functional requirements. What separates them entirely is the non-functional side — one serves 10 people who'll tolerate a slow day, the other serves a billion people who leave after 2 seconds of lag.

"Users never ask for a cache. Users ask for a fast app. The cache is just how you deliver that."

And a fair warning: non-functional requirements fight each other. Faster usually costs more money. Never-goes-down needs idle backup machines sitting around, still costing you every month. You can't add everything — you decide what this app actually needs.

Chapter Four

The 5 questions to ask before you draw a single box

Strong candidates (and good engineers) don't start sketching boxes immediately. They ask questions first.

  • 1. How many users, and how fast are they growing? We'll design for the millions we're heading toward — 10,000 users today, doubling every few months.
  • 2. Read-heavy or write-heavy? People scroll hundreds of photos a month but post maybe five. So this app is heavily read-heavy — most of our effort goes into making the feed fast.
  • 3. What can we never lose, vs. what can we afford to lose? Losing someone's uploaded photo = losing them forever. A like-count being off by 3 for a few seconds? Nobody notices.
  • 4. How much latency can we tolerate? The feed must feel instant (under 200ms). An upload can take 2-3 seconds — people expect uploading to feel like "work."
  • 5. What does it cost? Every replica, every cache, every server is a monthly bill. The best design isn't the fanciest one — it's the cheapest one that still meets the first four answers.

🎯 Interview tip

The first five minutes of a design interview aren't about design at all — they're about whether you ask these questions before you start drawing. Every component you add later, justify it with one of these answers: "I'm adding a cache because we established reads dominate." That's the sentence interviewers remember.

Chapter Five

Should the app be a monolith or microservices?

Monolith: one codebase, one deployment, everything (signup, upload, feed, likes) bundled into a single program that talks to itself through plain function calls.

Microservices: that one program is split into many small independent services (upload service, feed service, likes service, notifications service), each with its own codebase, deployed separately, talking to each other over the network.

Monolith vs Microservices
flowchart LR
    subgraph Monolith["Monolith: one codebase"]
      direction TB
      M1[Signup]
      M2[Upload]
      M3[Feed]
      M4[Likes]
      M1 --- M2 --- M3 --- M4
    end
    subgraph Micro["Microservices: separate services"]
      direction TB
      S1[Signup Service] -.network call.-> S3[Feed Service]
      S2[Upload Service] -.network call.-> S3
      S4[Likes Service] -.network call.-> S3
    end

For a photo app with a few thousand users, monolith is the correct choice — no network calls to fail, one thing to deploy, one place to look when something breaks. Teams split into microservices for two real reasons only: independent scaling (feed needs 10 servers, upload needs 2 — you shouldn't have to scale both together) and team size (40 engineers stepping on each other's code in one repo).

⚠️ Don't cargo-cult microservices

"I've seen a five-person startup run 30 microservices and spend more time debugging the network between services than building the actual product. Most companies you'll join run a monolith plus a handful of services that got split off for a good reason — not one giant program, not 300 tiny ones."

Chapter Six

Two ways to get more power: vertical vs horizontal scaling

Vertical scaling = make your one server bigger (more CPU, RAM, faster disk). Zero code changes, and genuinely the right move for a while. But it has a ceiling — once you own the biggest machine on the market, you're stuck, prices stop scaling linearly, and it's still one server: a single point of failure.

Horizontal scaling = run many small servers instead of one giant one. No upper limit (just add another machine), and no single point of failure (if one dies, the rest keep serving).

Vertical vs Horizontal Scaling

    subgraph V["Vertical Scaling"]
      direction TB
      V1["Small Server"] --> V2["Bigger Server"] --> V3["Biggest Server
(hits a ceiling)"]
    end
    subgraph H["Horizontal Scaling"]
      direction LR
      H1["Server 1"]
      H2["Server 2"]
      H3["Server 3"]
      H4["...add Server N"]
    end

Rule of thumb: scale up vertically first (it's simple), then scale horizontally once you hit the ceiling or can't afford a single point of failure. But 10 servers running your app immediately raises a new question: which of the 10 should answer a given user? That's the load balancer — coming up in Chapter 8.

Chapter Seven

What actually happens when you hit Enter

You type photoapp.com and hit enter. Here's the real journey:

From typing a URL to seeing the feed
sequenceDiagram
    participant Phone
    participant DNS as DNS (Internet's Phone Book)
    participant Server
    Phone->>DNS: Where is photoapp.com?
    DNS-->>Phone: Here's the IP address
    Phone->>Server: HTTPS request: "get me the home feed"
    Server-->>Phone: Response: feed data
  • IP address = the machine's phone number. Nobody types numbers, so we type names instead.
  • DNS (Domain Name System) = the internet's phone book. It translates the name into the IP address.
  • HTTP = the shared language phone and server use to talk. HTTPS adds the "S" for secure — without it, anyone on the same coffee-shop Wi-Fi can read your passwords in plain text; with it, the whole conversation is scrambled.

Two more terms that get mixed up constantly:

  • Latency — how long one round trip takes.
  • Bandwidth — how much data you can push through at once (the width of the pipe).

A feed of 30 tiny thumbnails isn't slow because the images are big — they're small. It's slow because of 30 separate round trips across the network. This is exactly why caches and CDNs exist later in this design — they exist to cut down round trips.

But there's a hole in this story: DNS points to one address, and we just decided to run 10 servers. So which one does DNS actually point to?

Chapter Eight

The load balancer: your traffic officer

Here's the trick: the IP address DNS returns doesn't point at any of your 10 app servers — it points at the load balancer. The load balancer is itself just a server running an application whose entire job is forwarding each request to one of your real servers.

Load balancer in the request path
flowchart LR
    U["User's Phone"] -->|DNS lookup| LB["Load Balancer
(a reverse proxy)"]
    LB --> S1["App Server 1"]
    LB --> S2["App Server 2"]
    LB --> S3["App Server 3"]
    LB -.health check every few seconds.-> S1
    LB -.health check.-> S2
    LB -.health check.-> S3

Any server that stands in front like this, taking requests on behalf of others, is generically called a reverse proxy — and a load balancer is the most common kind you'll meet. It does two jobs:

  • Health checks — it quietly pings each server every few seconds. If server 3 stops answering, the load balancer stops sending it traffic within seconds. Users never see an error.
  • Picking who gets the next request, using strategies like:
    • Round robin — server 1, then 2, then 3, then back to 1.
    • Least connections — send to whichever server currently has the fewest pending requests.
    • Weighted distribution — bigger servers get a bigger share of traffic.

Most companies don't build their own — they use battle-tested ones like NGINX, HAProxy, or a cloud provider's managed load balancer (like AWS's Elastic Load Balancer). And yes, the load balancer itself can die — which is why real production systems run multiple load balancers, not just one.

Chapter Nine

Stateless vs stateful: why users kept getting logged out

Here's a bug that shows up the moment you go from 1 server to many: users start getting randomly logged out, even though nobody changed any code.

Here's why: when Allen logs in, server 1 might handle it and save his "login session" (a little note saying "Allen is logged in") in its own memory. A few minutes later, his next request lands on server 5 — which has never heard of Allen, so it says "please log in again."

Why the login-session bug happens
flowchart TD
    A["Allen logs in"] --> B["Load Balancer sends request to Server 1"]
    B --> C["Server 1 saves session in its OWN memory"]
    D["Allen opens another page"] --> E["Load Balancer sends request to Server 5"]
    E --> F["Server 5 checks its own memory
❌ No record of Allen"]
    F --> G["Allen gets logged out"]

A server that keeps memory of previous requests like this is called stateful. The fix: make servers stateless — they handle a request, reply, and forget everything. Any real state (like login sessions) moves to a shared store that every server can check.

The fix: a shared session store
flowchart TD
    A["Allen logs in on Server 1"] --> S["Shared Store (e.g. Redis)"]
    B["Next request hits Server 5"] --> S
    S --> C["Server 5 finds the session ✅
Allen stays logged in"]

⚠️ What about "sticky sessions"?

One tempting fix is telling the load balancer to always send Allen to server 1. But this brings the exact problem back: if server 1 dies, Allen still loses his session, and the load balancer can no longer spread traffic evenly. Mentioning this trade-off before the interviewer asks earns real credit.

Simple test for statefulness: "If this server vanished right now, would any user lose something?" If yes, that data doesn't belong on the server. Note: storing photos in a database or S3 does not make a server stateful — that data already lives outside the server.

Chapter Ten

Data modeling: figure out the questions before the tables

Before picking a database, figure out the access patterns — the questions your users will ask the app thousands of times a day:

  • Show me a user's profile
  • Show me all photos uploaded by a user
  • Show me my home feed
  • Upload a photo / Like a photo / Comment on a photo / Follow a user

From these, five simple data pieces emerge — and notice how connections are always just a pair of IDs plus a little extra info:

Notice: the actual image file is never stored inside the photo record — just a link to where it lives (like S3). And "show me my home feed" is the most revealing question: to build it, the app must find everyone Allen follows, fetch their recent photos, and sort by time. That single question touches two tables and needs sorting — you'd only discover this by starting from access patterns, not from picking a database first.

Chapter Eleven

SQL or NoSQL?

It boils down to one question: is your data structured (same shape every time) or unstructured (different shape every time)?

SQL (e.g. Postgres, MySQL)NoSQL (e.g. MongoDB, DynamoDB)
Fixed table shape (rows & columns)Each record can look different
Great at joins / relationshipsBuilt to spread across hundreds of machines
ACID transactions — all-or-nothing writesGreat for high-volume, loosely-structured data
Best for: users, photos, likes, followsBest for: user preferences, behavior/analytics events

Since our photos, users, likes and follows are structured and full of relationships (we constantly join them to build a feed), we pick Postgres (SQL) for the core app, and keep a MongoDB (NoSQL) database on the side for loosely-structured stuff like user preferences. It's just an if condition in the app code deciding which database to query — nothing magical.

🎯 Interview tip

Never say "I'll use NoSQL because it scales" — the interviewer will immediately ask what exactly stops SQL from handling the load. Instead, derive your choice from access patterns: "My data is relational, I need joins to build the feed, so SQL. If I later add a high-volume piece with no relationships, like analytics events, that can go to NoSQL."

Chapter Twelve

Indexing: the same trick as a book's index page

As your user base grows, some queries slow down. Finding "all photos by Allen" out of millions of rows means scanning every single row, one by one — painfully slow.

The fix is the same trick as the index at the back of a textbook: instead of scanning the whole book, you look up "mitochondria" in the index and jump straight to page 100. We create a database index on the posted_by column, and the database can jump directly to Allen's rows instead of scanning everything.

⚠️ Don't index everything

Every index has to be updated on every new write — more indexes means more work on every insert. Rule of thumb: start with zero indexes, find your genuinely slow queries, then index only the columns those queries need. Most tables end up with 3–5 indexes, not 20.

For our photo app: index posted_by (find a user's photos fast) and upload_time (sort the feed by newest first).

Chapter Thirteen

Caching: don't ask the database the same question a million times

Picture a celebrity like Messi posting a photo. Millions of people ask for the exact same photo within seconds. Making the database run the identical query a million times is wasteful. Enter the cache — a small, blazing-fast store (like Redis) for popular items, sitting in front of the database. A cache read can respond in under 1ms vs 20-30ms from the database.

Cache hit vs cache miss
flowchart TD
    R["Request for trending photo"] --> C{Is it in Redis?}
    C -->|Cache Hit| H["Return from Redis instantly
DB never touched"]
    C -->|Cache Miss| M["Fetch from Database"]
    M --> W["Write result into Redis"]
    W --> RT["Return to user"]

Good cache candidates share one property: small, read constantly, changed rarely — trending photos, popular profile cards, and (as we saw in Chapter 9) login sessions.

But now you have two copies of the same data — one in the cache, one in the database — and they can drift apart. If Messi edits his bio, the database updates instantly, but the cache keeps serving the old bio to everyone. Two tools fix this:

  • TTL (Time To Live) — write cache entries with an expiry, e.g. "good for 60 seconds." The lazy fix: it waits for data to expire, then re-fetches fresh data. Fine for a home feed (30s TTL) or trending list (60s TTL), never fine for privacy settings.
  • Active invalidation — the moment data changes in the database, you immediately delete the old copy from the cache. More work per write, but zero tolerance for stale data — use this for anything security-shaped, like privacy settings.

⚠️ Cache stampede

If a wildly popular entry expires and 10,000 requests miss the cache at the exact same moment, they all slam the database at once — a "cache stampede." Fixes: stagger TTLs so hot entries don't all expire together, let only one request rebuild the entry while others wait, or refresh hot entries just before they expire.

🎯 Interview tip

"Cache is full, what do you evict?" → LRU (Least Recently Used) — throw out whatever nobody's touched in the longest time. Bringing up "cache stampede" before the interviewer asks is a strong signal you think about failure, not just features.

Chapter Fourteen

Replication: copies of your database

Right now we only have one database — a single point of failure. The industry standard fix: keep two replicas (copies) alongside the primary database — three copies total.

Primary-replica setup
flowchart TD
    App["App Servers"] -->|ALL writes| P["Primary Database"]
    App -->|reads, load-balanced| RLB["Read Load Balancer"]
    RLB --> P
    RLB --> R1["Replica 1"]
    RLB --> R2["Replica 2"]
    P -.streams updates.-> R1
    P -.streams updates.-> R2

Key rule: all writes go to the primary only — never write to multiple places, or you'll get conflicting values with no way to know which is correct. Reads, however, get spread across all three copies (with their own load balancer) to reduce load.

Since replicas copy data from the primary with a small delay, they're always slightly behind — this is called replication lag, and the state where copies aren't identical yet (but will be) is called eventual consistency.

Real bug this causes: Allen uploads a photo (goes to primary), then instantly refreshes his own profile — that read might hit a replica that hasn't caught up yet, so his own new photo briefly appears missing. Fix: reads of your own recent data go straight to the primary (this is called strong consistency); everyone else's reads can go to replicas, since a half-second delay hurts nobody.

Replication also gives you failover: if the primary dies, one replica gets promoted to become the new primary, and the app keeps running.

⚠️ Replicas are not backups

If someone runs a wrong DELETE on the primary, replicas copy that mistake within milliseconds — all three copies end up empty. Replication protects against hardware failure, not human error. That's why you also need real, separate backups (snapshots) you can restore from.

Chapter Fifteen

Sharding: when the data itself is too big for one machine

Replicas don't help once your data is simply too big to fit on any single machine — every replica has to hold an identical full copy. At 50 million users, the fix is sharding: split the data itself across multiple databases, where each "shard" holds only a slice.

Sharding by user ID
flowchart TD
    K["Shard Key: user_id % 4"] --> S0["Shard 0"]
    K --> S1["Shard 1"]
    K --> S2["Shard 2"]
    K --> S3["Shard 3"]
    U1["Allen (id 10) → 10 % 4 = 2"] --> S2
    U2["User (id 13) → 13 % 4 = 1"] --> S1

We pick a shard key (here, user ID) and a rule (divide by number of shards, remainder = shard number) that tells every server exactly where to look, without searching all shards one by one.

Two things can go wrong:

  • Hot shard — if by bad luck all the celebrity accounts land on the same shard, that one shard gets crushed. Fix: pick a shard key that spreads accounts evenly.
  • Adding a new shard breaks the math — dividing by 4 vs by 5 changes almost everyone's remainder, meaning nearly all data would have to physically move. The industry fix is consistent hashing, where each shard owns a small range, and adding a new shard only moves a small slice of data from one neighbor — not everything.

Use sharding as late as possible — once data is split, joining it back together is the hardest thing to undo. (Good news: databases like MongoDB have sharding built in, so you rarely build this from scratch.)
