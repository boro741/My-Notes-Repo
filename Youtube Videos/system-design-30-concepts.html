Chapter One

Client-server, IP addresses & DNS

Nearly every app you've ever used — the one on your phone right now included — is built on one simple idea: client-server architecture.

On one side sits the client — a browser, a mobile app, anything with a screen. On the other sits the server — a machine that runs around the clock, waiting patiently for work to arrive. The client sends a request ("give me my messages," "save this photo"), the server does the work, and sends a response back.

Client ↔ Server

The client sends a request. The server processes it and sends a response. That round trip is the heartbeat of almost every application on the internet.

That raises an obvious question: how does the client know where the server actually is?

💡
IP addressEvery server has a unique numeric address on the internet — something like 142.250.71.14 — that works exactly like a phone number. It's how one machine finds another among billions.

Nobody wants to memorize strings of numbers, though — which is why we type google.com instead of an IP address. Something has to translate the friendly name into the numeric address, and that something is DNS.

💡
DNS (Domain Name System)Think of DNS as the internet's phone book. It maps easy-to-remember names like algomaster.io to the actual IP address of the server hosting that site.
1
You type a URLe.g. algomaster.io, into your browser.
2
Your computer asks a DNS server"What's the IP address for this name?"
3
DNS responds with an IP addressThe phone-book lookup completes.
4
Your browser connects to that IPAnd the actual request-response conversation begins.

🔧 Try it yourself

You can see this translation happen on your own machine using the ping command in a terminal — it will show you the IP address behind any domain name.

Chapter Two

Proxies and the latency problem

Your request doesn't always travel straight from your device to the destination server. Often it passes through a middleman first.

🕵️ Proxy server
  • Sits between your device and the internet
  • Forwards your request, retrieves the response, hands it back to you
  • Hides your IP address — keeps your identity and location private
🔀 Reverse proxy
  • Sits in front of one or more backend servers
  • Intercepts client requests and routes them onward
  • Decides which server should actually handle the work

Same basic idea, opposite direction: a proxy protects the identity of the client; a reverse proxy protects and manages the server.

Why every millisecond matters: latency

Whenever a client talks to a server, there's always some delay. The single biggest cause is physical distance.

💡
LatencyThe round-trip delay between sending a request and receiving a response. If your server sits in New York and a user is in India, the data has to physically travel there and back — and that trip takes time.

🌍 The fix: multi-region deployment

Instead of running one server in one location, companies deploy copies of their service across data centers worldwide. A user then connects to the nearest one — cutting the physical distance the data has to travel, and cutting latency along with it.

Chapter Three

Speaking the same language: HTTP & HTTPS

Once a connection is made, how do a client and server actually talk to each other? They follow a shared set of rules called HTTP — HyperText Transfer Protocol. It's the reason nearly every web address starts with http.

A typical exchange looks like this: the client sends a request containing a header (request type, browser info, cookies) and sometimes a body (form data, for example). The server processes it and replies with an HTTP response — either the data you asked for, or an error if something went wrong.

⚠️ HTTP's big flaw

Plain HTTP sends everything as readable text. Anyone intercepting the connection can read — or even alter — what's inside.

💡
HTTPSThe secure version of HTTP. It encrypts all data using the SSL/TLS protocol, so even if someone intercepts your request, all they see is scrambled noise — not your password or your payment details.

But HTTP is only a transport protocol — it doesn't say how a request should be structured, what format a response should take, or how a client should ask for exactly the data it wants. That's a separate job, handled by APIs, which is where we go next.

Chapter Four

APIs: REST vs. GraphQL

Think of an API (Application Programming Interface) as a well-defined middleman. The client sends a request to the API; the API — hosted on a server — talks to databases or other services, prepares an answer, and sends it back in a structured format the client understands, usually JSON or XML.

Two styles dominate how APIs are designed today: REST and GraphQL.

🧱 REST
  • Everything is modeled as a resource — users, orders, products
  • Stateless: every request stands on its own
  • Uses standard HTTP verbs: GET, POST, PUT, DELETE
  • Simple, scalable, easy to cache
  • Downside: can over-fetch or under-fetch data, needing multiple round trips
🎯 GraphQL
  • Introduced by Facebook in 2015
  • Client asks for exactly the fields it needs — nothing more
  • One query can combine what would be several REST calls
  • Downside: more processing work on the server, and harder to cache

Example: to show a user's profile plus their recent posts, REST might mean two separate calls to two different endpoints. GraphQL lets you ask for both in a single query, and the server returns only the fields you actually requested.

Chapter Five

Where data lives: SQL vs. NoSQL

A client request usually wants to store or fetch data — but where does that data actually live? For tiny amounts, you could keep it in memory or a file. Real applications, though, deal in volumes far beyond what memory can hold, so they rely on a dedicated database.

💡
DatabaseA dedicated system for storing, retrieving, and managing data efficiently — while keeping it secure, consistent, and durable.

Databases generally split into two camps:

🗂️ SQL databases
  • Data lives in tables with a strict, predefined schema
  • Follow ACID properties — strong guarantees on correctness
  • Ideal for structured, relational data — think banking systems
🧩 NoSQL databases
  • No fixed schema — flexible by design
  • Built for high scalability and performance
  • Comes in several flavors: key-value stores, document stores, graph databases, wide-column stores
💡
ACIDA set of guarantees (Atomicity, Consistency, Isolation, Durability) that ensure a database transaction either completes fully or doesn't happen at all — critical for something like a bank transfer.

Need strong consistency and structured relationships? Reach for SQL. Need to scale massively with a flexible schema? Reach for NoSQL. In practice, most large applications quietly use both, side by side, for different jobs.

Chapter Six

Scaling servers: vertical, horizontal & load balancers

As your user base grows, so does the number of requests hitting your servers. There are two fundamentally different ways to cope.

Vertical scaling — make one machine bigger

The quickest fix is to upgrade your existing server: more CPU, more RAM, more storage. This is called vertical scaling, or "scaling up."

⚠️ The ceiling

You can't upgrade a single machine forever — every server has a maximum capacity. Bigger machines get exponentially more expensive, and worst of all: if that one server crashes, your entire system goes down with it.

Horizontal scaling — add more machines

Instead of making one server bigger, horizontal scaling ("scaling out") spreads the workload across many servers. More servers means more total capacity, and if one goes down, the others keep the system running.

But this creates a new problem: with many servers available, how does a client know which one to talk to?

💡
Load balancerA traffic manager that sits between clients and your fleet of servers, spreading incoming requests across them. If one server crashes, the load balancer quietly redirects traffic to a healthy one.

How does it decide who gets the next request? Using a load balancing algorithm — common choices include round robin (take turns), least connections (send it to whoever's least busy), and IP hashing (always send a given client to the same server).

Chapter Seven

Scaling databases: indexing & replication

Servers aren't the only thing that needs to scale — as traffic grows, so does the volume of data. Databases can be scaled vertically too, but they hit the same ceiling. Here are two techniques built specifically for databases.

Indexing — the shortcut for reads

Think of the index at the back of a textbook. Instead of flipping through every page to find "mitochondria," you jump straight to page 214. A database index works the same way.

Scanning vs. Indexing
Without index — scan everything
row 1: id=104
row 2: id=812
row 3: id=317
row 4: id=592 ✓
row 5: id=201
With index — jump directly
id=592 → row 4 ✓

An index stores column values alongside pointers to their actual rows, so the database can find matches without scanning the whole table.

⚠️ The trade-off

Indexes speed up reads, but they slow down writes — every insert or update has to also update the index. That's why you should only index columns you query frequently: primary keys, foreign keys, and columns used often in WHERE clauses.

Replication — copies for reads

If indexing alone isn't enough and a single database can't keep up with read traffic, the next move is replication: creating copies of your database across multiple servers, the same instinct as adding more application servers.

Primary → Replicas

The primary replica handles all writes. Every write is copied out to the read replicas, which handle read traffic. If the primary fails, a replica can be promoted to take its place — improving both performance and availability.

Chapter Eight

Splitting data: sharding & vertical partitioning

Replication is great for read-heavy traffic — but what happens when your database itself has grown to terabytes of data, or writes have become the bottleneck? You split it up.

Sharding (horizontal partitioning)

💡
ShardingSplitting a database into smaller pieces called shards, each holding a subset of the total rows, distributed across multiple servers based on a "sharding key" — for example, user ID.

Because each shard only handles a slice of the total data, both read and write performance improve — no single server is doing all the work. Since it splits data by rows, this is also called horizontal partitioning.

Shard 1Users A–H
Shard 2Users I–P
Shard 3Users Q–Z
Sharding keye.g. user ID decides which shard

Vertical partitioning

Sometimes the problem isn't too many rows — it's too many columns. Imagine a user table storing profile details, login history, and billing information all together. As it grows, every query has to scan past columns it doesn't even need.

💡
Vertical partitioningSplitting one wide table into several smaller, more focused tables grouped by usage pattern — so a query only touches the columns it actually needs, cutting unnecessary disk I/O.

Chapter Nine

Speed tricks: caching & denormalization

No matter how much you optimize a database, reading from disk is always slower than reading from memory. So — what if the most frequently requested data just lived in memory?

💡
CachingStoring frequently accessed data in fast memory instead of repeatedly hitting the database for it.

The cache-aside pattern

1
Check the cache firstThe application looks for the data in the cache.
2
Cache hit → return instantlyNo database call needed at all.
3
Cache miss → fetch from the databaseThen store a copy in the cache for next time.
4
Next request is served from cacheMuch faster, on every subsequent read.
💡
TTL (Time To Live)A timer set on cached data so it automatically expires after a while — preventing users from being served stale, outdated information forever.

Denormalization

Most relational databases follow normalization — breaking data into many small, non-repeating tables to avoid duplication. That's tidy, but it means retrieving related data (like a user's orders) often requires expensive join operations across tables.

💡
DenormalizationDeliberately combining related data into a single table — even if it means some duplication — so common queries can skip the join and run faster.

Instead of separate users and orders tables joined at query time, you might keep a combined user_orders table. Fetching order history becomes a single, fast lookup. The trade-off: more storage used, and updates get more complex since the same data may need to change in more than one place.

Chapter Ten

The CAP theorem

Once your system spans multiple servers, databases, and data centers, you've entered the world of distributed systems — and one law governs everything you can and can't guarantee there: the CAP theorem.

Pick Two

No distributed system can guarantee all three of Consistency, Availability, and Partition tolerance at once. Since network failures are inevitable, you're really choosing between consistency + partition tolerance or availability + partition tolerance.

ConsistencyEvery read gets the latest write, everywhere
AvailabilityEvery request gets a response, even if not the latest
Partition toleranceThe system keeps working even if the network between nodes breaks

Because network partitions will happen eventually, partition tolerance isn't really optional — so in practice, the real-world choice comes down to consistency versus availability during a failure.

Chapter Eleven

Storing & delivering files: blob storage & CDNs

Modern apps don't just store rows of text — they handle images, videos, PDFs. Traditional databases aren't built to store large unstructured files efficiently, so we reach for something else.

💡
Blob storageA service like Amazon S3 built specifically for storing large files ("blobs") inside logical containers called buckets. Every file gets a unique URL, making it easy to fetch over the web.
📈
Scales automatically as files grow
💳
Pay-as-you-go pricing model
🔁
Automatic replication for durability
🔗
Simple, direct URL-based access

But streaming a video straight from blob storage can be painfully slow if that storage is far away — imagine watching a video hosted in California from India. The data has to cross the globe, causing buffering.

💡
CDN (Content Delivery Network)A global network of servers positioned around the world that cache and serve web content — HTML, JavaScript, images, video — from whichever location is physically closest to the user.

Because content is served from the nearest CDN server rather than the original one, users get faster load times and far less buffering.

Chapter Twelve

Real-time systems: WebSockets & webhooks

Regular HTTP follows a request-response model — the client always has to ask first. That's fine for a static webpage, but far too slow for a live chat app, a stock ticker, or a multiplayer game.

Without a better tool, the only option is polling — repeatedly asking the server "anything new?" every few seconds. It works, but it's wasteful: most of those responses come back empty, burning server resources and bandwidth for nothing.

💡
WebSocketsA protocol that opens one persistent, two-way connection between client and server. Once it's open, the server can push updates to the client instantly — no repeated asking required — and the client can send messages back just as fast.
🔁 Polling
  • Client repeatedly asks "anything new?"
  • Most responses are empty — wasted bandwidth
  • Simple to build, inefficient at scale
⚡ WebSockets
  • One connection stays open both ways
  • Server pushes updates the instant they happen
  • Ideal for chat, live scores, multiplayer games

Webhooks — servers notifying servers

WebSockets solve real-time updates between a client and a server. But what if one server needs to notify another server the moment something happens — like a payment gateway telling your app "the payment just went through"?

💡
WebhookInstead of your app constantly polling an API asking "did the payment happen yet?", the provider sends an HTTP POST request straight to a URL you registered, the instant the event occurs.

You register a "webhook URL" with the provider ahead of time. When the event fires, the provider hits that URL with the event details — saving both sides from wasteful, constant checking.

Chapter Thirteen

Breaking apart monoliths: microservices & message queues

Traditionally, applications were built as a monolith — every feature living inside one large codebase. That's fine for small apps, but at scale, monoliths become hard to manage, deploy, and grow.

💡
MicroservicesBreaking one large application into smaller, independent services, where each one owns a single responsibility, has its own database and logic, and can be scaled and deployed on its own.

These services talk to each other over APIs — or, when a direct call isn't the right fit, through message queues.

Message queues — asynchronous communication

Calling another service directly and waiting for an immediate answer (synchronous communication) doesn't scale well when the two sides don't need to move in lockstep.

💡
Message queueA buffer that lets services communicate asynchronously. A "producer" drops a message into the queue; the queue holds it; a "consumer" picks it up and processes it whenever it's ready — without blocking anyone.
1
ProducerPlaces a message into the queue.
2
QueueTemporarily holds the message safely.
3
ConsumerRetrieves and processes the message when ready.

Message queues decouple services from each other, improve scalability, and prevent one slow or overloaded service from taking down everything upstream of it.

Chapter Fourteen

Guarding the front door: rate limiting, API gateways & idempotency

Message queues protect services from each other internally — but what protects your public APIs from the outside world?

💡
Rate limitingRestricting how many requests a client or IP address can send within a given time window — say, 100 requests per minute. Exceed the limit, and the server temporarily blocks further requests. Without it, a bot firing thousands of requests a second could crash your servers.

Common rate-limiting algorithms include fixed window, sliding window, and token bucket — each trading off simplicity against fairness under bursty traffic.

API gateway

You rarely have to build rate limiting from scratch — it's usually handled by an API gateway.

💡
API gatewayA single, centralized entry point for all client requests in a microservices system. It handles authentication, rate limiting, logging, monitoring, and routing each request to the right microservice — before sending the response back through itself to the client.

Idempotency — surviving retries safely

In distributed systems, network failures and retries are a fact of life. If a user nervously refreshes a payment page, the server might receive the exact same payment request twice.

💡
IdempotencyA guarantee that making the same request multiple times produces the exact same result as making it once — so a duplicate payment request doesn't charge the user twice.
1
Assign a unique IDEvery request gets a unique identifier before processing.
2
Check for duplicatesThe system checks if that ID has already been handled.
3
Ignore or processAlready handled? Ignore the repeat. New? Process it normally.

🧩 Putting it all together

A client hits the API gateway, which checks rate limits and routes the request to the right microservice. That service reads or writes to a sharded, replicated, cached database, and the whole exchange rides on HTTPS, guarded by idempotency in case anything gets retried. That's a real system design interview answer — built entirely from the 30 pieces you've just walked through.
