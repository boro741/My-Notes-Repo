1 Why We Need the "Process" Abstraction

Start with the raw hardware: a CPU (with one or more cores), RAM, and disk. The CPU constantly reads and writes to RAM, and RAM spills over to disk when it needs permanent or overflow storage.

Very old computers could only run one program at a time — feed it in (even on a punch card), let it run start to finish, done. But modern computers need to run many programs at once: a chat app, music, a database, a terminal — all "at the same time," even on a single core.

This is done through context switching: the OS gives each program a tiny time slice on the CPU (say, 1–10 milliseconds), then swaps in the next program. If you have multiple cores, some programs can run truly in parallel; the rest is handled by slicing time. The part of the OS that decides who runs next and for how long is the scheduler.

Even with a single core, the OS rotates programs through short time slices so they all appear to run "at once."

The problem: if every program had to manually coordinate which chunk of RAM and CPU it's "allowed" to touch, engineering software would be a nightmare — and a buggy or malicious program could stomp on another program's memory.

The core problem Without isolation, any process could read or overwrite another process's memory — by accident or on purpose.

The process is the OS's answer: it's an abstraction that lets a running program act as if it owns the entire computer — its own CPU time, its own (virtually) unlimited memory, its own files — while the OS handles the real-world juggling of sharing hardware safely between everyone.

Analogy A process is like a hotel room. You get a key, and inside your room you can act as if you own the whole building — arrange furniture however you like, use the outlets, whatever. You don't need to coordinate with the guest three doors down. The hotel (the OS) is the one making sure nobody's room key opens someone else's door.

This is also why building custom AI agent code, databases, or operating systems benefits from having reliable "primitives" to build on — a process is one such primitive that application code can simply trust and build on top of.

2 Creating Processes: fork and exec

On Unix-like systems (Mac, Linux), new processes are created with two system calls used together:

CallWhat it does
forkMakes an identical clone of the currently running process (new process ID, but same code, same memory contents) and adds it to the OS's process list.
exec / execveReplaces the "text" (code) of the calling process with a brand-new program loaded from an executable file on disk, then starts running that instead.

So the normal way to launch a new program is: fork (clone yourself), then in the clone call exec (swap out your code for the new program). Right after boot, Unix systems start with one initial process, and every other process — kernel or user — descends from it via forking.

fork() clones the running process; exec() then swaps the clone's code for a new program.

From the man pages fork: the new child process is an exact copy of the parent except for a unique PID, a different parent PID, its own copy of file descriptors, and reset resource usage counters. execve: loads a new executable object file (a compiled binary, e.g. what GCC produces) and starts running it in place of the calling process.

Fun fact from the stream: in Linux, both processes and threads are internally represented as tasks. The main difference between them (covered more in section 5) is that a thread shares the same virtual memory space as its process but has its own program stack.

3 Anatomy of a Process (Memory Layout)

A process is split into two regions: the user address space (where your program's own code and data live) and the kernel context (bookkeeping the kernel keeps about your process).

User address space

  • Text — the actual compiled instructions (adds, moves, jumps) being executed.
  • Data / constants — fixed-size stuff, loaded near the bottom of the address space.
  • Heap — general-purpose memory for things not tied to a single function call (arrays, objects, hash maps). Grows in one direction as you allocate, though it can get fragmented as allocations come and go.
  • Stack — tracks function calls: each call pushes a "frame" with local variables; returning pops it off. Grows and shrinks constantly, and can get deep during heavy recursion.

Kernel context

  • Kernel stack — a separate stack used only while the process is executing in kernel mode (e.g., during a disk or network request).
  • Metadata — process ID, user ID (UID), timing info.
  • File descriptors — which files this process currently has open (more in section 4).

Each process has its own user-space stack/heap/text, plus kernel-side bookkeeping (kernel stack, IDs, open files).

Analogy Think of the heap as a big shared storage closet you can put boxes in whenever you need to, and the stack as a stack of sticky notes on your desk — you add one every time you start a task, and peel it off the moment that task finishes.

4 File Descriptors

When a process opens a file with the open system call, it gets back a small integer called a file descriptor — an identifier the kernel uses to track "this process currently has this file open." The kernel needs this to enforce file permissions and know what reads/writes a process is allowed to make.

Key point The file descriptor table lives in the kernel context of a process, not in user space — it's part of the bookkeeping the kernel does on your behalf.

5 Processes vs. Threads

A process always has at least one thread. A thread is a lighter-weight unit of execution inside a process: multiple threads in the same process share the same virtual address space and the same heap, but each has its own program stack (its own point of execution).

Multi-processMulti-threaded
IsolationFully isolated — separate memory spacesShared memory space (same heap)
CommunicationMessage passing or shared memory (must set up explicitly)Direct — just shared variables
Cost to create/switchHeavierLighter weight, cheaper to switch
Coordination neededLess (isolated by default)More (must coordinate access to shared data)

Threads in the same process share the heap and address space, but each keeps its own program stack.

Best practice / trade-off Use multiple processes when you want strong isolation (a crash in one shouldn't take down the other). Use multiple threads when you want cheap parallelism and don't mind coordinating shared state carefully (locks, etc.).

6 Process Lifecycle (States)

The scheduler has to track what state every process is in, since it can't run all of them on the CPU at once:

StateMeaning
ReadyWants to run, nothing is blocking it, just waiting for CPU time.
RunningActively executing on a CPU core right now.
WaitingBlocked on something like a disk read or network request; not using the CPU.
Killed / ZombieFinished executing, just needs the OS to clean up its remaining bookkeeping.

A process cycles between Ready and Running, drops to Waiting when blocked on I/O, and ends as a Zombie until the OS cleans it up.

7 Virtual Memory & the MMU

Virtual memory lets every process act like it owns all the memory on the machine — even more than physically exists. The CPU only ever thinks in virtual addresses (e.g. 0x12345). It never talks to RAM directly.

Instead, requests pass through the Memory Management Unit (MMU) — a mix of hardware and OS software — which translates the virtual address into the real, physical address in RAM (e.g. translating 0x12345 into 0x83145).

Analogy This is like a database proxy: instead of your app connecting straight to a database, it talks to a proxy, which picks the actual connection behind the scenes. The MMU is that same kind of middleman between the CPU and physical RAM.

The CPU only ever speaks in virtual addresses; the MMU rewrites them into real physical RAM addresses.

Why this matters: it's exactly what makes process isolation possible. Because every process's virtual addresses get mapped independently, the OS guarantees no two processes are ever handed the same slice of physical RAM at the same time.

Key point Memory isn't managed byte-by-byte — it's managed in fixed-size chunks called pages, typically 4KB–16KB (some systems support larger pages, e.g. 2MB "huge pages"). Pages are the unit used to map memory in and swap it out to disk.

8 Walking Through a Page Table Lookup

Say the CPU executes an instruction to load a value from virtual address 0x2C8. A virtual address is split into two parts:

  • Page table index — the higher-order bits (here: 2) — which page are we talking about?
  • Page offset — the lower bits (here: 0xC8) — how far into that page is the data?

The OS keeps a page map (array) per process. Each entry tracks two important bits:

BitMeaning
D (dirty)Has this page changed since it was loaded from disk? If 1, it must be saved back to disk before that RAM slot can be reused for something else.
R (resident)Is this page currently actually sitting in physical RAM (1), or has it been swapped out to disk (0)?

Walking through the example: the CPU looks up index 2 in the page map. It finds R = 1 (already resident — no disk trip needed) and a physical page number, say 9. The CPU jumps to slot 9 in physical RAM, then uses the offset 0xC8 to find exactly where inside that page the requested bytes live.

The index picks a row in the page map; that row points to a physical page; the offset finds the exact byte inside it.

What happens if R = 0 If the resident bit is 0, the page isn't in RAM. The kernel has to fetch it from disk, put the process into a waiting/sleeping state so something else can use the CPU, and wake it up (via a trap) once the data is ready. That whole round trip is why a "cache miss" to disk feels slow from the CPU's perspective — even though the CPU got to do other useful work in the meantime.

9 Why Page Tables Are Actually Trees

Modern OSes use large address spaces — around 48 bits even on 64-bit CPUs (e.g. x86). A single flat page map covering a 48-bit address space per process would be enormous and completely impractical to keep around for every running process.

The fix: a tiered (tree-like) structure. The address space is broken into large chunks, and those chunks are broken into smaller chunks, and so on. This works well because in practice, the vast majority of a huge virtual address space is unused — memory usage is sparse. A tree structure only needs to store mappings for the parts that are actually in use, instead of reserving space for every possible address.

Best practice This is a classic space/time trade-off: a flat table is faster to look up (single index) but wildly wasteful in memory. A tree-structured (multi-level) page table costs a few extra lookup steps but stays practical at real-world address space sizes.

✓ Cheat Sheet

Key facts to remember

  • A process = an abstraction that lets a program act like it owns the whole computer (CPU, memory, files) while the OS actually shares hardware safely between everyone.
  • New processes are made with fork (clone) + exec/execve (swap in new code).
  • A process has a user address space (text, heap, stack) and a kernel context (kernel stack, PID/UID, file descriptor table).
  • A file descriptor is the kernel's ID for a file a process has open.
  • A thread shares its process's heap and address space but has its own program stack — cheaper than a full process, but needs more coordination.
  • Process states: Ready → Running → (maybe) Waiting → back to Ready → eventually Zombie/Terminated.
  • Virtual memory lets every process pretend it owns all of RAM (and more); the MMU translates virtual → physical addresses using a per-process page map.
  • Memory is managed in pages (typically 4–16KB). Each page-map entry has a D (dirty) bit and an R (resident) bit.
  • Real page tables are multi-level trees, not flat arrays — because address spaces are huge but usage is sparse.

The one-paragraph mental model

Every running program lives inside a process, which is really just a comfortable lie the OS tells it: "you own this whole machine." Under the hood, the OS is constantly time-slicing the CPU across many processes (and their threads), while the MMU and page tables quietly translate every memory access from a pretend "virtual" address into a real slot in physical RAM — swapping pages to and from disk as needed — so that no process can ever see or corrupt another's memory, even though they're all sharing the exact same hardware underneath.
