Chapter One

LLD vs. HLD — what's actually different

If you've heard "system design" thrown around and felt confused about where low-level design fits in, here's the short version: they're two zoom levels on the same problem, not two different subjects.

💡 Quick definitions before we go further

HLD (High-Level Design) is the bird's-eye view of a system — how big pieces talk to each other. LLD (Low-Level Design) is the zoomed-in view — the actual classes and methods you'd write to build one of those pieces.

High-level design answers the "how do we scale this to a million users" questions — which database to pick, how services talk to each other, how you handle caching, message queues, and things failing at 3am. Low-level design goes one level deeper. It stops asking "what infrastructure do we need" and starts asking "what classes do we need, what is each one responsible for, and how do they talk to each other."

HIGH-LEVEL DESIGN

The big picture

  • How should the system scale?
  • Which database should we use?
  • How do services communicate?
  • How do we handle traffic, caching, queues, and failures?
LOW-LEVEL DESIGN

The implementation

  • What classes should we create?
  • What is each class responsible for?
  • How do objects interact with each other?
  • Which interfaces, methods, and data models do we define?

Here's why this matters beyond interviews: LLD is what turns a working prototype into software that someone else — including future you — can actually read, fix, and extend without wanting to rewrite it from scratch. And these days, a lot of companies run LLD rounds even for entry-level roles, so it's worth building this muscle early rather than cramming it right before an interview.

Chapter Two

The three flavours of LLD interview

Not every LLD round looks the same. Before you start prepping, it helps to know which version you're likely to face — because the skills you're judged on shift a fair bit between them.

Object-Oriented Design
45–60 min · Google, Amazon, Meta, Microsoft

You're asked to design something like a parking lot, an elevator, or a library system. You identify the classes, interfaces, methods, and relationships — usually as pseudo-code, class skeletons, or a diagram, not a running app. The interviewer is watching your grasp of OOP, SOLID, patterns, and how clearly you explain trade-offs.

Machine Coding
90–120 min · common at Indian tech companies & startups

This time, pseudo-code won't cut it — your code has to actually compile, run, and handle the required use cases. You're judged on correctness, code structure, how you handle edge cases, your testing approach, and how fast you can go from a design to working software.

Concurrency Design
Common at Uber, Rubrik, LinkedIn

Here the system has to behave correctly when multiple threads touch shared data at once — think a thread-safe queue, a rate limiter, a connection pool. It might be the whole question, or a twist tacked onto a regular LLD problem ("now make your parking lot thread-safe"). The interviewer wants to see you spot race conditions, pick the right synchronization tool, and avoid deadlocks.

💡 What's a "race condition"?

It's a bug that happens when two threads read and write the same piece of data at the same time, and the final result depends on which one happens to "win" the race — meaning the same code can give different, unpredictable answers on different runs.

This roadmap focuses mainly on object-oriented design and machine coding — the two you're most likely to hit first, no matter where you're interviewing.

Chapter Three

Pick one language and stop shopping

LLD is about writing actual classes, objects, and interfaces — so you need to be comfortable in at least one object-oriented language. The specific choice matters far less than people think.

Java is the most common pick for LLD interviews because it leans heavily into OOP and is everywhere in backend development. But C++, Python, C#, and Go all work fine — pick whichever the company allows and you're already most fluent in, then stick with that same language while you practice.

🎯 The one thing that actually matters

Your ability to express a clean, maintainable design matters far more than which language you use to express it. Interviewers are grading your thinking, not your syntax.

Chapter Four

OOP fundamentals — the building blocks

At its heart, low-level design is about taking a messy real-world problem and representing it as classes, objects, interfaces, and the relationships between them. Everything else you'll learn later sits on top of this foundation.

Start with the basic building blocks: classes, objects, constructors, enums, interfaces, abstract classes, and access modifiers. If any of those words feel fuzzy, that's completely normal — here's the quick version of each:

💡 The building blocks, in plain English

Class = a blueprint (e.g. "Car"). Object = one actual thing built from that blueprint (e.g. "my red Honda"). Constructor = the code that runs when you build a new object. Enum = a fixed list of named values (e.g. Monday–Sunday). Interface = a contract listing what a class must be able to do, without saying how. Abstract class = a partly-built blueprint other classes finish. Access modifier = a rule (like "private" or "public") controlling who's allowed to see or use a piece of code.

Next, learn the four pillars everyone name-drops in interviews. They're not abstract theory — each one solves a concrete, everyday coding headache.

Encapsulation Hide the messy internals, expose a clean way in
Abstraction Show what it does, not how it does it
Inheritance A new class reuses another's behaviour
Polymorphism Same method call, different behaviour per object

These four ideas are what let you design classes that stay easy to understand, extend, and maintain — instead of turning into a pile of tangled code six months later.

Then, learn how classes relate to each other

Finally, understand four class relationships: association, aggregation, composition, and dependency. These are what let you draw a class diagram that actually communicates your design, instead of a wall of disconnected boxes.

💡 Telling these four apart

Association: two classes just know about each other (Driver–Car). Aggregation: a "has-a" relationship where the parts can survive without the whole (a Book still exists if the Library closes). Composition: a tighter "has-a" where the parts die with the whole (a Room doesn't exist without the House). Dependency: one class briefly uses another to do a job, without holding onto it long-term.

Chapter Five

Design principles & the SOLID rules

Once OOP basics feel comfortable, the next layer is the set of principles that separate code that "just works" from code that's actually pleasant to work with later.

Start with these smaller, punchier ideas:

DRY — Don't Repeat Yourself KISS — Keep It Simple YAGNI — You Aren't Gonna Need It Law of Demeter Coupling Cohesion
💡 Coupling vs. cohesion, in one line each

Coupling is how tangled up two different classes are with each other — you want this low. Cohesion is how tightly focused a single class is on doing one job well — you want this high.

After that, learn SOLID — five rules that come up constantly in LLD interviews because they give you language to explain why your design is structured the way it is, not just that it works.

💡 What does SOLID stand for?

It's an acronym for five separate principles, covered one by one below. You don't need to memorize textbook definitions — just understand the practical idea behind each one.

S
Single Responsibility PrincipleA class should have exactly one reason to change — one job, done well.
O
Open/Closed PrincipleYou should be able to add new behaviour without editing existing, working code.
L
Liskov Substitution PrincipleA subclass should be swappable for its parent class without breaking anything.
I
Interface Segregation PrincipleDon't force a class to implement methods it will never actually use.
D
Dependency Inversion PrincipleDepend on interfaces/abstractions, not on concrete, specific implementations.

This is also the point where interfaces, class design, and these principles start working together as one skill instead of separate topics — you'll notice yourself naturally reaching for an interface because "Dependency Inversion says so," without consciously thinking about the acronym.

Chapter Six

UML — draw just enough, not a masterpiece

Here's some good news: in most LLD interviews, nobody expects a textbook-perfect UML diagram. Simply outlining your classes, methods, and how they relate is usually enough. Still, knowing a few standard diagram types makes your thinking much easier to follow.

💡 What's UML?

Unified Modeling Language — basically a shared visual vocabulary of boxes, arrows, and symbols that engineers use to sketch out software designs, so anyone reading it understands the design without you explaining every line out loud.

Class diagram

Shows the classes, their attributes, methods, and how they relate — the single most important diagram for LLD interviews.

Most important
Use case diagram

Shows the main actors (users) and the actions they can take — great for clarifying requirements before you design anything.

Clarify scope
Sequence diagram

Shows how objects interact step-by-step during one flow — like placing an order or processing a payment.

Show flow

You don't need to become a UML expert. Learn just enough of these three to communicate your design clearly and confidently under time pressure.

Chapter Seven

Ten design patterns worth knowing

As you solve more design problems, you'll notice the same shapes of problem keep reappearing. Design patterns are just proven, named answers to those recurring shapes.

💡 Where do these come from?

There are 23 classic patterns from a famous 1994 book written by four authors — nicknamed the "Gang of Four." For LLD interviews, you only need a working knowledge of the ones that come up most often. Tap or hover a card to see when to reach for it.

01
Strategytap for use case
Same task, different ways to do it — e.g. paying by card, UPI, or wallet.
02
Observertap for use case
One change needs to notify several others — e.g. broadcasting an order status update.
03
Statetap for use case
Behaviour depends on current state — e.g. an order moving created → paid → delivered.
04
Facadetap for use case
Hides a messy, complex subsystem behind one simple, friendly interface.
05
Factory Methodtap for use case
The exact object type to create depends on input — e.g. creating different vehicle types.
06
Compositetap for use case
Represents tree-like structures — e.g. files and folders nested inside each other.
07
Decoratortap for use case
Adds new behaviour to an object without touching its original class.
08
Commandtap for use case
Turns actions into objects — the classic way to implement undo/redo.
09
Chain of Responsibilitytap for use case
A request passes through multiple handlers in sequence — e.g. an approval workflow.
10
Template Methodtap for use case
Several workflows share the same overall structure but differ in a few individual steps.

⚠️ The rule that matters more than any pattern

Don't force a pattern into a solution just because you know it. Reach for one only when it genuinely makes your design cleaner, more flexible, or easier to extend — interviewers notice pattern-shoehorning immediately.

Chapter Eight

Build your practice roadmap

Once OOP, design principles, and common patterns feel solid, the real learning happens by solving actual problems. LLD problems rarely have one "correct" answer — different designs can be valid depending on requirements and trade-offs, and that ambiguity is normal, not a sign you're doing it wrong.

1
Clarify requirements

Before writing a single class, pin down what's actually in scope. Ask questions instead of assuming.

2
Identify the core entities

Pull the "nouns" out of the problem — these usually become your first draft of classes.

3
Define responsibilities

Decide exactly what each class owns and is accountable for — this is where SOLID starts paying off.

4
Design the relationships

Work out how the classes connect: association, aggregation, composition, or dependency.

5
Write the code

Turn the design into pseudo-code, class skeletons, or a working implementation, depending on the interview format.

Start with these commonly asked problems — and resist the urge to peek at a solution immediately. Struggle with it first, then compare notes.

🅿️ Parking Lot 🛗 Elevator System 📚 Library Management 🎬 Movie Ticket Booking 🎮 Tic-Tac-Toe ☕ Vending Machine 🍔 Food Delivery App 💳 Splitwise / Expense Sharing

For each one, follow the same loop every time: clarify requirements → identify entities → define responsibilities → design relationships → write the code. Then interrogate your own draft:

  • ? Is each class responsible for one clear thing?
  • ? Is the design easy to understand and extend?
  • ? Am I adding complexity nobody asked for?
  • ? Could I support a new requirement without rewriting large chunks?

The more reps you get in, the more naturally you'll start thinking in terms of objects, interfaces, and responsibilities — which, at the end of the day, is exactly what every LLD interview is quietly testing for.

Chapter Nine

Now go build something.

You don't need to master every pattern or memorize every SOLID definition before you start. Pick a language, learn OOP fundamentals, pick your first problem — a parking lot is the classic starting point — and let the rest of this roadmap unfold one chapter at a time as you actually need it.
