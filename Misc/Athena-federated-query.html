Athena Federated Query

How Athena reaches beyond S3 to query DynamoDB, RDS, and other live data sources — architecture, internals, and a worked example.

Recap from your notes

Your understanding of core Athena — table = metadata pointer to S3 data, Glue Crawler auto-generates that metadata, results land in a separate S3 bucket — is correct. Two pricing details needed a fix:

There is no free tier. Athena charges $5 per TB scanned from the very first query, with a 10 MB minimum charge per query.
You're billed for data scanned, not data returned. A query that reads 2 TB but returns 3 rows still costs for the full 2 TB scanned — which is exactly why partitioning and columnar formats (Parquet/ORC) matter.

Why Federated Query exists

Athena's engine only natively understands one map: the Glue Data Catalog, which tells it where tables live in S3 and what columns they have. That's a hard boundary — plain Athena cannot see into DynamoDB, RDS, or anything outside S3.

Real systems don't keep all their data in one place. Customer profiles might sit in DynamoDB, orders in RDS, logs in S3. Federated Query removes the need to export everything into S3 first — it lets one SQL query reach live into other stores.

How it works internally

The bridge is a Data Source Connector — a Lambda function that translates between Athena's SQL engine and the external source's native API.

teal = native S3 path via Glue Catalog · orange = federated path via Lambda connectors

Register the source. You tell Athena about a new catalog (e.g. dynamo) and point it at a specific connector Lambda, deployed from AWS's Serverless Application Repository.

Query planning. Athena's planner pushes down whatever it can — filters, column selection — to the connector, so the source does as much filtering as possible before sending data back.

Translation. The connector converts the pushed-down request into the source's native call: a DynamoDB Query/Scan, or a JDBC SELECT against RDS.

Data returned as Arrow batches. The connector hands rows back to Presto in Apache Arrow format, a shared in-memory structure, so Presto can join rows from DynamoDB with rows from S3 as if they were one table.

Worked example

Say orders lives in S3 (via Glue Catalog) and customers lives in DynamoDB, registered as catalog dynamo_customers. One query can join both:

athena-sql -- s3_orders → native Glue-catalogued S3 table -- dynamo_customers.customers → DynamoDB via Lambda connector SELECT c.customer_id, c.name, COUNT(o.order_id) AS total_orders, SUM(o.order_total) AS lifetime_value FROM s3_orders_db.orders o JOIN dynamo_customers.customers c ON o.customer_id = c.customer_id WHERE o.order_date >= DATE '2026-01-01' GROUP BY c.customer_id, c.name ORDER BY lifetime_value DESC LIMIT 20;

Notice the syntax looks like an ordinary SQL join — that's the point of federation. What's invisible here is that orders is being scanned from Parquet files in S3 (billed at $5/TB scanned), while customers rows are being fetched live from DynamoDB through a running Lambda function (billed separately, for Lambda invocation + duration).

Metadata sourceGlue Data CatalogGlue Catalog (S3) + connector-reported schema (external sources)
SetupCrawler or manual DDLDeploy a Lambda connector per source, then register it
Extra costNone beyond scan costLambda invocation + duration, on top of scan cost
NetworkingNot applicableConnector Lambda needs VPC access if source is inside a VPC (e.g. RDS)

Common mistakes

Assuming federation is free beyond the usual Athena scan charge — the connector Lambda's invocation and duration are billed separately, and can dominate cost on large DynamoDB scans.
Assuming "federated" means "any database, zero setup." Each source type needs its own connector deployed; there's no universal "point at any SQL server" option.
Forgetting VPC networking for RDS-backed connectors — the connector Lambda needs the right subnets and security groups to reach a database inside a VPC. This is a very common real-world timeout cause.
Expecting S3-level performance from a federated source. Lambda's memory/timeout limits make large-table scans through a connector noticeably slower than Athena's native, parallel S3 reads.

Summary

In one sentence

Federated Query lets Athena run one SQL statement across S3 and non-S3 sources by routing the non-S3 parts through Lambda-based connectors that translate SQL into each source's native API and return results as Apache Arrow batches — at the cost of extra Lambda charges, per-source connector setup, and VPC networking for sources like RDS.
