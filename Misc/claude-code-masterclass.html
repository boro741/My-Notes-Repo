Chapter One

Getting Claude Code onto your machine

Claude Code is a version of Claude that lives on your computer instead of in a browser tab. That one difference changes everything: instead of just talking about your files, it can actually open them, edit them, and run them.

💡 What's a "terminal"?

A terminal is just a plain text window where you type commands instead of clicking buttons. It looks intimidating the first time, but you'll only ever need to know a handful of commands to use Claude Code — you're not learning to be a programmer, you're learning to type instructions to an assistant.

Claude Code isn't available on Anthropic's free plan — you need at least the Pro plan (roughly $17–20/month depending on your currency). That might sound like a strange thing to pay for, but think of it as buying back hours of your week. The productivity difference is closer to thousands of dollars a month once you're using it daily for real tasks, not just tens of dollars.

Sign up for Claude Pro (or higher)Create your Anthropic account and subscribe — this is the only paid step.
Open a terminalMac/Linux: search "Terminal." Windows: search "PowerShell" or "cmd."
Run the install commandCopy the command from code.claude.com/docs for your operating system and paste it into the terminal.
Type "claude" to launch itThe first time, it'll ask you to log in — pick the Pro/Max/Team subscription option, not the pay-per-API-call option.
Say helloYou now have a chat interface with an AI model that can read and write files on your actual computer.

Two things worth knowing before you dive in. First, screenshots of Claude Code will look slightly different by the time you read this — Anthropic ships changes constantly. Don't worry about the exact buttons; worry about understanding what each thing does. Second, everything in this course is written for non-programmers as much as programmers. You don't need to read code to use it well — Claude explains what it's doing in plain English if you ask.

💡 What's a "token"?

A token is roughly a chunk of a word — not quite a word, not quite a letter. For almost everything in this piece, you can just mentally substitute "word" wherever you see "token" and you'll be close enough. Tokens matter because you pay for them and because a model can only hold a limited number in its head at once (more on this in Chapter 10).

Once you're logged in, the interface shows you a few things worth recognizing: which model you're using (e.g. Opus 4.6), your current plan, the folder Claude Code is currently "standing in" on your computer, and — this is the important one — a context readout that climbs from 0% to 100% as your conversation grows. We'll come back to that a lot.

Chapter Two

IDEs: your file cabinet, notepad, and chat window in one

Most people don't run Claude Code straight in the terminal — they run it inside an IDE (Integrated Development Environment), which is really just three familiar tools glued together.

💡 What is an IDE?

Take your computer's file explorer (Finder or File Explorer), add a text editor (like Notepad), add an AI chat window (like the claude.ai website) — and put all three side by side in one app. That's an IDE. On the left you browse folders, in the middle you view/edit files, on the right you chat with the AI.

There are two IDEs worth knowing right now: Visual Studio Code (VS Code), the long-standing, extremely well-supported original, and Antigravity, a newer, more AI-forward tool built on the same foundation as VS Code — think of it as VS Code's more modern younger sibling.

Visual Studio Code

  • The long-established standard — huge community, huge support
  • Claude Code isn't built in — you install it as an extension
  • Great choice if you want the most stable, most documented option

Antigravity

  • Built by Google, on top of the same base as VS Code
  • More modern layout, more AI-native features out of the box
  • Some features are still a little rough around the edges

To install Claude Code inside either one: open the Extensions panel (the little block icon on the left edge), search "Claude Code," and install the one published by Anthropic specifically — not a lookalike.

⚠️ Only install extensions from verified publishers

Fake extensions that closely mimic real ones have been used to sneak malware onto people's machines. Always check that the developer name matches the official one before installing anything.

Once installed, you'll have a chat panel on the right where you talk to Claude, a file tree on the left where you browse your project, and an editor in the middle where you can see (and manually tweak) whatever file Claude is currently looking at. There's also a little "eye" icon that shows you exactly which file is currently being fed to Claude as context — useful for understanding what it does and doesn't already know.

Chapter Three

Building your first website with Claude Code

Here's the headline claim of this whole course, proven in practice: modern coding agents can build an award-quality website, front to back, in under ten minutes. Not a hero section — the whole site.

There are three main ways people currently get Claude Code to design things well. Each works by giving Claude a strong starting point instead of a blank page.

1. Give it a reference designScreenshot a site you like, feed it in, and let Claude take its own screenshots to compare and refine until it matches closely.
2. Voice-dump the contentSpeak everything you want on the site into a transcription tool — you talk ~200 words/min vs. typing ~60, so this is a 3x speed-up.
3. Copy pre-built componentsSites like 21st.dev let you copy a ready-made button, card, or animation and paste the definition straight into Claude Code.

Option 1 — the screenshot loop — tends to give the best results, because it removes hundreds of tiny decisions (font sizes, colors, spacing) that would otherwise eat your time and Claude's guesses.

The screenshot trick

To capture an entire page (not just what's visible on screen): open developer tools (Cmd/Ctrl+Shift+I), switch the viewport to a widescreen desktop size, open the command palette (Cmd/Ctrl+Shift+P), and run "capture full size screenshot." Then shrink the image (a free tool like a PNG resizer works fine) down to a few megabytes before handing it to Claude — a huge image just burns tokens and slows things down.

💡 Why does image size matter to an AI?

Every image you attach gets converted into tokens too, just like text. A giant, uncompressed screenshot can eat tens of thousands of tokens before you've typed a single word — money and "attention" spent before the real work even starts.

The Build → Test → Verify Loop
1. Give it a taske.g. "recreate this screenshot"
↓
2. It attempts the workwrites the first draft (usually ~80% right)
↓
3. It checks its own worktakes a screenshot, compares to the original
↺ repeat until close enough

This loop — do the task, then verify the result — is the single most important habit in this entire course. Skip the verification step and you lose most of the value of using AI at all.

This matters because AI isn't valuable because it's perfect on try one — it almost never is. It's valuable because it's fast enough to try, check, and fix itself many times in the time it would take a human to attempt it once. A human might nail 100% quality in five hours. Claude might hit 99% in five minutes by trying, checking, and correcting itself six or seven times in a row.

🖥️ Working on multiple designs at once

Because each Claude Code window is independent, you can open two or three side by side, give each the same reference design, and pick your favorite once they're all done — like commissioning three drafts instead of one. Just watch that you're not context-switching so often that Claude sits idle waiting on you more than 10–20% of the time; that's usually a sign you've opened too many tabs.

A practical safety note before you go further: it's fine to build tools like this for internal use or for clients you know. Publishing something you "vibe-coded" live on the internet — especially anything that takes payments or stores passwords — deserves at least one human security review first. Use an unguessable URL, and don't handle real customer data without a second pair of eyes on the authentication code.

Chapter Four

CLAUDE.md — steering the ship

If you create a file called CLAUDE.md in your project folder, Claude Code automatically reads it before it reads your very first message. It's the closest thing this tool has to a personality and a rulebook combined.

💡 What's Markdown (.md)?

Markdown is just plain text with light formatting — you write # Heading for a heading, - item for a bullet, and so on. No special software needed; any text editor opens it fine. It's the preferred format for these instruction files because it's easy for both humans and AI to read.

Every conversation with Claude Code secretly has an extra message injected at the very top, before your first one: whatever's in your CLAUDE.md. You never see this happen, but it shapes everything that follows.

Steering a Ship Across an Ocean

Imagine sailing from the U.S. East Coast to West Africa — thousands of kilometers away. If your steering wheel barely turns, a tiny error in your starting heading becomes a massive miss by the time you arrive. CLAUDE.md is that starting heading: get it right once, and even an imperfect prompt later still lands you close to where you meant to go.

Practically, this means: instead of retyping your preferences, conventions, and constraints into every single message, you write them once in CLAUDE.md and every future Claude session in that folder automatically "knows" them.

Do's and don'ts for writing one

Do: run /init firstIn any new folder, this tells Claude to read your whole codebase and write its own summary — this alone is most of the value.
Do: use bullets, be denseWrite like you're paying by the word (you kind of are). Put your most important rules at the very top.
Do: prune it over timeTreat it like living code — review and delete stale instructions the way you'd clean up an old to-do list.
Don't: paste in whole API docsThat can blow the file up to 10,000+ tokens, loaded on every single run — slower, pricier, and it actually makes Claude a little dumber.

💡 Why does a longer prompt make Claude "dumber"?

There's a real, measurable pattern where response quality drops as prompt length grows — the same way a person struggles to follow a memo that's 40 pages instead of 4. This is sometimes called "context rot," and it's a big theme throughout this whole course.

There's also a memory quirk worth knowing, called primacy and recency bias — Claude (like people) remembers the beginning and the end of a long document far better than the middle.

How well information is remembered, by position in the prompt
BeginningStrongly remembered
MiddleWeakly remembered
EndModerately remembered

Which is exactly why your most critical rule — "never delete the production database," say — belongs at the very top of the file, not buried on line 140.

Keep the whole file under roughly 200–500 lines. If it's a task rather than a rule (e.g. "how to scrape leads"), it probably belongs in a skill instead (Chapter 11), not crammed into CLAUDE.md.

Chapter Five

The .claude folder: settings, rules, agents, skills

CLAUDE.md is only the entry point. Inside a hidden folder called .claude, Claude Code gives you around a dozen advanced features most users never discover.

💡 Why does the folder start with a dot?

In programming convention, a leading period hides a folder from normal view — your regular file browser won't show it unless you ask to see hidden files. It's simply a way of keeping configuration out of your way while you're organizing your actual work.

.claude/
  ├── settings.json — team permissions & hooks
  ├── settings.local.json — your personal overrides, never shared
  ├── CLAUDE.md — the brain (Chapter 4)
  ├── CLAUDE.local.md — personal, git-ignored version
  ├── agents/ — sub-agent definitions (Chapter 14)
  ├── skills/ — reusable checklists (Chapter 11)
  ├── rules/ — CLAUDE.md split into topics
  └── .mcp.json — connected external tools (Chapter 12)

The rules folder solves a real problem: once your CLAUDE.md grows past a page or two, it becomes one giant, unwieldy file. Instead, you split it — for example into code-style.md, testing.md, security.md, and front-end.md — so each topic can be edited, shared, or restricted independently. On a team, this also lets you give a junior teammate edit access to the styling rules without giving them the keys to the security rules.

✂️ How to actually split one

Just tell Claude: "Split CLAUDE.md into its component rules, using the Claude Code rule specification." It'll research the format if it doesn't already know it, then break your file into logical pieces automatically.

Chapter Six

Global vs. local memory (and auto-memory)

There are actually three layers of CLAUDE.md that quietly merge together every time you start a session, plus a separate memory file that works completely differently.

1
Personal global — ~/.claude/CLAUDE.mdApplies to every project on your computer. Your own personal preferences and conventions.
2
Per-project — .claude/CLAUDE.md inside your workspaceApplies only to this one folder. Project-specific rules and context.
3
Enterprise — managed, system-levelSet centrally by a company for every employee. Most individuals will never touch this one.

💡 What does that little "~" (tilde) mean?

In file paths, ~ is shorthand for "my home folder" — the top-level personal folder on your computer, like /Users/YourName. It's not the folder you happen to be working in; it's the one place shared across everything you do.

Separately, Claude Code also keeps a tiny memory.md scratchpad that it writes to automatically whenever you say something like "remember that my dog's name is Yelpers." Unlike CLAUDE.md, you don't write this yourself — Claude does, and it injects it quietly into every new session so it "remembers you" without you repeating yourself.

🐕 A quick real example

Tell one Claude Code session "remember that my brother's name is George," then open a brand-new session later and ask "what's my brother's name?" — it'll just know, because the fact got written to that shared memory file behind the scenes.

Chapter Seven

Permission modes: how much rope to give it

Claude Code can edit real files on your real computer, so it needs a setting for how much it's allowed to do without asking you first. You cycle through these with Shift+Tab, or by clicking the little mode button at the bottom of the chat.

Ask before editsThe cautious default. Confirms every single file change with you first.
Edit automaticallyFreely edits existing files, but still asks before creating brand new ones.
Plan modeRead-only. Researches, reads, reasons — but touches nothing until you approve a plan.
Bypass permissionsFull autonomy — reads, writes, creates, deletes, without asking. Fastest, riskiest.

"Ask before edits" used to be the default for almost everyone, but if Claude is deep into a real build, stopping to ask permission every five seconds gets old fast. Most experienced users have shifted to either "edit automatically" or full "bypass permissions" — with eyes open about the trade-off.

⚠️ Bypass permissions is powerful, not free of risk

There's a real, documented case of someone running bypass mode where a misinterpreted request led Claude to run a destructive terminal command that wiped a hard drive. This is rare, but it's not zero. If you use bypass mode regularly, it's worth occasionally asking Claude to clean up unused files it's created — workspaces can quietly bloat with temporary junk over time.

To turn on bypass permissions for the first time, you generally need to enable it explicitly in your extension settings (search for "dangerously skip permissions" in your Claude Code for VS Code settings) — it's deliberately not the default.

Chapter Eight

Plan mode: measure twice, cut once

Of everything in this course, plan mode might be the single highest-leverage habit to build. Instead of jumping straight into edits, Claude spends a few minutes researching, reading your existing files, and reasoning through the approach — then hands you a written plan to approve before touching anything.

Build-without-plan vs. build-with-plan (same task)
Without plan: build → test → discover it's wrong → rebuild~35 min
With plan: plan (5 min) → build once, correctly~15 min

The logic is simple: it's cheap to change your mind on paper, and expensive to change your mind after you've already built the thing. Construction crews don't figure out the floor plan by pouring concrete and seeing what happens — they draw the blueprint first. Same idea here, just at software speed.

💡 Why does planning also save tokens?

Without a plan, Claude often explores several dead-end approaches while building — each one burning tokens on code that gets thrown away. A plan front-loads that exploration into cheap reasoning, so the actual building phase goes straight to the right approach the first time.

In practice, plan mode is genuinely conversational: Claude will pop up a few multiple-choice-style questions (which frontend framework, which database, how should payments work) before finalizing its plan — you're not expected to know the "correct" technical answer, just your actual preference.

Chapter Nine

Building a real app: the proposal generator

To prove plan mode works on something serious — not just a landing page — the course builds a full sales-proposal platform (a lightweight DocuSign/PandaDoc alternative) with logins, a database, e-signatures, and Stripe payments, in about 20 minutes end to end.

Both offer free "test" tiers for exactly this kind of experimentation.

Chapter Ten

Context management: the token budget game

Every Claude Code model has a maximum amount of text it can "hold in mind" at once — its context window. Most models today sit around 200,000 tokens, some go up to a million. Once you understand what's actually eating that budget, you can use it far more efficiently.

Type /context in any Claude Code session and you'll see something surprising: before you've even sent your first message, a meaningful chunk of your budget is already spoken for.

System prompt / CLAUDE.md
Built-in tools
MCP tools
Your messages

A rough breakdown of a typical, moderately-loaded Claude Code session — proportions vary a lot depending on your setup.

The categories, in order of what typically loads first:

  • System prompt — your global, local, and enterprise CLAUDE.md files, all stacked together.
  • System tools — the built-in abilities Claude always has (running terminal commands, searching files, editing, web search) — often the single biggest chunk, and something you can't shrink.
  • MCP tools — whatever third-party connectors you've installed (Chapter 12) — this varies wildly and some are shockingly bloated.
  • Memory & skills — tiny by comparison, often under 1% each.
  • Your actual conversation — often the smallest slice of all, at least at the start.

💡 Why does a huge MCP tool list hurt more than helps?

Every tool definition Claude has access to gets described in the prompt whether you use it or not — like handing someone a 40-page manual before every single task, even a five-minute one. A bloated MCP server can quietly eat 20% of your entire budget before you've asked anything.

Practical ways to protect your context

Use /compactManually compresses the whole conversation into a dense summary once it's grown long.
Use /clear between unrelated tasksWipes the slate clean — don't drag yesterday's debugging session into today's new feature.
Prefer skills over MCP where possibleSkills load almost nothing until actually invoked (Chapter 11) — vastly cheaper than a full MCP connector.
Write specific prompts"Fix the login button on the signup page" burns far fewer tokens exploring dead ends than "improve this codebase."

Claude Code also does a lot of this for you automatically: as your conversation approaches the limit, it silently compresses older messages into denser summaries in the background — a process called auto-compaction — so you rarely hit a hard wall unannounced.

Chapter Eleven

Skills: turning your know-how into a button

A skill is a saved checklist — written once, in plain Markdown — that turns a repeatable piece of knowledge work into something Claude can execute on demand, the same way every time, without you re-explaining it.

Skill = Conductor + Orchestra

The SKILL.md file is the conductor — it doesn't play an instrument itself, it directs. The scripts/ folder next to it holds the actual "musicians" — small programs that do the same repeatable step reliably every time. Claude reads the checklist, runs the scripts in order, and uses its own judgment to recover when a step goes sideways.

A real example from the course: a "scrape leads" skill that finds business leads, verifies a small test batch, runs a full parallel scrape, classifies each lead with AI, uploads everything to a spreadsheet, and fills in missing email addresses — a task that used to take a person 30–60 minutes by hand, run in under two minutes.

~2 min
to scrape, classify & organize 1,000 leads
63
tokens loaded for an unused skill (near-zero cost until invoked)

💡 Why do skills cost so few tokens?

Only the very top of a skill file (its "name" and "description," called the front matter) is loaded into context by default. The full checklist only loads if Claude decides the skill is actually relevant to what you asked — so having fifty skills sitting around costs you almost nothing until one of them actually gets used.

How to build one

You don't need to write these from scratch. The fastest path: describe the task in plain language (bullet points or a voice dump), point Claude at an existing skill as a formatting example, and ask it to write the new one for you. Then run it on a fresh Claude session with zero prior context and see how it does — treat mistakes as feedback, refine, and repeat until it's reliably accurate.

In practice, this replaces a meaningful chunk of what a human assistant or contractor used to do: lead scraping, literature reviews, automated email labeling, YouTube editing checklists, client onboarding steps — anything that follows "do X, then Y, then Z, and handle it this way if something goes wrong" is a skill candidate.

Chapter Twelve

MCP: giving Claude new hands

MCP (Model Context Protocol) is essentially a skill that someone else already built for you — a plug-in that gives Claude the ability to operate a specific piece of software, like controlling a real Chrome browser, reading your Gmail, or managing tasks in ClickUp.

💡 So what's the actual difference from a skill?

A skill is your own checklist, usually backed by small scripts you (or Claude, for you) wrote. MCP is a ready-made connector, usually built and maintained by a third party, that you just plug in. MCP is faster to set up; skills are cheaper to run and easier to fully trust, because you can see exactly what they do.

To install one, you generally paste a small block of configuration text (provided by whoever built the connector) into Claude Code and say "install this in my local workspace." You'll often need to supply an API key or log in once to authorize access.

Token cost: a single MCP connector vs. a whole folder of skills
One task-management MCP connector~20,000 tokens
An entire folder of custom skills~300 tokens

A sensible workflow: use MCP to quickly test whether something is even possible ("can you check my ClickUp tasks?"). If it works and you'll use it often, ask Claude to convert that same capability into a lightweight, purpose-built skill instead — same result, a fraction of the ongoing token cost.

⚠️ Not every MCP server is trustworthy

These are typically built by third parties and listed on community directories, not officially vetted by Anthropic. Stick to well-known, actively maintained ones, and be cautious about connecting anything to sensitive accounts you can't afford to have misused.

Chapter Thirteen

Plugins and marketplaces

Plugins bundle up settings, rules, and sometimes MCP connectors into a single install — think of them as a starter pack rather than something you'll configure from scratch every time.

A couple worth knowing: Context7, which compresses API documentation into a token-efficient form Claude can search instead of reading in full, and Anthropic's own front-end design plugin, aimed at improving default visual quality (results are genuinely mixed — your own screenshot-loop workflow from Chapter 3 often beats it).

None of this is required. A completely default, plugin-free Claude Code install already does the vast majority of what's covered in this course perfectly well. Plugins are worth exploring once you've hit a specific, recurring friction point — not something to install preemptively "just in case."

Chapter Fourteen

Subagents: cheaper, faster, parallel

A subagent is a smaller Claude instance, spawned by your main ("parent") agent, that gets its own clean context window, does one focused job, and reports back a short summary — instead of dragging a hundred thousand tokens of research directly into your main, expensive conversation.

Why Delegate to a Subagent
Parent agentyour main, expensive, smart conversation
↓ delegates
Subagent (cheaper model)burns 100,000 tokens researching in its own isolated window
↓ returns only
~2,000-token summarythe only thing that touches your main context

That's roughly a 50x reduction in what your expensive parent model actually has to read — while the heavy lifting still gets done in full.

The three subagents worth having by default

ResearcherGoes and digs through the web or your files so your main thread doesn't have to hold all that raw material.
ReviewerLooks at freshly-written code with zero context and zero bias — often catches things the original "author" was too invested to notice.
QA / testingWrites and runs tests against new code or a new feature to verify it actually works as intended.

💡 Why is a "blank slate" reviewer actually more useful?

The agent that just wrote a block of code is biased toward defending the choices it already made — the same way a person who just spent ten hours on an approach struggles to see its flaws. Handing the result to a fresh agent with zero history, and asking "is this good?", strips out that bias entirely.

Parallelization: doing three things at once

Serial
Task 1 → Task 2 → Task 3 = 3 min
Parallel
All 3 at once = 1 min

Real-world result from the course: classifying and labeling 100 emails took 36 seconds one-at-a-time; splitting the same job across 10 subagents brought 1,000 emails down to roughly a minute total.

⚠️ More subagents ≠ always better

Each subagent has some chance of failing or returning malformed output. If each has a 95% success rate, running 3 in sequence succeeds ~86% of the time — but running 50 drops to roughly 7%. Keep subagent tasks narrow and simple, and don't spawn more than you actually need.

Chapter Fifteen

Agent teams & git worktrees

Agent teams take the subagent idea up a level: instead of one parent handing out isolated one-off tasks, you get a "team lead" agent that manages several fully independent teammates — each with its own complete context window, each able to message the others directly, coordinating through a shared task board.

Subagents

  • Report only back to the parent
  • Relatively cheap — narrow, focused tasks
  • Best for: one clear result you need quickly

Agent teams

  • Teammates can message each other directly
  • Roughly 7x the token cost of a normal session
  • Best for: complex work needing genuine back-and-forth
Case Study · Security Audit via Agent Team

10 agents scanned a large open-source codebase in parallel; 4 more consolidated findings while 2 "devil's advocate" agents debated each flagged issue back and forth to separate real risks from false alarms — a process that would realistically take a human security team days, compressed into roughly 15 minutes.

15real issues found
~$80in tokens spent
~15 mintotal time

⚠️ Agent teams are disabled by default for a reason

It's genuinely easy to spend far more than you intend once several full Claude instances are running in parallel, each with its own context window. Treat this feature the way you'd treat a company credit card with no spending limit — powerful, but worth a deliberate decision every time you reach for it.

Git worktrees: keeping agents out of each other's way

💡 What's "Git," in one sentence?

Git is a system for tracking every change ever made to a project, organized into "branches" — parallel copies of the same project that can be worked on independently and later merged back together.

A worktree gives each agent its own separate folder (backed by its own Git branch) to work in, so two agents building different pages of the same site can never accidentally edit the same file at the same time. When each is done, their separate branches merge back into one main project — cleanly, with no agents stepping on each other's toes.

Chapter Sixteen

Shipping it: turning workflows into URLs

The final piece is putting your work somewhere other people (or other software) can actually reach it. For a simple static site, a service like Netlify pushes your local files live in a couple of clicks. For backend logic — a skill, a script, a small API — a service like Modal lets you turn any workflow into its own public web address.

💡 What's an "API endpoint," really?

It's just a URL that does something instead of showing you a page — visit it (or have another program visit it) and it runs code and gives back a result. A "webhook" is the same idea in reverse: another service visits your URL automatically when something happens on their end.

Case Study · Skill → Public URL

The lead-scraping skill from Chapter 11 was wrapped into a public webpage in about two minutes: visit the link, fill in a simple form (what to search, how many results), and get back a downloadable spreadsheet of verified leads — turning a personal script into something any teammate could use without touching a terminal.

This is the pattern worth remembering: build the workflow once as a skill, wrap it behind a URL once, and from then on it's just a link — shareable, reusable, and pluggable into no-code tools like Zapier or Make.com through the same webhook mechanism they already understand.
