Quarkus ke Andar Kya Hai? Internal Architecture + Lambda

Why does Quarkus start in milliseconds while old-style Java takes seconds? Chalo, step by step samajhte hain.

8 min read • Architecture, AWS Lambda, Spring Boot comparison

Is blog mein kya hai 1. The big idea: build time vs runtime 2. Internal architecture 3. Why great for Lambda 4. Uploading to AWS Lambda 5. Quarkus vs Spring Boot 6. Summary

1. The big idea: kaam pehle hi kar lo

A traditional Java framework wakes up, then discovers your app: it scans classes, reads annotations, builds dependency-injection wiring, creates proxies. All of this happens at runtime, on every start. That is slow and eats memory.

Quarkus flips this. It does the discovery work once, during the build. At startup it only runs the already-prepared result.

Analogy (हिंदी में)

मान लो आप रोज़ सुबह ऑफ़िस जाते हो। Traditional framework हर सुबह बैग पैक करता है। Quarkus रात को ही बैग पैक करके रखता है, सुबह बस उठाओ और निकलो।

2. Internal architecture

Quarkus has four main parts working together. Pehle picture dekho, phir ek-ek part samjhenge.

Extensions

Each extension (REST, Hibernate, Lambda) has a build-time part that reads your code and a small runtime part. Yehi Quarkus ka dimaag hai.

ArC (CDI)

Dependency injection is resolved during the build. No heavy reflection or scanning at startup.

Jandex index

A pre-built index of your classes and annotations. Quarkus reads this instead of scanning every class.

Vert.x + Netty

Event-loop based I/O underneath. Few threads handle many requests, so memory stays low.

Build pipeline in 4 steps

  • Index: Jandex scans your jar once.
  • Augment: extensions process annotations and decide what is needed.
  • Record: startup actions are saved as plain bytecode (no reflection).
  • Package: output is a runnable jar or a GraalVM native binary.
Interview line

"Quarkus moves classpath scanning, DI wiring and config parsing to build time (augmentation), so runtime has less work and a smaller footprint."

Common mistake

Using reflection-heavy libraries in native mode. GraalVM needs to know every class upfront (closed-world), so dynamic loading must be registered or avoided.

3. Lambda ke liye kyun best?

Lambda starts a fresh environment when no warm one exists. That is a cold start, and you pay for its time. Quarkus attacks exactly this pain.

Fast cold start

Build-time work + native image means almost no startup cost.

Low memory

Smaller RAM setting on Lambda, so lower cost per invocation.

Small package

Fewer classes and no unused framework code. Deploy aur upload dono fast.

Paisa-vasool point

Lambda में आप milliseconds और memory के हिसाब से पैसे देते हो। Quarkus कम समय और कम memory लेता है, इसलिए bill भी कम आता है।

Tip

Even without native, the JVM build is a good Lambda citizen. Pair it with Lambda SnapStart if you want to stay on the JVM runtime.

4. AWS Lambda par upload kaise karein

Step 1: Add the extension

<dependency>
  <groupId>io.quarkus</groupId>
  <artifactId>quarkus-amazon-lambda</artifactId>
</dependency>

Step 2: Write a handler

@Named("hello")
public class HelloLambda implements RequestHandler<InputObject, OutputObject> {
    @Inject GreetingService service;   // normal CDI works

    @Override
    public OutputObject handleRequest(InputObject in, Context ctx) {
        return new OutputObject(service.greet(in.getName()));
    }
}

Step 3: Build

Option A: JVM mode (simple, use Java 21 runtime or SnapStart)

./mvnw clean package
# creates target/function.zip

Option B: Native mode (fastest start; build in a container so it targets Amazon Linux)

./mvnw clean package -Dnative -Dquarkus.native.container-build=true
# creates target/function.zip with a "bootstrap" binary

Step 4: Upload

# JVM mode
aws lambda create-function --function-name hello \
  --zip-file fileb://target/function.zip \
  --runtime java21 \
  --handler io.quarkus.amazon.lambda.runtime.QuarkusStreamHandler::handleRequest \
  --role arn:aws:iam::<ACCOUNT_ID>:role/<LAMBDA_ROLE> \
  --environment Variables={QUARKUS_LAMBDA_HANDLER=hello}

# Native mode: same, but use
#   --runtime provided.al2023 --handler not.used.in.provided.runtime
Good to know

Quarkus also generates sam.jvm.yaml and sam.native.yaml in target/, so sam deploy works too. Exact flags can change between versions, so check the current Quarkus AWS Lambda guide.

Common mistake

Building native on macOS/Windows without container-build=true. The binary will not run on Lambda's Linux. Also, do not forget to set the architecture (x86_64 vs arm64) to match your build.

Short mein

Extension जोड़ो, mvn package चलाओ, function.zip बनेगी, उसे Lambda पर upload करो। बस इतना ही!

5. Quarkus vs Spring Boot

Spring Boot is mature and has a huge ecosystem. Quarkus is newer and built for containers and serverless. Dono acche hain, bas use case alag hai.

PointQuarkusSpring Boot
Core approachBuild-time augmentationMostly runtime reflection and proxies
Cold start (Lambda)Very fast, especially nativeSlower on JVM; improves with SnapStart or Spring native (AOT)
MemoryLowHigher on JVM
Native imageFirst-class, designed for itSupported (Spring AOT), more setup
Dev experienceLive reload, dev servicesDevTools, very familiar
EcosystemGrowing, many extensionsHuge, plenty of libs, jobs, tutorials
Learning curveEasy if you know CDI/JAX-RS; Spring devs have a compat layerGentle for most Java devs
Best forServerless, microservices, K8sLarge enterprise apps, existing Spring teams
Kab kya choose karein

New Lambda function where cold start and cost matter: pick Quarkus. Big existing Spring codebase and team: Spring Boot with SnapStart is often the practical choice.

6. Summary

  • Quarkus does scanning, DI and config work at build time, so runtime starts fast.
  • Core parts: extensions, ArC, Jandex, Vert.x/Netty, and JVM or GraalVM native output.
  • For Lambda: faster cold starts, less memory, lower bill.
  • Deploy with quarkus-amazon-lambda, build function.zip, upload via CLI or SAM.
  • Spring Boot wins on ecosystem; Quarkus wins on startup and footprint.
