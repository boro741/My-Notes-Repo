Ek line mein har naam

javac
Compiler jo .java ko bytecode (.class) mein badalta hai. Build time par chalta hai.
JVM
Bytecode ko run karta hai. Pehle interpreter se, phir JIT ke saath.
JIT
JVM ke andar ka compiler. Runtime par hot (baar-baar chalne wala) bytecode ko machine code bana kar RAM mein rakhta hai.
JRE
JVM aur libraries ka package, bas chalane ke liye.
JDK
JRE ke upar javac jaise build tools. Developer isse install karta hai.

Code ka safar

  1. Build time: javac tumhare .java ko bytecode bana deta hai.
  2. Run: java -jar app.jar par JVM start hota hai aur interpreter bytecode line-by-line chalata hai.
  3. Runtime: JIT dekhta hai kaunsa code bahut chal raha hai aur use machine code bana kar RAM (Code Cache) mein rakhta hai.

Common galti: bytecode JIT nahi banata, javac banata hai. Aur JIT ka machine code sirf RAM mein rehta hai. App band hui toh sab gaya, aur agli baar warm-up phir zero se shuru hota hai.

HotSpot, GraalVM, JIT vs AOT

  • HotSpot: Default JVM. Iska JIT runtime par kaam karta hai, isliye warm-up time lagta hai.
  • GraalVM: Upgraded JDK. Ya toh smarter JIT deta hai, ya Native Image (AOT).
JIT: run karte waqt

Trigger: java -jar app.jar.
Machine code RAM mein banta hai, aur har run par dobara.

AOT: build karte waqt

Trigger: ./mvnw package -Dnative.
Machine code disk par ek binary file mein save hota hai.

AOT ka matlab Ahead-Of-Time: code ko chalne se pehle hi machine code bana lo. Run par OS binary ko seedha RAM mein load karta hai. Na JVM, na JIT, na warm-up.

Native file ko kaise pehchanein: Windows par .exe, Linux/macOS par bina extension ki file. Ise ./myapp se chalate hain, java command ke bina.

Kuch aur jargon

Reflection
Runtime par naam se classes dhoondhna aur call karna. Flexible hai, par slow.
Classpath scan
Saare jars mein @Component jaisi annotations wali classes dhoondhna.
Proxy
Tumhari class par ek wrapper, jaise @Transactional ke liye.

Spring Boot: har start par yeh hota hai

  1. Scan. Saari classes ki annotations reflection se padhta hai.
  2. Conditions check. Auto-configuration ki hundreds conditions dekhta hai. Zyadatar ka jawab "no" hota hai.
  3. Beans banata hai. Objects create karke ek-dusre se jodta hai.
  4. Proxies. Wrapper classes runtime par generate hoti hain.
  5. Server start. Tomcat on, ab app ready hai.

Har restart par yahi kaam repeat hota hai, aur iska data memory mein bhi padha rehta hai.

Quarkus: yeh sab build time par

  1. Index. Classes aur annotations sirf ek baar scan hoti hain (Jandex).
  2. Extensions decide karte hain. Kaunsa bean chahiye aur kaise jude, sab build mein tay ho jata hai.
  3. Code generate. Direct calls wala plain code ban jata hai. Reflection nahi.
  4. Unused hatao. Jo use nahi hota, wo app se nikal jata hai.

Startup par sirf generated code chalta hai. Scan nahi, check nahi, guess nahi.

Quarkus aur GraalVM ka jodi

  • Native Image ko build time par har class pata honi chahiye. Runtime reflection usko pasand nahi.
  • Spring Boot ko isliye extra AOT hints aur config files deni padti hain.
  • Quarkus sab build time par resolve karta hai, toh uska output native ke liye already ready hota hai.

Trade-off: Native build mein minutes lagte hain, aur lambe, heavy load par warmed-up JIT kabhi-kabhi thoda aage nikal jata hai. Native optional hai. Kai teams sirf JVM mode mein Quarkus chalake bhi fayda le lete hain.

Chhota aur tez kyun?

  • Kam classes load hoti hain aur scanning ka data memory mein nahi rehta.
  • Unused code build time par hi hat jata hai.
  • Native mein JVM ka overhead bhi nahi hota.

Spring Boot bhari kyun lagta hai? Runtime scanning, conditions aur proxies ki wajah se. Ye galti nahi hai, flexibility ki keemat hai.

Dhyan rahe: Spring Boot 3 mein AOT, native support, virtual threads aur CRaC aa chuke hain, aur gap kam ho raha hai. "Chhota" ka matlab zyadatar memory hota hai. Native file jar se badi ho sakti hai, par usse JDK nahi chahiye.

Khud try karo

Java 17+ aur Quarkus CLI (ya Maven) chahiye.

# app banao aur dev mode mein chalao
quarkus create app org.acme:hello --extension=rest
cd hello
./mvnw quarkus:dev

# native build (container mein hota hai)
./mvnw package -Dnative -Dquarkus.native.container-build=true

# Linux par check karo ki ye asli binary hai
file target/*-runner

Normal build ke baad target/quarkus-app/quarkus/generated-bytecode.jar kholo. Wahan wo classes hain jo Quarkus ne tumhare liye build time par likhi hain.

Yaad rakhne ke liye

  • javac bytecode banata hai. JIT runtime par hot code ko machine code banata hai.
  • Spring Boot: startup par figure out karta hai.
  • Quarkus: build par figure out karta hai, startup par sirf run karta hai.
  • GraalVM Native (AOT): isi ko build time par binary bana deta hai, instant start ke saath.
Numbers app ke hisaab se badalte hain. Decide karne se pehle apni service par khud measure karo.
