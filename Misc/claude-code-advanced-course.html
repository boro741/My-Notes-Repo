Chapter One

What a CLAUDE.md File Actually Is

A CLAUDE.md is a plain text file that Claude Code automatically reads at the start of every session. Think of it as a note you leave on Claude's desk before it starts work — except that note can save you thousands of tokens and hours of back-and-forth.

💡 New word: token

A "token" is roughly a chunk of a word. AI models are billed and measured by how many tokens they read and write. Fewer tokens = cheaper and usually faster, because the model has less to wade through before it can think clearly.

After watching how experienced users actually use this file, it boils down to four jobs. Your CLAUDE.md is never just one of these — it's usually doing all four at once, in different sections.

1. Knowledge compressionInstead of Claude reading every file in your project each time, the CLAUDE.md gives it a short summary of what's where and why.
2. Your preferencesHow you like file paths returned, which language you code in, what conventions you follow — things Claude doesn't know by default.
3. A list of capabilitiesSpelling out what Claude is actually allowed and able to do, so it stops underestimating itself and asking you to do things it can do on its own.
4. A log of failures and successesA running diary of "we already tried this and it didn't work" — so the next session doesn't waste time repeating old mistakes.

Why compression matters so much

Here's a real example from the course. A whole component file in a website project ran to about 1,100 tokens. The CLAUDE.md description of that same file was about 22 tokens — a 45x compression. Multiply that across a whole project, and you can see why a good CLAUDE.md means faster answers and a smaller bill.

Tokens needed to understand one file
Reading the raw file~1,100 tokens
Reading the CLAUDE.md summary~22 tokens

📌 The quickest way to start

Open a project in Claude Code and type /init. Claude will read through your whole workspace and generate a CLAUDE.md for you automatically — build commands, folder layout, style conventions, all of it. Then you edit it by hand from there.

Chapter Two

Global vs. Local: Two Notebooks, One Brain

Claude Code actually reads from two different CLAUDE.md files, and knowing the difference changes what you write in each one.

Global (~/.claude/CLAUDE.md)Loaded on every single session, in every project, no matter what. This is where your personal context, high-level reasoning habits, and standing preferences live.
Local (.claude/CLAUDE.md in a project)Loaded only when you're working inside that specific project. This is where low-level, project-specific knowledge and lessons learned belong.

A good rule of thumb: put things in global that are true about you no matter what project you're in — your name, your goals, how you like decisions explained, your general coding style. Put things in local that are true about this one project — where the code lives, which API it calls, what broke last time.

💡 New word: agent

An "agent" is an AI model that's been given tools — the ability to read files, run commands, browse the web, and so on — instead of just chatting back at you in text. Claude Code turns the Claude model into an agent.

"Claude entities are highly personal devices." — on why nobody should just copy someone else's CLAUDE.md word-for-word

Chapter Three

The Loop That Keeps Getting You Faster

There are two small workflows that, run over and over, make Claude Code noticeably better at your specific work over time.

The local loop

  1. Plan a feature or task with Claude.
  2. Claude builds it, hitting a mix of failures and successes along the way.
  3. You compile the learnings into a short, dense note.
  4. You update the local CLAUDE.md with that note.

Do this every time, and each future task gets a little faster — the first feature might take a certain amount of time, the second takes about 90% of that, the third 80%, and so on, because you keep shaving failed paths off the search space.

The Local Workflow Loop

Plan → build → compile learnings → update CLAUDE.md → repeat. Each lap makes the next lap shorter.

The global loop

After hundreds of local runs, patterns emerge that show up across every project — not just one. That's when you zoom out to the global file. Claude Code has a built-in /insights command that scans your conversation history and produces a report of recurring mistakes and habits.

📌 Keep a human in this part of the loop

Here's the math on why: if Claude is 90% reliable on its own, and you chain three AI decisions together with nobody checking in between, your overall reliability is 0.9 × 0.9 × 0.9 — about 73%, not 90%. Because your global file gets applied to every future project, it's exactly the spot worth a human giving it a manual read before saving.

1

Put together, the two loops form a figure-eight: mostly looping locally, occasionally looping up to global, then back down again — spending more time in the small loop over time as your global file matures.

Chapter Four

What Is an "Agent Harness"?

You'll hear "agent harness" thrown around a lot right now, and it's simpler than it sounds: it's just Claude Code itself — everything wrapped around the raw Claude model that lets it actually do things.

💡 New word: harness

By itself, an AI model like Claude only does one thing: takes in text and produces text back. A harness is all the extra machinery around it — the system prompt, the tools it's allowed to use, the memory settings, the rules about how often it checks in with you — that turns "a very smart text box" into "something that can edit files and run your business."

Same Core Technology, Different Range

Same gunpowder (the model's intelligence) — but the barrel and rifling (the harness) decide how far and how accurately it goes.

Claude Code is the dominant harness today, but it's not the only one. Others include Droid (by Factory AI), the open-source pi.dev, and various multi-agent frameworks. Anthropic's own November 2025 post, "Effective Harnesses for Long-Running Agents," is worth reading if you want to go deeper — it laid a lot of the groundwork for how Claude Code manages long tasks today.

⚠️ A harness also affects safety

How a harness handles permissions matters. There have been real examples of agents blocked from running a dangerous command (like one that wipes a whole drive) simply rewriting the same destructive action a different way to get around the block. The harness — not just the model — is what decides how much guardrail actually holds.

Chapter Five

Why Bother Running Things in Parallel

If you've ever fired off a long task and just sat there watching Claude work for fifteen minutes, you already know the problem: waiting isn't productive. Parallelization means doing several things at once instead of one after another.

Four reasons it's worth the extra setup

  • Speed. Independent steps don't need to wait on each other.
  • Better answers through randomness. AI models are "stochastic" — ask the same question five times and you'll get five slightly different answers. Running several at once catches ideas a single run would have missed.
  • Specialization. Different models are better at different jobs — a fast, cheap model for research; a stronger model for the final judgment call.
  • Cleaner context. A model thinks best with a short, focused conversation. Splitting work across fresh agents keeps each one in that sweet spot.

💡 New word: stochastic

"Stochastic" just means "involving randomness." AI models don't recalculate the exact same answer every time — there's a bit of controlled randomness in how they pick each next word, so repeated runs diverge, sometimes usefully.

Doing four steps one at a time vs. together

Total time for a 4-step task
One after another (serial)20 minutes
Three run together + one synthesis step12 minutes

That's a 40% time cut just from running the independent pieces side by side instead of in a queue.

📌 The "zone of good"

Model quality tends to drop as a single conversation gets longer and more cluttered. Splitting a big job across several short-lived agents keeps each one in what's informally called the "zone of good" — short, focused, high-quality — instead of one overloaded agent slowly sliding into worse answers.

Chapter Six

Three Team Patterns Worth Stealing

Once you accept that splitting work across agents is worth it, three patterns cover almost everything you'll want to do.

1. Fan out, then fan in

Instead of one agent researching four sources one after another (accumulating a longer and longer, lower-quality context window as it goes), you spawn several research agents at once — each with its own clean context — and then feed all their findings into a single "synthesizer" agent that combines everything.

Fan Out → Fan In

Fan out to several cheap, fast agents in parallel; fan in to one strong model that combines the results.

📌 Split the work by strength, not just by count

Research tends to need a lot of reading but not much deep reasoning — use a cheaper, faster model (like Sonnet or Haiku). Final synthesis needs judgment — use your strongest model (like Opus). This split alone can cut cost by 60% or more, while running faster.

2. Stochastic consensus and debate

Ask ten agents the same open-ended question independently, and count how often each idea shows up. Ideas that many agents land on independently are your safest bets; ideas only one agent proposed are your interesting outliers. "Debate" takes this further — agents get to see each other's answers in rounds and refine their own, converging on more nuanced solutions than any single agent would reach alone.

3. Pipelines: sequential handoffs between specialists

Some jobs are better split by role, not by running them all at once. A developer agent is naturally incentivized to build fast; a QA agent is naturally incentivized to find flaws. Those goals conflict, so handing the same agent both jobs tends to produce worse results than two specialized agents handing work back and forth.

📌 Two setups that cover most needs

Parent + researchers + QA: a strong "parent" model delegates research to several cheaper models and hands finished work to a QA specialist.
Developer + QA only: simpler — one strong builder, one fresh-context QA reviewer with zero bias toward the work it's checking.

Chapter Seven

Sub-Agents and Skills Are Secretly the Same Thing

You'll see a lot of elaborate "AI org chart" tools online — dashboards with a CEO agent, a CTO agent, a customer-support agent, and so on. It's tempting to dismiss these as gimmicks. But strip away the job titles, and both sub-agents and skills turn out to be doing the same underlying thing: organizing information into markdown files with a name, a description, and a set of allowed tools.

💡 New words: sub-agent and skill

A sub-agent is a mini version of Claude spun up with its own fresh, empty conversation and a specific job. A skill is a folder containing a markdown file (SKILL.md) describing a repeatable task, plus any tools or scripts it needs. The only real difference: a sub-agent always gets a completely clean memory; a skill is just very efficiently written, so it barely uses any memory anyway.

A well-designed skill is written so densely that using it costs about the same, in tokens, as spinning up a whole fresh sub-agent — which is why the line between the two keeps blurring.

📌 A saner alternative to giant org charts

Rather than building a 26-agent company chart with a "Head of Sales" and a "Customer Success Manager," the two design patterns worth actually using are the ones from Chapter Six: parent + researchers + QA, or the simpler developer + QA. Both get you the benefits of specialization without piling up unnecessary layers that add delay and compound errors.

Chapter Eight

Organizing a Workspace That Scales

A messy folder confuses your agent just as much as it confuses you. Here's a simple structure that holds up whether you're running a business, freelancing for clients, or just managing your own life.

The four folders every workspace needs

.claude/Your skills, sub-agents, and other Claude-specific setup live here.
active/Everything Claude generates day-to-day — reports, research, screenshots — sorted into subfolders, never dumped loose in the root.
.envAll API keys and credentials, and nowhere else. One place to secure, one place to rotate.
CLAUDE.mdYour local system prompt — the project's own memory and preferences.

Business, client, and personal — kept separate

One layout that holds up well: a top-level business workspace containing your own CLAUDE.md and skills, with separate client subfolders underneath — each with its own env, skills, and CLAUDE.md describing that specific client's context. A parallel personal workspace, organized by area of life (health, citizenship paperwork, hobbies) rather than by client, keeps personal and professional Claude conversations cleanly apart.

💡 Small trick: color-code your editor

Giving your personal workspace a different accent color in your code editor (via a simple settings file) gives your brain an instant visual cue: "I'm in personal mode now, this can include personal details" versus "I'm in business mode."

The golden rule: don't pollute the root

Every skill should specify exactly where its output files go (e.g., active/model-chat/), and it's worth periodically asking Claude to sweep the active folder — sorting loose files into proper subfolders and deleting genuine junk. A clean workspace tends to produce cleaner work.

📌 Backup plan: mirror your CLAUDE.md into other formats

Keeping a synced copy of your CLAUDE.md as AGENTS.md and GEMINI.md means that if Claude Code ever goes down, you can switch tools without starting from zero. More on why that matters in Chapter Eleven.

Chapter Nine

Auto Research: Let the AI Run the Experiments

This idea traces back to AI researcher Andrej Karpathy (former head of AI at Tesla, a founding member of OpenAI), who noticed his own research process was basically a loop he could hand entirely to AI: make a hypothesis, try it, measure it, keep it or discard it, write down what happened, repeat — overnight, without him.

The Auto Research Loop

Hypothesis → change the code → measure the result → log it → repeat, hundreds of times, with no human watching each cycle.

Three things you need before you can use it

  1. A metric — something objective you're trying to improve (a page-speed score, a conversion rate, a response time).
  2. A change method — a direct way to influence that metric (editing code, editing a prompt, editing copy).
  3. An assessment — a fast, repeatable way to check whether a change actually helped.

💡 New terms: LCP, FCP, TBT

These are Google's standard website speed measurements, part of the "Lighthouse" score: LCP (Largest Contentful Paint — how long the biggest visible element takes to load), FCP (First Contentful Paint — how long until anything appears at all), and TBT (Total Blocking Time — how long the page is too busy to respond to clicks).

Speed matters here. If a change takes an hour to make and an hour to assess, you only get one loop every two hours — still faster than a human, but far from spectacular. If both steps take about 30 seconds, you can run roughly 1,440 experiments a day.

Compounding a 1% improvement per successful run
30 good changes/day≈ 34% improvement
90 good changes/day≈ 2.4x
180 good changes/day≈ 6x
Real example

Shopify's CEO, Tobi Lütke, pointed an autonomous research setup at Shopify's own Liquid templating codebase overnight.

53%faster combined parse + render time
61%fewer object allocations

You can apply this same three-part recipe to almost anything with a measurable goal: a SaaS app's backend speed, a customer-support prompt, an ad's click-through rate, or cold email response rates. To try it, clone Karpathy's auto-research repository from GitHub and point it at your own metric, change method, and assessment.

Chapter Ten

Automating the Internet: HTTP, Browsers, and Computers

There are three levels of automation available to Claude, and each trades setup time for speed and reliability differently.

Level 1 — HTTP requests

💡 New word: HTTP request

HTTP (HyperText Transfer Protocol) is simply the way your browser talks to a website's server. When you type a web address and hit enter, your browser sends a "request," and the server sends back the page's content, which your browser then turns into the pretty page you see.

Claude can send these requests directly, which makes it very good at reading and scraping websites in bulk. It's the fastest and cheapest option once it's set up, but it's fragile — every website's structure is a little different, and many sites actively try to block this kind of automated access.

Level 2 — Browser automation

When a task needs clicking buttons, filling out forms, or navigating a page the way a person would, Claude can control an actual browser instance — using tools like Chrome DevTools MCP, or paid platforms like Browser Use that specialize in avoiding detection (useful for things like social media, which actively fight simple scraping).

Level 3 — Computer automation

The most general and most expensive option: Claude literally controls your mouse and keyboard, the same way you would. It always works, no matter how unusual the task, but it's slow and burns through a lot of tokens because it has to take a screenshot and think after nearly every click.

Setup time vs. speed and cost, by automation level
HTTP requestsMore setup, then fast & cheap
Browser automationMiddle ground
Computer automationAlways works, slow & pricey

📌 A practical rule of thumb

Start with browser automation to prototype something quickly. Once you know it works, ask Claude to inspect the underlying network requests and build a lighter, faster HTTP-based version for repeated use. Save full computer automation for tasks nothing else can handle, like scanning your own local file system.

⚠️ A word of caution

Automating interactions on platforms you don't control — scraping, mass messaging, bulk form submissions — is often against those platforms' terms of service. This is simply a description of what the tools can do, not a recommendation to break any rules you've agreed to.

Chapter Eleven

When Claude Code Has a Bad Day

Farmers learned this lesson centuries ago with monoculture crops: when one especially productive crop replaces everything else in a field, one bad season — a disease, a pest, a bad batch of soil — can wipe out the entire harvest at once. Relying on a single, highly productive AI tool for everything creates the exact same risk.

💡 New word: monoculture

Monoculture means growing (or in this case, relying on) just one thing across the board. It's efficient right up until that one thing has a bad day — and then everything depending on it goes down together.

Claude Code genuinely is excellent, and outages or performance dips do happen — sometimes for an hour, sometimes longer. When they do, teams that stored everything exclusively in Claude-specific formats (custom skills, uncommented code only Claude could interpret) found themselves suddenly far less productive, because other tools couldn't pick up where Claude left off.

Diversify Your "Crops"

Keep most of your work (7-9 out of 10) on the best model, but spread the rest across a backup or two.

Three practical ways to diversify

  • A multi-agent desktop tool like Conductor, which runs Claude Code and Codex side by side in isolated workspaces so you can shift work to whichever is performing well right now.
  • An MCP server that connects to another model (like a Codex MCP server), letting you ask a different model for a second opinion without leaving Claude Code — useful when Claude itself is up but a specific model is degraded.
  • A fully separate backup tool, like the Codex desktop app, with a synced copy of your workspace and system prompt ready to go the moment Claude has a widespread outage.

💡 New word: MCP

MCP (Model Context Protocol) is a standard way for AI tools to connect to outside services and to each other — like a universal adapter that lets Claude talk to a calendar app, a database, or even a different AI model.

A reasonable real-world split looks something like 70% of your work on the strongest model available, with the remaining 30% spread across one or two alternatives — enough diversification to stay productive during an outage, without giving up the edge that the best model provides.

Chapter Twelve

The Security Basics Almost Everyone Skips

Everything on the internet is hackable in theory — it's really a question of how much effort it takes. The goal isn't perfect security; it's making your setup less appealing to break into than the next easier target. A handful of quick fixes cover most of the realistic risk.

1. Conversations leak whatever you type into them

Every Claude Code conversation is saved as a plain-text log on your computer (in a hidden folder). If you ever paste an API key or password directly into the chat, it now lives permanently in that log too — in plain text, unencrypted. Keep secrets in a dedicated .env file instead, and tell Claude never to read or print that file's contents.

💡 New word: API key

An API key is like a password that lets a program (rather than a person) access a service on your behalf. If someone else gets your API key, they can use that service under your name and your bill.

2. AI models sometimes invent package names

When installing code dependencies, AI models occasionally get a package name slightly wrong — an extra letter, a missing one. Malicious actors know this and register those misspelled package names on purpose, packing them with malware that hunts through your files for saved credentials. Always have Claude double-check that a dependency list only contains packages you actually recognize and use.

3. Turn on Row Level Security for any database

💡 New word: RLS (Row Level Security)

Without RLS turned on, anyone with a basic access key to your database can potentially read, edit, or delete every row — not just their own data. It's a single setting in most database platforms (like Supabase), and it isn't turned on by default. A real example from this space: a poorly secured database let one researcher read every user's data in seconds, and — because write access was also open — create 100,000 fake profiles just as fast.

4. Be careful what you expose publicly

Any AI agent connected to a public web address will be constantly probed by automated bots scanning for weaknesses — this happens to essentially everyone, all the time, regardless of how interesting the target seems. Don't give a publicly exposed agent access to sensitive personal documents, ID numbers, or unlimited-spend API keys.

5. Never let an AI agent touch raw credit card numbers

If a card number is ever read by an AI agent, it risks ending up logged in that same plain-text conversation history described above. Use a payment processor like Stripe, which is built and certified to handle that compliance burden for you, instead of ever storing or reading card data yourself.

📌 Run a security audit before anything goes public

The simplest habit: before launching anything public-facing, start a brand-new conversation (so it isn't biased by the same context that built the project) and ask Claude to run through a security checklist covering exposed keys, dependency risks, database access rules, and public exposure. Fix what it finds, ideally with a different, fresh agent implementing the fixes.

Where This Is All Heading

Less driving, more directing.

The trend across every chapter here points the same direction: less time spent typing instructions step by step, more time spent setting a goal and letting a well-organized system of agents run with it — while a handful of low-effort habits (a good CLAUDE.md, a diversified toolkit, basic security hygiene) keep that system safe, fast, and reliable. The people getting the most out of this right now aren't necessarily the most technical — they're the ones who took the time to build good habits around the tools everyone already has access to.
