Before you load test, understand what you're actually testing on.

You've watched teammates run load tests against services in ECS, tweaking config like ecs_task_cpu: 2048 and ecs_task_memory: 8192. Before those numbers mean anything, you need to know what a CPU, a core, a vCPU, and memory actually are — and why "CPU memory" isn't a real thing.

task-definition.json
"ecs_task_cpu": 2048 → 2 full vCPUs reserved for this task
"ecs_task_memory": 8192 → 8,192 MiB (8 GB) of RAM — a ceiling while running, not disk space
01 — THE PHYSICAL LAYER

What a CPU and a core actually are

Think of the CPU as a small factory, and each core as an independent production line inside it.

A CPU (Central Processing Unit) is the physical chip that executes instructions — every calculation, every comparison, every "if this, do that" in your code eventually becomes a stream of instructions the CPU runs.

Early CPUs had exactly one production line: one core, running one instruction stream at a time. Modern CPUs pack many cores onto a single chip — 4, 8, 16, sometimes 64+. Each core can independently execute its own stream of instructions at the same time as the others. That's real, physical parallelism.

Worth knowing Many CPUs also use hyperthreading (SMT), where one physical core presents itself to the operating system as two logical threads. It's not two full cores' worth of power — it's one core getting slightly better at overlapping work while it waits on things like memory access. This is why cloud providers talk in vCPUs, not "cores."
02 — THE CLOUD ABSTRACTION

What is a vCPU, really?

Cloud providers don't hand you a physical core. They hand you a vCPU — a virtual unit that represents your share of compute time on the underlying physical hardware.

That's the key mental shift: a vCPU is not a fixed amount of "power." It's a promise about how much of the CPU timeline is reserved for you, not a guarantee of clock speed or instructions-per-second — those depend on whatever generation of physical hardware AWS happens to run your task on.

How is this different on Fargate vs. EC2?

On an EC2 instance, multiple containers can share the same physical cores, competing for cycles via CPU shares. On Fargate — the launch type most teams use for ECS today — the vCPU you request is isolated compute reserved for your task specifically. It's still virtualized, but you're not fighting a noisy neighbor for it.

Myth "1 vCPU always equals a fixed, comparable amount of processing power everywhere."
Reality 1 vCPU guarantees you a slice of time on a core. The actual throughput you get from that slice depends on the physical CPU generation underneath — which is exactly why relative benchmarking (covered below) matters more than any published spec sheet.
03 — ECS'S OWN CURRENCY

Decoding "CPU Units" — what 2048 means

ECS doesn't let you write cpu: 2. It uses its own unit, and once you know the exchange rate, the config reads itself.

In ECS and Fargate task definitions, CPU is expressed in CPU units, where:

Exchange rate 1024 CPU units = 1 full vCPU

This traces back to Docker's underlying --cpu-shares mechanism, a relative-weight system from Linux cgroups where 1024 was chosen as the baseline "one share" value. ECS kept that number and built a clean vCPU scale on top of it.

04 — WORKING MEMORY, NOT STORAGE

What "memory: 8192" is telling you

This is the one that trips almost everyone up — including the "is this storage?" question you asked. It isn't.

Memory in ECS is RAM — the fast, temporary workspace your application uses while it's running. It holds things like variables, loaded objects, request buffers, caches, and your app's heap. It is emptied every time the task restarts.

ecs_task_memory: 8192 means 8,192 MiB (≈8 GB) is the ceiling your task's containers are allowed to use during execution. It has nothing to do with how much code or how many files you can "load onto" the vCPU — that's a completely different resource (ephemeral disk storage), configured separately and rarely the bottleneck people mean when they say "memory."

Myth "CPU memory" is a separate resource from regular memory, and 2048 vs 8192 are two flavors of the same thing.
Reality There is no such thing as "CPU memory" in this context. You are allocating two independent resources: compute (CPU units → vCPU) and working memory (MiB → RAM). They just happen to sit next to each other in the same config file.

What happens if your app tries to exceed 8192 MiB? The Linux kernel's OOM (out-of-memory) killer terminates the container, and ECS reports the task as stopped — not "disk full," not "CPU exhausted." A memory ceiling breach and a CPU bottleneck look completely different in your metrics, which is exactly why load testing needs to watch both separately.

05 — WHY THESE TWO NUMBERS ARE PAIRED

Fargate doesn't let you pick CPU and memory freely

For every CPU value, Fargate only accepts memory values within a fixed range. Your team's 2048 / 8192 pairing sits comfortably inside the valid range for 2 vCPU — nowhere near the edges, which is a reasonably balanced, general-purpose ratio.

06 — GIVE YOURSELF SOMETHING RELATIVE

How strong is "1 vCPU," concretely?

This is the right instinct — a raw number like "1 vCPU" is meaningless without a reference point. AWS doesn't publish a fixed clock speed for it on purpose, because the underlying hardware generation changes over time. So don't look for a universal constant. Build your own reference instead.

A rough intuition to start with

Treat 1 modern vCPU (post-2020 cloud hardware) ≈ one core of a decent modern laptop running flat out. Good enough to reason about orders of magnitude, not good enough to size production capacity.

The reliable way: benchmark it yourself

A 10-minute relative benchmark

1
Deploy the same service twice — once at cpu: 1024 (1 vCPU) and once at cpu: 2048 (2 vCPU), same memory ratio.
2
Hit each with an identical, CPU-bound load test (e.g. via k6 or wrk) — same endpoint, same payload, ramping RPS.
3
Record the RPS each configuration sustains before latency or error rate spikes.
4
Now you have a number that means something: "1 vCPU on our stack ≈ X sustained RPS for this endpoint." That's your real unit of measurement — specific to your code, not a generic spec sheet.
07 — THE PART THAT ACTUALLY USES THE CPU

What is a "worker"?

Cores execute. Workers are what your application gives the cores to execute.

A worker is a process or thread your application spins up to handle requests. When a request arrives, it's picked up by an available worker — not directly by "the CPU." The number and type of workers determines how much of your allocated vCPU actually gets used.

Sync worker
Handles exactly one request at a time and blocks while waiting on I/O (database calls, external APIs). Examples: Gunicorn's sync workers, Puma's default mode.
Async / event-loop worker
Juggles thousands of in-flight requests on a single thread by never blocking on I/O wait. Examples: Node.js, Python asyncio, Netty.
A common starting rule of thumb (sync workers) workers = (2 × cores) + 1
Why more workers than cores can still help If your workload is I/O-bound (waiting on a database, another service, disk), a worker that's blocked on I/O isn't using CPU — so extra workers let the core stay busy serving someone else while others wait. If your workload is CPU-bound (heavy computation, no waiting), piling on workers beyond your core count just adds context-switching overhead with no throughput gain.
08 — THE NUMBERS LOAD TESTS ACTUALLY REPORT

Throughput vs. RPS

RPS
Requests Per Second — a rate. A snapshot of how fast requests are arriving or completing at a given moment.
Throughput
The RPS your system can actually sustain without a growing backlog — the real, steady-state ceiling of what it can push through.

During a load test, watch for two different curves: the offered load (the RPS your test tool is firing) and the achieved throughput (the RPS actually completing successfully). They track together — until your system saturates. Past that point, offered load keeps climbing while achieved throughput flattens or drops, and latency starts creeping up. That divergence is your system telling you where its ceiling is.

09 — CONNECTING THE DOTS

Little's Law: tying CPU, workers, and RPS together

One formula quietly governs almost every capacity question in load testing:

Little's Law Concurrency = Throughput × Avg. Response Time

Concurrency here means "requests in flight at any instant" — which is exactly what your worker pool has to be sized to handle.

Worked example

1
Target: 500 RPS, average response time: 200 ms (0.2s).
2
Concurrency needed = 500 × 0.2 = 100 concurrent in-flight requests at any instant.
3
Your worker pool (across all vCPUs) needs to comfortably handle ~100 simultaneous requests — this is the number that should drive your worker count and, from there, how many vCPUs you actually need.

This is a planning estimate, not a guarantee — real systems have variance, tail latency, and non-uniform load. Use it to set a starting point for your load test, then verify with real numbers.
