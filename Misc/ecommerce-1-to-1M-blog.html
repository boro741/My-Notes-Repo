FROM 1 TO 1 MILLION USERS

Follow one T-shirt shop as it grows from 100 sales a day to a 70-engineer company. Every problem it hits teaches one big idea in system design.

We solve problems one at a time. Each time the business hurts, we add the simplest fix that works, then move on. That is all system design is.

The story so far

A friend sells T-shirts on social media. They want to sell online. You are the engineer they call. Let's go!

Three questions to judge every design

The instructor uses the same three yardsticks again and again. Keep them in your pocket.

1. Simplicity

Can people understand it and change it easily?

2. Fidelity

Does it really do what the business asked for?

3. Cost

Can we afford to build it and run it?

Golden rule

Solve the business problem, not the technical one. If a tool already solves it, use the tool.

Hosting: Server or Serverless?

Where does your code run? At the start, pick serverless. It is the easiest. Switch later when the bill or the traffic grows.

Why not a laptop at home?

A spare laptop can answer requests. But hardware breaks, power goes out, and you might be locked out of the house. A cloud company can replace a broken machine in minutes. A hobby site can live with downtime. A real business cannot.

Two cloud choices

Managed server

The cloud company looks after the machine and the operating system. You deploy the code and restart it if it crashes.

Serverless

You only write code and hand it to AWS. You do not even know if a server exists. You just need answers fast enough.

Cost vs. spikes

The lecture gives a simple example: 10,000 requests might cost about $10 on serverless and about $5 on a managed machine. Serverless is also slower to react. It adds capacity only after requests arrive, so early customers may wait. With a managed fleet you can book extra machines before a big sale, such as Diwali or New Year.

But serverless has a great side: after the sale you stop paying for the extra capacity. At low volume it is cheaper, and you do almost no work.

CDN, DNS & Database

Put pages and images on a CDN so they load from a nearby server. Keep changing data (like stock) on your own server. DNS turns a name into an address.

Web pages are just files

A page is HTML, CSS and JavaScript files. They have to live somewhere. You could serve them from your server. Better: store them in S3 and let a CDN copy them to many places around the world.

Jargon Buster
CDN
A network of servers spread across the world. You connect to the nearest one. Examples: CloudFront, Akamai, Cloudflare.
S3
Amazon's storage for files. The CDN watches it and copies new files out.
Edge
One CDN server close to users.

Never cache things that change

Static things go on the CDN: banners, images, product descriptions, videos. Changing things stay on your server and database, which is the single source of truth.

Logs, Monitoring & Single Points of Failure

When something breaks you must be able to find out why fast (logs), notice it early (dashboards), and make sure no single part can bring everything down.

The problem

Many orders failed at payment this week! Is the payment company broken?

The payment gateway promises about 98 percent success. Your numbers show 2 percent failures. So the gateway is fine. The real problem: your team cannot find the cause quickly.

Trace one request from start to finish

Give every request an ID. Write a log line when it arrives, before each risky step (a database write, a call to another system), and when you answer. Then support can search by order ID.

Press "Next step".
Support workflow
  1. Customer gives their email.
  2. Look up the order ID in the database.
  3. Search the logs for that order ID (a pattern search works).
  4. Read the story of that request and find the failing step.

The first tool to suggest is Amazon CloudWatch. It keeps all logs in one place and lets you search them. GCP and Azure have similar tools.

Observability: see how healthy you are

The founder expects about 100 sales a day. If sales fall to 10, you must know quickly. Build a dashboard of sales, visits and registrations so a person can spot a strange drop. (Automatic anomaly alerts come in a later chapter.) For a startup, Google Analytics is free and usually enough. Power BI and Tableau are paid options.

Single points of failure (SPOF)

A SPOF is a part which, if it fails, breaks everything. Ask of each box and each wire: "If this vanishes, what happens?" Click the boxes below.

Click a box. Red means broken.

Failover in action

PayPal is handling payments.
  • Keep a backup database.
  • Use managed services from one provider. Reliability is their job.
  • Offer more than one payment provider (Stripe, Razorpay, PhonePe).
  • Show a friendly banner when a dependency fails: "We cannot serve you right now. We will fix it soon." This is graceful degradation. Like a bridge that survives losing one support.
  • Pass along readable errors, such as "database failing, try later", so support can act on them.
Trade-off

More backups mean more work to build and maintain. Shopify itself is a real SPOF, but having several order takers is costly. Choose based on the business risk. Microservices are not worth it yet.

Scaling Servers & Load Balancing

When one big machine is not enough, use many small machines behind a load balancer. The balancer spreads requests and skips dead servers.

Step 1: The bill is too big

Serverless is costing about $1,000 a month. Can we cut it?

Credits are used up and the code is already tuned. So you move to a reserved instance: rent a server for a whole year at a discount. Serverless charges extra for managing servers for you. Now you start, stop and deploy. The bill drops to about $500.

The request path now: api.fancytshirts.io/purchase?id=... → DNS (Route 53) gives the server's IP → the server picks the /purchase function → the values after ? become the function's arguments. Deploying means: push to GitHub → pull on the server → restart. A restart wipes anything kept in memory.

Step 2: Vertical or horizontal?

Users report crashes. Memory really is high. The quick fix is a bigger machine: large, XL, XXL, 4XL. The founder is on a yacht asking for upgrades. That cannot go on.

Vertical scaling
  • Simple: one box.
  • Single point of failure.
  • Hard to reserve well: you outgrow it.
  • Idle at night (maybe 10% used), short at peaks.
  • Bigger machines cost more per unit of compute.
Horizontal scaling
  • Survives a failure.
  • More compute per dollar. 32 small machines with 2 virtual CPUs each handle 64 requests at once, but one huge machine for the same money handles about 32.
  • Load is spread.
  • Needs a load balancer.
  • More moving parts.
Practical advice

Nobody buys a supercomputer. Start going horizontal around a "large" instance. Use medium machines with weighted balancing, not one XXL.

Why use a load balancer?

  • High availability: no server is overworked, and spikes are absorbed.
  • Flexibility: add or remove servers any time.
  • Lower response time: servers are not choked.

On AWS this is the Elastic Load Balancer (ELB). It has built-in algorithms and lets you add your own. DNS can also balance: one name can hold several IPs (India and US), pick the nearest, and fall back to the other region on failure with higher delay.

The algorithms

Stateless algorithms need no memory (round robin). Stateful ones (least connections) remember what is happening, so they are smarter but costlier. The lecture also calls them static and dynamic.

Caching & Consistent Hashing

A cache keeps a copy of data close by so it loads fast. Consistent hashing lets you add or remove cache machines without reshuffling everything.

The problem

Your shop feels slow!

You check the CDN (CloudFront). Pages are fine. The browser's network tab shows the call that fetches the T-shirt list is slow. Images are not the problem.

Fix 1: prefetch in the browser

When someone lands on the homepage, quietly call the products API in the background and keep the answer in the browser. The browser is making a calculated guess: nobody buys a shirt in the next 10 to 15 seconds, so slightly old data is fine.

Press "Next step".

Fix 2: also cache on the server

Even if someone opens the products page directly, the server answers from a cache instead of the database. But where should that cache live?

Where to put the cache

In-memory (inside each server)
  • Microsecond fast: a function call.
  • Simple. Libraries exist everywhere.
  • A restart empties it.
  • Copies go stale.
  • The same data is stored N times.
Global cache (Redis or Memcached)
  • One copy of the data.
  • Scales on its own. Can be owned by another team.
  • Extra network hop that can fail.
  • More architecture.
STALE!

Three servers, one T-shirt

For this shop the decision is a global Redis cache. The product list is small, and ultra-low latency is not the main need.

Sharding: split the data

One cache machine may not fit everything. Sharding splits data by a property: by country (India shirts here, US shirts there), by ID range (users 1 to 100, 100 to 200), or most often by hashing: hash(tshirtId) % numberOfCaches. The same shirt always goes to the same cache. There is no duplication.

The catch

Change the number of caches (a machine dies, or you autoscale) and almost every key moves. Going from 3 to 4 caches, only about 1 in 4 keys stay. The rest must be loaded fresh from the database. Warming a big cache can take hours (the lecture cites Facebook's Memcached). The lecture's "1/12 stay" figure undercounts. Counting all remainders gives 3/12 = 1/4.

Consistent hashing: the ring

  1. Bend the hash number line (0 to 264) into a ring.
  2. Hash each server onto the ring.
  3. Hash each key onto the ring. Walk clockwise to the first server. That server owns the key.
  4. Add a server: it takes over only the arc just before it.
  5. Remove a server: its keys pass to the next server clockwise.

The rule never mentions how many servers there are. That is why little moves. Adding one server to N moves about 1/(N+1) of keys. Removing one moves about 1/N.

Virtual nodes: with few servers the arcs are uneven. Give each server many points on the ring (the notes use 20, a bigger system may use 200). Loads even out, and a dead server's keys spread over many neighbours instead of one.

THE RING

Modulo vs. ring: how many keys move?

40 keys (small dots) are owned by servers (big dots). Change the fleet and watch the "moved" counter.

Where it is used

DynamoDB uses it to cut data migration. Redis offers it as a way to spread data. One honest limit: virtual nodes even out how many keys each server holds, not how much traffic. One very hot key can still get 20% of requests.

Cache Writes & Eviction

A cache only helps if you use it right. Store light data, choose how writes flow, and decide what to throw out when it is full.

Redis costs $2,000 a month! That is too much for us.

That bill means the tool is being misused. You look at what is cached. Three kinds of queries: most popular shirts ever, recently added shirts, and each user's recently viewed shirts. Two problems appear:

  • The "popular shirts" query runs on the database, not the cache. The team feared the two might disagree.
  • The per-user cache holds heavy shirt objects (all the details) under the user ID.

Filling a cache from the database on every read and then reading it defeats the point. You might as well read the database.

Fix 1: cache light things

Store only shirt IDs per user, like [D, C, B, A] (newest first). Keep the shirt details once in a shared cache. Fetch IDs, fetch details, merge. B, C and D are no longer stored twice.

Heavy objects
IDs + shared

Example sizes: 10 shirts per user, 2 KB per full object, 200 shirts in the catalog. These sizes are made up to show the shape.

Fix 2: let data be a little old

Give entries a TTL (time to live). Popular shirts can be an hour or six hours old. A top-10 list that swaps places 10 and 11 hurts nobody. How stale is okay is a product decision, not a technical one. Ask the business.

Keeping the cache and database in step: write policies

Write-through
  1. Update the database.
  2. Update the cache.
  3. Reply.

Always fresh. More database load. Use for payments.

Write-back
  1. Update the cache only.
  2. Later, flush to the database (on expiry or eviction).

Few database writes, but a crash loses data. Fine for view counts.

COMPARE

Send the updates, then try the crash before flushing.

Look-aside vs read-through: with look-aside (Facebook's Memcached style) your code checks the cache and, if empty, queries the database itself. With read-through (Redis style) the cache fetches from the database for you. Look-aside gives more control but needs more code. A third pattern, write-around, is rarely used.

Eviction: who gets thrown out?

A million users means a million entries. Cache only active users (say the top 1,000 or top 10 percent). When it is full, a rule picks who leaves. LRU removes the least recently used. LFU removes the least frequently used. For activity on a social-style site the lecture prefers LRU: old heavy users from "last Christmas" should not outrank people who came today. With LFU a new entry starts at a count of 1 against hundreds, so it may never get in.

  1. Placement: browser, server memory, or a global cache.
  2. Distribution: how data is split (sharding, hash ring).
  3. Consistency: the write policy.

Traffic Spikes & Rate Limiting

When too much traffic arrives, you cannot serve everyone. Serve some people well instead of everyone badly. Limit, shed and protect.

The flash sale story

Let's run a 50% off sale for 2 hours!

You size it first. The founder has 20k social followers, 50k emails, 1M ad views, and about 2,000 sales a day. They guess 10x: 20,000 sales in the 2 hours. Making the system ready for 10x is a business choice: pre-scaling is costly but smooth, a smaller buffer is cheaper but gives a worse experience if you are wrong. Ask about profit margin and tolerance.

Your plan: scale up a day (or a few hours) before, cache the shirt list on the server and CDN, and load test. Sale day comes. About 1 million concurrent requests hit. Far past 10x. The system collapses. Queues grow, users refresh and retry, and support calls buyers by hand.

The post-mortem finds the same user IDs sending thousands of requests in seconds from many IPs. It looks like a (distributed) denial-of-service attack. A rival, a prankster, or an innocent test, nobody knows.

A week later the sale runs again with new defences. Result: 10,000 T-shirts sold. A success. Here are the defences.

Defence 1: look at each request type

The list of shirts on sale is the same for everyone and rarely changes. Cache it on the server and the CDN. The CDN can hold more than files: pages, data, even a list of shirt IDs. Payments, order status and support are per-user and critical, so they need other protection. Load test by raising load step by step to find one server's limit. (Example: 20,000 requests at about 100 ms means one server handles 20k, so 40k needs two.)

Defence 2: layers that fail gracefully

Press "Next step".
Jargon Buster
WAF
Web application firewall (Cloudflare, AWS WAF). It inspects requests and blocks bad ones. At the CDN it stops bots eating bandwidth. At the server side you can write rules on headers and parameters. It adds a little delay and cost.
Request priority
Payments, order status and support rank highest. "Show shirts I viewed" ranks lower. (WhatsApp on New Year's Eve: sending matters more than read receipts.)
Short circuit (client side)
If the cache or database is slow, stop calling it and fail fast. Calling it only makes the overload worse and would time out anyway. This is the circuit-breaker idea.
Back pressure (server side)
An overloaded service rejects new requests on arrival so it can finish the ones it has. The error should say "temporary, retry soon" so smart clients wait.
Graceful degradation
Show something useful when things fail: a retry message, popular items, or a "heavy load" notice.
Guiding rule

Making some customers happy is more useful than making all of them unhappy. If you can handle 100 and get 1,000, drop 900. You cannot add servers in milliseconds, and the other servers are probably overloaded too.

Defence 3: head-of-line blocking

With one first-come-first-served line, one slow request (a heavy database query) makes everyone behind it wait. Picture one luggage counter with one slow customer. Three fixes:

  • Parallelism: more lines (more machines or cores).
  • Concurrency: threads. A slow request steps aside while it waits on input/output, and fast requests go ahead.
  • Protocol: gRPC multiplexes streams so requests can finish out of order.
LUGGAGE

Five requests: one takes 10 time units, four take 1 each

Lower average finish time is better.

Defence 4: rate limiting

Rate limiting keeps the work being processed at the maximum level, even when load goes above it.

Token bucket

A counter (say 1,000 tokens). Each request takes one. At 0, the next request waits or is rejected. When a request finishes, its token returns. If each takes about 100 ms, at most 1,000 run at once. You always know the maximum in flight.

Leaky bucket

One request is let through every fixed interval (say every 100 ms), like a steady drip. The outflow is perfectly smooth. But 1,000 queued requests take 100 seconds, so many time out, and it wastes capacity if you could do more.

BUCKETS

Throw 8 requests at both

Token bucket: 3 tokens, each request holds one for 2.5 seconds. Leaky bucket: one request let through every second.

Waiting: 0 · Done: 0

Leaky bucket

Queued: 0 · Done: 0

Local or central limiter?

Local: each server decides alone. It is fast and simple, and "99% of the time I have seen", it is what is used. Central: one limiter keeps a global counter and every server asks it first. Accurate, but it adds a hop and needs coordination.

Microservices & API Contracts

When too many people share one codebase, split the teams first, then the code. Let services talk through versioned contracts so changes fail at build time, not in production.

The pain

The company is doing well. Hire up! (From 5 engineers to 15 in two months. The business also wants accessories and T-shirt subscriptions.)
  • Stand-ups are long and full of updates that do not overlap.
  • Development is slower. Deploys are rare.
  • New hires need heavy hand-holding. Reading all the code takes forever.
  • Nobody owns payments: 15 commits from 15 people. You "right-click, git blame" to find someone.

The lecture calls this coupling and a lack of isolation of concerns. "Everybody manages everything, so nobody is an expert at anything." Code mirrors the shape of the organization. So split the teams, then split the code.

Wins
  • Short stand-ups
  • Each feature goes to one team
  • Independent deploys
  • Independent scaling
  • Own tech choices
Costs
  • Teams lose shared context
  • Common work done twice (logging, caching)
  • Network calls are slower
Guardrails
  • One language and one database type org-wide
  • Engineers do DevOps at 15 people. At 50 to 100, a platform team.

The lecture's honest summary: you trade code efficiency for organization efficiency.

Where does a new feature go?

Reviews do not fit inventory, payments or communications. Do not rush to build a new service. Young tech leads often create nanoservices: more projects than people, or one person owning two services. Use this path:

Talking across teams is expensive. Decisions need writing down (diagrams, emails). Count how often two services talk. A very heavy link suggests they should be one.

API contracts

An API contract is a public description of a function: its name, inputs, outputs and error codes. It says what it does, not how. Keep all contracts in one repository so everyone can check they use the latest. Without this, a changed API is not a compile error. You find out after deploy.

Each service publishes a client library with a version number. When the contract changes, consumers upgrade and the build tells them what broke.

Order contract v1.2
createOrder(tshirtId, qty)
Order contract v1.3
createOrder(itemId, itemType, qty)
All consumers are on v1.2 and happy.
Backward compatible change

Add a default: if itemType == null, assume T-shirt. Old clients keep working and move over slowly. New clients use the new fields.

Analytics & Data Pipelines

Do not let business people query the live database. Stream a copy of every team's data into one store that anyone can query, so production stays fast.

The pain

You are the CTO of 50 to 70 engineers in 10 to 12 teams. The managers are upset with each other.

You call a board meeting and gather feedback. The business pain points:

  1. Engineers are slow to run data queries. Insights come late, and chances are lost.
  2. Cross-team questions need coordination. Example: "people who buy a shirt at least 3 days after signing up". Sign-up is in the profile team's data, the order in the orders team's, and receipt in the delivery team's. Someone then merges it all in Excel.
  3. Product managers want to slice and dice data and download CSV files regularly.
  4. The operations chief wants daily dashboards (sales, sign-ups, pending and done deliveries) without asking engineers or getting database passwords.

The core diagnosis: business teams are tightly coupled to tech teams for data, in time and in knowing whom to ask.

The design: two worlds

Each of the 12 teams has its own production Postgres database. Collect all of them into one large copy. Business users query and chart the copy. Heavy analytics queries no longer lock or slow the live databases. The system splits into two halves: the live serving system, and the collected data store people can query any time. (Data people call these OLTP and OLAP. The lecturer does not use those words.)

Dashboards and custom queries

Dashboards need UI engineers plus server engineers who expose APIs that run the common queries on the copy. Daily sales count and total:

SQL
SELECT date, COUNT(*) AS orders, SUM(amount) AS total
FROM payments
GROUP BY date;

For custom questions, give a SQL interface with documented tables. Product teams can hire an analyst, learn SQL, or ask an AI assistant. "You are enabling many teams instead of just solving that problem."

Which tools? A fair debate

The AWS option: Kinesis streams the data and Athena queries it. Kinesis is very cheap, and Athena charges for the data scanned, not for storage. The product team counters with open source: easier hiring and training, and no vendor lock-in (moving from AWS to GCP could hurt). The CTO accepts. It is a bit more complex, but the ops and product teams carry that complexity.

What to remember

  • Judge every design by simplicity, fidelity and cost.
  • Reuse tools. Add custom code only where needed.
  • Estimate with numbers and state your assumptions.
  • Find single points of failure. Degrade gracefully.
  • Scale out. Cache light data. Choose write and eviction rules on purpose.
  • Under overload, protect the important requests. Shed the rest.
  • Split teams before code. Version every contract.
  • Keep analytics on a separate copy of the data.
