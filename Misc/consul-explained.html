A beginner's field guide

Why do hundreds of services need a departure board?

You don't need to know Spring Boot or microservices deeply to get this. We're starting from zero, and we're going to get there using something you already understand: a busy Indian railway station.

Start here

First, forget Consul for a minute

Before we talk about what Consul does, we need to talk about the mess it exists to clean up. And that mess starts with a simple shift in how applications get built: from one big application, to many small ones.

Imagine one giant railway office that handles ticket booking, catering, security, cleaning, and announcements — all under one roof, run by one team, deployed as one unit. That's a monolith. If the catering counter has a bug, the whole office might need to shut down to fix it. Simple to run when small, painful to change as it grows.

Now imagine instead: a separate Booking office, a separate Catering office, a separate Security office, each independently built, deployed, and scaled by its own team. That's microservices. Each one is simple on its own. But now they all need to talk to each other constantly — and that's where the actual story of Consul begins.

Why this matters

Nobody adopts microservices for fun. They do it so different teams can move independently, deploy independently, and scale only the parts that need scaling (e.g. Payments during a sale, not the whole app). The cost of that freedom is coordination — and that cost is exactly what today's post is about.

The problem

"Where even is the Payments service right now?"

In the one-big-office world, everything is in one building. You just walk down the hallway. In the many-small-offices world, every office can:

  • move to a different location overnight (containers get rescheduled to a new server)
  • multiply during rush hour and shrink afterwards (auto-scaling)
  • temporarily go out of service without warning (crash, restart, deploy)

So if the Booking service hardcodes the address of the Payments service — say, 10.2.4.17:8080 — that address is only valid until the next restart. Multiply this by 50 services, each calling several others, and you get a tangle of hardcoded addresses that breaks constantly.

This is the exact problem that Indian Railways solved over a century ago, long before your services had the same problem. You don't need to know which physical track a train is sitting on. You look at the announcement board. The board is always current, because someone (or something) updates it the moment anything changes. Nobody wires their own private phone line to the train.

The fix

Service discovery: a self-updating directory

Service discovery is the general idea — not specific to Consul — of having a central directory where:

  1. Services register themselves when they start up ("Hi, I'm Payments, I'm at 10.2.4.91:8080")
  2. Something keeps checking they're actually alive (a health check, like a TTE walking the platform)
  3. Other services can ask the directory instead of hardcoding an address ("Where's Payments right now?")

The important bit

Notice nobody edited a config file to make that happen. That's the whole value of service discovery: the directory reflects reality, automatically, all the time. Any service can ask "who's healthy right now?" and get a trustworthy answer.

Where Consul fits

So what does Consul actually do?

Consul, from HashiCorp, is a tool that implements that self-updating directory — plus a few closely related jobs that naturally come up once you have one. Here's the honest breakdown:

PieceWhat it isRailway equivalent
CatalogThe registry of every service and where it's runningThe departure/arrival board
Health checksConstant pings to confirm a service is actually working, not just runningSignal lights + track inspectors
KV storeA shared key-value store any service can read config/flags fromThe shared master timetable in the control room
Consul ConnectIts service mesh feature (secures + observes traffic between services)The signalling & interlocking system — see next section

Under the hood, Consul runs as a small agent next to every service (like a local station master), and a cluster of server agents (a handful of nodes, using a consensus protocol called Raft) that hold the source of truth and stay in sync with each other. You don't need to memorize Raft — just know it's how Consul's servers agree on "what's true right now" even if one of them goes down.

Clearing up the confusion

This is usually where people get stuck, so let's be precise: "service mesh" is a general architectural pattern (like "microservices" is a pattern). Consul is a specific tool that can do service discovery on its own, and can also act as a service mesh if you turn on Connect. You could use Consul purely as a directory and skip the mesh entirely — plenty of teams do exactly that.

The other half

Okay but why does "service mesh" need to exist at all?

Knowing where a service is solves discovery. But once Booking finds Payments and calls it directly, a new pile of problems shows up — and these have nothing to do with addresses:

  • Security — is this really Payments I'm talking to, and is the connection encrypted?
  • Permissions — should Booking even be allowed to call Payments directly?
  • Resilience — if Payments is slow, should Booking retry? Back off? Give up gracefully?
  • Observability — when something's slow, which of the 50 services is actually the culprit?

The naive answer is: every team builds this logic into their own service. In practice that means the same retry logic, the same TLS handling, the same logging, rewritten 50 times, slightly differently, by 50 teams. That's fragile and exhausting to maintain.

The service mesh idea

Instead, you attach a tiny helper proxy — called a sidecar — right next to every single service instance. All traffic in and out of a service passes through its sidecar. The sidecars handle encryption, identity checks, retries, and metrics uniformly, so individual services can stay simple and just talk to "localhost." The mesh is the sidecars plus the control plane (Consul) that configures them all consistently.

Every service gets its own sidecar (like an RPF ticket checker posted at every compartment door). Services never talk to each other directly — only sidecar to sidecar, always encrypted.

In railway terms: imagine every compartment door has its own ticket checker who verifies your ticket and silently logs the checkpoint and encrypts what's said between compartments — without the passengers having to do any of that themselves. That consistency, applied network-wide, is what "mesh" means. Consul's version of this is called Consul Connect, and it uses mutual TLS (mTLS) — both sides prove who they are, not just the caller.

🔒 mTLS: both sides show ID, every hop
Going deeper

"But couldn't I just use a URL and an ALB?"

Yes — and plenty of ECS setups do exactly that. If a task definition holds an env var like PAYMENTS_BASE_URL pointing at an ALB or a Cloud Map DNS record, you already have a working form of service discovery. So it's worth being precise about what changes when Consul enters the picture, instead of treating it as magic.

ConcernALB / Cloud Map + URLConsul (with Connect)
Finds the right instanceYes — DNS or target groupYes — the catalog
Extra network hop for east-west callsYes, through the load balancerNo — sidecar to sidecar, direct
Encrypts traffic between servicesOnly if you configure TLS yourself, per serviceAutomatic mTLS, every hop, by default
Proves identity, not just addressNo — anything that can reach the URL can call itYes — sidecars verify each other's certificate
"Who's allowed to call whom"Security groups (coarse, IP/port level)Intentions (per-service, e.g. "Search may not call Payments")
Health check depthOne HTTP check on an intervalMultiple checks per service, near-instant propagation
Shared config/flags across servicesUsually Parameter Store / env vars per taskBuilt-in KV store, watchable for live changes
Cost per internal callALB pricing + slightly higher latencyNo ALB in the path for internal traffic

None of this makes the ALB approach wrong — it's simpler to reason about and it's what you already have. Consul earns its keep once you specifically need encrypted, identity-checked, access-controlled traffic between your own services, without paying an ALB hop for every internal call.

Intentions: who's allowed to call whom

A security group says "anything on this port from this subnet may connect." An intention in Consul is far more specific — it operates on service identity, not IP ranges:

Example intention

allow: booking-svc → payments-svc
deny: search-svc → payments-svc

Even if search-svc and payments-svc sit on the same network and the same security group, the sidecar in front of Payments will refuse the connection from Search's sidecar — because Consul told it not to trust that identity. This is sometimes called zero-trust networking: nothing is trusted by default just because it's "inside the network."

The KV store, with an actual example

Consul's key-value store isn't just a place to dump settings — the useful part is that services can watch a key and react the moment it changes, without redeploying. A common real use: a feature flag or a rate limit.

Example

config/payments-svc/max-retries = 3
config/payments-svc/circuit-breaker-enabled = true

Flip circuit-breaker-enabled to false in the KV store during an incident, and every running instance of Payments picks it up within seconds — no redeploy, no restart. It plays a similar role to the shared master timetable in a railway control room: one source of truth every office reads from, updated once, seen everywhere instantly.

Agents, servers, and who's actually in charge

Two different things both get called "Consul" and it's worth separating them:

  • Client agents — a lightweight process running on (or beside) every node/task. It's the local "station master": it registers local services, runs their health checks, and forwards queries to the server cluster.
  • Server agents — a small cluster (typically 3 or 5 nodes) that holds the actual source of truth for the whole catalog. They use a consensus protocol called Raft to agree on "what's true right now," so the system keeps working correctly even if one server node goes down.

You never talk to the server cluster directly for everyday lookups — every service goes through its local client agent, which is why discovery stays fast even with hundreds of services asking questions constantly.

One more thing: multi-datacenter

Consul can federate multiple datacenters (or AWS regions) into one system, so a service in ap-south-1 can discover and securely call a service in us-east-1 using the same catalog and the same intentions. This is one of the harder things to replicate cleanly with ALB + Route53 alone, and it's a common reason larger, multi-region setups reach for Consul even if a single-region team wouldn't need it.

Recap

The mental model to keep

If you remember nothing else from this page, remember this chain:

01 — Microservices

Many small, independently deployed services instead of one big app. Great for teams, painful for coordination.

02 — The problem

Services move, scale, and restart constantly, so hardcoded addresses break. Nobody knows who's where.

03 — Service discovery

A self-updating directory: services register themselves, health checks keep it honest, others query it.

04 — Consul

A tool that runs that directory (catalog + health checks + KV store), backed by agents and a small server cluster.

05 — Service mesh

The pattern of attaching a sidecar proxy to every service to handle security, retries, and observability consistently.

06 — Consul Connect

Consul's own service mesh implementation — sidecars + automatic mTLS between every service, configured centrally.

One-line answer to your original question

Consul solves "how do dozens of constantly-moving services find each other safely" — first by being the directory (service discovery), and optionally by also being the security and traffic layer between them (service mesh, via Connect). Everything else it does supports one of those two jobs.
