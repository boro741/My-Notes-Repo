A beginner's field guide

Why do hundreds of services need a departure board?

You don't need to know Spring Boot or microservices deeply to get this. We're starting from zero, and we're going to get there using something you already understand: a busy Indian railway station.

Start here

First, forget Consul for a minute

Before we talk about what Consul does, we need to talk about the mess it exists to clean up. And that mess starts with a simple shift in how applications get built: from one big application, to many small ones.

Imagine one giant railway office that handles ticket booking, catering, security, cleaning, and announcements — all under one roof, run by one team, deployed as one unit. That's a monolith. If the catering counter has a bug, the whole office might need to shut down to fix it. Simple to run when small, painful to change as it grows.

Now imagine instead: a separate Booking office, a separate Catering office, a separate Security office, each independently built, deployed, and scaled by its own team. That's microservices. Each one is simple on its own. But now they all need to talk to each other constantly — and that's where the actual story of Consul begins.

Why this matters

Nobody adopts microservices for fun. They do it so different teams can move independently, deploy independently, and scale only the parts that need scaling (e.g. Payments during a sale, not the whole app). The cost of that freedom is coordination — and that cost is exactly what today's post is about.

The problem

"Where even is the Payments service right now?"

In the one-big-office world, everything is in one building. You just walk down the hallway. In the many-small-offices world, every office can:

  • move to a different location overnight (containers get rescheduled to a new server)
  • multiply during rush hour and shrink afterwards (auto-scaling)
  • temporarily go out of service without warning (crash, restart, deploy)

So if the Booking service hardcodes the address of the Payments service — say, 10.2.4.17:8080 — that address is only valid until the next restart. Multiply this by 50 services, each calling several others, and you get a tangle of hardcoded addresses that breaks constantly.

This is the exact problem that Indian Railways solved over a century ago, long before your services had the same problem. You don't need to know which physical track a train is sitting on. You look at the announcement board. The board is always current, because someone (or something) updates it the moment anything changes. Nobody wires their own private phone line to the train.

The fix

Service discovery: a self-updating directory

Service discovery is the general idea — not specific to Consul — of having a central directory where:

  1. Services register themselves when they start up ("Hi, I'm Payments, I'm at 10.2.4.91:8080")
  2. Something keeps checking they're actually alive (a health check, like a TTE walking the platform)
  3. Other services can ask the directory instead of hardcoding an address ("Where's Payments right now?")

The important bit

Notice nobody edited a config file to make that happen. That's the whole value of service discovery: the directory reflects reality, automatically, all the time. Any service can ask "who's healthy right now?" and get a trustworthy answer.

Where Consul fits

So what does Consul actually do?

Consul, from HashiCorp, is a tool that implements that self-updating directory — plus a few closely related jobs that naturally come up once you have one. Here's the honest breakdown:

PieceWhat it isRailway equivalent
CatalogThe registry of every service and where it's runningThe departure/arrival board
Health checksConstant pings to confirm a service is actually working, not just runningSignal lights + track inspectors
KV storeA shared key-value store any service can read config/flags fromThe shared master timetable in the control room
Consul ConnectIts service mesh feature (secures + observes traffic between services)The signalling & interlocking system — see next section

Under the hood, Consul runs as a small agent next to every service (like a local station master), and a cluster of server agents (a handful of nodes, using a consensus protocol called Raft) that hold the source of truth and stay in sync with each other. You don't need to memorize Raft — just know it's how Consul's servers agree on "what's true right now" even if one of them goes down.

Clearing up the confusion

This is usually where people get stuck, so let's be precise: "service mesh" is a general architectural pattern (like "microservices" is a pattern). Consul is a specific tool that can do service discovery on its own, and can also act as a service mesh if you turn on Connect. You could use Consul purely as a directory and skip the mesh entirely — plenty of teams do exactly that.

The other half

Okay but why does "service mesh" need to exist at all?

Knowing where a service is solves discovery. But once Booking finds Payments and calls it directly, a new pile of problems shows up — and these have nothing to do with addresses:

  • Security — is this really Payments I'm talking to, and is the connection encrypted?
  • Permissions — should Booking even be allowed to call Payments directly?
  • Resilience — if Payments is slow, should Booking retry? Back off? Give up gracefully?
  • Observability — when something's slow, which of the 50 services is actually the culprit?

The naive answer is: every team builds this logic into their own service. In practice that means the same retry logic, the same TLS handling, the same logging, rewritten 50 times, slightly differently, by 50 teams. That's fragile and exhausting to maintain.

The service mesh idea

Instead, you attach a tiny helper proxy — called a sidecar — right next to every single service instance. All traffic in and out of a service passes through its sidecar. The sidecars handle encryption, identity checks, retries, and metrics uniformly, so individual services can stay simple and just talk to "localhost." The mesh is the sidecars plus the control plane (Consul) that configures them all consistently.

Every service gets its own sidecar (like an RPF ticket checker posted at every compartment door). Services never talk to each other directly — only sidecar to sidecar, always encrypted.

In railway terms: imagine every compartment door has its own ticket checker who verifies your ticket and silently logs the checkpoint and encrypts what's said between compartments — without the passengers having to do any of that themselves. That consistency, applied network-wide, is what "mesh" means. Consul's version of this is called Consul Connect, and it uses mutual TLS (mTLS) — both sides prove who they are, not just the caller.

🔒 mTLS: both sides show ID, every hop
Going deeper

"But couldn't I just use a URL and an ALB?"

Yes — and plenty of ECS setups do exactly that. If a task definition holds an env var like PAYMENTS_BASE_URL pointing at an ALB or a Cloud Map DNS record, you already have a working form of service discovery. So it's worth being precise about what changes when Consul enters the picture, instead of treating it as magic.

ConcernALB / Cloud Map + URLConsul (with Connect)
Finds the right instanceYes — DNS or target groupYes — the catalog
Extra network hop for east-west callsYes, through the load balancerNo — sidecar to sidecar, direct
Encrypts traffic between servicesOnly if you configure TLS yourself, per serviceAutomatic mTLS, every hop, by default
Proves identity, not just addressNo — anything that can reach the URL can call itYes — sidecars verify each other's certificate
"Who's allowed to call whom"Security groups (coarse, IP/port level)Intentions (per-service, e.g. "Search may not call Payments")
Health check depthOne HTTP check on an intervalMultiple checks per service, near-instant propagation
Shared config/flags across servicesUsually Parameter Store / env vars per taskBuilt-in KV store, watchable for live changes
Cost per internal callALB pricing + slightly higher latencyNo ALB in the path for internal traffic

None of this makes the ALB approach wrong — it's simpler to reason about and it's what you already have. Consul earns its keep once you specifically need encrypted, identity-checked, access-controlled traffic between your own services, without paying an ALB hop for every internal call.

Intentions: who's allowed to call whom

A security group says "anything on this port from this subnet may connect." An intention in Consul is far more specific — it operates on service identity, not IP ranges:

Example intention

allow: booking-svc → payments-svc
deny: search-svc → payments-svc

Even if search-svc and payments-svc sit on the same network and the same security group, the sidecar in front of Payments will refuse the connection from Search's sidecar — because Consul told it not to trust that identity. This is sometimes called zero-trust networking: nothing is trusted by default just because it's "inside the network."

The KV store, with an actual example

Consul's key-value store isn't just a place to dump settings — the useful part is that services can watch a key and react the moment it changes, without redeploying. A common real use: a feature flag or a rate limit.

Example

config/payments-svc/max-retries = 3
config/payments-svc/circuit-breaker-enabled = true

Flip circuit-breaker-enabled to false in the KV store during an incident, and every running instance of Payments picks it up within seconds — no redeploy, no restart. It plays a similar role to the shared master timetable in a railway control room: one source of truth every office reads from, updated once, seen everywhere instantly.

Agents, servers, and who's actually in charge

Two different things both get called "Consul" and it's worth separating them:

  • Client agents — a lightweight process running on (or beside) every node/task. It's the local "station master": it registers local services, runs their health checks, and forwards queries to the server cluster.
  • Server agents — a small cluster (typically 3 or 5 nodes) that holds the actual source of truth for the whole catalog. They use a consensus protocol called Raft to agree on "what's true right now," so the system keeps working correctly even if one server node goes down.

You never talk to the server cluster directly for everyday lookups — every service goes through its local client agent, which is why discovery stays fast even with hundreds of services asking questions constantly.

One more thing: multi-datacenter

Consul can federate multiple datacenters (or AWS regions) into one system, so a service in ap-south-1 can discover and securely call a service in us-east-1 using the same catalog and the same intentions. This is one of the harder things to replicate cleanly with ALB + Route53 alone, and it's a common reason larger, multi-region setups reach for Consul even if a single-region team wouldn't need it.

Recap

The mental model to keep

If you remember nothing else from this page, remember this chain:

01 — Microservices

Many small, independently deployed services instead of one big app. Great for teams, painful for coordination.

02 — The problem

Services move, scale, and restart constantly, so hardcoded addresses break. Nobody knows who's where.

03 — Service discovery

A self-updating directory: services register themselves, health checks keep it honest, others query it.

04 — Consul

A tool that runs that directory (catalog + health checks + KV store), backed by agents and a small server cluster.

05 — Service mesh

The pattern of attaching a sidecar proxy to every service to handle security, retries, and observability consistently.

06 — Consul Connect

Consul's own service mesh implementation — sidecars + automatic mTLS between every service, configured centrally.

One-line answer to your original question

Consul solves "how do dozens of constantly-moving services find each other safely" — first by being the directory (service discovery), and optionally by also being the security and traffic layer between them (service mesh, via Connect). Everything else it does supports one of those two jobs.

Field notes · from a hands-on walkthrough

A city of apartments, and a real failover across two clouds

Everything above is the mental model. This part is a second pass at the same ideas through a different analogy, plus a walkthrough of an actual demo: two Kubernetes clusters, on two different cloud providers, connected by Consul, with one service failing over to the other live.

A different lens on the same idea

The city, the apartments, and everyone's personal assistant

Picture a city full of apartment buildings. Each building is a machine in your cluster. Each apartment is a pod. Each resident living in an apartment is a container — your actual microservice. Residents need to send messages to each other constantly: "update the stock count," "verify this user," "process this payment." Before any of this gets automated, every resident keeps their own personal address book of who lives where.

That's life without a mesh. It works, but it's fragile in exactly the ways we already covered: addresses go stale the moment someone moves apartments (a pod reschedules), and every resident is personally responsible for a pile of side-jobs that have nothing to do with their actual work — reporting their activity to the city's monitoring office, retrying messages that don't get a reply, handling the case where the recipient has gone quiet. Multiply that by dozens of residents, all doing this slightly differently, and the city's central monitoring office ends up with inconsistent, incomplete reports that don't stitch together cleanly.

Then the city hires a personal assistant for every resident

This is the sidecar. Each assistant tells their resident: "Just write the name of who you want to reach on the envelope. I'll figure out the address, deliver it, and bring back the reply. You focus on your actual job." The resident never learns another apartment's address. They just hand off mail with a name on it.

In Consul, that assistant is a small Envoy proxy container that gets automatically injected into the same pod as your service — which is why, once Consul is running, you'll notice each pod shows 2/2 containers instead of 1/1: your service, plus its assistant.

What the assistants actually share

A shared address book, encrypted mail, and a stamp nobody can forge

The interesting part isn't that each resident gets an assistant — it's that all the assistants work for the same company and share resources. Three things get shared across every assistant in the city:

  1. A shared, always-current address book. The moment a new pod shows up, its assistant announces itself to the network: "I'm here, this is who I'm assisting, this is how to reach me." Every other assistant can now route mail to it. When a resident moves out or falls sick (fails a health check), the book updates the same way — automatically, without anyone editing a file.
  2. Encryption, without the resident knowing it's happening. Every assistant carries a TLS certificate. Before mail leaves the building, the assistant seals it — encrypts it. It travels across the city unreadable to anyone who intercepts it. Only the receiving resident's assistant, holding the matching key, can open it and hand the plain message to its resident. The resident never touches encryption logic; they just write and receive plain messages, same as always.
  3. A stamp that proves who really sent it. This is the part worth sitting with: because every assistant's certificate is unique to the service it represents, that certificate doubles as an ID card. When mail arrives sealed with a specific certificate, the receiving assistant can check with the shared registry — "is this really who they claim to be, and is the stamp genuine?" That verified identity is what lets Consul enforce rules like only checkout-service may write to payment-service. This is called an intention, and it's enforced at the assistant level, before the message ever reaches your actual code.
Why this matters more than it sounds

Without a mesh, restricting "who can call the payment service" means a security group — coarse, IP-and-port based, and blind to identity. Two services in the same subnet look identical to a security group. To an assistant checking a certificate, they don't. This is what people mean by zero-trust or micro-segmentation: nothing is trusted just because it's inside the network perimeter — every single hop re-proves who's talking.

And because every assistant in the city is running the exact same software — Envoy — they all report their activity in the exact same format. That solves the "inconsistent handwriting" problem from before: metrics from fifty different services land in Prometheus or Grafana already speaking the same language, without any of the fifty teams writing a line of monitoring code themselves.

Who runs the assistants

Data plane vs. control plane

All those assistants, exchanging mail and checking stamps with each other — that network of activity is called the data plane. But someone has to hire the assistants, hand them their certificates, and keep the shared address book up to date in the first place. That's a separate office in the city: the control plane. In Consul, this is the server cluster — typically 3 or 5 instances for production, so the office survives even if one location is unreachable.

TermWhat it isCity equivalent
Data planeThe live network of sidecar proxies actually forwarding, encrypting, and checking trafficEvery resident's personal assistant, doing their daily job
Control planeThe Consul server cluster — source of truth for the catalog, certificates, and rulesThe assistants' head office, issuing instructions and ID cards
Connect InjectThe Consul component that automatically adds a sidecar to new podsHR, assigning a new assistant the moment a resident moves in
Mesh GatewayA proxy that sits at the edge of a cluster, routing traffic to other clustersA guard posted at the city's gate

Worth noting: the control plane doesn't even have to live in the same cluster. You can run a dedicated Kubernetes cluster purely for Consul's control plane and point several other "worker" clusters at it — one head office, many buildings, even across different cities entirely.

Scaling the analogy up

When your city needs allies — and when a "resident" lives on a VM

Real systems rarely stay inside one cluster. A company starts in one AWS region, then expands to Europe and Asia for latency reasons. Then a cloud outage costs real business, so leadership decides to replicate onto a second cloud provider entirely, as insurance. Now you have multiple clusters that all need to talk to each other securely — this is the multi-cluster, multi-datacenter problem.

Consul's answer: think of each cluster as its own city, and let cities form alliances. At the edge of each city stands a guard — the mesh gateway. If a service in City A wants to reach a service living in City B, its assistant doesn't need to know that B is a different city at all. It just hands the message to the local guard, who carries it to City B's guard, who hands it to the destination's assistant. The calling service is completely unaware that the request just crossed a cloud provider boundary.

Two independent clusters, peered through their mesh gateways. Neither service knows — or needs to know — which cloud the other one runs on.

One more real-world wrinkle the video covers well: not everything is Kubernetes. Plenty of established companies still run a company-wide database, or legacy services, directly on virtual machines — and migrating that to Kubernetes is often not worth the effort or risk. Consul treats a VM the same way it treats a pod: it's just another "house" in another "city," running a Consul client agent alongside the actual process, with its own mesh gateway at the edge. The database on a VM in an on-prem data center can be a first-class, securely-reachable member of the mesh — not a special case bolted on.

Watching it actually happen

The demo: two clusters, one dying service, zero downtime

The video backs all of this up with a real deployment, and walking through what actually happened is more useful than the theory alone. Here's the shape of it, in order:

  1. Stand up a real EKS cluster with Terraform. Nothing Consul-specific here except one detail: the worker nodes' security group needs specific ports opened so Consul's components can talk to each other, and the node role needs permission to provision EBS volumes — because the Consul server is a stateful application that needs persistent storage.
  2. Deploy an actual microservices app. The demo uses Google's open-source "Online Boutique" — a dozen-plus real services (frontend, cart, checkout, payment, recommendations, and more) talking to each other and a shared Redis cache. One service, payments, is deliberately left half-broken (missing an env var) to demonstrate how Consul surfaces a failing service later.
  3. Install Consul via its official Helm chart. The key configuration flags: connectInject.enabled=true with default=true (auto-inject a sidecar into every pod, no per-deployment annotation needed), meshGateway.enabled=true (needed later for cross-cluster traffic), and ui.enabled=true with a LoadBalancer type (a dashboard to actually see the mesh).
  4. Restart the app and watch pods go from 1/1 to 2/2 containers. The second container in each pod is the injected Envoy sidecar — Consul's "data plane." Checking its logs shows it registering its service with the control plane on startup.
  5. Open the Consul UI and see the topology. Every service shows up, along with the broken payment service — flagged as failing its health check, with its sidecar up but the application container crash-looping. Every other service can see that instantly, without ever sending it a request.
  6. Lock down the payment service with intentions. By default, every service can call every other service. The demo tightens this: only checkout-service is allowed to initiate a connection to payment-service; everything else is explicitly denied. This is configured declaratively as a small Kubernetes-native CRD (a ServiceIntentions resource) — the same "configuration as code" pattern as any other Kubernetes manifest.
  7. Stand up a second cluster on a completely different cloud (Linode Kubernetes Engine) and repeat steps 2–6 exactly, using the same Helm values, just with a different datacenter name. Same app, same Consul setup, second cloud provider.
  8. Peer the two clusters. First, both control planes are told to route peering traffic through their mesh gateways (a small Mesh CRD applied on each side). Then, from cluster A's Consul UI: generate a peering token, name the peer, done. From cluster B's UI: paste that token in as "establish peering." Both sides show the connection as active within seconds.
  9. Export one service across the peering connection. Cluster B's shipping-service gets explicitly exported to cluster A via an ExportedServices CRD — nothing is shared by default; you opt services in one at a time.
  10. Define a failover rule with a ServiceResolver. On cluster A, a small CRD says: "if the local shipping-service becomes unavailable, fail over to the peer's shipping-service instead."
  11. Kill the shipping-service pod in cluster A — and the app keeps working. Adding an item to cart, which depends on a shipping estimate, fails the moment the pod is deleted with no failover rule in place. The moment the ServiceResolver is applied and the pod is deleted again, the same action succeeds — silently served by cluster B's shipping-service, on a different cloud provider, without the frontend service or the user ever knowing anything failed over.
Why this demo is the whole point

Nothing in that failover step touched application code. No retry logic was written into the frontend service, no hardcoded fallback URL was added anywhere, and no human intervened when the pod died. The failover rule was declared once, centrally, as data — and every sidecar in the mesh enforced it consistently, immediately, and identically, regardless of which of the two clouds a request happened to be sitting in at the time.
