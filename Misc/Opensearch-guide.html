OpenSearch is a card catalog, not a filing cabinet.

A filing cabinet finds a folder because you know its label (a key). A card catalog finds every book that mentions a word — without ever knowing the book's title upfront. OpenSearch is the second kind of system, built for a world where your logs are the "books" and you rarely know their "title" in advance.

01 / First Principles

Why does search need a different structure at all?

Think about a library before computers existed. If you want the book titled "Moby Dick", you walk straight to the shelf — you know the title, so you go directly to it. That's a forward lookup: title → book. This is exactly how a normal database uses a primary key.

But what if your question is "which books mention the word whale?" You don't know which books to check — you'd have to open every single one and read it. That's unbearably slow. So libraries built a second system: the card catalog — a separate index where each card is a word, and behind it is the list of every book containing that word.

Forward index (row → content) vs. inverted index (word → rows)
Why

This is the actual reason you can search logs "by any means" — not because there's no schema, but because every word, in every field, becomes its own lookup key. OpenSearch builds one of these inverted indexes automatically, per field, for every document you feed it.

02 / Definition

What OpenSearch actually is

OpenSearch is a distributed search and analytics engine. It's an open-source fork of Elasticsearch (AWS forked it in 2021 after a licensing dispute), and both are built on top of a Java library called Apache Lucene, which does the actual inverted-index work under the hood.

You send it documents — JSON objects, like one log line or one order record — and it stores them while automatically indexing every field. You then query it using a JSON-based language called the Query DSL, or a Lucene-style query string.

It still has a schema — just an automatic one

This is the correction to your original framing: OpenSearch calls its schema a mapping (field name → data type: text, keyword, number, date...). If you don't define one, OpenSearch guesses it from the first document it sees — that's called dynamic mapping. So it's not "no schema," it's "schema inferred on write, instead of designed in advance."

03 / Internals

Anatomy of a cluster

OpenSearch never runs as a single machine in production — it runs as a cluster: a group of servers (nodes) that share the work.

Cluster → Nodes → Shards. Each index is split into shards (P = primary, R = replica) spread across nodes for scale and redundancy.
TermWhat it means
ClusterThe whole group of servers working together, identified by one cluster name.
NodeOne server in the cluster. Roles include master (coordinates) and data (stores + searches).
IndexA logical collection of documents — comparable to a "table," e.g. logs-2026.07.29.
ShardA physical, independent slice of an index. Splitting into shards is what lets a single index scale past one machine.
ReplicaA copy of a shard on another node, for fault tolerance and read throughput.
DocumentOne JSON record — e.g. one log line, indexed field by field.

05 / Mechanism

Why "no primary key needed" actually works

In a relational database, a query without an index on the filtered column means a full table scan — reading every row to check if it matches. That's why RDBMS design revolves so heavily around picking the right keys and indexes in advance.

OpenSearch flips the default: because it builds an inverted index for every field automatically (unless you turn it off), every field behaves like it's indexed. That's the entire trick — you're not getting free-form search because there's no structure; you're getting it because everything is pre-indexed for you, at ingestion time, at the cost of extra storage and slightly slower writes.

Trade-off

This is a classic engineering trade-off: OpenSearch pays the indexing cost once, on write, so that every future read is fast — the opposite bet of a system that indexes nothing and pays the cost on every read instead.

06 / Comparison

OpenSearch vs. Athena vs. a normal database

This is exactly the confusion you mentioned — and it clears up once you see what each one is actually optimized for.

Trait OpenSearch Athena RDBMS (e.g. RDS)
What it is A running cluster that continuously indexes data A serverless SQL query engine over files already in S3 A transactional database with rows and defined tables
When data is indexed Immediately, as each document is ingested Never — reads raw files each query (schema-on-read) On write, if you defined an index on that column
Best for Real-time log search, dashboards, alerting Occasional, large ad-hoc analytics over historical data Consistent transactional records (orders, users, payments)
Cost model Pay for the cluster continuously, running or not Pay per query, per data scanned — nothing when idle Pay for the instance continuously
Query language Query DSL (JSON) or Lucene syntax Standard SQL SQL
Joins across tables Weak — data is usually denormalized instead Strong — full SQL joins Strong — this is its core strength

So the practical rule of thumb: if the data must be searched right now, near-real-time, on live logs → OpenSearch. If you're running a one-off analytical question over months of archived data sitting in S3 → Athena. If you need reliable transactional records with relationships between them → a relational database.

07 / Pitfalls

Common mistakes

Mistake

Treating it as a system of record. OpenSearch doesn't give you ACID transactions the way a relational database does. Don't store your only copy of critical business data here — it's built for search and analytics, not for being the source of truth.

Mistake

Letting log indices grow forever. Since a new index is often created per day (like logs-2026.07.29), without an Index State Management (ISM) policy to roll over and delete old indices, storage and cluster load grow unbounded.

Mistake

Over-sharding. Creating far more shards than the cluster needs adds coordination overhead per query and wastes memory — a very common beginner default is too many shards "just in case."

Mistake

Expecting relational joins to perform well. The right pattern in OpenSearch is to denormalize — embed the related data directly into the document — rather than modeling normalized tables like in SQL.

08 / Recall

Summary — what to remember

  • OpenSearch is a distributed search & analytics engine built on Apache Lucene, forked from Elasticsearch by AWS.
  • Its core trick is the inverted index: word → list of documents, instead of document → its content. That's why you can search on any field without a primary key.
  • It still has a schema (a mapping) — it's just inferred automatically on write, not designed upfront.
  • A cluster is made of nodes; each index is split into shards (+ replicas) spread across those nodes for scale and redundancy.
  • Your Datadog mental model was correct: app → log shipper → OpenSearch (indexes every field) → dashboard for search.
  • OpenSearch ≠ Athena: OpenSearch is a live, continuously-indexing cluster for real-time search; Athena is a pay-per-query engine over files at rest in S3, better for occasional large analytics.
  • Don't use it as your primary transactional database, watch index growth with ISM policies, and avoid over-sharding.
