You know what 2048 and 8192 mean. Now go prove it.

Part 1 turned your ECS config into something you could reason about: CPU units, memory, workers, throttling. That knowledge is still just theory until you point real traffic at it. This part is about the four decisions that separate a load test that tells you something from one that just makes a graph go up: what kind of test to run, how to shape the traffic, what to watch while it runs, and how to read the result.

01 — PICK THE RIGHT QUESTION FIRST

Five tests, five different questions

"Load testing" isn't one thing. Each variant exists to answer a question the others can't.

The most common mistake isn't a bad test — it's the right test asking the wrong question. Running a 10-minute ramp when what you actually needed was a 6-hour soak will pass every time, right up until the memory leak that only shows up at hour four ships to production.

Smoke
Minutes · low load
Does the system work at all under light traffic? Run this before anything bigger — it catches broken deploys, not capacity problems.
Load
10–30 min · expected traffic
Does the system meet its latency and error targets at the traffic you actually expect, e.g. peak business hours?
Stress
Ramping · beyond expected
Where is the breaking point, and does the system fail gracefully (503s, backpressure) or catastrophically (OOM, cascading timeouts)?
Soak
Hours · sustained moderate load
Does anything degrade over time — memory leaks, connection pool exhaustion, disk fill-up — that a short test can't reveal?
Spike
Seconds · sudden surge
Can the system absorb a sudden jump in traffic — a marketing email, a viral post — before autoscaling catches up?
Why this matters for Part 1's numbers A smoke test will never throttle your CPU units. A stress test will, on purpose — that's the point. If you only ever run smoke and load tests, you will genuinely never see the freeze/resume behavior from Part 1 in a test environment, and the first time your team sees it will be in production.
02 — THE MOST MISUNDERSTOOD SETTING IN ANY TOOL

Closed model vs. open model

"100 virtual users" and "100 requests per second" sound similar. They are not the same test.

Locust, JMeter, and most load-testing tools default to a closed workload model: you spawn N virtual users, and each one sends a request, waits for the response, then immediately sends the next one. Real internet traffic doesn't work that way. A real user's browser doesn't know or care how long your server takes — it fires a request when the person clicks, full stop. That's an open workload model: requests arrive at a rate, independent of how fast the previous one finished.

The difference is invisible when your system is healthy and disastrous the moment it isn't. Watch what happens to each model when the server slows down:

As the server slows, each user simply waits longer between requests. Offered load quietly drops to match whatever the server can do. The test looks stable — RPS never spikes, nothing appears to break — because the tool is secretly protecting the server from the exact thing you're trying to test.
Open model — fixed arrival rate
New requests arrive on schedule, whether or not the server is ready.

0Arrival RPS
0Requests queued
As the server slows, requests keep arriving at the same rate anyway. The queue grows, visibly and measurably — which is exactly what happens to your real users while they stare at a spinner. This is the honest version of the test.
Myth "I ran 500 virtual users and RPS never went above 40, so 40 RPS must be our ceiling."
Reality In a closed model, that's just as likely to mean your users spent most of their time waiting, not that the server can't do more. You measured how patient your virtual users were, not the server's actual capacity. Locust's constant_pacing and open-model wait times exist specifically to avoid this trap.

03 — SHAPE THE TRAFFIC ON PURPOSE

Ramp patterns: the shape of the test is the test

The four test types from section 01 aren't run with the same traffic shape — the shape is how you point a tool at a specific question. Each pattern below is the same tool (Locust), configured differently.

Step ramp
Hold at a fixed user count for a few minutes, jump up, hold again. Reveals exactly which load level a metric crosses its threshold — precise, easy to correlate with a dashboard.
Linear ramp
Smooth, continuous increase from zero to a target over the whole test. Good general-purpose stress test — finds the breaking point without a specific hypothesis about where it is.
Spike
Sudden, brief jump far above baseline, then back down. Tests autoscaling reaction time and whether the system survives the gap before new tasks come online — not sustained capacity.
Soak
Quick ramp to a moderate, sustainable load, then flat for hours. The flat part is the point — it's the only shape that gives leaks and slow exhaustion time to show up.

The same shape, four ways, in Locust

Locust's LoadTestShape class controls this directly — you return the user count and spawn rate for the current elapsed time, and Locust drives the ramp for you.

step_ramp.py
from locust import LoadTestShape

class StepLoadShape(LoadTestShape):
    # (users, spawn_rate, duration_seconds) per step
    steps = [(50, 10, 180), (150, 20, 180), (300, 30, 180), (500, 30, 180)]

    def tick(self):
        run_time = self.get_run_time()
        elapsed = 0
        for users, spawn_rate, duration in self.steps:
            elapsed += duration
            if run_time < elapsed:
                return (users, spawn_rate)
        return None  # None tells Locust the test is over

Swap steps for a formula based on run_time and you get linear, spike, or soak for free — the shape is just a function of elapsed time. This is also where you plug in Part 1's numbers directly: if Little's Law said you need 300 concurrent requests to hit your target RPS, that's your top step.

04 — WHAT TO ACTUALLY WATCH

Averages lie. Percentiles don't.

If your dashboard's headline number is "average response time," it's hiding your worst users from you.

Imagine 100 requests: 95 take 40ms, 5 take 2000ms because they hit a cold cache. The average is about 137ms — a number that describes almost no actual request. Percentiles describe the distribution instead: p50 (median) is the typical request, p90 is "9 out of 10 requests are at least this fast," and p99 is the request your unluckiest users actually experience.

The average sits between the typical case and the worst case — describing neither. p99 is the only bar here that reveals the cold-cache problem exists at all.

The four numbers worth putting on one screen

p99 latency
Your worst-case-but-not-outlier experience. This is what correlates with support tickets and abandoned checkouts, not the average.
Error rate
Percentage of requests returning 5xx or timing out. A latency graph that looks fine while errors climb means requests are failing fast, not succeeding slowly.
Throughput (achieved)
From Part 1 — RPS actually completed, not offered. The gap between offered and achieved is your system telling you it's saturated.
Saturation
Part 1's CPU throttle ratio and memory headroom. This is the number that explains why the other three are moving — cause, not just symptom.
Why saturation belongs on the same screen Latency and errors tell you something is wrong. Throttle ratio and memory headroom tell you what is wrong — whether you're CPU-bound (raise cpu, add workers) or memory-bound (raise memory, check for a leak). Without it, "add more instances" is a guess.

06 — THE NUMBER YOU'RE ACTUALLY HUNTING FOR

Finding the knee

Part 1 defined throughput as what the system can sustain, not a rate you can just ask for. Plot offered load against achieved throughput across a full step ramp, and healthy capacity has a distinctive shape: a straight diagonal line, then a bend, then flat. That bend is the knee — the exact point where Part 1's scheduler starts saying no more often than yes.

The number that matters isn't wherever the line stops — that's just where you stopped the ramp. It's the RPS value directly under the knee. That's the figure you compare against Part 1's Little's Law estimate: if they're close, your sizing math was right; if the knee shows up much earlier, something you didn't account for — a slow downstream dependency, a lock, GC pauses — is eating CPU time your formula didn't know about.

07 — WHERE FIRST TESTS GO WRONG

Common mistakes in a first load test

Under-powered load generator
Running Locust from a laptop or a small instance means your test client saturates before your server does — you measure the generator's ceiling, not the system's.
Fix: run distributed Locust workers on dedicated infrastructure, and watch the generator's own CPU while testing.
Ignoring cold start
The first 30–60 seconds include connection pool warmup, JIT warmup, and cold caches. Blending that into your steady-state numbers drags your percentiles up for no real reason.
Fix: discard or clearly separate the first warmup window from steady-state stats.
Closed-model false confidence
Covered in section 02 — a closed-model test that "never breaks" often just means your virtual users patiently waited instead of revealing the real ceiling.
Fix: use an open model, or at minimum watch queued/waiting requests as its own metric.
App metrics without infra metrics
A p99 graph with no CPU or memory context tells you that something broke but not why — you're left guessing between "add instances," "add CPU," or "fix a leak."
Fix: put Part 1's throttle ratio and memory headroom on the same screen as latency, always.
CHEAT SHEET

Recap — planning your next test

  • 1
    Test type — smoke, load, stress, soak, or spike each answer a different question.
    Pick the type before the tool; the wrong type passes cleanly and tells you nothing.
  • 2
    Workload model — closed (wait for response) vs. open (fixed arrival rate).
    Closed models hide your real ceiling by quietly slowing down; open models show it as a growing queue.
  • 3
    Ramp pattern — step, linear, spike, or soak shapes the traffic to match the question.
    Locust's LoadTestShape turns elapsed time into user count and spawn rate.
  • 4
    The four metrics — p99 latency, error rate, achieved throughput, and saturation (CPU throttle ratio + memory).
    Averages hide your worst-case users; percentiles don't.
  • 5
    Read cause and effect together — latency/errors say something is wrong; throttle ratio and memory headroom say what.
    CPU-bound and memory-bound need opposite fixes — don't guess which one you have.
  • 6
    The knee — the point on an offered-vs-achieved plot where the line bends and flattens.
    That's your real capacity number — compare it against Part 1's Little's Law estimate.
  • 7
    Avoid the first-timer traps — under-powered generator, uncounted cold start, closed-model confidence, app metrics with no infra context.
    Each one produces a clean-looking graph that's quietly measuring the wrong thing.
