01 — THE FORMULA'S HIDDEN ASSUMPTION

The time budget your formula forgot

Little's Law tells you how many requests fit in flight. It says nothing about what a request spends its time doing.

Part 1 and Part 2 both leaned on a quiet assumption: that a request's service time is basically its compute time — the time a worker spends actually using CPU. That's true for a tight, CPU-bound endpoint. It's false for almost everything else. A request's real service time is a sum of parts, and only one of them shows up in "CPU Utilization: 40%."

Myth "CPU is at 40%, so we have 60% headroom left before we need to worry."
Reality CPU% measures busy-vs-idle CPU time — it has nothing to say about time a request spends waiting on a lock, a downstream call, or a garbage collector. Click "Under load" above: total time in system nearly quintuples while CPU utilization barely moves. That's the whole gap this part is about.
Revised service-time budget service_time = compute_time + lock_wait + downstream_wait + gc_pause

Little's Law — L = λW — still holds; it doesn't care what W (time in system) is made of. What breaks is any sizing estimate that quietly assumed W ≈ compute_time. The rest of this part walks through the three components most often left out, in the order they're usually cheapest to check: downstream calls first, locks second, GC third.

02 — WAITING ON SOMEONE ELSE

When the bottleneck isn't your container

Your ECS task can have CPU and memory to spare and still hit a wall — if the wall is a connection pool three services away.

Almost no service is pure compute. It calls a database, a cache, an internal API, a third-party service. Each of those calls usually goes through some kind of bounded resource — a connection pool, a rate limit, a concurrency cap on an HTTP client. Your ECS task can hold far more requests in flight than that resource can serve, so throughput plateaus at its ceiling, not your container's.

A downstream HTTP client pool capped at 5 concurrent connections. As offered load climbs past what 5 connections can drain, active connections flatline at 5 and the queue — not your CPU — is what actually grows.

There's a second-order effect that makes this worse under real conditions: retries. When a downstream call times out, most clients retry it — which adds more load onto a dependency that's already struggling, precisely when it can least afford it. A small, localized slowdown in one dependency can amplify into a full outage through nothing but well-intentioned retry logic.

Why this matters for Part 1's sizing math A benchmark that never exercises the real downstream — or that runs against a local database with an effectively unlimited connection pool — will look fine in isolation and then plateau in production. Size your downstream pools with the same seriousness Part 1 gave to CPU units and memory.
03 — WORKERS THAT CAN'T ACTUALLY RUN IN PARALLEL

Lock contention: five workers, one turnstile

Part 1 called workers "software, not hardware." A lock is what turns five workers back into one.

A mutex around a shared in-memory cache, a synchronized block, a single-writer log, a naive in-process rate limiter — anything that serializes access to a shared resource. Under light load this is invisible: contention is rare, and each worker gets the lock almost the instant it asks. Under real load, workers start queuing behind it, and your effective concurrency quietly drops even though the process still reports N workers running.

Effective parallelism right now: 1 of 5 workers actually making progress — the other 4 are parked on the same lock.

Five gunicorn/worker processes, one shared resource behind a lock. Only the current holder (green) is doing real work; everyone else (purple) is queued, burning wall-clock time without burning CPU.

Myth "We run 8 workers, so we should get roughly 8× a single worker's throughput."
Reality If those 8 workers share a global lock — a shared cache, a connection reused through a mutex, a homemade rate limiter — throughput caps near what one worker can push through the lock alone. Adding more workers adds more queued waiters, not more parallelism.
04 — THE PAUSE THAT DOESN'T SHOW UP IN CPU%

GC pauses and the stop-the-world tax

A garbage collector pause looks like nothing happened — no error, no log line, no CPU spike. It just... stopped.

Managed runtimes — the JVM, Go, .NET, Node's V8, even CPython's own collector — periodically pause application threads to reclaim memory. Minor collections are cheap and frequent; a major or full collection can pause everything for tens to hundreds of milliseconds. Averaged over a full minute, that's a rounding error in CPU utilization. But any request in flight during the pause takes a p99-sized hit, with nothing in CPU% to explain it.

CPU utilization — flat, unremarkable Request latency — spikes on every stop-the-world pause

Same window, two signals. CPU utilization barely leaves the 30–40% band; latency periodically spikes 8–10× baseline in lockstep with each full collection.

Minor / young-gen collection

Frequent, cheap, invisible

  • Runs often, usually <5ms
  • Rarely visible in p99 unless it stacks with real load
  • Not usually worth chasing
Major / full collection

Rare, expensive, exactly your knee

  • Pauses everything, often 100ms+
  • Shows up as periodic p99 spikes with flat CPU

The cleanest explanation for Part 2's teaser "p99 climbs with CPU still idle" is the GC pause signature almost verbatim. Before reaching for more CPU units, check your runtime's GC logs or pause histogram — verbose GC flags, a JVM's -Xlog:gc, or the equivalent for your runtime.
05 — READING THE SIGNATURE

Which one is it? Read the signature, not the vibes

All three culprits produce the same headline symptom — p99 climbs, throughput plateaus. They don't produce the same dashboard.

You don't need to guess. Each cause leaves a distinct fingerprint across the signals Part 2 already put on one screen, plus one or two cheap checks beyond it.

Downstream dependency
  • CPU / memory — both idle at the knee
  • Errors — timeouts or 5xx from one specific call, often clustered
  • Confirm with — connection pool metrics: active vs. waiting, or an APM trace showing time spent in an outbound call
Lock contention
  • CPU / memory — CPU often low — workers are waiting, not computing
  • Errors — usually none; just rising latency with no error at all
  • Confirm with — a thread/stack dump (jstack, py-spy) showing many threads blocked on the same lock
GC pause
  • CPU / memory — CPU flat; memory often near its limit right before each pause
  • Errors — none, but latency is periodic and correlates with heap growth, not with offered load
  • Confirm with — GC logs or a pause histogram lined up against the p99 timeline

06 — PUTTING IT TOGETHER

A worked example: the knee arrives at 38%, not 100%

Same task definition as Parts 1 and 2 — 2048 CPU units, 8192 MiB, 8 workers — run through the exact step-ramp load test Part 2 designed.

Isolating the bottleneck

1
Part 1/2's Little's Law estimate for this config, at the target p95, predicted a sustainable ≈ 120 RPS.
2
The offered-vs-achieved plot from the step ramp bends far earlier than that — the knee lands at ≈ 46 RPS, about 38% of the estimate.
3
Check Part 1's usual suspects first: CPU throttle ratio at the knee is 0%, memory headroom is 71% free. Neither CPU nor memory explains it.
4
Check the app's own metrics: an HTTP client pool to a downstream fraud-check API, capped at 5 concurrent connections, averaging 105 ms per call.
5
Pool capacity ≈ 5 ÷ 0.105s ≈ 47.6 RPS — matching the observed knee almost exactly. The downstream pool, not the container, was the ceiling.
6
Fix: raise the pool's max concurrency (confirming the downstream can absorb it) or add a cache in front of the call, then re-run the same step ramp to confirm the knee moves toward the original 120 RPS estimate.

Notice what didn't need to change: not the task definition, not the worker count, not a single CPU unit. The fix lived entirely in a setting Part 1 and Part 2 never touched — because it was never a compute problem.
