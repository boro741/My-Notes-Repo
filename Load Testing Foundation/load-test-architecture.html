Corrected from the original sketch: "CPU memory" isn't a real resource — CPU units and memory (RAM) are configured independently, so they're now siblings under one task definition instead of one flowing into the other. Workers were added — the piece that actually consumes CPU quota. Incoming RPS moved out of the system-metrics group into client/traffic signals, since it describes offered load, not server behavior — while throughput, throttle ratio, and backlog stayed with system signals, since they're effects of how the server handles that load. Arrows now show real relationships instead of just grouping boxes: requests flow from users through the application into workers, workers draw from the shared CPU quota, and both the server and the application produce their own downstream metrics. Good/watch/bad ranges were added to each metric — note none of these mean much read alone: CPU high + throttle high + latency climbing means genuinely CPU-bound; CPU low + latency climbing means the bottleneck is downstream (a slow DB, a lock, GC), not compute.
