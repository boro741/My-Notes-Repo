01

The setup: a time budget, not a task budget

The kernel manages CPU with a stopwatch, not a to‑do list. Every 100ms period, your app is handed a fixed slice of execution time — its quota, set by however many CPU units you configured. It doesn't matter what the work is; only how long it runs.

⏱️

The period

The scheduler checks in every 100 milliseconds. Each check‑in is a fresh window — your quota resets, whether or not you used it all last time.

🎟️

The quota

0.5 vCPU means 50ms of run time per 100ms period. Spend it all before the period ends, and there's nothing left to spend.

04

What the ratio tells you about your server

The live ratio from your simulation is marked below on the standard health bands. A ratio above 0% is not automatically bad — bursty traffic occasionally grazing the limit is normal and often a deliberate cost tradeoff. It becomes a real problem when it's sustained/high and shows up as user-facing latency or errors. Always read it next to CPU utilization — the ratio tells you whether the CPU is the ceiling, not just that something is slow.

0–5% healthy 5–20% moderate 20%+ severe

Low, occasional ratio (0–5%)

Normal. Traffic bursts briefly graze the limit now and then. Not a problem unless it's trending upward or you're already seeing latency/error spikes alongside it.

High ratio + CPU pinned at the quota ceiling

Genuinely CPU‑starved. Fix: raise the vCPU quota per instance (helps individual request latency) and/or add more replicas (helps overall throughput). Both are valid — quota for latency, replicas for volume.

High ratio, but the work itself looks light

Often an app/runtime problem, not a hardware one: thread pools, worker counts, or GOMAXPROCS set higher than the container's actual CPU quota cause self-inflicted contention. Fix the concurrency config or the code before adding CPU.

Low ratio + high latency

The CPU isn't the bottleneck. Workers are likely blocked on a slow database call, a lock, or garbage collection — look downstream, not at compute.

07

Guided walkthrough — build the throttle ratio intuition step by step

Four scenarios, run in order, on the live panel above. Each one has a button that sets the controls for you and scrolls you up to watch it happen — you don't need to click anything up there yourself. The goal is to see, in sequence, exactly when the ratio moves and why.

1

The healthy baseline

SETLoad = Normal, vCPU quota = 0.6 (the defaults).
WATCHThe period timeline stays almost entirely CLEAN (green tag). Throttle ratio sits near 0%. CPU usage floats well under the 60% ceiling.
WHYTraffic fits comfortably inside every period's 60ms budget, so no period ever runs out of quota. Zero periods hit the wall → 0 ÷ total = 0%. This is your reference point for "nothing is wrong."
2

Push traffic past the quota

SETLeave vCPU quota at 0.6. Switch load to Spike.
WATCHSome period boxes flip to PAUSED (red). Throttle ratio climbs into the 10–30% range. CPU usage pins right at ~60% — it stops climbing even as traffic keeps rising.
WHYThis is the core idea: once demand exceeds the period's budget, extra requests can't push CPU% any higher — the quota is a hard ceiling. Instead, they push the ratio higher, because more periods now fail the "did we run out?" check. Ratio and CPU% are measuring different things.
3

Go overload — watch the full chain, in order

SETSame 0.6 vCPU quota. Switch load to Overload.
WATCHRatio climbs fast, toward 60–90%, timeline mostly red. A beat later, backlog queue climbs. A beat after that, latency and error rate spike. Press 📸 Snapshot once things settle.
WHYNotice the order: ratio moves first — it's a direct readout of the quota math, immediate every period. Backlog builds next as unfinished work piles up. Latency and errors are last, only showing once the queue is deep enough to matter. That lag is exactly why the ratio is a leading indicator — by the time users feel it as slowness, it's already been climbing for a while.
4

Fix it with config, not less traffic

SETLeave load on Overload — don't touch it. Instead drag the vCPU quota slider up to ~1.4.
WATCHSame incoming traffic, but the ratio falls back toward 0% within a few periods. Backlog drains, latency and errors recover. Snapshot this too, then compare it against your scenario‑3 snapshot.
WHYNothing about the traffic changed — same RPS sent, same load generator. Only the CPU config changed. That's the real-world takeaway: a high throttle ratio is a budget problem, not automatically a traffic problem. The fix is usually raising the limit (or adding replicas), not asking upstream to send less.
